# 分段延迟该怎么量

> 状态：已验证
> 更新日期：2026-10-29

同一段代码在不同测法下能差 15 倍。本文记录差异来源，避免下次把测量假象当成性能回归。

---

## 1. 现象

stage0（8 层，全上卡）的耗时，四种测法四种结果：

| 测法 | 结果 |
| --- | ---: |
| `StageEngine` 同进程直连 | 3.6 ms |
| 只起一个 worker，走 socket | 4.4 ms |
| 两段链路，每步**先记时再调** stage0 | 67.8 ms |
| 两段链路，每步**只量整链** | 105.9 ms（含 stage1） |

第一种和第三种相差 19 倍，而代码路径完全一样。

## 2. 原因：上一次调用的账记到了下一次头上

`forward_token` / `forward_hidden` 是同步的请求-响应：worker 回包才算返回。但
CUDA 的计算是异步提交的，主机侧把图提交完就能回包，GPU 还在跑。

于是时间落在**下一个同步点**上：

```
第 N 步   stage0 提交图 → 立刻回包（看起来 5 ms）
第 N 步   stage1 在自己进程里算 36 ms   ← 期间 GPU 把第 N 步做完了
第 N+1 步 stage0 要读上一轮的输出 → 等 GPU → 记到这一步头上（67 ms）
```

两段链路的 loop 恰好把 stage1 的 36 ms 夹在两次 stage0 之间，所以 stage0 的计时里
多出了「等待自己上一轮结果」的时间。它是在等 GPU，不是在算。

单段测试没有这个夹层，所以看到的是真实的 3.6–4.4 ms。

## 3. 结论

- **分段计时只能用于定位「哪一段在排队」，不能直接相加当吞吐。** 各段之和大于整链
  时间是正常的，因为流水线本来就在重叠。
- **判断优化是否有效，只看整链吞吐**（每步 stage0 → stage1 → … 的总墙钟时间）。
- 定位单段真实成本时，要让它前面没有别的段，或者连续调两次取第二次。

## 4. 另一个已修正的测量错误

早期脚本推进 `n_past` 时跳号（上一次还在 10，下一次直接 21），worker 日志里出现：

```
find_slot: non-consecutive token position 21 after 10 for sequence 0 with 1 new tokens
```

llama.cpp 于是去 KV cache 里搜索空闲槽位而不是追加，比正常路径慢数倍。**热路径上跳号
测出来的数字没有意义**，n_past 必须连续。

## 5. 当前确认的数字

整链吞吐（各自单独运行，机器负载不同，不能横向比）：

| 拓扑 | 吞吐 | 备注 |
| --- | ---: | --- |
| 两段（8 + 16 层，本机） | 9.4–15.2 t/s | 区间来自背景负载差异 |
| 三段（+ ROG 16 层） | 2.5 t/s | ROG 段 p50 257 ms，占 64% |

ROG 段单跑 16 层是 10.6 ms/层，master 同样 16 层是 2.7 ms/层。换 CPU 变体只改善 15%
（haswell 7.7 对 skylakex 8.9 ms/层），**剩下的 2.8 倍差距来自 CPU 本身与共租的
qemu/npm 负载**，不是代码问题。

`qemu-system-x86_64` 在 ROG 上累计了 4145 秒 CPU 时间，那是 docker 后端。
