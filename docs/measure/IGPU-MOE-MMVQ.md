# 核显跑 MoE 的归因与 MMVQ 修复
> 面向 Qwen3.5 MoE · 基于 op 级 perf logger 与对照实验 · 产出 Intel 低比特 decode 的修复

> 状态：**实测结论（2026-11-14）**
> 平台：Intel Iris Xe（Gen12 / XE1）+ i9-13900H，Windows 专有驱动
> 相关：`docs/design/V3-IGPU-ROLE.md`（定位）、`docs/measure/IGPU-SLOWDOWN.md`（核显能不能用）、`docs/measure/L3-GEMV-NEGATIVE.md`（L3 否定）

标注约定：**[实测]** 本机带 bracket 对照测出；**[代码]** 源码读出；**[推算]** 公式算出。

---

## 1 结论

1. **MoE 在核显上输给 CPU 41%（10.28 vs 17.33 冷态），但根因不是 gather。** 同形状同量化、同一次运行内，`MUL_MAT_ID_VEC`（8 专家 gather）**6.5 GB/s** vs `MUL_MAT_VEC`（连续权重）**6.6 GB/s**，**惩罚≈0**。
2. **真正的瓶颈是 q2_K/q3_K 的 dequant 计算**：q2_K 只有 7.5 GB/s，而 q4_K 37.4、q6_K 35.2 已经贴着出口。q2_K + q3_K 吃了 **46% 的字节、66% 的时间**。
3. **根因是 kernel 选择错**：`ggml_vk_should_use_mmvq()` 的 Intel 分支注释说「!Q2/Q3/Q6 才比 fp16 差」，代码却对**所有类型** `return false`。XE2 修对了、XE1 漏了。
4. **修复后（`d43316a0d`）MoE decode 10.66 → 16.64 t/s（+56%）**，q2_K 带宽 6.5 → 33.9 GB/s（5.2×），9B dense **无回归**（7.88 vs 7.89）。
5. **Q6_K 不能一起放行**：XE1 上走 MMVQ 反而慢 17%（41.2 → 35.1 GB/s），会让 9B dense 掉 5.8%。
6. **每 token 实际读 1.46–1.49 GB**，不是早期估的 2.14 GB。所以效率是 **CPU 70% / iGPU 38%**——**两边都没跑满**。

| 9B Q4_K @ CPU `-ngl 0 -t 8` | 37.38 | 7.26 | |
| 35B-A3B Q2_K @ iGPU（修复前） | 69.09 | **10.28** | |

## 3 归因过程（D 实验）

用 `GGML_VK_PERF_LOGGER=1` 拿 op 级时间，按 op 反推带宽。MoE 每 token 122.98 ms 的分解：

| 类型 | 时间占比 | 字节 | 带宽 |
|---|---:|---:|---:|
| **q2_K** | **51.1%** | 472.7 MB | **7.5 GB/s** |
| **q3_K** | **14.8%** | 198.2 MB | **10.9 GB/s** |
| q6_K | 9.6% | 417.2 MB | 35.2 GB/s |
| q4_K | 6.3% | 289 MB | 37.4 GB/s |
| f32 | 2.2% | 84 MB | 30.9 GB/s |

**gather 惩罚的对照**（同形状、同量化、同一次运行内）：

| 形状 | `MUL_MAT_ID_VEC`（gather） | `MUL_MAT_VEC`（连续） |
|---|---|---|
| q2_K m=512 k=2048 | **6.5 GB/s** | **6.6 GB/s** |
| q3_K m=2048 k=512 | **11.2 GB/s** | 6.5 GB/s |

**第二行里 gather 反而快 1.7×**——8 个专家提供了更多工作组并行度。所以「gather 把顺序读打散」这个解释是错的。

**同形状跨量化的对照**（m=8192 k=2048）：q2_K **10.9** vs q4_K **38.0 GB/s**（3.5×），而 q2_K 读的字节**更少**、FLOP 相同——**是 dequant 计算受限，不是访存**。

## 4 根因与修复

**[代码]** `ggml/src/ggml-vulkan/ggml-vulkan.cpp` 的 `ggml_vk_should_use_mmvq()`：

```cpp
case VK_VENDOR_ID_INTEL:
    if (device->architecture == vk_device_architecture::INTEL_XE2) {
        if (Q2_0 || Q2_K || Q3_K || Q6_K) return true;   // ← 只有 XE2 走这里
    }

    if (device->driver_id == vk::DriverId::eIntelProprietaryWindows) {
        // MMVQ performance for !Q2/Q3/Q6 is worse than fp16     ← 注释说 Q2/Q3/Q6 是好的
        return false;                                            ← 但无条件否掉全部
    }
```

**注释和实现直接矛盾**。XE2 那个分支写对了，**只是没推广到 XE1**——Iris Xe 是 XE1，吃不到特判，于是 decode 全部走非 MMVQ 的 dequant shader。

**修复（`d43316a0d`）**：把 Q2/Q3 的例外提到 driver 判断之前、去掉架构限制；Q6_K 维持原逻辑（XE2 上仍走 MMVQ，XE1 上不走）。

**验证（带 bracket 的同窗口 A/B）**：

| op | 修复前 | 修复后 | 加速 |
|---|---|---|---|
| `MUL_MAT_ID_VEC q2_K m=512 n=8 k=2048` | 34044 us / 6.5 GB/s | **6490 us / 33.9 GB/s** | **5.2×** |
| q2_K 合计 | 62811 us / 7.5 GB/s | **15492 us / 30.5 GB/s** | 4.1× |
| 整图 median | 122.98 ms | **62.47 ms** | 1.97× |
| MoE tg128 | 10.66 | **16.64** | **+56%** |
| 9B dense tg128 | 7.89 | 7.88 | 无回归 |

**正确性**：同一 prompt、`--temp 0`，修复后与 `GGML_VK_FORCE_MMVQ=1` 的输出**逐字节相同**（两者走同一条 MMVQ 路径）；与修复前不同是预期的（q2_K 换了 kernel，浮点累加顺序变了），文本连贯无乱码。

## 5 每 token 字节数的修正

早期用「CPU 出口 37.0 GB/s 反推」得到 2.14 GB/token。**这个数偏大**，两条独立路径都指向 1.46–1.49：

- **gguf 张量级**：非专家 699 MB + output 417 MB + 8/256 专家 373 MB = **1.490 GB**
- **op 级累加**：**1.461 GB**
- 两者差 1.9%，正好是 nextn 层

**方法自检**：同一方法算 9B dense 得 5.093 GB vs 上游给定 5.098 GB，差 0.1%。

**所以效率要改写**：

| | 早期说法 | 修正后 |
|---|---|---|
| CPU 跑 MoE | 100% | **70%** |
| iGPU 跑 MoE | 55% | **38%** |

**两边都没跑满**——之前「CPU 跑满出口」的说法作废。这也解释了为什么 MMVQ 修复只对 Q2/Q3 有效：q4_K/q6_K 本来就贴着出口，没空间。

## 6 MTP 的收益公式（副产品）

**[实测]** MTP 的收益不是常数，由 `forward_ms` 决定：

```
收益倍数 = forward_ms × mean_len / (forward_ms + draft_ms)
```

其中 **`draft_ms` ≈ 78–91 ms，与设备无关**（iGPU 88.5、CPU 90.8 / 77.5）——就是跑一遍 nextn 层的固定成本。

| 设备 | forward_ms | mean_len | 公式 | 实测 |
|---|---:|---:|---:|---:|
| iGPU MoE | 97.3 | 2.14 | 1.118 | **1.112** ✓ |
| CPU MoE 冷态 | 57.7 | 2.27 | 0.88（亏） | — |
| CPU MoE 热态 | 71.0 | 2.27 | 1.086 | **1.076** ✓ |

**临界点 `forward_ms ≈ 75 ms`（约 13 t/s）**：比它快的设备上 MTP 亏，比它慢的才赚。这解释了为什么同一个 MTP 在 iGPU（10.3 t/s）赚 11%、CPU 冷态（17.3）亏 12%、CPU 热态（14.1）又小赚 7%。

**所以 iGPU 的 MTP 收益是「因为它慢」的副产品**，MTP 后 11.43 仍低于 CPU 热态无 MTP 的 14.09。

## 7 对「核显可用」的含义

**MoE 上核显接近 CPU 冷态（16.64 vs 17.33，输 4%）、超过热态（14.09，赢 18%）**，但前提是用 Q2 换装得下——15.82 GiB 只装得下 Q2/Q3 的 12.67 GiB，Q4 的 22.66 GB 装不下。**质量和容量是硬交换。**

**这不是「核显能替代 CPU」，而是「在低比特 MoE 上核显和 CPU 打平」**。真正的数量级优势仍然只在 prefill（2.51×），原因见 `docs/design/V3-IGPU-ROLE.md` §2 的算术强度分析。

## 8 方法论（这一轮踩过的坑）

1. **测量任务必须独占**。四个 agent 并发时，同一条命令的 pp512 测出 44.51，空闲时 93.78——**差 2.1 倍**。所有早期「核显不行」的数字都出自那个窗口。
2. **单点数字不采信**。同一配置连测 5 次可能 7.99→6.91（−13.5%），必须带同窗口 bracket。
3. **用对照实验而不是推理推翻假设**。「gather 慢」这个解释看起来很合理（8/256 专家、离散地址），但同形状对照一测就是 6.5 vs 6.6 GB/s。**今天最有价值的三个结论都是推翻，不是优化。**
4. **perf logger 的 op 级数据比端到端 t/s 有信息量**。端到端只能说「慢了」，op 级能说「慢在 q2_K 的 dequant」。

## 9 未做

- **Gen11（Surface）上 MMVQ 对 Q2/Q3 是否同样受益未验证**。`d43316a0d` 对所有 Intel 放行 Q2/Q3，若 Gen11 上更慢即为回归。
- **Q2_0 未实测**（与 Q2_K 同族放行，两个测试模型都不含它）。
- **XE2 上的 Q6_K 行为**未验证（修复保留了原行为，但本机无 XE2）。
- **IQ3_XXS 未测**（量化需 25 分钟；MoE 结论已由 Q2_K 给出）。
