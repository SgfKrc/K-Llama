# 指标索引：同一个数的所有版本与口径

> 状态：**现行**
> 更新日期：2026-11-12
> 适用范围：**查数时先看这里**。同一指标在本仓库出现过多个值，绝大多数不是「谁写错了」，而是**口径不同**——
> 但以前没有一处把它们并列，所以看起来像自相矛盾。这张表就是那个并列。
>
> 用法：写文档引用某个数时，**从「现行值」列取，并把口径一起抄过去**。历史值只用于对照，不能当现行值用。

## 为什么需要这张表

2026-11-12 的一次数据审查在 `docs/` 里找出 **31 条矛盾**（P0 15 / P1 10 / P2 6）。逐条看下去，根因几乎都是同一个：
**每个数字都对，但每个数字都缺了口径标签**，而不同口径的值被并列引用。

三个典型：

- **三段链 tok/s** 有四个值（9.09 / 6.53 / 6.94 / 5.85），差异来自**线程数（14 vs 8）、切分（三套）、prompt 长度（941 vs 1522）**
- **35B 权重** 有四个值（21.11 / 21.87 / 20.82 / 21.10），差异来自**三个不同的 GGUF 文件**
- **跨机投机收益** 有 +17% 和 +51%，差异来自 **prompt 长度（1522 vs 941）导致的接受率差**

**没有一张表的时候，这些值散落在 9 篇 measure + 6 篇 report + 6 篇 deploy 里**，读者无法判断哪个是现行值。

## 七、引用纪律

1. **抄数必须抄口径**。至少带四样：拓扑（切分）、prompt 长度、线程数、版本。缺一样，这个数就不可复算。
2. **`-t`（线程数）是必填**。2026-11-12 实测：同一个三段链，`-t 14` 是 9.09 t/s、`-t 8` 是 5.85——**差 55%**，
   而 decode 是 M=1 的单行 GEMV，完全吃线程数。
3. **`cache_prompt` 是必填**。默认 `true` 时第 2/3 次请求会命中 prefix cache（`prompt_n` 从 941 掉到 4），
   `prompt_ms` 从 30 s 掉到 0.33 s。量 prefill 必须 `cache_prompt: false`。
4. **`client_host` 是必填**。「两段 153.4 ms」客户端在 Y700、「三段 201.7 ms」客户端在本机——两个数**不可比**，
   相减出来的「31%」没有意义（同口径下是 21.6%）。
5. **单次跨机测量不可信**。Surface + DSpark 同一配置在不同时刻量到过 2.27 / 7.54 / 11.30 / 12.36，而接受率逐位相同
   （0.93182）。跨机数字**必须多跑取中位**。
6. **版本标签不能省**。「33–35 ms」是 v2 的，v2.1 是 10–20 ms——差 2–3 倍，混用会直接算错段数成本。
7. **远端状态是必填**。跨机数字不只依赖本机，还依赖对端是否空闲、可用内存多少、Tailscale 走 direct 还是 DERP。
   2026-11-11 的三段链量到过 9.09 t/s，2026-11-12 同配置复测只有 5.85–6.29，而 `prompt_ms` 几乎一样（31.2 s vs 32.3 s）、
   只有 decode 差 52%——**prefill 一致、decode 差一半，只能是对端状态或网络路径不同**。所以记录里要写
   「对端空闲 / 内存可用 / direct|relay」，否则这个数一周后又是一笔糊涂账。

## 八、跨机延迟不能用线性模型外推（2026-11-12 实测）

给仿真器标定 `T = L·c + f` 时，**35B 上这个形式不成立**。三条独立证据：

| 证据 | 数据 |
| --- | --- |
| **`f` 解出来是负的** | 最小二乘：`c_L=638.2 ms`、`c_F=355.5 ms`、**`f=−300.5 ms`**，RMS 125.1 ms |
| **最小切分残差大** | `0:4` 预测 1969 ms vs 实测 1748 ms，**+12.7%**；其余七点都在 ±2.5% 内 |
| **端到端比模型高 29–34%** | `QLH_STAGE_TIMING` 实测 head `0:32` ≈ 23899 ms，模型算 17861 ms |

**物理原因**：每层边际成本随层数**递增**（`0:4` 是 437 ms/层，`0:32` 是 555 ms/层，涨 27%）——固定开销被摊薄。
按「T = L·c + f」拟合会把这个效应塞进**负的 f**。

**`c_L` 与 `c_F` 无法分离**：`0:4/0:5/0:6` 的 `nF` 恒为 1，`c_F` 与 `f` 的系数列完全相同，
**3×3 矩阵奇异**。硬解只能得到互相矛盾的 `c_L` 相邻差（717 / 846 / 782 ms）。而且解出的
`c_F=355` 比 `c_L=638` 还小——full attention 比 linear 便宜，物理上荒谬。

**建议的模型形式**：

```
T_seg = n_layer · c_avg(m) + f(m, seg_type)
```

- `c_avg = (3c_L + c_F)/4` = **554–568 ms/层**（本机，`-t 8`，`llama-bench` 随机 token 口径）
- `f` **按段型分别标定**：head ≈ **5.7 s**，tail ≈ **1.3 s**（不是全局常数）
- **不要**试图分离 `c_L`/`c_F`

**测法上的三个坑**：

1. **单段 `0:N` 在 `llama-server` 上全部起不来**——`common/common.cpp:1331` 的截断检查拒绝任何
   `range_hi != n_layer_src` 且无 tail/remote 的配置。只能用 `llama-bench` + `LLAMA_LAYER_RANGE=0:N`
   （loader 的 fallback，不走 `common_init_from_params`）。
2. **`llama-bench` 的 prompt 是随机 token**（`std::rand()%n_vocab`），不是 `sp_prompt.json` 的真实 prompt
   ——**所以 P1 的 prefill 数不能和 P0 的直接比**。
3. **`0:1/0:2/0:3` 崩溃**（`GGML_ASSERT(buffer) failed`）——范围里没有 full-attention 层
   （`i=3` 是第一个 F），recurrent/attention 相关 buffer 缺失。
