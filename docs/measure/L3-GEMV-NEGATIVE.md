# L3 decode GEMV 的实测否定，以及设计前提的重新审视

> 状态：**L3 已实测否定（2026-11-14）**
> 对应设计：`docs/design/IGPU-DECODE-KERNEL.md`
> 适用范围：Intel Gen12（Iris Xe）+ Windows + Vulkan 驱动 IGC 101.6790

标注约定：**[实测]** 本轮真跑出来的数；**[代码]** 从源码读出；**[推算]** 公式算出，假设写在旁边；**[未定因]** 有对照实验但没锁定单一原因。

---

## 1 结论

**L3 独立 kernel 在这个平台组合上不成立。** 四条验收判据：判据 1 不达标、判据 2 反向（慢 1.7~2 倍）、判据 3 不达标（−28%）、判据 4 达标。

但比「L3 不行」更重要的是：**L3 的两个基础假设都错了，而且第一个在 L1 落地时就已经倒了**。

| 设计假设 | 何时被推翻 | 证据 |
|---|---|---|
| ① in-flight 不足是 decode GEMV 的主因 | **L1 落地时**（`6e5e95c7b`） | 双缓冲预取把 in-flight 提到 2 倍，tg 只 +1.4%（7.24 → 7.34） |
| ② 减活跃变量 → ≤64 GRF → 2 warp/EU → 计算与 load 重叠 | **本轮** | 源码层面能减到 48 GRF（剥离版），但 IGC 立刻把省下的寄存器换回 ILP，实测 kernel 仍是 112~128 GRF、1 warp/EU |

假设 ① 被推翻时，L3 的收益机制其实已经失去落脚点——「2 warp/EU 的价值」全部来自「让计算与 load 重叠」，而重叠能省的上限是计算占比本身：**108.5 us / 687.5 us = 15.8%**（§2.2）。在 in-flight 已经够用的前提下，这 15.8% 是 L3 唯一能碰到的天花板，而它还要先付出 prepack 的代价。

**教训**：L1 的 +1.4% 当时被读成「L1 不够深」，正确的读法应该是「in-flight 已经不是瓶颈，这条路上没有肉」。设计文档 §3.5 在 L1 之后仍然保留 +10~15% 的预期，是把一个已被反证的前提继续当了基础。

## 2 四条判据的实测

### 2.1 判据 1：GRF ≤ 64 —— 不达标

**[实测]** 用 `verify/tools/grf`（本轮新建，见 §7）从 `vkGetPipelineCacheData` 的 blob 里抽 Gen12 ISA 数出来：

| kernel | GRF/thread | warps/EU |
|---|---|---|
| 对照 `mul_mat_vec_q4_k.comp`（stock） | **112** | 1 |
| L3（`NUM_ROWS=2`，初版） | **112** | 1 |
| L3（`NUM_ROWS=1`） | 128 | 1 |
| L3（+ `[[dont_unroll]]`，bg 与 k 都加） | 128 | 1 |
| L3（强制 `[[unroll]]`） | 128 | 1 |
| L3（chunk 数从 push constant 传，IGC 无法证明常量） | 128 | 1 |
| L3（`local_size 64`、4 subgroup 各一行，最终版） | 128 | 1 |
| **剥离版**（每迭代只 1 条 b load + 1 个 dot，无 scale 项） | **48** | **2** |
| 剥离版 + scale 项 | 72 | 1 |

**结论：源码层面确实能减（48 证明），但 IGC 不让你减。** `[[dont_unroll]]` 和「运行期循环边界」两条路在 IGC 101.6790 上**实测均被忽略**——ISA 里始终是 4 条背靠背 16 B load。

### 2.2 判据 2：单 kernel ≤600 us —— 反向

**[实测]** perf logger 稳定态（第 3 个打印块，`-n 16`）：

| 算子 | stock | L3 初版 | L3 最终版（wg64） | 走 L3 |
|---|---|---|---|---|
| `m=4096 n=1 k=12288`（**判据目标**） | **625.0 us** | 602.3（未走） | **1197.2** | 仅最终版 |
| `m=12288 k=4096` | 607.5 | 1288.6 | **1098.4** | 是 |
| `m=8192 k=4096` | 354.6 | 739.8 | **693.1** | 是 |
| `m=4096 k=4096`（plain） | 240.5 | 475.3 | **443.3** | 是 |
| `m=1024 k=4096`（m<2048，不触发） | 54.4 | 56.8 | 56.3 | 否 ✓ |

走 L3 的算子带宽 **23 GB/s**，stock 是 **39~53 GB/s**。

**判据 2 本身有口径问题**：9B 模型的 perf log 里 `q4_K m=4096 n=1 k=12288` **只以 `MUL_MAT_ADD + MUL_MAT_VEC` 融合形式出现**（16 次采样无 unfused 条目）。所以设计文档 §3.1 的 687.5 us 实际是**融合后**的算子，而 §3.3 的骨架没有 bias 融合——照抄骨架实现，根本跑不到判据点名的那个算子上。最终版补了 bias 融合才真正走进去。

### 2.3 判据 3：tg ≥7.96 —— 不达标

**[实测]** `-t 8 -n 128 -r 5`，三轮交替：

| | round 1 | round 2 | round 3 | 中位数 |
|---|---|---|---|---|
| stock | 7.88 | 7.92 | 7.92 | **7.92 t/s** |
| L3 | 5.63 | 5.68 | 5.69 | **5.68 t/s（−28%）** |

**注意基线已经变了**：本机当前 stock 是 **7.92**，不是设计文档 §2 的 7.24（+9.4%，[未定因]）。所以判据 3 实际只需 +0.5% 即可通过——L3 却是 −28%。

### 2.4 判据 4：logits 相对误差 ≤1e-5 —— 达标

**[实测]** `llama-debug --save-logits`，单 token prompt（`n_tokens: 1`，确认是 decode 步、确实走 L3），248320 个 logits 逐元素比：

- `max|a| = 12.7987`，`max|a−b| = 7.53e-05` → **max|a−b| / max|a| = 5.89e-06 ✓**
- **rel RMS = 2.79e-06 ✓**
- 逐元素最大相对误差 0.32，出现在 `|a| ≈ 1e-8` 的近零 logits（任何累加顺序变化都会这样）；`|a|>1` 上最大相对误差 5.48e-05，`|a|>0.1` 上 4.79e-04

另有 CPU 布局对拍：参考实现用 ggml 的 `dequantize_row_q4_K`，被测侧用 GLSL 的**逐字转写**（两份独立实现，避免共用错误假设），并故意把 min 高 2 位的 bug 塞回去验证**会报错**。元素覆盖 256/256 恰好一次。

**判据 4 通过说明 L3 的语义是对的**——错的不是实现，是方向。

## 3 根因：IGC 把省下的寄存器立刻换回 ILP

**[实测 + ISA 级证据]** L3（`NUM_ROWS=2` 初版）的 632 条指令里有 4 个结构相同的 91 条指令大块，每块开头是：

```
L110: send.dc1 (16|M0)  r6   r96  ...   // 地址 +0   B
L112: send.dc1 (16|M0)  r16  r14  ...   // 地址 +16  B
L114: send.dc1 (16|M0)  r26  r24  ...   // 地址 +128 B
L116: send.dc1 (16|M0)  r36  r34  ...   // 地址 +144 B
```

偏移 0/16/128/144 B 正好是源码 `k=0..3` 的 `off = eb + 4k`（k<2）与 `eb + 32 + 4(k−2)`（k≥2）乘 4 字节。四条 load 目标各占 8 GRF（`rd:8` = 16 B × SIMD16），**r6–r43 共 32 GRF 同时 in flight**。

所以：源码「每轮只留 1 个 b-vec4 + 1 个 nibble-vec4」的意图确实做到了，但 IGC 用省下的寄存器做了 4 路 load 并行。**这不是跨 `bg` 迭代的软件流水**（块间有 fence，bg 之间不重叠），纯粹是 `k` 维度展开。

对照组 stock 的 112 是另一条路径：它本来就有 45~60 个显式活跃变量加 `pf_qs[2][2][2]` 预取数组，展开后到 112。**两者终点相同，来路不同**——stock 是「本来就多，展开后更多」，L3 是「本来少，展开后变多」。

## 4 两个归因假设都被对照实验否掉

判据 2 的「慢 1.7~2 倍」试了两个解释，都不成立：

| 假设 | 实验 | 结果 |
|---|---|---|
| SCM 的「16 lane × 16 B 同址」不是合并访问，把 144 B 放大到 ~384 B（2.7×） | 改成 4 个 u32/块、lane group g 读第 g 个 word（天然合并）+ dm 拆成独立 uniform load | **没有变快**（1288 → 1098 只是 wg 结构带来的 15%），假设不成立 |
| L3 把 wg 从 64 降到 16，砍掉 4× 的 warp 内并行 | 改成 `local_size 64`、4 个 subgroup 各处理一行（仍零 barrier） | **仍慢 1.8 倍**，也不是主因 |

**[未定因]** 剩下的最可能解释：**每元素指令数没省**（L3 22.75 vs stock 22.6 指令/元素）**而每线程工作量涨了 3.6 倍**（stock 每 subgroup 只处理 `num_blocks/4` 个 superblock，L3 串行处理全部），在 1 warp/EU 的占用率下暴露成 ~2 倍。没有继续深挖，因为它是判据 1 的下游——判据 1 已经把 L3 否了。

## 5 重新审视：那 19% 的差距到底在哪

**[实测]** 当前 39.6 GB/s 对纯读上限 48.9 GB/s = **81%**。设计文档把剩下的 19% 归给「in-flight 不足」，L1 证明不是。那它是什么？下面三条按可验证性排序，**都还没有实测**。

1. **sector 对齐浪费（最具体）**。Q4_K block 是 144 B，起始地址是 `block_idx × 144`，不是 32 B 的整数倍。[推算] 起始偏移在 0~31 B 均匀分布时，144 B 平均跨 `(144 + 15.5)/32 = 4.98` 个 32 B sector，即实际读 **160 B 取 144 B，浪费 11%**。48.9 GB/s × (144/160) = **44.0 GB/s**，正好把 39.6 的解释力推高一大截。**修法是让 prepack 后的每块对齐到 32 B 的整数倍（128 B 或 160 B），而不是 L3 那种「重排成 lane-major」。**
2. **`send.dc1` 走 L1 data cache 的 miss 代价**。ISA 里 load 是 `send.dc1 ... untyped surface read`，走 data cache 1。权重每 token 只读一遍，命中率≈0，每次都是 miss。[未实测] 这条路径的 miss 代价是否高于 direct global load（`send.ugm`），不知道。
3. **CPU 侧 9.5 ms/token（占 6.9%）—— 归因已排除读回**。原以为其中 logits 读回占 4.8 ms（按 607 KB @ ~100 MiB/s 推），**实测否定**：decode 的 logits 走 `get_tensor_async` → `ggml_vk_buffer_read_2d_async`，**不经过** `ggml_vk_buffer_host_read_direct()` 的判据；Iris Xe 的 `support_async = true`，该路径本身已是 GPU copy → cached staging → memcpy。把判据换成上游 #32024 的「只排除 NVIDIA」后（`415ac0096`），同步路径读回从 **3.92 ms 降到 1.36 ms（−65%）**，但 **tg 完全不动（7.947 → 7.953 t/s）**。所以 9.5 ms 的构成仍未查清，读回不是它。

**方向建议（未验证，供决策）**：优先顺序应该是 **1 → 2 → 9.5 ms 的构成**。1 有 11% 的算术支撑，且不改变 kernel 结构（只改数据布局的对齐，保留 stock 的 4-subgroup 并行度）；2 需要工具才能证伪；读回这条已被实测排除，不要再往那里投入。

## 6 对设计文档的修正

`docs/design/IGPU-DECODE-KERNEL.md` 有三处硬伤，本轮已修：

1. **§3.2 字节账**：`2×128 + 2×16 = 288 B` 里那个 288 已经等于 `2×144`（含 dm），漏算了 dm。按 `uint16` 存 scm 实际是 **296 B（+2.78%）**；要真做到零膨胀必须把 8 个 12-bit 打进 12 B 或并入同一 16 B 记录。
2. **§3.3 缺 bias 融合**，而判据点名的算子恰好是融合算子（见 §2.2）。
3. **§3.3 lane↔元素映射**：低/高 4 位对应的元素相距 **32** 不是 16（`dequantize_row_q4_K`，`ggml-quants.c:1551-1559`），骨架里的 `hi0` 配 `b1`、`g*32 + h*16` 都是按 16 写的，会让 prepack 布局整体失效且整模上只表现为「logits 全错」。

```bash
# 构建（必须先 vcvars64；改过 .h 要 touch 所有包含它的 .cpp）
cmd //c "H:\llamacpp-c\.qlh_tmp\l3\build_l3.bat"

# 判据 1：GRF（不需要 igc-probe，见 verify/tools/grf）
bash verify/tools/grf/grf.sh mul_mat_vec_q4_k_l3.comp 16 1 1

# 判据 2 / 3 / 4
bash .qlh_tmp/l3/perf_kernel.sh 1 l3      # perf logger
bash .qlh_tmp/l3/bench2.sh 1 l3           # tg128 ×3 轮
```

L3 全部改动默认关闭：`GGML_VK_L3_GEMV` 未设置时连两条 pipeline 都不注册，默认路径与改动前逐字节一致（stock tg 7.88/7.92/7.92 可复现）。改动本身**未提交**，存档在 `.qlh_tmp/l3/l3-rejected.patch` + 两个 `.comp` 原件。

## 8 未做

- **`send.dc1` vs `send.ugm` 的代价没测**。
- **判据 2 的「慢 2 倍」未定因**（§4），只在判据 1 的框架下被当作下游。
- **stock 基线 7.24 → 7.92 的 +9.4% 未归因**，与设计文档 §5 记的「6.31 → 7.24 的 14% 未归因」是两笔独立的账。
