# 重构供给与部署 R3

> 状态：**现行**（R3软件门完成）
> 更新日期：2026-10-18
> 适用范围：`REFACTOR-DEPLOYMENT-01` 的模型操作、供给、部署发布、持久命令、清理债务及模型控制恢复域。接力执行器和本地 runtime owner 的交付见[R4接力执行](重构接力执行-R4-2026-10-18.md)，客户端裁撤与设备验收分别属于 R5、R6。

## 1. 持久 owner 与提交语义

[deployment.py](../src/qlh_core/control/deployment.py)`DeploymentService`拥有 operation、selected 指针、supply、deployment、active 指针、command outbox、runtime cleanup 及登记失败工件债务。[model_control_repository.py](../src/qlh_core/adapters/model_control_repository.py)`SqliteModelControlRepository.transact`在一个 SQLite 事务中保存聚合 revision 与独立 hash-chain 事件；`read`和`recovery_status`分别提供只读快照和完整链校验。组合入口为[model_control.py](../src/qlh_core/bootstrap/model_control.py)`build_model_control`，连接端口绑定所属 runtime 的 store。

恢复域为[deployment合同](../src/qlh_core/contracts/deployment.py)`MODEL_CONTROL_DOMAIN = "model-control:v1"`，提交范围明确为`local_sqlite`。当前模型控制日志的复制能力限于本地耐久提交；跨主多数提交仍需独立复制及接管验收。[cluster_auto_role_runtime.py](../src/cluster_auto_role_runtime.py)`JournalPrefixAuthority`从 voter ledger 读取持久 floors，提议覆盖已承诺域并校验模型控制链；读失败、缺域、倒退或分叉均拒绝续期／接管。

`DeploymentService.start`只在所属 boot 首次启动时执行恢复：清空 active 指针，未完成操作／供给产生具名失败，旧 prepare／commit 命令转为 superseded，保留清理义务。历史 ready 保持操作结果，当前可执行性由同 boot、authority、connection、输入版本和真实回执另行判断。新 boot 取得控制后，旧 owner 的供给、操作和部署写入受到围栏约束。

## 2. 选择、供给与自动重规划

[model_supply.py](../src/model_supply.py)`ModelSupplyCoordinator.accept`先耐久接受供给与用户 operation、selected 指针，再发布进程内工作记录和启动后台线程。首次接受的幂等键在同一 SQLite 写事务中核对；不同 owner 竞争相同键只产生一项 supply／operation。相同键绑定其他 intent 时返回`INTENT_IDEMPOTENCY_CONFLICT`。

[model_intent.py](../src/model_intent.py)`ModelIntentCoordinator.create`串行执行退休、供给和 prepare 准入。同一未完成 intent 返回当前操作；新选择使旧未完成操作成为 superseded 并撤销候选，历史 ready 结果继续保留。operation 与 supply 的查询优先读取同一持久 owner 快照；`revision/boot_id/commit_scope/durable/runnable`也出现在等待、取消和失败投影中。查询保持只读，缓存只承载工作进度。

容量不足且采用自动节点池时，`_extend_auto_inventory`同时等待新节点完成 REGISTER／hello，并周期性重采已有节点的 inventory。RAM、VRAM、引擎和工件库存变化可在原 operation 内触发重算；供给计划发布到 building 后冻结参与集合。`_advance/_wait_for_replan`对 prepare 连接／能力／输入变更保留原因，等待精确清理完成后复用已验证工件并创建新候选，持续遵守原 absolute deadline、取消和模式围栏。供给阶段已经终止的传输通过显式重试创建新操作，旧 receiver 的终局身份继续有效。

## 3. 冻结规格与发布协议

[load_spec.py](../src/qlh_core/planning/load_spec.py)`assignment_load_spec`从准入结果冻结 device、dtype、quant、context、KV、组件和物化方式。[worker_prepare_coordinator.py](../src/worker_prepare_coordinator.py)`_build_worker_prepare_assignment`将 spec digest 绑定 assignment，`_send_pipeline_worker_config`仅投递已提交 outbox 授权的 prepare／commit，重发仍保留相同命令身份。实际发送次数和结果由`DeploymentService.note_delivery`记录。

每个新 assignment 的成功回执携带实际`load_spec/materialized_bytes/memory_scope/layer_range/artifact_sha256`。`require_runtime_receipt`核对完整冻结策略、精确工件与层段，并检查物化字节和 KV 预算；prepare／commit 回执分别满足对应状态转换。PC 的[EngineHost](../src/inference_service/engine_host.py)`_build_supplied_layer_manager`将明确策略传给实际 loader，无 spec 的兼容路径使用固定 FP32 策略，避免读取可变本机 quant。

本地首段由[model_host.py](../src/model_host.py)`freeze_pipeline_candidate_assignment/materialize_pipeline_candidate`在 native 工作前冻结身份，加载后经[runtime_observation.py](../src/qlh_core/adapters/runtime_observation.py)`observe_runtime`观测真实张量或 native runtime。PyTorch 的[ModelManager](../src/model_module.py)`load_layer_range`执行明确 device／dtype；GGUF 的[LlamaCppEngine](../src/llama_engine.py)`load_layer_range/deployment_materialization_observation`将权重与 KV 放在 keep-head runner，[LlamaVocabulary](../src/qlh_core/adapters/llama_vocabulary.py)使用`vocab_only`句柄提供分词，保持唯一权重物化。

[scheduler_pipeline.py](../src/scheduler_pipeline.py)`_save_model_control_lifecycle/_commit_pipeline_load_transaction`在本地提交和最终 reshard 发布前重验 authority、Catalog／capability 输入、冻结的 resource 预算、本地及远端实际回执。`DeploymentService.save_execution`执行冻结 assignment 与合法状态转换检查，收齐精确 committed 回执后在同一事务内设置 active 指针及 operation ready。输入变化、旧 ACK、磁盘失败及已取消／超时操作均关闭发布准入。

Android 的[WorkerPrepareContract.kt](../android/app/src/main/java/com/qlh/inference/worker/WorkerPrepareContract.kt)、[WorkerPrepareController.kt](../android/app/src/main/java/com/qlh/inference/worker/WorkerPrepareController.kt)和[TaskWorkerProtocol.kt](../android/app/src/main/java/com/qlh/inference/worker/TaskWorkerProtocol.kt)保持相同 spec、digest 与实际回执合同；spec 版本只接受整数 1，组件重复、context／device 漂移和缺少实际回执均具名拒绝。JNI 与 PC shim 提供实际物化字节及 context／batch 观测入口。

## 4. 清理与磁盘失败

runtime cleanup 与 operation 终局分别保存。`DeploymentService.save_execution`将清理债务与命令原子提交，空 ledger 投影保留既有债务；`settle_cleanup`只接受匹配旧 assignment／action 的释放回执，或绑定旧 process boot、PID、创建时间的独立结束证据。`_load_pipeline_recovery_state/_dispatch_pipeline_model_cleanup`跨重启保留本地和远端债务，同一进程新建 Scheduler 后继续等待真实释放证据。离线节点债务在重连后重发。

操作终局落盘失败时，`fence_operation_failure`在 owner 内保留发布围栏，查询明确返回`durable=False, commit_scope="volatile_failure"`；显式重试落盘成功后解除该围栏。GET 持续呈现状态，保存重试只由显式命令触发。

登记失败入口经[model_download_jobs.py](../src/model_download_jobs.py)`retain_unregistered_publication`保留位置及文件 stamp 证据，债务由 owner 耐久保存。[publication_cleanup.py](../src/qlh_core/adapters/publication_cleanup.py)`PublicationReclaimer`默认 dry-run，显式 managed root 限定目录；claim 与 Catalog CAS 在 SQLite 中串行核对所有 path 叶子、未退休部署及 runtime 债务，锁外隔离并回收。`require_adoptable`拒绝重新登记 reclaiming／reclaimed 位置，崩溃后可继续原隔离义务。目录证据包含文件路径、大小和 mtime 摘要；实际回收仅验证于临时 fixture，自动供给保留优先，服务层的显式回收另行调用。

## 6. 后续阶段与适用边界

R4 `REFACTOR-EXECUTION-01`软件门及F05／F15正确目标已通过，唯一详细交付与验收见[R4接力执行](重构接力执行-R4-2026-10-18.md)。本页§5保留R3固定输入的历史验收数字，后续阶段使用各自证据目录。

旧执行入口与无 spec 的 legacy 观察适配按 R5 迁移裁撤，当前仍保留兼容路径。Android SAF 平台端到端、新发行物实际首启与 9B LL／DL 多设备接力属于 R5／R6。PC shim 导出加载、Android native 编译和 fixture 加载路径提供软件证据，实际 GGUF 单权重加载及设备无整模观测由 R6 采集。
