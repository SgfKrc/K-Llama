## MT-LORA-N0 只读 LoRA 头检查实施复核（2026-08-12）

- 统一入口新增 `python scripts/model_tools.py sd15_lora_inspect <file>`，兼容连字符别名 `sd15-lora-inspect`，支持可选 `--root` 约束输入文件必须位于指定根内；仅接受单个 `.safetensors` 文件，不扫描目录、不写入文件。
- 实现只读取 8 字节 little-endian header 长度与最多 16 MiB UTF-8 JSON header，不导入 `safetensors`、Torch 或 Diffusers，不读取权重区、不分配张量，也不初始化 CUDA。头部 JSON、元数据类型、tensor shape、data offset、重叠区间和文件边界均校验；截断、超大头、异常 JSON、越界/重叠张量或路径逃逸均 fail-closed。
- JSON schema v1 仅返回通用输入类别、文件/已读 header 字节数、LoRA down/up/alpha 计数、组件摘要及 `ss_*` 聚合。数值训练参数（如 network dim、learning rate、epoch、steps）可按原数值返回；训练集目录、触发词/标签频率和其他文本元数据只返回数量、长度和数值总计，不输出原文、文件名、绝对路径、未知键名或可逆哈希。
- 自动化覆盖正常 LoRA、无元数据、截断 prefix、超大 header、非法/重叠 tensor range、`--root` 路径越界及 JSON/CLI 脱敏；当前 `tests/test_model_tools.py` 为 `48 passed / 2 skipped`。本票不检查权重数值质量、不保证可与特定 base model 合并，也不替代真实 LoRA 的人工验证。

## P2 LLM 冒烟矩阵实施复核（2026-08-10）

- 统一入口新增 `python scripts/model_tools.py llm_smoke_matrix`。固定 `qlh-llm-smoke-v1` 四项：中文、英文、精确 JSON 对象和中等长度上下文 marker；默认每项最多 32 个新 token、每个“模型×格式”独立子进程和 180 秒超时，矩阵最多 32 个单元，参数上限不可绕过。
- 发现事实源为 `src/model_config.py` 注册表；`both` 模型分别形成 GGUF/llama.cpp 与 Safetensors/PyTorch 单元。缺资产、CUDA 不可用或 RAM/VRAM 余量不足显式记 `skipped`，不通过 OOM 探测；某一模型加载失败或某条生成失败不会阻断后续单元。执行门和覆盖门分开：退出 0 只表示所有实际执行单元通过，`coverage_complete=false` 时不得宣称全注册表通过。
- worker 强制离线，Hugging Face 动态模块/Hub 缓存重定向到单元临时目录并自动清理；除显式 `--output` 外不持久写入。报告不保存生成原文或模型绝对路径，只保存模型 ID、格式、耗时、输出字符数、SHA256 与语言/JSON/marker 门结果；输出路径落入模型根目录时拒绝。
- 真实证据：Qwen 1.8B 的 GGUF 与 Safetensors 两格式均通过，`2/2 units`、`8/8 jobs`，JSON 可直接解析且 marker 正确；注册表有界扫描发现 10 个单元，实际执行 2 个并全部通过，6 个因资产未落盘跳过，DeepSeek 7B GGUF/Safetensors 分别因当前 RAM/VRAM 余量不足跳过，0 failed，故 `execution_gate_passed=true / coverage_complete=false`。工具定向 `29 passed / 2 skipped`，Python 全量 `1738 passed / 31 skipped`。
- `gguf_convert` 预检与执行事务均已完成；Windows `llama-quantize` 受管包已固定并打包，下一票是 Linux 真机工具链验收，之后才在用户明确批准目标、空间和耗时预算时执行真实模型转换验收。`sd15_merge` 继续等待写入事务和资产门评审。

## P2 GGUF 转换执行事务实施复核（2026-08-10）

- dry-run 仍为默认行为；实际转换必须同时给出显式 `--target --apply --confirm CONVERT`。缺少精确确认或参数无效时 CLI 返回 2 且不写文件；执行前重新运行完整预检，目标父目录必须已存在，目标 GGUF 及相邻 `.sha256` 均必须不存在。
- 转换在目标同卷的 `.qlh-gguf-staging-*` 临时目录中运行，子进程不经 shell，强制 Hugging Face/Transformers 离线并受 `--timeout-seconds` 限制。F16/BF16/F32/Q8_0 走单阶段；Q4/Q5/K 系列先生成 F16 中间件并完成 GGUF 结构检查，再调用 `llama-quantize`。
- 最终 staging 工件必须通过 GGUF 结构解析和全文件 SHA256 校验。发布顺序固定为“摘要旁车先、GGUF 后”，两者都以同卷无覆盖硬链接落位；目标在转换期间被其他进程创建时保持原文件不变，禁止使用可覆盖 rename。发布成功时可见 GGUF 已有摘要旁车；任一阶段失败、超时、取消或竞态均回收 staging 和未完成发布。
- 合成真实子进程证据覆盖 F16 单阶段成功、Q4_K_M 两阶段成功、SHA256 旁车可复验、转换器失败、超时、取消和目标竞态。MODEL-TOOLS 与同步定向为 `48 passed / 2 skipped`；本票代码落地后的 Python 全量为 `1752 passed / 31 skipped`。
- 对真实 Qwen 1.8B 只执行安全门：F16 dry-run 通过；Q4_K_M 因缺 `llama-quantize` 阻塞；未确认的 F16 `--apply` 返回 2 且没有目标、旁车或 staging。**本票没有执行真实 Qwen 转换，也没有生成新的真实模型工件。**
- 固定/打包票已由下节完成 Windows 开发门；下一票在 Linux 真机上执行同一 revision 的构建、运行库和 `.deb` 验收。跨平台门关闭后，再单独申请用户批准，以明确目标路径、空间/时限预算执行真实 F16/Q4 转换，验收摘要、加载冒烟和清理。

## 2. 候选小工具清单（按类别）

### 2.1 GGUF 文件工具（当前缺口最大，P0）

GGUF 是二进制格式，元数据（架构、量化类型、上下文长度、词表大小、张量清单）内嵌在文件头，llama.cpp 加载失败时很难人工排查。三个最值得做的工具：

| 工具 | 功能 | 依赖 | 工作量 |
|---|---|---|---|
| **`gguf_inspect` 元数据查看器** | 读取 GGUF 头：`general.architecture`、`general.name`、量化类型（从文件名之外直接读 `block_count`/`quantization_version` 推导）、上下文长度、词表类型与大小、张量名/形状/类型列表 | `gguf`（llama.cpp 官方 Python 包，轻量）或手工解析 header | 小（0.5-1 天） |
| **`gguf_verify` 完整性校验** | ① 比对 `.sha256` 侧车文件；② 无侧车时用 `gguf` 包完整解析张量元数据（能解析 = 结构未损坏）；③ 可选做张量字节级哈希抽样 | 无额外依赖 | 小（0.5 天） |
| **`gguf_convert` 量化转换器** | 已完成只读源/工具链/空间/路径预检，以及显式确认下的 Q4_K_M / Q8_0 / F16 staging→校验→无覆盖发布事务；Windows 量化器受管包已验证 | llama.cpp `convert_hf_to_gguf.py` + 固定 `llama-quantize`（Linux 真机包待验收） | 中（Windows 开发门完成，Linux 分发与真实模型验收待做） |

> 价值场景：下载的模型报"加载失败"时先 `gguf_inspect` 看量化/架构是否与引擎预期一致；`gguf_verify` 快速区分"文件损坏"与"引擎问题"；`gguf_convert` 支持把新模型按设备显存降量化，无需重新下载。

## 3. 优先级与实施建议

### 3.1 推荐路线

| 优先级 | 工具 | 理由 |
|---|---|---|
| **P0（先做）** | `gguf_inspect` + `gguf_verify` | 缺口最大、工作量最小、立即提升排查效率；纯标准库/官方 `gguf` 包，无环境风险 |
| **P0** | `models_sweep`（含 junction 感知） | 模型已迁 H 盘，全库体检能发现迁移残留与损坏，复用现有 SHA256 基建 |
| **P1** | `models_clean`、`model_disk_usage` | 磁盘治理刚需，注意 junction 安全 |
| **P1** | `sd15_prompt_batch` / `sd15_sampler_matrix` | 直接服务 preset 调参与质量门，复用 quality_gate 报告格式 |
| **P2** | `models_sync_status` / `llm_smoke_matrix` / `gguf_convert` 预检与执行事务（开发门已完成）；Windows `llama-quantize` 已固定/打包，下一票 Linux 真机工具链验收；经明确批准再做真实转换验收；后续 `sd15_merge` | 转换/融合需工具链、空间、校验、无覆盖发布和人工批准门 |

### 3.2 通用原则

1. **只读工具优先**：inspect/verify/sweep/status 全部只读，无副作用，先落地建立信心。
2. **复用而非重造**：SHA256 用 `src/model_sync.py`；SD 校验用 `src/diffusion/assets.py:verify_asset_directory`；报告格式对齐 quality_gate 系列；模型注册用 `src/model_config.py` BUILTIN_MODELS。
3. **CLI 优先，输出双格式**：人类可读表格 + `--json`（对齐 `export_model_catalog.py` 与 `quality_gate` 的报告约定，未来可被自动化实验框架消费）。
4. **junction 安全**：`models/` 现为 H 盘 junction，任何删除/统计工具必须 `os.path.islink()` 或 `Path.is_junction()` 判断，只操作 junction 内部文件，绝不删联接本身。
5. **环境隔离**：GGUF 纯解析工具只用标准库 + `gguf` 包（轻量）；SD 工具走 CUDA 侧车；不往主解释器塞重依赖。

### 3.3 落地形态建议

统一入口：`scripts/model_tools/` 目录 + 一个 `model_tools.py` 子命令分发（`python scripts/model_tools.py inspect models/xxx.gguf`），或直接复用 TUI 指令集模式注册进 `bjtu` 命令体系（对齐 `docs/TUI指令集.md`）。P0 两个工具建议一次性提交。
