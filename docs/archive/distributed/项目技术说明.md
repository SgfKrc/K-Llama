## 0. 先建立正确的整体认识

QLH 的主线不是把请求切成完整模型 Stage，而是用 llama.cpp host/RPC worker 研究“单机装不下、节点各持一部分”的模型分片。控制面统一管理请求、节点、模型身份、分片、租约、状态和指标；PyTorch 层流水线只用于 PC 对照，任务图中的完整 Worker 只作为临时回退。

当前主要路径如下：

| 路径 | 模型工件 | 设备 | 当前状态 |
|---|---|---|---|
| 本地 llama.cpp | GGUF，例如 `Q4_K_M` | CPU/集显 PC、Android | 生产主路径；先做单机基线 |
| llama.cpp RPC 模型分片 | GGUF | PC host + PC/Android RPC worker | 主攻；必须先完成同机双进程模拟和部分驻留证据 |
| Relay 层接力 | 裁层 GGUF + hidden/`embd` | 当前仅 PC；L→L 已验证，D→L 长序列失败 | 架构兼容轨道；默认关闭，不替代 RPC，不进入 Edge 默认路径 |
| PyTorch 层间流水线 | 同一份 Safetensors 的连续层段 | 仅 PC 节点 | PC 对照实验及 D→L Relay 来源，不再作为生产路径 |
| 任务链/DAG | 文本或 JSON Stage 输入输出 | PC、未来 Android Worker 和其他异构设备 | 临时完整模型回退，不代表模型分片 |
| 张量并行（QLH 自己编排 rank） | 由外部 Provider 管理的分片模型 | 高速同构 GPU 或 Apple Silicon 集群 | 规划/调研阶段，未实施 |
| TP 孤岛（`island`） | 无本地工件，端点指纹作模型身份 | 网关 PC 节点 + 集群外张量并行运行时 | 阶段 1 PoC，已实施并双节点验证；整请求，不参与层拆分 |
| 外部推理服务（`external_api`） | 无本地工件，端点指纹作模型身份 | 任意服务节点 → 集群信任域外端点 | 阶段 1 PoC，已实施；整请求外发，默认 `opt_in` 门控 |
| 投机解码（`speculative_assisted`） | 本地 draft 模型 + 外部 verify 端点 | 本地 + 集群外端点 | 探索性 PoC，**只有独立实验端点，未接生产解码循环** |

四个容易造成误判的事实：

1. GGUF 是 llama.cpp 的模型工件，不能直接加入旧 PyTorch `LAYER_FORWARD` 协议；当前新增的 Relay 使用独立 hidden handoff 合同，已证明 L→L 裁层接力逐 token 16/16 行为等价。D→L 同机文件交接的 5-token prefill 通过，但 141-token f16/f32 均有错误 argmax，仍不准入。目标生产路径仍是通过 llama.cpp RPC 让多个节点共同承载 GGUF。Android Full/Lite 远程模式是 HTTP 客户端，不等于 Android 已经成为 RPC worker。
2. 节点在线、TCP 已连接、节点已注册、模型已就绪、流水线已经实际执行，是五个不同状态。UI 或日志必须以实际执行指标为准，不能因为“节点在线”就显示“分布式已参与”。
3. **任务图、TP 孤岛和投机解码是回退/辅助 PoC，不是模型分片生产能力。** 任务图要求某个节点装下完整模型；投机解码仍是独立测量入口，`QLH_SPEC_ENABLED` 默认关闭时端点返回 404。
4. **“RPC 已经证明精确按层拆分”也是错的。** llama.cpp 上游和 Silica 证明了 RPC/offload 入口，但 `-ngl`/`--tensor-split` 仍需 QLH 实测升级为可校验的部分驻留合同；同机双进程门未通过前不做真机分布式结论。

推荐阅读顺序：先看本文第 4～8 节，再看[整体架构](../../整体架构.md)、[模块接口说明](../../模块接口说明.md)、[分布式推理流水线实施计划](分布式推理流水线实施计划.md)和[任务链下一阶段实施计划](任务链下一阶段实施计划.md)。外部辅助三条路线的背景见[张量并行外部辅助与混合拆分调研方案](../relay/张量并行外部辅助与混合拆分调研方案.md)。

## 1. 一次请求经过什么

### 1.1 两个生成阶段

自回归模型通常把一次生成分成两个阶段：

- **Prefill**：把用户已有的 prompt 一次性送入模型，计算整段输入，并建立每层的 Key/Value（KV）缓存。Prefill 的张量形状通常是 `(batch, prompt_length, hidden_size)`。
- **Decode**：每次只追加一个新 token。模型读取已有 KV，只为新 token 计算新的 Key/Value，再采样下一个 token。Decode 的输入通常是 `(batch, 1)`，但 KV 的序列长度会持续增长。

单机完整推理由 `ModelManager.chat()`/`chat_stream()` 统一入口处理；PyTorch 层流水线则由 `Scheduler.run_pipeline()` 逐步协调。API 层在 `src/api_server.py` 暴露普通响应和 SSE 流式响应，主线 TUI 和外部产品壳均通过 `/api/chat` 或 `/api/chat/stream` 使用它们；Web/Android 不是主仓交付边界。

### 1.2 QLH 的边界对象

| 对象 | 含义 | 谁负责 |
|---|---|---|
| `model_id` | 逻辑模型名称，例如 `qwen-1_8b` | 模型注册表和 Provider |
| `format` | `safetensors` 或 `gguf` | 模型工件校验 |
| `revision`/`sha256` | 具体版本和内容身份 | 注册、层配置和任务 Worker 准入 |
| `task_id` | 一次流水线/推理任务 | 调度器和 KV 生命周期 |
| `workflow_id` | 一次任务图工作流 | `TaskGraphCoordinator` |
| `stage_id` | 工作流中的业务 Stage | 任务图状态机 |
| `attempt_id` | 一个 Stage 的一次执行尝试 | Provider、租约和结果 fencing |
| `lease_id`/`lease_epoch` | 某次尝试的所有权和代次 | 防止断线重派后的迟到结果提交 |

不要把 `task_id`、`workflow_id` 和 `attempt_id` 混用。它们对应不同故障域和不同清理边界。

## 2. KV 优化：为什么缓存、缓存什么、如何保证不乱

### 2.1 KV Cache 是什么

注意力层在计算当前 token 时需要历史 token 的 Key 和 Value。如果每次 Decode 都重新计算历史，会产生越来越多的重复工作。KV Cache 保存历史 Key/Value，使 Decode 只处理新增 token：

```text
Prefill:  prompt tokens -> 每个本地层生成完整 KV
Decode:   新 token + 本地 KV -> 新 hidden state + 追加 KV
```

QLH 的实现位置：

- `src/model_module.py::forward_layers()`：负责 Prefill/Decode 的前向接口、`past_key_values` 输入和新缓存输出。
- `src/scheduler.py`：按 `task_id` 保存每个节点的缓存，在任务完成、取消、超时和 `PIPELINE_ABORT` 时清理。
- `src/paged_kv_cache.py::PagedKVCache`：提供固定页、追加、读取、窗口读取和清理的通用分页缓存结构；显式传入 `cold_cache_dir` / `cold_max_pages` 时，可将超出热页上限的封存页下沉到按实例隔离的磁盘冷层。
- `src/llama_engine.py`：llama.cpp 使用引擎自己的 KV 管理和 `reset_kv_cache()`；它不是 PyTorch 的 `past_key_values` 实现。

### 2.2 分布式流水线的 KV 所有权

PyTorch 层流水线只在节点边界传递必要的 hidden states、位置/掩码和任务控制字段，不在每一步跨节点传输所有层的 KV：

```text
主节点本地层段 + 本地 KV  --hidden_states-->  从节点 A 本地层段 + 本地 KV
                                                  --hidden_states--> 从节点 B
```

这样做有三个原因：

1. **通信量小**：KV 随上下文长度增长，跨节点搬运会远大于单 token hidden state。
2. **状态边界清楚**：每个节点只负责自己加载的层，`past_key_values` 的长度必须等于本地层数。
3. **故障容易收敛**：一个 attempt 失败时，清理每个节点的 `task_id` 缓存，不把部分 KV 当成下一次请求的合法状态。

Qwen2 使用 Transformers `DynamicCache`。分布式节点只加载局部层，如果直接使用原模型的全局 `layer_idx`，缓存内部会出现空洞索引。因此 `forward_layers()` 在前向期间临时把本地层索引改成 `0..N-1`，结束后恢复原始索引。Decode 还会检查：

- step 0 必须是 Prefill，不能声明已有 KV；
- step > 0 必须使用 KV，且必须严格接续上一个 step；
- 收到的缓存层数必须等于本地层数；
- `config_id`、模型架构、模型 ID、层范围和模型 SHA256 必须与已确认的活动配置一致。

### 2.3 分页与内存上限

`config.py` 的默认参数是 `PAGE_SIZE=128`、`MAX_PAGE_NUM=256`、`MAX_SEQ_LEN=4096`。分页的目的不是改变注意力数学，而是降低长会话和取消/回收时的内存碎片。实际部署时还要根据模型、设备和并发量调整：

- 页太小：管理开销高，频繁分配；
- 页太大：短请求浪费内存；
- 缓存上限太高：多任务并发时容易 OOM；
- 缓存上限太低：长上下文被截断或请求失败。

当前 PyTorch 层流水线为了保护 GPU 和节点状态，默认同一时间只执行一条流水线。`PIPELINE_PAUSE/RESUME` 是协议预留；实际已实现的协同抢占只在 Decode 步边界、满足最小 token 数和间隔条件时运行，抢占开销超过阈值会自动关闭后续抢占。

### 2.4 KV 调试要看什么

不要只看“缓存已启用”。应同时检查：

1. 每个节点的 `task_id`、当前 step 和本地 KV 层数；
2. Prefill 是否为 `use_kv_cache=false`，Decode 是否为 `true`；
3. `kv_seq_len` 是否单调增加；
4. `PIPELINE_DONE`/`PIPELINE_ABORT` 后缓存是否变为零；
5. 取消后是否还有迟到结果尝试推进下一 step。

## 3. 算子融合：用什么、何时用、为什么有门槛

### 3.1 是什么

算子融合把一串可以连续执行的算子组合成更少的 GPU kernel 或更紧凑的执行图，减少 kernel launch、临时张量读写和 Python 调度开销。QLH 不手写一套只适用于某个模型的融合 kernel，而是使用 PyTorch `torch.compile()` 的后端编译能力。

### 3.2 当前实现

入口是 `src/model_module.py::_apply_compile()`，配置是 `config.USE_COMPILE`：

```python
if USE_COMPILE and CUDA 可用 and quant_type == "fp16":
    model = torch.compile(model, mode="reduce-overhead")
```

以下情况会主动跳过：

- CPU 或集显路径没有 CUDA；
- INT4/INT8 与当前 bitsandbytes kernel 组合不兼容，实测可能变慢；
- 编译失败时记录 warning，保留普通 PyTorch 模型，不让启动失败。

### 3.3 和注意力后端的关系

Transformers 的 Qwen2 路径可能根据运行时选择 SDPA/FlashAttention 等注意力后端；这是模型前向内部的后端选择，不等于 QLH 自己实现了 FlashAttention。`torch.compile` 也不是“打开后所有算子都融合”，它受 PyTorch、CUDA、驱动、模型动态行为和量化 kernel 影响。

### 3.4 什么时候使用

- **显存充足且追求吞吐**：优先测试 FP16 + `USE_COMPILE=true`，用固定 prompt/输出长度测首 token、Decode tok/s 和峰值显存。
- **显存紧张或集显/CPU**：使用 llama.cpp GGUF 或普通 PyTorch，不要为了“融合”强行启用 compile。
- **量化模型**：先比较量化收益和 compile 代价。当前项目默认 INT4 不加 compile。

配置文件中的 +3.6% 等数字是特定 Qwen-1.8B、GPU、PyTorch 版本和 50 token 基准的测量值，不是跨设备保证。每次改变模型工件、驱动、量化或 batch 都应重新测量。

## 4. 模型量化：两条引擎路径不能混用

### 4.1 PyTorch/Transformers 路线

Safetensors 权重通常保持原始精度存盘，加载时由 `BitsAndBytesConfig` 转换：

| 配置 | 机制 | 适用和代价 |
|---|---|---|
| `fp16` | 半精度权重和计算 | 显存最高，便于 compile，精度基线 |
| `int8` | bitsandbytes 8-bit 加载 | 显存下降，但当前基准速度可能明显下降 |
| `int4` | NF4、double quant、FP16 compute | CUDA 显存最低，适合独显；有量化误差，不能与当前 compile 组合 |

bitsandbytes 的 INT4/INT8 是 CUDA 优先路径。不能把“配置写着 int4”理解为所有 CPU 节点都能执行同样的 4-bit kernel。层流水线的内存估算会根据设备和实际加载精度区分 CUDA/CPU；模型加载和 ready ACK 仍以真实运行时为准。

### 4.2 llama.cpp/GGUF 路线

GGUF 已经把量化信息封装在模型文件中，`src/llama_engine.py` 通过 llama.cpp 加载。例如：

- `Q4_K_M`：较小、速度和质量平衡，适合集显/CPU；
- `Q5_K_M`：文件更大，质量通常更高；
- `Q8_0`：更接近高精度，内存和带宽开销更大。

GGUF 的量化格式不能当作 PyTorch 的 `int4` 参数，也不能把 GGUF 层直接发给旧 PyTorch Worker。当前 QLH 的 GGUF 分片走 llama.cpp RPC；Relay 只在独立合同下传递 hidden，已完成 L→L 行为验证，D→L、跨进程/网络和长序列仍不属于已支持能力。

### 4.3 量化选择流程

1. 先确认模型架构、tokenizer 和工件身份；
2. 再根据设备选择引擎，而不是先写一个 `quant_type` 再期待引擎自动适配；
3. 记录模型 ID、revision、format、量化类型、设备和运行时版本；
4. 用固定评测集比较质量、首 token、Decode tok/s、峰值内存和长上下文稳定性；
5. 分布式层流水线还要确认所有节点使用同一模型身份和兼容 PyTorch 运行时。

## 5. 分布式推理架构（重点）

### 5.1 控制面和数据面

QLH 把“决定怎么执行”和“真正计算”分开：

```text
TUI（主线）/外部 Web 或 Android 产品壳
        | HTTP / SSE
FastAPI API Server (api_server.py)
        | 请求、节点、模型、任务图 API
Scheduler (scheduler.py) + ProviderRegistry/TaskGraphCoordinator
        | 控制消息、任务身份、就绪状态、取消、租约
TCP cluster transport / task_worker protocol
        | hidden states、文本/JSON Stage 数据
推理 Provider
  ├─ 本地完整 ModelManager / llama.cpp
  ├─ Relay R：裁层 llama.cpp + hidden/embd（PC 显式实验）
  ├─ PyTorch 连续层段 Worker
  └─ PC Full Worker（实验门控制）
```

FastAPI 不直接保存“某个节点应该执行哪一层”的临时判断；调度器生成计划后，必须通过配置、模型身份和 ready ACK 形成可执行契约。数据面失败时，控制面负责让当前 attempt 进入明确终态、清理缓存或创建新 attempt。

### 5.2 主节点、从节点和 Android 的职责

- **主节点**：接受 API 请求，维护集群视图，生成 RPC 分片、Relay 实验或任务图计划，负责请求队列和最终结果；Relay 不改变主节点的控制面职责，层段由设备画像和合同决定。
- **PyTorch 从节点**：只加载被确认的连续层段，收到 `LAYER_FORWARD` 后执行本地层并返回 hidden states 或 logits；本地维护自己的 KV。
- **Relay 节点**：仅在 PC 显式实验中接收与合同匹配的 hidden，使用裁层 llama.cpp 继续计算；必须校验模型身份、层边界、shape/dtype、位置和 step，并用 argmax/top-k 做行为判定。`embd` 的 bitwise 非确定性不应被写成逐位一致。
- **PC Full Worker**：把完整业务 Stage 交给能独立加载完整模型的节点。它不是 hidden-state 层 Worker；通过 `hello`、能力声明、Stage offer、租约和结果提交协议工作，当前受 TC-N2.4 实验开关和物理验收门控制。
- **Android Full/Lite**：当前可以本地 llama.cpp 完整推理，或通过 HTTP 把请求交给 PC 主节点。Android 当前不加入 PyTorch 层配置，也不应在 UI 上显示为已参与 `LAYER_FORWARD`。

角色名不是性能等级。主节点不应因为是主节点就固定少算层；层数由算力、可用内存、Embedding/LM Head 负担和网络代价共同决定。

### 5.3 PyTorch 层间流水线的准备阶段

一次可执行的层流水线必须按顺序完成：

1. **网络发现**：从节点通过 Tailscale/广告地址发现主节点，使用实际可达地址，而不是 `0.0.0.0`、localhost 或错误网卡地址。
2. **TCP 注册与认证**：从节点提交 node ID、角色、节点类型、设备画像、广告地址和模型摘要；主节点使用共享 `QLH_CLUSTER_SECRET` 做 HMAC-SHA256 校验。
3. **能力筛选**：排除 Android、错引擎、模型缺失、模型架构不兼容、版本不匹配或当前不可用的节点。
4. **层分配**：`Scheduler.compute_layer_assignment()` 生成连续的 `[start_layer, end_layer)` 区间。节点数量较多时，`GraphOrchestrator` 可用最大带宽生成树 + DFS 做候选拓扑；否则使用能力权重和约束回退。
5. **配置推送**：主节点发送 `LAYER_CONFIG`，包含 `config_id`、模型 ID、模型 SHA256、模型架构、总层数、层范围、Embedding/LM Head 标志。
6. **从节点加载并 ACK**：只有实际加载成功、层范围和模型身份一致的 `LAYER_CONFIG_ACK` 才能进入 ready 集合。TCP connected 不代表 ready。
7. **锁定执行契约**：执行请求携带配置 ID、模型身份、step 和链路路径；从节点每次都校验，防止旧配置或错误模型混入。

层分配不是把一个综合分数直接换算成层数。调度器先应用模型架构、引擎、模型身份、层连续覆盖、Embedding 锚点和可用内存等硬约束，再用独显/CPU 能力、可用内存以及网络画像形成相对权重。Embedding 和 LM Head 的内存开销与普通 Transformer 层分开估算；显存不足时尝试转移层，无法保持完整覆盖则让 ready 检查触发回退，而不是静默丢层。较强主节点因此通常会承担更多 Transformer 层或 LM Head，而不是因为“主节点负责协调”就固定少算。

### 5.4 层流水线的执行阶段

推荐拓扑中，主节点先执行自己的首段，然后把 hidden states 送给首个 Worker；后续节点可通过 `CHAIN_FORWARD` 直连传递，直连失败时由主节点中转或使当前 attempt 失败：

```text
step 0 (Prefill)
prompt -> 主节点 Embedding/首段 -> hidden_states
       -> Worker A 中段 -> hidden_states
       -> Worker B 末段/hidden_states 或 logits
       -> 主节点 LM Head（若归属主节点）-> 采样 token

step 1..N (Decode)
新 token + 各节点本地 KV -> 重复相同层链 -> 采样下一个 token
```

每一步的主要控制字段包括：`task_id`、`step`、`config_id`、`model_sha256`、`model_type`、`use_kv_cache`、`chain_path`、`chain_next`、温度和 top-p。数据字段是 `input_ids` 或序列化后的 `hidden_states`；不传输整个 KV。

末节点可以返回 logits，也可以返回 hidden states 由主节点执行归一化和 LM Head。这样可以避免弱节点计算并回传完整词表 logits；最终归属由层分配和运行时路径共同决定，不能只看旧 UI 上的 `has_lm_head` 文本。

### 5.5 失败边界和回退

层流水线的最小故障域是一次完整的 pipeline attempt。网络中断、配置失效、节点超时、模型不匹配、KV 缺失或迟到结果都不能把半个 hidden state attempt 直接交给另一个 Provider 继续。处理顺序是：

1. 标记当前 step/attempt 失败；
2. 广播 `PIPELINE_ABORT`，清理各节点的本地 KV 和活动任务；
3. 过滤迟到的 `LAYER_RESULT`、旧 `config_id` 和旧 `task_id`；
4. 如果没有已经不可撤回的流式输出，按策略回退到主节点完整模型或重新规划；
5. 更新实际参与节点、失败原因、回退次数和耗时指标。

不能只捕获异常后继续下一节点，因为这样会造成：旧 KV 与新请求串用、下一请求收到迟到结果、UI 显示“分布式成功”但实际只执行了主节点。

### 5.6 任务链/DAG：另一种分布式架构

任务链拆分的是**业务 Stage**，不是 Transformer 层：

```text
root input
   ├─ candidate_a: full_inference
   ├─ candidate_b: full_inference
   └─ aggregate: 依赖至少一个成功候选
```

`TaskGraphCoordinator` 管理 Workflow/Stage/Attempt 状态、依赖、并行度、取消、SQLite journal、Provider reservation、租约和结果提交屏障。Stage 的输入输出是受 schema 约束的文本/JSON，不应把任意 hidden states 塞进任务链协议。

默认配置中 `TASK_GRAPH_ENABLED=false`，`TASK_WORKER_EXPERIMENTAL_ENABLED=false`。即使控制面 hello 已经成功，物理设备准入完成前公开状态仍保持 `adapter_connected=false`；不能通过前端按钮或修改展示字段绕过这个门。

任务图当前最重要的保护：

- 同一 Stage 的结果只有当前 `lease_epoch` 和获胜 `attempt_id` 才能提交；
- `message_id` 重放必须幂等，内容不同的复用要拒绝；
- Worker 断线后可以创建新 attempt，但旧 attempt 的迟到结果不能覆盖新 winner；
- 聚合 Stage 只有显式 `retry_safe` 且满足 `same_provider_retryable` 条件，才允许有限同 Provider 重试；
- 外部数据库不可用时，先依赖本地 journal 保持状态边界，不能把数据库连接当作执行成功条件。

任务图可以组合本地完整模型、PC Full Worker 和未来 Android Worker，但目前 Android Full Worker 仍是后续阶段；不要把任务图的 Stage 并行误报为 PyTorch 层流水线参与。

### 5.7 张量并行和 GGUF 分布式的边界

张量并行把一个矩阵或 tensor shard 分给多个 rank，要求高频 collective、稳定 rank、低延迟互联和同构运行时。它不适合把普通 Tailscale/Wi-Fi Android 节点加入当前 `LAYER_FORWARD` 链。后续应以独立 `TensorParallelProvider` 或外部 exo/MLX/CUDA Provider 接入，不能修改现有 PyTorch socket 协议来“凑出”张量并行。

GGUF 层拆分同样应作为独立 GGUF Stage Provider 验证，模型分片、版本、sidecar、断线清理和收益都要单独验收。当前 QLH 的 llama.cpp 路径是本地完整推理。

### 5.8 外部辅助：整请求交出去（阶段 1 PoC）

上一节的结论没有松动——变化的是**换一种用法**：不把 collective 拉进 mesh，而是把整条请求交给一个自行做张量并行的外部运行时。

- **TP 孤岛（`island`）**：网关节点同时接入孤岛内网与 QLH 集群，以 `engine="island"` 注册；对集群呈现为**单个逻辑高算力节点**，承担整请求推理。“加载模型”实际是 `GET /v1/models` 健康检查加解析后端模型名。孤岛节点被 `compute_layer_assignment()` 按 `device_info.island.enabled` 过滤，网关侧收到分层配置也会拒绝并退出分层 worker 池——双保险，行为等同 `llama_cpp` 节点。孤岛的聚合 GPU 数与显存由部署者用 `QLH_ISLAND_*` 声明并进入注册画像，主节点据此上浮排序权重；**网关探测不到孤岛内部硬件，因此这些数字是声明值，虚报会直接造成调度失真。** 故障域是整个网关逻辑节点。
- **外部推理服务（`external_api`）**：没有专职节点，服务节点按每条请求决策是否把整请求路由到集群信任域**之外**的 OpenAI 兼容端点。门控是硬约束，判断顺序是：`QLH_EXTERNAL_DATA_SCOPE`（`deny`/`opt_in` 默认/`allow_all`，取值非法一律 fail-closed 回落 `deny` 并告警）→ 请求是否显式带 `allow_external` → 是否 `prefer_external` 或消息长度超过 `QLH_EXTERNAL_MIN_PROMPT_CHARS`。门控在路由决策与发出请求前各执行一次，重构无法绕过。外部失败自动回退本地路径并记 `fallback_reason`。
- **投机解码（`speculative_assisted`）**：本地小模型起草、外部大模型校验，只有实验端点，**未接入 `model_module` 的生产解码循环**；数据作用域复用上一条的门控（草稿 token 由用户内容派生，确实出网）。`PagedKVCache.truncate(n)` 已能回滚被拒绝草稿对应的尾部 KV，但真实 draft/verify、收益门与生产接线仍未完成。

三者的取消都是 **chunk 边界 best-effort**：OpenAI 兼容端点没有服务端取消原语，QLH 断开 SSE 后外部端可能继续算完当前请求。排查时不要把“QLH 已取消”当成“外部没算”。

## 6. 并发调度（重点）

QLH 有两层调度，不要把它们混成一个队列：

1. `PipelineQueue` 调度用户推理请求；
2. `TaskGraphCoordinator` 调度工作流中的 Stage 和 Provider reservation。

### 6.1 PipelineQueue：请求级 MLFQ

`src/scheduler.py::PipelineQueue` 默认使用三级反馈队列：

| 队列 | 默认条件 | 目的 |
|---|---|---|
| Q0 | `max_new_tokens <= 128` | 交互短请求，优先降低等待 |
| Q1 | `129..512` | 普通生成 |
| Q2 | `>512` | 长文或批量请求 |

MLFQ 选择规则：

1. Q0 > Q1 > Q2 严格优先级；
2. 同级按预估执行时间 SJF 排序；
3. Q2 等待超过 120 秒可升到 Q1，Q1 等待超过 60 秒可升到 Q0；
4. 任意请求超过 300 秒触发绝对上限，置顶 Q0，防止饥饿；
5. `fifo` 兼容模式仍按 Q0/Q1/Q2 级别取任务，并非严格跨级全局 FIFO。

当前单条流水线默认独占推理锁，队列容量默认 100。这样做是因为 GPU 模型、各节点 KV 和网络链路共同构成一个执行实例；盲目同时执行多个流水线会导致显存超限、KV 交叉、TCP 结果错配和吞吐下降。

### 6.2 协同抢占

当长 Q1/Q2 任务已经 Decode 一段时间，满足 `PIPELINE_PREEMPT_MIN_TOKENS` 和 `PIPELINE_PREEMPT_MIN_INTERVAL` 时，Q0 可以在 Decode step 边界被内联执行。实现要点：

- 保存生成 token、输入引用、拓扑和流式回调；
- 释放当前推理锁，执行 Q0；
- Q0 的异常只影响 Q0，不污染被抢占任务；
- Q0 完成后恢复长任务；
- 抢占开销超过 `PIPELINE_PREEMPT_MAX_OVERHEAD_MS`，自动禁用后续抢占。

这不是任意时刻的硬抢占，也不会在 Prefill 中间切断节点。`PIPELINE_PAUSE/RESUME` 是未来协议能力，不能据此宣称已经支持任意暂停和恢复。

### 6.3 TaskGraphCoordinator：Stage 级并行

任务图把无依赖的 Stage 提交给 `ThreadPoolExecutor`，默认最大并行 Stage 数由 `TASK_GRAPH_MAX_PARALLEL_STAGES` 控制，默认 4，但最终还要受每个 Provider 的 `max_concurrency` 和当前 reservation 数限制。

一个 Stage 的典型流程是：

```text
依赖满足 -> 选择 Provider -> reserve -> 创建 attempt/lease
         -> offer/accept -> execute -> result digest 校验
         -> winner commit -> release reservation
```

Provider 选择至少检查：Stage 类型、模型身份、健康状态、可用槽位、历史失败/重试状态和稳定 Provider ID。两个候选 Stage 应尽可能分给两个独立 Worker；单槽 Worker 不应被误计为两个并发远端执行。

### 6.4 取消、超时和清理

- API 取消先进入控制面状态机，再给当前 Provider 发送 cancel；
- 运行中的本地前向使用协作取消事件，不能从任意线程强杀 Python/GPU 调用；
- lease 到期会使旧 attempt 失去提交资格，必要时创建新 attempt；
- reservation、KV、线程事件、TCP pending map 和 journal 状态必须在成功、失败、取消三条路径都能回收；
- 结果 TTL、工作流保留天数和最大记录数限制内存增长。

## 7. 通信协议（重点）

QLH 同时有客户端 HTTP/SSE、集群 TCP 和任务 Worker envelope 三层协议。三者用途不同。

### 7.1 客户端 HTTP/SSE

FastAPI 是对用户和 Android 的控制面入口：

- `POST /api/chat`：普通聊天响应；
- `POST /api/chat/stream`：`text/event-stream`，逐 token 或完整流程流式返回；
- `/api/models`、`/api/cluster/*`、`/api/bootstrap/*`：模型、节点和首次发现；
- `/api/workflows` 及其子路径：任务图查询、取消和 journal 清理；
- `POST /api/experimental/speculative`：投机解码实验端点，`QLH_SPEC_ENABLED` 默认关闭时返回 404，不写会话历史、不入对话统计。

`/api/chat` 与 `/api/chat/stream` 另有 `allow_external` / `prefer_external` 两个可选布尔字段，缺省均为 `false`，旧客户端行为不变；只有它们与数据作用域档位共同放行时请求才会离开集群。

`/api/status` 在对应功能启用时会增加 `island` / `external` / `speculative` 段，端点与凭据一律脱敏。

2026-07-26 修复：`/api/cluster/connect` 等 9 个端点此前在 async handler 内同步阻塞，连接不可达主节点时会冻结整个事件循环最长约 50 秒，前端整站假死；现已全部移入 `run_in_threadpool`。排查“前端整站没反应但进程还活着”时应先确认版本是否包含此修复。

HTTP 请求包含会话和请求身份，但不要把 HTTP 连接是否成功当作后端 Worker 已参与。流式输出一旦发送给客户端，就要考虑重试是否会产生重复 token；Provider 切换原则是“在不可撤回输出前重试，输出后默认新建 attempt 或返回明确错误”。

### 7.2 集群 TCP：长度前缀 + JSON 控制

文件：`src/tcp_comm.py`。

基础封包格式：

```text
4 字节：大端序 uint32，表示 payload 长度
N 字节：UTF-8 JSON 或二进制 payload
```

`recv_exact()` 负责处理 TCP 粘包和拆包，长度超过 `MAX_PACKET_SIZE=256 MiB` 必须拒绝。常见 `MessageType` 包括：

| 类别 | 消息 |
|---|---|
| 生命周期 | `register`、`heartbeat`、`heartbeat_ack`、`status_req`、`status_res` |
| 模型/层配置 | `layer_config`、`layer_config_ack` |
| 层流水线 | `layer_forward`、`layer_result`、`chain_forward`、`chain_forward_ack` |
| 任务控制 | `task_start`、`task_stop`、`pipeline_done`、`pipeline_abort` |
| 从节点转发 | `infer_forward`、`infer_result`、`infer_cancel` |

注册认证使用：

```text
message = "{node_id}:{timestamp:.6f}"
signature = HMAC-SHA256(QLH_CLUSTER_SECRET, message)
```

服务端检查签名、节点 ID 和时间戳窗口（默认 ±5 分钟）。生产环境必须让所有节点使用相同的随机 `QLH_CLUSTER_SECRET`，建议至少 32 个字符；缺失密钥时认证应失败，而不是把“能访问 Tailscale”当作协议身份。

2026-07-26 的一批控制面修复直接影响“节点在线”的判定，排查断连问题时应先确认版本（均经双节点实测验证）：

| 症状 | 原因 | 现行行为 |
|---|---|---|
| 从节点心跳照发、主节点显示在线，但永远不响应、也不重连 | 客户端 `_recv_loop` 的清理未放 `finally` 且只捕获部分异常，帧解析异常让接收线程静默死亡，形成“僵尸连接” | 清理移入 `finally` 并补齐兜底 `except`，异常退出必然触发重连 |
| 偶发协议错乱、后续消息全部解析失败 | `recv_exact()` 在帧中途超时时丢弃已读字节并 `continue`，造成字节流失步 | 区分空闲超时与帧中途超时，后者抛 `ConnectionError` 走重连 |
| 注册失败后恢复很慢（最长 60 秒） | 心跳与重连线程被连接代数淘汰成孤儿 | 连接代数改为注册成功后才推进 |
| 从节点只卡顿几秒就被踢掉并重新分层 | 服务端 per-socket 固定 5 秒收包超时架空了 12 秒心跳容忍，卡顿 6 秒即误踢 | 注册后放宽到 `HEARTBEAT_INTERVAL*(MAX_HEARTBEAT_MISSED+1)+2` |
| 帧交叉损坏 | `scheduler.py` 三处 ACK 绕过 `_send_lock` 直接 `sock.sendall`，与心跳并发写冲突 | 统一改走 `send_data` 加锁通道 |
| 日志里出现莫名其妙的“已自动重连” | 健康监控启动首轮的假“恢复”跳变，并对健康链路做了多余重连 | 首轮不再判为恢复 |

### 7.3 张量传输格式

层流水线热路径使用 `serialize_tensor_fast()`/`deserialize_tensor_fast()`：

- 小于 1 MiB：`TNR1` + `torch.save`，保留 dtype/shape 元数据，兼容性优先；
- 大于等于 1 MiB：`TNR0` + dtype code、维度和连续 raw bytes，减少序列化开销；
- 支持的 dtype 是 float16、float32、int64、int32；不支持的 dtype 必须显式报错；
- 传输前通常把 CUDA tensor 移到 CPU，接收端按 shape/dtype 重建，再复制到目标设备。

通用 `build_message()` 的 tensor 分支仍使用 `torch.save` 形式；层流水线的 `LAYER_FORWARD`/`LAYER_RESULT` 由调度器显式调用 fast serializer。不要因为看到 `TNR0` 就把它当作量化格式，它只是传输编码，不改变模型权重精度。

### 7.4 PC Full Worker：`qlh.task_worker` v2 envelope

文件：`src/task_worker_protocol.py`、`src/task_worker_adapter.py`。

Worker envelope 不另开一套未认证的裸 TCP 服务，而是放在现有集群 TCP 的 `TASK_WORKER` 消息中传输，因此继承外层已完成的节点注册、HMAC 身份和连接生命周期；envelope 再负责 Stage 级版本、幂等、租约和摘要校验。

外层字段严格固定：

```json
{
  "protocol": "qlh.task_worker",
  "version": 2,
  "message_type": "stage_offer",
  "message_id": "msg_...",
  "sent_at_ms": 0,
  "payload": {}
}
```

当前协议版本范围为 1～2，适配器要求协商结果为 v2；单条消息上限 8 MiB。允许的消息类型是：

`hello`、`hello_ack`、`stage_offer`、`stage_accept`、`lease_renew`、`stage_result`、`stage_error`、`stage_cancel`、`stage_cancelled`。

`hello` 声明 node ID、Worker 类型、协议范围和能力：Stage 类型、引擎、模型身份、最大并发。`stage_offer` 携带 Workflow/Stage/Attempt/Lease 身份、依赖输入、根输入摘要和模型身份；`stage_result` 必须携带输出 SHA256，协调器重新计算并检查。

协议层的保护机制：

1. 严格字段校验和安全 ID 正则，未知字段或错误类型拒绝；
2. canonical JSON + SHA256，使相同输入具有稳定摘要；
3. `message_id` 缓存 1024 条，重复消息返回相同响应，内容不同的 ID 复用报 `message_id_conflict`；
4. `lease_id`、`lease_epoch`、`attempt_id` 共同构成提交资格；
5. 原始异常、prompt 和候选正文不直接塞进公共错误日志，使用稳定错误码和安全 metadata。

注意：仓库中的 `tests/fixtures/task_worker_protocol_v1.json` 是历史/兼容测试夹具，不能据此认为生产适配器已降级为 v1。

### 7.5 一次层流水线消息时序

```text
从节点 -> 主节点: register(auth, capabilities, model_sha256)
主节点 -> 从节点: register ACK / node list
主节点 -> 从节点: layer_config(config_id, model identity, layer range)
从节点 -> 主节点: layer_config_ack(loaded, ready, error)

主节点 -> 首节点: layer_forward(step=0, input_ids or hidden_states, use_kv_cache=false)
节点 -> 下一节点: chain_forward(hidden_states, chain_path)  [可选]
末节点 -> 主节点: layer_result(hidden_states or logits, metrics)
主节点 -> 全链: layer_forward(step=1, use_kv_cache=true)
...
主节点 -> 全链: pipeline_done 或 pipeline_abort
```

每个接收方都要校验前驱、链路路径不能重复、当前配置和 step 顺序。ACK 只证明消息被接收或注册被确认，不证明模型前向成功；成功必须由结果消息和最终 metrics 证明。

### 7.6 通信失败时怎么判断

| 现象 | 可能状态 | 正确处理 |
|---|---|---|
| TCP connect 失败 | 地址、端口、Tailscale 或防火墙问题 | 不进入 ready，不显示参与 |
| register 被拒绝 | 密钥、角色、ID 或协议错误 | 修复配置后重新注册，不重试旧连接 |
| 已注册但无 `layer_config_ack` | 模型未下载、引擎不符或加载失败 | 节点保持非 ready，允许主节点回退 |
| heartbeat 正常但 layer result 超时 | Worker 忙、前向异常或链路故障 | 结束当前 attempt，广播 abort/回退 |
| 收到旧 `config_id`/旧 step | 迟到或重放消息 | 丢弃并计数，不推进状态 |
| 任务图收到旧 epoch 结果 | lease 已过期或已被重派 | reject，不覆盖 winner |

## 8. 从启动到实际参与：新人排查清单

下列检查项都可以用 HTTP 接口完成；不方便敲 curl 时，可以用交互外壳 `src/tui_textual.py`（`qlh` / `start_tui.sh` / `start_tui.bat`）查看状态、节点、队列、日志与设备画像，或用只读薄层 `python src/tui_commands.py <command>` 直接查一条。两者都只是既有 HTTP 接口的终端外壳，不新增控制协议，也不改变任何准入判定；`--host/--port` 可查询远程 Tailscale 主节点。写操作（连接主节点、注销、角色转让等）请在交互外壳或 API 侧完成。

### 8.1 主节点

1. 确认选择的引擎、模型 format、模型 revision 和 SHA256；
2. 确认 Tailscale IP/广告地址可从对端访问；
3. 确认 `QLH_CLUSTER_SECRET` 一致且足够长；
4. 查看 `/api/health`、`/api/status` 和集群状态，而不是只看 UI 在线灯；
5. 检查层分配是否连续覆盖所有 Transformer 层，首段包含 Embedding，LM Head 归属合理；
6. 检查每个从节点的 `layer_config_ack`、ready 和模型身份；
7. 发送一条短 Q0 请求，查看 `execution_mode`、`distributed_used`、`workers_used`、step metrics 和 fallback reason；
8. 再测试断开从节点，确认当前 attempt 清理并回退，不留下下一次请求可见的旧 KV。

### 8.2 PyTorch 从节点

1. 确认使用 Safetensors，而不是 GGUF；
2. 确认 PyTorch/Transformers/tokenizer/模型架构与主节点兼容；
3. 确认角色是 client，广告地址不是 localhost；
4. 查看 `layer_config` 的 `config_id`、层范围和 `model_sha256`；
5. 确认加载后发送 ready ACK；
6. 检查 `layer_forward` 的 step 是否严格从 0 开始，Decode 是否命中本地 KV；
7. 任务结束后确认本地活动 task 和 KV 都被清理。

### 8.3 任务链 Worker

1. 先确认任务图实验开关和 `adapter_connected` 状态，不要通过修改 UI 文案绕过准入；
2. 检查 v2 hello 协商、能力和模型身份；
3. 检查 Provider `max_concurrency` 和 reservation 数；
4. 对每个 Stage 记录 `workflow_id/stage_id/attempt_id/lease_epoch`；
5. 断线后确认旧结果被拒绝，新 attempt 才能成为 winner；
6. 取消后确认 journal、Provider cancel、reservation release 和 UI 终态一致。

## 9. 常见错误观念

| 错误观念 | 正确认识 |
|---|---|
| 节点越多，每台机器层数越平均越好 | 层分配必须看算力、内存、I/O 头和网络；平均分可能让瓶颈节点拖慢全链 |
| 主节点是控制节点，所以不应该计算 | PyTorch 层流水线需要主节点首段；强主节点通常应承担更多工作 |
| TCP 连通就代表分布式推理已经生效 | 还必须经过模型身份、层配置、ready ACK 和实际结果校验 |
| Android 接入主节点就算参与层间推理 | 当前 Android 是本地 GGUF 或 HTTP 客户端，不是 PyTorch layer Worker |
| `int4` 在所有引擎和 CPU 上都一样 | bitsandbytes INT4 是 CUDA 优先；GGUF Q4_K_M 是另一套 llama.cpp 工件 |
| `torch.compile` 打开就必然更快 | 只在满足 CUDA + FP16 等门槛时尝试，必须以同条件基准为准 |
| 任务链可以把失败 Stage 的正文直接传给聚合 | 下游接收受控的 Stage 状态和合法输出；错误需要稳定 error code，避免污染聚合输入 |
| 可以让新 Provider 接着旧 Provider 的 hidden state 继续 | Provider 是故障边界；失败后清理并重启新的 attempt，不能混用内部状态 |
| 接了 TP 孤岛就等于 QLH 支持张量并行 | QLH 只把整请求交给孤岛，感知不到其 rank、并行策略和 collective；自己编排 collective 的 Provider 仍未实施 |
| 配了外部端点，请求就会自动用上 | 数据作用域默认 `opt_in`：请求必须显式带 `allow_external`，且 `prefer_external` 或达到长度阈值才真正外发；取值写错会 fail-closed 成 `deny` |
| 投机解码已经能加速生产聊天 | 它只有默认关闭的独立实验端点，未接生产解码循环；PoC 的 draft 侧是占位实现，不承诺任何加速比 |
| QLH 取消了，外部端就停了 | OpenAI 兼容端点无服务端取消原语；断开 SSE 只是 chunk 边界 best-effort，外部端可能算完并照常计费 |
