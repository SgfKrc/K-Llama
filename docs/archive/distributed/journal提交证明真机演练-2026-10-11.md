## 1. 目的与范围

验证 #93 新接线的「提交证明」链路在**真实跨机 TCP** 上成立：

| 场景 | 期望 |
|---|---|
| S1 多数耐久推送（回包前栅栏） | `accepted=True`、`durable_acks>=required` |
| S2 栅栏拒绝 | 未达多数 ⇒ `accepted=False` / `quorum_not_reached`（**不回 OK**） |
| S3 跨机追赶 | 落后副本从对端拉回已自洽前缀并追平 |
| S4 接管核对 | 落后 ⇒ 拒绝（`committed_prefix_behind`）；有追赶钩子 ⇒ 先追上再放行 |

**不在本次范围**：物理故障注入（网络分区 / split-vote / 日志分叉）——属破坏性演练，
按约定单独安排。

## 3. 实测输出（原文）

```
[source] workflow=wf-drill last_sequence=3 digest=91077c133476...
[peers] [('127.0.0.1', 9201), ('127.0.0.1', 9202), ('100.116.17.12', 9200)]
[S1 quorum-push]       accepted=True  durable_acks=3 required=2 failures={}
[S2 barrier-refuse]    accepted=False status=quorum_not_reached durable_acks=1 required=2 failures={'127.0.0.1:1': 'JournalReplicationTransportError'}
[S3 catch-up]          before=1 recovered=True after=3 verified=True failures={}
[S4 enforce-cold]      refused code=committed_prefix_behind
[S4 enforce-recovered] accepted last_sequence=3
```

要点：

- S1 的 3 个 ACK 是**耐久 ACK**：`send_checkpoint` 会校验对端回显的 `durable_sequence` 与
  `checkpoint_digest` 与请求一致，否则判为失败 ⇒ 3 个 ACK 意味着三处都**真正落盘到同一点**。
- S2 的 `durable_acks=1 < required=2` ⇒ 函数返回 `accepted=False`；HTTP 端点在此分支回 **503**
  （该 HTTP 语义由 `tests/test_journal_replication_quorum.py` 的端点级测试钉住）。
- S3 的 `before=1 → after=3` 且 `verified=True`：拉取到的 checkpoint 被 `apply_checkpoint` 接受
  并让副本重新自洽（追赶前它只是"自洽的落后前缀"）。
- S4 先在没有追赶钩子时**拒绝接管**，加了钩子后先追平（3）再放行。

## 7. 第二轮：端点真机（#93 剩余项③）

拓扑：本机 master（带 `QLH_JOURNAL_REPLICATION_*`）+ 三个 replica 目标（本机 `9201`/`9202` +
ROG `100.116.17.12:9200`），栅栏阈值 `quorum_size=2`。

先造一个**真实 workflow**（非脚本 journal）：`execution_mode=task_graph` +
`task_graph_template=dual_candidate` + `workflow_id=wf_*` 走一次 chat ⇒
`wf_drill1791705509`（15 个 journal 事件）。

| 场景 | 请求 | 结果 |
|---|---|---|
| 多数耐久 | `POST /api/workflows/journal/replicate?workflow_id=wf_drill1791705509` | **200** `accepted=true, durable_acks=3, required_quorum=2, failures={}, event_count=15, durable_sequence=15` |
| 栅栏拒绝 | 停掉本机两个目标后同一请求 | **503** `journal 多数耐久未达成（durable_acks=1/2），已拒绝回包。` |

真机暴露的接口事实（本文档早期版本写错过，已一并修正）：

- 端点是 `POST /api/workflows/journal/replicate`，`workflow_id` 走 **query 参数**（不是路径参数）；
- 造 workflow 必须同时给 `execution_mode=task_graph` 与 `task_graph_template`，且
  **`workflow_id` 必须以 `wf_` 开头**（否则 400）；
- `execution_mode=task_graph` 要求**整模已加载**（`model_host.model_loaded` 且
  `model_manager.is_loaded`）⇒ 带 `QLH_LAYER_GGUF` 的分层 master 不满足 ⇒ 本机演练时去掉了分层配置。

## 8. 第二轮：真机完整自动选主接管（#93 剩余项②）

拓扑：`QLH_NODE_ROLE=auto` 的 master（本机，身份 `master-voter`）+ 三机 voter
（`master-voter` / `rog-voter` / `y700-voter` @9102）。接管由 `scheduler.start()` 自动触发，
落 `event=auto_role_start` 日志行。

| 场景 | 条件 | 结果 |
|---|---|---|
| **A 拒绝** | leader 提出水位，但 voter 都**不**耐久持有该前缀 | `accepted=False state=read_only runtime_role=client reason=**quorum_watermark_unavailable**` |
| **B 放行** | 让 ROG voter 也指向持有该 workflow 的副本 | `accepted=True state=leader runtime_role=master reason=quorum_certificate_accepted`；证书携带 `CommitWatermark(wf_drill1791705509, 15, 958f7ebb…)`，签名者 `(master-voter, rog-voter)` |

**本项真机挖出并修掉一个真缺陷**（提交 `3dd1f138`）：远程 voter 把水位错误码吞成了
`quorum_unavailable`，主节点因而无法区分「多数不可用」与「多数不持有」—— 两处吞码分别是
`AutoRoleRuntime.handle_rpc` 的兜底 `except` 与 `HTTPRemoteVoter._call` 的错误码白名单。
修复后 A 场景的 reason 才显示为 `quorum_watermark_unavailable`（修复前是 `quorum_unavailable`）。

**部署同步清单（真机踩到）**：给远端 voter/节点换新版时，除了
`cluster_auto_role_runtime.py`，还必须同步 **`cluster_control_contract.py`** 与
**`cluster_quorum.py`** —— 漏了前者会让 voter 直接 `ImportError: cannot import name
'CommitWatermark'` 而起不来（表现为 voter 端口不监听、主节点侧只看到 quorum 不可用）。
