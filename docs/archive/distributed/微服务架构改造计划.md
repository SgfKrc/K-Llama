## 一、背景与动机

### 1.1 现状问题

冷启动优化方案（2026-07-11 创建）已落地：保留 sklearn 依赖治理、`.pyc` 预编译、导入面治理、PyInstaller 打包等。但单体架构的**结构性**问题没有消失：

| # | 问题 | 证据 |
|---|------|------|
| 1 | **任何变更都要重启整个进程，重启代价 = 模型加载**（12s 量级，其中 model_module 子树 9.7s） | `import_time.log`：api_server 累计 12.1s；transformers 6.06s、torch 1.97s、sklearn 1.51s |
| 2 | **从节点被迫加载全部代码**。从节点与主节点跑同一套 `api_server.py`（`config.py:350` 的 `QLH_NODE_ROLE` 区分），实际只需要推理数据面（model_module 层段 + tcp_comm 客户端），却 import 了 FastAPI、scheduler、全部 110 个端点 | `api_server.py:7579-7587` 唯一入口 `uvicorn api_server:app` |
| 3 | **跨模块运行时循环依赖**：`api_server.py` 顶层 import scheduler（:48），scheduler 20+ 处函数内 `import api_server as _api` 反访问 `_api.model_manager`（:3461、:8254 等） | scheduler 靠"延迟 import"规避导入环，进程内耦合无法独立演进 |
| 4 | **config.py 是全局可变状态**：scheduler 在运行时写回 `cfg.NODE_ID`（`scheduler.py:127-140`），其他模块函数内重新 `import config as cfg` 感知变化，无显式变更通道 | `config.py:40/403 ↔ node_config.py:221` 函数内双向延迟引用 |
| 5 | **控制面技术栈单一**：会话 CRUD、日志管理、审查投票、邮件通知、设备画像等纯 IO/状态逻辑用 Python 承载，没有获得推理能力，却共同承担冷启动与内存成本 | api_server 端点分布：会话 8 个、日志 12 个、审查 8 个、设置 2 个 |

### 1.2 目标

1. **推理数据面保留 Python**：model_module / llama_engine / paged_kv_cache / island_engine / external_provider / speculative / diffusion 及流水线执行段，独立为 `inference-svc`。
2. **调度器保留 Python 独立成服务**：scheduler 与数据面深度耦合（运行时调用 `model_manager.forward_layers`、张量序列化、KV 缓存生命周期、TCP 主从协议），自身冷启动仅 3.2ms 不是瓶颈，迁移新语言成本极高收益低 → 独立为 `scheduler-svc`。
3. **控制面迁移 TypeScript**：对外 API 网关（110 端点壳 + SSE + 静态前端）→ `api-gateway`（NestJS + Fastify）；会话/日志/审查/通知/设备画像/模型注册/任务图控制面 → `control-svc`（TS）。
4. **冷启动与部署收益**：主节点用户感知可用时间从 12s+ 降到 <1s（网关先行、模型异步加载）；从节点启动到注册从 12s+ 降到 ~2s（不再 import fastapi/scheduler）；服务常驻、崩溃自拉起，模型加载只发生在推理进程内且不随网关重启。

### 1.3 非目标（明确不做）

- 不重写推理核心（量化、KV 缓存、层前向、投机解码算法语义不变）。
- 不改变 TCP 主从协议对外行为（tcp_comm 帧格式、MessageType、HMAC 认证、心跳语义）。
- 不改变前端 / Android / TUI 的 API 契约（`BASE=/api`、SSE 格式、错误 `detail`/`request_id` 结构在阶段 2 保持兼容）。
- 不做容器化（当前交付形态是 Windows 安装包 + Linux .deb + 裸机部署，无 Docker 环境）。

### 1.4 实施策略：并行共存（2026-08-03 修订）

> 本策略修订取代此前“边拆边删”的表述。**新微服务一律独立实现，不修改现有 Python 后端（api_server.py / scheduler.py 及控制面模块）的一行代码，也不改变现有启动方式**；现有后端保持为唯一可运行基线。全部微服务完成并通过验收后，才按 §5.0 标记清单在清理阶段（§5.1）统一清理。

| 规则 | 内容 |
|---|---|
| 1 复制迁移 | 数据面执行段迁 inference-svc 采用**复制**而非移动：源函数保留在 api_server.py / scheduler.py 内不动（单进程拓扑继续可用），服务侧持有等价副本；行为等价纪律不变（副本不改业务逻辑） |
| 2 新增入口 import 复用 | scheduler-svc 通过新建 `scheduler_svc_main.py` import 现有 `scheduler.py` 运行（阶段 0 的 `Scheduler(host=...)` 注入已就绪，构造时传 `InferenceClient`），scheduler.py 源码零改动 |
| 3 并行运行错开端口 | 开发期新旧拓扑同时运行时用 `QLH_*_PORT` / `QLH_SERVER_PORT` 等环境变量错开监听端口；生产切换只发生在清理阶段 |
| 4 删除动作冻结 | 阶段 2.5（FastAPI 退役）、阶段 3.3（Python 控制面清理）、`start_backend.bat` 改造等一切修改/删除现有后端的动作不再于原阶段执行，统一移至清理阶段（§5.1），当前仅保留标记（§5.0） |
| 5 桩与临时服务不动 | `scripts/dev_stubs.py`、`src/legacy_control.py` 是网关当前可运行性依赖，真实 scheduler-svc / inference-svc / control-svc 全部完成前不得移除；它们本身列入 §5.0 待退役标记 |

### 2.3 冷启动分布（import_time.log 复核）

| 模块/子树 | 耗时 | 占比 |

| model_module 子树 | 9.71s | 80.2%（transformers 6.06s + torch 1.97s + sklearn 1.51s + pandas 0.41s；model_module 自身仅 358ms） |

### 4.1 inference-svc 契约（HTTP :8010）

```http

GET  /v1/ready                           # 模型/层段已就绪（区分 /health 与 /ready，冷启动方案 §5.4 要求）
GET  /v1/status                          # 引擎、当前模型、显存、层段、KV 缓存状态

POST /v1/diffusion/unload                # 取消活动任务并释放 pipeline
POST /v1/diffusion/generate              # 202 + 异步 job；支持 preset 或显式参数

POST /v1/layers/load                     # 层段加载（client 角色；master 角色本地层段同用）
POST /v1/layers/unload                   # {layer_range}

```

**SD 本地边界（2026-08-05）**：上述 diffusion 契约仅在 `master` 角色开放；LLM 与 SD 通过同一模型生命周期锁显式互斥。资产登记、job 和 PNG blob 当前均为进程内状态，blob 上限为 16 项/64 MiB/TTL 30 分钟，服务重启即丢失；它不是 SD-N3 的跨节点 blob/Worker 协议，也不得计入分布式任务统计。任意服务器路径的 inspect/register 只允许主节点本机调用，网关会按原始客户端地址再次拦截。

**张量跨进程传输策略（阶段 1 决策）**：
- 主节点本机 `scheduler-svc → inference-svc`：`/v1/layers/forward` 的 hidden states 走 **loopback TCP + 既有 `serialize_tensor_fast`**（`tcp_comm.py:670-792`），每 token 传输量 = hidden 向量（Qwen-1.8B：2048 float16 ≈ 4KB），loopback 上开销 ~0.1ms 级。**KV 缓存始终留在 inference-svc 进程内**，跨进程只传 `past_key_values_ref`（任务 ID + 层段），不传 KV 数据。
- 性能验收门槛：分布式流水线 token 级延迟相比单进程基线劣化 <5%。若 loopback pickle 不达标，升级为**共享内存环形缓冲**（`multiprocessing.shared_memory`），契约不变（`tensor_ref` 换为共享内存名+offset），此为本计划的预留方案，不做第一实现。

### 4.2 scheduler-svc 契约（HTTP :8020）

> **对外适配原则（关键）**：§4.2 是**调度器内部契约**，不是网关对外的适配契约。网关对外端点必须按 **api_server 现有路径/方法/字段**原样实现（以 §2.2 域清单 + `tui_admin.py` 全部调用点为准，见 2.4），内部契约与对外契约**不得混用**。典型差异：对外是 `POST/DELETE /api/cluster/spare-master`、`PUT/DELETE /api/cluster/layers`、`GET /api/cluster/config`，对应内部能力是 spare 设置/清除、分层覆盖读写、配置读取——内部端点形态由 scheduler-svc 自行决定，网关负责映射。

> **落地决策（2026-08-02，T3）**：网关对 `/api/cluster/*` 采用 **1:1 透传代理**——内部端点路径 = 对外路径去掉 `/api` 前缀（`GET /api/cluster/nodes` → `GET /cluster/nodes`），实现见 `gateway/src/modules/cluster/cluster.controller.ts`；scheduler-svc 按 §2.2 字段契约提供响应（`gateway/test/fake-scheduler.ts` 是字段对齐的测试基线）。下方 `/v1/*` 清单因此**降级为参考**：scheduler-svc 实现时以透传路径 + §2.2 字段为准，`/v1/*` 形态不再要求。

## 七、风险与回退

| # | 风险 | 影响 | 缓解 / 回退 |
|---|------|------|-------------|
| 1 | 流水线时序敏感，进程间 IPC 引入抖动 | 分布式推理延迟劣化、超时误判 | 本地前向优先 loopback `serialize_tensor_fast`（复用成熟序列化）；预留共享内存方案（契约不变）；每阶段双节点实测把关 |
| 2 | 张量跨进程传输开销失控 | token 级延迟劣化 | KV 缓存永不跨进程（只传 ref）；4KB/token 传输量上限可量化；性能门槛 §6.3 |
| 3 | 行为等价移植中出现隐性差异 | 流式事件、错误结构、状态机偏差 | "纯移动、禁重构"纪律；逐函数 commit + 契约对比脚本；1089 项回归兜底 |
| 4 | TS 网关与 FastAPI 行为差异 | 前端/Android/TUI 兼容破坏 | 前端零改动为硬验收；`contract_diff.py` 逐字段对比；SSE 逐字节保真；**TUI 以 38 个调用点为契约测试用例（2.4），5 项细节（/api 前缀、detail JSON、DELETE 返回 JSON、数值字段类型、Log-Token 可选语义）逐项断言**；**网关适配面必须覆盖 TUI 依赖的全部 cluster/device 端点（§4.2 内部契约之外的约 15 个端点），不得按 §4.2 清单透传实现** |
| 5 | 会话/审查等状态数据迁移不兼容 | 历史数据丢失 | 阶段 3 先迁移数据读取层，旧格式文件直接读取为验收项；PostgreSQL 表结构沿用 |
| 6 | Windows 打包复杂度上升（多进程 + Node 运行时） | 安装包构建失败 | 阶段 4 专项；Node SEA 单文件化；PyInstaller 多 spec 复用现有 venv 隔离策略；`QLH_MONOLITH=1` 保留到阶段 4 末尾 |
| 7 | 团队对 NestJS/TS 后端不熟 | 开发节奏下降 | 控制面为纯 IO/CRUD 无重计算，TS 性能足够；先网关（脚手架自动生成）后控制面；每域独立小步提交 |
| 8 | 从节点多进程部署变复杂 | 从节点配置负担 | 从节点 = 1 进程（inference-svc client 角色），比现状（整包 api_server）更简单；连接配置沿用 `QLH_CLIENT_MASTER_HOST/PORT` |
