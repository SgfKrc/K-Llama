| **E. ExecuTorch（端侧）** | `.pte` 导出 → 真机 → 与 GGUF/JNI 同量化对照 | ⚠️ **实验立项，未执行** | 票 `CORE-ET-EXP-01` | 导出与真机数据（**Android 设备也是单机可做，不依赖 Surface**）|

### 1.1 三条重要关系

1. **B 与 C 是孪生的**：同一套「层切分 + hidden 传递」机制；区别只在**是否按需加载权重**
   （B 的上游仍载整模，C 不载）。**B 的"手动 4 层前向"正是 C 的上游实现。**
2. **C 是 D 的"跨框架版"**：D 档用 PyTorch 做层流水线（已有生产路径），C 把它扩展到
   **一侧 torch + 一侧 llama.cpp**。
3. **A 与 B/C 不冲突但不同层**：A 解决「单机装不下 → 借别的机器」；
   B/C 解决「两侧异构引擎协作」。按既有裁决，**Relay 默认关闭、不替代 RPC**。

### 1.2 ⚠️ 性能上的诚实结论（本轮实测）

跨框架接力（B/C）在**单序列**上**不具备性能优势**，原因是 **batch=1 是 memory-bound**：
上游 torch-GPU **9.2 ms/层** ≈ 下游 llama.cpp-CPU **8.3 ms/层** ——
**决定速度的是"搬运多少字节"，不是"CPU 还是 GPU"**。

**→ B/C 的价值在「能力组合」与「容量」，不在「提速」**（详见 §14 / 性能汇总报告）。
