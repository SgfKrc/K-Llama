### 2.2 分布式执行形态对照（《文档状态与维护规则》第 10 条）

| 执行模式 | Provider | 参与节点（统计口径） | 故障边界 | 降级路径 |
|---|---|---|---|---|
| `pytorch_layer` | 本地 PyTorch 层段（`scheduler` + `model_module`） | 主节点 + 同 artifact 的 PC 从节点 | 节点下线 → 重编排 → 当前 attempt 失败 | 回退主节点完整模型 |
| `task_graph` | `local_full_model` / `remote_full_worker` | 主节点 + 已认证 PC Full Worker（仅完成 attempt 的计入 `nodes_participated`） | attempt / lease / epoch / winner fencing | 跨 Provider 重派 → 本地 `local_full_model` |
| `island`（路线 A） | 网关节点的 island 引擎 | 孤岛计 **1 个**逻辑节点；岛内 N 张卡不得计入 | 网关探活失败 = 该逻辑节点下线 | 复用现有节点下线 → 重编排路径 |
| `external_api`（路线 B） | `ExternalOpenAIProvider` / `ExternalChatClient` | 外部端点**不入图**、不计为集群节点 | HTTP 4xx/5xx/超时按 `retryable` 分类 | 回退本地路径并记 `fallback_reason` |
| `speculative_assisted`（路线 C） | 本地 draft + `ExternalVerifyClient` | 本机 + 外部 verify 端点 | 取消粒度为轮边界；已发出的 verify 不可服务端取消 | **无生产降级路径**——未接入 `/api/chat`，仅实验端点可达 |

**做了什么。** 这 6 项都不是"代码不好看"，而是在真实集群里会表现为具体运行故障——对答辩与结题材料而言，这一列比修复本身更有说明力：

| "外部推理服务已经可用了" | 默认 `opt_in` 且请求必须显式 `allow_external`，未授权数据不出集群。是否放开 `allow_all` 是**人的决定**，不能因为要跑通实验就改默认值 |
| "1650 项全部通过" | 不准确；临时验证结果为 `1643 passed / 7 skipped / 0 failed`，但当前仓库正式基线仍为 `1641 passed / 7 skipped / 2 failed`。跳过项仍需对应环境或依赖，失败项需先落地修复 |
| "任务链分布式已经能用了" | 停在 **TC-N2.4 物理设备准入**：`adapter_connected=false`、`task_dispatch_enabled=false` 依旧保持，只有显式实验开关下的路径可用 |
| "投机解码的输出分布与大模型严格一致" | 该性质是**投机采样纯核心**的性质。经 OpenAI 兼容接口只能拿到 top-k logprobs：接受判定精确，但**修正 token 的残差采样被 top-k 截断**，偏差随 `QLH_SPEC_TOP_LOGPROBS` 增大而收敛，自建端点返回完整 logits 才能彻底消除 |
| "孤岛可以承担层间流水线的重层段" | 那是 A-1 形态，**尚未实现**。已实施的是整请求形态：主节点在 `compute_layer_assignment` 中按 `device_info.island.enabled` 过滤孤岛节点，网关侧收到分层配置也会拒绝 |
| "Android 可以参与分布式推理" | 取决于指哪一种。Android 可作请求端与 presence 节点；**不参与 PyTorch 层间拆分**（上报 `pipeline_worker=false`，主节点排除 `node_type=android`）；完整 Worker 尚未实现 |
