## 1. 结论先行

当前校园网环境已经确认 `UDP=false`，Tailscale 无法建立直接 WireGuard UDP 路径，只能使用中继。项目目前使用的自建 DERP 通过 HTTPS/TCP 443 可达，已经解决“节点完全无法通信”的首要问题，但没有解决中继吞吐、单点故障、路径观测和 QLH 内层 TCP 在弱网上的队头阻塞问题。

专项路线按以下优先级推进：

1. **保住现有自建 DERP**：补齐版本、证书、健康探测、容量、备用区域和故障记录；它是当前最可靠的生产兜底。
2. **先增强 QLH 自身协议**：控制、任务、张量和 Blob 分通道；增加路径观测、幂等、分块、校验、续传、流控和自适应超时。
3. **增加应用层 WSS/TCP 443 传输**：主节点 TCP 443 可达时，Worker 直接建立 `wss://` 长连接，把 QLH 大数据面移出 DERP；Tailscale 不稳定时也可承载控制面和任务链。这比修改 `tailscaled` 风险低，也能覆盖 Android。
4. **再做 `qlh-netshim` sidecar PoC**：先复用成熟的 WebSocket 隧道内核验证 UDP-over-WSS；只有证明 stock Tailscale 能稳定接入端点重定向后，才考虑产品化。
5. **不把 KCP、QUIC、Hysteria 或“FakeTCP”当作无 UDP 网络的主解**：前几者仍依赖 UDP；FakeTCP 并不等于真正的 TCP，网络若按协议或状态机丢弃 UDP/异常报文，仍可能失败。

Tailscale 官方说明，直连使用 UDP；UDP 被完全阻断时，通用回退是 DERP，Peer Relay 只有在客户端仍能访问其 UDP 端口时才可用。DERP 数据链路使用 HTTPS/TCP 443，因此“UDP 被阻断”会导致直连失败，但**不会单独解释公共 DERP 的 TCP 443 也不可达**。[连接类型](https://tailscale.com/docs/reference/connection-types)、[防火墙端口](https://tailscale.com/docs/reference/faq/firewall-ports)

## 2. 当前网络事实与因果边界

### 2.1 2026-08-08 本机只读诊断快照

本次使用 `tailscale status` 和 `tailscale netcheck` 只读取连接状态；文档不保存节点 IP、自建 DERP 域名、证书或密钥。

| 项目 | 实测结果 | 解释 |
|---|---|---|
| UDP | `false` | STUN 未收到本机出站 UDP，直接路径不可用 |
| IPv4 公网映射 | 未获取 | 无法通过 STUN 得到外部 UDP 地址 |
| IPv6 | 不可用 | 当前不能作为直接路径替代 |
| 最近 DERP | 自建 DERP | 客户端已选择自建区域 |
| 自建 DERP RTT | 约 20 ms | 当前可用，且明显优于唯一有结果的远端公共区域 |
| 公共 DERP | 大多数无延迟结果 | 除 UDP 外，还需要排查 DNS、TCP 443、TLS/SNI、出口路由或目标过滤 |
| 活跃从节点路径 | `relay` 经自建 DERP | 当前双机分布式实测使用的是中继路径，不是 Tailscale 直连 |

`tailscale netcheck` 的 `UDP` 字段表示 STUN 是否收到出站 UDP。DERP 则通过 TCP 443 建立连接。所以上表只能得出两条独立结论：

1. `UDP=false` 足以证明 Tailscale 直连在该网络下不可用；
2. 多数公共 DERP 无结果还存在额外的 HTTPS 出口可达性问题，不能仅归因于 UDP。

官方诊断字段定义见 [Device connectivity](https://tailscale.com/docs/reference/device-connectivity)。

### 2.2 建议补采的校园网证据

每次网络策略变化后保存脱敏结果：

```text
tailscale netcheck
tailscale status
tailscale ping <peer>
tailscale debug derp
nslookup <public-derp-host>
TCP 443 connect + TLS handshake（只记录成功/阶段/耗时，不记录地址）
```

诊断要分层，避免“能 ping 域名”就推断 DERP 可用：

| 层 | 检查 | 失败含义 |
|---|---|---|
| DNS | A/AAAA 是否返回 | 域名解析或污染问题 |
| TCP | 443 三次握手 | 出口路由、ACL、目标 IP 或端口阻断 |
| TLS | 证书、SNI、ALPN | TLS 检查、代理或证书问题 |
| DERP upgrade | HTTP 后协议切换 | 普通反向代理不兼容、DERP 服务异常 |
| Tailnet data | `tailscale ping/status` | 端点选择、ACL、客户端或中继数据面问题 |

## 3. 当前 QLH 通信实现

### 3.1 已实现能力

QLH 当前不是直接发送 UDP。应用在 Tailscale 虚拟网卡之上使用普通 TCP：

```text
QLH message / tensor / task stage
  -> QLH TCP framing（默认 8888）
  -> inner TCP
  -> Tailscale WireGuard packet
  -> direct UDP 或 DERP HTTPS/TCP 443
```

[tcp_comm.py](../../../src/tcp_comm.py) 和 [config.py](../../../src/config.py) 已实现：

- TCP 长连接，默认主节点端口 `8888`；
- 4 字节大端长度头 + JSON/二进制正文；
- 单包上限 256 MiB，正文读取前校验长度；
- `torch.save` 张量序列化；
- HMAC-SHA256 注册认证与时间窗口；
- 3 秒心跳、RTT 估计、连续心跳缺失离线判定；
- 断线后连接重试和持续重连；
- 半帧超时后关闭连接，避免字节流失步；
- Task Worker 的 reservation、lease、epoch、取消和迟到结果 fencing；
- TaskGraph journal 可把任务状态与临时网络连接解耦；
- 图像 Blob 数据面具备内容摘要、Range 和 attempt 作用域的基础设施。

这些能力已经能处理“连接断开”，但还不能充分处理“连接没有断、只是非常慢或间歇性卡住”。

### 3.2 尚未实现的弱网能力

| 能力 | 当前状态 | 影响 |
|---|---|---|
| Tailscale 路径识别 | 未接入调度；只知道 Wi-Fi/以太网 | 无法区分 direct、DERP、peer-relay |
| 控制/张量/Blob 分通道 | 单节点主要共享 TCP 字节流 | 大张量可阻塞心跳、取消和状态消息 |
| 自适应心跳 | 固定 3 秒和固定离线窗口 | 高抖动时可能误离线，低延迟时恢复又偏慢 |
| 块级 ACK/续传 | 普通帧整体成功或整体失败 | 大 Blob/模型中断后重复传输 |
| 连接迁移 | 断开后重建，任务级恢复 | Wi-Fi/热点切换会打断活动流水线 |
| Path circuit breaker | 未统一 | 不可用节点可能反复进入候选路径 |
| WebSocket 传输适配 | 未实现 | Tailscale/DERP 整体不可用时无应用层备用通道 |
| 传输级背压 | 主要依赖 socket 阻塞和上层 deadline | 慢接收端可能拖住发送线程或占用大内存 |
| 弱网压测通道 | 仅有真机计划和零散故障测试 | 没有固定丢包/抖动/限速回归门 |

### 3.3 DERP 下的 TCP-over-TCP 问题

当 QLH 的内层 TCP 经 DERP 的外层 TCP 传输时，会形成嵌套可靠传输：

```text
QLH inner TCP:      [control][tensor chunk][heartbeat][cancel]
DERP outer TCP:     [encrypted WireGuard packets in one ordered stream]
```

外层 TCP 丢失一个段时，后续内容即使已经到达也要等待重传；内层 TCP 可能同时判断拥塞并重传。结果是：

- 心跳可能排在大张量和丢失段后面；
- 单次抖动被放大为整条连接的停顿；
- 多个逻辑任务共享连接时互相影响；
- 层间流水线每 token 都等待网络边界，受影响最大；
- 任务链、模型下载和图像 Blob 粒度较大，更适合做分块续传与重派。

TCP 是有序可靠字节流，WebSocket 同样建立在 TCP 上；WSS 能提高穿透性，但不会消除 TCP 队头阻塞。[TCP 标准 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)、[WebSocket RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)

## 4. 自建 DERP 运行基线

### 4.1 当前定位

自建 DERP 是当前校园网的**可用性基础设施**，不是 QLH 代码内的组件。它盲转发端到端 WireGuard 加密包，不能读取 QLH prompt、张量或结果，也不能替代 QLH 的 HMAC、任务租约和模型身份校验。

官方建议自建 `derper` 与客户端同步更新；DERP 在 TLS 内从 HTTP 切换到专用双向协议，不能当普通 Web 应用放到任意 HTTP 反向代理之后，也不宜放在全局负载均衡器之后。[官方 derper 运维说明](https://github.com/tailscale/tailscale/blob/main/cmd/derper/README.md)

### 4.2 必须建立的运维清单

| 项目 | 要求 |
|---|---|
| 监听 | TCP 443 必须稳定可达；TCP 80 用于证书/探测时按部署方式开放 |
| STUN | UDP 3478 可开放；校园网阻断时不影响 DERP TCP 转发，但会影响端点发现和 netcheck |
| 地址 | 静态 IPv4，条件允许时增加静态 IPv6；DERP map 明确地址 |
| 证书 | 公信 TLS 证书、自动续期、到期告警；禁止把私钥写进仓库 |
| 版本 | `derper` 与 Tailscale 节点同步维护；`--verify-clients` 时必须同 revision |
| 监控 | `derpprobe`、`/debug/varz`、连接数、带宽、错误率、TLS 到期、进程重启次数 |
| 容量 | 记录出口带宽、月流量、CPU、内存和并发连接；推理期间重点看 tx/rx 排队 |
| 日志 | 只保留连接元数据和错误，避免收集不必要的节点标识 |
| 备份 | 增加第二个独立 region；优先两个单节点 region，而不是同一 region 内复杂 mesh |
| 回滚 | 保留至少一个官方 DERP 区域作为非校园网络兜底，未完成故障演练前不要全部禁用 |

### 4.3 当前进度

| 项目 | 状态 | 证据/缺口 |
|---|---|---|
| 自建 DERP 上线 | 已完成（外部基础设施） | 当前客户端可达，约 20 ms |
| 校园网 UDP 阻断确认 | 已完成 | `netcheck UDP=false` |
| 真实从节点经 DERP 通信 | 已确认 | 活跃节点显示 `relay`，已有分布式真实请求证据 |
| 公共 DERP 故障分层定位 | 未完成 | 需区分 DNS/TCP/TLS/DERP upgrade |
| DERP 监控与 SLO | 未在仓库登记证据 | 需脱敏运维记录 |
| 第二独立 DERP region | 未确认 | 当前存在单点风险 |
| DERP 故障切换演练 | 未完成 | 需在活动任务中断场景验证 |

## 5. 目标传输体系

### 5.1 分层结构

```text
业务语义层
  TaskGraph / Pipeline / Image Blob / Model Sync
        |
可靠消息层
  request_id + attempt_id + seq + checksum + ACK + resume + fencing
        |
传输适配层
  Tailscale TCP | direct-to-master WSS 443 | LAN TCP | future netshim UDP-over-WSS
        |
路径层
  Tailscale direct UDP | direct TCP/WSS | self DERP | official DERP | peer relay | public HTTPS gateway
```

业务层不得直接依赖某个 socket。传输更换只能改变时延和吞吐，不能绕过：

- `workflow_id/stage_id/attempt_id/lease_id/epoch`；
- 模型 SHA、tokenizer/revision 和层配置 generation；
- HMAC/TLS/ACL；
- winner、迟到结果拒绝和 journal 终态；
- 取消与资源回收。

### 5.2 传输抽象

建议新增内部接口，不一次性重写现有 `TCPServer/TCPClient`：

```python
class ClusterTransport:
    def connect(self, endpoint, capabilities): ...
    def send(self, channel, envelope, payload): ...
    def close_stream(self, stream_id, reason): ...
    def snapshot(self) -> dict: ...
```

首批实现：

| Transport | 作用 | 状态 |
|---|---|---|
| `LegacyTcpTransport` | 包装当前 8888 TCP 协议，行为不变 | N1 兼容层 |
| `WebSocketTransport` | Worker 直连主节点或公网网关的 WSS 443 | N2 PoC |
| `BlobHttpTransport` | 复用现有 HTTP Range/Blob store | 已有基础，N3 加续传 |
| `NetshimUdpTransport` | UDP datagram 经 WSS sidecar | N4 实验，不进默认路径 |

### 5.3 通道隔离

至少划分四种逻辑通道，并支持独立队列上限：

| 通道 | 内容 | 优先级 | 弱网策略 |
|---|---|---:|---|
| `control` | 注册、心跳、取消、lease、状态 | 最高 | 小帧、禁止压缩、预留发送额度 |
| `task` | offer/accept/result 元数据 | 高 | 幂等、ACK、重放 fencing |
| `tensor` | hidden states、层结果 | 中 | 有界窗口；超时直接 abort，不做无限重传 |
| `blob` | 模型、图片、较大工件 | 低 | 分块、Range、SHA、断点续传 |

在 TCP/DERP 上可先使用两条物理连接：`control/task` 与 `tensor/blob`。这比在单一有序字节流里只做逻辑优先级更能避免大帧阻塞取消和心跳。

### 5.4 QLH Transport v2 envelope

建议冻结传输包络，不把 WebSocket 自带 framing 当业务协议：

| 字段 | 用途 |
|---|---|
| `version` | 协议协商与兼容拒绝 |
| `message_type` | 复用现有 MessageType / Task Worker schema |
| `channel` | control/task/tensor/blob |
| `connection_id` | 区分重连代次 |
| `stream_id` | 一次张量、Blob 或 Stage 流 |
| `seq` / `ack` | 分块顺序、确认与恢复位置 |
| `flags` | start/end/abort/compressed |
| `payload_len` | 读取前限额校验 |
| `checksum` | 单块 CRC32C 或 BLAKE3；最终对象仍用 SHA256 |
| `request_id/attempt_id` | 关联业务 fencing，不依赖连接身份 |

握手能力建议包含：

```json
{
  "transport_versions": [1, 2],
  "channels": ["control", "task", "tensor", "blob"],
  "max_frame_bytes": 1048576,
  "resume": true,
  "compression": ["none", "zstd"],
  "path_hint": "derp"
}
```

`path_hint` 只用于调度和观测，不能作为认证依据。

### 5.5 分块、压缩与背压

- 默认块大小从 256 KiB 起测，允许 64 KiB～1 MiB 协商；
- 每 stream 使用小窗口 ACK，避免一次把 256 MiB 放进内存或 socket 缓冲区；
- Blob 可按确认块续传；任务元数据只做幂等重发；
- decode hidden state 过期后没有续传价值，应终止当前 pipeline step/task 并清理 KV；
- 通用 zstd 只对可压缩 JSON/Blob 启用；已经加密或高熵数据不重复压缩；
- hidden state 优先研究 INT8/FP8 传输量化，而不是期待通用压缩获得稳定收益；
- 每节点、每通道和每任务分别设置内存/排队预算；超过预算要返回可观测的 backpressure 错误，不得无限排队。

## 6. 应用层 WSS 备用通道

### 6.1 为什么优先做它

如果客户端能访问普通 HTTPS 443，即使 Tailscale DERP map、控制面或虚拟网卡路径异常，QLH Worker 仍可主动连接主节点的公网/校内 WSS 网关：

```text
PC/Android Worker
  -> outbound WSS 443
  -> QLH gateway / FastAPI
  -> Scheduler + TaskGraphCoordinator
```

该路径不尝试承载整个 tailnet，只承载 QLH 自己的消息，因此：

- 不需要修改 stock `tailscaled`；
- PC、Android 和 TUI 都能复用；
- 仍可使用集群 HMAC、模型摘要和任务租约；
- 可只开放 Worker 主动出站连接，无需校园网入站端口；
- 可按通道拆多条 WSS 连接，控制队头阻塞范围。

### 6.2 需要增加的组件

1. `WssClusterEndpoint`：主节点 `/internal/cluster/ws/v1`，不进入公开 OpenAPI；
2. `WebSocketTransport`：PC Python 与 Android OkHttp 客户端；
3. Transport handshake：版本、节点、模型、通道和 frame 限额；
4. 认证：TLS + 现有 HMAC challenge，禁止仅凭来源 IP；
5. 连接绑定：一个 node 只能有一个 active generation，旧连接被 fencing；
6. 代理兼容测试：Nginx/Caddy/直连三种模式；关闭 proxy buffering；
7. 日志脱敏：不得记录 prompt、原始 tensor、cluster secret 或 Bearer grant。

### 6.3 限制

WSS 仍运行在 TCP 上，不能提供 QUIC 那样的跨 stream 丢包隔离。它的价值是“可达性和可控的多连接隔离”，不是让弱网拥有局域网性能。WebSocket 协议基于 HTTP upgrade 和 TCP；QUIC 则明确是 UDP-based，在当前 `UDP=false` 网络下不能作为第一备用路径。[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)、[RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)

### 6.4 主节点能否成为“基于 TCP 的 WireGuard VPN 服务器”

**严格结论：不能把它称为原生 TCP WireGuard。** WireGuard 协议规定所有报文通过 UDP 发送，不提供 TCP listen/connect 模式。[WireGuard 协议说明](https://www.wireguard.com/protocol/)

可以实现的其实是下面四种不同方案：

| 方案 | 技术上是否可行 | DERP 是否承载大流量 | 本项目决策 |
|---|---|---|---|
| 主节点运行原生 WireGuard Server | 可行，但仍是 UDP | 无；前提是客户端能访问主节点 UDP | 当前校园网 `UDP=false`，不能解决问题 |
| 主节点运行 Tailscale Peer Relay | 可行，但客户端到 Peer Relay 仍使用 UDP | 使用主节点而非 DERP 中继 | 当前校园网无法访问 UDP 时不可用 |
| WireGuard UDP 外包 TCP/WSS | 条件可行；两端部署 netshim，把 WireGuard UDP 封装进 TCP/WSS | 主节点 TCP 443 可直达时不经过 DERP | 仅作为独立 PoC；stock Tailscale endpoint 不易接管 |
| 另建真正的 TCP VPN/TUN | 可行，但已不是 WireGuard | 主节点 TCP 端口可直达时不经过 DERP | 暂不优先；权限、路由、MTU、跨平台和 TCP-over-TCP 成本高 |
| QLH 直接连接主节点 WSS 443 | 可行，不构造完整 VPN | 主节点可直达时不经过 DERP | **推荐近期方案**；只承载项目流量，边界最小 |

即使实现 UDP-over-TCP，QLH 当前应用流仍是 TCP，因此会形成：

```text
QLH TCP
  -> WireGuard encrypted UDP
  -> netshim TCP/WSS
  -> Internet
```

这仍是 TCP-over-TCP。丢包会阻塞 netshim 的有序流，内层 QLH TCP 也会独立拥塞和重传。完整 VPN 还需要管理员权限、虚拟网卡、路由/DNS/MTU 管理和安装卸载恢复；对 Android 还会引入 VPNService 生命周期及与现有 Tailscale 客户端的共存问题。只为 QLH 推理流量时，应用层 WSS 的实现和故障边界都更小。

### 6.5 “DERP 只当交换机”需要先统一术语

这里有两种含义，网络代价完全不同：

1. **DERP 当中继/交换节点**：它接收并转发每个加密数据包。此时全部业务流量仍经过 DERP，正是当前 `relay` 路径。
2. **DERP 只做会合/信令**：它只交换端点和连接协商信息；主从随后建立直接连接。连接成功后，业务流量不再经过 DERP。

Tailscale 的确会先通过 DERP 转发 DISCO 发现消息，再尝试建立直接路径；但 stock Tailscale 建立的是 **UDP 直连**。当前校园网完全阻断 UDP，DERP 即使成功交换端点，也无法把这条 UDP 路径变为 TCP 直连。[DERP 工作方式](https://tailscale.com/docs/reference/derp-servers)、[Tailscale 连接建立流程](https://tailscale.com/docs/reference/connection-types)

因此，目标架构应表述为“**DERP 保留为 Tailscale 身份网络和低带宽控制兜底，QLH 大数据面优先直连主节点 WSS/TCP**”，而不是“让 DERP 交换一次地址后由 Tailscale 自动走 TCP”。后者不是当前 Tailscale 的能力。

```text
低带宽控制/故障兜底：Worker ---- Tailscale/DERP ---- Master
                                 register / heartbeat / path status

高带宽业务数据面：    Worker ===== direct TLS/WSS 443 ====> Master
                                 task / tensor / blob
```

第二条链路未建立前，调度器不得把第一条链路标成“控制面专用”：当前实现仍可能把 payload 放进 Tailscale/DERP，必须以实际路径和 DERP tx/rx 增量确认分流已经生效。

### 6.6 绕开 DERP 大流量的成立条件

从节点能否直连主节点 TCP 443，是方案成败的分界线：

| 主节点网络条件 | 结果 | 建议 |
|---|---|---|
| 有公网 IPv4，或路由器可做 TCP 443 端口映射 | 从节点可直接建立 TLS/WSS | 首选；DERP 只保留状态/备用路径 |
| 有可入站的全球 IPv6 | 可直接建立 TLS/WSS | 验证校园防火墙和证书后使用 |
| 主从位于同一可路由校园网/LAN | 可使用内网 TCP 地址 | 优先 LAN direct，Tailscale 仅作发现/备用 |
| 主节点只能主动出站，但从节点无法入站 | 单靠主节点不能成为公网 VPN Server | 需要反向隧道或公网网关；网关仍转发全部数据 |
| 主从都在 CGNAT/严格防火墙后 | 普通 listen/connect 失败 | 只能尝试 TCP 打洞；失败后必须回到中继 |

任何“反向 SSH/WSS 隧道”“云端 TCP 转发”“TURN/TCP relay”只要由公网服务器转发字节，都会把 DERP 的带宽问题搬到另一台服务器，并没有消除中继数据面。它仍可能有价值，但服务器必须按真实推理流量选带宽、CPU、流量配额和可用区。

### 6.7 TCP 打洞可以研究，但不能作为默认承诺

TCP simultaneous-open 和 ICE-TCP 提供了两端主动连接、候选收集、连通性检查与回退的标准框架。[RFC 5382](https://www.rfc-editor.org/rfc/rfc5382.html)、[RFC 6544](https://www.rfc-editor.org/rfc/rfc6544.html)

QLH 可以做一个独立的 `tcp-rendezvous` 实验：

```text
master  --outbound TCP-->  rendezvous（只记录临时候选）
worker  --outbound TCP-->  rendezvous
          exchange candidates + synchronized connect
master  <=============== direct TLS/TCP ===============> worker
```

但是：

- DERP 连接看到的是 Tailscale 虚拟地址，不足以直接得到可复用的公网 TCP 映射；需要单独的 TCP rendezvous/ICE 服务；
- 成功依赖 NAT mapping/filtering、入站 SYN 处理、两端操作系统 simultaneous-open 和本地端口复用；
- 多层 NAT、CGNAT、端点相关映射和严格状态防火墙会降低成功率；
- TLS、节点身份、候选过期、重放和连接代次仍需 QLH 自己处理；
- TCP 直连失败不能卡死任务，必须快速回到 DERP 控制通道、WSS 网关或本地执行。

PoC 只有在校园网、家庭 NAT、手机热点、双 CGNAT 四类环境各连续连接 50 次，成功率至少 95%、P95 建连不超过 5 秒，且成功后 DERP tx/rx 不再随负载增长时，才进入产品化评审。否则冻结 TCP 打洞，改为明确要求主节点具备可达 TCP 443，或部署足够容量的公网数据网关。

### 6.8 DERP 容量为什么必须现在评估

DERP 不解密内层 WireGuard 业务，但它仍要接收、TLS 处理并转发每个中继包。若应用单向有效载荷速率为 `R`：

```text
DERP ingress  ~= R + protocol overhead
DERP egress   ~= R + protocol overhead
aggregate I/O ~= 2R + overhead
```

多个从节点同时工作时按所有流相加。短 token 测试主要暴露 RTT 和正确性，不能代表长上下文 prefill、持续 decode、模型同步、图像 Blob 或多 Worker 并发；这些负载会持续占用 DERP 带宽、TLS CPU、socket buffer 和连接队列。Tailscale 官方也明确说明 DERP 的 QoS 和最大吞吐通常低于直连，relay 是常见性能瓶颈。[性能排障说明](https://tailscale.com/docs/reference/troubleshooting/poor-performance-tailnet)

在任何生产式分布式实测前，至少采集：

- DERP 主机上行/下行带宽、CPU、内存、连接数和丢包/重传；
- 主从两侧 goodput、RTT p95/p99、stall、重连和 DERP tx/rx 增量；
- 1、2、4 个 Worker 并发下的 TTFT、tok/s、任务完成率；
- 4 KiB 控制消息、100 MiB Blob、长 prompt prefill 和持续 10 分钟 decode 四类负载；
- direct WSS 成功后，DERP 流量是否只剩心跳、发现和失败回退。

初始采用保守告警线：DERP NIC 任一方向持续超过可用带宽 60%、CPU 持续超过 70%、RTT p95 翻倍或 stall 明显增加时，停止在该路径上分配 PyTorch 层流水线；优先切换任务链完整 Worker、直连 WSS、大对象独立下载，或升级中继容量。该阈值不是通用性能标准，必须在 NW2 用服务器规格、并发数和真实负载校准。

## 7. `qlh-netshim`：UDP-over-WebSocket/TCP 工具计划

### 7.1 产品定位

`qlh-netshim` 是独立 sidecar，不进入 Python 全局解释器，也不和 LLM/SD 依赖共用环境。第一阶段只做配置、进程托管、健康检查和指标采集，隧道内核优先复用成熟项目，不从零实现 TLS/WebSocket。

建议命令形态：

```text
qlh-netshim diag
qlh-netshim app-proxy --remote wss://gateway.example/qlh
qlh-netshim udp-proxy --listen 127.0.0.1:<udp-port> --remote wss://gateway.example/udp
qlh-netshim service install|start|stop|status
```

二进制和配置必须独立版本、独立日志、独立升级；安装包只在用户显式勾选“弱网 sidecar”时安装。

### 7.2 可复用技术

`wstunnel` 已支持 UDP 本地转发到 WSS/HTTP2，并给出普通 WireGuard 把 peer Endpoint 改为 `localhost` 的示例；它还支持 mTLS、HTTP 代理、访问范围限制和静态二进制。可先用它验证 MTU、吞吐、断线恢复和代理兼容，不应立即复制其协议实现。[wstunnel 项目](https://github.com/erebe/wstunnel)

PoC 拓扑：

```text
local UDP producer
  -> 127.0.0.1 UDP
  -> wstunnel/netshim client
  -> WSS 443
  -> netshim server
  -> remote UDP endpoint
```

### 7.3 为什么不能直接宣称支持 Tailscale

普通 WireGuard 配置允许把单个 peer 的 `Endpoint` 改成 `127.0.0.1:<port>`，因此容易接入 UDP proxy。stock Tailscale 的 peer endpoint 由控制面、STUN/DISCO 和 `tailscaled` 动态管理，没有普通 `wg0.conf` 的稳定编辑入口。

要让 netshim 接管 Tailscale UDP，至少需要证明以下一种集成可行：

1. `tailscaled` 正式支持可配置的 underlay proxy/endpoint；
2. 在不破坏端点发现的情况下，对 `tailscaled` UDP 做透明重定向；
3. 维护受控的 Tailscale fork/补丁，把 underlay datagram 接口注入 netshim；
4. 不代理 Tailscale，改为让 QLH 应用协议直接走 WSS（推荐的近期路线）。

Tailscale Peer Relay 也不能解决“客户端完全没有 UDP”：官方要求 relay 监听一个可达 UDP 端口，参与设备必须能访问该 UDP 端口。因此它适合硬 NAT 或有指定 UDP 白名单的网络，不适合作为本校园网当前策略下的首选。[Peer Relay 要求](https://tailscale.com/docs/features/peer-relay)

### 7.4 PoC 准入与止损

只有全部满足才继续做 Tailscale netshim：

- stock 客户端，无手工改 peer 配置，重启后仍能自动恢复；
- Windows 与 Linux 均不需要危险的全局网络钩子；
- Android 不要求 root 或常驻 Termux 才能使用；
- 连续 30 分钟、网络切换、隧道进程重启后无路由环；
- 内层 TCP 吞吐不低于自建 DERP 的 1.2 倍，或故障恢复明显更快；
- CPU、内存、MTU 和额外 RTT 可接受；
- TLS/mTLS、访问范围和升级路径可维护。

任一条件长期不满足，则停止“Tailscale UDP 伪装”，保留 `qlh-netshim app-proxy` 作为 QLH WSS sidecar。

## 8. 路径感知调度

### 8.1 路径画像

每个节点定期生成脱敏画像：

```json
{
  "path_kind": "derp",
  "relay_region": "self-hosted",
  "rtt_ms_p50": 20.1,
  "rtt_ms_p95": 34.0,
  "jitter_ms_p95": 8.0,
  "throughput_mbps": 18.5,
  "reconnects_10m": 0,
  "stalls_10m": 1,
  "measured_at": "..."
}
```

来源优先级：Tailscale local API/CLI → QLH 心跳 RTT → 主动小包 echo → 有限频率吞吐探测。CLI 不可用不能使节点离线，只把 `path_kind` 标为 unknown。

### 8.2 执行模式准入

| 执行类型 | direct/LAN | 自建 DERP/WSS | 高抖动/频繁重连 |
|---|---|---|---|
| 控制面、TUI、聊天转发 | 允许 | 允许 | 允许，延长 deadline |
| 任务链完整 Worker | 允许 | 允许，优先大粒度 Stage | 可重派/可恢复 Stage 才允许 |
| 图像 fan-out / Blob | 允许 | 允许，必须续传 | 降低并发、分块续传 |
| PyTorch 层流水线 | 允许，按实测门槛 | 实验；必须显示路径和收益 | 拒绝或回退本地 |
| 张量并行 | 仅快速孤岛 | 拒绝 | 拒绝 |

初始门槛只作为实验默认值，必须由 E0/E1 实测校准：

- 层流水线：RTT p95 ≤ 60 ms、抖动 p95 ≤ 20 ms、10 分钟无重连；
- 任务链：Stage deadline 至少为 RTT p95 的 20 倍，并有幂等/lease；
- Blob：必须支持 Range/块 ACK，单连接停顿不能导致整个对象重传；
- 连续 3 次传输失败后打开 circuit breaker，冷却期内不再分配实时流水线。

调度结果和 UI 必须显示 `transport/path_kind/fallback_reason`，禁止“任务成功”掩盖全程只在主节点执行。

NW1.2 冻结口径：RTT/jitter 使用最近 64 个有效 ACK 的有界窗口和 nearest-rank 百分位；jitter 是窗口内相邻 RTT 的绝对差。新心跳覆盖同代未确认心跳或带 pending 心跳断连时记录一次 stall；首次成功连接不算 reconnect，后续成功 generation 才记录 reconnect；有效 ACK 同时清零连续 stall/reconnect。事件计数也是最近 64 个 ACK/stall/reconnect，而非 10 分钟时间窗，NW1.3 不得把它命名为 `*_10m`。这些值仅由 `TCPClient.get_network_quality_snapshot()` 本地读取，不改变心跳帧、离线判定、重连或调度。

NW1.3 冻结口径：`network_path` 是 schema v1 可缺省只读诊断字段，不是调度输入。只有 client 本机掌握到 master 的 RTT/质量；不修改消息帧时，master 不能获得远端 client 的该窗口，UI 必须显示缺省而非填零。现有注册连接可作为精确端点已可达的被动证据，但不能区分 Tailscale direct/DERP；没有 status 路径事实时一律 `unknown/degraded`。API/TUI/Web 只消费白名单字段，不序列化 endpoint host、Tailnet、region 或原始命令输出。

NW1.4 冻结口径：`sanitize_network_path_view()` 是所有可序列化路径诊断的唯一白名单边界；`network_path_diagnostic_json()` 直接序列化该返回值，未知字段、地址、Tailnet、region、原始样本和原始命令输出均不保留。运行时 client 投影只读取既有连接与本地质量快照，禁止启动 CLI、probe 或外部 I/O；投影失败日志只保留异常类型。loopback 回归仅使用临时本地 TCP 端口，指标采集不得改变既有注册、心跳、取消或结果帧语义。

### 9.2 NW3 最小 PoC

- 不发送真实 tensor，只跑 register → heartbeat → 4 KiB echo → cancel；
- 固定 30 分钟，注入 1%/3% 丢包、50/150 ms RTT、20/80 ms jitter；
- 优先直接连接主节点 WSS 443，并与现有 Tailscale+DERP TCP 8888 做同机同提示同负载对照；
- 同时记录 DERP tx/rx；直连 WSS 承载负载时 DERP 流量应保持在控制基线，而非随 payload 增长；
- WSS 失败时明确回到 Legacy TCP，不允许双通道重复执行同一个 attempt；
- PoC 通过后再接 Task Worker，最后才评估层流水线。

### 9.2.1 NW3.0 契约骨架（2026-08-19）

- `TransportCandidate` 只接收受信端点的 TCP/TLS/认证观察；普通 8888 TCP 或 DERP 状态不能被提升为 `wss_443`；
- `select_transport()` 默认保持 `legacy_tcp`，只有显式 `prefer_wss=true` 且 TCP、受信 TLS、认证和有效期均通过才选择 `wss_443`；
- `TransportSession` 以节点 `generation` 和业务 `attempt_id` fencing 旧连接、迟到结果和重复开始；WSS 失败沿用同一 `attempt_id` 一次性切换 Legacy TCP，禁止双通道重复执行；
- `snapshot()` 与选择结果只返回路径类型、状态码和合同摘要，不暴露端点、租约令牌、提示词、权重或张量；
- 本票不创建 socket、不接入 `TCPClient`/Scheduler、不改变生产路由；真实 WSS endpoint、TLS 证书、代理/网关和 DERP 流量对照仍属于 NW3.1+ 外部验收。

## 11. 安全、合规与运维边界

1. 自建 DERP、WSS 和 netshim 只部署在项目拥有或明确授权的服务器上；遵守校园网使用规定。
2. 传输伪装只解决协议可达性，不用于隐藏未授权流量或绕过身份审核。
3. DERP/WSS/netshim 不能降低现有 tailnet ACL、HMAC、模型身份和任务 fencing。
4. WSS 必须使用 TLS；公网端点限制 upgrade path、请求大小、连接速率和可访问目标。
5. `wstunnel` 等外部二进制必须固定版本、SHA256、许可证和来源；不得启动时自动下载未校验的 latest。
6. netshim server 使用 allowlist/restrict 配置，禁止成为任意 UDP/TCP 开放代理。
7. 日志默认脱敏，不写 IP、prompt、tensor、密钥、证书私钥和 Blob grant。
8. sidecar 使用独立进程和配置目录，不污染项目 Python、LLM、SD 或打包虚拟环境。

### 9.3 NW4.1 Transport v2 契约与故障矩阵（本地契约与运行时接线门完成）

NW4.1 先冻结应用层传输契约，不改变当前 Legacy TCP 默认路由，也不把契约文档误记为 WSS/DERP 已上线。统一 envelope 至少包含 `schema_version/request_id/connection_generation/attempt_id/channel/sequence/deadline/payload_digest`；敏感字段和 payload 正文仍不进入普通诊断日志。

| 通道 | 语义 | 必须具备 |
|---|---|---|
| control | 注册、心跳、取消、能力和错误 | 有界帧、幂等 request、generation fencing |
| stream | token/hidden state/小结果流 | sequence、窗口 ACK、背压、deadline |
| blob | 大对象或层权重引用 | Range、chunk ACK、断点续传、SHA-256 |

故障矩阵至少覆盖：连接建立超时、TLS/认证失败、半连接、重复 ACK、乱序/重复 chunk、窗口耗尽、deadline 到期、旧 generation 迟到结果、连续失败触发 circuit breaker、WSS 到 Legacy 单次回退。每个格子固定 `reason_code/retryable/next_action`，禁止以“任务成功”掩盖回退到主节点单机。

### 9.4 NW3.1 本地自签名 WSS loopback（本机开发门 Completed，2026-08-20；测试专用）

NW3.1 已由 `src/wss_loopback.py` 实现本地 CA/自签名证书和 loopback WSS。服务器只允许 `127.0.0.1`、`localhost` 或 `::1`，使用临时证书目录，客户端只信任测试 CA；客户端从实际 TLS peer 证书计算 SHA-256 后再与 challenge 指纹比对。认证绑定 node、generation、attempt、nonce、证书指纹和 HMAC secret；数据面只回显 `TransportEnvelope`，复用 payload SHA、deadline、代际、attempt 和连续序号校验。旧 generation、错误 secret、错误 CA/指纹、重复/乱序帧和断线重连均 fail-closed，专项目标为协议测试，不承担公网证书或生产信任。

- 证书 SAN 固定为 `localhost`/loopback 测试地址，不把普通 8888 TCP 或 DERP 状态提升为 WSS 证据。
- 已覆盖 IPv4 loopback、错误 CA、TLS peer 指纹、认证失败、旧 generation、重复/乱序帧和断线重连；IPv6 loopback、过期证书、主机名不匹配、半开连接、代理兼容与单次 Legacy 回退属于后续 NW3/NW4 接线或真实端点验收。
- 可用 `mkcert` 或项目内最小 CA fixture；不下载或自动信任未知证书。
- 真实公网部署仍需要用户拥有域名并完成 HTTP-01、TLS-ALPN-01 或 DNS-01；Let's Encrypt 不为 `localhost` 签发证书。

NW3.1 通过后才能进入真实 TCP 443/WSS endpoint 的 NW3 最小 PoC；在此之前保持 Legacy TCP 默认路由。真实 endpoint、代理兼容、双端流量对照和运行时接线仍是后续票。
