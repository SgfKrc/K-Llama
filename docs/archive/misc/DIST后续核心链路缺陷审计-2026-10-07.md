## 结论摘要

DIST 系列的“能跑通”判据已经成立，但当前交付物还不能称为稳定可用版。核心问题不是单个算法错误，而是同一条请求经过多套准入、配置、健康、租约和回退判据；前一层把节点判为可用，后一层才发现工件、传输或执行条件不成立，于是形成“修好一个继续暴露下一个”的链式失败。

产品目标应收敛为两条且只保留两条生产路径：

1. D→L：主节点深度框架首段 + 一个或多个 layer worker。
2. L→L：纯 llama.cpp/GGUF 的多段接力。

A1 relay 已被产品入口剔除，现行代码仍保留探针/legacy 分支。它不应继续参与生产状态判定；否则会继续制造角色、会话和失败原因串台。

## 已证实的 P0 问题

### P0-1：Android 层段取消没有确定性 ACK，取消可退化为等待超时

`TaskWorkerClient.handleCancel()` 在存在 `stageHandler` 时只调用 `executionJob?.cancel()`，只有 `stageHandler == null` 才发送 `stage_cancelled`（`android/app/src/main/java/com/qlh/inference/worker/TaskWorkerClient.kt:728-743`）。正常执行的 `CancellationException` 分支会发送 ACK，但 JNI 的一次 `nativeLayerForward*` 调用不能保证被 Kotlin 协程取消打断。因此主节点可能已经返回取消请求，worker 仍继续计算，主节点收不到取消确认并等待到租约/步骤超时。

另一个入口 `cancelActive()` 将取消编码成 `stage_error`（同文件 `:530-553`），与 `stage_cancelled` 的协议语义不一致。这使“用户取消”“执行失败”“对端已经停止”在 coordinator 侧难以统一收敛。

**影响**：取消验收无法证明传播；长 stage 会占用 worker，后续请求遇到 busy/lease 竞争，形成二次故障。

**修复（DIST-NEXT-1，2026-10-07）**：定义唯一取消状态机 —— 收到 `stage_cancel` 后**立即**回 `stage_cancelled`（带 attempt 身份与 `execution_state`：`execution_stopped` / `execution_in_flight`），执行真正停止后再补发终态；JNI 在每个可分割的张量边界检查取消标志；master 对 ACK、迟到结果与「原子调用未中断」分别记账。

- `android`：`TaskWorkerClient.handleCancel` 不再区分 `stageHandler` 是否为 `null`，一律立即 ACK；`finishCancelledExecution` 在执行停止后补发终态（同 attempt 同状态去重）；`cancelActive` 改发 `stage_cancelled`（不再编码成 `stage_error`），且不再顺带停心跳。
- **回程 `provider_id` 口径（新定位的第二个真因）**：`stage_cancel` 的 payload 里没有 `provider_id`，旧实现回裸 `nodeId`，被 master 以 `attempt_identity_mismatch` 拒绝 ⇒ 这是「`stage_cancel_acknowledged` 恒缺席」的另一半原因。现改为回显 offer 时记录的主节点口径 `remote_<node_id>`。
- native：`llama_set_abort_callback` + 进程级标志（`nativeSetLayerForwardAbort`），`qlh_layer_forward_impl` 与 keep-head 版在可分割边界退出并返回 `-4`，Java 侧映射为 `layer_forward_aborted`（按取消而非执行失败处理）。
- master：`stage_cancelled.execution_state` 可选字段（v3，出现才放宽、值域封闭）；worker **主动**取消不再按 `unexpected_stage_cancelled` 拒绝，而是收敛为可重试的远端取消；新增 `RemoteFullWorkerProvider.cancel_diagnostics()` 分类计数。

### P0-2：层段 hidden 使用单帧 JSON/Base64，8 MiB 上限会在已准入后击穿链路

主仓和 Android 协议都把单条消息限制为 8 MiB（`src/task_worker_protocol.py:21,1017-1061`；`android/app/src/main/java/com/qlh/inference/worker/TaskWorkerProtocol.kt:63,287-299`）。Android 中间段把完整 `hidden_out_f32` Base64 放进同一 `stage_result`（`AndroidFullWorkerStageExecutor.kt:322-331,419-425`），socket frame 也只允许约 8 MiB（`TaskWorkerClient.kt:321-325,352-371`）。没有分片、压缩、大小协商或 dispatch 前置估算。

**影响**：合法的长 prefill、大 `n_embd` 或中间段输出在执行完成后才触发 `message_too_large`，随后是 stage 超时、回退或 `distributed_required` 拒绝。它不是“正确的 fail-closed”，而是过晚的契约发现。

**修复（DIST-NEXT-2a，2026-10-07）：dispatch 前的大小预检 + 具名拒绝。**

- 预算单一事实源：`src/task_worker_protocol.py` 的 `hidden_wire_bytes` / `stage_payload_budget_bytes` / `hidden_fits_stage_frame` / `max_hidden_tokens`（`STAGE_FRAME_RESERVE_BYTES` 为 JSON 外壳与 `seq_ids`/`positions` 留余量）；`android` 的 `TaskWorkerProtocol.hiddenWireBytes` / `stagePayloadBudgetBytes` 与之同公式同常量。
- master：`scheduler_pipeline._assert_layer_stage_offer_fits_frame` 在 `_execute_layer_stage_offer` 的 reserve/execute **之前**判定；超限抛 `LayerStageFrameTooLarge`（reason code `route_a_stage_frame_too_large`，含 wire/budget/n_tokens/n_embd），Route A 生成循环以该 reason 直接收敛。
- worker：`AndroidFullWorkerStageExecutor` 在产出中间段 hidden 前做对称预检，超预算返回 `stage_result_too_large`（原先由协议层 `encode` 抛 `message_too_large`，在 worker 客户端被记成 `worker_execution_failed`，原因丢失）。

**修复（DIST-NEXT-2b 协议层，2026-10-07）：分片契约与装配器（默认不启用，零行为变化）。**

- `task_worker_protocol`：v3 新增消息类型 `stage_chunk`（identity + `chunk_index` / `chunk_count` / `payload_b64` / `payload_sha256` / `total_bytes`）与三个硬上限（`MAX_STAGE_CHUNKS`=64 / `STAGE_CHUNK_BYTES`=1 MiB / `MAX_STAGE_PAYLOAD_BYTES`）；单条不合法给具名错误码（`chunk_index_out_of_range` / `chunk_count_out_of_range` / `chunk_too_large` / `stage_payload_too_large`），v2 客户端得到 `unsupported_message_type`。
- `task_worker_chunks`：发送端 `plan_stage_payload_chunks()`（切分 + 全文摘要）/ `build_stage_chunk()` / `stage_chunk_ref()`；接收端 `StageChunkAssembler`（按序号装配、重复/漂移/摘要不符/超限一律拒、集齐才产出、`discard` 复位、`pending` 诊断）。
- 判据：片数与总字节是硬上限 —— 分片不能用来绕过帧预算；逐片 `payload_sha256` 校验，装配后仍由 `stage_offer.hidden_sha256` 兜底。

**修复（DIST-NEXT-2b 接线，主仓两侧，2026-10-07）：**

- 能力位 `stage_chunked_input`（可选、布尔；主仓 `_validate_capabilities` 与 Android `validateHello` 同键集）。**默认关**：只有声明的 worker 才会收到分片。
- 发送侧 `RemoteFullWorkerProvider._maybe_send_stage_chunks()`：对端声明能力**且** hidden 超帧预算时，先同步发出有序 `stage_chunk`，再把 `stage_offer.root_input.hidden_f32` 换成 `hidden_ref`（`input_sha256` 按改写后的 root_input 计算）；未声明或未超预算 ⇒ root_input 逐字节不变。
- 接收侧 `scheduler_task_worker`：`stage_chunk` 消息路由 + `_assemble_stage_root_input()`（层段专用：装配 → 校验 `hidden_sha256` → 回填 `hidden_f32` → 丢弃分片状态；分片未齐备/摘要不符以具名原因失败）。
- 顺带修掉一个量化缺陷：base64 长度改用标准 `4 × ceil(n/3)`（`ceil(n × 4/3)` 近似对 1 MiB 少算 2 个字符，会把「刚好一片」误判成超限）。

**修复（DIST-NEXT-2b Android 侧，2026-10-07）：**

- Kotlin `StageChunkAssembler`（`android/.../worker/StageChunkAssembler.kt`，与主仓同语义、同错误码）：按序号装配，重复/漂移/摘要不符/超限一律拒，集齐才产出。
- `TaskWorkerProtocol`：v3 新增 `stage_chunk` 与三个上限常量（与主仓同值），放行并校验其 payload 形状（角标越界 / 片数超限 / 单片超限 / 总量超限都给具名错误码）。
- `TaskWorkerClient`：接收 `stage_chunk`（分片错误只记具名日志，**不断连**）；在 accept **之前**装配 `hidden_ref` ⇒ 校验 `hidden_sha256` ⇒ 回填 `hidden_f32` 并移除 `hidden_ref`；装配不齐以 `incomplete_chunks` 拒绝该 offer。
- `AndroidWorkerCapabilities` / `TaskWorkerService` 声明 `stage_chunked_input`；两侧装配后都移除 `hidden_ref`（避免执行侧看到两个来源）。

**剩余（DIST-NEXT-2b 最后一项）**：「大 prefill + 大 hidden」真 socket 端到端回归（与 DIST-NEXT-1d 同批等三机窗口）。两侧装配、能力协商与上限均已就绪并有单测；未声明能力的对端仍走内联路径（超限请求由 dispatch 前预检具名拒绝）。

### P0-3：准入、容量和就绪仍不是单一事实源

容量候选在 `src/scheduler.py:2695-2810` 检查 `NodeState` 与 `WORKER_HEARTBEAT_MAX_AGE=120s`；task-worker 控制面另用 `max(30s, HEARTBEAT_INTERVAL*4)`（`src/scheduler.py:1136-1140`、`src/scheduler_types.py:55-75`）；Android task-worker 心跳固定 15s（`TaskWorkerClient.kt:623-628`）。流水线 readiness 还同时检查 TCP、节点心跳、legacy ACK、v3 stage offer（`src/scheduler_pipeline.py:4313-4500`）。这些判据有意分层，但没有一个“本次 assignment 的可执行租约”作为唯一入口。

**影响**：节点可能已进容量计划但控制面已不健康，或控制面 accepted 而 assignment 尚未准备；断线后的旧配置、旧 ACK、旧 reservation 只能靠多处清理。实际表现就是候选存在、请求仍 60s 超时，或者同一会话先 admitted 后为空。

**下一票**（原）：以 `assignment_id/config_id + worker connection generation + lease` 建立统一 `WorkerAssignmentState`，容量、readiness、dispatch、release 只读它；健康阈值由一个配置源计算；断线、心跳过期、服务重建都必须原子撤销 assignment 和 reservation，并记录单一 reason code。

**修复（DIST-NEXT-4a「健康阈值单一配置源」，2026-10-07）**：

- `scheduler_types.py` 成为心跳类阈值的唯一来源：新增 `ANDROID_TASK_WORKER_HEARTBEAT_INTERVAL_SECONDS`（15s，与设备侧 `TaskWorkerClient.HEARTBEAT_INTERVAL_MS` 同值）与 `ANDROID_PRESENCE_HEARTBEAT_INTERVAL_SECONDS`（45s），并提供派生函数 `worker_heartbeat_max_age_seconds()`（容量规划与 readiness 共用）、`task_worker_control_plane_health_timeout_seconds()`（控制面 health）、`worker_liveness_thresholds()`（诊断）与 `assert_worker_liveness_thresholds()`（启动期自检，错配直接 fail-loud）。
- `scheduler.py`：`ANDROID_HTTP_CLIENT_HEARTBEAT_INTERVAL_SECONDS` 改为引用该来源（保留既有名字，`scheduler_cluster` 的 facade 读取不变）、控制面超时改走派生函数、导入时执行自检。数值与行为**不变**（控制面 30s、规划层 120s）。
- `android`：心跳间隔由硬编码 `15_000L` 提为 `TaskWorkerClient.HEARTBEAT_INTERVAL_MS` 常量并注明与主仓同值。
- 测试：`tests/test_worker_liveness_policy.py`（自洽性、控制面先于规划层翻转、心跳判据不晚于 TCP 巡检 131s、错配 fail-loud、`scheduler` 别名指向同一来源）；Android 断言 15s 同值。

**修复（DIST-NEXT-4b「原子撤销 + 单一 reason code」，2026-10-07）**：

- `task_worker_adapter`：撤销 reason 收敛成闭集（`worker_tcp_disconnected` / `worker_heartbeat_stale` / `worker_service_restarted`）；`notify_disconnect(reason_code=...)` 记一条 `event=task_worker_reservations_released`（单一来源）；新增 `release_stale_reservations()` —— 只回收**已终结**条目，不打断 in-flight 执行。
- `scheduler`：新增 `_reap_stale_worker_reservations()`（心跳过期且无在跑 attempt ⇒ 回收，reason 固定 `worker_heartbeat_stale`，逐节点记事件），在 `_get_pipeline_capacity_nodes()` 入口调用 —— 补的正是「TCP 仍在线、心跳线程失效」这段窗口，此前那类节点的 `max_concurrency=1` 槽位会被「已预留未执行」占住直到对端重连。断线路径显式传 `worker_tcp_disconnected`。
- 测试：`tests/test_worker_reservation_release.py`（reason 闭集、空闲回收、in-flight 不被打断、心跳过期回收并记录单一 reason、fresh 心跳不动、幂等）。

**剩余（DIST-NEXT-3）**：`assignment_id + generation + lease` 的 `WorkerAssignmentState` 单一事实源（替代多集合交叉判定）。

## 已证实的 P1 问题

### P1-1：运行时配置是多套集合，不是显式状态机

主仓同时维护 `_layer_config_pushed`、`_layer_config_expected`、`_layer_config_acks`、`_pipeline_load_transaction`、`_active_pipeline_capacity_plan`、`_pipeline_recovery_state` 等集合/字典（`src/scheduler.py:1020-1050`，多处读写见 `src/scheduler_pipeline.py:1400-1715,3080-3310`）。`_maybe_finish_pipeline_recovery()` 还需要再次比对 generation、config、pushed 集合和 v3 readiness（`src/scheduler_pipeline.py:521-590`）。当前没有 `assignment_id` 维度；相同 node 在重连或重配时只能通过 config/generation 的组合间接隔离。

这不是单纯的代码风格问题：它解释了恢复 fence、release/re-ACK 竞态和“某处判 ready、另一处仍 not_configured”。下一轮应先把状态模型收敛，再继续叠加闸门。

**修复（DIST-NEXT-3 第一步「状态模型 + 写路径接线」，2026-10-07）：**

- 新增 `src/worker_assignment_state.py`：`WorkerAssignmentState`（`assignment_id` + `config_id` + connection generation + lease + phase + **单一** `reason_code`）与 `WorkerAssignmentRegistry` —— `begin()` **每次下发都换 `assignment_id`**（迟到 ACK 无法冒充当前配置的就绪）、`attach_lease()` 把 lease 绑到当前代际、`transition()` 只许前进（越级允许、回退/未知相位拒绝）、`release()` 进入终止态并只记一个原因（重复撤销幂等）。撤销原因复用 `task_worker_adapter.RELEASE_REASON_*` 闭集。
- 接线（**只写不读** ⇒ 零行为变化）：`_publish_layer_configs` 每次下发换代际；`_clear_layer_config_state` 记 `config_cleared`；released ACK 记 `worker_released`；普通 ACK 推进到 `acked`。
- 测试：`tests/test_worker_assignment_state.py`（8 例）。

**剩余（DIST-NEXT-3 第二步）**：把**读路径**逐条切到该视图（容量候选、readiness、dispatch、release 与 `_maybe_finish_pipeline_recovery()` 的 generation/config/pushed 交叉比对），并删除随之失效的集合读写。切换前，权威视图只作诊断与回归依据。

**进展（DIST-NEXT-3 第二步·观测点，2026-10-07）**：`evaluate_assignment_consistency()` 把三种分歧具名化（`state_missing_but_legacy_expected` / `terminal_state_but_legacy_pushed` / `state_ready_but_legacy_not_pushed`），并在审计点名的恢复闸门交叉比对处接入 `_observe_assignment_state_consistency()` —— **判据不变**，只在分歧时记 `event=worker_assignment_state_divergence`。先让真实分歧在日志里可见，再逐条切换判据。

**进展（DIST-NEXT-3 第二步·第一条读路径切换，2026-10-07）**：`pushed_from_state()` 给出 `_layer_config_pushed` 的等价相位（`ACKED`/`READY` ⇒ 真），`_effective_layer_config_pushed()` 在有 assignment 记录时**以权威视图判定**，无记录或分歧时保留旧判据（fail-closed，分歧已记事件）。`_maybe_finish_pipeline_recovery()` 的 pushed 判据走该入口 —— 正常路径不再"仅由旧集合推断"，分歧场景零行为漂移。

**进展（DIST-NEXT-3 第二步·第二条读路径 + 收紧语义，2026-10-07）**：`_get_pipeline_readiness` 的 `ready_nodes = set(self._layer_config_pushed)` 改走 `_effective_layer_config_pushed_nodes()`；`pushed_from_state()` 定为**三档**语义（`ACKED`/`READY` ⇒ True；`RELEASED`/`ABORTED` ⇒ False；`STAGED`/`PUSHING` ⇒ None —— 尚无 ACK 证据不等于否定），切换规则为**只收紧、不放宽**：终止态的陈旧 `pushed` 残留被排除，而"权威判真、旧集合判假"保持旧值（放宽会改变 readiness 结论）。三档语义与"只收紧"都是回归实测驱动的结论（把 `PUSHING` 当 False 会让 `test_push_waits_for_worker_load_ack` 变红）。

**进展（DIST-NEXT-3 第三步·重发判据，2026-10-07）**：`_retry_pending_layer_configs()` 的 `node_id in self._layer_config_pushed` 同样改走 `_effective_layer_config_pushed()` —— 陈旧残留（节点实际已 terminated）不再**永久阻止重发**；真 pushed 照旧跳过（零行为漂移）。三条读路径（恢复闸门、readiness、重发）现在共用同一入口与同一分歧口径。

**进展（DIST-NEXT-3 第三步·第四读点 + 派生不变量，2026-10-07）**：legacy 二次就绪检查的 `layer_ready` 也改走同一入口（第四个读点）。同时补上 `_handle_layer_config_ack()` 的 `if ready:` 分支对权威视图的相位推进（此前只有 release 类分支推进 ⇒ registry 停在 `pushing`，与已填充的 `_layer_config_pushed` 长期不一致）。新增**不变量测试**：走完 legacy ready ACK 后，`_layer_config_pushed` 与 registry 派生的集合（`phase ∈ {ACKED, READY}`）逐元素一致 —— 这是把旧集合**降级为派生视图**的前置条件。

**修复（DIST-NEXT-3 收口·集合降级为派生视图，2026-10-07）**：`_layer_config_pushed` 改为 **property**（返回 `frozenset`，相位 `ACKED`/`READY`）—— 事实源只剩 `_worker_assignments`。不可变返回是刻意设计：遗留的 `add`/`discard`/`clear` 会立刻 `AttributeError`（fail-loud），实测据此抓出 4 处测试夹具的直接写入。写入点收敛为 `begin`（publish）/ `release`（清除、worker released、rejects-legacy）/ `invalidate`（ACK 不成立 ⇒ 相位退回 `pushing`）/ `transition`（ACK 推进），并新增 `_ensure_assignment_state()` 兜底「本端直写 `_layer_config_expected` 后收到 ACK」的路径；`Registry.clear()` 承接 api_server / engine_host / scheduler_cluster 三处全局清理。附带修正：**迟到的 prepared ACK 不再撤回已就绪的节点**（旧写法会把它踢出 `pushed`）。

### P1-2：恢复持久化把“可恢复配置”与“运行时真相”混在一起

流水线生命周期被写入本地 store，并在启动时重新 arm recovery fence（`src/scheduler_pipeline.py:272-350,490-590`）。这能防止重启后误用旧 ACK，但也意味着一个历史 `ready`/事务记录会阻塞新会话，直到模型摘要、worker hello、权威重发和新代际全部吻合。持久化应只保存模型身份、期望拓扑和恢复原因；连接、ACK、reservation、活动 attempt 不应被当作可恢复事实。

任务图 journal 的 SQLite/WAL 与跨进程锁本身是合理的，但 API 在 journal 不可用时直接拒绝不可恢复执行（`src/api_server.py:2787-2793`）。这对真正需要恢复的任务图是正确的安全策略，却不应成为普通 D/L 请求的隐式前置条件；两类请求应在入口分离。

### P1-3：Android Service 重建不能可靠恢复 worker

`TaskWorkerService` 返回 `START_STICKY`，但只有带完整配置的 `ACTION_START` 才能创建 client；系统重建若 intent 为空，会因 host/port/node 校验失败而 `stopSelf()`（`android/.../TaskWorkerService.kt:45-95`）。连接和活动 attempt 仅在内存，进程被杀后没有恢复协议。`awaitInferenceService()` 只等待约 5 秒，慢启动会在真实 stage offer 中表现为 `inference_service_unavailable`。

清单的三个前台服务没有 `android:stopWithTask="false"`，没有电池优化引导；`InferenceService` 的 WakeLock 固定 30 分钟（`InferenceService.kt:562-570`）。这些不是“加个前台通知就解决”的问题，应通过真机锁屏、划掉任务、系统重建和长任务验收。

**修复（DIST-NEXT-5a「重建恢复 + 就绪屏障」，2026-10-07）：**

- 纯逻辑抽出：`android/.../worker/TaskWorkerStartup.kt` 的 `TaskWorkerStartupConfig`（解析 / `usable` 唯一校验 / JSON 往返）与 `decideTaskWorkerStartup(action, hasPersistedConfig, hasActiveClient)`（决策表）—— JVM 单测可锁住重建路径。
- `TaskWorkerService.onStartCommand` 改为「决策 + 分派」：`intent == null`（`START_STICKY` 回收后重建）且有持久化配置时 **`Resume`**（此前落进 `when` 的默认分支什么都不做）；`startWorker(config)` 与首次启动共用同一条路径；`ACTION_STOP` 或配置不足时清除持久化配置（避免坏配置被反复拉起）。配置经 `SettingsDataStore` 的 `task_worker_startup` 键持久化。

- 测试：`TaskWorkerStartupTest`（配置校验、JSON 往返、损坏配置、无参重建的 Resume/Stop/Ignore、显式 action 语义）。
- **剩余（DIST-NEXT-5b）**：电池优化豁免引导（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）、`InferenceService` WakeLock 时长策略，以及真机锁屏 / 划任务 / 长任务 soak 验收（与 DIST-NEXT-1d 同批等三机窗口）。

## 设计债务与遗留隔离

### A1 relay：当前不应再进入生产判定

`_relay_segment_for_worker()` 在 `PIPELINE_RELAY_PROBE_ONLY=1` 时返回 `None`，生产入口已转向 A3 `stage_offer_v3`（`src/scheduler_pipeline.py:5023-5065`）。但 A1 的 relay session、`relay_middle` assignment、scheduler 缓存和 peer 缓存仍在主仓（`src/scheduler_pipeline.py:1878-1922`、`src/inference_service/peer.py:673-811`），并继续出现在 readiness、角色和配置分支中。

审计结论不是要求立即删除探针，而是要求把它从生产状态机中隔离：独立模块、独立诊断 namespace、默认不可被 scheduler assignment 选中。否则旧会话缓存和 legacy release 分支仍可能改变生产错误原因。

**修复（DIST-NEXT-7，2026-10-07）：调度侧的隔离边界落地。**

- 新增 `src/relay_a1_legacy.py` —— A1 的**唯一入口与诊断来源**：`a1_production_enabled()`（门的真值表：仅「总开关开 + 探针闸门关」为真）、`a1_isolation_status()`（独立 namespace `relay_a1.*`）、`parse_relay_segment_map()`（段映射解析自 `scheduler_pipeline` 迁入，判据仍复用 `_normalize_relay_segment`）。
- `scheduler_pipeline._relay_segment_for_worker()` 只经该门供给；「不供给」的两种表现（探针闸门一次性告警 / 总开关关闭静默）保持原行为。新增 `get_relay_a1_status()` 与启动期 `event=relay_a1_isolation` 日志 —— 「A1 会不会被调度选中」变成一条可 grep 的自证事实，而不是逐个开关推断。
- 生产 assignment 层面：默认（`PIPELINE_RELAY_PROBE_ONLY=1`）下 `_relay_segment_for_worker()` 恒 `None`、`_is_relay_host()` 恒 `False` —— 已由 `tests/test_relay_a1_isolation.py` 锁定（含探针入口仍可用、诊断字段集合固定）。
- **剩余**：worker 侧的 A1 承载（`inference_service/peer.py` 的 relay session / `via_relay` / `relay_middle` 配置分支）仍在原处。它只在探针模式下发 `relay_middle` 配置时才被走到，不参与生产路径；彻底裁撤属 `LEGACY-RETIRE` 票的范围。

### fail-closed 的边界

以下拒绝是正确方向：部分 GGUF 禁止整模回退（#38）、keep-head 不可用禁止静默退回 embeddings、Android 工件身份/range/digest 不匹配禁止执行。这些保护了“HTTP 200 垃圾文本”问题。

但以下做法属于“发现过晚”或“拒绝代替恢复”：

- hidden 超过帧上限后才拒绝，而不是 offer 前预检或分片；
- manifest 错误被静默剔除，未提供可修复原因；
- worker accepted 后 service 未就绪，等 stage 执行时才 `inference_service_unavailable`；
- 取消只取消本地协程，不保证远端 ACK/停止；
- 多个超时源叠加，最终只看到 60/120s 的泛化失败。

判定标准应改为：**不安全的执行必须拒绝；可恢复的暂态必须先重试/重连/重新发布；不可恢复的条件必须在 dispatch 前以稳定 reason code 结束。**

## 两条产品路径的验收闸门

### D→L

必须在同一模型身份和明确层范围下完成 prefill + 至少 2 个 decode；首段不加载整模；中间段 hidden 语义、KV 位置和 `seq_ids/positions` 与整模基线逐 token 对拍；取消必须收到远端 ACK；大 hidden 不得靠偶然小输入绕过帧限制。

### L→L

必须使用真实裁层 GGUF，段类型/层范围/源模型摘要/工件摘要全部一致；纯 llama.cpp 节点不得把裁层工件当整模回退；连续 decode 的 KV 由每段保持且位置单调；任一 worker 断线要在单一窗口内失败或重排，不得先后经过多个互相独立的 60/120s 超时。

### 两者共同要求

一次请求的日志和响应 metrics 能重建：选了谁、哪个 assignment/generation、是否实际发送 offer、是否 ACK、是否执行、失败属于可重试还是不可恢复、是否发生 fallback。没有这些事实，就不能把“请求返回 200”当作稳定可用证据。

**修复（DIST-NEXT-8「metrics truth」，2026-10-07）：相位 + 互斥终态。**

- 新增 `src/request_outcome.py`：`request_phase_metrics()` 给出相位（`admitted` / `started` / `completed` / `fallback` / `refused` / `cancelled` / `failed`）与**唯一终态** `outcome`（`derive_outcome()` 的互斥优先级：`cancelled` > `refused` > `failed` > `fallback_completed` > `completed` > `incomplete`），并给出稳定 reason code（`generation_cancelled` / `request_refused` / `request_failed`）。
- 接线：成功路径的 `done.metrics` 带上相位（`admitted` = 本次真的拿到分布式 assignment：`config_id` / `workers_used` / `layer_assignments` 任一存在）；流式取消事件与非流式 409 都带 `outcome="cancelled"` + `reason_code`；`_error_event` 区分 `refused`（路由门：不可恢复、dispatch 前拒绝）与 `failed`（链路/执行失败）；`event=chat_route_summary` 增加 `outcome=` 字段。
- 效果：`fallback=True` 只描述「回退后仍完成」，不再承担「取消」或「拒绝」的语义 —— 取消/拒绝/失败各有一个可 grep 的终态。
- **剩余**：`admitted` 的粒度仍是「有无分布式 assignment」，细分到 `assignment_id`/`generation` 级属 DIST-NEXT-3（assignment 状态机）。

## 真机验收清单（待三机窗口）

以下三项都需要**真实三机链路**（本机 master + Surface worker + Y700 worker，按当次拓扑），并且必须在
**重启 master 与设备侧 UI** 之后执行 —— 已运行进程里是旧代码，用它验收等于验旧代码。

### 1. DIST-NEXT-1d：取消合同（P0）

前置：Y700（`HA26PYZQ`）与 Surface 都已作为 layer worker 接入，一次请求可覆盖至少两个层段。

1. 发起一个会产生可见中间段的请求（长 prompt + 较大 `max_tokens`）。
2. 在首段执行中取消（前台停止生成）。
3. 通过判据（全部满足）：
   - master 侧出现 `stage_cancel_acknowledged` 日志，并带 `execution_state`；
   - 从取消发起到收敛的耗时落在固定的取消收敛窗口内（日志会打出实际耗时）；
   - 取消后**没有**迟到的 `stage_result` 被采纳（授权已作废）；
   - 响应终态 metrics 为 `outcome="cancelled"` 且 `reason_code="generation_cancelled"`，**不是** `fallback`。
4. 反向判据：若表现为「等到 60/120s 泛化超时才失败」，本项**不通过** —— 那正是 P0-1 描述的退化。

### 2. DIST-NEXT-2b：大 hidden 真 socket 回归（P0）

判据：让首段产出逼近或超过单帧预算的 hidden（大 prefill），确认走**分片路径**而不是报错：

- master 侧的 offer 前预检**不**抛 `route_a_stage_frame_too_large`；
- worker 侧先收到多个 `stage_chunk`（`chunk_count > 1`），装配完成后才收到 `stage_offer`；
- 装配校验 `hidden_sha256` 通过，`stage_result` 与整模基线逐 token 对拍一致；
- 负例（必须同时跑）：把单帧预算人为调小（例如临时抬高 `STAGE_FRAME_RESERVE_BYTES`）⇒ 必须在 **offer 前**以 `route_a_stage_frame_too_large` 拒绝，而不是运行中失败。

### 3. DIST-NEXT-5b：锁屏 / 划任务 / 长任务 soak（P1）

建议在 Y700 上做（OEM 省电策略最激进）：

1. 安装新 APK（含电池优化豁免权限与首启引导）：首启确认系统对话框出现**且只出现一次**；拒绝后再次启动不再弹。
2. 把设备启动为 worker，然后：锁屏 10 分钟、从最近任务划掉 App、再打开；期间主节点持续发起小请求。
3. 通过判据：
   - worker 未掉线（心跳持续到达；没有异常密集的 `task_worker_reservations_released`）；
   - 划掉任务后服务被系统重建（`START_STICKY`）并能自动恢复为 worker（`TaskWorkerStartup` 决策 + 持久化配置生效）；
   - 单段耗时超过续租窗口（10 分钟）时 WakeLock 被**续租**而不是提前释放；

4. `pidof` 查不到进程本身**不**作为失败判据（见「未判为现行缺陷的项」#55）。

**真机窗口暴露的新问题（不在本轮票面内，需后续票）：**

1. **取消/失败后 worker 不再服务后续请求（P0，已定位并修复）**。症状：取消之后每个新请求都在 step 0/1 失败（`remote worker rejected the Stage offer (reason_code=worker_busy_or_lease_invalid)` / `remote Stage response timed out` / `remote worker reported a Stage error`），设备侧 `top` 显示 **775% idle**（并不在计算）；重启 master 或 App 让 worker 重连即恢复。
   **三条根因**（`android` `b40dc46`）：
   - **取消收敛跑在被取消的协程上** —— `executionJob.cancel()` 后执行协程里的任何挂起（含 `send` 的 `withContext(Dispatchers.IO)`）立刻抛 `CancellationException`，把「终态 `execution_stopped` ACK + `machine.cancelled()` 槽位释放」一起带走 ⇒ attempt 停在 `CANCELLING`（`ACTIVE_ATTEMPT_STATES` 成员）⇒ 后续 offer 全被拒到 lease 过期。修法：独立 `NonCancellable` 协程轮询执行器直到真正停止再收敛（超时 30s 也释放并留 WARN），协调方取消与本地取消共用该路径。
   - **去重标记写在了发送之前** —— 执行协程那次发送抛异常后标记已置位，独立收敛协程被去重挡掉 ⇒ 终态 ACK 再也发不出去（现场只看到 `execution_in_flight`）。修法：标记代表「已成功发送」；终态 ACK 允许集合放宽到取消家族（`CANCELLING`/`CANCELLED`）。
   - **引擎中止标志无人复位** —— `requestLayerForwardAbort()` 置位后，取消之后的**第一次** `layerForward` 在引擎入口被判 `layer_forward_aborted` 直接失败（设备侧证据 `code=worker_execution_failed detail=layer_forward_aborted`）。修法：执行器在每次 `executeLayerForward` 开始前复位该标志。

⇒ ⑤ 是本节最强证据：强杀**发生在 decode 第 8 步**（推理进行中），master 在 **5.3s** 内识别 worker 断开、释放 1 个 reservation 并以**具名 reason** 结束 ⇒ 命中判据「固定时间收敛 + 单一 reason code」，整请求 **10.7s** 远小于 60/120s。

**本节暴露的观察（建议后续处理）**：

1. **`admitted=True` 语义过粗**：master 重启后、Y700 完成重连之前，容量求解会先给出 `admitted=True` + `assignments=[('master',0,24)]` 的**单机退化解**（持续约 8s），随后才升级为两节点 ⇒ **不能把 `admitted=True` 单独当作「分布式就绪」判据**（`distributed_required` 请求还需看 `require_distributed` 与 `workers_used`）。
2. **严格 TCP 半开：首测无效、补充实验已复现（同日）**。第一次尝试用「切断 WiFi」制造半开**判定无效**（实验顺序出错：先强杀、后断网，观察到的 `offline` 是前一步遗留）。改用 **`run-as … kill -STOP` 挂起 worker 进程**（TCP 保持、心跳停止）后成功复现：**125.5s** 判 offline，日志明确指出触发者是 **`心跳超时 (129s)，连续丢失 43 次`**（心跳判据，非纯 TCP 巡检），与 DIST-NEXT-4a「心跳先于 TCP 巡检翻转」一致；`SIGCONT` 后 **0.2s** 自动恢复 online、容量计划回到 `admitted/True/ready`（同一 PID，无需重启 App）。

**未覆盖 / 未观测**：Surface 侧的断线、重连（设备离线）；⑤ 中未出现「迟到 stage 结果被采纳」的记录 ⇒ 「旧任务结果不串台」记为**未观测到**，不作正面结论。
