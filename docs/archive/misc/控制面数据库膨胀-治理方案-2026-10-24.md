## 2. 根因（代码级）

### 2.1 事件写的是「完整快照」而不是增量

`src/qlh_core/adapters/model_control_repository.py:46-62`：

```python
def transact(self, mutation, *, domain=MODEL_CONTROL_DOMAIN):
    with self._transaction() as connection:
        self._initialize(connection)
        state = self._read(connection)
        before = canonical(state)
        mutation(state)
        if canonical(state) == before:
            return deepcopy(state)
        state["revision"] += 1
        ...
        event = {"sequence": sequence, "domain_id": domain,
                 "previous_digest": previous_digest, "state": state}
        event_digest = digest(event)
        connection.execute("INSERT INTO model_control_events VALUES (?,?,?,?,?)",
                           (sequence, domain, previous_digest, event_digest, canonical(event)))
        connection.execute("INSERT INTO model_control_state VALUES (1,?) ON CONFLICT(id) DO UPDATE SET payload=excluded.payload",
                           (canonical(state),))
```

`event["state"]` 是**整个 aggregate state**。所以：
- 每条事件的体积 = 当前快照体积（现为 2.04 MiB）
- 快照体积又由四个无界容器决定 ⇒ **双重放大**

`empty_state()`（L13-16）定义了这些容器：

```python
return {"schema_version": 1, "revision": 0, "boot_id": "", "selected_operation": "",
        "active_deployment": "", "operations": {}, "supplies": {}, "deployments": {},
        "outbox": {}, "cleanup": {}, "artifact_cleanup": {}, "lifecycle": None, ...}
```

### 2.2 四个容器只写不淘汰

| 容器 | 写入点 | 是否有淘汰 |
|---|---|---|
| `supplies` | `control/deployment.py:86` `state["supplies"][value["operation_id"]] = value` | **无** |
| `deployments` | `control/deployment.py:183` `state["deployments"][config_id] = deployment` | **无**（只有终态保护 `DEPLOYMENT_TERMINAL`） |
| `operations` | `control/deployment.py:92`（新建时） | **无** |
| `outbox` | 待定（见 §7，子 agent 探查中） | 已知重启时只标记不删：`control/deployment.py:65-67` 把 `prepare`/`commit` 置为 `"superseded"`，注释明确写 "Old commands remain auditable" |

⇒ 没有任何一处做保留上限，容器随运行时长单调增长。

### 2.3 恢复校验要求全量 replay

`model_control_repository.py:64-88` 的 `recovery_status()`：

```python
previous = "0" * 64
sequence = 0
for row in connection.execute("SELECT * FROM model_control_events ORDER BY sequence"):
    value = json.loads(row["payload"])
    if (row["sequence"] != sequence + 1 or row["domain_id"] != MODEL_CONTROL_DOMAIN
            or row["previous_digest"] != previous or value.get("previous_digest") != previous
            or value.get("sequence") != row["sequence"] or value.get("domain_id") != MODEL_CONTROL_DOMAIN
            or digest(value) != row["digest"]):
        raise ModelControlError("model_control_journal_corrupt")
    sequence, previous, last = row["sequence"], row["digest"], value["state"]
if last is not None and last != self._read(connection):
    raise ModelControlError("model_control_journal_corrupt")
```

两个硬约束决定了「不能裸删」：
1. `sequence` 必须**从 1 连续**（`row["sequence"] != sequence + 1`）
2. `previous_digest` 必须首尾相接成链（起始锚点是 `"0"*64`）

⇒ 直接 `DELETE FROM model_control_events` 会让下次启动抛 `model_control_journal_unverified`，master 无法启动。**必须先有 checkpoint 概念。**

## 3. 治理方案（三层，按收益/风险排序）

### L1 给四个容器加保留上限（根治增长）

**目标**：让每条事件的体积从 2.04 MiB 降到 ~0.35 MiB。

**改点**：`src/qlh_core/control/deployment.py`，在每个 `save(state)` mutation **内部**（同一事务、同一 revision）追加修剪：

```python
def _trim_container(state, key, *, keep, pinned, terminal):
    """保留 pinned/未终结/最近 keep 条；其余删除。"""
    items = state[key]
    ranked = sorted(items.items(),
                    key=lambda kv: kv[1].get("created_at", 0) or 0,
                    reverse=True)
    survivors = {}
    for index, (k, v) in enumerate(ranked):
        if k in pinned or v.get("status") not in terminal or index < keep:
            survivors[k] = v
    state[key] = survivors
```

各容器的 `pinned` / `terminal`：

| 容器 | pinned（绝不删） | terminal（可删的条件之一） | 建议 keep |
|---|---|---|---|
| `supplies` | `state["selected_operation"]`；被 `cleanup`/`artifact_cleanup` 引用的 | `{"available", "failed", "cancelled"}` | 10 |
| `operations` | `state["selected_operation"]`；未终结 | `OPERATION_TERMINAL` | 10 |
| `deployments` | `state["active_deployment"]`；被 `cleanup` 引用的；`publication_cleanup.py:84` 依赖的未终结项 | `{"aborted", "retired"}` | 10 |
| `outbox` | 未确认的（待 §7 定性） | `{"superseded"}` + 已投递超 TTL | 50 |

**新增设置**（遵循项目惯例，不硬编码）：

```
QLH_STATE_KEEP_SUPPLIES=10
QLH_STATE_KEEP_OPERATIONS=10
QLH_STATE_KEEP_DEPLOYMENTS=10
QLH_STATE_KEEP_OUTBOX=50
QLH_STATE_TRIM_ENABLED=1        # 紧急关闭开关
```

**必须守住的安全约束**（这几条比收益更重要）：

1. **清理债务引用不可删**。`adapters/publication_cleanup.py:84` 用 `state["deployments"]` 与 `state["cleanup"]` 决定是否能安全退役；删掉被引用的 deployment/supply 会让清理债务永远无法结算。
   ⇒ 修剪前先收集 `set(state.get("cleanup", {})) ∪ set(state.get("artifact_cleanup", {}))` 中被引用的 id，加入 `pinned`。
2. **终态不可复活**。`save_supply` 有 `supply_terminal_conflict` 检查（L84-85）、`save_deployment` 有 `deployment_retired` 检查（L176-177）——它们依赖**旧条目存在**来判断"是否已终态"。若把某终态条目删了，之后同 id 的迟到写入会被当成新建。
   ⇒ 保留规则应保证：**最近 N 条 + 任何仍在被重试/被引用的**；并且对**已删 id 的迟到写入**要有兜底（例如保留一个 `retired_ids` 集合，或接受"已终结且超期即忽略"的语义）。
3. **`recover()` 的语义依赖容器**。`deployment.py:53-67` 在重启时把未终结的 operations/supplies/deployments 置为 failed/invalidated、把 outbox 的 prepare/commit 置 superseded。若容器被过度修剪导致"未终结项"提前消失，重启会**静默跳过**本该失败的清理。
   ⇒ 修剪必须在**非重启路径**的 transact 内进行，且绝不能删未终结项。

**风险等级：中**。改动在恢复链路的核心契约上，必须有针对性测试（见 §6）。

### L2 事件表 checkpoint + 尾部保留（收益最大）

**目标**：磁盘 3.79 GiB → ~175 MiB，**启动 replay 81 s → ~4 s**。

**新表**（schema 演进，需 migration）：

```sql
CREATE TABLE IF NOT EXISTS model_control_journal_checkpoint (
  id       INTEGER PRIMARY KEY CHECK(id = 1),
  sequence INTEGER NOT NULL,
  digest   TEXT    NOT NULL
);
```

语义：`sequence` 之前（含）的事件已被裁剪；`digest` 是被裁剪的最后一条事件的 digest，作为**新的链锚点**。

**写入侧**：`model_control_repository.transact()` 在插入事件后追加修剪：

```python
MAX_JOURNAL_ROWS = int(env QLH_MODEL_CONTROL_JOURNAL_MAX = 1000)
KEEP_JOURNAL_ROWS = int(env QLH_MODEL_CONTROL_JOURNAL_KEEP = 500)

if sequence - checkpoint_sequence > MAX_JOURNAL_ROWS:
    cutoff = sequence - KEEP_JOURNAL_ROWS
    row = connection.execute(
        "SELECT digest FROM model_control_events WHERE sequence=(SELECT MAX(sequence) FROM model_control_events WHERE sequence<=?)",
        (cutoff,)).fetchone()
    if row:
        connection.execute("DELETE FROM model_control_events WHERE sequence<=?", (cutoff,))
        connection.execute("INSERT INTO model_control_journal_checkpoint VALUES (1,?,?) "
                           "ON CONFLICT(id) DO UPDATE SET sequence=excluded.sequence, digest=excluded.digest",
                           (cutoff, row["digest"]))
```

**读取侧**：`recovery_status()` 改为从 checkpoint 起校验：

```python
checkpoint = connection.execute(
    "SELECT sequence, digest FROM model_control_journal_checkpoint WHERE id=1").fetchone()
sequence = checkpoint["sequence"] if checkpoint else 0
previous = checkpoint["digest"] if checkpoint else "0" * 64
for row in connection.execute(
        "SELECT * FROM model_control_events WHERE sequence>? ORDER BY sequence", (sequence,)):
    ...
    # 校验逻辑不变
if last is None and not checkpoint:
    return {"verified": False, ...}
# 尾部最后一条的 state 必须等于当前快照（原 L82-83 不变）
```

**同样要改 `transact()` 里取 previous 的 L55**：

```python
previous = connection.execute(
    "SELECT sequence,digest FROM model_control_events ORDER BY sequence DESC LIMIT 1").fetchone()
```
⇒ 事件表被裁空时必须回落到 checkpoint，否则 `sequence` 会从 1 重新开始、`previous_digest` 变回 `"0"*64`，链直接断。

**不变量（必须在实现时用断言守住）**：
1. `checkpoint.sequence < 任何现存事件的 sequence`
2. `checkpoint.digest == 被删区间最后一条的 digest`
3. 现存事件仍首尾相接，且第一条的 `previous_digest == checkpoint.digest`
4. 最后一条事件的 `state` 仍等于 `model_control_state.payload`

**风险等级：中高**。这是恢复正确性的核心，但改动面集中在一个文件内，且可用 §6 的用例把不变量钉死。

**收益**：磁盘 −3.6 GiB；启动 **−77 秒**；且增长速度降到可控。

### L3 文件空间回收（VACUUM）

SQLite 删除行后**不缩小文件**（当前 freelist 只有 522 页，说明历史数据从未删过）。裁剪后必须：

```sql
PRAGMA auto_vacuum = INCREMENTAL;   -- 需要一次全量 VACUUM 才生效
VACUUM;
```

- 3.9 GiB 库 VACUUM 需要约等量临时空间（C 盘当前 100 GiB 空闲，够）
- **必须在没有其他连接写入时执行**（独占锁）；建议放在启动早期、或一次性维护动作
- 之后可定期 `PRAGMA incremental_vacuum(N)` 增量回收，避免每次全量

⚠️ VACUUM 期间 master 不可用，且对磁盘 I/O 压力大——**不要放在推理请求路径上**。

## 5. 对耗时测量的影响（GPT 统计用时必读）

1. **`recover()` 在每次启动时固定付 81 秒**（`deployment.py:46`），且随事件增长线性恶化。任何"启动耗时 / 就绪耗时"的统计里都包含它。
2. 这个值**不是常数**：事件表每分钟都在长（实测 14:51 时 3861.3 MiB，几分钟后 3894.1 MiB）。跨时段对比启动耗时会引入这个漂移。
3. **L2 上线后该值会突降到 ~4 秒**。若在同一次统计里混入改动前后，数据会失真 ⇒ 建议在实施前后各标一次基线，并把 replay 耗时单独打点（见下）。
4. **建议先加埋点再改**：在 `recovery_status()` 前后各打一条 `event=model_control_journal_replay rows=… bytes=… elapsed_ms=…`，这样"启动慢"能被拆成 replay / 模型加载 / 其它三段，而不是一个总数。

## 7. outbox 探查结论、新增实测与未验证清单

### 7.1 已定性：`outbox` 不是队列，是「命令授权 + 投递审计台账」

**删除路径从来不存在**，346 条堆积 = 设计缺口（无保留策略）+ 1 个确定 bug。

- 唯一写入点：`control/deployment.py:317-324`（`save_execution` 内逐条 `state["outbox"][key] = {...}`）。
- 状态改写 3 处，**均不删**：`deployment.py:325-330`（收到 ACK → `acknowledged`）、`:64-67`（每次重启把 `prepare`/`commit` 置 `superseded`，注释明文 *"Old commands remain auditable"*）、`:361-364`（`settle_cleanup`）。
- 全仓唯一的 `.pop(` 是 `state["cleanup"].pop(cleanup_id)`（`:361`）——**cleanup 有终结，outbox 没有**，这就是不对称点。
- 唯一读取判据：`authorize_command`（`:333-345`），**非 prepare/commit 恒返回 True**；唯一调用者是 `worker_prepare_coordinator.py:232-238`。
- 实测构成：`acknowledged 155 / superseded 114 / pending 77`；`attempts=1` 209、`attempts=0` 77；`delivered=True` 269。

⇒ **既不是「TTL 未到」，也不是「重试堆积」**：重试逻辑（`scheduler_pipeline.py:3793-3923`，退避 `min(60, 5·2^(n-1))`、无上限、无死信）**完全不读 outbox**，它读内存态 `transaction["retry_state"]`。

**顺带查实一个确定 bug（1 行，独立于本方案，建议立即修）**：
`settle_cleanup`（`control/deployment.py:362-364`）按 `payload["cleanup_id"]` 匹配，而 **master 债务的 cleanup_id 落在 `payload["config_id"]` 上**（由 `scheduler_pipeline.py:772-778` 构造）⇒ **恒不命中**。实测 77 条 pending 中有 **74 条是 `node_id="master"` / `action="cleanup"`**（`action` 还是 `deployment.py:322` 的兜底默认值，真实语义在 `payload["cleanup_action"]`），这批对应债务早已 settle，台账却永远停在 pending。
**功能影响：无** —— `authorize_command` 对非 prepare/commit 恒 True、准入/退役判定不读 outbox、master 清理走本地 psutil 路径（`scheduler_pipeline.py:826-864`）。**这是记账/可观测性 bug，不是故障**；但若不修，未来加保留策略时会把它误判成「未完成投递」而永远保不住。

**仓库里那张独立 `outbox` 表**：是 control-svc（Node/TS）SQLite v1 的 legacy「本地→远端投影」积压表，**与聚合内 outbox 同名不同物、不存在迁移双写**，0 行是预期空壳（M1.3 已让 projector 退场）。

**⚠️ 对本方案预期的重要修正**：裁剪 outbox **对本轮启动的 73.3 s 只值 5–6 s（7–8%）**。历史事件无法改写，它只让**未来**每条事件小约 22.6%（outbox 占当前单条快照 494,512 B / 2,189,413 B），属渐进收益。**真正该先处理的是「每次都写整份快照」的写放大**，见 7.2。

### 7.2 新增实测：写放大与读取放大比 outbox 更严重

1. **写速率是首要风险**：实测 10 分钟内 events `6937 → 6994`（**+57 条 ≈ +125 MB**）。写入侧 `_persist_pipeline_lifecycle_locked` 有 **19 个调用点**（`scheduler_pipeline.py` 多处 + `worker_prepare_coordinator.py:336` + `scheduler.py:3989/4061`），每次写一条 ~2.19 MB 事件。
   *口径说明*：这是**活动期**速率（含本次排查与并行改动的测试），不代表空闲稳态；但「每次 2.19 MB」是恒定放大系数，与活动量无关。
2. **膨胀呈平方级**：events 体积采样 seq1=405 B、seq500≈209 KB、seq2000–4000≈226 KB、seq5000≈698 KB、seq6000≈1.50 MB、seq6800≈2.09 MB ⇒ 梯形积分 **≈3.9 GB**；**最近约 2000 条（29%）占约 71% 体积**。
3. **单条成本实测 15.03 ms/MB**（2.175 MB 的 `json.loads` 16.22 ms + `canonical+sha256` 16.46 ms）。
4. **两次独立测量的启动校验耗时一致**：本次 73.3 s（`mode=ro&immutable=1`，`verified=true`，`durable_sequence=6994`）vs §1.4 的 81.12 s（6912 条）——同量级，可作为稳定基线。调用链确认为 `scheduler.py:662` → `deployment.py:46`。
5. **`snapshot()` 是热路径读取放大**：`deployment.py:24-32` 每次读整行 ~2.19 MB，而 `bootstrap/client_snapshots.py:14/33/46` **单次快照读 3 次**、`model_intent.py:49/57/63/88/90/104` **单次 API 读 3–4 次** ⇒ 每次 TUI 5 s 刷新约解析 **6.5 MB**（其中 outbox ≈1.5 MB）。这条不直接影响启动，但持续吃 CPU。
6. **`supplies` 是单条快照的最大单体**（1.30 MiB / 81 条，每条 ≈16 KiB）。`supplies + outbox + deployments` 合计占 state 的 **96.6%** ⇒ L1 的优先级应是 **`supplies` > `outbox` > `deployments`**。

### 7.3 仍未验证

1. **L1 修剪会降低审计能力**（历史 supplies 不可查）。`recovery_status` 只校验事件链与最终 state 等值、不校验容器条目数，所以不会导致 `journal_corrupt`；但"历史可查"这个产品语义需要确认可接受。
2. **未实测 VACUUM 在 3.9 GiB 库上的耗时**。
3. **HA 场景是重大未决风险**：若启用 auto/HA，`renew_lease` 会每 ≤5 s 触发一次全链校验（`cluster_auto_role_runtime.py:629`、`:445-447`）——届时 73 s 的校验按每 5 s 跑一次是灾难级。本机 `.env` 的 HA 段整段被注释、`node_config.json` 为 `role:"master"` ⇒ **静态 master 不触发，属配置推断、未实测**，必须先复验 `NODE_ROLE`/`QLH_NODE_ROLE` 实际取值。
4. **截断 events / 重建库与 quorum floor 的冲突未实测**：floor 记录 `(domain, sequence, digest)`（`cluster_quorum.py:189/393-404`、`cluster_auto_role_runtime.py:243-252/266-269`）。**裁剪 state 安全**（不改变 sequence/digest，每次裁剪都推进 revision 与 sequence）；但**删 events 或重建库**会与 floor 冲突（`committed_prefix_behind`）。该结论从代码语义推出，未实测，是 L2 的前置风险。
5. **events 精确总字节未测**（活动写入下 `SUM(length(payload))` 易被撕裂），3.9 GB 为 12 点采样积分。
6. **未查 voter ledger**（`quorum-master-voter-r2/r3/r4.sqlite3`）中是否含 `model-control:v1` 的 floor。
7. **在活动写入的库上做只读全扫必须容忍撕裂重试**：本次探查首次尝试即遇 `database disk image is malformed`，重试成功——数据库本身没坏，但任何诊断脚本都要按此设计。
8. 段工件那 10.70 GiB（hardlink 去重后）未纳入本方案——属另一话题（免裁/供给优化），且当前是**必要**的。

## 8. 建议的实施顺序

1. **先加 replay 埋点**（零风险，让 81 秒可观测、可拆分）——这直接服务 GPT 的用时统计。
2. **顺手修 `settle_cleanup` 匹配键**（`control/deployment.py:362-364`，1 行，独立零风险）：同时接受 `payload["cleanup_id"]` 与 `payload["config_id"]`，让 74 条 master 清理台账结清。功能上无影响，但**不修会让未来加保留策略时把它误判成「未完成投递」而永久保留**。
3. **L1 容器修剪**（收益中等、风险中，但它是 L2 收益的前提：state 变小后每条事件才变小）。**优先级 `supplies` > `outbox` > `deployments`**（三者合计占 state 的 96.6%）。
4. **L2 checkpoint**（收益最大，风险中高，需 §6 全套测试）。
5. **L3 VACUUM**（最后做，一次性回收；需维护窗口）。

⚠️ 实施方注意：该契约位于 `src/qlh_core/`，与并行进行中的 `src/model_supply*` 改动属于不同模块，但**都影响 master 启动链路**，合并时建议先各自跑 §6 的回归基线再合。
