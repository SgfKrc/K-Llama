# 关键架构泛化与分布式调度可用性审查报告

日期：2026-10-04  
范围：只读审查当前 `dev` 工作区代码、测试与现有证据；本报告未修改运行代码，也未把单元测试结果等同于三机生产验收。

## 结论摘要

### 1. 模型泛用性：不是通用架构适配器，而是“Qwen 家族适配器 + 明确拒绝未知架构”

结论为 **P1 风险**。当前设计已经比最初的 Qwen-1.8B 硬编码好：架构描述有单一事实来源，支持 `qwen`、`qwen2`、`qwen3_5`、`qwen3_5_text`，并对不支持架构 fail-closed。这是正确的安全策略，但不能称为按模型基座/架构种类的通用适配。

证据：

- [pipeline_model_descriptor.py](../../../src/pipeline_model_descriptor.py) 的运行时白名单只有四种 Qwen 系类型；布局表 [pipeline_model_descriptor.py](../../../src/pipeline_model_descriptor.py) 依赖固定 tensor 前缀。
- [model_module.py](../../../src/model_module.py) 将层加载器和 attention/mask 语义绑定到 Qwen 结构；[model_module.py](../../../src/model_module.py) 对未知架构直接拒绝，Gemma 也明确不复用 Qwen2 执行器。
- [pipeline_assignment_manifest.py](../../../src/pipeline_assignment_manifest.py) 对未知 `model_type` 直接报 `unsupported model type`。
- 调度的 KV 长度解释在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 仍按 `qwen` 与“其它”二分，属于架构形状硬编码。
- GGUF keep-head/跨层接力在 [llama_engine.py](../../../src/llama_engine.py) 对 `qwen3*` 明确禁用；这意味着 GGUF 能加载不等于能参加跨节点层接力。
- GGUF chat fallback 在 [llama_engine.py](../../../src/llama_engine.py) 仍有 Qwen ChatML/文件名兜底；默认 GGUF 搜索在 [llama_engine.py](../../../src/llama_engine.py) 按 `Q4_K_M`、`Q5_K_M`、目录首个文件选择，存在模型选择脆弱性。
- `model_config.py` 的产品模型目录绝大多数为 Qwen 或 Qwen 派生模型，Gemma 4 仍被隔离到 sidecar；现有文档也登记了 [已知问题记录.md](../../已知问题记录.md) 的 Gemma PyTorch 层适配未闭环。

因此，当前“泛化”的准确表述应是：

> 对已登记且已实现 adapter 的 Qwen 系架构，按模型描述符、层数、权重前缀和 KV 语义进行适配；对其它架构安全拒绝，不能自动适配。

这套策略的优点是避免把未知模型误当 Qwen 跑出错误结果；缺点是新增 Llama/Mistral/Phi/Gemma 等基座时，需要同时补布局、选择性加载、forward/cache、最终 norm/LM head、GGUF relay 挂点、协议能力和真实验收，改动面大，脆性集中在架构分支。

### 2. 分布式调度可用性：协议层较严谨，但产品链路仍有明显脆弱性

结论为 **P0/P1 可用性风险**。调度不是完全不可用：已有重连、ACK、generation、lease、断线重分片和 fail-closed 机制；但真实链路的成功依赖多个状态机、两套 relay 数据面和严格时序，导致实测中容易从“可用”退化为 503、回退或等待超时。

直接证据：

- 现有问题记录 [已知问题记录.md](../../已知问题记录.md) 仍记录真实双机曾出现重复注册、旧 socket、ACK 顺序和 reservation 重复释放问题；长时间升级/断电验收 `T-RACE-6-C` 仍未完成。
- [已知问题记录.md](../../已知问题记录.md) 记录过裁层工件被整模回退、A1/A2/A3 角色判据分散、relay 与 Stage 并存时所有请求 fail-closed 等问题。这些不是理论风险，而是近期真机暴露的生命周期/隔离问题。
- `_run_pipeline` 在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 对 v3 Stage 与 legacy relay 混合拓扑直接返回 `route_a_mixed_legacy_execution_bridge_not_ready`。这是正确的防错，但意味着同一集群中两类节点并存时可用容量会直接变成不可用容量。
- 请求前同步在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 最多等待 `PIPELINE_MODEL_SYNC_TIMEOUT`，默认配置为 60 秒；失败后普通请求回退整模，`distributed_required` 则返回错误。用户感知是长等待或 503，而不是快速选择可用拓扑。
- 每步等待在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 使用 `PIPELINE_STEP_TIMEOUT`，默认 120 秒；跨设备链路中任一节点、ACK 或 relay 无响应，整步失败并广播 abort。
- worker 心跳容忍在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 为 120 秒，TCP 端的最大丢心跳次数又由 step timeout 计算（[tcp_comm.py](../../../src/tcp_comm.py)）。这对长计算步骤较宽松，但会延迟失效发现；而 Route A/Android presence 又有独立心跳与准入状态，多个时间基准增加了竞态面。
- 断线处理 [scheduler.py](../src/scheduler.py) 同时做任务失败、节点 offline、注销、重分片/重推配置；若断线发生在配置事务或任务中间，恢复依赖多个异步路径，尚未有长时真实设备证据。
- layer config retry 在 [scheduler_pipeline.py](../../../src/scheduler_pipeline.py) 采用 5、10、20、40、60 秒退避，且只对“尚未 pushed”的状态重发；ACK、release、active config 与 restart rehydrate 由不同状态集合维护，正是近期 release/re-ACK 互相打断问题的高风险来源。
- relay 会话实际由 `inference_service.peer` 持有，而调度侧仍保留另一套 `_relay_segment_clients`（[scheduler_pipeline.py](../../../src/scheduler_pipeline.py)）。现有问题记录明确指出调度侧关闭路径曾是死代码，形成“看似清理、实际不清理”的可用性错觉。

### 3. 已有证据的边界

- `docs/archive/distributed/分布式推理线路清单-2026-10-04.md:17-29` 说明 A1 有三机产品级证据，A2 有 Y700 真机证据，但 A4 legacy PyTorch 真机层段对拍缺少独立记录。
- 同一清单 `:32-50` 明确 Qwen3 sidecar 跨物理机、Gemma、Android Edge RPC 生命周期和断线/热/电量仍未验收。
- 单元测试数量多，且覆盖大量竞态模型；但这些测试不能证明真实设备上的 socket、后台残留进程、心跳抖动、模型加载耗时和重启窗口可用。

## 分级问题清单

### P0：不应宣称“分布式可用”但尚未解决/验收

1. **A1 legacy relay 与 A3 Route A 并存时没有统一调度域。** 当前混合拓扑按设计拒绝，导致节点在线但不可用；需要产品决策：单一主线路由，或统一 Stage/relay 的 KV 与生命周期契约。
2. **配置生命周期在重启、release、re-ACK、任务进行中存在竞态风险。** 应用层需要单一版本化 active config、事务状态和任务引用，不能继续靠多个集合旁路修补。
3. **缺少真实长时/断电/升级验收。** 至少要完成 `T-RACE-6-C`，覆盖 master 重启、worker 重连、配置恢复、任务中断和再次请求。

### P1：高脆性与泛化不足

1. 将架构适配集中在 Qwen layout 与 Qwen mask/cache 分支；未知架构虽安全拒绝，但新增架构成本和回归面很大。
2. GGUF 文件名、Q4/Q5 默认选择和 Qwen ChatML 兜底仍可能把“模型可加载”与“模型语义正确”混为一谈。
3. keep-head relay 对挂点和 shim 强依赖，Qwen3* 明确禁用；跨架构 relay 不能由通用 `forward_layers` 名称推断可用。
4. 心跳、TCP、task-worker lease、Android presence、layer-config retry 使用多套时钟与 readiness 判据，实际网络抖动下容易出现在线/未就绪/已分配三个状态不一致。

### P2：工程治理与验证缺口

1. 继续保留 legacy relay 与 Route A 两套并列实现，会持续产生隔离和死代码问题；应确定淘汰顺序与唯一入口。
2. 为每个支持架构建立独立的 descriptor → assignment → prefill → decode → full-model 对拍矩阵；当前 Qwen 覆盖较深，其它架构多数只到拒绝或 sidecar。
3. 将“可用”拆成协议可用、同机可用、跨机可用、重启恢复可用、长时可用五个门，不能用探针或单次 HTTP 200 代替。

## 建议的验收门

1. 架构门：至少 Qwen2、Qwen3.5 hybrid、一个非 Qwen decoder（如 Llama/Mistral）分别给出“已支持并对拍”或“明确拒绝”；禁止仅凭 `model_type` 白名单通过。
2. 调度门：三机连续运行 2 小时，注入 master 重启、Surface 断线、Android 重连、配置重发、请求取消；要求无 stale active task、无旧 generation ACK 污染、无错误 HTTP 200。
3. 线路门：A1、A3 分别验收；混合拓扑必须快速返回具名不可用原因，并且不能绕过裁层整模校验。
4. 证据门：每次成功请求必须同时具备 `distributed_used=true`、`fallback=false`、非空 `claimed_layers`，并与完整模型逐 token 对拍；只出现探针成功或 fallback 成功不算分布式通过。

## 总判定

当前项目的引擎/调度实现具备较强的实验性深度和安全拒绝意识，但产品泛用性与分布式可用性都不能按“通用、稳定”宣称。更准确的定位是：**Qwen 系重点架构上的研究型异构分布式运行时，具备若干真实三机成功证据，但配置生命周期、线路合并和长时故障恢复仍是产品化阻塞项。**

## 裁定与登记（2026-10-04，项目作者）

以下为对本报告 P0/P1/P2 与「建议的验收门」的正式裁定，以及登记为待做的项。

### P0-1 线路形态：**条件性保留 A1，以淘汰 A1 为目标**

> 2026-10-04 复审后修订。前一版裁定为「不淘汰，定义统一契约让混链可跑」；专门的 A1/A3 差异调研推翻了它的前提。

**调研结论（推翻前一版裁定的依据）**：A1 名义上的「独有能力」逐条不成立——`head` 角色被调度侧显式拒绝（`src/scheduler.py:2244-2247`）、传输量化档被客户端硬拒（`src/relay_segment_client.py:136-141`）、多段链本身有 1 段硬上限（`src/scheduler.py:2267-2270`「多段 relay chain 尚未接线」）、keep-head 上游通道与末段 argmax 都与 A3 共用。**A1 的实质唯一性只剩一条**：段执行体可以是集群外、只暴露 loopback 的独立进程（`scripts/relay_mid_service.py` 无注册逻辑）。而 A3 在**多段链（无上限，真机三段已跑）、worker 载体（PC + Android）、每步 offer/lease/取消/对账、开关可热切换、跨机无需 SSH 隧道**上全面胜出。

**并且「并存」的真实代价不是冗余而是净损失**：集群同时存在 relay 宿主与 stage worker 时 `stage_offer_nodes ≠ pipeline_nodes`，`_run_pipeline` 全拒（`src/scheduler_pipeline.py:5319-5339`）——而调度侧仍把 relay 宿主容量计为可用（`capacity_source="relay_exempt"`），**看得见、拿不到**。

**裁定**：目标形态是**只剩 A3 一套产品数据面**。

**A1 的定位（2026-10-04 作者确认）**：A1（legacy relay + `relay_mid_service` + 强制 loopback + SSH 隧道）**本质上是服务探针与实验的支撑设施，不算产品路径**。它的 40/40 产品级数值证据虽然真实，但那条路径依赖「段服务在集群外 + SSH 隧道把远端端口映射到本机 loopback」（`src/relay_transport.py:432-433`、`:822-826`），属于实验/验证形态，不作为产品交付形态。因此：

- **不做「先让 A3 顶上来再淘汰 A1」的替换式过渡**；A1 可以按其自身节奏退场，不必以 A3 达标为前置。
- **过渡期只做清理**（C5），不动 A1 的数据面，也不以它作为容量路径。A1 默认关闭，且不允许与 A3 被自动同时选中。

**C1/C2 的定位（本次分清）**：下面这两条**不是「淘汰 A1 的前置条件」，而是 A3 自身的质量门** —— A3 要成为唯一产品数据面，自己就该满足它们。它们的排期与 A1 的去留无关。

- **C1（A3 自身质量门）**：A3 补**产品路径逐 token 同精度对拍**（≥40 decode，与 f16 整模基线），覆盖末段（argmax、master 无 lm_head）与中段各一次。
- **C2（A3 自身质量门）**：A3 补 **≥3 段真机链的 prefill+decode 验收**（目前只有 Y700 单链），并把段数上限与失败语义写成判据。

以下两条仍是**淘汰 A1 的动作项**（而非质量门）：

- **C3**：A3 的 PC 侧补齐 `middle_channel` 语义或显式拒绝 —— 当前 PC 执行体忽略它（`src/inference_service/engine_host.py:2026` 只看 `want_hidden`），只有 Android 执行体消费，属隐性不对称。
- **C4**：给出取代 A1-1 唯一性的方案 —— 即「集群外段服务 + SSH 隧道」这件事**是否还需要**；按作者确认，答案为**不需要**，该形态随 A1 一并退场。

**清理面（C5）**：

- **C5**：删 `_close_all_relay_segment_clients()`、把角色判据收进 `_is_relay_host()` 唯一入口、把 relay 会话所有权收敛到单一真源（见 `已知问题记录.md` `#34`）。

### 双重角色：**互斥，启动期检测，两开关同开则拒绝启动**

`QLH_RELAY_ENABLED`（import 期常量，`src/config.py:452`）与 `QLH_TASK_WORKER_EXPERIMENTAL_ENABLED`（可运行时热切换，`api_server.py` 的 `_set_task_graph_runtime_settings`）从未出现在同一条件里。

**裁定**：**一个节点只能是一种角色**。落地方式为**启动期检测**——两个开关同时开启时直接 fail-closed、以具名错误拒绝启动，而不是运行时默默看谁先生效（不沿用当前的「relay 优先」隐式行为 `:572`）。

### P0-2 配置生命周期：登记为待做，本轮不改代码

调研清点出 **~20 个**维护层配置生命周期的状态集合（初始化见 `src/scheduler.py:1004-1037`、`:1064-1075`；含 `_layer_config_pushed` / `_expected` / `_acks` / `_retry_state` / `_generation` / `_receive_sequence` / `_inflight` / `_pending_layer_config` / `_prepared_layer_configs` / `_active_layer_config`，另有 peer 侧的**第二套** `src/inference_service/peer.py:79-96`）。其中至少 5 处可互相不一致：

- `_layer_config_pushed`（就绪）与 `_active_layer_config`（生效）
- `_layer_config_acks` 与 `_layer_config_expected`（缺 `generation` 的 ACK 会被整条忽略）
- `_pending_layer_config` 与 `_expected`（早退不广播中止即永挂，`#33` 第②层）
- `_pipeline_load_transaction.worker_ids`（只含 legacy）与 `_active_pipeline_capacity_plan`（可含混合条目）
- master `_layer_config_generation` 与 peer `_latest_layer_config_generation/_id`（重启窗口）

收敛方向「单一版本化 active config」**已认可但未实施**。

### P0-3 长时验收：登记为待做
