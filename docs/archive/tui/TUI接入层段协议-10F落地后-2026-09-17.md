## 1. 10F 提供了什么（可直接消费的接口）

### 1.1 `PipelineNode`（`pipeline_node_contract.py:193`）

```python
node_id: str
kind: str                      # local | remote_rpc | cross_framework | ...
layer_range: tuple[int, int]   # [start, end) 半开
engine: str                    # llama.cpp | pytorch
location: str
capacity: PipelineNodeCapacity
artifact: PipelineArtifactRef
has_embedding: bool = False
has_lm_head: bool = False
federated: bool = False         # ★ 维度 A：是否跨机
cross_engine: bool = False      # ★ 维度 B：是否跨引擎
handoff_at: int | None = None   # 跨引擎交接层号
```

**→ `federated` / `cross_engine` 正是[可行性确认 §2.1](../relay/层流水线节点类型与顶层透明性-可行性确认-2026-09-17.md) 建议的两个正交维度，已被采纳。**

### 1.2 `PipelineLayout`（`:257`）—— ★ 顶层真正需要的东西

| 成员 | 值 | 对顶层的意义 |
| --- | --- | --- |
| **`is_distributed`** | `any(n.federated)` | **「是否分布式」的单一事实来源** |
| **`engines`** | 去重元组 | 「用了哪些引擎」|
| **`contract_sha256`** | 布局哈希 | **可校验**（同一布局稳定）|
| **`aggregate_capacity`** | 总量 + **`by_execution_device`** | **聚合资源视图**（顶层只读）|
| `total_layers` / `model_sha256` / `architecture` | | 身份校验 |

**⚠️ 关键**：`aggregate_capacity` 是**聚合**的（本地 + 远端），不是本机画像 ——
这正好解决[可行性确认 §4.1](../relay/层流水线节点类型与顶层透明性-可行性确认-2026-09-17.md) 指出的问题。

### 1.4 ★ 实测确认的实际返回（2026-09-17 用 `TestClient` 打过）

**`/api/cluster/pipeline-capacity`** —— **扁平结构，`PipelineLayout` 嵌在 `pipeline_layout` 键下**：

```json
// 无活动计划时（本机实测）
{"status": "unavailable", "admitted": false,
 "reason_code": "pipeline_descriptor_unavailable", "assignments": []}

// 有活动计划时（由 scheduler._attach_pipeline_node_contract():3201 附加）
{"status": "ready", "admitted": true, "assignments": [ {...} ],
 "pipeline_layout": { "is_distributed": ..., "engines": [...],
                      "aggregate_capacity": {...}, "nodes": [...],
                      "contract_sha256": ... },
 "transaction_phase": "planned"}
```

**⚠️ 因此 TUI 必须读 `plan["pipeline_layout"]`，而不是 plan 顶层。**
失败时 `pipeline_layout` 为 `None` 且 `reason_code="pipeline_node_contract_invalid"`（fail-closed）。

**`/api/cluster/pipeline-reshard`** —— **已实测**：

```json
{"status": "inactive", "epoch": 0, "last_decision": null}
// 激活时额外含：active_contract_sha256 / staged（scheduler.py:3362-3368）
```

### 1.5 `kind` 取值与 `location` 脱敏（**重要**）

`scheduler._pipeline_node_metadata()`（`:3172`）产出：

```python
"location": "local" if node_id == local_node_id else f"node:{node_id}",  # ★ opaque
"kind":     "local" if node_id == local_node_id else "remote_pipeline",
"federated": node_id != local_node_id,
"engine": "pytorch",      # ⚠️ 硬编码
```

**`KNOWN_NODE_KINDS`（`pipeline_node_contract.py:20`）= `{local, remote_rpc, remote_pipeline, cross_framework}`**

| 观察 | 含义 |
| --- | --- |
| **`location` 是 opaque（`node:<id>`）** | ✅ **符合「顶层不关心谁在远端」** —— TUI 可安全显示，不会泄露 IP |
| **`kind` 目前只产出 `local` / `remote_pipeline`** | ⚠️ **`remote_rpc`（借算力）与 `cross_framework` 尚未由 scheduler 产出**，TUI 现在看不到这两种 |
| **`engine` 硬编码 `"pytorch"`** | ⚠️ **未按节点画像取引擎** —— TUI 若显示引擎会**全部显示 pytorch**（失真）|

## 3. 接入方案

### 3.1 原则（来自用户构想）

> **顶层默认不知道谁在本地、谁在远端；可按需查询「是否分布式」；可显式约束。**

**推论（三条设计约束）**：

1. **默认视图用聚合量**（`is_distributed` / `engines` / `aggregate_capacity`），**不逐节点列 `location`**；
2. **`location` 若显示，必须脱敏** —— 与 `/cluster/pipeline-reshard` 的 **"address-free"** 保持一致
   （**默认显示为 `本地` / `远端`，不显示 IP/主机名**）；
3. **引擎与节点类型可以显示**（它们不是"谁在哪"，而是"怎么算的"），**因为选择引擎是顶层要做的决策**。

### 3.2 改动一：`DistributedScreen.fetch()` 增补新端点（**低风险**）

```python
def fetch(self):
    di = self.api.get("/cluster/config/distributed-inference")
    layers, layers_err = self._sub("/cluster/layers")        # 保留：手动覆盖用
    capacity, capacity_err = self._sub("/cluster/pipeline-capacity")   # ★ 新增
    reshard, reshard_err = self._sub("/cluster/pipeline-reshard")
    cfg, cfg_err = self._sub("/cluster/config")
    return {"di": di, "layers": layers, "layers_err": layers_err,
            "capacity": capacity, "capacity_err": capacity_err,      # ★
            "reshard": reshard, "reshard_err": reshard_err,
            "cfg": cfg, "cfg_err": cfg_err}
```

**为何不替换 `/cluster/layers`**：`/cluster/layers` 承载**手动覆盖**的读回
（`LayerOverrideItem{node_id, start_layer, end_layer}`，见 `api_server.py:7742`），
与 `pipeline_layout`（只读投影）**职责不同**，应并存。

### 3.3 改动二：「模型分层」表改为消费 `plan["pipeline_layout"]`（**核心**）

**⚠️ 关键路径**（§1.4 实测）：**`PipelineLayout` 嵌在 plan 的 `pipeline_layout` 键下**，
不是 plan 顶层。取用方式：

```python
plan = d.get("capacity") or {}
layout = plan.get("pipeline_layout")          # ★ 嵌套，可能为 None
if not isinstance(layout, dict) or not plan.get("admitted"):
    # 退化为：显示 plan["status"] / plan["reason_code"]（如 pipeline_descriptor_unavailable）
    ...
is_distributed = bool(layout.get("is_distributed"))
engines = layout.get("engines") or []
nodes = layout.get("nodes") or []
aggregate = layout.get("aggregate_capacity") or {}
contract = layout.get("contract_sha256", "")
```

**新表列**（在 `DistributedScreen.lines()` 中，来源均为 `layout["nodes"][i]`）：

| 列 | 来源 | 说明 |
| --- | --- | --- |
| **节点** | `node_id` | 保留 |
| **类型** | **`kind`** | ★ 新增；中文标签（见 §3.5）；**当前只会出现 `local` / `remote_pipeline`** |
| **层区间** | `layer_range` | `[start, end)` → 显示 `start-end` |
| **引擎** | **`engine`** | ★ 新增；**⚠️ 当前恒为 `pytorch`**（§1.5），显示前需确认是否已按画像取值 |
| **端** | **`federated` / `cross_engine`** | ★ 新增；**显示为「本地/远端」+「跨引擎」**；`location` 是 opaque 可直接显示 |
| **Embedding / LM Head** | 同名 | 保留 |
| **容量** | `capacity.required_bytes` / `capacity.headroom_bytes` | ★ 新增 |
| **交接点** | **`handoff_at`** | ★ 新增（仅 `cross_engine` 有意义）|

**表头行（区块头部，代替旧的 `total/strategy`）+ 聚合**：

```
◆ 层段布局
  总层数: 24    节点数: 3    引擎: llama.cpp, pytorch
  模式: 分布式    合同: 3f2a1b9c
  聚合容量: 需求 4.2 GB / 余量 1.1 GB（按执行设备: cuda 2 节点, cpu 1 节点）
```

**★ 关键**：**「模式」一列直接取 `layout.is_distributed`**，不再由 `assignments` 是否为空推断。

### 3.4 改动三：`tui_shared.py` 补端点常量

```python
API_PATHS = {
    ...
    "cluster_resources": "/cluster/resources",          # 已有
    "cluster_pipeline_capacity": "/cluster/pipeline-capacity",   # ★ 新增
    "cluster_pipeline_reshard": "/cluster/pipeline-reshard",     # ★ 新增（L1037 现为字面量）
}
```

### 3.5 改动四：节点类型图例（**可选，但建议**）

**⚠️ 前置事实**（§1.5 已核）：**scheduler 目前只产出 `local` / `remote_pipeline`**，
`remote_rpc` 与 `cross_framework` **尚未被产出**。因此图例有两种做法：

| 做法 | 说明 |
| --- | --- |
| **A（推荐）只列可达值** | 列 `local` / `remote_pipeline` —— **眼下不会误导** |
| B 列全部 4 种 | 需同时标注「未接入」—— 否则用户会以为 `remote_rpc` 已在用 |

**做法 A 的图例**：

```
  类型: local=本机层段  remote_pipeline=流水线远端节点
```

**理由**：`remote_rpc`（原「Silica 式兜底」改名后的节点）**要等 scheduler 真正产出后才该出现在图例里**，
否则是「文档先行、代码未至」。**建议把 B 留到 `remote_rpc` 落地时再改。**

## 4. 明确**不做**的事（边界）

| 不做 | 理由 |
| --- | --- |
| **逐节点显示 IP / 主机名** | 违背「顶层不关心谁在远端」；与 `pipeline-reshard` 的 **address-free** 不一致 |
| **按「本机 vs 远端」分组展示** | 那是中层的组织方式；顶层只关心「是否分布式」这一个布尔 |
| **把 `PipelineNode` 做成可编辑** | 编辑入口是 `/cluster/layers`（手动覆盖）；`PipelineLayout` 是**只读投影** |
| **在 TUI 里做重分片决策** | `pipeline-reshard` 已有 `PipelineReshardDecision` / `CommitDecision`，**TUI 只读状态** |
| **改 `/cluster/layers` 的返回格式** | 兼容既有 `LayerOverrideItem` 调用方（可能被其他客户端消费）|
