# Koakuma TUI 重写方案（2026-09-16）

> 状态：**实现已落地，持续收口**
> 关联：[TUI 使用指南](../../TUI使用指南.md) · [TUI 指令集](../../TUI指令集.md) · [TUI 适配实施计划](TUI适配实施计划.md) · [整体架构](../../整体架构.md)

> **2026-09-17（晚）重大转向：改用 Textual 外壳，放弃自绘 ANSI。**
> **实测证据**（独立控制台窗口采数，非管道）：`isatty=true`、`console_mode=0x3`（未启 VT）、
> `SetConsoleMode` 可启用 VT、`tui_splash.supported()=true` —— 即环境**支持动画**，走的是动画路径，
> 而自绘 splash 仍**不可见**。根因有两条且都属结构性问题：
> ① 帧序列用 `"\x1b[2K\n"`（LF）—— VT 模式下 LF 不回第 0 列，逐行向右累积错位；
> ② 像素字完全由 `▀`(U+2580) 半块字符 + 24 位真彩色拼成——传统 conhost 默认字体/色深下
> 整块 logo 渲染为空白（于是"黑屏"）。
> **裁决**：主仓 TUI 改为 **Textual**（`requirements-tui.txt`；**Edge 同装**，见 `requirements-edge.txt`），
> 由 Textual 承担终端适配；协议层抽出为**纯标准库** `src/tui_api.py`，因此单命令/CI 路径不需要 UI 依赖。
> 新外壳：`src/tui_textual.py`（启动屏 + 聊天 SSE + 状态/模型/分布式/关于）；
> 入口：`qlh` 默认走 Textual；`qlh --tui-engine builtin` 保留参数但**明确报已归档**（rc=2，不静默回退）。
> 冷启动反馈改为**跨终端可靠**的单行 CR 进度（`\r` 回列首），不再依赖自绘动画。
> 三个标准库 TUI 文件（`tui_admin.py` / `tui_chat_screen.py` / `tui_splash.py`，共 4114 行）
> 连同旧 Textual 聊天 `tui_chat.py`、走查脚本与专属测试，**已于 2026-09-17 归档到 `_to_delete/`**
> （该目录不入库、可随时取回）；单命令面抽出为只读薄层 `src/tui_commands.py`。

> **2026-09-17 当前实现记录（历史基线；当晚转向 Textual 后该标准库实现已归档）**：当时 `qlh` 无参与 `qlh chat` 曾进入统一标准库 TUI；本机入口可在当前进程的 daemon 线程内启动并探活 FastAPI，聊天屏曾注册为第 8 个屏幕，支持 SSE 流式输出、会话管理、路由偏好和 thinking 展示。`DistributedScreen` 已消费 `pipeline_layout`，保留旧 `/cluster/layers` 作为手动覆盖兼容入口。该段只保留历史证据，不是当前实现口径；当前为 Textual 9 个功能屏 + 1 个调试兜底屏，现行口径见 [TUI 使用指南](../../TUI使用指南.md)。

> **启动体验与视觉基线（2026-09-17）**：冷启动由 `BackendSupervisor.ensure_ready` 与 `TuiSplash` 并行承载，状态行显示探活、组件加载、API 启动和健康检查阶段；uvicorn/API 控制台日志在统一入口中静默，文件与内存日志继续供日志屏查看。`--no-splash` 保留无动画交互入口，`--plain` 只保留两行状态输出。**（该标准库实现基线已于 2026-09-17 归档，交互面改由 Textual 外壳承担；`--plain` 随归档移除。）**主菜单采用品牌头部、版本/后端元信息、`WORKSPACE` 导航区、`COMMANDS` 快捷区和统一底栏提示，作为类成熟 CLI 的主仓标准库实现基线。

## 0. 一句话

把"**两个窗口 + 两个 TUI**（聊天用 Textual / 管理用标准库）"收敛为 **单进程、单窗口、单 TUI**：
`qlh` 一条命令 → **进程内**起后端 → 播**启动动画** → 进入**统一 TUI**（聊天与全部管理页同在一个界面）。

## 1. 现状与痛点（均有实证）

| 事实 | 证据 |
| --- | --- |
| 原始基线是**两个窗口** | 历史 `start_tui.bat` 会另开后端窗口；统一 `qlh` 入口已改为进程内 supervisor |
| 聊天与管理曾是两个 TUI | 历史聊天页 `src/tui_chat.py` 与 `src/tui_chat_screen.py` 均已归档；当前统一为 `src/tui_textual.py`（9 个功能屏 + 1 个调试兜底屏） |
| 入口语义曾不统一 | `qlh` 无参与 `qlh chat` 统一进入聊天屏；`qlh status/models/nodes/queue/device/logs/help` 为不自动启动后端的**只读**单命令 |
| 依赖曾分裂 | 核心 TUI 使用标准库；`qlh chat --fixture` 已走零依赖回放，`tui_chat.py --fixture` 仅保留历史兼容 |
| 动画只覆盖一条路径 | 曾由 `src/tui_splash.py` 承担；**该文件已于 2026-09-17 归档**，启动动画改由 Textual 外壳的启动屏（LOGO + 启动条）承担 |

**用户痛点原文**：开两个窗口、聊天和其他页面分开，"太蛋疼"。

## 2. 目标（验收口径）

1. **单命令**：`qlh`（无参数）= 一键：起后端 → 等 `/api/health` → 播动画 → 进 TUI；
2. **单进程单窗口**：后端在 **TUI 进程内的线程**里跑（`uvicorn.Server`），**不再 `start` 新窗口**；
3. **单 TUI**：聊天页成为统一 TUI 的**一个页面**，与其余管理屏平级、可互相跳转；
4. ~~**零第三方依赖**（保持主仓/L 档边界，**不引入 Textual**）~~ → **已被 2026-09-17 裁决取代**：交互外壳以 Textual 为主仓硬依赖（Edge 同装）；零依赖边界保留在**协议层与单命令/CI 路径**（`src/tui_api.py`、`src/tui_commands.py`）；
5. **保持既有能力**：7 个管理屏 + 1 个聊天屏、35 条命令、`--plain` 降级、**单命令模式仍不拉后端**（`qlh status` 不误启）；
6. **动画只在进入交互 TUI 时播一次**（`tui_splash.py` 已就位；alt screen 无残影）。

## 3. 架构

```text
qlh（qlh.py，唯一入口）
  └─ KoakumaApp（单一 TUI 进程）
       ├─ BackendSupervisor   ← 探活 8000；未起则进程内 uvicorn（daemon 线程）
       ├─ TuiSplash           ← 启动动画（与 health 探测并行，不延长启动）
       ├─ AnsiTerm            ← 备用屏 + 原始按键（复用 tui_admin 现有实现）
       └─ PageStack           ← 统一页面栈（复用 tui_admin 的 Screen 基类）
            ├─ ChatScreen     ← `tui_chat_screen.py`，零依赖 SSE/会话交互
            └─ 7 个管理屏     ← Status / Nodes / Distributed / Queue / Device / Logs / Settings
```

RAG、独立 Runtime/Registry 产品页不属于主仓核心 TUI；它们随外置仓库或 Koakumix 侧车维护。分布式核心观测不另造页面，直接落在 `DistributedScreen` 的 `PipelineLayout` 区块中。

**关键设计点**

1. **后端进程内化**：`api_server.py` 已暴露 `app = FastAPI(...)` 与 `register_uvicorn_server()`
   （`src/api_server.py:327`、`:819`），可在 `daemon` 线程内 `uvicorn.Server(app).run()`；
   后端日志沿用既有约定写入 `logs/`（**不写 TUI 的 tty**），因此不污染界面；
2. **退出语义不变**：仍由 `/api/system/shutdown` 触发优雅退出（`api_server.py:807-811` 已有该机制），
   避免 Windows 上线程内信号处理问题；
3. **页面抽象复用**：`tui_admin.py` 的 `Screen`（`:626`）与 `AnsiTerm`（`:347`，已用备用屏 `\x1b[?1049h/l`）
   即为统一的页面/终端基类；聊天页实现同一接口（`render()` + `on_key()` + actions）；
4. **HTTP 复用**：`ApiClient`（含 `X-QLH-Log-Token`）；聊天流式复用 `tui_sse.py` 的 SSE 解析。

## 4. 页面清单（统一后）

| 页面 | 来源 | 说明 |
| --- | --- | --- |
| **聊天** | `src/tui_chat_screen.py` | SSE 流式、会话列表、路由偏好、thinking 展示（`/api/chat/stream`、`/api/chat/clear`、`/api/sessions*`） |
| 状态 / 模型 / 设备 / 集群 / 队列 / 日志 / 设置 | `tui_admin.py` 现有 7 屏 | 原样保留（不动协议） |
| RAG / 独立 Runtime / Registry | 外置仓库或 Koakumix 侧车 | 不进入主仓核心 TUI；避免把已裁撤的非核心功能重新耦合回来 |
| Pipeline 观测 | `DistributedScreen` | 消费 `/cluster/pipeline-capacity` 的 `pipeline_layout`；旧 `/cluster/layers` 仅作手动覆盖 |

> 端点覆盖不再通过手工复制路由表维护，但 OpenAPI 调试屏不计作产品功能覆盖：模型、集群、节点（含入群请求码/授权消费）、日志、设备和设置的稳定流程必须从功能屏完成，尚未接入的研发接口才允许留在调试兜底。当前主后端快照为 152 个操作；聊天流式/上传仍由专用页面处理。主线验收仍以统一入口、聊天可用、分布式布局可观测、边缘标准库协议层和兼容回退为准。

## 6. 风险与处置

| 风险 | 处置 |
| --- | --- |
| 进程内 uvicorn 与 TUI 争用 stdin/stdout | 后端日志写 `logs/` 文件；TUI 独占 tty |
| Windows 线程内 uvicorn 信号处理 | 复用 `register_uvicorn_server()`；退出统一走 `/api/system/shutdown` |
| 聊天页零依赖重写导致体验回退 | 保留 `tui_sse` 流式解析 + 分段刷新；旧 Textual 页只作为 fixture/兼容路径 |
| 大改风险 | P0–P4 分阶段，每阶段独立可跑、可回退；不动 `/api/*` 契约 |

## 7. 明确不做

1. ~~不把 Textual 变成**必需**依赖（保持零依赖发行边界）~~ → **已取代**：Textual 是**交互外壳**的硬依赖；L 档/单命令/CI 路径仍不依赖任何 UI（薄层为纯标准库）；
2. 不改 `/api/*` 契约（只增加消费方）；
3. 不在本方案内改 Relay / RPC 语义；
4. 不恢复已裁撤的生图/邮件/旧前端。
