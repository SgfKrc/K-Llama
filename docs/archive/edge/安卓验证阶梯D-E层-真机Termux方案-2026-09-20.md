手里这台安卓真机（Termux + SSH）让原「AVD 方案」变得**没必要**：

| 路径 | 本质 | 证据强度 | 评价 |
|---|---|---|---|
| **P1（本方案）真机 + NDK 交叉编译 + SSH** | **真 ARM64 硬件 + 原生 NEON/dotprod/i8mm kernel** | **最强**，同时覆盖 D 与 E | ✅ **推荐** |
| P2 备选：AVD `x86_64` + ARM 翻译 | x86_64 主机上的**翻译层** | 中（掩盖 ARM64 原生 kernel 差异） | 仅当设备长期不可用 |
| ~~P3：AVD `arm64-v8a` 镜像~~ | — | — | ❌ emulator **硬编码拒绝**（见 `docs/archive/edge/安卓验证阶梯D层-AVD执行方案-2026-09-20.md` §2） |

**P1 为什么强**：它跑的是**真 ARM64 指令**，而 llama.cpp 的量化路径**重度依赖** dotprod / i8mm / fp16

「**ARM64 原生 kernel 下层段数值正确**」的路径。

| 层 | 内容 | 通道 | 现状 |

**P1-B 通过 = 「层段算法在真 ARM64 上数值正确」** —— 这是继 C+（x86_64）之后**最强**的证据，
且两者用**同一份源码 b9902**，可直接对照。

> ⚠️ **D0 ≠ P1**：`android_validation.py` 只验「装得上/起得来/ABI 对」，**不验数值**。
> 若只拿到 D0，**不得**宣称「设备上层段数值已验证」。

### 2.1 ⚠️ 常见误解：P1 **不需要**打包 APK

P1 用的是 **NDK 交叉编译出的 aarch64 ELF 可执行文件**，直接在 Termux 里跑 —— 它是 Linux
用户态程序，**不经过 Android 的 APK/JNI 打包链路**。这样做的理由：

- **快**：绕开签名、打包、安装、`adb` 授权等全部环节
- **直接**：验证的正是「llama.cpp 在真 ARM64 上的数值行为」本身，没有额外中间层
- **可对照**：与 C+（x86_64）用**同一份源码 b9902**、同一个探针，只换目标架构

**但 P1 不能替代 APK 验证** —— 它绕过了这些东西：

| 被绕过的东西 | 因此无法回答的问题 |
|---|---|
| `qlh_llama_jni.cpp` 的 JNI 封装 | `jfloatArray` 拷贝、异常处理、句柄生命周期是否正确 |
| Kotlin 层（`LocalInferenceEngine` / `AndroidFullWorkerStageExecutor`） | 执行器接线、能力探测、协议 v3 编解码是否可用 |
| APK 打包/签名、Android 权限与前台服务 | 能否装、能否起、能否常驻后台 |
| 设备 ABI 上报 | 拿不到 `native-worker-candidate` 档证据 |

⇒ **建议两步走**：
1. **P1（本方案 §3）**：先把「算法数值在真 ARM64 上正确」钉死
2. **P1-APK（§5.1）**：再装 APK，验证应用层集成

**APK 现状**：`android/app` 的 `assembleFullDebug` **已能构建**（30.9 MB，含
`lib/arm64-v8a/libqlh_llama_jni.so`），但**从未装到真机**。

## 3. P1 执行方案

### 3.1 第 0 步（不可跳）：上线后先探测设备

前提（设备侧）：Tailscale 已连 + Termux 里 `sshd` 已起（Termux sshd 默认端口 **8022**，
用户名 = Termux 内的 `whoami`，形如 `u0_a123`）。

```bash
# 本机
ssh -p 8022 <termux_user>@100.99.211.13

# 设备内（Termux）
uname -a
getprop ro.product.model            # ★ 判定 Y700 2022 / 2023
getprop ro.product.cpu.abilist      # ★ 期望含 arm64-v8a
getprop ro.build.version.sdk        # 期望 >= 26（项目 minSdk）
grep -m1 -E 'CPU part|Features|model name' /proc/cpuinfo
head -30 /proc/cpuinfo
nproc
free -m                             # 内存余量（决定能否跑 948 MB 模型）
df -h $HOME                         # 磁盘余量（模型 + 可执行文件）
python3 -c "import os; print(hex(os.sysconf('SC_PAGE_SIZE')))" 2>/dev/null || true
```

**判据与后续**：
| 观察 | 决定 |
|---|---|
| `ro.product.model` 含 2023 / SoC 为 SM8475 | 用 `armv8.6-a+dotprod+fp16+i8mm` |
| 实为 Y700 2022（Snapdragon 870） | **去掉 `+i8mm`**，用 `armv8.2-a+dotprod+fp16` |
| `nproc` / `free -m` / `df -h` 不足 | 换更小模型或只推 cut 模型（见 §3.4） |

### 3.2 本机 NDK 交叉编译 llama.cpp（→ aarch64）

> 产出**设备可直接执行的 aarch64 二进制**，避免在手机上编译（手机上编 800+ 文件会非常慢）。

```powershell
$sdk = "C:\Users\Koakuma\Android\Sdk"
$ndk = "$sdk\ndk\27.2.12479018"
$env:PATH = "C:\msys64\ucrt64\bin;C:\msys64\usr\bin;$ndk\toolchains\llvm\prebuilt\windows-x86_64\bin;$env:PATH"

cd G:\C\PYT\qlh\android\app\src\main\cpp\llama.cpp

cmake -B build-aarch64 -G "MinGW Makefiles" `
  -DCMAKE_TOOLCHAIN_FILE="$ndk/build/cmake/android.toolchain.cmake" `
  -DANDROID_ABI=arm64-v8a `
  -DANDROID_PLATFORM=android-26 `
  -DANDROID_STL=c++_static `
  -DCMAKE_BUILD_TYPE=Release `
  -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DLLAMA_BUILD_SERVER=OFF `
  -DGGML_OPENMP=OFF `
  -DGGML_CPU_ARM_ARCH="armv8.6-a+dotprod+fp16+i8mm"

cmake --build build-aarch64 -j 8 --target llama
```

**要点**：
- `-DANDROID_STL=c++_static` ⇒ **静态链接 libc++**，避免依赖设备上的 libc++（Termux 的 libc++ 与 NDK 不同源）。
- `-DGGML_CPU_ARM_ARCH=...` ⇒ 必须显式给，否则退到 `armv8-a` baseline，**慢数倍**且**不编译** dotprod/i8mm kernel。
- ⚠️ 若 NDK toolchain 也注入了 `-march`，需在编译日志里确认**最终生效的** `-march` 是本行指定的那个（冲突时以 cmake 传入顺序为准，必要时改用 `CMAKE_C_FLAGS`/`CMAKE_CXX_FLAGS` 显式覆盖）。

### 3.3 编译层段探针（aarch64）

port 自 C+ 的 `layer_forward_probe3.cpp`（该探针已把 android 版 llama.cpp 的层段语义跑通）。
用 **NDK 的 clang++ wrapper**，链接 §3.2 产出的静态库：

```powershell
$cxx = "$ndk\toolchains\llvm\prebuilt\windows-x86_64\bin\aarch64-linux-android26-clang++.cmd"
& $cxx -O2 -std=c++17 -static-libstdc++ `
  -I include -I ggml/include `
  G:\C\PYT\qlh\build\cplus-probe\layer_forward_probe3.cpp `
  -o G:\C\PYT\qlh\build\cplus-probe\probe_aarch64 `
  build-aarch64\src\libllama.a build-aarch64\ggml\src\ggml.a `
  build-aarch64\ggml\src\ggml-cpu.a build-aarch64\ggml\src\ggml-base.a `
  -lm
```

> ⚠️ 探针里两处**架构相关**参数（C+ 时踩过）：
> - `N_POS_PER_EMBD`：qwen2.5 是**标准 RoPE ⇒ 1**（qwen35 的 M-RoPE 才是 4）——**别照抄 4**
> - `n_pos_per_embd > 1` 时才需要重建 pos 数组；`= 1` 时保持 `llama_batch_init` 原样

### 3.4 推送到设备并执行

```powershell
$dev = "100.99.211.13"
scp -P 8022 G:\C\PYT\qlh\build\cplus-probe\probe_aarch64 "$dev`:~/"
scp -P 8022 G:\C\PYT\qlh\build\cplus-probe\prompt.txt    "$dev`:~/"

# 模型（⚠️ 948 MB + 607 MB，Tailscale 传输可能较慢）
scp -P 8022 "G:\C\PYT\qlh\build\cross-framework-layer-poc\out\qwen25-05b-f16.gguf"        "$dev`:~/"
scp -P 8022 "G:\C\PYT\qlh\build\cross-framework-layer-poc\out\qwen25-05b-f16-cut-k12.gguf" "$dev`:~/"
```

设备内执行（Termux）：

```bash
cd ~ && chmod +x probe_aarch64
./probe_aarch64 qwen25-05b-f16.gguf qwen25-05b-f16-cut-k12.gguf prompt.txt 12 --gen 5 --threads 4
echo "exit=$?"
```

**先省一步的做法**：设备上若**已存在**同名/可用 GGUF（有 reasonix cli 的设备常带模型），
可先 `find ~ -name '*.gguf'` 查，避免重复传 1.5 GB。

### 3.5 验收判据

**主判据（与 C+ 同口径，便于对照）**：

```
step 0: relay=576    baseline=576    MATCH
step 1: relay=9396   baseline=9396   MATCH
step 2: relay=11     baseline=11     MATCH
step 3: relay=14019  baseline=14019  MATCH
step 4: relay=9396   baseline=9396   MATCH
PASS: 5 步逐 token 一致
exit = 0
```

**P1-B 达成条件**：至少两个 prompt、共 ≥10 步，**逐 token 全部 MATCH**，退出码 0。

**辅助判据（必须看，否则可能"过了但没跑快速 kernel"）**：
- 探针/llama.cpp 的加载日志里应出现 **`DOTPROD`** 与 **`MATMUL_INT8`**（或等价的 feature 列表）。
  若只报 `NEON`/`ARM_FMA` ⇒ **退到了 baseline**，此时"一致"的结论**不能**外推到"ARM64 优化路径正确"。

## 5. 可选：D0 控制面证据（需 adb 通道）

`scripts/android_validation.py` 的 `--install/--launch` 走 **adb**，而 adb 需要设备开
`adb tcpip`。两条路：

1. **adb over TCP/IP**：设备内 `adb tcpip 5555`（Termux 里若无 adb 可 `pkg install android-tools`），
   然后本机 `adb connect 100.99.211.13:5555`，再跑：
   ```powershell
   .\.venv-test\Scripts\python.exe scripts\android_validation.py --assemble --install --launch --json
   ```
   目标：`status == "native-worker-candidate"`（= `apk_install && apk_launch && arm64_abi`）。
2. **跳过 D0**：P1-B 是更强证据，D0 只是"官方脚本口径"的补充。**不强求**。

### 5.1 P1-APK：装 APK 验证应用层（§2.1 说的第二步）

**前提**：APK 已构建 —— `android/app` 的 `assembleFullDebug`（30.9 MB，含 `lib/arm64-v8a/libqlh_llama_jni.so`）。

**两条装法**：

1. **无线调试**（Android 11+；设备是 Android 15 ✓）
   - 设备：设置 → 开发者选项 → **无线调试** → 打开 →「使用配对码配对设备」→ 记下 `IP:端口` 与 6 位配对码
   - 本机（adb 37.0.0 支持 `pair`）：
     ```
     adb pair <ip:配对端口>      # 输入配对码
     adb connect <ip>:5555
     adb install -r <fullDebug.apk>
     ```
2. **手动**：把 APK `scp` 到 `/sdcard/Download/`，在设备上点安装（需允许「安装未知来源应用」）

**装完跑官方脚本**：
```powershell
.\.venv-test\Scripts\python.exe scripts\android_validation.py --install --launch --json
```
目标 `status == "native-worker-candidate"`。

> ⚠️ **与 P1 的分工**：这一步验的是**应用链路**（JNI 封装 / Kotlin 执行器 / v3 协议 / 安装启动），
> **不验数值**；P1 验数值、**不验应用链路**。两者**互补，不可互替**。

## 6. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 设备长期不在线 | 全方案阻塞 | 备选走 P2；或换 Tailscale 里其它在线节点（`iz0jl6qanyr13j72pj73mwz` 是 **linux**，**不是** Android） |

| 设备内存/磁盘不足 | 跑不动 948 MB 模型 | 只推 cut 模型 / 用更小模型 / 换量化版（`qwen25-05b-q4km`） |

| NDK `-march` 冲突 | 实际未启用 dotprod/i8mm | 编译日志确认最终 `-march`；必要时用 `CMAKE_C_FLAGS` 覆盖 |
| Termux 执行位/W^X 限制 | 二进制跑不起来 | 放 `$PREFIX/bin/` 或 `chmod +x`；避免放 `/sdcard`（noexec） |
| 只看到 `NEON` 无 `DOTPROD/i8mm` | "一致"结论被高估 | §3.5 辅助判据强制检查 |

### 9.4 ⚠️ 链路韧性：设备会被压制 / Tailscale 会掉

实测两次中断：
1. 传 `qwen25-05b-f16.gguf` 到 **18.6 MB** 时设备转 `offline`，Tailscale 路径由 `direct` 退到 **`relay "hkg"`**
2. 用户确认「**刚才 tailscale 死了**」⇒ 属**链路侧故障**，非设备崩溃（设备 `up 84 days` 未重启，sshd 一直在跑）

⇒ **对策**：传输脚本必须**可重试 / 可续跑**；长任务前先确认设备已解锁、WiFi 与 Tailscale 正常。

### 9.5 传输带宽（实测 —— 推翻早先的「153 MB/s」）

| 场景 | 吞吐 |
|---|---|
| ~~早先测到的 153 MB/s~~ | **假数据**：传到 `/tmp/qlh_t1.bin`，而 Termux 里 `/tmp` 不存在 ⇒ scp **秒失败**，0.42 s 是**失败返回时间**（千兆网物理上也到不了 153 MB/s）|
| **真实单连接 scp**（→ `~/` 或 → `/sdcard`）| **~1.3–1.4 MB/s** |
| 直连 `192.168.0.101:8022`（绕开 Tailscale）| **~1.56 MB/s**（仅 +21% ⇒ **Tailscale 不是主因**）|
| **并行 4 连接** | **~2.75 MB/s**（1.94×）|
| 设备内 `cp ~/ → /sdcard`（FUSE 写）| **~154 MB/s** |
| 设备内 `cat ~/ → /sdcard` | **~164 MB/s** |

**结论**：瓶颈是 **WiFi 链路**（本机 `WLAN 192.168.0.102` ↔ 设备 `192.168.0.101`，RTT 9–76 ms 波动大），
呈「延迟 × 窗口」受限 ⇒ **分片并行**是正确对策。
**策略**：32 MB 分片传进 Termux **内部存储**，再在设备上 `cat` 合并到 `/sdcard/...`（内部→FUSE 很快）。
脚本：**`build/y700-push-models-parallel.ps1`**（并发 6，支持续跑 + 大小校验 + SHA-256）。
预估 948 MB + 607 MB 在 6 并发下约 **9–12 分钟**。

### 9.7 工具链踩坑（本会话实测，复用价值高）

| 坑 | 现象 | 正解 |
|---|---|---|
| **PowerShell 5.1 按 ANSI 读 .ps1** | 无 BOM 的 UTF-8 脚本里中文变乱码，**破坏引号配对导致语法错误** | 脚本**一律纯 ASCII** |
| **PowerShell 双引号内 `$` 被本机展开** | `ssh y700 "ls $PREFIX/..."` 里的 `$PREFIX` 被本机替换成空 ⇒ 远端路径变成 `/var/service` | 用**单引号**或**脚本文件** |
| **`ssh y700 "…"` 里的远端 `$()`** | `\$(date +%s%N)` 被本机执行（报 `Get-Date` 错） | 改走 **base64**：`echo '<b64>' \| base64 -d > ~/x.sh && sh ~/x.sh` |
| **CRLF 传给远端 bash** | `bash: line N: $'\r': command not found` | `Get-Content -Raw \| ssh y700 "tr -d '\r' \| bash -s"`，或 base64 通道 |
| **采信未校验的测速** | 把 scp 的**失败秒返回**当成 153 MB/s | **每次传输后校验远端字节数**，别只看耗时 |

### 9.8 ★ D/E 层实测结果：**PASS**（真 ARM64，2026-09-20）

**做法**：本机 NDK 交叉编译**同一份 b9902 源码**为 aarch64（`build-aarch64`，4 个 `.so` 共 ~49 MB），
连同探针（57 KB）经 `scp` 推到设备 `~/qlhprobe/`，用 **`$ORIGIN` rpath** 解析动态库，
在 Termux 里直接运行。

**结果**：

```
=== QLH 层段数值验证 v3（android 版 llama.cpp b9902, aarch64 (ARM64)）===
--- step 0 (n_tokens=8) ---    relay(cut+embd)=576    baseline(full)=576    MATCH
--- step 1 (n_tokens=9) ---    relay(cut+embd)=9396   baseline(full)=9396   MATCH
--- step 2 (n_tokens=10) ---   relay(cut+embd)=11     baseline(full)=11     MATCH
--- step 3 (n_tokens=11) ---   relay(cut+embd)=14019  baseline(full)=14019  MATCH
--- step 4 (n_tokens=12) ---   relay(cut+embd)=9396   baseline(full)=9396   MATCH
=== 结果 ===
PASS: 5 步逐 token 一致 —— android 版 llama.cpp 的层段算法
      （embd 注入 + pos 补救 + 续算 + argmax）在 aarch64 (ARM64) 上数值正确。
EXIT=0
```

**证据存档**：`build/cplus-probe/result_arm64_device.txt`（设备侧原始输出，980 行 / 55 KB）

**★ 与 C+（x86_64）交叉对照**：token 序列**完全相同**（`576 / 9396 / 11 / 14019 / 9396`）
⇒ 层段算法**跨架构一致**。

**★ 辅助判据（§3.5 要求，必须看）**：反汇编 `libggml-cpu.so`：

```
sdot    (dotprod, vdotq_s32)      1063 次
smmla   (i8mm, int8 matmul)        244 次
fmla*8h (fp16 arithmetic)          440 次
```

⇒ 确认跑的是 **dotprod + i8mm 快速 kernel**（**非 baseline**）⇒ 「一致」的结论**可以**外推为
「**ARM64 原生优化路径下层段数值正确**」。

**⇒ §3.5 的验收判据满足 ⇒ D/E 层达成。**

> ⚠️ **本证据的边界**：它来自 **Termux 里的原生可执行文件**，**绕过**了
> JNI 封装 / Kotlin 执行器 / 协议 v3 / APK 打包与安装（见 §2.1）。
> **APK 应用链路仍未验证** —— 需按 §5.1 补。
