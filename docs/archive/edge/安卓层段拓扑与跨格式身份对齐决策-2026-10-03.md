## 1. 现状约束

- 当前 qwen3_5 descriptor 为 24 层。
- Y700 通过 v3 `hello` 上报 `stage_types=[layer_forward]`、`layer_ranges=[[4,16)]`、`resource_gate.admitted=true`。广告区间由设备上的层段工件清单决定，不是硬编码：`android/app/src/main/java/com/qlh/inference/service/LayerArtifactCatalog.kt` 读工件元数据的 `layer_range` / `source_layer_range`，`android/app/src/main/java/com/qlh/inference/worker/AndroidWorkerCapabilities.kt` 把它写进 `capabilities["layer_ranges"]`。更换或增加 artifact 即改变广告区间。
- master 把 `layer_ranges` 当执行合同：`src/pipeline_capacity.py` 的 `_normalize_layer_ranges` 归一化区间，assignment 必须完全落在节点广告区间内；无法连续覆盖请求区间时返回 `pipeline_layer_range_coverage_insufficient`，不再生成 `[1,24)` 这类越界计划。当前 master 加该 Android 节点覆盖不了 `[0,24)`，真实请求被拒绝是正确行为。
- 层段帧与尾段 token 的桥接已实现：`src/scheduler_pipeline.py` 的 `_execute_layer_stage_offer`、`_layer_stage_result_to_pipeline_value`、`_stage_offer_assignment_ready`，准入记录 `execution="stage_offer_v3"`，开关 `layer_stage_dispatch_enabled` 与全模型派发分离。
- 尾段语义在 relay 侧已有先例：relay worker 零层、由远端代跑，master 前后都跑（`src/scheduler.py` 的 `_split_relay_nodes` 与 `_append_relay_assignments`）。

## 2. 拓扑：设备自荐 + 自动分配（2026-10-03 修订）

主路线不再由人工预先切好固定区间的工件塞进设备。设备按自身可用内存申报"本地裁层后可承载的层数上限"，master 汇总各节点申报量后分配连续区间，设备按分配在本地裁出该区间并装载。

三个字段语义不同，不可互相替代：

| 字段 | 含义 | 产出方 |
| --- | --- | --- |
| `capabilities.layer_ranges` | 该节点**当前已就绪、马上能跑**的区间（硬约束） | 设备（按已加载工件） |
| `capabilities.layer_budget` | 该节点**本地裁层后能承载的层数上限**（`available_bytes` / `per_layer_bytes` / `max_layers` / `local_cut`） | 设备（按内存与整模推算） |
| `layout.assignments` | master 的分配结果：每节点的连续区间 | master（容量规划器） |

两端已落地：

- master：`src/pipeline_capacity.py` 的 `_normalize_layer_budget` 校验申报并把 `max_layers` 作为该节点的分配上界；`src/task_worker_protocol.py` 的 `_validate_layer_budget` 把 `layer_budget` 纳入 v3 hello 的能力校验（可选键，向后兼容）。
- 设备：`AndroidWorkerCapabilities.computeLayerBudget()` 按可用内存与已选工件推算 `per_layer_bytes` / `max_layers`（缺依据时返回 `null`、不上报），`TaskWorkerService` 的 `buildCapabilities` 在 hello 里带上；`TaskWorkerProtocol` 同步接受该可选键。`local_cut` 目前恒为 `false` —— 本地裁层执行体未落地前不虚报能力。

契约测试：`tests/test_pipeline_capacity.py`、`tests/test_task_worker_protocol.py`、`android/app/src/test/java/com/qlh/inference/worker/AndroidWorkerCapabilitiesTest.kt`。

设备侧已落地（2026-10-03 真机验证）：

- 本地裁层执行体：`scripts/model_tools/qlh_device_cut_range.sh`（Termux 运行，复用 `scripts/cut_layers.py`）。既支持直传区间，也支持 `--from-master <url> --node-id <id>` 直接读主节点给本节点的分配。
- 真机证据（Y700）：`python3 -m pip install gguf` 之后，裁出 24 层模型的 8 层工件耗时 **7.45 s**（`block_count: 24 -> 8`），产物与 manifest 落在模型目录。
- 闭环证据：把裁出的工件放进 `/sdcard/Download/QLH/models` 后重启 App，它自行扫描并把区间上报 —— hello 从 `ranges=[[4,16]]` 变为 `ranges=[[8,16],[16,24]]`，主节点 `task_worker_hello_acked accepted=True`。设备侧产出工件后能力上报自动跟上，不需要 App 侧新增触发逻辑。
- `layer_ranges` 表达"目录里有哪些工件（因而能按需加载哪几段）"，不表示能同时执行多段（一次只加载一份工件）。

真机进展（2026-10-03）：`routing_preference=distributed_required` 的请求已在 Y700 上跑通 —— master 前缀 `[0,16)` + Android 尾段 `[16,24)`，返回 HTTP 200、`distributed_used=true`、`fallback=false`，产出正确 token（`execution_mode=route_a_stage_offer_v3`）。四处准入修复详见 [已知问题记录](../../已知问题记录.md) #30。

多步 decode 也已跑通（2026-10-03）：同一 prompt 下 13 步（1 prefill + 12 decode，每步 320–400 ms），三次重复的 token 序列完全一致（`16,11,220,17,11,220,18,11,220,19,11,220,20`）⇒ 分布式路径自身是确定的。

per-token 对拍（2026-10-03）：`max_new_tokens=1` 时两端**首 token 一致**（都是 `1`，dist 侧 `token=16`）⇒ 提示构造与 chat 模板一致。放开步数后若拿**不同档**的整模作对照，字面本就不同（D 档 torch 出 `1,2,3,4,5`，L 档 llama.cpp 出 `1, 2, 3, 4`）——分词后是同一串数字，差别只在空格 token（`220`）插入的位置 ⇒ 属**跨档基线差异**，与接力实现无关（判据见下文 Route A 验收段）。

`capacity` 策略端到端也已验证（2026-10-03）：`distributed_required` 请求会写入 capacity plan —— 请求后 `/api/cluster/layers` 返回 `strategy=capacity`、`plan_id=680d2306…`，分配 master `[0,16)` + android `[16,24)`，答案正确。

L→L 分段对拍（2026-10-03，`scripts/relay_l2l_net_probe.py`；本机 head `[0,16)` + Y700 tail `[16,24)`，纯 llama.cpp）：**32/32 逐 token 完全一致**（判据 `per_token_argmax`，`first_mismatch_index=null`），层覆盖 `verified`。证据 `local_docs/evidence/l2l-segment-parity-2026-10-03.json`。

本机 D→L 对拍（2026-10-03，`relay_experiment --path d2l_mainrepo`；torch 上游 + llama.cpp 下游）：**逐 token 一致** —— `per_token_argmax`、`tokens_match=True`、`first_mismatch=None`。

跨机 D→L→L 对拍（同日，`--path d2l2l_keep_head_net`；master torch `[0,8)` + **Y700 middle `[8,16)`（shim）+ 本地 tail `[16,24)`**）：**同样逐 token 一致** ⇒ master 的 torch 上游、跨机 hidden 传输、**设备侧的层段处理本身**都是对的。

⇒ 本机 D→L 与跨机 D→L→L 都以 `relay_experiment` 的 `--whole-model`（**同精度整模 GGUF**）为对照 ⇒ 跨框架 D→L 在**同档基线**下逐 token 一致。

Route A 验收（2026-10-03）：**对照必须取同档整模**。同一 prompt、`temperature=0`、逐档加长实测 —— Route A 与 **L 档整模 GGUF**（`engine=llama_cpp`）逐字相同（n=3 `1,`、n=4 `1, 2`、n=6 `1, 2,`、n=10 `1, 2, 3, 4`、n=16 `1, 2, 3, 4, 5`）；而 **D 档整模**（`engine=pytorch`）在 n=10 出 `1,2,3,4,5`。两者是同一串数字、仅空格 token 位置不同，属跨档基线差异。

此前用 D 档整模作对照，看到的是"第 3 个 token 起分歧"，一度被当作 Route A 的实现缺陷逐项排查。设备侧插桩实测把链路排除干净：设备收到的 hidden 与主节点发出的**整段字节校验和逐条相同**（587 KB/步，FNV-1a）、`positions` 连续递增（prefill `0..40`、decode `41..45`）、decode 步 `clear_kv=0` 且 KV 深度从 40 递增到 44、通道（`layer_inp` 的 `lid == n_layer` 槽位）与加载参数（`n_ctx`／`n_batch`／`n_ubatch`／`type_k`／`type_v`／`flash_attn`／`embeddings`／`n_seq_max`）与 shim 一致、两侧 `cut-16` 工件 sha256 相同 ⇒ **跨机 D→L 接力没有缺陷**。

三段链已验收（2026-10-03）：**master torch `[0,16)` + Surface `[16,20)`（keep-head shim）+ Y700 `[20,24)`（JNI）**，三段同 prompt 跑通，且与 **L 档整模**逐字一致（n=3 `1,`／n=4 `1, 2`／n=6 `1, 2,`／n=10 `1, 2, 3, 4`／n=16 `1, 2, 3, 4, 5`）。每步两个 stage worker 依次 handoff，Surface 产生的 `hidden_sha256` 与早先单段 Route A 时 master 侧记录的完全相同 ⇒ 三段接力未引入数值偏差。

让第二台 worker 真正上链，需要补齐五处（本会话逐一定位并修复）：

1. **能力声明**：`_task_worker_capabilities` 的 `stage_types` 原先把 `layer_forward` 写死在外，PC worker 永远轮不到层段；层段声明还依赖 `_active_layer_config`（要等 master 下发）⇒ 首次 hello 为空、形成死锁。改为从**工件 manifest** 的 `source_layer_range` 推导。
2. **准入判据**：`_task_worker_layer_stage_ids` 写死 `node_type == "android"`；`_handle_task_worker_stage_offer` 又用 `coordinator["layer_stage_dispatch_enabled"]`（那是"**别的** worker 有没有层段就绪"）判**自己** ⇒ 合法 offer 被拒成 `worker_not_admitted`。改为就地按本机 capabilities 判。
3. **分配器**：默认准则是最优解之间取"节点数最少"（省网络跳数，对普通请求合理）⇒ 三段永远选不上。新增 `prefer_all_workers`（`QLH_PIPELINE_PREFER_ALL_WORKERS`），并把"声明了 `layer_ranges` 的节点是否跑满该区间"提到优化首位（否则节点数最多的解会把它切碎，offer 必被 `layer_range_not_advertised` 拒）。
4. **legacy 通道分流**：master 在**节点注册那一刻**就推送 legacy `LAYER_CONFIG`（早于 hello 往返），v3 层段 worker 收到后会按 legacy 语义去同步模型，跨机被 `MODEL_API_SOURCE_UNTRUSTED` 拒 ⇒ 释放自己、掉出层段名单。worker 侧改为明确拒绝该配置，master 侧把它当**分流信号**（从待 ACK 集合摘除）、并在就绪判据里跳过这类节点。
5. **两个只在真机上才暴露的坑**：① 工件推导出的 `model_id` 取自 manifest 的 `artifact` 字段（相对路径，**含反斜杠**），而协议要求 `^[A-Za-z0-9_.:-]{1,128}$` ⇒ 整个 hello 被判非法（这条错误长期被第 4 项的 legacy 噪声盖住）；② keep-head 子进程的 **KV 跨请求残留**，新 prompt 的 prefill 从位置 0 开始即 `decode: failed to initialize batch` ⇒ 判据与 JNI 侧 `qlh_layer_batch_starts_at_zero` 同语义，批次从位置 0 开始就 `reset()`（这一条只在**连续第二个请求**时暴露）。

另有两处既存不一致顺带修掉：从节点心跳容忍上限写死 10s 而 App 侧间隔是 45s（`AndroidPresenceStateMachine.heartbeatIntervalMs = 45_000`，且有两处同型判据）；`api_server._execute_task_worker_stage` 是 `EngineHost.execute_task_worker_stage` 的同源副本，层段分支只加在后者不会生效（PC 侧走的是前者）。

Route A 本身仍是 D→L（master 段固定 pytorch，`prepare_pipeline_model` 硬编码 `_engine_type="pytorch"`）⇒ 同引擎的 L→L 判据不适用于它，需要 L→L 时走 relay 链。

`scripts/cut_layers.py` 手工产出分段工件并投递的过渡路径仍然可用（本会话的三段链就是用它产出 `[16,20)` 与 `[20,24)`），但不再是打通三段链的前置。

## 3. `model_identity`：源指纹 + 转换可复现

跨格式逐权重数值相等不作为准入条件。身份对齐以源指纹与转换可复现为准，两端各自计算下列字段，握手时逐字段相等即认定为同一模型：

| 字段 | 内容 |
|------|------|
| `source_safetensors_sha256` | master 侧源模型各分片 SHA-256 |
| `conversion_command` | 产出 GGUF 的完整命令，含 llama.cpp 转换脚本的 commit |
| `quantization` | 量化类型与参数（如 Q4_K_M、group size） |
| `gguf_sha256` | stage artifact 文件 SHA-256 |
| `tokenizer_sha256` | tokenizer 资产指纹，两端必须同一份 |
| `arch` | `n_layer` / `n_embd` / `n_head` / `n_kv_head` / `rope_theta` / `vocab_size` |
| `layer_range` | 该 artifact 认领的 `[start, end)` |

身份判据与正确性判据分离：身份对齐回答"两端是不是同一个模型"，数值正确性由行为对拍承担 —— stage 返回的 `hidden_out_sha256` 校验与最终 per-token argmax 对拍。GGUF 量化权重与 safetensors fp16 权重的逐层数值不相等属预期，既不作为拒绝理由，也不作为模型不一致的证据。

未实现部分：

- 上述字段尚未进入 v3 握手与 `pipeline_capacity` 的准入契约；当前参与准入的是 `layer_ranges` 与 `resource_gate`。
- `conversion_command` 要成为可复现证据，必须固定 llama.cpp 转换脚本的 commit；两端该 commit 不同即视为不可复现。

真机证据（2026-10-03）：master 用 `qwen2.5-0.5b-instruct` 准备流水线（`POST /api/models/prepare-pipeline`，`safetensors_headers_only`，不加载权重），设备上报同模型的 GGUF 尾段 `[16,24)`；发起 `routing_preference=distributed_required` 的真实请求后得到明确的 fail-closed 拒绝：

```
503 distributed_required 执行失败：route_a_model_identity_unavailable
```

该拒绝来自 `scheduler_pipeline._run_route_a_stage_pipeline`：`callbacks.active_task_graph_model_identity()` 返回 `None`，而它要求 `model_host.model_loaded` 与 `model_manager.is_loaded` 都为真 —— `prepare-pipeline` 刻意不物化权重，所以 master 侧根本没有活动模型身份。⇒ **Route A 准入的前提是 master 先真正加载模型**，与跨格式身份无关。

两端身份比对（本节规则的对象）发生在 master 有活动模型身份**之后**：master 侧 `pytorch` 引擎算的是 safetensors 的摘要，设备侧上报的是 GGUF 源模型摘要，两者必然不同，那时才需要本节规则把它们对齐。

## 4. 落地顺序

均已完成（2026-10-03）：

1. ✅ 产出分段 GGUF artifact（`[16,20)` 与 `[20,24)`，各带 manifest 的 `source_layer_range` / `artifact_sha256`），同步登记第 3 节的 identity 字段。
2. ✅ Android 侧把 artifact 纳入 catalog 与能力上报（`layer_ranges=[[16,24],[20,24],[8,16]]`）；PC 侧（Surface）由 env `QLH_LAYER_GGUF` 指定工件，声明从 manifest 推导（`layer_ranges=[[16,20]]`）。
3. ✅ master 编排三段链跑通 prefill 与 5 步 decode，与整模逐字一致（判据 per-token argmax；证据见第 2 节）。
4. ✅ identity 字段接进 v3 握手校验，不一致时 fail-closed（`task_worker_adapter._layer_model_matches` 比对 engine/format/sha256）。
