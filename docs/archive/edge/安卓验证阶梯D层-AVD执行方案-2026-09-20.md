## 2. 关键约束：为什么不能用 `arm64-v8a` 镜像

AOSP emulator 源码 `android/emulator/main-emulator.cpp` 里有一段**针对 x86_64 host 的硬编码拒绝**：

```cpp
#ifdef __x86_64__
  if (sarch == "arm64" && apiLevel >= 28) {
      APANIC("Avd's CPU Architecture '%s' is not supported by the QEMU2 emulator on x86_64 host.\n", avdarch);
  }
#endif
```

- 提交说明：*"Except for very old apis (apilevel < 28), emulator does not support running arm on x86_64 hosts"*。
- **后果**：本机（x86_64）创建 `arm64-v8a` AVD 后启动会**立刻 PANIC**。
  API ≤ 27 的 arm64 镜像能起，但**全软件模拟、极慢**，且 API 27 < 项目 `targetSdk=34`，不具备验证意义。
- 参考：[SO #74760054](https://stackoverflow.com/questions/74760054/panic-avds-cpu-architecture-arm64-is-not-supported-by-the-qemu2-emulator-on)、[AOSP 源码](https://android.googlesource.com/platform/external/qemu/+/1381d44efe69ba0b37fb7f7ef868125e279fc14a/android/emulator/main-emulator.cpp#910)

### 2.1 救赎：API 30+ `x86_64` 镜像自带 ARM 翻译

自 Android 11（API 30）起，**`x86_64` 的 Google APIs / Play Store 镜像内置 ARM 指令翻译**（`libndk_translation`），
按进程把 ARM 指令翻译到 x86_64 ⇒ **arm64-v8a APK 通常能安装并以接近原生速度运行**。

- 参考：[Google 官方博客 "Run ARM apps on the Android Emulator"](https://android-developers.googleblog.com/2020/03/run-arm-apps-on-android-emulator.html)、[Emulator 30.0.0 release notes](https://developer.android.com/studio/releases/emulator)
- ⚠️ 限制：翻译**只在 Google APIs / Play Store 镜像**里；许可仅限开发/调试；个别 ARMv7 二进制仍会失败。

**⇒ 因此方案 A 的路线是：`x86_64` 镜像 + 让翻译层承载 arm64-v8a 的 `.so`。**

⚠️ **但**：`android_validation.py` 的 `arm64_abi` 判据读的是**设备属性** `ro.product.cpu.abilist` / `ro.product.cpu.abi`。
翻译启用时该属性**通常**含 `arm64-v8a`，**但这是必须实测确认的第一步**（见 §6 步骤 3）。若不含 ⇒ 只能拿到 `device-control-pass-native-worker-pending`。

## 3. 方案 A：x86_64 镜像 + ARM 翻译（推荐）

### 3.1 前置：升级 cmdline-tools（强烈建议）

现有 cmdline-tools 12.0 报 `SDK XML version 4` 警告，可能不认识较新的包名。

```powershell
$sdk = "C:\Users\Koakuma\Android\Sdk"
# 下载最新 commandlinetools（或用 Android Studio 的 SDK Manager 更新）
# 解压到 $sdk\cmdline-tools\latest（覆盖），或新目录后改 PATH
& "$sdk\cmdline-tools\latest\bin\sdkmanager.bat" --version
```

### 3.2 安装镜像与模拟器

```powershell
$sdk = "C:\Users\Koakuma\Android\Sdk"
$env:ANDROID_HOME = $sdk
$env:ANDROID_SDK_ROOT = $sdk
$sdkm = "$sdk\cmdline-tools\latest\bin\sdkmanager.bat"

# ① 先看可用包名（不同 cmdline-tools 版本命名略有差异）
& $sdkm --list 2>&1 | Select-String "system-images;android-3[56].*x86_64"

# ② 安装：emulator + Google APIs 的 x86_64 镜像（必须 google_apis，才有翻译）
& $sdkm --install "emulator" "platform-tools" "system-images;android-35;google_apis;x86_64"

# ③ 接受许可（如提示）
& $sdkm --licenses
```

> **API 选择**：项目 `targetSdk=34` ⇒ 镜像 API 需 ≥ 34。优先 **35**（36 可能因 cmdline-tools 偏旧而包名未收录）。
> **必须 `google_apis`**（不是 `default`、不是 `google_apis_playstore`）：`default` 无翻译，`playstore` 有签名/账号约束。

### 3.3 创建并启动 AVD

```powershell
$sdk = "C:\Users\Koakuma\Android\Sdk"
$avdm = "$sdk\cmdline-tools\latest\bin\avdmanager.bat"

& $avdm create avd -n qlh_d35 -k "system-images;android-35;google_apis;x86_64" -d pixel_6 --force

# 启动（无窗口，便于脚本化；首次冷启动较慢）
& "$sdk\emulator\emulator.exe" -avd qlh_d35 -no-window -no-audio -no-boot-anim -gpu swiftshader_indirect

# 另开终端等待就绪
& "$sdk\platform-tools\adb.exe" wait-for-device
& "$sdk\platform-tools\adb.exe" shell "while [[ -z $(getprop sys.boot_completed) ]]; do sleep 2; done; echo booted"
```

### 3.4 ★ 关键闸门：确认 abilist 含 arm64-v8a

```powershell
$adb = "$sdk\platform-tools\adb.exe"
& $adb shell getprop ro.product.cpu.abilist      # ★ 期望包含 arm64-v8a
& $adb shell getprop ro.product.cpu.abi
& $adb shell getprop ro.product.cpu.abilist32
& $adb shell getprop ro.product.cpu.abilist64
& $adb shell getprop ro.kernel.qemu              # 期望 1（说明是模拟器）
```

- **含 `arm64-v8a`** ⇒ 继续 §3.5，有望拿到 `native-worker-candidate`
- **不含** ⇒ **停**。此时 D 层在本机只能拿到 `device-control-pass-native-worker-pending`；
  真 ARM64 证据必须走方案 C（云设备/真机）。**不要用改属性/伪造的方式绕过** —— 那就成了证据造假。

### 3.5 跑官方验证脚本

## 4. 验收判据（`scripts/android_validation.py` 原生口径）

脚本产出 5 个检查位与 2 个证据位（`src` 见 `android_validation.py:199-248`）：

| 检查位 | 含义 |
|---|---|
| `adb_available` | `adb` 可执行 |
| `online_device` | `adb devices -l` 有 `device` 状态条目 |
| `arm64_abi` | 设备 `abilist + abi` 拆分后含 `arm64-v8a` |
| `apk_install` | `adb install -r <fullDebug.apk>` 成功 |
| `apk_launch` | `adb shell monkey -p <pkg> 1` 成功 |

| 证据位 | 定义 |
|---|---|
| `apk_device_control_plane` | `apk_install && apk_launch` |
| `arm64_native_worker` | `apk_device_control_plane && arm64_abi` |

`status` 三档流转：
```
jvm/build-pass-device-pending
  → device-control-pass-native-worker-pending
  → native-worker-candidate        ← D 层的目标档
```

**D 层达成 = `status == "native-worker-candidate"`**（`evidence.arm64_native_worker == true`）。

## 5. ⚠️ 必须知道的关键缺口：控制面 ≠ 数值面

`android_validation.py` 的 D 层证据**只覆盖控制面**（装得上、起得来、ABI 对）。
它**不验证层段数值正确性**。所以要把"设备上层段算法正确"钉死，需要额外两层：

| 层 | 内容 | 是否已有 |
|---|---|---|
| **D0** | 控制面：install + launch + abilist | ✅ 脚本已支持 |
| **D1** | 设备上 JNI 层段链路 smoke：能加载模型 → `nativeLayerForwardInfo` 返回合理值 → 注入一段 hidden 不崩、argmax 落在 `[0, n_vocab)` | ❌ **需新做** |
| **D2** | 设备上层段**数值对照**（把 C+ 的 full vs cut-kK 对照搬到设备） | ❌ **需新做**，工作量最大 |

### D1/D2 的实现路径（择一）

1. **App 内自检入口**（推荐，最省事）：加一个 debug-only 入口，跑
   `nativeLayerForwardInfo` + 一小段 hidden 注入，把结果写 `logcat`；D2 再比对 argmax。
2. **Android instrumentation test**（`androidTest`）：需把 `qwen25-05b-f16.gguf`(948 MB) 与
   `qwen25-05b-f16-cut-k12.gguf`(607 MB) 推到设备（`adb push`）。⚠️ AVD 磁盘默认偏小，需扩 `-partition-size`。
3. **只做 D1 不做 D2**：诚实地把 D 层结论限定为「**接线通 + 控制面过**」，
   数值正确性仍以 C+ 为据（C+ 与 D 用的是**同一份 llama.cpp 源码**，这正是 C+ 的价值）。

> **方法学立场**：D 层若只到控制面，**不得**宣称"设备上层段数值已验证"。
> 现阶段可宣称的是：C+ 已证「**算法在 android 版 llama.cpp 上数值正确**」，
> D 层要证的是「**在 Android 运行时 + JNI 封装下仍成立**」——两者不可互相替代。

| 风险 | 影响 | 缓解 |
|---|---|---|
| **`abilist` 不含 `arm64-v8a`** | 拿不到 `native-worker-candidate` | 转方案 C（云 ARM64 / 真机）。**不要伪造属性** |

## 8. 与真机（E 层）的关系

**即使 D 层拿到 `native-worker-candidate`，也不能替代 E 层**：

- 方案 A 实际执行的是 **`x86_64` 主机 + ARM 翻译层**，**不是真 ARM64 CPU**。
  指令翻译会掩盖 NEON/dotprod/i8mm 等 **ARM64 原生 kernel 的差异** ——
  而 llama.cpp 的 ARM64 量化路径恰恰重度依赖这些指令。
- 因此：**D 层证明「Android 运行时 + JNI 接线 + 翻译层下能跑」**，
  **E 层（真 ARM64 手机）才证明「ARM64 原生 kernel 下数值正确」**。
