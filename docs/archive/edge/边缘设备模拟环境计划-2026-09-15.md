## 2. 手段对比

| 维度 | Docker Desktop + WSL2 | 虚拟机（VirtualBox/VMware/Hyper-V/QEMU） | 裸机 cgroup/任务限制 |
| --- | --- | --- | --- |
| 资源限制能力 | `--cpus/--memory/--pids-limit` + `.wslconfig` | vCPU / RAM / 磁盘**独立分配**（最"硬"） | `systemd-run` / `cgroup v2` |
| 是否独立内核 | 否（共享宿主内核） | **是**（真独立内存与网络栈） | 否 |
| 体积/冷启动保真 | **高**（依赖与文件系统与部署一致） | 中（磁盘 IO 与缓存不同） | 高 |
| CPU 性能保真 | **低**（宿主同核，频率/缓存不变） | 中（vCPU 仍是宿主核，但可限频/限核） | 低 |
| ARM/aarch64 模拟 | 否（仅 x86） | **可**（QEMU 系统模拟） | 否 |
| 网络拓扑模拟 | 弱（端口映射为主） | **强**（NAT/桥接/Host-only/内部网） | 无 |
| 多节点组网 | 需 docker network + 端口 | **自然**（虚拟机网段即拓扑） | 无 |
| GPU 透传 | WSL2 + nvidia-container-toolkit（可选） | PCI 直通（复杂）；QEMU 支持有限 | 宿主 GPU |
| 启动成本 | 低（秒级） | 高（镜像/系统安装，分钟级） | 极低 |

**结论**：**尺寸/依赖/冷启动类指标 → 容器**；**网络拓扑/多节点/ARM 类指标 → 虚拟机**。

## 3. 方案 A：Docker Desktop + WSL2（首选，阶段 1）

### 3.1 限制整个 WSL 分发（`.wslconfig`，位于 `%USERPROFILE%\.wslconfig`）

```ini
[wsl2]
memory=4GB          # 模拟小内存设备（宿主 16GB，留出余量）
processors=2        # 模拟 2 核设备
swap=2GB
```

改后需 `wsl --shutdown` 生效。**注意**：这会同时影响 Docker Desktop（其后端跑在 WSL2 上）。

### 3.2 逐容器限制（推荐，粒度更细、可写进脚本）

```bash
docker run --rm -it \
  --cpus=1 --memory=2g --memory-swap=2g \
  --pids-limit=256 --storage-opt size=8G \
  -v "$PWD:/work" -w /work \
  python:3.12-slim bash
```

### 3.3 边缘基线度量（容器内执行，作为验收证据）

```bash
python -m venv .venv-edge
.venv-edge/bin/python -m pip install -r requirements-edge.txt
.venv-edge/bin/python scripts/edge_preflight.py --python .venv-edge/bin/python --json
.venv-edge/bin/python qlh_edge.py --help
```

Windows 将上面的 `.venv-edge/bin/python` 替换为 `.venv-edge\\Scripts\\python.exe`。`edge_preflight.py` 会一次性检查 venv 体积、导入冷启动、必需模块、
禁用模块和 `/health`、`/status`、`/generate` 路由；主线 TUI 仍在主环境单独验收，不能由 Edge
最小环境中的 HTTP 进程替代。

### 3.4 局限（必须如实写进结论）

- **CPU 保真度低**：容器与宿主共享内核与 CPU，`--cpus=1` 只限**配额**，不改频率/缓存/内存带宽 → **不能**用它宣称"低端设备上的吞吐/延迟数字"；
- **无 GPU**：L 档本就无 torch、不依赖 CUDA，故**不影响**本计划的指标；若将来要验证多模态（vision）路径，需 WSL2 CUDA 透传（另行评估）；
- **文件系统差异**：容器内 ext4 vs Windows NTFS → 冷启动数字以容器内为准。

## 4. 方案 B：虚拟机（阶段 2，需网络拓扑时启用）

### 4.1 资源分配

- vCPU = 1–2、RAM = 2–4GB、磁盘 = 16–32GB（可快照回滚，便于"脏环境复现"）；
- 若要更接近 ARM 边缘（手机/树莓派类），用 **QEMU 系统模拟 aarch64**（速度慢，仅做兼容性验证，不做性能数字）。

### 4.2 网络模式与"网络问题"的处理

这是本方案唯一真正需要解决的问题——**QLH 的主从节点拓扑要在宿主与 VM 之间、或 VM 与 VM 之间组网**：

| 模式 | VM → 外网 | 宿主/局域网 → VM | 适用场景 |
| --- | --- | --- | --- |
| **NAT**（默认） | ✅ | ❌（需**端口转发** `hostfwd`/NAT 规则） | 只做单机受限资源验证 |
| **桥接（Bridged）** | ✅ | ✅（与宿主同网段，需 DHCP 或静态 IP） | 模拟"同局域网的两个节点" |
| **Host-only / 内部网** | ❌（可选第二张 NAT 卡） | ✅（私有网段，宿主↔VM、VM↔VM） | **主从节点私网模拟（推荐）** |

**推荐配法（主节点=宿主，从节点=VM）**：

1. 给 VM 两张网卡：**NAT**（供安装依赖/联网）+ **Host-only**（私有网段，如 `192.168.56.0/24`）；
2. Host-only 网卡配**静态 IP**（避免 DHCP 漂移破坏节点地址）；
3. QLH 侧用显式 endpoint 连接（`/api/cluster/connect`，host/port 明确）——**不要依赖自动发现**，模拟环境里 mDNS/广播常不通；
4. 需要从宿主访问 VM 内的服务端口（如 `--serve-port 8090`）：Host-only 直接可达；NAT 则加端口转发。

**已知坑**：

- **Hyper-V / WSL2 与 VirtualBox 互斥**：Hyper-V（含 WSL2 后端）启用后，VirtualBox 只能跑"Hyper-V 后端"（性能差），或必须**关闭 Hyper-V**（则 Docker Desktop/WSL2 不可用）→ **两方案需取舍，不能同时全速使用**；
- **防火墙**：Windows Defender 对 Host-only 网卡的入站规则需显式放行；
- **时钟/休眠**：VM 挂起恢复后时钟漂移会影响超时类断言（建议禁用宿主休眠或用 NTP 校时的镜像）。

### 9.4 落地中发现并修掉的两个真问题

**（1）`edge_preflight.py` 在 symlink-shim venv 上判定错误**

原实现先对解释器路径做 `Path(...).resolve()`。`uv venv`（以及 POSIX venv 的普遍做法）把 `bin/python`
做成指向基础解释器的符号链接，`resolve()` 会跟到基础解释器目录 —— 那里**没有 venv 的 site-packages**，
于是 probe 用「裸解释器」运行并报 `ModuleNotFoundError: psutil`，导致 `cold_start` / `required_routes` /
`probe` 三项误判为失败。对照实验（一锤定音）：

```
raw      ~/qlh-wsl/.venv-edge/bin/python             → rc=0  'psutil 7.2.2'
resolved .../uv/python/cpython-3.12.../bin/python3.12 → rc=1  ModuleNotFoundError
```

修法（两处最小改动，对 `Scripts/` 布局向后兼容，Windows 侧回归同样 8/8 PASS）：
- `_venv_root()` 优先用**同目录的 `pyvenv.cfg`** 判定 venv 根，不再依赖 `resolve()`；
- `run_preflight()` 不再 `resolve` 解释器路径，保留 venv 语义交给子进程。

**（2）构建工具不得进 Edge 运行时 venv**

初版把 `cmake`/`ninja` 装进了 `$EDGE_VENV` 以便编译 RPC worker。cmake 二进制约 90MB，直接把 volume
从 **246MB 顶到 322MB**，**击穿 ① 的 300MB 门禁**。改为独立 `~/qlh-wsl/.venv-build` 后回落至 246.2MB。

> 这条反过来印证：**preflight 的 300MB 门禁是有效的** —— 它能抓到「开发期便利」对运行时边界的侵蚀。

### 9.5.1 模型 + RPC worker **同进程**（`distributed_inference` 的实义）

指标⑤ 只验到「worker 能被起停」；`/capabilities` 的 `distributed_inference` 想表达的其实是
**同一进程内既持有模型、又管理 RPC worker，且模型把层交给 RPC0 计算**（即"借算力"）。2026-09-18 补测通过。

**关键前置（踩坑）**：WSL 里装的 `llama-cpp-python 0.3.35` 是**预编译 wheel**
（`py3-none-linux_x86_64`），**不含 `libggml-rpc.so`** —— 而注入的 RPC device 必须注册到 `Llama`
实际使用的那个 `libggml.so` 上。Windows 侧此前也遇到同构问题（必须重编带 `GGML_RPC=ON` 的绑定）。

**采用的最小改动路径**（比重下 75MB sdist 重编更省）：
1. 在已有 `llama-rpc-build` 上**增量编出 `libllama.so`**（`cmake --build . --target llama`）；
2. **备份** edge venv 的 `llama_cpp/lib/`（14 文件）→ 再替换/新增那一套 `.so`（含 `libggml-rpc.so`）。

**验证结果**（`build/wsl-edge/verify_sameproc_rpc.py`，走**主仓的 `EdgeRpcWorker`** 起 worker）：

| `worker_stop()` | `running:false` |
| 总判定 | **`ok: true`** |

证据文件：`local_docs/evidence/edge-sim/CORE-EDGE-SIM-01-wsl-sameproc-rpc-2026-09-18.json`

> **口径**：本项证明的是**能力可用**（层确实经 RPC0 算出了正确结果），**不是性能结论**。
> `gen_s=0.674` 是本机回环 RPC 的数字，跨节点会显著不同。

### 9.6 复现方式

```bash
# 1) 主机侧（Windows / Git Bash）：限制 WSL 资源，然后重启 WSL
bash scripts/edge_sim_setup.sh --host-config
wsl --shutdown

# 2) WSL 内：建受限 venv、编 RPC worker、跑全部 5 项验收（幂等）
wsl -d Ubuntu-22.04 -- bash <repo>/scripts/edge_sim_setup.sh
# 落盘证据：
wsl -d Ubuntu-22.04 -- bash <repo>/scripts/edge_sim_setup.sh --json local_docs/edge-preflight.json
```

**退出码**：`0` 全部通过 / `1` 有验收项失败 / `2` 前置条件不满足。
`--rebuild` 可强制重建 venv 与 rpc-server。

**跨环境调用注意**（踩坑记录，脚本已内置规避）：
- Git Bash 调 `wsl -- bash -lc` 会把 Windows PATH（`C:\Program Files\...`）注入 WSL，报
  `C:/Program: No such file or directory` → 脚本内显式 `export PATH=<干净路径>`；
- Git Bash 的 `/tmp` 与 WSL **不互通**，跨环境脚本须放仓库内（如 `build/`）或 WSL 侧路径。

### 9.7 局限（沿用 §3.4，必须如实随结论引用）

- **CPU 保真度低**：`--cpus=2` 只限配额，不改频率/缓存/内存带宽 → **不得**用本环境的吞吐/延迟数字宣称「低端设备性能」；
- **无 GPU**：L 档本就无 torch、不依赖 CUDA，故不影响本计划指标；
- **文件系统差异**：容器/`$HOME` 内 ext4 vs Windows NTFS → 冷启动数字以上述环境内为准；
- **仍不替代真机验收**：真实手机/ARM 的最终验收留待实体设备（§3 阶段 3）。

### 9.9 阶段 2 基础设施：QEMU 与 WSL2 共存（2026-09-18）

文档 §4.2 把「**Hyper-V/WSL2 与 VirtualBox 互斥**」列为已知坑，并据此建议"两方案需取舍"。
选 **QEMU** 可绕开该限制（走 `-accel whpx`，即 Windows Hypervisor Platform），本次实测确认。

| 项 | 结果 |
| --- | --- |
| QEMU 版本 | **11.1.0**（`winget install SoftwareFreedomConservancy.QEMU`）|
| 二进制 | `C:\Program Files\qemu\qemu-system-x86_64.exe`、`qemu-img.exe` |
| 可用加速器 | **`tcg`、`whpx`** |
| 测试 A：WSL 运行中启 QEMU | QEMU **存活**（whpx 被接受）|
| 测试 B：WSL 跑 CPU 负载 + QEMU(whpx) 同跑 | QEMU **存活**、WSL 侧 **`ALIVE`**（`nproc=2`）|
| 残留 warning | `WHPX: Failed to get performance monitoring features`（**仅性能计数器，与功能无关**）；加 `-cpu max` 后 `svm` 警告消失 |

**结论**：**阶段 1 的 WSL 环境与阶段 2 的 VM 可同时全速使用**，无需二选一 —— 这比文档 §4.2 预设的
VirtualBox 方案**少一个硬约束**。证据：`local_docs/evidence/edge-sim/CORE-EDGE-SIM-02-qemu-wsl2-coexist-2026-09-18.txt`。

**阶段 2 待做的仍是**：主从节点组网（显式 endpoint，不依赖 mDNS）、弱网注入（`tc netem`）、地址持久化。
