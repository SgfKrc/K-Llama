## 0. 结论（一句话）

**Silica 是「标准 llama.cpp RPC + 比例/上限 offload」的 Android 外壳，不含任何层段分配协议、
无容错、无安全；作为 QLH 兜底只能解决「借别的设备算力」，不能证明「多设备合持一个装不下的模型」。**

---

## 1. 机制判定（含代码证据）

**仓库性质**：纯 **Kotlin Android 单模块应用**（GitHub API `language: Kotlin`，`size=11619KB`，
`pushed_at 2026-04-30`）；顶层仅 `app/` + `settings.gradle.kts` + README + **AGPLv3** `LICENSE.txt` +
截图/logcat + 一个 **`llama.cpp` git submodule**。**没有 PC 侧实现**（PC 端靠 llama.cpp 原生
`llama-server` / `ggml-rpc-server` 或 Termux）。

| 项 | 判定 | 证据 |
| --- | --- | --- |
| **传输** | **llama.cpp 内建 RPC（非自研）** | `BinaryRunner.kt` worker 分支：`binaryName = "librpc.so"`，`--host 0.0.0.0 --port <50052..50100 首个空闲>`；master 分支 `libllama.so -m <gguf> --port 8080 -c 4096 -t N`，并把校验通过的节点拼成 **`--rpc ip:port,ip:port`** |
| **切分** | **全局标量 `-ngl` + 比例 `--tensor-split`** | `BinaryRunner.kt`：`-ngl 999` + `--tensor-split "<masterPct>,<100-masterPct>"` |
| **层数算法** | 由比例换算，**非 per-node 层段** | `SilicaService.kt`：`masterLayers = totalLayers * masterPct / 100`；`offloadedLayers = totalLayers - masterLayers`；`totalLayers` 取自 `GgufMetadataParser.getTotalLayers()`（读 GGUF `*.block_count`）|
| **★ full-offload 路径** | **整模上传给一台 worker** | `SilicaService.kt`：**HTTP POST `/upload-model`（requestTimeout 3600s）** → `/start-full-engine` 附 `rpcNodes` 挂二级 worker |

**→ 多远端节点如何分摊层，由 llama.cpp 决定；Silica 从未指定「哪台持哪些层」。**

## 2. Android 承载方式（值得参考的工程做法）

| 做法 | 细节 | 证据 |
| --- | --- | --- |
| **不用 NDK/JNI 绑定** | 把可执行文件当 `.so` 放进 `jniLibs`，运行时从 `applicationInfo.nativeLibraryDir` 取路径 → `setExecutable(true)` → `ProcessBuilder(exec).start()`，设 `LD_LIBRARY_PATH=nativeLibDir` | `SilicaService.kt` |
| **保持可执行位** | `packaging { jniLibs { useLegacyPackaging = true } }` | `app/build.gradle.kts` |
| **强制 `--no-mmap`** | Android 连续 3GB+ 大块映射失败 | `BinaryRunner.kt` |
| **服务化** | `SilicaService : Service`，`foregroundServiceType="dataSync"` + `PARTIAL_WAKE_LOCK` | `AndroidManifest.xml` |
| **权限集** | `INTERNET / ACCESS_NETWORK_STATE / FOREGROUND_SERVICE(_DATA_SYNC) / WAKE_LOCK / REQUEST_IGNORE_BATTERY_OPTIMIZATIONS / RECORD_AUDIO`；`usesCleartextTraffic="true"`；minSdk 24 / targetSdk 36 | 同上 |
| **发现（无 mDNS）** | 对本机 `/24` 做 **TCP 扫描 1..254，每批 45**，探测 **8082**（telemetry 先起，50052 要等模型加载完） | `NetworkManager.discoverLocalWorkers()` |
| **活体检测** | 裸 TCP connect（`pingWorkerNode()`） | 同上 |
| **join 握手** | `POST http://worker:8082/request-join {masterIp}` → `GET /join-status`（`isAuthorized`）；worker 的真实 RPC 端口经 telemetry `rpcPort`（默认 50052）上报 | `NetworkManager.kt` / `TelemetryServer.kt` |
| **对外入口** | master 另起 Ktor 网关 8081 + Cloudflare/Ngrok/Tailscale 隧道 | `ApiGatewayServer.kt` |

**⚠️ 关键缺口**：`librpc.so` / `libllama.so` **不在仓库**（根 `.gitignore` 含 `*.so`），
`app/src/main/` **只有** `AndroidManifest.xml`、`java`、`res` —— **无 `jniLibs/`、无 `cpp/`、
无 `CMakeLists.txt`、无 `externalNativeBuild`**。
→ **交叉编译产物与构建脚本均未提供，仓库对 Android 侧不可复现（未确认项）。**

## 3. 与 QLH 目标的差距清单

| QLH 需要 | Silica 现状 | 证据 |

| 每节点**连续 `layer_range` 合同** | **无**；只有全局 `-ngl` + `--tensor-split` | `BinaryRunner.kt` / `SilicaService.kt` |
| 每节点**持有哪些层（manifest）** | **无**；只有节点属性（RAM/CPU/温度/Tops/rpcPort） | `NodeManager.kt` 的 `WorkerTelemetry` |

## 4. 可复用 / 需自研 / 不可用（三分清单）

### 4.1 可直接参考（**工程做法，非代码**）

- **`.so` 塞 `jniLibs` + `useLegacyPackaging` + `nativeLibraryDir` + `setExecutable`
  + `ProcessBuilder` + `LD_LIBRARY_PATH`** —— 「没有 JNI 也能跑原生可执行」的打包法；
- 前台服务 + `PARTIAL_WAKE_LOCK` 抗后台限制；
- 僵尸进程清理（`ps` / `kill -9` 或 `killall` 回收 50052/8080）；
- **`--no-mmap`、`--host 0.0.0.0`**（绕 IPv4/IPv6 loopback 问题）；
- **telemetry HTTP 侧信道（8082）**承载控制面与端口上报；
- 无 mDNS 时的**局域网 TCP 扫描发现**；
- **启动前 pre-flight 校验**（先验证节点再上 RPC）。

### 4.2 需重写（QLH 必须自研）

1. **层段合同与 manifest**（`layer_range` + 校验 + 与 GGUF 一致）；
2. **身份校验与传输保护**（mTLS / 节点令牌；注意 Silica 的 `ApiKeyManager.kt`
   只保护自家对外网关，**不保护 worker 间 RPC**）；
3. **租约 / epoch / fencing + 掉线重分片与恢复**；
4. **按层段的模型分发**（**禁止整模上传**）；
5. **PC 侧与服务端编排**（Silica **无 PC 代码**）；
6. **构建流水线**（自建交叉编译 + ABI 产物）。

### 4.3 不可用

- **Silica 的 Kotlin/Compose 应用代码本身**（**AGPLv3**，QLH 政策不整合）；
- **full-offload 整模上传路径**；
- **把 `--tensor-split` 比例分配当作「容量合并」方案**。

## 5. 兜底可行性结论与风险

### 5.1 判定

**只能作为「借设备/后端」的兜底，不能作为「容量合并」的兜底证据。**

若主路径受阻，采用 Silica 式做兜底的**真实收益 ≈ 把 Android 变成 `ggml-rpc-server` 后端**；
**容量语义仍依赖远端能装下它该装的层**（`-ngl 999` 时远端要装整模）。

这**印证仓内既有定位**：路线 A = 「借用别的机器的 GPU（借后端，非集群编排）」
（`docs/archive/distributed/单机工作整理与分布式路线盘点-2026-09-16.md`）。

### 5.2 主要风险

1. **AGPL** → 不能搬码，人力成本 ≈ 从零写 Android 编排层；
2. **Wi-Fi + 无容错**：任一 worker 掉线即整栈失败，且无重分片/检查点；
3. **无鉴权无加密**（README 自认）→ 不能上公网/公共 Wi-Fi；
4. **热/电与 Android 后台限制**，靠 WakeLock 硬扛；
5. **仓库不含原生产物与构建脚本** → Android 侧工程链路完全靠自己复现；
6. **性能未实测**：`--tensor-split` 每 token 跨设备张量同步在 Wi-Fi 上的代价未知。

## 6. ★ 对 QLH 的直接含义

| 命题 | 判定 |
| --- | --- |
| **Silica 式可作为「借设备算力」的兜底** | ✅ 可行 |
| **Silica 式可作为「多设备合持装不下的模型」的兜底** | ❌ **不成立**（它是整模上传 / 比例 split）|
| **「容量合并」需要什么** | **层段协议自研** —— 这正是本项目 §14 已做出雏形的能力（上游按需加载 + 下游裁层，**64/64 一致**）|
| **`--tensor-split` 的跨设备同步代价** | 与本人对 `--override-tensor` 的实测结论**一致**：**跨设备往返代价高，不适合当作容量方案** |

**→ 建议**：
1. **路线 A 的「兜底」定位精确化为「借后端」**，不要写成「容量合并」；
2. **层段协议（`layer_range` 合同 + manifest + 校验 + 掉线重分片）作为自研项单独立项**，
   这是 QLH 相对 Silica 的**真实增量**；
3. **Android 打包法**（§4.1）可直接移植，**但与其应用代码无关**（避 AGPL）。
