# 同进程双后端接力：实现与性能（2026-09-16，历史报告）

> 背景：实测跨进程 D→L 为 **1.44 s/步**（64 步 92 s），其中约 1.3 s 被判定为 Python 进程间通信开销。
> 用户裁决：**消除 D→L 的进程边界（同进程双后端）**；多卡/多节点方向排除（边缘设备集群凑不出规模）；
> **D 档永远有存在理由**（天然适合层间流水线 + 可做对照实验）。
>
> 性质：**实现 + 实测**。关联：[引擎单序列与并发性能对比](引擎单序列与并发性能对比-2026-09-16.md) · [网络接力辨析](跨框架接力与异构内存分层-辨析-2026-09-16.md)

> **有效性覆盖（2026-09-21）**：本文的 828/333 ms、生产门和“Windows 无 Triton 构建”均属于当时实验快照。当前有效 D→L 数据、准入规则和 Windows 原生 `triton-windows==3.8.0.post28` 口径见[当前有效基线与后续优化计划](../../跨框架接力-当前有效基线与后续优化计划-2026-09-21.md)。本文仍可用于理解历史优化过程和 WSL2 对照，不作为当前性能基线。

## 1. 实现：为什么不需要 fork

上游 `llama.cpp` 的 `relay-gen-dl.cpp` 仅 176 行，其 hidden 注入机制是：

```cpp
llama_batch batch = llama_batch_init(n_tokens, n_embd_inp, 1);
memcpy(batch.embd, hidden.data(), hidden.size() * sizeof(float));
llama_decode(ctx, batch);
```

**`batch.embd` 是 llama.cpp 的标准 `llama_batch` 字段**（不是本项目 patch 的 API）。
因此 **PyPI 版 `llama-cpp-python` 的底层绑定即可完成同进程注入，无需重新编译、无需 fork**。

### 1.1 关键调用链（`llama-cpp-python` 0.3.28，基于 ctypes）

| 步骤 | API |
| --- | --- |
| 加载裁层模型 | `llama_model_load_from_file(path, model_params)` |
| 建 context | `llama_init_from_model(model, ctx_params)` |
| 每步清 KV | `llama_get_memory(ctx)` + `llama_memory_clear(mem, True)` |
| 构造批次 | `llama_batch_init(n_pos_per_embd * n_tokens, n_embd_inp, 1)` |
| **注入 hidden** | `ctypes.memmove(batch.embd, hidden.ctypes.data, hidden.nbytes)` |
| 解码 | `llama_decode(ctx, batch)` |
| 取 token | `np.ctypeslib.as_array(llama_get_logits_ith(ctx, n-1), shape=(n_vocab,)).argmax()` |

**版本提示**：本项目 `.venv-xframe` 装的是 **0.3.28**（主仓 `requirements-edge.txt` 要求 **0.3.35**）；
0.3.28 的绑定为 **ctypes**（`batch.embd` 是 `LP_c_float`），不是 cffi，故写入用 `ctypes.memmove`。

### 1.2 ⚠️ 两个踩坑记录（都有明确根因）

#### 坑 1：`0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND`（exit=127）

**症状**：脚本导入 `llama_cpp` 后立即以 `127` 退出。

**根因**：为运行 MSYS2/MinGW 编译的 C++ exe 而 `export PATH="/c/msys64/ucrt64/bin:$PATH"`，
这个 PATH 让 `llama_cpp` 的 DLL **误加载 MSYS2 的 libstdc++**，入口点不匹配。

**修法**：**Python 进程不要注入 MSYS2 PATH**（那是给 C++ exe 的必要条件，对 pip 装的 DLL 反而有害）。

> 📌 与既有经验不冲突：`export PATH="/c/msys64/ucrt64/bin:$PATH"` 是**跑 MinGW exe** 的硬要求；
> 而 `llama-cpp-python` 的 DLL 自带运行时，**两者不能混在同一个进程环境里**。

#### 坑 2：`0xC0000374 STATUS_HEAP_CORRUPTION`（堆损坏）

**症状**：`llama_batch_free(batch)` 时崩溃。

**根因**：`#28963` 的调用方修法要求 **pos 数组按 `n_pos_per_embd * n_tokens` 提供**，
而 `llama_batch_init(n_tokens, ...)` 只分配 `n_tokens` 个槽位。
我最初的做法是**把 `batch.pos` 指针替换成 Python 的 ctypes 数组** —— 但 `llama_batch_free()`
会对它调用 C 的 `free()`，**释放一个非 malloc 指针 → 堆损坏**。

**修法**：**直接 `llama_batch_init(n_pos_per_embd * n_tokens, n_embd_inp, 1)`**，
让 llama.cpp 自己分配足够大的 pos（分配与 `free()` 天然配对），然后只把 `batch.n_tokens` 设为真实 token 数。
代价是 `embd` 也多分配 `n_pos_per_embd` 倍（本场景 ≤16 MB，可忽略）。

## 2. 实测：同进程 vs 跨进程（严格同配置）

**配置**：prompt = `The capital of France is`（5 token），gen = 64，下游 = `qwen35-2b-f16-cut.gguf`（从 layer 4 起），
上游 = torch f32 + eager，`threads=8`，下游纯 CPU（`gpu_layers=0`）。

| 版本 | 传输机制 | 总墙钟（64 步） | 一致步数 |
| --- | --- | ---: | ---: |
| **跨进程** | stdin/stdout 二进制管道（子进程） | **182 s** | 64/64 |
| **同进程** | `ctypes.memmove`（进程内内存） | **167 s** | 64/64 |
| 差异 | — | **−15 s（−8%）** | — |

**同进程版内部耗时拆解**（167 s）：

| 环节 | 耗时 | 占比 |
| --- | ---: | ---: |
| torch 上游加载 | 7.0 s | 4% |
| llama.cpp 下游加载 | 0.6 s | 0.4% |
| **下游 decode（64 步）** | **37.5 s**（**586 ms/步**） | 22% |
| **上游 torch 前向（64 步）** | **≈122 s**（**1.9 s/步**） | **73%** ⚠️ |

## 3. 分析：为什么只快 8%

### 3.1 IPC 确实被消除了，但它不是主要成本

原判「1.3 s/步是 IPC 开销」**过于乐观**。同进程后下游变成 586 ms/步，可见 IPC 的绝对量在**百毫秒级**，
而不是秒级。原因：`relay-gen-dl.cpp` 每步只传 **整段 hidden**（5→69 token × 2048 × 4 B ≈ 40–565 KB），
在本地管道上并不昂贵；且该子进程**常驻**（模型只加载一次），省掉了进程启动成本。

### 3.2 真正的瓶颈：上游 torch（1.9 s/步）

两个叠加原因（**均非实现缺陷，而是配置问题**）：

1. **无 KV 复用**：每步调用 `model(input_ids=full_seq, output_hidden_states=True)`，
   序列从 5 增长到 69，复杂度 **O(n²)**；而 llama.cpp 侧有 KV cache（O(n)）。
2. **算子回退**：transformers 明确警告
   - `causal_conv1d_fn` → *"falling back to its reference PyTorch implementation because `causal_conv1d` is not installed"*
   - `chunk_gated_delta_rule` → *"...`flash-linear-attention` is not installed"*

   **Qwen3.5 是 hybrid 架构（Gated Delta Net）**，这两条正是它的关键优化算子；
   缺失时回退到参考实现，**"much slower"**（transformers 原文）。

| 对照 | 单步耗时 |
| --- | ---: |
| 上游 torch（全段重算 + 无优化算子） | **1900 ms** |
| 下游 llama.cpp（5 层，全段重算） | 586 ms |
| （参考）llama.cpp **整模 28 层 GPU** | **13.5 ms**（74 t/s） |

### 3.3 结论（⚠️ 已被 §4 的实测修正）

> 初版结论说「消除进程边界是必要条件但不是充分条件」。**实测证明这个判断仍然过于乐观**：
> **进程边界根本不是主要成本（仅 8%），真正的杠杆是 KV 复用（3.15×）**。详见 §4。

## 4. 第二轮：双侧 KV 复用（决定性优化）

### 4.1 实现

`relay_sameproc_kv.py` 在 `relay_sameproc.py` 基础上让**两侧都走增量**：

| 侧 | 改动 |
| --- | --- |
| **上游** | 传 `past_key_values` + `use_cache=True`；prefill 喂整段，其后每步只喂 1 个 token |
| **下游** | 不再每步 `llama_memory_clear`；只注入**新增的末位 token** 的 hidden（`n_tokens=1`），`pos` 用绝对位置递增 |
| 传输量 | ~565 KB/步 → **8 KB/步** |

**⚠️ 实现中踩到的坑**：初版在 prefill 那一步**只传了最后 1 个 token 的 hidden**
（因为 `past` 已被赋值，无法区分首步），导致下游缺少前 4 个 token 的 KV，
输出退化为 `369 369 369 ...`。修法：在覆盖 `past` **之前**先记录 `is_prefill`，prefill 传整段。

### 4.2 实测（同配置，gen=64）

| 版本 | **总墙钟** | 上游/步 | 下游/步 | 一致步数 |
| --- | ---: | ---: | ---: | ---: |
| 跨进程 + 全段重算 | 182 s | 1900 ms | 586 ms | 64/64 |
| 同进程 + 全段重算 | 167 s | 1900 ms | 586 ms | 64/64 |
| **同进程 + 双侧 KV** | **53 s** | **287 ms** | **151 ms** | **64/64** |
| **累计加速** | **3.4×** | **6.6×** | **3.9×** | ✅ 一致保持 |

**分解各手段的单独收益**：

| 手段 | 收益 |
| --- | --- |
| 消除进程边界（同进程） | **8%**（182 → 167 s） |
| **KV 复用（两侧增量）** | **3.15×**（167 → 53 s）✅ |

### 4.3 结论修正

> **真正的杠杆在算法/数据流层面，不在传输层面。**
> 消除进程边界只值 8%；**KV 复用值 3.15×**。这与用户在「分块流水线」上的一贯判断一致 ——
> llama.cpp 的优势同样来自 prefill 分块与 KV 复用，而非传输。
>
> **KV 复用不破坏数值一致性** —— 64/64 逐 token 一致（增量与全段重算在 argmax 判据下等价）。

### 4.4 但仍远未可用

| 对照 | 每步耗时 |
| --- | ---: |
| 本项目跨框架（**同进程 + KV**） | **828 ms** |
| llama.cpp 原生整模 GPU（28 层） | **13.5 ms** |
| **差距** | **61 倍** ⚠️ |

**残留开销定位（已由 §4.6 实测修正）**：

1. **上游 ~287–466 ms**：`output_hidden_states=True` 每步都需保留 hidden；且 **Gated Delta Net 算子回退** ——
   `flash-linear-attention` 依赖 **triton**，而 **triton 无 Windows 官方 wheel** → 本机无法启用；
   `causal-conv1d` 需 nvcc 编译，pip 安装失败。
   **⚠️ 这是环境限制（上游包发布矩阵），不是架构限制** —— 可通过 **WSL2** 绕开（见 §4.6.3）。
2. **下游 ~151–185 ms**：⚠️ **初版推测的「`llama_batch_init/free` 的 malloc 对是瓶颈」已被 §4.6.1 证伪**。

### 4.6 第三轮：两项固定开销优化 —— **均被证伪**

针对 §4.5 列出的两个候选的实测（脚本 `relay_sameproc_fast.py`）。

#### 4.6.1 优化①：复用 `llama_batch` → ❌ **无收益**

做法：按最大 token 数 `llama_batch_init` **一次**，每步只改 `n_seq_id` / `seq_id` / `logits` / `pos` / `n_tokens` / `embd`。

| 版本 | 总墙钟（gen=64） | 上游/步 | 下游/步 | 一致 |
| --- | ---: | ---: | ---: | ---: |
| 双侧 KV（每步 init/free） | **53 s** | 287 ms | 151 ms | 64/64 |
| **双侧 KV + batch 复用** | **68 s** | 466 ms | 185 ms | 64/64 |

**→ 不仅无收益，反而更慢。** 结论：**`llama_batch_init`/`llama_batch_free` 不是瓶颈** ——
§4.4 的推测**错误**。下游的真实开销在 llama.cpp 的 CPU 前向本身与 248320 词表的 argmax。

**⚠️ 复用 batch 时踩坑**：`llama_batch_init` 后各槽位的 `n_seq_id[i]` / `seq_id[i][0]` 是**未初始化值**，
必须**每步重设** `for i in range(n_tokens)`；否则 `llama_decode` 报
`init: invalid seq_id[N][M] = <垃圾值> >= 1`。

#### 4.6.2 优化②：上游只跑前 4 层 → ❌ **数值被破坏**

**决定性对比实验**（同一输入 `The capital of France is`，完整模型 vs 截断到 4 层）：

```
FULL : n_hidden_states = 25   h[4] = (5, 2048)
TRUNC: n_hidden_states =  5   h[4] = (5, 2048)
max|h_full - h_trunc| = 19.62                     ← 差异巨大
h_full [0,:4] = [ 0.01186,  0.02383,  0.05641, -0.08277]
h_trunc[0,:4] = [ 0.30760,  0.60799,  1.89447, -2.22753]
```

**同 shape 下数值完全不同** → 截断后模型内部行为被破坏（**0/8 步一致**，确定性错误）。

**根因**：**Qwen3.5 是 hybrid 架构**（部分层 Attention、部分层 Gated Delta Net），
`Qwen3_5TextModel.forward` 的层角色/配置**依赖完整的层结构**。简单执行
`model.layers = ModuleList(model.layers[:4])` 无法得到与完整模型一致的前 4 层输出。

**⚠️ 顺带排除**：改不改 `config.num_hidden_layers` **结果完全相同**（错误序列一字不差），故**不是** config 的问题。

**正确做法**：手动实现前向（`Qwen3_5DecoderLayer.forward(hidden_states, position_embeddings, attention_mask, position_ids, past_key_values)` + 自算 `position_embeddings`）；
**成本与风险高，收益（上游 4×）低于已获得的 KV 复用（3.15×）** → **不做**。

#### 4.6.3 WSL2 路线（已实测可行）

「算子缺失」的具体含义是：**`flash-linear-attention` 依赖 `triton`，而 triton 没有 Windows 构建**。
本机 WSL 环境实测：

| 项 | 结果 |
| --- | --- |
| 发行版 | **Ubuntu-22.04**，**VERSION = 2**（WSL2） |
| `nvidia-smi`（WSL 内） | ✅ **可用**：`RTX 4060 Laptop GPU, 610.47, 8188 MiB` |
| `/usr/lib/wsl/lib/` | ✅ 有 `libcuda.so.1`（WSL GPU 直通） |

**→ WSL2 可绕开该限制**，GPU 直通可用，性能损失通常 <5%；
pip 装 `torch+cu12x` 自带 CUDA runtime，**无需在 WSL 内另装 CUDA toolkit**。
**⚠️ 未验证**：WSL 内实际跑 CUDA kernel（`nvidia-smi` 能跑 ≠ torch 能算）。

#### 4.6.4 三轮优化的总账

| 手段 | 收益 | 判定 |
| --- | ---: | --- |
| **KV 复用（两侧增量）** | **3.15×**（167 → 53 s） | ✅ **唯一有效** |
| 消除进程边界（同进程） | 8% | ⚠️ 小 |
| 复用 `llama_batch` | ~0（甚至更慢） | ❌ **证伪** |
| 上游层截断 | 数值破坏 | ❌ **不可行** |
| 启用 fla / causal-conv1d 算子 | 未测（Windows 不可用） | ⏸ WSL2 可试 |

**→ 结论：真正的杠杆在算法/数据流层面（KV 复用），工程侧的微优化收益有限。**

## 5. 对 D 档（PyTorch 引擎）的含义

用户裁决「**D 档永远有存在理由**」在本轮得到支撑：

| D 档的不可替代性 | 本轮证据 |
| --- | --- |
| **天然适合层间流水线** | 同进程双后端已验证可行（`relay_sameproc.py`），且是**层流水线的最简载体**（层切分点可任意移动） |
| **可做对照实验** | 同一模型两条实现路径对拍：跨进程 / 同进程 / 纯 llama.cpp / 纯 torch，四条路径并存且可逐 token 比较 |
| ⚠️ **但性能仍需证明** | 当前端到端 **2.6 s/步**（167 s / 64 步）**远慢于** llama.cpp 原生 GPU（13.5 ms/步）——**D 档的价值在当前实现下是"能力"而非"性能"** |

**⚠️ 必须诚实的边界**：本文**没有**证明 D 档在性能上有竞争力。
它目前证明的是：**跨框架接力在正确性上可靠、在进程边界上可消除**，而**性能瓶颈在上游 PyTorch 侧**。

## 9. WSL2 路线实测（2026-09-16 追加，回答「算子缺失能否靠 WSL」）

### 9.1 结论：**可以，WSL2 的 CUDA 与加速算子均可用**

| 环节 | Windows | **WSL2（Ubuntu-22.04, VERSION=2）** |
| --- | --- | --- |
| GPU 可见（`nvidia-smi`） | ✅ | ✅ `RTX 4060 Laptop GPU, 610.47, 8188 MiB` |
| GPU 直通库 | — | ✅ `/usr/lib/wsl/lib/libcuda.so.1` |
| `torch.cuda.is_available()` | ✅ | ✅ |
| **GPU 实际计算**（matmul 2048²） | ✅ | ✅ **成功**（`sum=115647.875`） |
| **`triton`** | ❌ **无 Windows 构建** | ✅ **3.8.0**（随 torch 自动安装） |
| **`chunk_gated_delta_rule`** | ❌ **import 失败** | ✅ **OK** |

## 10. 长上下文复测：WSL2 的 fla 收益**确实存在**（2026-09-16 追加）

用 **1720 token** 长 prompt 重测同一基准（`bench_torch_opt.py --mode kv`，f32 + eager，gen=8）：

| 指标 | Windows | **WSL2** | 比值 |
| --- | ---: | ---: | --- |
| **prefill（1720 token）** | 2.649 s | **1.606 s** | **WSL2 快 1.65×** ✅ |
| **decode（ms/步）** | 69.92 | 134.41 | Windows 快 1.92× ⚠️ |
| 峰值显存 | 10.335 GB | 10.335 GB | 同 |
| **算子回退警告数** | **4** | **2** | WSL2 少 2 个 |

**长序列下 transformers 多触发了两个（decode 路径的）算子**：

| 算子 | Windows | WSL2 |
| --- | --- | --- |
| `chunk_gated_delta_rule` | ❌ 回退 | ✅ **生效** |
| `fused_recurrent_gated_delta_rule` | ❌ 回退 | ✅ **生效** |
| `causal_conv1d_fn` | ❌ 回退 | ❌ 回退（需编译） |
| `causal_conv1d_update` | ❌ 回退 | ❌ 回退（需编译） |

### 10.1 结论

1. **fla 的收益真实存在，且只在长序列显现** —— prefill 快 **1.65×**。
   这解释了 §9.2 中短序列（29 token）「无差异」的原因：**prefill 占比太小**。
2. **⚠️ 但 decode 反而慢 1.92×** —— 两个叠加因素（**未分离**）：
   - `causal_conv1d` / `causal_conv1d_update`（**decode 路径算子**）在**两侧都缺失**；
   - WSL2 的 GPU 直通（`/usr/lib/wsl/lib`）在**小 kernel 密集调用**时开销更明显。
3. **→ 「算子缺失是 Windows 环境限制」成立**；WSL2 **能解锁 prefill 侧收益**，

4. **⚠️ 显存超额**：本轮峰值 **10.335 GB > 8 GB 物理显存**，说明该配置已触发 CUDA 显存超额
   （允许，但性能受损）—— **长上下文的显存压力本身就是瓶颈**。

## 12. 五段剖析：真正的耗时在哪（2026-09-16，决定性）

用户要求「实验要做就做完备」后，写了 `relay_sameproc_prof.py`（与 KV 版数值路径完全相同，
只加五段计时）实测 gen=64：

| 段 | 秒 | 占 loop | **ms/步** |
| --- | ---: | ---: | ---: |
| **t_torch**（上游 forward） | **26.09** | **66.49%** | **407.6** |
| **t_decode**（下游 decode + argmax） | **12.92** | **32.93%** | **201.9** |
| t_convert（hidden→numpy） | 0.061 | 0.15% | 0.95 |
| t_batch_setup（init + 填字段 + memmove） | 0.032 | 0.08% | 0.50 |
| t_batch_free | 0.003 | 0.01% | 0.04 |
| **unaccounted**（循环/同步/其他） | **0.135** | **0.34%** | **2.11** |
| **loop 合计** | **39.24** | 100% | **613.1** |

### 12.1 三个修正（均否定本文先前的判断）

1. **❌ 「瓶颈是同步次数」被推翻** —— `unaccounted` **仅 2.11 ms/步（0.34%）**。
   同进程接力的通信/同步开销**几乎为零**。§11 及更早基于推断的判断**错误**。
2. **❌ 「Python 侧 init/free 是瓶颈」再次被否** —— `batch_setup + batch_free`
   合计 **0.54 ms/步（0.09%）**，与 §4.6.1「复用 batch 无收益」互相印证。
3. **✅ 耗时 99.3% 是两侧的实际计算**：上游 66.5% + 下游 32.9%。

### 12.2 ★ 由此暴露的最大单项收益：上游在白跑 20 层

上游 **407.6 ms/步** 的真实含义：**它跑的是完整 24 层模型**（因为无法安全截断，见 §4.6.2），
但**只用了前 4 层的输出**。

**→ 若能把「只跑前 4 层」做对，上游理论降到 ~68 ms（6×）** —— 这是**当前最大的单项收益**，
**大于下游 GPU offload（2.18×）**。

**⚠️ 做法**：朴素截断会破坏数值（§4.6.2 实测 0/8），必须**手动实现前向**：
`Qwen3_5DecoderLayer.forward(hidden_states, position_embeddings, attention_mask, position_ids, past_key_values)`
+ 自算 `position_embeddings` 与 causal mask。

### 12.3 对「块接力 / 投机解码」的重新评估

**❌ 原论证（"减少同步次数"）不成立** —— 同步只占 0.34%。

**✅ 但仍有价值，机制不同**：收益来自**用一次批量前向替代 k 次串行前向**，
而非减少同步。下游 `decode` 的 **201.9 ms/步** 若能通过批量验证摊薄，才是真正的杠杆。

**⚠️ 定量门槛**：仅当下游「批量验证 k 个 token 的耗时」<「k 次单 token 耗时」时才有收益；
llama.cpp 的 prefill 分块能力（实测量级 3.3×）说明该前提**可能成立**，
但投机解码还**需接受率达标**（与是否异构无关的独立条件）。

### 12.4 修正后的优化优先级

| 优先级 | 动作 | 预期 | 依据 |
| ---: | --- | ---: | --- |
| **1** | **上游只跑前 4 层（手动前向，非截断）** | **~6×**（407→68 ms） | §12.2 |
| **2** | **下游 GPU offload** | **2.18×**（已实测） | §11.1 |
| 3 | 投机解码（批量验证） | 取决于接受率 | §12.3 |
| — | ~~消除进程边界~~ | **实测 ~0** | §12.1 |
| — | ~~复用 batch~~ | **0.09%** | §12.1 |

**总账修正**：本文 §4.6.4 与 §9 中「同进程 8%」「同步是瓶颈」等表述**以 §12 为准**。

## 13. 上游手动 4 层：10.7× 加速，数值 bit-exact（2026-09-16，本轮最大成果）

### 13.1 为什么朴素截断失败、正确做法是什么

读 `Qwen3_5TextModel.forward` 源码后发现两处关键：

```python
for i, decoder_layer in enumerate(self.layers[: self.config.num_hidden_layers]):
    hidden_states = decoder_layer(
        ...
        attention_mask=causal_mask_mapping[self.config.layer_types[i]],   # ← 关键
        ...)
```

1. 层循环按 `config.num_hidden_layers` 切片 → 改它是有效路径；
2. **但每层的 attention 类型由 `config.layer_types[i]` 决定**，两种 mask 是**预先建好**的
   （`create_causal_mask` / `create_recurrent_attention_mask`，后者**依赖完整 config**）。
   → 改 `num_hidden_layers=4` 会让 recurrent mask 的 state 配置错位 = 0/8 的真正原因。

**正确做法**：按该 forward 的真实逻辑**手动复现前 4 层**
（`embed → 4 段 M-RoPE position_ids → rotary_emb → 两种 mask → 4×DecoderLayer`）。

**正确性验证**（`verify_manual_4L.py`）：

```
max|diff|      = 0.000000e+00      ← 与完整模型 hidden_states[4] **bit-exact**
mean|diff|     = 0.000000e+00
allclose(1e-4) = True
```

### 13.2 性能（gen=64，同进程 + KV）

| 版本 | loop | 上游/步 | 下游/步 | 一致 |
| --- | ---: | ---: | ---: | ---: |
| 同进程 + KV（全模上游） | 39.24 s | **407.6 ms** | 201.9 ms | 64/64 |
| **同进程 + KV + 手动 4L** | **13.12 s** | **38.1 ms** | 166.6 ms | **64/64** |
| 加速 | **2.99×** | **10.7×** | — | ✅ |

**完全验证 §12 的剖析**：上游确实在白跑 20 层；修掉后上游 **10.7×**，且**数值 bit-exact**。

### 13.3 下游 KV 复用：新增 `--keep-kv`

组合「上游增量（只出末位 hidden）」+「跨进程下游」时发现**结构性矛盾**：
`relay-gen-dl.cpp` 原先**每步 `llama_memory_clear`**、需要**整段 hidden**；增量上游只出 1 行 → **3/64**。

**修法**：给下游加 `--keep-kv`（跳过 clear + pos 绝对累加）；driver 通过 `QLH_DOWNSTREAM_KEEP_KV=1` 透传。

**结果**（跨进程 + 4L + keep-kv）：

| 下游 | 墙钟（64 步） | 一致 |
| --- | ---: | ---: |
| offload=0 | 93 s | 64/64 |
| offload=99（GPU） | 81 s | 64/64 |

**✅ 正确性恢复 64/64**；但**只有 13% 提升** —— **跨进程 IPC 已成为新瓶颈**。

### 13.4 ★ 结论修正：「IPC 只占 8%」是两侧都慢时的假象

| 版本 | 墙钟 | IPC 角色 |
| --- | ---: | --- |
| 同进程 + 全段重算 | 167 s | 8%（小） |
| **同进程 + KV + 4L** | **21.3 s** | — |
| 跨进程 + KV + 4L + GPU | 81 s | **主导** |

与 §12.1 **不矛盾**：§12.1 测的是**同进程内部**的"同步/循环"开销（≈0），
而 IPC 是**跨进程**成本 —— 两者在被优化前都被两侧的慢计算掩盖。

**→ 最优配置：同进程 + KV + 手动 4L（21.3 s / 64 步 ≈ 333 ms/步）**。
若要再叠加 GPU 下游，需 **CUDA 版 llama-cpp-python**（未构建）。

### 13.5 累计进展总表

| # | 配置 | 墙钟（64 步） | 一致 | 相对首版 |
| ---: | --- | ---: | ---: | ---: |
| 1 | 跨进程 + 全段重算 | 182 s | 64/64 | 1.0× |
| 2 | 同进程 + 全段重算 | 167 s | 64/64 | 1.09× |
| 3 | 同进程 + KV | 53 s | 64/64 | 3.4× |
| **4** | **同进程 + KV + 手动 4L** | **21.3 s** | **64/64** | **8.5×** |
| 5 | 跨进程 + KV + 4L + GPU offload | 81 s | 64/64 | 2.2×（受 IPC 拖累）|
| — | llama.cpp 原生整模 GPU（对照） | ~0.9 s | — | ~200× |

**对照组**：llama.cpp 原生整模 GPU 约 13.5 ms/步 × 64 ≈ 0.9 s，即**当前最优配置仍慢约 25 倍**（`333 ÷ 13.5 = 24.7`；⚠️ 参照不唯一，`-ngl 24` 的 `26.6 ms/token` 口径下为 12.5× —— 见[跨框架层接力-实验数据汇总](跨框架层接力-实验数据汇总.md) §F/§H），
但其间差距已从 **180× 缩到 20×**。

## 14. 层流水线：彻底摆脱整模加载（2026-09-16，用户命题）

**用户命题**：llama.cpp 的分布式（RPC）需要 leader 持有完整 GGUF；Silica 式尚未落地；
但**层流水线可以彻底摆脱整模加载** —— 且**层流水线与跨框架接力是孪生的**（同一套「层切分 + hidden 传递」机制）。

### 14.1 重量分布（切分依据）

统计 `models/qwen3-5-2b` 的 632 个张量（单分片 4.55 GB，f16）：

| 部分 | 元素 | 占比 | 备注 |
| --- | ---: | ---: | --- |
| **visual（多模态）** | 331.4 M | **14.6%** | **纯文本推理不需要** |
| **embed_tokens** | 508.6 M | **22.4%** | 上游必需 |
| **language L0-3** | 228.9 M | **10.1%** | **上游** |
| **language L4-23** | 1144.4 M | **50.3%** | **下游** |
| 其他（norm / rotary / mtp） | 60.8 M | 2.7% | |
| **全模型** | **2274.1 M** | 100% | |

**→ 上游（embed + L0-3）= 32.4%（1.47 GB）**；**下游（L4-23）= 50.3%（2.29 GB）**。

### 14.2 实现与验证

`layer_pipeline_upstream.py`：

1. 从原始 safetensors **只提取** `model.language_model.embed_tokens.*` 与 `layers.0..3.*`（54 张量）；
2. **剥离 key 前缀** `model.language_model.` —— `Qwen3_5TextModel` 的 state_dict **不带**前缀，
   否则 `load_state_dict` 全部 missing（首次实测 `missing=55 / unexpected=54` 即此因）；
3. 用**截断 config**（`num_hidden_layers=4`, `layer_types[:4]`）**从零构造** 4 层文本模型；
4. 只加载那部分权重，与完整模型的前 4 层输出逐元素比对。

**结果**：

| 指标 | 整模 | **层流水线上游** | 收益 |
| --- | ---: | ---: | ---: |
| 权重体积 | 4.55 GB | **1.47 GB** | **3.1× 小** |
| 张量数 | 632 | **54** | — |
| **数值** | — | **max\|diff\| = 0（bit-exact）** | ✅ |
| `missing` | — | **1**（`norm.weight`，上游不需要） | — |

**✅ 结论：「上游不加载整模」已实证可行，且数值 bit-exact。**

### 14.3 意义

1. **内存**：上游从 4.55 GB 降到 **1.47 GB（32.4%）**，且**排除 visual（14.6%）**；
2. **✓ 与跨框架接力孪生**：两者共用「层切分 + hidden 传递」机制 ——
   本文 §13 的**手动 4 层前向**正是层流水线的上游实现；区别在于此前仍加载整模，
   现在改为**按需加载**；
3. **⚠️ 但速度不变**：层流水线降低的是**内存与加载**，不是单序列延迟
   （§7.3 已证上游 97% 是计算，且 batch=1 为 memory-bound）；
4. **✓ 因此层流水线的价值是「能跑原本装不下的模型」** —— 与用户 2026-09-16 的
   「**能否装下不比速度重要性低**」判断一致。

### 14.4 未验证

1. **未接入接力端到端**（本脚本只验证上游加载的等价性，未接下游）；
2. **未测下游的按需加载**（下游现为裁层 GGUF，已天然满足"只持有自己那段"）；
3. **未测真实内存峰值**（只统计权重体积，未测 RSS / CUDA 峰值）；

### 14.5 端到端接入（2026-09-16 完成）

### 14.6 llama.cpp 能否裁层？（2026-09-16 用户提问的核查）

**结论：能，但分两个层次，语义不同。**

| 方式 | 是否**物理**裁层 | 机制 |
| --- | --- | --- |
| **裁层 GGUF**（本项目 `cut_layers.py` 已用）| ✅ **是** | **离线预处理**，文件中物理上只有那段层 |
| **`--load-mode mmap`**（默认）| ⚠️ **虚拟完整、物理按需** | 未访问的层不读入物理内存 |
| `--load-mode none` | ❌ 全部读入 | 反而更占 |
| **`--override-tensor <pat>=<buf>`** | ❌ 否 | **只改设备放置**（GPU/CPU/磁盘），不改加载量 |
| **`--fit-target <MiB>`** | ⚠️ 自动适配 | 较新功能 |

**⚠️ 对用户表述的修正**：「一部分放显存、内存一部分放磁盘，但**终归还是完整加载**」——

- 前半 ✅ **正确**（`--override-tensor` 确实按张量分派 GPU/CPU/磁盘）；
- 后半需澄清：**「完整加载」指**虚拟地址映射**完整，而物理内存是**按需的** ——
  mmap 把整个文件映射进虚拟空间，但**只有被访问的层会读入物理内存**。

**两个限制**：
1. **虚拟地址空间仍是全文件**（64 位无碍，32 位进程受限）；
2. **页缓存不可控**（可能被其他访问挤出或污染），**不如离线裁层确定**。

**→ 要「确定的物理裁层」仍须离线生成裁层 GGUF；mmap 只是「概率性的省内存」。**
这正是本项目采用 `cut_layers.py` 离线裁层的原因。

**⚠️ 主仓缺口**：`src/llama_engine.py` 目前**只暴露 `n_gpu_layers`**，
未暴露 `--override-tensor` / `--load-mode` / `--fit-target`（见 §1.1 的扩展手段清单）。

## 15. 真实内存占用与「积木式」切层（2026-09-16）

### 15.1 实测内存占用：整模 vs 层流水线

用 `measure_memory.py`（`psutil` 测 RSS，torch 测 CUDA）：

| 指标 | **整模 24 层** | **层流水线上游 4 层** | 降幅 |
| --- | ---: | ---: | ---: |
| 参数 | 1881.8 M | **737.4 M** | 2.55× |
| **加载时间** | **5.68 s** | **0.14 s** | **41×** |
| **RSS delta** | **7.87 GB** | **2.56 GB** | **3.1×** |
| **CUDA 占用** | **7.53 GB** | **1.475 GB** | **5.1×** |
| CUDA peak | 7.57 GB | 2.95 GB | 2.6× |

**★ 两个关键数字**：

1. **CUDA 占用 7.53 → 1.475 GB（5.1×）** —— 这是「能否装下」的直接答案；
2. **加载时间 5.68 → 0.14 s（41×）** —— 来自 `torch.device("meta")` + `to_empty()` + `assign=True`
   （避免随机初始化 737M 参数；初版不用 meta 时加载要 29 s）。

**⚠️ 速度说明**：层流水线**不提升单步速度** —— 表中 18.42 vs 59.97 ms 是
**工作量不同**（4 层 vs 24 层）所致，不是"加速"。同工作量下速度不变（§7.3 已证上游 97% 是计算）。

### 15.2 「积木式」切层：可行性核查（用户提问）

**问题**：能否离线自动生成单层 GGUF，再像拼积木一样按需加载？

**答：分三层看。**

| 能力 | 可行 | 证据 |
| --- | --- | --- |
| **离线生成任意层段 GGUF** | ✅ **可行** | `make_slice_gguf2.py` 切出 **L4-23（20 层）**，llama.cpp **成功加载并推理**（pp5 48.06 / tg4 12.44 t/s）|
| **单层 GGUF**（最细粒度） | ⚠️ **受阻** | 单层 L12 加载失败：`GGML_ASSERT(buffer) failed`（疑似 linear_attention 的 SSM 状态约束）|
| **运行时拼接多个 GGUF** | ❌ **不可行** | llama.cpp 只接受**单个** `-m`，无多模型组合接口 |

**⚠️ 切分不是「纯数据搬运」** —— 踩到 4 个架构约束：

1. **`<arch>.block_count`** 必须改为实际层数；
2. **`nextn_predict_layers`**（Qwen3.5 的 MTP 层数）**必须 < block_count**；
   切掉尾部 MTP 层（`blk.24`）时**必须置 0**，否则 `qwen35.cpp:17` 的
   `GGML_ASSERT(n_layer_nextn < n_layer_all)` 失败；
3. **`n_layer()` = `block_count − nextn`** 用于判定模型类型（`case 24/32/64`，否则 `LLM_TYPE_UNKNOWN`）；
4. **非 blk 张量**（`token_embd` / `output_norm` / `output`）**必须原样保留**，
   否则加载失败 —— **这也是单层「积木」仍有 1.15 GB 的原因**（`token_embd` 独占 ~1 GB）。

**KV 复制的三个坑**（`cut_layers.py` 已验证；`make_slice_gguf.py` 初版曾踩）：

- 必须跳过 **`general.architecture`** 与 **`GGUF.*`**（否则重复写入导致文件损坏）；
- KV 值用 **`field.contents()`** 取，按**原始类型** `add_key_value` 写回（不能用 `add_uint32` 等猜类型接口）；
- ARRAY 类型要带子类型。

**→ 结论**：

- **「按需生成任意层段」可行且已验证**（这是层流水线的基础设施）；
- **「运行时拼积木」不可行**，但可用「**按需生成不同切分**」替代；
- **单层粒度受架构约束**，实用粒度是**多层的层段**（如 4 / 8 / 20 层）。

## 16. `--override-tensor` 实测评估（2026-09-16，用户命题）

**用户命题**：`--override-tensor` 能做到什么？「想改就改」→ 直接变**定制化 llama 引擎**，符合 Koakuma 引擎定位。
**⚠️ 但需要实测性能提升，否则不如不改。**

### 16.1 能力（真实且精确）

CLI 形态：`-ot --override-tensor <tensor name pattern>=<buffer type>;...`

| 能力 | 说明 |
| --- | --- |
| **精确指定单个张量的设备** | `CPU` / `CUDA0` / `CUDA_Host` 等 |
| **按张量名正则匹配** | 如 `blk\.(0|1|2|3)\..*=CUDA0` |
| **完全替代 `n_gpu_layers`** | 从「前 N 层」升级为**白名单式**放置控制 |
| **层粒度异构放置** | 甚至可只把 `full_attention` 层（每 4 层 1 个）放 GPU |

### 16.2 实测：**它不是提速工具，而是容量旋钮**

下游 `qwen35-2b-q4km.gguf`，`-p 5 -n 24`：

| 配置 | pp5 (t/s) | **tg24 (t/s)** | 相对基线 |
| --- | ---: | ---: | ---: |
| **基线：全 offload（`-ngl 99`）** | 194.16 | **70.03** | — |
| `-ot token_embd.weight=CPU` | 157.87 | **49.88** | **−29%** |
| `-ot output.weight=CPU` | 181.74 | **63.40** | **−9%** |
| **基线：全 CPU（`-ngl 0`）** | — | **22.50** | — |
| **`-ngl 99` + 后 20 层全 CPU**（只前 4 层 GPU） | 58.87 | **19.59** | **比全 CPU 还慢 13%** ⚠️ |

### 16.3 ★ 两个反直觉结论

1. **把大张量赶到 CPU 会掉 9~29%** —— 换取的是显存（`token_embd` ~1 GB、`output` ~0.5 GB）；
2. **「只前 4 层 GPU」比「全 CPU」还慢（19.59 < 22.50）** ——
   **跨设备（PCIe）往返开销超过了 4 层的 GPU 加速收益**。
   这也解释了 `n_gpu_layers` 为何只做**前 N 层连续 offload**：减少跨设备往返次数。

### 16.4 ⚠️ 必须澄清：两种「切分」不是一回事

| 机制 | 跨什么 | 每步代价 | 适用 |
| --- | --- | --- | --- |
| **本项目 D→L 接力** | **跨进程** | 一次 **8 KB** 传输（便宜） | 层流水线（§14）|
| **`--override-tensor` 部分 offload** | **跨设备（PCIe）** | 20 层反复往返（贵） | 显存不足时的妥协 |

**→ 不能互相替代**；`--override-tensor` 的 partial-offload 模式**不适用于**层流水线。

### 16.5 结论（按用户标准裁定：**不改**）

- **用户标准**：「需要实测性能提升，否则不如不改」；
- **实测结论**：`--override-tensor` **无速度收益**，且部分 offload 情形下**为负**；
- **→ 不为「提速」改绑定**；若将来为「省显存」而改，须同时接受 **9~29% 的速度代价**；
- **⚠️ 旁证**：该能力在 `llama-cpp-python 0.3.35` 中**未暴露**，补齐需改上游 C 绑定
  （与既定 Policy 一致：贡献归对方、不提 PR）。
