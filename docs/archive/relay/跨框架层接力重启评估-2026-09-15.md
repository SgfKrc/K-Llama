## 0. 结论摘要

**结论：原"不推荐开工"结论已细分为两层：L→L 层接力已具备主仓架构接入条件；D→L 仍为可研究、未准入能力。** L→L 的 16/16 行为等价不等于 bitwise 数值一致，也不等于跨进程/网络生产可用。

三点变化：

1. **触发条件变化（用户裁决 2026-09-15）**：接受**自研 / fork 推理引擎**。§3.1 两个"强"障碍（无公开中间层 API、层间观测需自研补丁）**根源都是"不能改 llama.cpp"**；此项放宽后障碍等级下降，代价转为**维护成本**。
2. **上游实况变化（本次实查）**：llama.cpp 已存在 **4904 行 / 37 文件的完整 hidden-state 提取实现**（PR #27073，**含 HTTP server endpoint**），**未合并但已有人 cherry-pick 并在 Windows 上跑通**。§3.3 条件 4「出现成熟第三方实现可引用」**部分命中** —— 不必从零自研。
3. **不变的部分**：issue #27112 **仍 open**（条件 1 未命中）；**量化误差累积仍无公开测量**（本方向生死题）；**prompt cache 与 RPC backend 曾不兼容**（跨机缓存需单独验证）。

**仍然成立的关键判断**：实现"异构适配"的生产默认路径**不需要**跨框架接力 —— llama.cpp 自身覆盖 CPU/GPU，弱节点用 GGUF 即可；Relay 的价值是验证架构兼容和为 PC 研究保留 D→L 可能性，不改变 L/RPC 主路径。

**另需澄清的概念分层**（避免把三件事混为一谈）：

| 概念 | 含义 | 本项目态度 |
| --- | --- | --- |
| **A 层接力兼容（Relay R）** | 同一请求内以 hidden 边界连接连续层段；先 L→L，再 D→L | **L→L 已进主线架构轨道；D→L 短序列通过但长序列失败；PC-only、默认关闭** |
| **B 权重格式转换** | HF ↔ GGUF 互转（含逐层语义映射） | **单向已成熟**（`convert_hf_to_gguf.py`），异构适配的最低成本路径 |
| **C 混档调度** | 按节点能力把**整模型**分派给 L 档 / D 档 | **现行设计**，不需跨框架 |

### 7.1 环境与对象

| 项 | 值 |
| --- | --- |

### 7.2 关键结果：未量化路径**逐层精确一致**

| 精度 | 抽样层 | cosine（token-mean） | 两侧范数比 |
| --- | --- | --- | --- |
| **fp16（未量化）** | **0, 12, 20, 21, 22** | **1.000000**（全部） | **1.000** |
| Q4_K_M | 0, 12 | 0.9920 / 0.9927 / 0.9916 / 0.9908 / 0.9857 | ≈1.00 |

**结论一（本方向的核心答案）**：`layer 0–22` 在 fp16 下 `cosine = 1.000000` 且**范数一致到小数点后三位** —— 两侧对"层输出"的定义、token 聚合方式、数值尺度**完全一致**。**§3.2 步骤 2 判据（未量化 ≥ 0.999）PASS。**

**结论二**：Q4_K_M 引入 **0.7–1.4% 偏差**（0.986–0.993），即量化代价 —— 对应 §3.2 步骤 3。**跨框架接力的量化预算由此有了第一个实测量。**

### 7.3 末层（layer 23）异常：**已定位，未完全解释**

| 观测 | 值 |
| --- | --- |
| llama 侧 l23 范数 | 28.748（延续 l22=23.367 的平滑增长 → 正常） |
| torch 侧 `hs[24]` 范数 | **125.145**（自 `hs[23]=23.367` 跳变 5.4×） |
| `hs[23]` vs `hs[24]` | cosine **0.321** / ratio **5.356** |
| **`norm(hs[23])` vs `hs[24]`** | cosine **0.476** / ratio **1.457** → **不匹配** |

**已定位并解释**（读源码 + 实测双向确认）：

- **实测**：`hs[24]` 与 `base.last_hidden_state`、`base.hidden_states[-1]` 的 cosine = **1.000000**、范数比 **1.0000** → **`hs[24]` 就是文本模型输出的 `last_hidden_state`**。
- **源码**（`transformers/models/qwen3_5/modeling_qwen3_5.py:1288-1307`）：

```python
        hidden_states = inputs_embeds
        for i, decoder_layer in enumerate(self.layers[: self.config.num_hidden_layers]):
            hidden_states = decoder_layer(hidden_states, ...)
        hidden_states = self.norm(hidden_states)      # final RMSNorm
        return Qwen3_5ModelOutputWithPast(last_hidden_state=hidden_states, ...)
```

**结论：两侧差的不是"语义"，而是 final RMSNorm 做在哪一侧。**

- **llama.cpp**：`t_hidden_layers.push_back(cur)` 位于**层循环内部** → 得到**未 norm 的层输出**（28.748）；
- **HF**：`last_hidden_state` 只在 `self.norm(...)` **之后**暴露 → 给出 **norm 后**的值（125.145）。

量级吻合：`125.145 / 28.748 = 4.35`，即该 final norm 权重对输出的放大倍数。

**一处已纠正的误判（诚实记录）**：本文早期版本据 `norm(hs[23])` 与 `hs[24]` 的 cosine 0.476，判断"不是 final RMSNorm"。**该对照选错了输入** —— `hs[23]` 是**第 23 层**输出，而 `hs[24]` 是**第 24 层**输出再 norm，本非同一层。结论现已由源码确证。

**可操作规避**：跨界传 **`0 .. n_layers-2`**；若必须用最后一层，需在 llama 侧补 final norm，或让 HF 侧暴露 norm 前的值（当前未暴露）。

### 7.3.1 这**不**意味着什么（重要）

本 PoC 验证的是**跨框架 hidden 的数值一致性** —— "两侧对同一层输出是否算同一个量"。**这是层间拆分的必要条件，不是充分条件。**

**已确立**：hidden 语义一致（fp16 逐层 cosine = 1.000000）；量化代价已有实测（Q4_K_M 0.7–1.4%）。

**仍未验证（因此不能据本 PoC 宣布"llama 层间拆分推理流水线可行"）**：

1. ~~**反向能力（注入）**~~ → **已验证可行（2026-09-16，见 §7.8）**：`llama_batch.embd` **接受任意 `n_embd` 向量**（头文件仅要求"float vector of size n_embd"，**不校验来源**）。实测把 5×2048 的**随机噪声**注入 `qwen35-2b`，`llama_decode` 返回 **0**、logits 非零 → **前向正常完成**。**故"把外部 hidden 写回并续算"在接口层面成立。** 新增的剩余缺口见 §7.8 第 ③ 项。
2. **跨节点传输开销** —— decode 每跳 hidden 约 4KB/token（估算），**每步同步的实际延迟未测**；
3. **调度与图重建** —— `llama-context.cpp:1241` 注释已提示"t_hidden_layers output tensors → the scheduler must re-reserve compute"，**多节点下的实际代价未测**；
4. **误差累积** —— Q4_K_M 的 0.7–1.4% 偏差在**多层多跳**下是否放大，未测；
5. **异构算力** —— 两端性能不对称（§7.1 与硬件评估）对流水线吞吐的影响未测。

**已可排除的**：该方向**不存在"两侧算的不是同一个量"这一根本性障碍** —— 这曾是本方向最硬的技术疑问。

### 7.6 对上游代码的两处改动（**仅在实验目录内**）

### 7.9 裁层实验：剪掉前 4 层后仍能加载并注入（2026-09-16）

**动机**：§7.8 表格第 ③ 项 —— "让模型从第 k 层开始"。llama.cpp 无跳层选项，故 B 侧只能靠裁 GGUF。

**做法**（`build/cross-framework-layer-poc/cut_layers.py`，gitignored 不入库）：读入 `qwen35-2b-f16.gguf`（`block_count=25`、335 张量），保留 `blk.4..blk.24` 并重命名为 `blk.0..blk.20`，非 blk 张量（`token_embd` / `output_norm` / `output`）原样保留，KV 全量复制、仅改 `qwen35.block_count: 25 → 21`；产出 282 张量、41 个 KV。

**判据与结果**（`llama-embd-inject-test`，5×2048 随机噪声注入）：

```
llama_model_loader: loaded meta data with 42 key-value pairs and 282 tensors ...
print_info: n_embd_inp            = 2048
print_info: n_layer               = 20      n_layer_all           = 21
[6c] inject 向量已写入 batch.embd，准备 decode
[decode] rc=0
[logits] 末 token 前 10 项 |和| = 60.003920
PASS: embd 通道接受了注入向量，前向正常完成
```

**结论**：**③ 项成立** —— 裁层 GGUF 被 llama.cpp 当作"层数更少的模型"正常加载与前向，注入通道依旧可用。**① ② ③ 三项已在接口与模型形态层面闭环。**

**三条限制（先讲清）**：

1. **层号映射**：裁层后 llama.cpp 报 `n_layer=20 / n_layer_all=21` —— 它把最后一个 block 视作 MTP 层（`nextn_predict_layers=1` 被原样保留）。故裁层模型 `layer i` ↔ 原模型 `layer i+4`，跨节点传 hidden 时**必须带偏移**。
2. **状态起点**：裁层模型的 KV cache / recurrent state（qwen35 为混合 SSM+attention）**从裁剪边界起算**，A 侧历史状态不在 B 侧。单请求逐层接力不受影响（每步位置一致），但"两端各自缓存"的形态需另行设计。
3. **tokenizer 全量保留**：与"换模型"不同，裁层仍带 24.8 万 token 词表 —— 这不是优化，只是满足加载。

**踩坑（gguf-py 写入）**：

- `GGUFWriter.add_array()` **只有 2 个参数**（无子类型）；数组 KV 须走 `add_key_value(name, val, ARRAY, sub_type)`；
- 必须**跳过 `GGUF.version` / `GGUF.tensor_count` / `GGUF.kv_count`**（reader 会把这三个头部字段也列进 `fields`），否则写出重复字段 → `KeyError: Duplicate GGUF.version already in list`；
- 运行实验二进制时要把 **ucrt64 置于 PATH 最前** —— `/mingw64/bin` 在前的 DLL 会让进程直接 `exit 127` 且**无任何输出**，极易误判成"命令不存在"。

**④ 类四项**中，**误差累积已获首批实测**（见 §7.10）；传输/同步开销、调度与图重建、异构算力仍未测 —— 见 §7.3.1 与 §7.7。

### 7.10 接力一致性对拍：行为等价、数值有累积（2026-09-16）

**动机**：§7.9 只证明"接口通"。本实验把它推进到**数值与行为层面** —— 接力路径的输出与整模型直接前向是否一致。

**工具**（均在本机实验目录内，gitignored 不入库）：

- `llama-relay-check`（`llama.cpp/tools/hs-extract-batch/relay-check.cpp`，新增）—— 同一模型两条路径产 logits：`--tokens`（对照 C）/ `--embd`（接力 B）；支持 `--dump`、`--dump-all`（逐位置）、`--threads`、`--n-ubatch`；
- `relay_compare.py`（单点对拍）、`compare_all.py`（逐位置对拍）、`emb_from_gguf.py`（从 GGUF 取 token embedding，用于"通道 vs 模型"的分离对照）。

**设置**：prompt `The capital of France is`（llama tokenize = 5 tokens：`760 6511 314 9338 369`）；A 侧 = 原模型 `hs-extract-batch --raw` 取 **layer 3** 输出；B 侧 = 裁层模型（K=4，§7.9）注入该 hidden；C 侧 = 原模型 token 路径。

**结果 1｜层映射正确**：分别注入 layer 2 / 3 / 4 的 hidden，与 C 的末位置 logits cosine = **0.9605 / 0.9972 / 0.9836** —— **layer 3 单峰最优**，与 §7.4 的映射一致（"llama layer 3 的输出"正是裁层模型的起点输入）。

**结果 2｜逐位置对拍**（`--dump-all`，两路径逐位置 logits 对比）：

| 位置 | cosine | argmax |
| --- | --- | --- |
| 0 | **1.000000** | 一致 |
| 1 | 0.998781 | 一致 |
| 2 | 0.996687 | 一致 |
| 3 | 0.997822 | 一致 |
| 4 | 0.995525 | 一致 |

**argmax 5/5 一致**；偏差从位置 0 的"打印精度内为 0"随位置累积到 ~5e-3（cosine 0.9955），形态与"SSM 递推放大微小实现差异"一致 —— 这正是 §7.3.1 第 4 项（误差累积）此前缺失的第一批数据。

**结果 3｜抖动定位在 `embd` 通道，不在接力**：同一输入重复运行的抖动（cosine 0.991–0.998）**同样出现在"整模型 + 注入 token embedding"上**（不经裁层、不走接力）；而 **token 路径两次运行完全一致**（cosine ≈ 1.000000）。已逐项排除：线程数（`--threads 1` 照抖）、ubatch 大小（`--n-ubatch 8` 照抖）、cut 文件完整性（裁层模型加载无 missing tensor；末层张量被判 unused，且**原模型对 blk.24（MTP 层）的行为完全相同**）。**结论：`llama_batch.embd` 路径在本构建（CPU / MinGW / 当前 commit）上非确定**，其量级（~1e-3 至 ~1e-2）覆盖了"接力 vs 直接"的差异。

**判定（按"架构兼容"口径）**：

- **行为等价 ✅**：逐位置 argmax 全一致（贪心生成路径不会分叉），top-10 高度重合；
- **数值等价 ❌（限本构建）**：差异与 `embd` 通道自身抖动同阶，**不能据此宣称"数值上等价于直接前向"**；要拿到数值等价，需要先消除 `embd` 路径的非确定性（f32 权重对照 / 上游 issue / GPU 后端复验）。

**踩坑**：`--dump-all` 是开关，路径必须写成 `--dump <file> --dump-all`（写成 `--dump-all <file>` 会被当作位置参数拒绝）。

**未测**：f32 权重下的累积曲线；跨框架（torch → llama.cpp）逐位置对拍；逐 token 接力（需要 A/B 双侧交互，本机工具尚不支持）。

### 7.11 逐 token 接力一致性 + `embd` 非确定性判定（2026-09-16）

本轮把 §7.10 留下的两个悬而未决问题做完；新增两个工具（均 gitignored 不入库）：`llama-relay-gen`（逐 token 接力）与 `relay-repeat`（非确定性探针）。

#### 7.11.1 逐 token 接力：**16/16 步与整模型完全一致（PASS）**

**工具**：`llama-relay-gen`（`build/cross-framework-layer-poc/llama.cpp/tools/hs-extract-batch/relay-gen.cpp`）—— 单进程加载两个模型：A = 整模型，B = 裁层模型（K=4）。

- **baseline**：整模型 token 路径增量贪心；
- **relay**：每步 A 取 `llama_get_hidden_state(ctx, 3)`（layer 3 输出、全位置）→ 用 `llama_batch.embd` 注入 B → 末位置 argmax → 追加 token 进入下一步。这就是真实的"逐 token 双向接力"形态：**每个新 token 都要回到 A 算 layer 0..3**。

**结果**（prompt `The capital of France is`，`--gen 16`，`--threads 4`）：

```
baseline (16): 11751 13 198 32 13 2912 198 33 13 3439 271 248068 198 90700 8340 25
relay    (16): 11751 13 198 32 13 2912 198 33 13 3439 271 248068 198 90700 8340 25
RESULT: 全部 16 步一致（relay == baseline）
```

**r1 / r2 / r3 三次独立运行逐项相同，未分叉、未 OOM**（`out/relay-gen-r{1,2,3}.log`）。

**判定**：**层间接力在"行为层"闭环** —— 逐 token 生成路径不会偏离整模型。配合 §7.10 的逐位置对拍（argmax 5/5 一致），"接力可用性"已不依赖任何未验证假设。

**复现**：`bash build/cross-framework-layer-poc/run-relay-gen.sh`（cmake + make + 跑 3 次）。

#### 7.11.2 `embd` 非确定性：**进程内固有**（"跨进程才抖"的假设被证伪）

**探针**：`build/embd-nondet/relay-repeat.cpp`（4 模式 + 一条 `tokenheap` 对照）。

| 模式 | 含义 | 结果 |
| --- | --- | --- |
| `repeat` | 同进程、同 context、清 memory 后重复 6 次 | **两两 bitwise 全不等**；cosine 0.984–0.9999 |
| `twocontext` | 同进程内两个 context 各一次 | cosine 0.98851898 |
| `tokens` | token 路径（对照） | **bitwise YES，cosine = 1.0** |
| `tokenheap` | token 路径 + 堆扰动（对照） | **bitwise YES** |
| 跨进程 | 同一命令独立跑 3 个进程 | pairwise cosine 0.9946–0.9971，bitwise 全 False |

**argmax 在以上全部情形下稳定为 11751。**

**判定**：

- **非确定性是 `embd` 注入路径单进程内固有的** —— "进程内稳定、跨进程才抖"的假设**被证伪**；
- `heap` 扰动**未能**独立坐实"未初始化内存被读"（`repeat` 本身就抖且幅度相当，无法分离）；但 `tokenheap` 证明堆扰动对确定路径无害。

**保留的结构线索（未坐实，供上游定位）**：embd 模式下 `build_inp_embd`（`llama-graph.cpp:2280-2367`）**仍把未选中的 token 分支 `ggml_get_rows(tok_embd, inp->tokens)` 展开进图**，而 `inp->tokens` 在该模式下从不被 `set_input` 写入；CPU 后端按 `GGML_TENSOR_FLAG_COMPUTE` 跳过其计算（`ggml-cpu.c:3101`），但**调度器不按该 flag 过滤**（该节点仍参与 buffer 分配与 liveness 复用）；且 `ubatch_reserve` 按 **token 拓扑**预留图（`llama-batch.cpp:393,417`）而实跑按 **embd 拓扑**重建（`llama-context.cpp:1402`）。

#### 7.11.3 对工程的结论（2026-09-16 晚 **重写**）

> **前提已变更**：本节原结论建立在"`embd` 路径固有非确定性"之上。上游在 **issue #28963** 给出根因 ——
> **`llama_batch_allocr::ubatch_add` 对调用方 `pos` 数组的堆越界读**（M-RoPE 模型 + `embd` 批次读

> **cosine min = 1.000000**，**L→L 141 步接力与 D→L prefill 均 141/141**。
> 故 §7.11.2 的"非确定性"定位与本小节第 1、3 条原文**作废**。

1. **判据**：接力判定用**逐 token argmax / 生成序列一致**（`judge_relay_generation`，`src/relay_contract.py`），不用 cosine 阈值；**`top_k_tolerant_argmax` 只作诊断档**，不再作为准入依据（修复后严格判据已可达）；

**未测**：跨框架逐 token 生成接力、跨进程实时 IPC/网络 handoff、采样（temperature/top-p）矩阵、故障后状态清理与回退。

### 7.12 D→L 同机文件边界验证：短序列通过，长序列拒绝（2026-09-16）

**范围**：Qwen3.5-2B，裁切边界 `K=4`。PyTorch eager float32 导出 layer 3 的 hidden（`float32_le`），完整 llama.cpp token 路径产生对照 logits，裁层 llama.cpp 独立进程从该 hidden 文件续算。三者通过文件交接，因而覆盖了**同机跨进程的静态 prefill 边界**；它不是网络传输，也不是逐 token 生成接力。

| 权重/长度 | 逐位置 argmax | 首个分歧 | 诊断 | 判定 |
| --- | --- | --- | --- | --- |
| f16，5 token | 5/5 | 无 | cosine mean 0.997525；bitwise 否；top-10 8–10/10 | 仅该小样本通过 |
| f16，141 token | 132/141 | 18 | 分歧位 `18,22,32,33,38,54,58,64,79`；cosine mean 0.973769 | 拒绝 |
| 全 f32 GGUF，141 token | 128/141 | 14 | 分歧位 `14,21,24,32,33,38,54,58,64,67,79,82,140`；cosine mean 0.975004 | 拒绝 |

完整 f32 llama.cpp 对照与 PyTorch 末位 logits 的 cosine 为 `0.999999881`、argmax 相同、top-10 `10/10`；而 f32 D→L 接力末位 cosine 降至 `0.911730`，argmax 从 `10041` 变为 `42500`。因此不能把失败归因于 GGUF f16 量化：**仅传递 hidden 的 D→L prefill 尚未保住长上下文的行为等价**。位置、cache/循环状态与 `embd` 图路径均仍是待分离变量，本轮不作单一根因断言。

新增主仓判定器 `scripts/llama_relay_xframe_probe.py` 流式读取两份 raw `float32_le` logits，复用 `judge_relay_generation(...)` 的逐位置 argmax 判据，记录 SHA256、bitwise、cosine 与 top-k 诊断。三份可复算报告保存在 `local_docs/CORE-RELAY-XFRAME-01-dl-*-2026-09-16.json`；其中通过证据不改变 `admit_relay_xframe(...)` 的 fail-closed 生产门。

`llama-relay-check` 对一次性 `embd` 注入要求 `n_batch >= n_tokens`；141-token f32 路径使用 `--n-ubatch 141` 成功运行，`--n-ubatch 16` 会触发该运行器的 batch 断言，不能被误记为模型或行为结果。

### 7.13 `CORE-RELAY-XFRAME-01` 收口（2026-09-16 晚）

> 本节是该票的**收口结论**：**实验轨道收口，生产准入按 fail-closed 保持关闭**。
> §7.12 及本文其余"长序列拒绝 / `embd` 非确定性"表述**均已被本节取代**（其读数源自上游 #28963 的 `pos` 越界读）。

#### 7.13.1 根因（上游给出 + 本仓库独立复现）

`llama_batch_allocr::ubatch_add` 在 **M-RoPE 模型 + `embd` 批次**时读 `batch.pos[0 .. n_pos_per_embd*n_tokens)`，
而 `llama_batch_init` 只分配 `n_tokens` 个 `pos` → **调用方 `pos` 数组的堆越界读**
（上游 valgrind 实证；上游 issue **#28963**，本情形对应 **#28902**，与 `pos == NULL` 的 **#28910** 是孪生）。
**调用方修法**：`embd` 批次的 `pos` 按 `n_pos_per_embd * n_tokens` 分配、每段填 `pos[j*n+i] = i`。

**触发条件（实测）**：需**同时**满足 ① 走 `embd` 批次（token 路径永不触发）② `n_pos_per_embd > 1`（M-RoPE）。
四组对照：`qwen35`（`sections=[11,11,10,0]` → 4 段）**不做修复即触发**（`identical=False`，maxabsdiff 0.959）；
`Qwen-1.8B`（`arch=qwen`，无 `sections` 键 → 1 段）**不做修复也不触发**（`identical=True`）。
→ **主线（L 档单机推理 / TUI / RPC 分片）走 token 路径，任何模型都不受影响。**

#### 7.13.3 跨机部署要点（已实测，供后续复用）

1. **远端依赖**：Surface 无 MSYS2 → 需随 exe 复制 `libgomp-1.dll` / `libstdc++-6.dll` / `libgcc_s_seh-1.dll` / `libwinpthread-1.dll`；
2. **常驻方式**：Windows OpenSSH 会在会话结束时终止 `start /b` 的子进程 → 改用 `powershell Start-Process`，或"远端前台 + 本机后台 ssh"；注意 `Start-Process` 的 `-RedirectStandardOutput` 与 `-WindowStyle` **不能同时用**；
3. **时序**：bridge 启动后需等 runner 打印 `[ready]`（加载 3.4G 裁层模型约 30–60 s）才能连接，否则首帧即被关闭（`connection_closed_mid_frame`）；
4. **资产分发**：Surface 无代理，`git pull` 不可用 → 用 `scp` 直传（3.4G 模型实测 4m38s）；主仓已有 `RemoteAssetSyncPlan`（`scripts/llama_pc_rpc.py`）可把这一步自动化。

#### 7.13.4 未证 / 未做（**生产准入的必要缺口**）

1. **长时运行（soak）** —— 未做；
2. **更大模型容量收益** —— 当前仅 2B，且跨机 B 侧为 CPU，**无吞吐收益数据**（不宣称）；
3. **远端资产分发自动化** —— `RemoteAssetSyncPlan` 已有基础，但**未接入 relay 链路**；
4. **生产接线** —— 主仓引擎侧未接入（`CORE-RELAY-01` 记为"生产接线后置"）；
5. **多跳 / 3+ 节点** 层接力 —— 未测；
6. **采样的正式形态**（"只由 B 侧采样"）—— 判据与工具未实现，当前仅用 `T=0`。

#### 7.13.5 准入条件（放开的必要条件）

`admit_relay_xframe(...)` **继续 fail-closed**。要放开至少需要：

- **技术前提**：① 上游**库侧**修复（单段位置广播 / header 语义扩展），或明确采用"调用方 `pos` 契约"并写入接入文档；② 覆盖 §7.13.4 的 1–3 与 5；
- **纪律前提**：③ Relay **默认关闭、显式开启**不变；④ 只允许 **`temperature=0, top_p=1`**，或实现"**单侧 RNG**"采样形态（§7.13.2 #5）；⑤ **不替代 RPC** —— Relay 解决 hidden 边界兼容，RPC 解决部分驻留。

#### 7.13.6 本票结论

**实验轨道收口**：该票的**验证目标已达成** —— D→L 在 **prefill、逐步生成（同机 + 跨机）、f32、采样矩阵**
四个正交维度上均取得**可复算的等价证据**，根因定案为上游 **#28963** 并已独立验证修复；
**生产准入不放开**：缺口见 §7.13.4，门保持 fail-closed（§7.13.5）。

### 7.14 性能实测收口（2026-09-16 晚，回填 §6 / §7.1 的性能未测项）

§6 与 §7.1 曾把「**异构算力 —— 两端性能不对称对流水线吞吐的影响**」列为未测项。本节补齐。

**实测**（本机 RTX 4060 Laptop 8GB，prompt=5，gen=64，下游 f16 裁层，**全程 64/64 argmax 一致**）：

| # | 配置 | 端到端 | 关键点 |
| ---: | --- | ---: | --- |
| 1 | 跨进程 + 每步全段重算 | 182 s | 起点 |
| 2 | 同进程双后端 + 全段重算 | 167 s | 消除进程边界**仅 8%** |
| 3 | + 双侧 **KV 复用** | 53 s | **3.4×** |
| **4** | **+ 上游只跑前 4 层（手动前向）** | **21.3 s** | **总计 8.5×** |
| 5 | 跨进程 + 4L + 下游 GPU offload | 81 s | 受跨进程 IPC 拖累 |

**★ 对「异构算力不对称」的直接回答**：

- **上游 torch-GPU 9.2 ms/层 ≈ 下游 llama.cpp-CPU 8.3 ms/层** → **两端性能并不不对称**；
- 根因：**batch=1 是 memory-bound** —— 决定速度的是「搬运多少字节」，不是「CPU 还是 GPU」；
- **故 §6 该未测项的实测结论是：异构算力不对称对流水线吞吐的影响很小。**

**其他被回答的未测项**：

| 原未测项 | 实测结论 |
| --- | --- |
| 传输/同步开销 | **同进程内 ≈ 0.34%**；但**跨进程在两侧都优化后反成主导**（同配置 21.3 s vs 81 s）|
| 精度对性能的影响 | f16/bf16 **反而慢 8.4–8.7×**；NF4 只慢 1.09× 但**亦无速度收益**（延迟受限，非带宽受限）|

**★ 与 §7.13.6 收口结论的关系**：
§7.13.6 的**正确性**结论不变（生产门保持关闭）；本节补充**性能维度**：
接力在单序列上**不具备性能优势**（最优 333 ms/步 vs llama.cpp 原生整模 GPU **13.5 ms/步**，差 **≈25×**）。⚠️ 口径注（2026-09-19 核）：参照不唯一 —— 按 `13.5 ms/步` 算 **≈25×**（`333 ÷ 13.5 = 24.7`），按 `-ngl 24` 的 `26.6 ms/token` 算 **12.5×**；参照谱与算式见 [跨框架层接力-实验数据汇总](跨框架层接力-实验数据汇总.md) §F/§H。
**定位为「能力组合」而非「提速」**。

**证据**：[跨框架接力性能优化-汇总报告](跨框架接力性能优化-汇总报告-2026-09-16.md)、
