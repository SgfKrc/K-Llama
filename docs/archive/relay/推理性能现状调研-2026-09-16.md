## 1. KV cache / 分页现状（D 档 PyTorch）

### 1.1 是真分页结构，不是"名字带 paged"

`src/paged_kv_cache.py`(1088 行) 确有块表与页池：

| 结构 | 位置 |
| --- | --- |
| `KVPage` 页对象 | `:46-67` |
| `page_table: List[int]`（逻辑 token → 物理页 id） | `:188` |
| 页池 `free_pages` / `allocated_pages` | `:191-192` |
| 分配 / 写入 `_allocate_page` / `append_kv` / `append_kv_single` | `:490-548` / `:564` / `:630` |
| 读取 `get_all_kv` / `get_kv_window` | `:680` / `:741` |
| 回收 `truncate` / `clear` | `:859` / `:923` |
| 两级缓存冷层 `ColdPageRecord` | `:70-80`，`:329/387/426` |

### 1.2 但三个致命限制

1. **物化回连续张量**：`get_all_kv()` 把分散页切片后 `torch.cat` 成连续张量（`:736-738`）—— **这正是 PagedAttention 要消除的动作**；
2. **逻辑→物理仅支持顺序追加**：`truncate` 依赖"当前页是分配序列尾页"，否则报错（`:906-908`）；**不支持非连续/乱序块写入**；
3. **块表从未进入算子**：attention 拿到的仍是连续 KV。

### 1.3 服务哪一档

- **D 档独占**：`api_server.py:413` 注释 `PagedKVCache is D-tier (torch) only`；`api_server.py:1928-1930` 明确 L 档（无 torch）不用；
- **L 档（llama.cpp/GGUF）主仓生产路径无 KV 复用开关**：`src/llama_engine.py:1210-1220` 的 `reset_kv_cache()` 是 **no-op**；全仓 grep `cache_prompt|prompt_cache|--prompt-cache|n_cache_reuse` 在 `src/` 下**零命中**；
- llama.cpp 的开关本身存在，但只在 vendored 上游（`android/app/src/main/cpp/llama.cpp/common/arg.cpp:3155-3167` 等）与外置 `harness_workbench/adapters/llama_server.py:113`。

### 1.4 已接线 vs 仅组件级

**已接线（仅生命周期/可观测层）**：`api_server._init_kv_cache`(`:1922-1968`)、`engine_host._init_kv_cache`(`:2651-2689`)、`KVHost`(`kv_host.py:31-140`)、`/v1/kv/init`、`/v1/status.kv_cache`。

**仅组件级（生产无调用者）**：`append_kv` / `append_kv_single` / `get_all_kv` / `get_kv_window` / `truncate` 全部**无生产调用者**；`cache_unit_layout` 的 `match_cached_prefix` 同。
❗ 关键旁证：`api_server.py:2628` 自承「单机模式下 `model.generate()` 使用内置 KV 缓存，PagedKVCache 未接入」，而 `/api/status` 的 `kv_stats` 是**按 token 数估算的伪统计**（`:2627-2653`）。

### 1.5 距真正 PagedAttention 的差距

1. 无 paged attention kernel（块表不进算子）；
2. 无任意块映射（只能顺序追加 + 尾回滚）；
3. 无跨请求块共享 / 引用计数 / CoW；
4. 无调度器集成（`scheduler.py:1074` 的 `_kv_cache` 只是 `task_id → past_key_values` 字典，与 `PagedKVCache` 无关）；
5. 无跨进程持久化（冷层按 `session-{uuid}` 隔离，`paged_kv_cache.py:167-170` 明确不承诺跨进程恢复）；
6. 无真实命中率度量（基于合成 token id）；
7. L 档完全另一套机制，**两套不可互推**。

## 2. 量化现状（★ 回答核心问题）

### 2.1 一句话判定

> **PyTorch 侧量化（bitsandbytes NF4 / llm.int8）与 GGUF 的 Q4_K_M 不是一回事，也不能互相替代或对拍。**

### 2.2 PyTorch 侧：bitsandbytes，加载时在线量化，**只支持 CUDA**

唯一构造点 `src/model_module.py:318-343` `_get_bnb_config()`：

- `int4` → `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16, bnb_4bit_use_double_quant=True, bnb_4bit_quant_type="nf4")`（`:329-334`）→ **是 NF4，不是朴素 INT4**；
- `int8` → `BitsAndBytesConfig(load_in_8bit=True, llm_int8_threshold=10.0, ...)`（`:336-341`）→ llm.int8；
- `fp16` → 返回 `None`（不量化）。

应用点 `src/model_module.py:1936-1952`（CUDA 路径 `quantization_config=bnb_config`）。
**全仓仅此一处**，没有自研 4-bit kernel、没有 `Linear4bit` 手写替换。

### 2.3 GGUF 侧：QLH 只"选文件 + 贴标签"，不参与计算

- `src/llama_engine.py:46-52` `QUANT_FILES` 是**文件名映射**；`:168-173` 按文件名反推 `_quant_type`（找不到就填 `"GGUF"`），仅用于日志/展示（`:184`）；
- 真正加载 `:191-198` `Llama(model_path=..., n_ctx=..., n_threads=..., verbose=False)` —— **无任何量化参数**；
- `src/model_module.py:1695-1741` `_load_llama_cpp()` **不接收 `quant_type`**；
- `src/api_server.py:6455-6467` `_normalize_quant_for_engine`：`llama_cpp` 直接 `return raw or "gguf"`（`:6458-6459`）—— 原样透传/忽略。

### 2.4 对比表

| 维度 | PyTorch NF4 4-bit | PyTorch int8 | GGUF Q4_K_M |
| --- | --- | --- | --- |
| 算法 | 正态分位构造 16 个非均匀码值 | llm.int8：逐通道 int8 + 离群 fp16 | k-quant 块/超块 scale+min 整数块量化 |
| 数值格式 | 4-bit 码本 + double-quant scale，compute 在 FP16 | int8 权重 + FP16 离群 | ~4.9 bpw，固化在 .gguf 文件头 |
| 运行时 | CUDA + **bitsandbytes GPU kernel**（**无 CPU 实现**） | CUDA + bitsandbytes | ggml：CPU/集显/Metal/Android，运行时反量化 |
| 由谁实现 | QLH 调 bnb（`model_module.py:318-343`） | 同上 | llama.cpp 工具链，QLH 只选文件 |
| 生成时机 | **加载时在线量化** | 加载时在线 | **离线预量化** |
| 可比/可对拍 | — | — | **不可**（不同数值栈；docs 明确 hidden 不可混用） |

`docs/archive/runtime/2bit与4bit量化调研与实施计划.md:85-90` 亦明确二者是**两条并列对照线**（`PyTorch: FP16↔NF4`、`GGUF: F16↔Q4_K_M↔IQ2`），`:104,224` 警告 hidden state 不能混用。

### 2.5 `--quant` 传递链（TUI → 引擎）

```
TUI /quant <int4|int8|fp16|gguf>            src/tui_admin.py:2218；cmd_quant :1842-1853
  → POST /models/switch {model_id,quant_type,engine}
  → LoadModelRequest.quant_type（默认 "int4"）  src/api_server.py:885-893
  → load_model                                src/api_server.py:2861-2914（cfg.QUANT_TYPE :2890）
  → _normalize_quant_for_engine               src/api_server.py:6455-6467
      pytorch: 仅接受 fp16/int8/int4，否则 400（:6465-6466）
      llama_cpp: 透传原值/“gguf”（:6458-6459）  ← 量化参数在此失效
  → 引擎分发                                   src/model_module.py:642-650
      llama_cpp → _load_llama_cpp()（丢弃 quant）
      否则     → _load_pytorch(path, quant_type, profile) :650
  → 落点                                       src/model_module.py:1936-1952
```

### 2.6 实测数字（仓库自留，非独立复现）

- **PyTorch（Qwen-1.8B / RTX / PyTorch 2.12 / 50-token）**：`README.md:907-910`、`src/config.py:6-10`
  fp16 **3.47 GB / 53.2 tok/s**；int8 **2.30 GB / 9.8 tok/s**；int4 **1.75 GB / 28.7 tok/s**
  ❗ **int8 反而比 int4 慢**（9.8 vs 28.7），说明 bnb kernel 行为强依赖 GPU/版本；
  且 `src/api_server.py:2296` 把 `speed_map = {"fp16":53,"int8":10,"int4":29}` **硬编码**。
- **GGUF Q4_K_M**：`README.md:918-919` ~**1.2 GB / ~12 tok/s**。
- **内存估算**用经验系数：`src/graph_orchestrator.py:114` `fp16=1.0, int8=0.55, int4=0.35`。

### 2.7 量化缺口

1. **torch 侧无真正 4-bit kernel**，完全依赖第三方 bnb，且**只支持 CUDA**；
2. **CPU 路径无量化**：`src/model_module.py:1907-1921` 在无 CUDA 时警告"bnb 不支持 CPU"并**强制回退 fp32**（`:1921`）；
3. **无法与 GGUF 对齐**：无 NF4↔Q4_K_M 数值/质量对照工具；
4. **GGUF 侧 quant 只是标签**：传 `Q4_K_M` 不改变任何计算；
5. **无 2-bit/3-bit**，docs 明确禁止加 `int2` 做"伪支持"。

## 6. 未核实 / 存疑项（诚实标注）

1. **warmup / 预热**：子 agent 的 grep 对该 pattern 反复返回异常去重结果，**未取得有效命中**，故**未下"无实现"断言**；

3. **Relay / RPC 在 `llama_engine` 解码循环中的实际接线深度**：仅确认实现存在，**未逐行核对**；
4. **llama.cpp 当前 GPU offload 层数**：未核实（影响 §5 第 6 项的收益判断）；
5. 本文所有实测数字均为**仓库自留**，**本次未独立复现任何基准**；
6. 第三份调研（算子融合/加速）被 host 标记 `partial`：AC4（投机解码）缺少 host receipt 支撑，结论以 `speculative.py` 的 `StubDraftModel` / `SPEC_ENABLED` 默认值为准。
