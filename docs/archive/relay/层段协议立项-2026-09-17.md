## 0. 定位：取消「兜底」这一概念

**原表述**（路线 A「Silica 式」= **兜底方案**）**被用户否决**，理由与结论：

- Silica 式**只能借算力**，**不能做容量合并**（见 [调研](Silica式分片方案调研-2026-09-17.md) 的代码级证据：
  full-offload = 整模上传；切分 = 全局 `-ngl` + 比例 `--tensor-split`）；
- 因此**不存在**「主路径 vs 兜底」的对立 —— 它是**同一个层流水线里的另一种节点**。

**新定位**：

> **「借算力」= 层流水线中的一种节点类型（`remote_rpc`），与本地节点、跨框架节点同构。**
> **三者共用一个抽象：`(layer_range, engine, location)`。**

## 1. ★ 统一节点抽象（本文档的核心新增）

### 1.1 三种节点，同一契约

| `kind` | 含义 | 例子 | 引擎 | 通信 |
| --- | --- | --- | --- | --- |
| **`local`** | 本机进程内的层段 | 本机 GPU 上的 L0-3 | llama.cpp / pytorch | 进程内 |
| **`remote_rpc`** | **借来的算力**（原「Silica 式兜底」）| Android/PC 上的 `ggml-rpc-server` | llama.cpp | 网络（ggml RPC）|
| **`cross_framework`** | 跨引擎的层段接力 | torch 上游 + llama.cpp 下游 | **两种** | 进程内或 stdio（§13/§14 已验证）|

**三者都能回答同一组问题**：**「你持有哪些层」+「你用什么引擎」+「你在哪」+「你的容量多大」。**

### 1.2 抽象数据结构（拟）

```python
@dataclass(frozen=True)
class PipelineNode:
    node_id: str
    kind: Literal["local", "remote_rpc", "cross_framework"]
    layer_range: tuple[int, int]        # [start, end) 半开区间
    engine: Literal["llama.cpp", "pytorch"]
    location: str                       # "local" 或 "host:port"
    capacity: PipelineNodeCapacity      # 见 pipeline_capacity.py
    artifact: PipelineArtifactRef       # GGUF / safetensors 片段（见 §2）
```

**`PipelineNode` 是**新增**的；它把既有模块的产物**串起来**，不替代它们：
`pipeline_capacity.solve_pipeline_capacity` 负责容量求解 →
`pipeline_assignment_manifest.build_assignment_manifest` 负责每节点清单 →
`relay_contract.RelayTrimPlan` 负责跨引擎侧的层索引映射。

### 1.3 与既有实现的映射（**避免重复设计**）

| 需求 | 既有实现 | 缺口 |
| --- | --- | --- |
| **层段合同**（`layer_range`）| ✅ `build_assignment_manifest(start_layer, end_layer, total_layers)` + 校验 | 无 |
| **层索引映射**（裁剪实例 ↔ 源模型）| ✅ `RelayTrimPlan.local_to_source_layer()` | 无 |
| **分配清单**（每节点持哪些权重）| ✅ `build_assignment_manifest` → `public_assignment_manifest` | 无 |
| **容量求解**（谁装得下多少层）| ✅ `solve_pipeline_capacity` | 未与 `PipelineNode` 串接 |
| **跨引擎接力合同** | ✅ `relay_contract` 全套（含 `admit_relay_xframe`）| **未纳入统一节点模型** |
| **RPC 借算力合同** | ✅ `llama_rpc_contract.py`（152 行）| **未与层段绑定** |
| **统一节点抽象** | ❌ **无** | **本文档新增** |
| **重分片 / 容错** | ❌ **无** | **本文档新增（§4）** |

## 2. layer_range 合同（沿用 + 收紧）

**沿用** `build_assignment_manifest` 的语义（已实现校验）：

```
0 <= start_layer < end_layer <= total_layers
total_layers 必须等于 config.num_hidden_layers
```

**收紧三条**（新增）：

1. **区间半开**：`[start, end)`，**与 Python 切片一致**，避免 off-by-one；
2. **全覆盖**：所有节点的 `layer_range` 并集必须**恰好等于** `[0, total_layers)`，
   **不允许重叠、不允许空洞**（这是「合持」的定义）；例外：`cross_framework` 节点的
   两侧由上游/下游共同覆盖，需显式声明 `handoff_at`（交接层号）；
3. **边界职责**：**embedding 与 lm_head 的归属必须显式声明**
   （`has_embedding` / `has_lm_head`），并纳入 manifest 校验 —— 因为 §14 证实
   **单层切片仍须携带 `token_embd`**（否则加载失败）。

## 3. manifest 与校验（沿用 + 补三项）

**沿用**：`build_assignment_manifest` / `public_assignment_manifest` / `MANIFEST_SCHEMA_VERSION`。

**补三项校验**（新增）：

| # | 校验 | 为什么 |
| ---: | --- | --- |
| 1 | **并集覆盖**（§2.2）| 防止「某层没人算」——静默错误 |
| 2 | **模型身份一致**：所有节点的 `model_sha256` 必须相同 | 已在 `relay_contract` 有此要求（`:192`），需扩展到 `PipelineNode` 层 |
| 3 | **架构 KV 一致性**：切片产物的 `block_count` / `nextn_predict_layers` 必须自洽 | §14.6 实测：切掉 MTP 层时 `nextn_predict_layers` 必须置 0，否则 `GGUF_ASSERT` 失败 |

**校验失败一律 fail-closed**（与 `admit_relay_xframe` 现有风格一致）。

**→ 结论修正：容错的地基（租约/epoch/fencing/回退）已具备；
缺的是「**自动重分片**」这一层，以及把它纳入统一节点模型。**

### 4.2 ★ 自动重分片（唯一真正新增的容错能力）

### 4.2.1 为什么它比「本地回退」更难

「断线本地回退」= 主节点把**全部层**收回来自己跑（§票 10 已验证）。
「自动重分片」= 把**失效节点的层区间**重新分配给**幸存节点**。后者要求：

| 前提 | 为什么 |
| --- | --- |
| **容量预检** | 幸存节点临时多装若干层，**可能装不下 → 直接 OOM**（§14 已证层流水线只降占用，不降单层计算需求）|
| **权重可得性** | 幸存节点必须**能拿到**那段层的权重（裁层 GGUF / safetensors 片段）→ 依赖 `RemoteAssetSyncPlan` 的扩展 |
| **epoch 切换原子性** | 新分配生效时，旧 epoch 的结果必须被 **fencing 丢弃**（已有机制）|
| **`layer_range` 重算** | 需重解 §2 的「并集恰好覆盖」约束 |

### 4.2.2 分阶段（更正后）

| 阶段 | 内容 | 现状 |
| --- | --- | --- |
| **S0** | 静态分配 + 启动前校验 | ✅ **已有**（`build_assignment_manifest`）|
| **S1** | 租约 + 心跳；节点失效 fail-closed | ✅ **已有**（`RpcShardLease` + 票 10 验证）|
| **S2** | epoch + fencing（防旧结果）| ✅ **已有**（票 10 验证「拒绝旧 lease」）|
| **S2.5** | **断线本地回退**（全部收回本地）| ✅ **已有**（票 10 验证）|
| **★ S3** | **自动重分片**（幸存节点接管失效区间）| ✅ **已实现开发门**：容量重解 → 工件/边界职责证明 → 同一计划 ready ACK → epoch 切换 |

**S3 的实现约束**：恢复容量记录必须包含临时加载余量；重解要求至少两个仍在线的执行节点，故双节点拓扑失去一个节点仍走既有本地回退。每个候选层段连同首段 Embedding、尾段 LM Head 都须有已验证同模型/同工件类型的覆盖；`RemoteAssetSyncPlan` 只有在 `already_current`/`applied` 后才可形成整 GGUF 覆盖证明。调度器仅在恢复计划与新两阶段加载的 `plan_id` 和布局摘要完全一致后提交新 epoch，旧 lease 结果被 fencing 拒绝。

## 5. 与「借算力」的整合（原 Silica 式）

### 5.1 一个关键澄清

**llama.cpp 的 `--rpc` 不支持连续层段**（只有全局 `-ngl` + `--tensor-split`）。
因此「借算力」要纳入层段协议，有两条路：

| 路径 | 做法 | 说明 |
| --- | --- | --- |
| **A. 固定切分 + 各自加载** | 用**裁层 GGUF**（`local` 侧）与 `--rpc`（`remote_rpc` 侧）组合；**层段分配由我们管** | ✅ **§14 已验证上游按需加载 + 下游裁层 64/64 一致** |
| B. 改造 `--rpc` 支持层段 | 改上游 C 代码 | ❌ 与 Policy 冲突（不整合上游），且成本高 |

**→ 推荐 A**：**本项目的层段协议是「分配层」，llama.cpp 的 `--rpc` 只是「执行借用」** ——
`remote_rpc` 节点声明它持有哪些层，由**我们**保证不重叠、不空洞。

### 5.2 节点类型带来的能力对照

| 能力 | `local` | `remote_rpc`（借算力）| `cross_framework` |
| --- | --- | --- | --- |
| 降低**单机显存**占用 | ⚠️ 否（本机仍要装）| ✅ **是** | ✅ 是（§14：CUDA 7.53→1.475 GB）|
| **借**别的设备算力 | ❌ | ✅ **是** | ❌ |
| 跨**引擎**组合 | ❌ | ❌ | ✅ **是** |
| 需要网络 | ❌ | ✅ | 可选 |

**→ 三者互补，不是替代关系。** 这正是「不搞兜底、统一为节点类型」的实质收益。

## 7. 未验证声明

1. **真实 PC/Android 故障重分片尚未实测**；当前覆盖的是容量、工件和 epoch 的确定性合同及既有 PyTorch 两阶段加载接线。
2. **`--rpc` 与裁层 GGUF 的组合未实测** —— §14 验证的是「同进程双后端」与「上游按需加载」，
   **不是** `--rpc` 借算力场景；
3. **`remote_rpc` 节点的实际收益未测**（网络往返、Wi-Fi 延迟、Android 侧算力均未知）；
4. **Silica 调研的 5 条未确认项** 依旧未确认（见 [调研文档](Silica式分片方案调研-2026-09-17.md) §7）；
5. **跨引擎 `remote_rpc` 的实际装载器尚待 Android/裁层 GGUF 票实现**；当前统一合同和同步可用性证明不替代该执行器。
