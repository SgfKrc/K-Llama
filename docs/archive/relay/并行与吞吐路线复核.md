# 并行与吞吐路线复核：层接力能不能「切块吃满」？

> 文档状态：**结论性复核（现行）** ｜ 最后更新：2026-09-18
>
> 触发问题（用户 2026-09-18）：**「我知道大模型层层依赖，所以层接力得串行，能不能做到尽量吃满——比如把一个任务切块、或者把数据切块计算，减少每个块计算量的同时尽量吃满性能，以达到类似并发的效果？或者别的不需要层接力的并行方案？异构没法张量并行，高吞吐带来的传输时延会比 RPC 还恐怖，这是过去已经得到的结论。」**
>
> 采信纪律同 `分布式推理并行与跨框架路线调研汇总-2026-09-15.md`：**实测 > 上游原文 > 估算（写明算法）> 未查到**；估算不写成实测。本文件**不重复**该汇总的全部分档推荐，只回答上面的问题并更新有实测数据支撑的部分。

## 0. 先给结论

1. **「把数据切块」对 decode 无效，且对层接力是负收益。** decode 单序列是 **memory-bound**（决定速度的是搬运字节数，不是算力）；`-b` 分块只提升 **prefill**，整模 llama-bench 口径下 **0.74×**（反而慢 26%）。层**内**再切分就是张量并行（TP）⇒ 已被**同步次数 × RTT** 定量否决，异构下 straggler 还会被放大。
2. **「把一个任务切块」在解码语义上做不到**：自回归的每一步都依赖前一步的 token，同一序列无法切成互不依赖的块。能切的只有**互不依赖的多个请求**——那在系统层面就是「多请求」而非「切块」。
3. **真正能「尽量吃满」的机制只有一个：多请求交错（软件流水线 / continuous batching）。** 它填的是**空闲**（A 算上游时 B 算下游），而不是把单个请求算得更快。本仓实测（P2）**1.291×**，理论上限约 **1.79×**，差额来自**同机上下游争用**（P12）。
4. **⚠️ 用户的判断成立（关键）**：给层接力加 batch ⇒ **每步要传的 hidden 随 batch 线性增长**，而 RPC 传的是**权重、一次性且可缓存** ⇒ 层接力在高吞吐下的**传输延迟**确实会比 RPC 更难受。定量见 §3。
5. **所以最该做的不是「给层接力切块」，而是「给不接力的 L 档接多序列（continuous batching）」。** llama.cpp 原生多序列的**绝对吞吐**实测领先同精度 torch **1.2–1.6×**（batch32：Q4_K_M 689.75 / f16 523.32 t/s vs torch f16 384.91 t/s），而**主仓的 L 档 decode 仍是单序列**（`src/llama_engine.py:995` 的 `n_seq_max=1`），`load_model()` 也只设 4 个参数（`:308-313`）⇒ 这是**当前最大的吞吐缺口**。⚠️ 另外：D 档（PyTorch 层流水线）的串行由 `PIPELINE_MAX_CONCURRENT = 1`（`src/config.py:396`，**该常量无消费者**）与 `_pipeline_lock`（`src/scheduler.py:1087`）体现，与 L 档是**两件事**。

## 1. 把「并行」拆成三层，避免概念混用

| 层 | 含义 | 能否提高吞吐/吃满 | 与本项目的关系 |
| --- | --- | --- | --- |
| **A. 单请求内·数据切块** | 把一个请求的序列/张量切小块并行 | **prefill 可以**（chunked prefill，llama.cpp 已实现）；**decode 不行**（batch=1，无可切） | 对层接力**有害**（放大传输） |
| **B. 单请求内·层并行** | 把不同层放不同设备 | ❌ 层间**串行依赖不可破**，只能流水线填充，不能缩短单请求延迟 | **就是层接力本身** |
| **C. 多请求·交错** | 把**多个独立请求**交错，填充各段空闲 | ✅ **唯一有效**，且**不需要层接力** | 被长期忽略的吞吐正路 |

> 用户问题里的「任务切块」若指 A ⇒ 见 §2（对 decode 无效）；若指「把一个大任务分解成多个独立请求」⇒ 那落在 C（§4）。

## 2. 「数据切块」为什么救不了 decode

### 2.1 事实基线（仓内实测/核实）

| 事实 | 出处 |
| --- | --- |
| decode（batch=1）是 **memory-bound**：上游 GPU 每层 8.25 ms ≈ 下游 CPU 每层 8.3 ms ⇒ 决定速度的是**搬运字节数** | `docs/跨框架接力性能优化-汇总报告-2026-09-16.md:31-32, 94-95` |
| 同上结论的独立复述：「根因是 batch=1 的 memory-bound」 | `docs/archive/distributed/单机工作整理与分布式路线盘点-2026-09-16.md:31-33`；`docs/archive/relay/分布式推理并行与跨框架路线调研汇总-2026-09-15.md:236` |
| prefill 分块 `-b 1/8/16/32`（**llama.cpp GPU Q4_K_M**）⇒ prefill **68.30 → 217.57 t/s（3.3×）**，而**生成速度几乎不变**（74.40 → 73.11/74.54/74.78）⇒ 证明「数据分块」对 **prefill 早已用尽、对 decode 无效** | `docs/archive/relay/引擎单序列与并发性能对比-2026-09-16.md:64-79` |
| 但整模 llama-bench 口径下「分块」（`-b 1024 -ub 256`）**= 0.74×**（decode 受损），`-fa` 1.00×、KV `q8_0` 0.92× ⇒ **把 prefill 块开大反而伤 decode** | `docs/archive/relay/跨框架层接力-实验数据汇总.md:279` |
| ⚠️ 本仓 **torch 路径完全没有 prefill 分块**（prefill 5 token 耗时 93 ms，未切分） | `docs/archive/relay/引擎单序列与并发性能对比-2026-09-16.md:76-77` |
| ⚠️ `-b` **不是并发序列数**，只影响单序列 prefill 的内部切块 | `docs/archive/relay/引擎单序列与并发性能对比-2026-09-16.md:78` |
| 由此推出的判断：「**未测 batch>1 的跨框架接力**（理论上是让 GPU 转成 compute-bound 的唯一途径）」 | `docs/跨框架接力性能优化-汇总报告-2026-09-16.md:216, 231` |

### 2.2 结论

- **prefill 切块 = 已用尽**：llama.cpp 已实现，3.3× 已吃到；主仓未显式设 `n_batch/n_ubatch`（走默认）⇒ 属「改一行参数可试」的第一批动作，但**上限就在那里**。
- **decode 切块 = 不存在**：batch=1、每步只算 1 个 token，**没有可并行的维度**。
- **层内切分 = TP ⇒ 已否决**：每 token 需 **48 次 all-reduce 同步栅栏**，RTT 下限 **960 ms（@20 ms）**，瓶颈是**同步次数 × RTT** 而非带宽（TPI-LLM arXiv:2410.00531「link latency, not bandwidth」旁证）；异构下 straggler 被放大 48 倍。出处：`docs/archive/relay/张量并行外部辅助与混合拆分调研方案.md:33-56`；`docs/跨框架层接力-项目报告.md:84-89`。
- ⇒ **「减少每个块计算量」这条思路，在 decode 上没有任何着力点。** 唯一能让 GPU 从 memory-bound 转 compute-bound 的是**加 batch（多序列）**——那是 §4 的 C 层，不是切块。

## 3. 为什么「加 batch」会把层接力推向比 RPC 更糟的传输

### 3.1 定量（估算，写明算法）

层接力的跨切点传输是 **hidden state**，**每一步**每个切点传一次：

```
每步传输字节 = B（batch/并发序列数）× hidden_size × dtype_size
```

以 1.8B 级模型（hidden 2048，bf16）为例：

| 并发 B | 每步每切点传输 | @100 Mbps 的传输时间 | 备注 |
| --- | --- | --- | --- |
| 1 | 4 KB | 0.33 ms | 与单步计算（~10 ms）比可忽略 |
| 8 | 32 KB | 2.6 ms | 开始显著 |
| 32 | **128 KB** | **10.2 ms** | **≈ 单步计算本身** ⇒ 带宽把收益吃光 |
| 128 | 512 KB | 41 ms | 高吞吐场景 ⇒ **不可行** |

> 参照：`docs/archive/relay/分布式推理并行与跨框架路线调研汇总-2026-09-15.md:62` 给出同量级估算——「decode 每跳 hidden 约 4 KB（1.8B/24 层/hidden 2048/bf16）、KV 约 200KB/token —— 两者差 50×」。即 **KV 留在本地、只传 hidden** 是接力的相对优势；但一旦加 batch，hidden 的优势被 B 倍抹平。

**对比 RPC**：传的是**权重**（一次性）

- 2B f16 ≈ 4.3 GB ⇒ @100 Mbps ≈ **344 s（一次性）**，之后靠 `-c/--cache`（按张量字节内容 hash 的本地缓存）在**内容逐字节相同**时命中 ⇒ 0 字节传输；
- 运行期不再传权重（只走图描述指令），KV 常驻远端不回传 ⇒ **没有「每步 × B」的项**。

### 3.2 结论

- **RPC 的代价是一次性的、且可被内容 hash 缓存摊薄；层接力的代价是每步的、且随吞吐/B 线性增长。**
- ⇒ 用户「**高吞吐带来的传输时延会比 RPC 还恐怖**」的判断**成立**，并且可定量复述为：**层接力的传输项 ×B，RPC 没有该项**。
- ⇒ 因此 **「给层接力加 batch 提吞吐」是错误的优化方向**——它把接力唯一的相对优势（只传 4 KB/步）亲手抹掉。

## 5. 那「层接力」自己能不能吃满？（在「必须接力」的前提下）

结论：**能挤出的都挤过了，且上限由设备比而非调度决定。**

| 手段 | 实测 | 出处 |
| --- | --- | --- |
| 切点重搜（P0） | 最优切点由**单位层耗时比**决定：GPU 上游 < 下游 ⇒ 取最大 N（预测 N=20 = 实测 N=20，误差 ≤2.02%）；CPU 上游 > 下游 ⇒ 不接力（预测 N=4 = 实测 N=4，≤6.36%）⇒ **不存在「中间切点最优」的谷底** | `local_docs/evidence/relay-xframe/CORE-RELAY-XFRAME-02-切点-2026-09-18.json` |
| 上游设备 | `--upstream-device cuda` 后 N=20 = **129.1 ms/步**，比「不接力」186.8 快 **1.45×** | P0 修正 v2 |
| 多请求交叠（P2） | **1.291×**（上限 1.79×） | `local_docs/evidence/relay-xframe/CORE-RELAY-XFRAME-02-p2-2026-09-18.json` |
| 为什么达不到上限 | P12：同机下游 CPU decode 与上游 torch **争用内存/总线** ⇒ 上游 +17.726 ms/step（C/A = 2.482×），交叠仅达上限 ~72% ⇒ **部署应让上下游分处不同机器** | `local_docs/evidence/relay-xframe/CORE-RELAY-XFRAME-02-upstream-profile-2026-09-18.json` |

⇒ **「吃满」的天花板**：把两侧算力都占满 ⇒ 加速上限 = `(上游+下游)/max(上游,下游)`。同机达不到（争用）；**跨机才有意义**（也就是 QLH 的目标场景，`B5` 待测）。
⇒ ⚠️ 但即使完全吃满，**层接力仍不是更快的推理路径**：P2 对照 llama.cpp+CUDA 整模 **26.6 ms/token**，接力最优 129.1 ms/token ⇒ **慢 4.85×**。接力的价值是「**只能用 torch 跑的层**」与「**容量合并**（单机装不下）」，外加实验平台。

## 6. 给下一步的建议（按收益/成本）

1. **【高】给 L 档接多序列/continuous batching**（方案 #1）：llama.cpp 原生多序列的**绝对吞吐**已实测领先同精度 torch 1.2–1.6×，主仓却是**单序列**。这是**唯一不需要层接力、且有现成实测背书**的吞吐提升。落地要点：① `load_model()` 已有 **kwargs 透传机制**（docstring 明列 `flash_attn/type_k/type_v/...`），但 `n_parallel` **未列** ⇒ 需先确认 `llama-cpp-python`（0.3.28）对该参数的支持；② decode 侧从 `n_seq_max=1`（`src/llama_engine.py:995`）扩到多序列。
2. **【高】把 D 档的 `PIPELINE_MAX_CONCURRENT` 与真实串行语义对齐**（`src/config.py:396` 的常量**无消费者**，易误导）——要么接线，要么标注「未接线」。
3. **【中】P2 交叠的跨机复测**（票 `B5`，**需 Surface 从节点在线**）：P12 表明同机会低估收益，跨机才是真实值。
4. **【中】不要把 batch 加到层接力的 decode 上**（§3）——若确有吞吐需求，应走 #1，而不是给接力加批。
5. **【低】级联/路由、prefix cache**：调研结论可行但无实现、无实测，收益面窄，暂不投入。
