## 1. 摘要

**目标**：D→L 跨框架逐层接力（上游 PyTorch + 下游 llama.cpp 裁层）在**本机（RTX 4060 Laptop 8GB, 16GB RAM）**单序列场景下的性能。

**结果**：

| 指标 | 首版 | **终版** | 提升 |
| --- | ---: | ---: | ---: |
| 端到端（gen=64） | 182 s | **21.3 s** | **8.5×** |
| 上游/步 | 1900 ms | **38.1 ms** | **50×** |
| 与 llama.cpp 原生整模 GPU 的差距 | ~180× | **~20×** | 缩窄 9× |

**全程 64/64 逐 token 一致（per-token argmax）** —— 所有优化**未损害数值正确性**。

**最重要的两个结论**：
1. **真正的杠杆是「减少无谓计算」（上游只跑 4 层，10.7×）与「KV 复用」（3.15×）**；
   所有工程侧微调（进程边界、batch 复用、同步）**实测均 ≈0**。
2. **单序列（batch=1）是 memory-bound**：上游 GPU 每层 8.25 ms ≈ 下游 CPU 每层 8.3 ms ——
   **决定速度的是「搬运多少字节」，不是「CPU 还是 GPU」**。

## 2. 五轮演进（全部数据）

统一配置：prompt = `The capital of France is`（5 token），gen = 64，
下游 = `qwen35-2b-f16-cut.gguf`（从 layer 4 起），threads=8。

| # | 配置 | 端到端 | 上游/步 | 下游/步 | 一致 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | 跨进程 + 每步全段重算 | 182 s | 1900 ms | 586 ms | 64/64 |
| 2 | 同进程 + 每步全段重算 | 167 s | 1900 ms | 586 ms | 64/64 |
| 3 | 同进程 + **双侧 KV 复用** | 53 s | 287 ms | 151 ms | 64/64 |
| **4** | **同进程 + KV + 上游手动 4 层** | **21.3 s** | **38.1 ms** | 166.6 ms | **64/64** |
| 5 | 跨进程 + KV + 4L + 下游 GPU offload | 81 s | 38.1 ms | — | 64/64 |

### 2.1 各手段的**单独**收益（关键：不要被总账误导）

| 手段 | 单独收益 | 性质 |
| --- | ---: | --- |
| **上游只跑前 4 层**（手动前向） | **10.7×**（上游） | ✅ 减少无谓计算 |
| **KV 复用**（两侧增量） | **3.15×**（端到端） | ✅ 算法/数据流 |
| 下游 GPU offload | **2.18×**（跨进程） | ✅ 算力放置 |
| 消除进程边界（同进程） | **8%**（≈0.4 s） | ⚠️ 小 |
| 复用 `llama_batch` | **≈0**（甚至更慢） | ❌ 证伪 |
| 上游层截断（朴素） | **数值破坏**（0/8） | ❌ 不可行 |

## 3. 四次自我推翻（本报告最重要的部分）

实验过程中**四次推翻了自己的判断**，每次都记录在案：

### 推翻 1：「IPC 是瓶颈（1.3 s/步）」

- **初判**：跨进程 D→L 1.44 s/步，两侧计算仅约 101 ms → 推断 IPC 占 1.3 s。
- **实测**：同进程后总耗时只降 **8%**（182 → 167 s）。
- **再修正**（§13.4）：**「IPC 只占 8%」也是假象** —— 那是**两侧都很慢时**的占比。
  当两侧都被优化后（4L + KV），**跨进程 IPC 反成主导**：
  同配置同进程 21.3 s vs 跨进程 81 s。

**教训**：**占比是相对的** —— 分子不变时，分母变小会让占比反转。

### 推翻 2：「Python 侧 `llama_batch_init/free` 是瓶颈（~10×）」

- **初判**：下游 5 层实测 586 ms，按 llama.cpp 折算应 ~15 ms → 推断 Python 调用开销 ~10×。
- **实测**：复用 batch（不每步 init/free）**反而更慢**（68 s > 53 s）；
  五段剖析显示 `batch_setup + batch_free` 合计 **0.54 ms/步（0.09%）**。
- **真因**：下游开销就在 **llama.cpp 的 CPU 前向本身 + 248320 词表的 argmax**。

### 推翻 3：「同步次数是瓶颈」

- **初判**（基于"乒乓串行"的推理）：64 步 = 64 次同步，是并行度锁死的主因。
- **实测**（五段剖析）：`unaccounted`（循环/同步/其他）= **2.11 ms/步（0.34%）**。
- **结论**：**同进程接力的同步开销几乎为零**；耗时 **99.3% 是两侧实际计算**（上游 66.5% + 下游 32.9%）。

### 推翻 4：「GPU 段必然更快（D 档异构红利）」

- **初判**：GPU 跑上游、CPU 跑下游 → 上游应显著快于下游。
- **实测**：上游 4 层 38.1 ms（**9.5 ms/层**），下游 20 层 166.6 ms（**8.3 ms/层**）；
  扣除上游固定开销（embed + rotary + 两种 mask ≈ 5 ms/步）后，**上游纯计算 ≈ 8.25 ms/层 ≈ 下游 8.3 ms/层**。
- **真因**：**单序列（batch=1）是 memory-bound** —— GPU 利用率 <10%，
  瓶颈是「把权重从显存搬到 SM」的带宽。**决定速度的是搬运字节数，不是设备类型。**

## 4. 核心技术发现（可复用的知识）

### 4.1 同进程双后端**无需 fork**

`relay-gen-dl.cpp` 仅 176 行，hidden 注入依赖 `llama_batch` 的**标准字段 `embd`**：

```cpp
llama_batch batch = llama_batch_init(n_tokens, n_embd_inp, 1);
memcpy(batch.embd, hidden.data(), hidden.size() * sizeof(float));
llama_decode(ctx, batch);
```

→ PyPI 版 `llama-cpp-python` 的底层绑定即可完成（本机装 0.3.28，**绑定为 ctypes 非 cffi**）。

### 4.2 上游「只跑前 N 层」的正确做法

**朴素截断会破坏数值**（实测 0/8），根因是读源码才发现的：
`Qwen3_5TextModel.forward` 中每层的 attention 类型由 **`config.layer_types[i]`** 决定
（Qwen3.5 是 **hybrid**：`linear_attention` 与 `full_attention` 每 4 层交替），
而两种 mask 是**预先建好**的，`create_recurrent_attention_mask` **依赖完整 config**。

**正确做法**：按该 forward 的真实逻辑**手动复现前 4 层**：
`embed → 4 段 M-RoPE position_ids → rotary_emb → {full_causal_mask, recurrent_mask} → 4×DecoderLayer`。

**验证**：与完整模型的 `hidden_states[4]` **bit-exact（max|diff| = 0.000000e+00）**。

### 4.3 下游增量模式需要 C++ 侧配合（`--keep-kv`）

上游增量（只出末位 1 行 hidden）与下游「每步 `llama_memory_clear` + 需要整段 hidden」**结构性矛盾** → 3/64。
修法：给 `relay-gen-dl.cpp` 加 `--keep-kv`（跳过 clear + pos 绝对累加），driver 用环境变量透传。

### 4.4 两个 Windows 环境踩坑（已定位根因）

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| `0xC0000139`（exit=127） | Python 进程注入了 **MSYS2 PATH**，使 `llama_cpp` 的 DLL 误加载 MSYS2 libstdc++ | Python 进程**不要**加 MSYS2 PATH |
| `0xC0000374`（堆损坏） | 把 `batch.pos` 指针替换成 Python ctypes 数组，`llama_batch_free` 会对它调 C `free()` | 用 `llama_batch_init(n_pos_per_embd * n_tokens, ...)` 让分配与 free 配对 |

**另注**：`cmd` 的 `.bat` 必须**纯 ASCII**（GBK 读入会拆碎中文字节导致命令解析错乱）。

## 6. 对架构决策的含义

| 决策项 | 本报告的支撑 |
| --- | --- |
| **D 档（PyTorch）的价值不在单序列速度** | 最优跨框架 333 ms/步 vs llama.cpp 原生 13.5 ms/步（差 **≈25×**；口径注见文末脚注）|
| **D 档真正的价值 = 层间流水线载体 + 四路对照实验** | 同进程双后端已验证可行（单进程内 torch + llama.cpp 协同）|
| **跨框架接力的适用场景** | **不是提速**，而是**能力组合**（某一侧有另一方没有的算子/精度/架构支持）|
| **L 档仍是单机单序列的正解** | 全程数据均指向 llama.cpp；且它无 Python/triton 依赖链之累（纯 C++ 交付） |
| **~~低精度是 batch=1 场景的第一杠杆~~** | ❌ **已实测证伪**（§7.1）：上游 f16/bf16 **反而慢 8.4–8.7×** |
| **真正的第一杠杆仍是「减少无谓计算」** | 上游只跑 4 层（10.7×）+ KV 复用（3.15×）|

## 7. 实测补充：上游低精度的**反直觉结果**（2026-09-16 追加）

针对 §6 中「低精度是 batch=1 第一杠杆」的推理，实测上游 4 层改用低精度（gen=64，其余不变）：

| 上游 dtype | **上游 ms/步** | 相对 f32 | 权重 | 一致 |
| --- | ---: | ---: | ---: | ---: |
| **f32** | **39.8** | 1.0× | 7 GB | 64/64 |
| f16 | **333.9** | **8.4× 慢** | 3.6 GB | 64/64 |
| bf16 | **345.4** | **8.7× 慢** | 3.6 GB | 64/64 |
| **nf4**（bitsandbytes） | **43.4** | **仅 1.09× 慢** | **~1.8 GB** | 48/64（有损，符合预期） |

**→ 假设被推翻：低精度在 torch 侧没有任何速度收益。**

**但 NF4 与 f16 的差距极大（1.09× vs 8.4×），这揭示了一个关键区别**：

> **量化内核（NF4：dequant+compute 融合）远优于朴素 dtype 转换（f16：每步 cast）。**

**推测原因（未做 profiling）**：
1. **朴素 dtype 转换的代价**：权重为 f16/bf16，但 `position_embeddings`、causal mask、`rotary_emb` 等仍是 f32
   → 每步产生 cast 开销；消费级 Ada 的 f16 吞吐也不高于 f32；
2. **NF4 走不同路径**：bitsandbytes 内核内融合 dequant 与 matmul，无显式 cast，故只慢 9%；
3. 与此前 E5 的观测**一致**：全模 24 层下 `f16 + sdpa` 也反而更慢（7.76 vs 17.29 t/s）。

**★ 真正的解释：4 层 + batch=1 是「延迟受限」而非「带宽受限」**
每步的**固定开销**（kernel launch、mask 构造、rotary）主导，**权重搬运量已不是瓶颈** ——
这解释了「上游 9.5 ms/层 > 下游 CPU 8.3 ms/层」的反常现象（上游每层背着更多固定开销）。

**→ 结论修正**：
- **「memory-bound ⇒ 低精度直接有效」在 torch 上不成立**（4 层场景延迟受限）；
- **llama.cpp 的 Q4_K_M 加速（74 t/s）来自 C++ 内核层的量化-计算融合**，而非"低精度"本身；
- **NF4 的真实价值在**容量**（7 GB → 1.8 GB），不在速度** —— 对应
  [异构内存分层辨析](跨框架接力与异构内存分层-辨析-2026-09-16.md) 中"能否装下"的需求。


**⚠️ 未测**：NF4（bitsandbytes）在 4 层场景的表现 —— 它走的是不同的实现路径（量化内核 + dequant），
与朴素 `dtype=float16` 不可类比。

### 7.2 上游 4 层的内部构成剖析（gen=32）

用 `profile_upstream_4L.py` 分段计时（每段前后 `torch.cuda.synchronize()`）：

| 段 | ms/步 | 占比 |
| --- | ---: | ---: |
| **t_layers（4 层计算）** | **36.76** | **77.7%** |
| ~~t_embed~~ | ~~8.78~~ | ~~18.5%~~ → **测量伪影**（见下） |
| t_rotary | 0.98 | 2.1% |
| t_mask_full | 0.45 | 0.9% |
| t_pos | 0.24 | 0.5% |
| t_extract（hidden→numpy） | 0.11 | 0.2% |
| t_mask_rec | 0.01 | 0.0% |

**⚠️ 排除一个伪影**：`t_embed` 显示 8.78 ms，但单独实测 `embed_tokens`
**真实耗时仅 0.013 ms**（median，n=1/5，各 20 次）。
伪影来源：该段测量**没有前置 sync**，吸收了上一步的异步尾部；
且剖析脚本额外调用了 `lm_head`（248320 词表）用于推进序列，未计入任何段。

**修正后的真实构成（上游接力版 38.1 ms/步）**：

| 环节 | ms/步 | 占比 |
| --- | ---: | ---: |
| **4 层计算** | **~36.8** | **~97%** |
| 固定开销（rotary + mask + pos + extract + embed） | **~1.8** | **~4.7%** |
| 合计 | ~38.1 | 100% |

**逐层**：layer0 12.0 / layer1 8.8 / layer2 8.7 / layer3 7.2 ms
→ **平均 9.2 ms/层**，与下游 llama.cpp **CPU 的 8.3 ms/层**基本相当。

### 7.3 ★ 由此得出的终点结论

1. **上游 4 层已是纯计算主导（~97%）**，固定开销只剩 ~4.7%；
2. **→ CUDA Graph 等「减少 launch 开销」的手段最多省 ~1.8 ms/步（~5%）** —— **不值得做**；
3. **→ GPU 在 batch=1 下对 CPU 无优势**（9.2 vs 8.3 ms/层），与 §3「推翻 4」完全一致；
4. **→ 跨框架接力的上游侧已无进一步优化空间**（除非改变 batch 规模或算法）。

**⚠️ 方法论教训**：**分段计时的每一段都必须自带前后 sync**，
否则会把上一步的异步尾部算进本段（本次 `t_embed` 即为此类错误）。
