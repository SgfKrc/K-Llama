## 1. 构想的形式化：三层抽象

| 层 | 知道什么 | 不知道什么（默认）| 对应既有模块 |
| --- | --- | --- | --- |
| **顶层（TUI / 交互）** | **聚合资源**（GPU/CPU/内存）+ 可选策略 | **谁在本地、谁在远端** | `api_server.py` 端点、`src/tui_*.py` |
| **中层（层流水线 / 控制面）** | **节点列表** + 每节点资源与层段 | 引擎内部实现细节 | `pipeline_capacity.py`、`pipeline_assignment_manifest.py`、`scheduler.py` |
| **底层（节点 / 数据面）** | **自己的层段 + 自己的引擎** | 全局布局 | `llama_engine.py`、`model_module.py` |

> 同文 `:13`：**「控制面负责调度、分片合同、节点、租约和故障绕行」**

**→ 用户构想的「顶层不关心谁在远端」，就是「控制面对数据面选型不敏感」的同义表述。**

## 2. 节点类型（回答「都有什么节点类型」）

见 [层段协议立项 §1](层段协议立项-2026-09-17.md) 的三分法，此处补上**判定维度**：

| `kind` | 判据 | 引擎 | 通信 | 典型例 |
| --- | --- | --- | --- | --- |
| **`local`** | 与本进程**同机** | llama.cpp **或** pytorch | 进程内 | 本机 GPU 上的 L0-3 |
| **`remote_rpc`** | **跨机**，但**同引擎族** | llama.cpp | ggml RPC | Android/PC 上的 `ggml-rpc-server`（原「Silica 式」）|
| **`cross_framework`** | **同机或跨机**，**跨引擎** | **两种** | 进程内 / stdio / 网络 | torch 上游 + llama.cpp 下游（§13/§14 已验证）|

### 2.1 三者不是互斥的分类，而是**正交的两个维度**

```
维度 A：位置  ── local ──┬── remote
维度 B：引擎  ── 单引擎 ──┬── 跨引擎
```

**→ 三个 `kind` 是「两维上的三个常见组合」，不是完备枚举。**
例如「跨机 + 跨引擎」（Android 上跑 torch 上游 + PC 上跑 llama.cpp 下游）在两个维度上都是"远"，
当前**未被命名**，但**协议上应当允许**（因为抽象只要求 `(layer_range, engine, location)`）。

**建议**：`kind` 采用**能力标注**而非**封闭枚举**：
```python
kind: str            # "local" | "remote_rpc" | "cross_framework" | 未来扩展
federated: bool      # 是否跨机（维度 A）
cross_engine: bool   # 是否跨引擎（维度 B）
```
这样新增组合**不需要改协议**。

## 4. 三处必须精确化的点

### 4.1 资源视图必须是「聚合」的

**问题**：`device_profiler` 描述的是**本机**画像；而 `solve_pipeline_capacity` 接受的是
**节点列表**（`nodes: list[dict]`），并明确要求：

> 「`capacity_bytes` must describe **currently free memory**, not installed physical memory.」
> 「`reserve_bytes` is charged **once to every participating node**.」

**→ 所以顶层若只报「本机 GPU/CPU/内存」，中层会缺少**远端节点的容量**，
无法做出「合持」决策。**

**建议**：顶层暴露的应是**聚合视图**：
```
available = {
    "local":  {gpu, cpu, ram},          # device_profiler 本机画像
    "remote": [{node_id, gpu?, cpu, ram}, ...],   # 来自集群注册表
}
```
**而「哪些是 remote」由中层填充，顶层只读。**

### 4.2 引擎选择 = 资源 + 能力 + 目标（不只是资源类型）

**用户原表述**：「根据资源类型选择 pytorch、llama」。

**⚠️ 实测反例**（同机 RTX 4060 8GB，Qwen3.5-2B）：

| 引擎与配置 | 单序列生成 t/s |
| --- | ---: |
| **llama.cpp GPU Q4_K_M** | **74.40** |
| torch GPU f32 + KV cache | 17.29 |
| torch GPU f16 + sdpa | 7.76（**反更慢**）|

**→ 同资源下差 4.3×，且 `f16+sdpa` 比 `f32` 更慢。「有 GPU 就用 torch」会选到最差组合。**

**另有能力约束**（非性能）：

| 能力 | 只在哪一侧可用 |
| --- | --- |
| **GGUF 量化（Q4_K_M 等）** | 仅 **llama.cpp** |
| **bitsandbytes NF4 / 新版架构支持** | 仅 **torch** |
| **`flash-linear-attention`（Gated Delta Net 加速）** | 仅 **torch**（且 Linux/WSL）|
| **mmap 磁盘分页** | 仅 **llama.cpp** |

**建议**：引擎选择输入应为三元组：
```
select_engine(resources, required_capabilities, objective)
# objective ∈ {latency, throughput, capacity}   ← 目标不同，选择不同
```
**「有 CUDA 默认开 torch」应表述为**默认策略**，而非**资源直接映射****（架构文档 `:13` 的
"显式开关、可关闭并退化" 已具备这个形状，只需把**依据**从"有无 CUDA"扩展为三元组）。

### 4.3 「不关心」是默认，但必须**可查 + 可约束**

**用户自己已指出**：「当然，实际上要能查出是分布式还是本地单节点」。

**既有支撑**：TUI 已有 `/api/cluster/config/distributed-inference`（可读可写）与 `node_role`。

**⚠️ 但要补两类约束开关**（当前**没有**）：

| 约束 | 为什么必须 | 建议形态 |
| --- | --- | --- |
| **隐私/数据边界** | 「把 hidden 发到别的设备」是**数据出境**；某些部署不得跨机 | `allow_remote: bool` + 目标节点白名单 |
| **带宽/网络代价** | 实测：跨设备往返代价高（`--override-tensor` 的部分 offload **比全 CPU 还慢 13%**）；跨机更甚 | `max_remote_latency_ms` 或 `prefer_local` 权重 |

**→ 所以顶层的语义应是**：

> **默认透明（不提分布式）；可按需查询（`is_distributed`）；可显式约束（禁止/允许远端）；**
> **异常时必须可见（节点失效 → 用户需要知道，而不是静默变慢）。**

## 5. 一个已存在的设计巧合（值得确认）

`solve_pipeline_capacity(..., require_distributed: bool = False)` 的 docstring 原文：

> 「When `require_distributed` is true, a single-node full-model placement is
> **deliberately rejected**; the returned plan must contain **at least two participating nodes**.
> This is used by an **explicitly distributed request**, while **ordinary capacity inspection
> remains single-node efficient**.」

**→ 这正好实现了你要的「默认不关心、可显式要求」**：

| 语义 | 参数 |
| --- | --- |
| 普通请求（顶层不关心分布）| `require_distributed=False` → **单节点高效路径** |
| 显式分布式请求 | `require_distributed=True` → **强制 ≥2 节点** |

**结论：架构上「分布式 vs 本地」的开关已经存在**，无需新增。
