## 0. 执行摘要

四份调研（A 并行手段 / B 开源引擎 / C 跨框架逐层接力 / D ExecuTorch）以及本次 Silica Cluster 外部复核指向同一结论：

**当前没有可直接接入的生产级跨异构引擎，但 llama.cpp RPC 是唯一已有 Android 实现参考、且值得本项目主动攻克的模型分片入口。** 本地新增实验又证明了 L→L 裁层 GGUF + `embd` hidden handoff 的 16/16 行为等价，因此增加一个 PC-only Relay 架构兼容轨道；它不替代 RPC，也不把 D→L、跨进程/网络或长序列写成已支持能力。任务图/整请求分发仍有价值，但只能解决“某个节点已经装得下完整模型”的迁就场景，不能替代“单机装不下、节点各持一部分”的分布式目标。

> **2026-10-07 结论更正（原文「PyTorch 层流水线保留为 PC 对照和 Relay 来源」已过时）**：
> PyTorch/Safetensors 层流水线自 2026-09-16 起是**有 CUDA 节点的默认加速 backend**
> （见 [QLH 异构分布式形态决策](../../QLH异构分布式形态决策-2026-09-14.md) 的 v7 裁决），
> **不再只是「PC 对照」**；而 Relay（A1）已按 DIST-0 从产品调度入口**剔除**，
> 生产层接力唯一主线是 A3 Route A（`stage_offer_v3`），已于 2026-10-07 在三机产品路径
> 跑通（[真三机产品路径攻坚-2026-10-07](../distributed/真三机产品路径攻坚-2026-10-07.md)）。
> 本文其余「增加 PC-only Relay 架构兼容轨道」相关表述同属历史记录。

本次新增的 [Silica Cluster](https://github.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI) 证明了"Android 原生应用承载 llama.cpp RPC worker"这条工程路径可以实现。**本方向由"隔离候选"升级为攻关**：它是目前唯一有真实实现参考（且含 Android）的"模型切分"路径，上游通道是开着的（对比"跨框架逐层接力"的 issue #27112 仍 open）。需要说清的是：Silica **没有**证明跨节点连续 `layer_range` 协议已存在——QLH 要做的正是把"比例/上限"升级为**可校验的部分驻留/分片合同**；它验证的是**可行性**，不是生产就绪（无身份校验、无传输保护、无租约）。技术原理、分片改造与 G0-G4 闸门见 §2.2.1。

## 1. 调研 A：异构设备上的非线性并行手段

### 1.1 事实基线（本地代码核实）

| 证据 | 位置 | 含义 |
| --- | --- | --- |
| `PIPELINE_MAX_CONCURRENT = 1` | `src/config.py:366` | PyTorch 参考层流水线当前**串行**：同一时刻只有一个节点在算 |
| `PipelineQueue` / `compute_layer_assignment` | `src/scheduler.py:387/2448` | 已有层分配与队列基础，但未做 micro-batch 交叠 |
| 单序列 `llama_decode`（`n_batch = 64`） | `src/llama_engine.py:663-697` | L 档侧当前是**单请求**解码，未启用 continuous batching |

### 1.2 手段评估

| 手段 | 原理 | 本机可行性 | 关键限制 |
| --- | --- | --- | --- |
| Continuous batching（llama-server） | 多请求在服务端动态合批 | ✅ 可行 | 依赖 llama-server 常驻；QLH 侧需接线 |
| 多请求流式交叠 | 串行流水线内交错 micro-batch | ✅ 可行（改造量大） | 需要调度层重写 + 队列/取消/超时语义 |
| 非均匀层分配 | 按显存/算力比例切层 | ✅ 可行 | 需真实标定每层耗时（当前缺失） |
| draft-verify / 投机解码 | 小模型草稿 + 大模型校验 | ⚠️ 受限 | 见 `EX-SPEC-ROLE-01`：本机实测混合词表族不可用、最好仅 1.342× 且分布一致性 fail |
| 级联 / 路由 | 小模型先答、大模型兜底 | ✅ 可行 | 需要质量判据与回退策略（纯调度层，无新依赖） |
| 本地 prefix cache / 会话级 KV 复用 | 复用前缀命中 | ✅ 可行 | 单机内收益明确；跨节点迁移不划算 |
| 跨节点张量并行（TP） | 层内切分 | ❌ 不可行 | 要求同构 GPU + 高带宽互联 |
| 序列/上下文并行 | 序列切分 | ❌ 不可行 | 每步同步 + 带宽门槛 |
| 专家并行（MoE-EP） | 专家分布 | ❌ 不可行 | 本机模型非 MoE；异构下通信开销压倒收益 |
| prefill/decode 分离 | 两阶段分离部署 | ❌ 不可行 | KV 需跨节点搬运（~200KB/token 估算） |
| KV 迁移 / 跨节点缓存 | 缓存移动 | ❌ 不可行 | 同上网带宽门槛 |

### 1.3 伪并行清单（必须避免）

跨节点 TP、跨框架逐层接力、prefill/decode 分离与 KV 迁移、训练式 1F1B/zero-bubble、hidden 压缩、RAM 受限的多副本——这些在本机组合下"看起来并行、实际受带宽或串行依赖限制"。

### 1.4 PyTorch 参考路径的三个对照项（不改变主线）

1. **真实标定 + 非均匀层分配**：先测每层真实耗时与内存，再按比例切层（当前分配缺依据）；
2. **多请求流式交叠**：在 `PipelineQueue` 上引入 micro-batch 交错（把 `PIPELINE_MAX_CONCURRENT=1` 变成可配置且可解释）；
3. **会话级 KV 复用 + 队列优先级**：先做单机收益最大的缓存复用，再叠加优先级调度。

> 估算说明（非实测）：decode 每跳 hidden 约 4KB（1.8B/24 层/hidden 2048/bf16 估算）、KV 约 200KB/token——两者差 50×，这是"带宽不是瓶颈、同步才是"的判断依据。

## 2. 调研 B：开源分布式推理引擎

### 2.1 核心结论

**2026-09 不存在可直接拿来用的“生产级 + 跨异构 + 模型分片”方案。** 这不是放弃模型分片的理由，而是 QLH 的核心科研工程问题：以 llama.cpp RPC 为底座，先验证部分驻留和容量聚合，再补身份、租约、故障和安全合同。

### 2.2 分档推荐

| 档位 | 项目 | 理由 / 风险 |
| --- | --- | --- |
| **值得借鉴设计**（不直接引入） | `accelerate` `device_map` | 零新依赖的同机异构**上界基线**（做对照极合适） |
| | `petals` | 层流水线 + 私有 swarm 语义最贴近 QLH 形态；**2024-09 后停更** |
| | `ktransformers` | CPU 侧 AMX/AVX2 kernel 与 hot/cold 放置思路可借鉴 |
| | `exo` | 拓扑感知放置协议；但 Linux 侧目前仅 CPU 后端 |
| **主攻底座** | llama.cpp `--rpc` + Silica Cluster | 原生 GGML RPC、已有 Android 参考；上游自述 PoC/fragile/insecure，QLH 需补部分驻留、身份、租约、故障和传输保护 |
| **仅作对照实验** | `b4rtaz/distributed-llama`（**新发现**） | 纯 C++ 跨机张量并行、无 torch、CPU worker 可参与；限制：节点数必须 2ⁿ、节点上限 = KV heads 数、量化组合受限（q40/f32） |
| | PowerInfer / MLC-LLM / Xinference / OpenLLM | 定位或异构能力不匹配 |
| **不建议** | TensorRT-LLM / LMDeploy / TGI | 强绑定 NVIDIA 栈或已转维护模式（TGI 为未证实传闻） |

#### 2.2.1 Silica Cluster（Android + llama.cpp RPC）→ 本方向由"隔离候选"**升级为攻关**

> **2026-09-15 方向定档**：Android 参与分布式推理是 QLH 的核心命题之一 —— 既然上游通道是开着的，就应借鉴、改造、迁移、整合、实现，而不是只做隔离验证。

**一、它为什么能用（技术原理；源码/上游核对，非估算）**

1. **底层是 llama.cpp 自带的分布式后端，不是 Silica 自研**：`ggml-rpc-server` 把一台设备的 GGML 后端暴露为 RPC 端点，`llama-cli --rpc host:port[,host:port…]` 让**主 host 把远端设备当作可用 backend**参与同一模型的计算。构建开关 `GGML_RPC=ON` 即启用。本机已有可执行：`runtime/llama-cpp/b10964/ggml-rpc-server.exe` 与 `llama-cli.exe`（`--version` = `0.4.1-dev (build 10964)`），具备**立刻起 PoC** 的条件；PC 的 Python server 也已暴露 `rpc_servers`/`tensor_split` 参数，但不能代替原生 RPC 的驻留实测。
2. **Silica 的贡献是"把这条能力搬到 Android"**：应用内携带 `libllama.so`（主节点角色）与 `librpc.so`（worker 角色），经标准 `--rpc` 接入；`BinaryRunner.kt` 在没有层数元数据时退化为 `--tensor-split` 比例，有层数时把剩余层数交给 `-ngl`。**它证明了 Android 能编译/加载 GGML 后端并以 RPC 方式参与计算**——这正是"Android 不该只当任务池客户端"的第一份外部实证。
 3. **分配语义必须辨析清楚（不因激进而改事实）**：`-ngl` 是"设备最多装载多少层"，`--tensor-split` 是"各设备张量比例"，**两者都不是** QLH 的连续 `layer_range` 合同。QLH 的第一验收目标应定义为**可校验的部分驻留/分片合同**，只有实测能证明连续层所有权时才称为 layer-range。
 4. **"上传整模型"是 Silica 的工程选择，不是 QLH 的目标**：`SilicaService.kt` 的 full-offload 路径先把完整 GGUF 上传到主 worker；QLH 主线必须优先验证标准 `--rpc` 路径是否能让 worker 只持有被分配的部分，并用 RSS/PSS、backend buffer、文件映射和容量上限证据排除整模复制。
5. **安全缺口是可补的**：上游 README 明确本地 RPC **未加密**，Silica 也没有节点身份/模型摘要/租约/故障恢复协议。QLH 侧**已有可用件**：Ed25519 入群合同 + 一次性 nonce（`src/cluster_join.py`）、TOTP 一步确认（`AUTH-TOTP-01` 设计）。

**二、借鉴 → 改造 → 迁移 → 整合 → 实现**

| 阶段 | 具体做什么 | 本机可行性 |
| --- | --- | --- |
| **借鉴** | Android 三件套分工（`libllama.so` 主节点 / `librpc.so` worker / 标准 `--rpc` 接线）；参数化入口 `-ngl` + `--tensor-split` | ✅ 二进制已就位 |
| **改造** | ① **分片合同**：先定义 `shard_spec`/模型摘要/部分驻留证据，再决定能否映射为 layer-range；② **免整模型上传**：验证 worker 只持有分配部分；③ **身份（auth）**：worker 必须持有可验证身份 + 一次性入群授权（复用 `src/cluster_join.py` 的 Ed25519 + 一次性 nonce），高危动作走 **TOTP 一步确认**；④ **可用性**：分片**租约**（有时限、可回收）+ 故障恢复（掉线重分配、恢复不双写）+ **epoch fencing** + 备用主节点快转让 + RPC 限定内网/隧道 | ✅ 先做单机与双进程；③④的完整设计见[形态决策 §2.1](../../QLH异构分布式形态决策-2026-09-14.md) |
| **迁移** | Android Full 构建启用 **`GGML_RPC=ON`**，产出 `librpc.so` 与 `ggml-rpc-server`（**当前构建未启用，是明确缺口**） | ⚠️ 需 Android 工具链 |
| **整合** | llama.cpp 分片成为主形态；任务图只保留完整模型回退；PyTorch 只保留 PC 对照 | ✅ 设计层 |
| **实现** | 四步升档：**G0** 裁切/低耦合门 → **G1** PC 单机 → **G2** 同机 host + 1 worker 双进程 → **G3** PC 跨机 → **G4** Android 真机 worker | ✅ **G0-G2 可本机先做** |

**三、为什么这条线值得激进**

QLH 的命题是"异构 + 弱节点也能参与算力"。llama.cpp RPC 是目前**唯一**有真实实现参考（且含 Android）的"模型切分"路径——相比"跨框架逐层接力"（上游无公开中间层 API，已止损），它的**上游通道是开着的**。做成它，等于给"Android 从客户端变成算力"提供第一条可验收路径。

**四、保留的边界（激进不等于丢失纪律）**

- Silica 是 **AGPLv3**：**不复制其代码**，只借鉴协议边界与验证方法；直接集成前须单独做许可证与发布形态评估。
- 仍**不宣称**"跨 Android 精确按层拆分"已被验证；当前主张是“llama.cpp 模型分片/RPC 为攻关主线，PyTorch 仅 PC 对照”，实测不通过就保留单机/任务图回退。
- 证据等级不变：Silica 的结论为**上游源码核对**（非本机复现）；"升级为攻关"是**方向定档**，不是把既有证据升级。

### 2.3 三个关键问答

- **a. 混合设备（含无 CUDA 节点）跑 Transformer 有成熟方案吗？** 没有。现有分布式引擎都以"同构加速器 + 高带宽互联"为隐含前提。
- **b. 是否能用 PC llama.cpp 替代 torch 生产路径？** 可以作为攻关假设，但必须依次通过单机基线、同机双进程部分驻留、PC 真机 RPC 和故障/安全门；在全部门通过前不能删除 PyTorch 回退。
- **c. 有没有方案能替代“完整模型任务图”？** llama.cpp RPC 是唯一值得主动验证的模型分片底座；任务图只能作为迁就回退，不能回答单机装不下的问题。

## 3. 调研 C：跨框架逐层接力与 Relay（2026-09-16 基线更新）

### 3.1 核心障碍（上游原文支撑，强度：强）

| 障碍 | 事实 | 来源 |
| --- | --- | --- |
| llama.cpp **无公开中间层 API** | 公开接口只提供 token embedding（`llama_batch.embd`，`n_embd` 维）与 logits；post-block residual 无公开读写通道 | llama.cpp 上游 issue **#27112**（open，2026-08-15）："没有公开方式读取中间层，需要的人都在维护私有 fork" |
| 层间观测需自研补丁 | 只能走 `ggml_backend_sched_set_eval_callback` 一类内部钩子 | 同上（ggml-backend.h 全文抓取） |
| 先例不对口 | Petals = **同框架**（PyTorch）层接力；KTransformers = **算子级**混合（非 hidden 交接）；distributed-llama = **张量并行**（非层接力） | 各自 README（抓取） |
| 层语义差异（待 PoC 核对） | QKV 融合布局、RMSNorm eps、GQA 布局、RoPE 实现、attention mask 约定——GGUF 与 HF 导出逐层差异需 `convert_hf_to_gguf.py` / `gguf-py` 逐项核实 | **标注为待核对**（本次未逐项验证） |
| 量化误差累积 | **未查到**公开的跨框架逐层误差测量 | 未查到 ≠ 不存在 |

### 3.2 最小 PoC（若将来重启，5 步 + 判据）

1. 单机内用带钩子的 llama.cpp 补丁取第 k 层 hidden；
2. 同一权重在 PyTorch 侧复现前 k 层，逐层对拍；
3. 未量化路径判据：**cosine ≥ 0.999** 视为对齐（否则终止）；
4. 换 Q4_K_M 路径重测，记录误差是否随层数放大；
5. 只有前两步成立，才评估跨节点传输与协议设计。

### 3.3 重启条件（满足任一）

- llama.cpp 上游提供**公开**中间层读写 API（issue #27112 关闭）；
- QLH 需要一个**无法用"只传 token"方案解决**的异构分工场景（例如某设备只能承担特定层且必须跨框架）；
- PyTorch 参考路径的串行流水线被证明是首要瓶颈，且 micro-batch 交叠已到上限；
- 出现成熟的第三方跨框架层接力项目可直接引用。

### 3.4 重启评估（2026-09-15：放宽约束 + 上游实查后）

**结论：L→L 的本地架构闭环已成立，D→L 的长序列行为等价亦已打通。** 上游调用方按 `n_pos_per_embd * n_tokens` 提供 `pos` 后，D→L 141-token prefill、逐步生成、f32 权重对照与跨机 SSH 隧道逐步生成均严格 `141/141` 逐 token 一致，`CORE-RELAY-XFRAME-01` 按正确性即准入。当前索引见[跨框架接力-当前有效基线与后续优化计划](../../跨框架接力-当前有效基线与后续优化计划-2026-09-21.md)。

### 4.2 决策（2026-09-15）：实验先行，接入另议

**策略变更**：不再采用"等 GGUF 硬缺口或真机 >1.5× 才立项"的条件式观察；改为**主动实验**——ExecuTorch 实验本身**立即立项**（票 `CORE-ET-EXP-01`，独立环境，不阻塞主线），**是否接入主项目（第三引擎 / Android 端侧替代）另行裁决**；实验价值不依赖接入结论。

**实验目标（不预设结论）**：
1. 独立环境用官方链路导出 Qwen3-4B `.pte`（int4），记录转换链路与算子覆盖；
2. Android 真机跑通，采集 TTFT / decode t/s / RSS / 体积；
3. 与现有 GGUF + llama.cpp（`libqlh_llama_jni.so`）在同机同量化级别对照；
4. 产出可复现证据（数据 + 命令 + 版本号），作为后续裁决依据。

**接入裁决条件（实验后再评估，需至少满足其一）**：
- GGUF 出现**硬能力缺口**（某目标模型无法转换/量化）且 Android 有明确需求；
- 真机同量化级别 **decode t/s 领先 > 1.5×**（实测量，非官方页面数字）；
- Kotlin 生态集成在工程成本/维护性上**显著优于**现有 JNI 路径（需量化对比）。

### 4.3 实验步骤（已立项：`CORE-ET-EXP-01`）

① 独立环境导出 Qwen3-4B `.pte`（int4）→ ② 真机验证与现有 JNI **同进程共存** → ③ TTFT / decode t/s / RSS / 体积对照 → ④ 记录算子覆盖与输出质量差异 → ⑤ 出报告交裁决（接入与否另议）。

环境隔离要求：实验依赖**不进入** L 档边缘安装与主仓运行时（"无 torch 可运行"硬约束保持）；实验产物与脚本独立存放，不并入主线发行。

### 5.1 对主线计划止损清单的影响

- **ExecuTorch 条**：维持 2026-09-15 的"**不立即合入 + 实验先行**"（由 `CORE-ET-EXP-01` 在独立环境执行）——止损只约束"立即合入"，不约束实验；接入裁决条件见 §4.2。
- **GGUF RPC 条**：原表述"不把 llama.cpp RPC / Silica 式 Android RPC 接成默认生产路由"是**保守止损**。现改为**分阶段准入**：S1/S2 PoC 通过，**且**身份校验、传输保护、回滚与 soak 证据齐备后，**允许作为 Android/GGUF 侧的正式路径接入**；在此之前仍不默认开启。即**止损对象由"方向"收窄为"未验收前的默认开启"**。

### 5.2 性能实测收口（2026-09-16，D→L 跨框架接力）

**背景**：§3 的跨框架接力已从"当前不推荐开工"转为"可研究、前置成本下降"。本节补齐此前缺失的**性能维度**收口。

**实测**（本机 RTX 4060 Laptop 8GB，prompt=5，gen=64，下游 f16 裁层，**全程 64/64 argmax 一致**）：端到端优化链的逐档数据（跨进程全段重算 182 s → 同进程 + 双侧 KV 复用 + 上游只跑前 4 层 21.3 s，总计 8.5×）见[跨框架层接力重启评估 §7](跨框架层接力重启评估-2026-09-15.md)与[跨框架接力性能优化-汇总报告](跨框架接力性能优化-汇总报告-2026-09-16.md)；该链为 **CPU 上游历史口径**，当前 D→L 索引见[跨框架接力-当前有效基线与后续优化计划](../../跨框架接力-当前有效基线与后续优化计划-2026-09-21.md)。

**各手段单独收益**：KV 复用 **3.15×** / 上游只跑 4 层 **10.7×**（上游侧）/ 下游 GPU offload **2.18×**。
**证伪项**：消除进程边界 8%、复用 `llama_batch` ≈0、朴素层截断数值破坏（0/8）。

**★ 结构性结论（对 §3 的重启判断有直接影响）**：

1. **接力在单序列上不具备性能优势** —— 最优 333 ms/步 vs llama.cpp 原生整模 GPU **13.5 ms/步**（差 **≈25×**）。⚠️ 口径注（2026-09-19 核）：参照不唯一 —— 按 `13.5 ms/步` 算 **≈25×**（`333 ÷ 13.5 = 24.7`），按 `-ngl 24` 的 `26.6 ms/token` 算 **12.5×**；参照谱与算式见 [跨框架层接力-实验数据汇总](跨框架层接力-实验数据汇总.md) §F/§H。
2. **根因是 batch=1 的 memory-bound 特性** —— 上游 torch-GPU **9.2 ms/层** ≈ 下游 llama.cpp-CPU **8.3 ms/层**；
   **决定速度的是"搬运多少字节"，不是"CPU 还是 GPU"**；
3. **低精度不是解** —— 实测上游 f16 **反而慢 8.4×**、bf16 慢 8.7×；NF4 只慢 1.09× 但**也无速度收益**
   （4 层场景是**延迟受限**而非带宽受限）→ **NF4 的价值在容量（7 GB → 1.8 GB），不在速度**；
4. **上游侧已无优化空间** —— 4 层计算占 **97%**，固定开销仅 **4.7%**
   → **CUDA Graph 等 launch 优化最多省 ~5%，不值得做**；
5. **→ 接力的正确定位是「能力组合」**（能跑 llama.cpp 跑不了的东西），**不是「提速」**。

**与 §3.3 重启条件的关系**：本节**不改变**重启条件的技术判断，但**显著降低了"以性能为目的"的重启动机**；
若重启，应以**能力/兼容性**为目标，而非吞吐。

**完整证据**：[跨框架接力性能优化-汇总报告](跨框架接力性能优化-汇总报告-2026-09-16.md)（含五次自我推翻与全部数据）、
[同进程双后端接力实现与性能](同进程双后端接力实现与性能-2026-09-16.md)（实现细节与逐轮剖析）。

## 6. 证据强度与未决项（诚实清单）

**强证据（上游原文/仓内可复跑）**：
- PyTorch 参考路径的串行与层分配入口（`src/config.py:366`、`src/scheduler.py:387/2448`）、llama.cpp 单序列解码（`src/llama_engine.py:663-697`）；

- 开源引擎对比表中的版本/star/近况（部分未逐条核实，TGI "维护模式"为未证实传闻）；

- 跨框架逐层接力的量化误差公开测量；
