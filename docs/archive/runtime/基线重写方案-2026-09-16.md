## 1. 目标形态

### 1.1 节点角色（两级 + 边缘形态）

```text
                 ┌──────────────────────────────┐
                 │  主节点（Control）            │
                 │  调度 / 合同 / 舰队 / 租约     │
                 │  compute = optional（可关）   │
                 └───────────┬──────────────────┘
                             │  合同：任务 / 分片 / 模型
        ┌────────────────────┼────────────────────┐
        │                    │                    │
┌───────▼────────┐  ┌────────▼─────────┐  ┌───────▼──────────┐
│ 算力节点 W-GGUF │  │ 算力节点 W-torch │  │ 边缘节点 Edge     │
│ llama.cpp/RPC   │  │ 有 CUDA 的节点    │  │ ≤1B 本地推理      │
│ 全平台          │  │ 默认开启(D 档)    │  │ + 可选 RPC 席位   │
│                 │  │ 可关闭→退化 GGUF  │  │ 无 torch（硬约束）│
└────────────────┘  └──────────────────┘  └──────────────────┘
```

- **角色与引擎解耦**：`node_role ∈ {control, control+compute, compute, edge}` 是**运行时身份**（配置 + 注册时声明），不是安装包差异；同一安装包可跑任意角色（Edge 无 torch 预检仍成立）。
- **主节点默认只调度**：`compute=false` 为默认；开启后才参与计算（保留单机演示与小组网形态）。
- **按画像选档**（沿用 v3/v5 的画像策略，v7 修订）：`device_profiler` 结论 + 模型档位 → 决定节点以 L 档（GGUF）还是 D 档（torch）参与。**v7 明确两条方向相反的回退纪律**：
  1. **有 CUDA 的节点**：保留 torch 能力并**默认开启**（显式开关可关闭）；关闭后**退化为 L 档（llama.cpp）**，不因关闭而不可用；
  2. **无 CUDA 的节点（含 Edge）**：**不允许**引入 torch —— 画像判定无 CUDA（或 torch 不可用）时一律以 L 档参与，**不得因 D 档不可用导致节点不可用**。
  3. 两条都会被"能力表"如实上报，参与资格按能力标签判定（不按硬件型号硬编码）。

### 1.2 引擎档位与 torch 按需（进程内延迟加载）

**档位定义（v7 修订）**：

| 档位 | 依赖 | 参与能力 | 可用平台 |
| --- | --- | --- | --- |
| **L 档** | 无 torch（**硬约束**） | 单机 GGUF 推理、RPC 模型分片（host/worker）、TUI 对话 | Edge / PC / Android / **任意无 CUDA 节点** |
| **D 档** | torch（**按需引入，有 CUDA 节点默认开启**） | PyTorch 层流水线、跨框架层接力（含 CUDA 节点作为 D→L 来源侧） | **有 CUDA 的节点**（PC/工作站/CUDA 服务器）；**不适用无 CUDA 节点与 Edge** |

**backend 归属（v7 新增）**：两档都是 **Koakuma** 的内部 backend —— 上层只调用 Koakuma 的统一接口，**"这个节点用 llama 还是 torch"由引擎层按画像决定**，调度层与其它层不关心（这是本项目"高内聚低耦合"的核心判据之一）。

实现约束（可测）：

1. **入口模块顶层不得 `import torch`** —— `llama_engine.py` / `qlh_edge.py` / TUI / 调度器入口全部满足；torch 只在 D 档执行路径内部延迟导入。
2. **可断言**：新增 import 检查测试（无 torch 环境下启动 Edge 入口并断言 `"torch" not in sys.modules`），接入现有边缘基线门（≤300MB venv / ≤15s 冷启动 / 无 torch）。
   - **已知现状缺口（2026-09-16 架构核查）**：`src/api_server.py:37`、`src/config.py:162`、`src/paged_kv_cache.py:38`（顶层）、`src/scheduler.py:101,5068` 仍出现 torch 符号，当前仅靠 `try/except` + `_LazyModelManager`（`model_host.py:45-67`）单点兜底 → 属 R3 的待收口项。
3. **Android 不引入 torch**：保持现有 llama.cpp + JNI 形态，本文档不为 Android 增加 torch 计划。
4. **两个默认值都要显式且入档**（v7）：**Relay 默认关闭**；**有 CUDA 节点的 torch backend 默认开启但必须可显式关闭并退化**。任何"隐式默认"都不作为验收依据。

### 1.3 调度与算力解耦（主节点 + 可选算力）

- 调度器不假设"自己所在节点必然参与计算"：分片/层分配只依据**注册能力表**（引擎、模型、层驻留、内存、加速器）。
- 主节点关算力时：自身不出现在候选算力集；`control+compute` 时按普通算力节点参与（同一套画像与容量门）。
- **调度层对 backend 选型不敏感**（v7 明确）：调度只看到能力表与合同，不读 `_engine_type` 之类的引擎内部状态。**已知现状缺口**：`scheduler.py:2412,10381,10737,13333` 等仍穿透 `mgr._engine_type` / `mgr.tokenizer` → 属 R2/R4 的待收口项。
- **租约/故障语义不变**：单请求内任一环节失败即结束 attempt 并按可恢复边界重试或降级（沿用现行纪律）。
- 交付形态不变：`qlh chat`（TUI）与最小 HTTP（`qlh_edge`）继续是数据面对外面。

### 1.4 层接力 Relay R（新能力，依托 §7.8–§7.11）

- **形态**：`节点 A（llama.cpp，算 layer 0..k）→ hidden → 节点 B（llama.cpp 裁层模型 + `embd` 注入，算 k+1..N）`；`A=torch / B=llama.cpp` 是仍在验证的 D→L 变体：短序列存在性已证，但长序列行为等价未通过。
- **已具备（逐条有实测）**：
  - **注入通道**：`llama_batch.embd` 接受任意 `n_embd` 向量（§7.8）；
  - **裁层模型可用**：保留 `blk.K..` 并改 `block_count` 即可，**llama.cpp 源码无需改动**（§7.9）；
  - **两侧 hidden 语义一致**：fp16 逐层 cosine = 1.000000（§7.2）；**XFRAME 首轮补充**：llama.cpp 自身 layer 3 hidden 与 PyTorch hidden 平均 cosine **1.0**、最大绝对误差 **≈2.44e-4**；
  - **逐 token 接力端到端一致**：A（整模型，layer 0..3）→ B（裁层模型，`embd` 注入）贪心生成 **16/16 步与整模型完全相同**，三次独立运行未分叉（§7.11.1）；该结论只覆盖 L→L 同机单进程。
- **未具备**：跨节点传输与同步、调度与图重建代价、异构算力配比；**误差累积已有首批数据**（§7.10：逐位置 cosine 由 1.000000 累积到 0.9955，argmax 5/5 一致）。
- **D→L 根因与修复（XFRAME，2026-09-16 晚 —— 已定案）**：
  - **首轮控制组（prefill 口径，其读数已被推翻）**：141-token f16 **132/141**（首分歧 18）、f32 **128/141**（首分歧 14）；当时据此把根因判为"llama.cpp 长批 `embd` 输入图/续算路径" ✗ —— 该判断**错误**。
  - **实际根因（上游给出 + 本仓库独立验证）**：`llama_batch_allocr::ubatch_add` 在 **M-RoPE 模型 + `embd` 批次**时读 `batch.pos[0 .. n_pos_per_embd*n_tokens)`，而 `llama_batch_init` **只分配 `n_tokens` 个 `pos`** → **调用方 `pos` 数组的堆越界读**（上游 valgrind 实证：`Invalid read of size 4 … 0 bytes after a block of size 20 alloc'd`；与 `pos == NULL` 的 #28902/#28910 是同一循环的孪生情形）。
  - **修法（调用方）**：`embd` 批次的 `pos` 按 `n_pos_per_embd * n_tokens` 分配，且每段都填 `pos[j*n_tokens + i] = i`（Qwen3.5 的 `rope.dimension_sections` 为 4 段，故 `n_pos_per_embd = 4`）。
  - **修复后实测（本仓库：Windows 11 / MSYS2 UCRT64 / Qwen3.5-2B f16 / CPU）**：

    | 实验（同一 exe、同一输入） | 修复前 | 修复后 |
    | --- | --- | --- |
    | `embd` 同输入连跑两次（141 位置） | argmax `126/141`，cosine 0.85–0.99 | **`141/141`，cosine min = `1.000000`** |
    | `embd` vs token 路径（同一 prompt） | argmax `132/141` | **`141/141`，cosine min = `0.999999`** |
    | `llama-relay-gen` L→L 141 步生成（连跑 2 次） | 第 46 / 51 步分叉 | **`全部 141 步一致`（2/2）** |

  - **因此作废的结论**：此前"`embd` 路径固有非确定性"、"D→L 长序列拒绝"、"L→L 16/16 边界 ≈16 步"、"分歧是 top-1↔top-2 互换"、"严格判据不可达" —— **全部是该越界读的假象**；"分段短序列接力"不再是必要绕开。
- **工程约束（2026-09-16 晚修订）**：
  1. **契约事实（必须遵守）**：在 **M-RoPE 模型**上使用 `embd` 批次时，调用方的 `pos` **必须**按 `n_pos_per_embd * n_tokens` 提供（否则命中上游 #28963 的越界读）；接入新模型前先确认其 `rope.dimension_sections` 长度；
  2. **判据**：接力判定**用逐 token argmax / 生成序列一致**（`judge_relay_generation`），不用 cosine 阈值；**`top_k_tolerant_argmax` 仅作诊断档，不作准入依据**（修复后严格判据已可达）；
  3. 接力实验**固定在单进程内完成**（`relay-gen` 即此形态）；
  4. 若生产形态是 A/B 两进程通信，**"行为等价"与"逐位复现"必须分开声明**（与本次 bug 无关，仍是好实践）；
  5. 本地补丁（仅实验 fork）见 `build/cross-framework-layer-poc/patches/embd-pos-overread-fix-2026-09-16.patch`；**主仓运行时不依赖**，上游若在库侧修复即可移除。
- **定位**：**架构兼容能力，PC only、显式开启**；不进入 Edge 默认路径，不替代 llama.cpp 原生 RPC 分片（RPC 解决部分驻留，Relay 解决 hidden 边界兼容）。`CORE-RELAY-01` 负责 L→L 主仓接入，`CORE-RELAY-XFRAME-01` 负责 D→L/跨进程/网络扩展。

## 3. 分阶段与验收判据

| 阶段 | 动作 | 验收判据（可复跑） |
| --- | --- | --- |
| **R0 基线裁决**（本文档） | 冻结目标形态、模块判定、阶段划分；确认 L/R/P 三条数据面边界 | 当前文档基线生效；代码重写仍以 R1 断点门为起点 |
| **R1 断点与接口冻结** | 产出逐文件断点清单；固化"控制面 → 数据面单向"import 断言；确认对外合同（HTTP/CLI/TUI）不变 | 断点清单覆盖 `src/` 全部 102 文件；import 断言测试通过；现有定向回归通过 |
| **R2 角色解耦** | 引入 `node_role` 与 `compute` 开关；主节点纯调度模式跑通集群；画像→档位选档接线 | 主节点 `compute=false` 时：注册/心跳/分片分配/租约/故障绕行全部通过；`compute=true` 时按普通算力节点参与 |
| **R3 torch 按需** | torch 延迟导入边界；无 torch 环境断言测试；D 档入口收口；**消除 §1.2 已知缺口（`api_server`/`config`/`paged_kv_cache`/`scheduler` 的 torch 符号）** | 无 torch 环境启动 Edge/TUI/调度入口成功且 `torch not in sys.modules`；D 档在 PC 上按需加载成功；**有 CUDA 节点 torch backend 默认开启、可关闭并退化成功** |
| **R4 数据面收口** | llama.cpp 主路径（单机 + RPC 分片）在新骨架上跑通；L/D 档边界固化；**backend 选择收进引擎层（`select_backend(node_profile)`）** | 单机基线（票 `CORE-LLAMA-SINGLE-01` 形态）复跑通过；同机双进程分片（票 `CORE-LLAMA-SIM-01` 形态）复跑通过；Edge 无 torch 预检通过；**调度层不再读 `_engine_type` 等引擎内部状态** |
| **R5 Relay 合同接入** | 将 L→L 已验证形态收口为独立 hidden handoff 合同、裁层工件准入、argmax 对拍和失败回退；不改旧 `LAYER_FORWARD` | L→L 同机单进程 16/16 证据可由主仓最小复现复跑；模型身份、层号、shape/dtype、step/位置和回退状态均有结构化合同 |
| **R6 D→L 与跨边界验证** | 按 XFRAME 首轮确立的四步顺序推进：① 编译验证 `build_inp_embd()` 假设补丁 ② 重跑完整模型 token/embedding 141-token 控制组 ③ 控制组恢复后跑裁层 D→L ④ 实时双进程/网络 handoff、逐 token 生成、采样与误差累积；不把 bitwise 当默认判据 | D→L 长序列逐位置 argmax 全匹配；跨进程/网络结果单独记录；`embd` 非确定性不导致错误 token 或未清理状态；任一项失败都保持生产门关闭 |
| **R7 迁移收尾** | 降级模块退出默认路由/默认安装；归档与文档同步 | 主仓生产发行 = llama.cpp + **Koakuma（按节点选 backend）** + control + TUI + contracts + evidence；Relay 默认关闭但可在 PC 显式启用；**无 CUDA/Edge 安装包不得含 torch 依赖**；降级模块仍可显式启用但不在默认路径；全量测试通过 |

纪律（沿用 v5 与迁移安全规则）：

1. 每阶段先固化断点再动结构；**不删能力，只改归属与默认可达性**；
2. 现有测试是回归门（全量测试作为 R1–R7 的每阶段门）；
3. 不伪造：未测项不得在文档或汇报中写成已达成；
4. 高危变更（大范围移动/删除）先 dry-run（列清单 → 确认 → 执行后验证）。

## 4. 风险与诚实边界

| 风险 | 事实依据 | 处置 |
| --- | --- | --- |
| 重写规模失控 | `src/` 9 万行；`scheduler.py` 单文件 1.4 万行 | 只重写骨架（4 个模块群），其余迁移；每阶段以测试门收口 |
| 破坏已验证能力 | 全量测试 3032 passed 是资产 | 迁移阶段保持全量测试通过；降级模块"退出默认路由"而非删除 |
| 角色解耦引入新故障面 | 主节点不再算力时，分片/租约路径依赖注册表 | R2 单独阶段 + 集群定向回归；`compute=true` 与旧行为等价对照 |
| torch 按需破坏 D 档 | torch 延迟导入易被顶层 import 稀释；**现状已有 4 处泄漏点** | 断言测试 + CI 门；D 档路径在有 CUDA 节点实测；R3 集中收口 |
| 层接力被过度承诺 | L→L 已闭环；D→L 旧的 5-token/141-token 分歧是修复前历史，不能作为当前正确性结论 | 定位为架构兼容轨道；当前合同按正确性证据准入（双主仓矩阵 27/27 已跑完），速度只影响默认路由；长时、远端资产与多段仍待验收 |
| **`embd` 通道非确定性** | 同进程重复 6 次 bitwise 全不等（cosine 0.984–0.9999）；token 路径逐位确定（§7.11.2） | 判据用 argmax；接力实验固定单进程；跨进程形态分开声明；**按"自己查自己修"纪律在实验 fork 定位（不阻塞主线）** |
| **默认值语义相反** | Relay 默认关闭；CUDA 节点 torch 加速默认开启 | 两处都必须显式配置且入档（§1.2 约束 4）；上线前用配置断言测试覆盖 |
| Edge 基线回退 | 现基线：≤300MB venv / ≤15s 冷启动 / 无 torch | R3/R4 复跑边缘基线作为门 |

**历史边界**：本方案是**骨架重写方案**，不是当前实验数据源。本文记录的 D→L 141-token 分歧属于修复前快照；当前正确性、容量和主仓引擎口径以 2026-09-21 当前基线索引为准。`qlh-android` / `qlh-shell` / `qlh-release` / `qlh-toolbox` 四个外置仓不在本方案范围内（只在需要对齐合同时提及）。

## 5. 明确不做（本期排除）

1. 不重写已迁移为外置仓/子模块的能力（产品壳、Android、发布、Koakumix、docagent、bridge、spawnledger）；
2. 不为 Android 引入 torch；**不向无 CUDA 节点引入 torch**；
3. 不扩展 `LAYER_FORWARD` 为通用张量协议（沿用整体架构 §5 的边界）；
4. 不让任务图体系回到默认路由；
5. 不把层接力写进 Edge 默认路径；
6. **主仓不依赖修改后的 llama.cpp 上游**（`embd` 非确定性、长批 `embd` 输入图等只作为上游 issue 素材收集）；**实验 fork 内的假设补丁仅用于定位，不得成为主仓运行时依赖**，若验证有效再单独评估向上游提交（人审后提交）。
