## 2. 不可改变的架构不变量

后续所有修复、优化和重构必须同时满足以下约束：

1. **星状拓扑不变。** master 是唯一协调节点和 worker 数据转发中心；worker 不建立 worker peer 数据连接。
2. **D→L / L→L 多段逻辑接力不变。** 去掉的是 worker 直连能力，不是层段顺序，也不是跨框架接力能力。
3. **Route-A 产品主线不回退。** Route-A 继续由 master 顺序编排各段；task graph/workflow 保持实验入口，不重开为默认产品路由。
4. **执行契约必须可验证。** task、step、model、config、assignment 和相邻段关系必须由 master 的冻结契约校验，不能相信 worker 自报的目标或前驱。
5. **失败必须具名且只有一个终局。** 不允许在 API、scheduler、solver、worker 各层重写真因，或同一请求同时呈现多个互相矛盾的结果。
6. **未来重构与当前修复隔离。** 当前修复票可以在 `dev` 上局部落地；结构重构必须另建干净分支并设置行为特征测试门。

## 4. 审计后的风险地图

### 4.1 已确认缺陷

1. **legacy 层流水线仍残留 worker peer 数据能力。** 原实现既能发起 `pipeline_peer` 连接，也能接收非 master 的 `LAYER_FORWARD` / `CHAIN_FORWARD`。只删除发送函数不足以保证星状拓扑。该项由 `ARCH-STAR-01` 处理。
2. **引擎、模型路径、量化和层段能力没有联合裁决。** `.gguf`、PyTorch、量化和运行时能力在多个入口分别判断，已经出现同一输入在 load、switch、自动加载和 scheduler 得到不同答案的确定分叉。
3. **模型/工件一致性检查发生得太晚。** worker 工件与请求模型不一致时，可能进入 step 0 后才以 hidden width 或 stage error 失败；应在准备或加载阶段拦截。
4. **普通聊天与 SSE/interactive 的会话事实源分叉。** 该缺陷已由 `CHAT-CONTEXT-01` 在代码层闭合；真实客户端断开、跨进程与发行物组合仍按验收轨复核。
5. **发行角色和版本事实源分叉。** 该缺陷已由 `PKG-CONTRACT-01` 建立 canonical 合同并通过代码/配置门；最终签名产物的干净安装证据仍未建立。
6. **Android 恢复能力不足。** SAF 授权丢失后缺少默认目录扫描和自动工件匹配；DataStore 损坏可能形成永久启动崩溃。

### 4.2 条件风险

1. 掉线或 opted-out 节点是否完整进入 `excluded_nodes`，以及 relay 覆盖是否被容量求解重复算成缺口，仍需先写 characterization test；当前只能作为 #84 N10/N11 候选，不能写成生产已发生。
2. bootstrap 密钥获取、`cluster_secret` 落盘、legacy TCP 准入、轮换/撤销和 Android 备份边界已由 `SEC-BOUNDARY-01` 收敛为明确合同；剩余风险转为外部验收：Android Keystore 尚未真机执行 instrumentation，Windows 干净机迁移、签名 release 备份/恢复和真实 Tailnet 撤销流程尚未验证，loopback WSS 仍只算诊断门。
3. 多候选 auto-role、journal replication、quorum commit watermark 和物理故障恢复缺真实跨机证明，不能宣称生产 HA。
4. Surface 侧掉线、重连和严格半开时序仍缺外部设备复验；两机 Y700 证据不能自动推广到全部节点类型。

### 4.3 结构债

1. 引擎能力矩阵至少有多份实现，且别名、量化、层段模式和 runtime 条件并不一致。
2. 容量、覆盖、relay 段和失败 reason 被 scheduler、solver、API 和 UI 重算或改写。
3. assignment 多事实源已由 `ASSIGN-SOURCE-01` 收敛：active expected contract、ACK receipt、identity 和 phase 统一进入 `_worker_assignments`；旧 `_layer_config_expected/_acks` 已删除。后续只在该 registry 与冻结 task contract 的边界上演进，不再恢复平行状态。
4. 准备、accept、execute、relay、fallback 原先各自拥有超时常量；该缺口已由 `DEADLINE-01` 收敛为 admission 创建的单一不可变 deadline，各阶段只能消费剩余预算。heartbeat、worker lease 和 TCP liveness 仍保留独立语义。
5. 模型切换的原子事务缺口已由 `MODEL-TXN-01` 在代码层闭合；按需下载和跨请求排队仍是后续能力缺口，不再与失败回滚混记。
6. 会话历史、当前 session、SQLite 持久化和各聊天模式的统一服务已由 `CHAT-CONTEXT-01` 落地；后续只在不破坏 revision/CAS 合同的前提下讨论并发优化。

### 4.4 外部验收缺口

1. Windows/Linux 干净机、全新用户目录、新 shell 和双栈真实网络。
2. 当前新契约构建出的安装包、签名 release APK、native 库和包体边界扫描。
3. 至少两个不同远端节点的 Route-A 自动化产品门，要求连续有序两段、每段真实 handoff、`fallback=false` 和星状连接证据。
4. 多候选 auto-role、journal 复制和物理故障注入。
5. 9B 大工件真加载接力、大显存/CUDA 构建和真实运营商弱网。

## 5. 排票顺序

票序以“先封住拓扑旁路和伪成功，再统一事务与事实源，最后决定结构重构”为原则。外部验收单独成轨，不能拿设备缺口阻塞已完成的代码票，也不能拿本地 mock 冒充产品验收。

### 票 1：`ARCH-STAR-01` 星状数据路径硬化（P0，代码完成，未提交）

目标：移除 legacy 层流水线中的 worker→worker TCP 数据能力，同时保留 D→L / L→L 多段逻辑接力和 `CHAIN_FORWARD` 的 wire 名称。

范围：

- 删除 worker peer client、地址解析、连接缓存和主动直连函数。
- worker 只把中间 hidden 通过既有 master 连接上送，并用 `_relay_to` 声明下一逻辑段。
- master 校验连接身份、task/config/model/step 契约和相邻段关系，再向下一 worker 发送 `CHAIN_FORWARD`。
- worker 不接收非 master 来源的 `LAYER_FORWARD` / `CHAIN_FORWARD`。
- `pipeline_peer` 注册在协议层和 scheduler 层 fail-closed。
- 下发给 worker 的逻辑路由只含 `node_id`，不含 peer host/port。

完成定义：

- 代码中不存在 `_send_chain_forward`、`_chain_clients`、`_get_node_address` 的生产实现或调用。
- 非 master 数据帧不能执行模型、修改 KV/step 或发送成功 ACK。
- 三逻辑段测试证明实际顺序为 `master→w1→master→w2→master→w3→master`。
- Route-A 现有顺序接力行为不变。
- 专项测试、TCP 回归、API/Android gate 和文档检查通过。

不做：不重命名 `_relay_to`，不扩大 wire 协议，不改 Route-A 编排，不在本票拆 scheduler 大文件。

### 票 2：`ENGINE-RESOLVE-01` 引擎、路径、量化和层段能力联合裁决（P0，代码完成，未提交）

目标：一次解析同时产出 engine、model path、quant、runtime 和 layer-range mode，禁止入口各自纠正一遍。

完成定义：

- `.gguf` 不得进入 PyTorch loader；别名在 API、scheduler 和 worker 得到同一答案。
- `load_model`、`switch_model`、自动加载和分布式准备共用 resolver。
- 真实 resolver 行为有直接测试，不能只 monkeypatch。
- `fp32`、CUDA fp16/int8/int4 和 CPU-only 能力转换必须显式，禁止静默改变对拍精度。
- solver reason 在 scheduler/API 层只能追加上下文，不得覆盖原始 reason code 和缺口范围。

2026-10-09 实现与验收记录：

- 新增依赖轻量、不可变的统一 resolver，一次返回 model identity、effective engine、artifact path、effective quant、runtime、layer-range mode 和具名 reason；API 主服务、inference-svc、ModelHost/ModelManager、自动加载及分布式准备消费同一裁决对象，不再在实际 loader 前二次改判。
- 引擎请求别名单源化并 fail-closed；`llama_cpp` / `llama.cpp` / `llama-cpp` / `llama` / `gguf`、`pytorch` / `torch`、`island` / `tp_island` 在 API、task-worker wire、scheduler/worker 工件匹配和 RPC/pipeline node 合同中归一为同一 backend，未知值不再静默回退。
- backend 能力查询也改为 fail-closed：`external_api`、`speculative_assisted`、`relay_middle` 及拼写错误不再被默认映射为 llama.cpp，也不会获得 `FORWARD_LAYERS` 后误入层段拓扑；配置中的未知本地 engine 直接拒绝，不再按 CUDA/CPU 静默退化为 auto。
- 层段模式明确分为 PyTorch `dynamic`、llama.cpp `precut_artifact`、island `none`。通用层段请求按所选引擎保留对应实现；显式 llama.cpp 分布式请求不再被静默改成 PyTorch。
- inference-svc 与 legacy peer 的层段入口已去掉“先加载整模、再加载层段”的峰值错误：PyTorch 直接按 key 物化指定 Safetensors 层段；llama.cpp 先准备整模描述器，再按 manifest 选择预切 GGUF 工件。星状拓扑、master 顺序编排及 D→L / L→L 接力不变。
- 预切 GGUF 工件选择不再只按 `source_layer_range` 猜测：manifest 必须同时给出并通过 `source_model_sha256`、`artifact_sha256` 校验；同目录混放其他模型的同区间工件会被忽略，段文件被篡改会被拒绝，同一源模型出现多个有效同区间工件时 fail-closed，避免按文件名顺序静默选错。
- 段工件选择时强制重新计算工件 SHA，不复用跨次选择的摘要缓存；即使文件被同尺寸替换并恢复 mtime，也会在下一次选择时被拒绝。显式 llama.cpp 请求若给出非 `.gguf` 路径也直接拒绝，不再回退到全局遗留 GGUF。
- `.gguf` 进入 PyTorch 的路径在 resolver、ModelHost 和 ModelManager loader 三层 fail-closed；有注册画像的 model id 在画像路径失效时不再回退到另一个模型的全局遗留路径。
- CPU-only PyTorch 的 fp16/int8/int4 请求在裁决阶段显式转为 fp32；设备画像强制 edge/mobile/ultrabook 使用 CPU 时也执行同一裁决。CUDA 完整模型保留 fp32/fp16/int8/int4，其中 fp32 已真实传入 `torch.float32`；CUDA 动态层段的 int8/int4 请求显式转为 fp16。
- GGUF 的 effective/runtime quant 统一标记为工件所有的 `gguf`，不再把调用方传入的 `fp32` 等标签伪装成实际工件精度；原始请求仍保留在 `requested_quant`。
- 自动加载统一使用 artifact/CUDA preference；Safetensors-only 不再把 `gguf` 作为 PyTorch quant；inference-svc 的运行模式从生产 `RUN_MODE` 初始化，分布式裁决分支不再只存在于测试注入。
- 分布式 `/api/models/load` 省略 `model_id` 时，容量判定现在使用 resolver 已解析出的默认模型标识，不再把 `None` 当作“需求未知”后静默强制整模加载。
- resolver/API/host/manager/inference/capacity/task-worker/pipeline-contract（含 relay manifest 与 llama.cpp 预切工件）回归 `612 passed`，scheduler/TCP 回归 `429 passed`，reshard/inference-routing/relay/cut-layer 邻接回归 `79 passed`；相关模块 `py_compile`、文档检查与 `git diff --check` 通过。该证据是本地代码门，不替代后续真实 CUDA、Android 和跨机发行物验收。
- 复核残余边界：inference-svc 的直接分布式加载端点目前执行联合 resolver，但不执行主 API 的整模容量判定。当前未证明它承担 master 容量编排职责，暂不扩大本票；在票 4 `MODEL-TXN-01` 前先补角色 characterization，若它是公开主控入口，则必须共用同一加载形态决策。

### 票 3：`MODEL-PREFLIGHT-01` 模型与 worker 工件事前一致性（P0，代码完成，未提交）

目标：把 `model_id`、hidden size、tokenizer、artifact SHA、层区间和 segment mode 的一致性检查从每步 offer 热路径前移到准备/加载阶段。

完成定义：

- 选择或加载模型时即判断当前集群是否具备全部匹配工件。
- 不匹配时在进入 pipeline 前具名拒绝，并指出节点、模型和缺失区间。
- 第一阶段只做事前裁决；按需下载和多模型切换另归事务票，避免一次票面同时解决带宽、并发和缓存策略。

实施结果（2026-10-09，已完成）：

- 合同明确区分逻辑模型与物理工件：`source_model_id` / `hidden_size` / `tokenizer_sha256` 描述逻辑模型，原 `model_id` / `artifact_sha256` 继续描述具体 GGUF；`source_model_sha256` 绑定 L→L 各段共同来源的完整 GGUF。
- 自动容量计划和手动计划在 admission 后统一执行 `model_preflight`；校验逻辑模型 ID、hidden width、tokenizer 摘要、源模型摘要、工件摘要、精确层区间、segment mode 和对应的 `llama_cpp/gguf` 物理身份。失败计划清空可执行 assignments，同时保留 `proposed_assignments`、节点明细和 `missing_layer_ranges`。

### 票 8：`DEADLINE-01` 端到端 deadline 与终局收敛（P1，代码完成，未提交）

目标：准备、accept、execute、relay、fallback、cancel 都只消费请求剩余预算；心跳和 lease 保持各自语义，但依赖关系显式化。

完成定义：

- 请求只有一个绝对 deadline，子阶段不得重置完整 timeout。
- 掉线、取消、stage timeout 和 fallback 只能产生一个终局 reason。
- timeout、heartbeat、lease、TCP half-open 和 cancel convergence 的关系有状态图和测试。
- Surface 外部时序作为验收子轨，不与本地代码完成定义混写。

实施结果（2026-10-10，已完成）：

- HTTP admission 只创建一次不可变 `RequestDeadline`：本机等待以 monotonic 绝对时刻为权威，跨进程 wire 只传 epoch 毫秒并在接收端换算成本机 monotonic 时刻。API、inference-service、会话事务、模型锁、scheduler queue/prepare/execute、client→master forward、TaskGraph/provider/worker、relay、fallback 和 commit 均消费同一剩余预算，子阶段不得重新获得完整 timeout。
- 新增 first-terminal-wins latch，成功 `completed` 也必须占据终局，不能被迟到 cancel 反写。用户取消稳定为 `generation_cancelled`，端到端预算耗尽稳定为 `request_deadline_exceeded`，发行/路由拒绝稳定为 `request_refused`；后到的 heartbeat、disconnect、lease expiry、stage error 或迟到成功只进入去重且有界的 `secondary_observations`，不能覆盖已经决定的响应终局。TaskGraph 增加 `result_ready → completed` commit fence，deadline/cancel 之后的结果不得提交为成功。
- request deadline 与 worker ownership lease、heartbeat ACK watchdog、TCP/relay transport timeout 分账：lease 负责 attempt ownership/fencing，heartbeat/TCP 只提供 liveness observation；请求到期后不再续租或开启新连接。worker 等模型执行锁、accept/result、heartbeat ACK 和 pending attempt 均有界收敛。
- relay connect/send/recv/close 使用同一 absolute monotonic deadline，partial send/recv 不能靠持续小片段续命；deadline、半帧或协议失败后 hard-close session。scheduler 与 inference peer 的 relay cache key 去掉动态 remaining timeout，复用同一任务 session 时只允许收紧 deadline；已过期请求在构造 client/TCP 连接前 fail-closed。
- scheduler 的 Q0 抢占 release/reacquire、立即执行与队列执行共享请求内锁所有权状态；恢复锁等待受原 deadline 截断，外层只释放本请求实际持有的锁。流式整模 backend 在线程真正退出前继续持有推理锁；API 已返回 deadline 终局时，不会把仍在退出中的 backend 误判为空闲。
- deadline 终局之后禁止第二层整模 fallback 和 history/result commit；同步 generator/SSE bridge 在 deadline 后有界返回 canonical reason。inference-service 的流式 backend 由独立 owner 线程持有会话事务和模型锁：调用方可在 deadline 后返回，但 backend 真正退出前锁不释放；协作式 cancel 保留原有收敛，非协作 backend 最多等待 250ms 后返回 canonical cancelled 终局。旧 fake/插件若仍使用不含 `request_deadline` 的覆盖签名，通过签名检测保持兼容，但不会撤回 admission deadline。
- 冷启动子进程的 task-journal 问题已查清：跨进程独占锁本身正确，缺陷是 `api_server` import 阶段 eager 构造 writer。现改为 lazy coordinator；import 和 `/api/health` 不争生产锁，首次真实 TaskGraph 使用才物化 writer。若锁已被其他进程持有，执行在调用 executor 前 fail-closed，单写者 fencing 未放宽。
- 状态关系如下；在 deadline/cancel/liveness 这组信号中，request deadline 与 user cancel 可决定请求终局，lease/heartbeat/TCP 维持各自职责并只能作为受栅栏约束的观测或 attempt 终止条件；普通执行错误仍按既有具名失败路径决定终局：

```text
HTTP admission
    |
    v
immutable request deadline
    |
    +--> conversation/model/queue/prepare/accept/execute/relay/fallback/commit
    |
    +--> expiry => request_deadline_exceeded（不可续期）

worker lease
    +--> attempt ownership / fencing
    +--> request 到期后不得续租

heartbeat / TCP
    +--> liveness observation only

user cancel
    +--> generation_cancelled

terminal latch
    +--> first writer wins
    +--> 后到信号只进入 secondary_observations
```

**为什么 `total_layers=32`，以及这是缺口而非设计（2026-10-11 源码核实）**

用户质疑「项目一直避免加载整模，任务图路径就因为这个被踹出生产」——核实后**质疑成立**：

- 求解器判据：`src/pipeline_capacity.py:490`/`:499` 取 `total_layers = len(layer_bytes)`，用于
  ① 校验每个节点 `layer_ranges` 的上界（`:74` `end > total_layers` ⇒ `exceeds total_layers=`），
  ② 计算未覆盖空隙（`:452-453`）。⇒ 它**必须**等于**原始模型**的层数，否则任何远端区间都被拒。
- `layer_bytes` 来自 **`descriptor`**，而 descriptor 由**引擎按当前加载的模型**构造
  （`src/scheduler.py:3352` 读 `descriptor["total_layers"]`；`llama_engine.py:335`、
  `model_module.py:1499` 的 `get_pipeline_descriptor()`）。
  ⇒ 加载 head 工件就把该视图钉成 16。
- **项目的设计意图恰恰是不加载整模**：`pipeline_capacity.py:491-496` 已有
  `capacity_source="relay_exempt"` —— relay 段节点**不占层、不计容量、但算参与节点**；
  `:500-505` 的 `local_layer_budget` 让本机层节点只需放下 `[0, k)`。
  **但这套机制同样要求 `descriptor.total_layers` 是原始模型的 32。**
- ⇒ **真正的缺口**：缺少「**只声明模型元数据（`total_layers`），不加载权重**」的入口。
  这与票12 前文已记的一条吻合：`prepare-pipeline` 走 Safetensors 动态物化，GGUF 预切工件
  **未找到「只 prepare、不 load」的入口**。
- ⇒ **候选修法**（待立项）：① 让 registry 条目可携带 `total_layers`/层元数据，注册即声明；
  ② 或新增「按工件 manifest 声明 descriptor（不加载权重）」的入口（manifest 里本就有
  `n_layer=32`/`block_count=32`）。
- ⇒ 因此「加载 9b 整模（5417 MB）」只是**绕过缺口的手段**（本机 Free 仅 ≈4 GB，有压力），
  不应被当作必须的步骤。

**B. `qwen3-5-9b` 的 safetensors「头部与 index 不一致」结论（子 agent 查证 + 实测复现）**

- 代码路径：`declared` 取 `index.json` 的 `metadata.total_size`（`pipeline_model_descriptor.py:255-274,357`）；
  `observed` 是逐个 `safe_open` 读 safetensors 文件头、按 `shape × dtype` **累加 tensor 数据字节**（`:292-304,
  362-394`）；严格等值断言在 `:418-422`，HTTP 400 由 `routes_models.py:336-355` 包装。
- **实测复现**（我跑的）：4 个 shard 的 header JSON 长度之和 = **94432**，`Σ(8 + header) = 94464`，
  与 `declared - observed = 94464` **完全相等**。
- ⇒ **结论**：工件**没有损坏**；是该 index 的 `metadata.total_size` 用了「**文件占盘字节**」口径
  （恰好 = 4 个 shard 的 `stat` 之和），而服务假定的是 safetensors/HF 规范口径「**纯 tensor 数据字节**」。

  **非** 工件损坏（①）。

### 票 12b：`MODEL-SUPPLY-01` 主节点目标计划与层段工件供给（P1，票 13 前置）

目标：用户在一处选模型后，由 master 计算目标段与缺失资产，调用现有转换/裁层工具，并供给可签验的段包。
现有配置强推只能发布分配，不等于远端取得、校验和加载工件；`plan.ready` 也不能代表所有远端执行器准备完成。

完成定义：

- 输入是一份明确的选模意图、同源身份和实时节点容量；主节点生成连续完整覆盖、资源可承担的目标计划。
- 建立段工件 manifest，绑定源模型、tokenizer、转换证明、区间、角色、逐层字节和实际工件摘要。
- 复用现有元数据检查、容量求解与模型事务；缺少工件时在 master 调度下载/转换/切段/分发，具名报告失败。
- 工件接收支持断点续传、校验与本机登记，不要求用户在每台设备手选区间或导入工件。
- Safetensors 的按 key 加载与传输粒度分别验收；现有下载完整 shard 的行为不能宣传成只传本段字节。
- worker 仅与 master 通信；保持 D→L / L→L 顺序接力及各节点无整模驻留。

兜底供给路径（**就地切段**，当层段传输较慢或不可达时）：

master 分发段工件是主路径，但单个段工件动辄数 GB，跨机（尤其 Android/Termux 侧实测
1.4–4.2 MB/s）传输会成为准备阶段的长尾。因此提供一条兜底：**发行包携带裁层工具，各节点
预先下载源模型后在本地切段并登记本机工件**。这条路径不改变用户流程 —— 用户仍只提交一次
选模意图，由 master 决定某一段是「分发」还是「就地生成」。

- 打包要求：裁层工具与其运行依赖（`scripts/cut_layers.py`、纯 Python 的 `gguf` 依赖、
  以及 `llama_keep_head_worker.py` 一类**子进程脚本**）必须作为 data 显式进包，不能只靠
  import 收集 —— 当前 `qlh-edge.spec` 只含 keep-head worker，尚无裁层工具。
- 只覆盖 GGUF 源：Edge 包内无 `torch`，safetensors 源无法在边缘节点就地切段，需由具备
  torch 的节点转换或仍走主路径分发；不得宣称所有格式都能就地生成。
- 就地产物与分发产物**同口径可签验**：`cut_layers.py` 产出的 manifest 已绑定源模型摘要、
  区间、角色、tokenizer 摘要与工件摘要，master 侧校验一视同仁，不得因「本机自己切的」免检。
- 容量核算计入磁盘与切段峰值：源模型落盘与切段临时占用都进候选容量，不能只算运行时内存。
  「各节点无整模驻留」指**推理期**不驻留整模，与磁盘持有源模型不冲突。
- 就地生成的段仍按分配契约上报区间、角色与逐层字节，不允许回落到「按文件名猜段」。

### 票 16：`MASTER-REACH-01` 远程设备的主节点发现与 bootstrap 可达性（P1）

**状态：修复与验收中（2026-10-14）；完成证据见 [票16–18验收记录](tickets16-18-acceptance-2026-10-14.md)，未完成项不计通过。**

问题：远程设备无法完成「发现主节点 → 绑定」，界面报「未发现可验证的主节点，请确认主节点在线后重试」，
而同一时刻控制面 TCP 是通的。

根因分两层，2026-10-14 同日复测后确认如下。

**主因：主节点不确认自己的身份。**

- 判定入口 `src/scheduler_cluster.py:3167 _verify_master_identity`，其 docstring 第四条写明：
  「本机 MAC 与本地记录无交集 ⇒ 身份验证失败（`mac_mismatch`）（可能是不同机器）」。
  记录存在 `cluster_settings.master_identity_v1`（`src/local_store.py:30`、`:840-870`）。
- 复测现场：该键值为 `{"mac_addresses": ["001122334455"], "bound_at": "2026-10-14T02:30:24Z"}`，
  而本机真实网卡是 `08-bf-b8-2d-f1-38` 等 5 个 ⇒ `mac_mismatch` ⇒
  `src/scheduler.py:1517`「master identity mismatch; no confirmed master discovered」
  ⇒ 主节点**不对外确认自己是主节点** ⇒ 远程必然「未发现**可验证的**主节点」。
- 该假 MAC 的来源是**测试污染**：`tests/test_scheduler.py:10162`
  `test_distributed_start_defers_network_identity` 把 `transport_port.get_mac_addresses` patch 成
  `["001122334455"]`（`:10206`），而 `tests/conftest.py:127 _isolate_local_store` 用
  `pytest.MonkeyPatch.context()` 设的 `QLH_SQLITE_PATH` 会在 teardown 还原；该测试在**后台线程**里启动
  scheduler，线程在 teardown 之后才走到 `scheduler.py:1500 _initialize_network_identity`，
  读到空 env ⇒ `_sqlite_path()` 落回 `%LOCALAPPDATA%\QLH-Edge-Inference\state` ⇒ 把假 MAC 写进用户真实库。
  audit hook 实测栈：`threading._bootstrap` → `scheduler.py:1500` → `scheduler_cluster.py:3199
  _verify_master_identity` → `local_store.set_local_master_identity`，且那一刻 `QLH_SQLITE_PATH=None`。
- 结论：**发现链断在第一环**（主节点自我否认），与远端能否达到 API 端口无关。

**次因：API 端口只绑 loopback（仍是真缺陷，但非本症状的成因）。**

- `android/app/src/main/java/com/qlh/inference/network/MasterDiscovery.kt`：UDP 广播只产出**不可信 hint**，
  其注释写明 `Callers must verify /api/bootstrap/info and complete encrypted first-connect`。
- `src/tui_api.py:30` 的 `DEFAULT_HOST = "127.0.0.1"` 与 `qlh.py:125` 的
  `"host": value_of("--host", "127.0.0.1")` 决定了 auto-start 后端恒绑 loopback
  （该 `--host` 是**客户端要连的目标**，非后端绑定地址；`qlh.py:113-116` 对非 loopback 只移除 `--auto-start`）。
  `src/api_server.py:6740` 的 `run_api_servers(host="0.0.0.0")` 默认值被上述调用链覆盖，且无覆盖项。
- 绑定与访问控制是两件事：`src/model_api_access.py:45` 对 loopback 默认放行，`:52` 否则按
  `QLH_MODEL_API_TRUSTED_CIDRS` 判定。绑 loopback 时远程连包都收不到，配 CIDR 也无用。
- 实测：`Get-NetTCPConnection -State Listen` ⇒ `127.0.0.1:8000`（API）与 `0.0.0.0:8888`、`:::8888`（控制面）；
  Y700 日志 `测试连接: http://<master>:8000` 必失败，`测试连接: http://<master>:8888` 无失败记录。

请注意两层不可互相掩盖：`uvicorn --host 0.0.0.0` + `QLH_MODEL_API_TRUSTED_CIDRS` 的临时绕法
**不能**解决主因，而清 identity 也**不能**让 loopback 端口对远程可达。

完成定义：

- **测试不得改写用户真实库**：任何在测试中启动 scheduler/worker 的路径（含后台线程，
  与 fixture teardown 时序无关）都不得写到 `%LOCALAPPDATA%\QLH-Edge-Inference\state`；
  以「跑完整套单元测试后 `cluster_settings.master_identity_v1` 不变」为判据。
- 后端监听地址可显式配置，默认保持既有行为，**由配置决定是否对外**；对外时
  `QLH_MODEL_API_TRUSTED_CIDRS` 仍是唯一准入边界，不因绑定放宽而放行任意来源。
- 远程设备能完成「发现 → 验证 `/api/bootstrap/info` → 加密首连 → 注册」，无需预置本机临时来源配置，
  也无需预先清理本机 `master_identity_v1`。
- 验收以「新设备只启动软件即可发现主节点」为准；靠临时 `/32` 才可达的路径不计通过
  （沿用 `docs/model-intent-ux-acceptance-2026-10-13.md` 已记录的边界）。
- Android 的「测试连接」判据改用控制面端口或经 worker 转发，不再用 loopback-only 的 API 端口冒充连通性；
  身份类失败必须与网络类失败**可区分地**呈现。

### 票 17：`WORKER-RECONNECT-01` worker 断线后的退避重连与存活判据（P1）

**状态：修复与验收中（2026-10-14）；完成证据见 [票16–18验收记录](tickets16-18-acceptance-2026-10-14.md)，未完成项不计通过。**

问题：worker 与控制面的连接断开后不再重建，master 与 worker 双方互等。

证据（同一次实测）：

- master：`15:25:10 tcp_comm: 客户端 android-d83bf4d0 已断开` 后接
  `scheduler: 节点 android-d83bf4d0 TCP 断开，已标记 offline (old_state=online, role=master)`；
  此后 8888 只有 `Listen`、无 `Established`。
- Y700：断线前心跳正常（`TaskWorkerClient` 的 `heartbeat sent` / `frame received size=78`）；
  断线**之后**仍报 `MainViewModel task worker identity ...` 与 `TaskWorkerService worker_start_reused=true`
  ⇒ 复用了疑似已死的 worker，未发起重连；重启 app 后仍未重连。

**2026-10-14 复测（同日，清掉 `master_identity_v1` 并让 API 绑外部之后）**：
16:28:05 master 记 `客户端 android-d83bf4d0 已断开` + `已标记 offline`，**16:28:20 即自动重连成功**
（`✅ 节点注册成功: android-d83bf4d0 role=client`），随后 `task_worker_hello_acked accepted=True version=3`、
`layer_ranges=[[8,32]]`、`resource_gate_admitted=True`。⇒ 上面的「双方互等、重启 app 也不重连」
**至少部分是票 16 身份失败（master 不确认自己）的次生现象**，不是单纯的重连缺失。
因此本票的判据要能**区分**：身份层失败导致的「假死锁」由票 16 负责，
本票只针对**身份正常时连接被断开**的情形；`worker_start_reused=true` 的语义问题仍未被证伪，保留。

完成定义：

- worker 区分「进程存活」与「连接存活」：连接已死时 `worker_start_reused` 不得复用，必须重建。
- 重连带退避与上限（持续失败给出具名状态）；断线期间界面显示真实状态，不显示「已连接」。
- master 侧 offline→online 恢复可观测（节点列表 + 日志），且不把「进程在跑」当成「已注册」。
- 回归覆盖三种断法：连接被杀、心跳超时、控制面重启。

### 票 18：`SUPPLY-DEDUP-01` 供给去重与「本地可切则本地切」优先序（P1）

**状态：修复与验收中（2026-10-14）；完成证据见 [票16–18验收记录](tickets16-18-acceptance-2026-10-14.md)，未完成项不计通过。**

  （缺工具、磁盘不足、预算超限）时才传输，并在进度里具名说明选择了哪条。
- operation 结束后按保留策略回收可再生段，不以缓存名义无限累积；回收前逐 manifest 核实
  无 native 引用、无 reparse。

## 新增票（2026-10-14，层流水线通信开销削减）

来源：`docs/层流水线通信开销削减-机制设计与规划-2026-10-14.md`（三名只读子 agent 核查后产出）。
背景实测：每段 2 次跨机往返、一次往返中位 19ms，2 段 ≈76ms/步，占整步 195ms 的 **39%**（`docs/已知问题记录.md` #70）。

**贯穿约束（三子票共同适用）**：这些通信路径同时承载分布式可用性机制，**当前稳定可用**。
下列语义在 21c 之前**不得改动**：注册握手 / 心跳阈值（`src/scheduler_types.py:78/82`，task-worker 15s）/
offline-online / 重连退避与**单一重连所有者**（`src/tcp_comm.py:2091-2092`、`:2801-2836`、`:2838-2912`）/
**旧包在重连后到达必须 fencing**（`src/cluster_partition.py:375-404`）/ 心跳栅栏（`src/network_path.py:222`）/
幂等与租约世代 / deadline 收敛（票 8）/ 供给事务性（`src/model_supply.py:431`）/
协议 fail-closed（`src/task_worker_protocol.py:163-234`、`:1304-1313`）。

**新机制一律建立在 `src/transport_runtime.py` 的既有 seam 上**（`mode=legacy_tcp` 是纯影子、**不改 wire 字节**；
断路器 `failure_threshold=3, cooldown=30`；`TransportWindow(1MiB)`；`generation`+`attempt_id` 栅栏），
切换开关**只用能力位/协议版本协商**，且每个子票都必须写明**旧路径删除判据**（contract 完成条件）。
