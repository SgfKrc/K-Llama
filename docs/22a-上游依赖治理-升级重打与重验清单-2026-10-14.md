## 1. 当前依赖合同

| 事实源 | 合同 |
| --- | --- |
| [llama_quantize.lock.json](../scripts/model_tools/llama_quantize.lock.json)的`upstream.revision`、`revision_local`与`patches` | 上游基线、本地vendor revision与受管补丁摘要 |
| [sync_llama_cpp](../scripts/model_tools/sync_llama_cpp.py)的`inspect_sync`／`_contract` | 检查pin、补丁内容和目标文件 |
| [layer-forward补丁](../scripts/model_tools/patches/llama-cpp-layer-forward-api.patch) | 在匹配的`include/llama.h`公开QLH使用的layer-inp等声明，并补逐架构wiring；内部机制仍由vendor维护 |
| [EngineRegistry.validate_advertisement](../src/qlh_core/contracts/engines.py) | 引擎能力与ABI准入；按实际合同拒绝未知／不匹配广告 |
| [build_keep_head_cpu.ps1](../scripts/model_tools/build_keep_head_cpu.ps1) | 固定CPU／ISA参数、构建并核验libllama与shim |
| [keep_head_resources](../packaging/packaging/keep_head_resources.py)的`collect_keep_head_binaries` | 打包所需导出、依赖闭包与来源边界 |

`qlh_keep_head.c`使用匹配头文件定义的按值结构体；升级libllama必须同时重编shim。补丁登记的架构wiring、产品模型能力和真实数值验收分开记录，具体架构以当前补丁及能力合同为准。

## 2. 升级流程

1. 记录vendor、lock、补丁及当前二进制摘要，确认工作树和现有验收结果。
2. 检查目标上游与受管补丁的差异，先执行补丁dry-run，逐项核对`llama-context`及各架构graph中的layer-inp边界。
3. 更新vendor、匹配补丁与lock，运行`inspect_sync`；新增／变化架构先登记能力或保持具名拒绝。
4. 用固定构建脚本重建匹配libllama与shim，核对构建参数、导出及打包依赖闭包。
5. 重跑§3的源码、native和模型数值门，保留失败原件；通过后进入共同来源包设备门。

## 3. 重验判据

| 门 | 验证 |
| --- | --- |
| 来源与ABI | lock／补丁摘要、受管vendor及实际DLL一致；能力广告的ABI未知或不匹配具名拒绝 |
| 段边界语义 | 导出本段最后层、`output_norm`前的残差；下游保持`llama_batch.embd`注入 |
| 数值 | 同精度整模与层段的逐token argmax门；改变架构或ISA时重采对应证据 |
| 固定构建 | `GGML_NATIVE=OFF`及显式AVX2参数由构建脚本核验；候选ISA另按22d A/B |
| 物化与清理 | proper段、原生权重owner、KV预算及释放回执遵守冻结部署合同 |
| 发行设备 | 实际新包的模型／范围／来源与请求终局由R6绑定 |

基础回归入口：`tests/test_llama_cpp_sync.py`、`tests/test_refactor_engine_registry.py`、`tests/test_keep_head_cpu_build.py`、`tests/test_packaging_keep_head.py`和`tests/native/test_keep_head_native_argmax.py`。逐架构输出与设备门根据实际变更选择。
