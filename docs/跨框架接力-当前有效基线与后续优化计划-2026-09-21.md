## 1. 数据有效性规则

引用 D→L 数据时按以下优先级处理：

1. 当前代码和最新提交对应的实验报告优先；当前基线以 `610f4b3`（hybrid cache 修复）及其父提交后的代码为准。
2. “上下游都走主仓引擎”必须同时满足：上游使用 `ModelManager.load_layer_range()` / `forward_layers()`，下游使用 `LlamaCppEngine.forward_layers_from_hidden()`。
3. 使用裸 `llama_cpp`、实验区手写前向或旧 runner 的结果可以作为诊断/历史数据，但不能作为最终主仓端到端性能基线。
4. 性能数字必须同时记录模型、层数、切点、dtype/量化、prefill、decode、线程、重复次数、设备和构建指纹；不同口径不得横向比较。
5. 正确性判据与速度判据分离。D→L 的速度不占优不等于容量收益不存在；容量收益必须单独按“单设备必需驻留权重字节”计算，并注明受控预算不等于物理 OOM。
6. 引用“档位 / 速度”前必须核对**实际生效**的 dtype 与开关：主仓层流水线的 `quant_type="int4"` **静默回退 fp16**（按 key 手工物化、不走 `BitsAndBytesConfig`）；上游 compile 在参数量 `< COMPILE_MIN_PARAMS`（1.5B）时被规模门禁用。混合精度档位的 `capacity_gain_x` 只在同精度口径下解释（实测混合精度 < 1×）。
7. **纯 L→L（全部由 llama.cpp 承载，无 torch 参与推理）的「主仓引擎」口径**（★ 2026-09-23 补 §10.1）：
   上游/中段使用 `src/llama_keep_head.py` 的 `KeepHeadUpstream`（配主仓自建的**补丁版 llama.cpp shim**，
   源码在 `scripts/model_tools/keep_head_shim/`，构建见 `scripts/model_tools/build_keep_head_shim.ps1`）；
   末段使用 `ShimTailRunner`（**同一份 shim，首选**）或 `llama_engine.LlamaCppEngine.forward_layers_from_hidden()`
   （pip 绑定，可用但属**另一套构建**）。段工件由 `scripts/cut_layers.py` 生成：
   `--keep-head N`（上游段）/ `--k K1 --end K2`（中段）/ `--k K`（末段）。
   ⚠️ **混用两套构建时必须显式取齐 `flash_attn` 与 batch 线程**，否则近并列的 top-1 会被翻转
   （实测：同一 head 段下 pip 末段 1/32、取齐后 32/32，见 §10.7）；记录里应逐段写出实际 runner 与
   构建标识（§10.2 待办）。

## 2. 当前成立的事实

### 2.1 Windows Triton

README 中“缺失算子只能走 WSL2，Windows 不能用 Triton/fla”已经过时。当前事实是：

- Windows 原生 `torch.compile` 已用 `triton-windows==3.8.0.post28` 实测可用，依赖声明在 `requirements-compile.txt`。
- Windows 启动编译路径还必须设置 `PYTHONUTF8=1`；缺失时可能静默回退 eager。
- WSL2 Ubuntu-22.04 + CUDA/fla 仍是另一条已实测路径，不再是 Windows 的唯一可用路径。
- `flash-linear-attention`/fla 的具体算子收益不能从“compile 可用”直接推出，仍须按模型和算子单独验收。

### 2.3 D→L 的实际价值

- 速度：单机 CUDA 上，完整 llama.cpp GPU 路径通常更快；D→L 不应宣传为通用提速方案。
- 容量：两段切分把单设备必需驻留权重降到两侧最大段，qwen2.5-0.5B 和 qwen3.5-2B 的实测收益约为 1.568× 和 1.547×。
- 可运行性：同一受控 CUDA 预算 3.0 GB 下，整模拒绝而上游 12 层通过；这是受控分配预算证据，不得写成物理显存 OOM。
- 精度：上游使用 PyTorch 全精度、下游使用 GGUF 量化是有意义的“不完整量化”路径。验收必须与同一份下游量化整模对拍，不能拿量化下游与 f16 整模直接比较输出质量。

## 4. 实验基线（P0 已于 2026-09-21 完成）

### P0：主仓双引擎 D→L 重跑 —— ✅ 已完成（2026-09-21）

固定 qwen2.5-0.5B 与 qwen3.5-2B 两个模型，使用同一套公共接口：

- 上游：`ModelManager.load_layer_range()` + `forward_layers()`；
- 下游：`LlamaCppEngine.forward_layers_from_hidden()`；
- 工件：裁层 GGUF 由 `scripts/cut_layers.py`（+ `llama-quantize` 造 Q4_K_M）生成，JSON 内记录源模型与工件 SHA-256、层范围、commit 与运行环境；
- 档位：f32 hidden + 下游 f16、上游 f32 + 下游 Q4_K_M、上游 NF4 + 下游 Q4_K_M；
- 负载：prefill 32/128/512，decode 32/64/256，单序列和 batch 2/4；
- **结果：27/27 逐 token 与同精度整模一致**（切点 9、负载 8、batch 4、混合精度 6）；驱动 `build/cross-framework-layer-poc/relay_mainrepo_both.py`（`p0_matrix.ps1` / `p0_quant.ps1`），数据 `out/p0/*.json`，明细见《跨框架层接力-容量收益实测-2026-09-21》§9；
- 通过条件：同精度整模对照逐 token 一致；compile 若造成分叉，只能作为性能实验，不能进入一致性路径。

**P0 执行中新增的引用规则（引用档位/速度前必读）**：

1. `--upstream-quant int4` **不生效**（`load_layer_range()` 按 key 手工物化、不走 `BitsAndBytesConfig`，dtype 实测仍 fp16）⇒ 引用“上游档位”必须核对实际 dtype；真 NF4 需显式把 `nn.Linear` 替换为 `Linear4bit`（qwen2.5 84 层 / qwen3.5 93 层）。
2. 上游 compile 被规模门禁用（0.5B/2B < `COMPILE_MIN_PARAMS` 1.5B）⇒ 本矩阵是 **eager 上游**口径，不含 compile 收益。
3. **混合精度下容量收益 < 1**（实测 0.2722–1.2359×）：`capacity_gain_x` 只在**同精度**口径下解释。
4. 主仓下游 `forward_layers_from_hidden()` 在 M-RoPE（qwen3.5，`n_pos_per_embd=4`）上逐 token 一致；该契约目前**只有端到端证据、尚无单测固定**。
5. 下游是 CPU-only 绑定 ⇒ **prefill 是主要开销**（K=12 下游 prefill：32 token ≈ 1.5 s、512 token ≈ 5.7 s），且该计时含首次 ubatch 图开销。

**P0 未覆盖**：3 段及以上外推；跨机 SSH/RPC、弱网、长时 decode；下游 GPU offload；上游 compile 档；混合精度只做 K=12 且判据仅为 32 步贪心单 prompt（不构成质量结论）。

### P1：统一实验驱动与报告 schema —— ✅ 已完成（2026-09-21）

把裸 runner、主仓引擎和 L→L 对照统一到一个只读实验驱动，强制写入 relay experiment record：模型身份、权重格式、量化、层布局、引擎接口、commit、环境锁、设备画像和判据。报告必须区分 `mainrepo_end_to_end`、`raw_binding_probe`、`capacity_only` 三类，避免以后再把不同层级数字混成一张表。

**交付物**：

- `scripts/relay_experiment.py` —— 只读统一驱动，四条链路一条命令：`d2l_mainrepo`（主仓下游端到端）/ `d2l_raw_binding`（裸 `llama_cpp` 下游探针）/ `l2l_llama`（L→L 对照）/ `capacity_scan`（容量专项）。写入前必须过 schema 校验（fail-closed）；`--dry-run` 不加载模型即可预检链路与字段。
- `schemas/relay-experiment-record.schema.json` —— 记录 v1。`kind` 三类互斥；schema 负责结构与字段存在性，`src/relay_experiment_record.py` 的接口注册表负责 **kind/path/engines.*_iface** 的语义一致性（错标直接被拒）。
- `src/relay_experiment_record.py` —— 记录构建/校验与接口→(kind, path) 映射；未登记的新链路必须显式登记才能写记录。
- `tests/test_relay_experiment_record.py` —— 27 项守卫（schema 自检、kind/path/接口错标拒绝、四条链路 dry-run、L→L 通道守卫）。

**落地实测（同代码基线）**：四条链路各出一条记录（`build/relay-records/*.json`），kind/path 由接口自动判定：`capacity_only/capacity_scan`（qwen2.5 K=12，容量 1.568×）、`mainrepo_end_to_end/d2l_mainrepo`（qwen2.5 K=12，32/32）、`raw_binding_probe/d2l_raw_binding`（qwen3.5 K=8，32/32）、`raw_binding_probe/l2l_llama`（qwen2.5 K=12，**fail-loud 默认拒绝**，见下）。

**P1 暴露并已固化为守卫的工程约束**：

1. **L→L 上游通道语义不成立**：pip 绑定的 embeddings 通道 = `output_norm(H)`（证据 `scripts/relay_diag_head_norm.py`，复现命令见该脚本 docstring），L→L 端到端 `first_mismatch=2` ⇒ 驱动默认 `fail-loud`，只有 `--allow-normed-upstream` 才放行，且记录里写 `handoff.upstream_applies_output_norm=true`。正确做法是 PyTorch 上游或自建 llama.cpp 的 keep-head / 层输入通道。
2. **下游 hidden 的形状契约**：各分支一律吃 2D `[n_tokens, n_embd]`、返回 `[n_tokens, n_vocab]`。这条曾是真实 bug（raw 分支返回 ctypes 指针 ⇒ 全 0 输出；L→L 分支把特征维当 token 数 ⇒ 索引越界），已由测试与实现共同固定。

**结论（P2 最终版）**：

1. **本实验的测量噪声很大（最大相对离散 36%）⇒ 单轮扫描的"最优切点"完全不可信**。单轮曾得出
   实测最优 K=3；多轮取中位后 **total 随 K 单调递增**（分段中位数相加，线性拟合 slope **+0.63**、**r² 0.97**）
   ⇒ 实测最优是 **K=1**，"K=3 最优"只是噪声。
2. **历史补测曾得到中位数拟合结果**：当时用中位记录重跑 `relay_cut_plan.py` 得
   `predicted_cut=1`、`measured_optimum=1`、`passed=true`；但该记录是合成输入，不是端到端可追溯的决策证据。
   当前工具要求直接从带 `record_origin.kind=raw_measurement`、实验身份和 warmup 的原始多轮记录生成分析报告，
   因此这条历史结果不能单独宣称当前闭环完成。
   历史中位合成记录 `build/relay-records/cut-plan-qwen25-05b-median.json` 仅保留为审计材料；
   现在的分析器拒绝 `record_origin.kind=median_of_repeats` 作为原始输入，规划器只消费带来源、身份、warmup
   和多轮闸门的分析报告。
3. **当前数据未检出显著内部最优**：求解器的成本模型
   （`_estimate_latency` 的 `fixed + per_layer × layers`，`SegmentProfile.ms_fixed_decode`）
   对 K **数学上就是线性**，而实测分段中位数相加后的线性度很高（总耗时 r² 0.97；分段拟合 r² 0.996/0.999）。
   在当前切点和噪声水平下**未检出统计显著的内部最优**，现有模型暂可用于容量导向的规划；这不是对所有未测切点
   或更低噪声环境中不存在内部最优的证明，若未来检出显著内部最优再补非线性项。
4. **但切点选择本身仍然重要，收益体现在"端点方向"**：K=1（33.29）vs K=20（45.91）差 **1.38×**，
   远超噪声；且**上游每层 1.54 ms/层（torch/GPU）比下游每层 0.91 ms/层（llama/CPU）贵**
   ⇒ **应尽量把层放在下游一侧**，与"L 档为主"的既有策略一致。

   ⚠️ **场景标注（2026-09-23 补）**：本条结论**只在本节的实验口径内成立**，与 `README.md` 切点扫描节的
   「层推给上游」**不可并列比较** —— 两者模型、量化、单序列口径与测量工具都不同：

   | 来源 | 上游边际 | 下游边际 | 结论 |
   | --- | ---: | ---: | --- |
   | 本节（`relay_cut_model_analysis`，K=1..20，r² 0.996/0.999） | 1.54 ms/层 | 0.91 ms/层 | 放下游 |
   | `README.md` 切点扫描（`CORE-RELAY-XFRAME-02-p0-corrected`，单序列 gen=64，f16 裁层） | 2.48 ms/层（r²=0.944） | 6.43 ms/层（r²=0.991） | 推上游 |

   上游差 1.6×（可能与 `torch.compile` 是否启用有关），而**下游差 7×，用现有信息无法解释**
   ⇒ 两条都**不能**当作普适结论。**待办**：用**同一把尺**（同一模型、同一量化、同一 gen、同一分析脚本）
   重测一组作为唯一口径；在那之前，路由决策应以**容量**为准，不要以"哪侧每层便宜"为准。

**工具口径已收紧**：`relay_cut_model_analysis.py` 默认要求每个切点至少 3 轮、轮数平衡且所有
per-token argmax 记录通过；不满足时返回非零并拒绝生成可用于决策的报告。`total_median_ms` 定义为

否则裁层 GGUF 层类型错位、无法加载。求解器把它做成 `cut_multiple`，缺省 1（dense 模型）。
hybrid 的每层成本不均匀（r² 0.79）也指向同一处修正方向：按层类型分组拟合，或把实测切点直接当
离散候选（求解器已支持只在这些点上比较）。

### P3：激活与缓存数据流 —— 部分完成（多序列已实证；量化往返已实证；**线上压缩已上 wire（2026-09-23）**；传输-计算重叠未完成）

**① prefill 传整段 / decode 只传末位（已完成，且已显式化）**

链上每一段都是这个策略：prefill 一次给整段 hidden（让下游一次建立本地 KV/recurrent state），
decode 每步只给末位激活。现在它**写进记录**（`load.activation_policy =
prefill:full_sequence+decode:last_position`），引用任何带宽/延迟数字前先核对该字段。

**② 多序列 `seq_ids` / `positions` 显式绑定（已完成）**

| 件 | 内容 |
|---|---|
| shim | `qlh_kh_load(..., n_seq_max)` + 新入口 `qlh_kh_forward_embd_seq(embd, n_tokens, n_past, n_seq_id, seq_ids, positions, out)`（三个数组可 NULL ⇒ 单序列向后兼容） |
| 绑定 | `KeepHeadUpstream.forward_hidden_to_hidden(hidden, n_past=…, seq_ids=…, positions=…)` —— 与 `llama_engine.forward_layers_from_hidden()` **同一契约**；`seq_id ≥ n_seq_max` 直接 fail-loud |

### P4：量化边界与精度预算 —— 首轮边界扫描（2026-09-21）

> 本节是过程记录；**结论与交接见 §6「P4 收口」**。

票面四个问题（上游全精度是否降低下游量化误差传播 / 下游量化的误差是否随切点累积 /

⇒ **margin 具有预测能力**：它能在 token 真的翻转之前指出"这个档位在这条 prompt 上已经危险"，

（margin 7.86 ≫ 阈值 ~4.5）。**越界的是"上游 4bit（fp4）叠加 hidden 4bit"这条组合**。

**结论（诚实版）**：

1. **边界已定位，而单 prompt 看不见它**：单 prompt 下即使 hidden 4bit（元素误差 0.355）+ 上游 fp4、
   prefill 128→1024 也**不翻**；但**换 prompt 立刻显形** —— 最激进档 6 个 prompt 里翻 3 个
   （对照组 6/6 通过）。⇒ **单 prompt 的"全绿"从来不是安全证据**；
   能画出边界的是**绝对 margin**（翻转档 ≤ 4.01 / 未翻转档 ≥ 4.80 ⇒ 阈值落在 4.0~4.8）。
2. ⇒ **要分辨压缩档的优劣，只能靠 margin**（或更多样的 prompt）。这正好验证了
   "argmax 作判据 + margin 作观测量"的双轨设计：argmax 给**否决权**，margin 给**分辨力**。
3. **【最有价值的发现】上游量化**表**比位宽更伤边距**：同是 4bit、上游驻留字节都是 302 MB，
   **fp4（`int4` 档）把 margin 压低 12.85%**，而 **nf4 反而抬高 8.58%** —— 相差约 **21 个百分点**；
   相比之下 hidden 侧从 8bit 换到 4bit 只变动约 **4.5 个百分点**。
   ⇒ 工程含义：**先挑量化表（nf4 优于对称 fp4），再谈位宽**；"4bit 一定比 8bit 差"这个直觉
   在本链路里并不成立。
4. **上游 int8 几乎无损**：`int8` 档在 f16 hidden 下 margin 仅 −0.68% ⇒ **LLM.int8 是"便宜的容量手段"**
   （容量降到 4bit 档同级的收益需要另行核验，但边距代价明显小于 4bit 档）。
5. **margin 随 hidden 位宽单调变薄**：f16 ≈ baseline（+0.06%）、int8 −4.3%、int4 −6.8%（fp16 上游）；
   长上下文下同样稳定在 −7.5% ~ −4% 区间。幅度温和，说明 4bit 压缩的余量还很大。
6. **待查（假设已被收窄）**：nf4 抬高 margin 曾疑似"4bit 噪声改变 logits 尺度"，但
   发现 **fp4 反向压低** ⇒ 起作用的更可能是**量化表本身**（nf4 的 outlier-aware 非对称表），
   而不是"4bit"这个位宽 ⇒ 下一步可直接对比 nf4/fp4 的权重重构误差与 logits 尺度变化。
   `load_layer_range()` 手工物化权重 ⇒ **静默回退 fp16**（症状：int8/int4/fp16 三档 margin
   连小数位都完全相同）。现已改为 bnb 显式替换，四档 margin 立刻各不相同
   （fp16 8.8125 / int8 8.7469 / int4 7.6749 / nf4 9.5629），且 int4/nf4 的上游驻留字节
   降到 302 MB（fp16 511 MB）⇒ **档位真实生效**。
   ⚠️ 遗留小问题：`int8` 档的 `resident_weight_bytes.upstream` 仍报 510 MB（`_param_bytes`
   对 `Int8Params` 仍按 fp16 估算）⇒ 字节口径待修（不影响 margin 结论）。

| fp16 | f16 | 12 | 0 | 3 | 5.0892 | 5.6833 | +0.05% | 3584 | 510.9 MB | **safe** |
| fp16 | int4_block128 | 12 | **8** | 3 | 3.9064 | 4.8836 | −35.85% | 3584 | 510.9 MB | tight |
| int4 (fp4) | f16 | 12 | 3 | 3 | 4.8971 | 5.8203 | −12.62% | 3584 | 302.1 MB | tight |
| int4 (fp4) | int4_block128 | 12 | 7 | 3 | 3.8284 | 4.7363 | −39.36% | 3584 | 302.1 MB | tight |
| nf4 | f16 | 12 | 3 | 3 | **5.2932** | 6.1803 | −24.56% | 3584 | 302.1 MB | **safe-headroom-only** |

**判据与用法**（已工具化，`--flip-threshold` / `--safety-margin` 可调）：

- 闸门：`margin_min(有余量子集) ≥ flip_threshold(4.5) + safety_margin(0.5) = 5.0`；
- **分层**：基线 margin 本身就低于闸门的 prompt（本例 3 条：`code` / `numbers` / `rare`）**没有任何
  预算空间**，单独记 `no_hd` 而不参与档位判定 —— 否则对照档 `fp16×f16` 也会被判 tight（实测踩到）；
- 建议在 `safe` / `safe-headroom-only` 档里按"线路字节 + 上游驻留"最省者给出，但
  `safe-headroom-only` **必须先确认基线 margin 达到闸门**，否则只能回退全精度 → **`nf4 × f16`（条件安全）**。

**结论（直接回答 P4 票面第 4 问"何时优先容量、何时优先质量"）**：

1. **可用的激进档只有"上游 4bit、hidden 不压"**：`nf4 × f16` 判 **safe-headroom-only**（上游驻留 511 → 302 MB，
   **−41%**）；`int4(fp4) × f16` 虽然**翻转全部发生在无余量 prompt 上**，但最坏余量 4.8971
   仍差 0.1 未过闸门 ⇒ 判 tight（**这两档的差别再次印证"量化表 > 位宽"**：同为 4bit 上游，
   nf4 5.2932 vs fp4 4.8971）；
2. **hidden 侧不能压到 int4**：`fp16 × int4_block128` 在 12 条 prompt 上翻 **8** 条 ——
   这是最重要的修正（上一轮单 prompt 曾得出"hidden int4 也安全"的假象）；
3. **"上游 4bit + hidden 4bit"双压必然越界**（翻 7/12）；
4. **存在一类输入本身没有量化预算**：3 条 prompt 的**全精度接力基线** margin 已低于闸门 ⇒
   对这类输入只能走 fp16 全精度链路（或换更保守的路由），量化不是"少省一点"而是"必然出错"；
5. **容量优先**：只要输入不落在"无余量"类别，`nf4 × f16` 可同时满足质量与容量；
   **质量优先**：输入基线偏低时宁可不压缩。

**仍未覆盖（P4 后续）**：多 prompt 分布下的翻转率（当前是单 prompt，无法给出"什么时候会翻"）；
四段 × int4 的跨机加压；int8/int4 上游真实档；把 margin 衰减换算成"可接受的压缩档预算"。

最终输出应是按模型、切点和设备画像选择的策略表，不能全局武断把上游默认改成 f32 或 f16。

**n 段容量外推（2026-09-24，同机，本机部分已完成）**：P5 列的另一项。用**同机三段**
（head8 → mid8-12 → cut-k12；本机 middle/tail 服务、`--middle-endpoint` 走 loopback）验证正确性，
再用**真实工件字节**做容量外推：

- **正确性**：`l2l_net_3seg` **PASS 32/32**（`middle_hops=32`、`first_mismatch=None`；三段 shim/DLL 的
  sha256 全部一致 ⇒ 无构建混用）。证据
  `build/relay-records/l2l-net-local-05b-3seg-capacity-20260924.json`。
- **容量（0.5B f16；字节取实际工件文件）**：

  | 配置 | 各段 MiB | 最大段 MiB | 收益 = 整模 / 最大段 |
  | --- | --- | --- | --- |
  | 整模 | 948.1 | 948.1 | 1.000× |
  | head8 + tail8 | 492.9 + 720.5 | 720.5 | 1.316× |
  | head8 + cut-k12 | 492.9 + 606.7 | 606.7 | **1.563×** |
  | **head8 + mid8-12 + cut-k12（三段）** | 492.9 + 379.1 + 606.7 | 606.7 | **1.563×** |

- **结论（容量外推的一般式）**：`收益 = 整模字节 / max(各段字节)` ⇒ **增加段数本身不带来容量红利**，
  只有把**最大段**压下去才提升容量。0.5B 的瓶颈是**末段**（`cut-k12` = 606.7 MiB：层数更多且含非分层
  权重），所以**三段与两段（head8 + cut-k12）收益完全相同（1.563×）**，并与既有「两段 1.547–1.568×」
  口径一致。⇒ 要进一步提升收益必须**继续切末段**（需要 4 段拓扑，而当前探针只支持一个 middle 段）。

**压缩档的误差累积（2026-09-24，同机 512 步）**：A5 的压缩档验证只到 32 步，这里拉到 **gen=512**
（同一跳、payload 走 wire 编解码 + 服务端解码）：

| 档位 | gen=512（2026-09-24） | gen=32（A5） |
| --- | --- | --- |
| `none` | ✅ **512/512** | ✅ 32/32 |
| `f16` | ✅ **512/512** | ✅ 32/32 |
| `int8_block128` | ✅ **512/512** | ✅ 32/32 |

⇒ **`f16` 与 `int8_block128` 的误差不随 decode 步数累积**（至少到 512 步）；`int4_block128` 在 32 步
即 23/32 失败，无需再测长时。证据 `build/relay-records/l2l-net-local-05b-quant-*-g512-ctx8192.json`。
（口径：三档都必须在 **ctx=8192** 的服务上跑 —— 见下条。）

**⚠️ 真问题（已定位并给出修复规则）**

1. **长 decode 的"ctx 硬边界"—— 根因是 `n_ctx` 被 `n_seq_max` 均分**（2026-09-24 定位）。
   症状：长 decode 在中途报 `runner_failed`；**此前所有 relay 实验都 ≤256 步，所以从未暴露**。
   定位手段：让 shim 透出 `llama_decode` 的**原始** rc（新增导出 `qlh_kh_last_error`；`qlh_kh_forward*`
   的返回码仍是 `-2`，**不破坏既有契约**）并打印**实际生效**的 ctx，于是看到：
   * `llama_decode rc=1` = llama.cpp 的 **"failed to find a memory slot for batch"**；
   * tail 段 worker 日志：`ctx ready: n_ctx=2048 n_batch=1024 (requested n_ctx=1024 … n_seq_max=8)`
     ⇒ **llama.cpp 把 `n_ctx` 向上取整后按 `n_seq_max` 均分** ⇒ 单序列可用槽位 = `n_ctx / n_seq_max`
     = 2048/8 = **256** ⇒ decode 到第 **256** 步连 `batch of size 1` 都找不到槽位而失败；
   * 与两个历史观测**完全吻合**：`4096/8 = 512` ⇒ 失败在 ~**481**（481 + 32 prefill ≈ 513）；
     `8192/8 = 1024` ⇒ 失败在 ~**1000**。
   ⇒ **规则**：单序列长 decode 必须 **`--n-seq-max 1`**（此时每序列拿到全部 `n_ctx`），或者把
   `--n-ctx` 放大到 `n_seq_max` 倍。`relay_mid_service.py` 现在启动即打印 `ctx_per_seq=`，并在
   `n_seq_max > 1` 时给出 WARN。**这不是 llama.cpp 的缺陷，是调用方把并发序列数设得比实际大。**

   **规则已落到代码（把这类坑一次性清掉，2026-09-24）**：
   * `KeepHeadUpstream.ctx_per_seq` = `ctx_per_seq_for(n_ctx, n_seq_max)`（纯函数、可单测），
     `n_seq_max > 1` 时构造即告警 ⇒ 不变式在**唯一入口**上可见，不再靠各脚本各自记着。
   * `relay_mid_service.py` 的 `--n-seq-max` **默认从 8 改为 1**（对齐 relay 的单序列用法；
     多序列实验显式传）。
   * `relay_experiment.py` 的 `_load_keep_head_segment` 增加**启动前**预算校验（fail-closed）：
     `batch × prefill + gen + 256 > ctx_per_seq` 直接拒绝启动，并提示所需的 `--n-ctx`；
     实测 `--n-ctx 4096` 通过、`--n-ctx 256`（需求 320）被明确拒绝。
   * 紧贴预算的余量统一为 **256**：`relay_l2l_net_probe.py`（两处 `+8`）、
     `relay_bitwise_probe.py`（`+8`）、`verify_xframe_longseq.py`（`+64`）。
   * **顺带修复一个既有 bug**（与本坑无关，是在验证时撞上的）：`relay_experiment.py:middle`
     只在三段分支赋值却在函数尾部无条件引用 ⇒ 2 段链路（`l2l_keep_head` 等）必然
     `UnboundLocalError`。修后 `l2l_keep_head` 实测 `passed=True tokens_match=True`。
2. **decode 失败会让服务进程直接退出**（已修）：`relay_mid_service.py` 以前在 `runner_failed` 后
   仍调 `runner.reset()`，而 worker 已不可用 ⇒ 异常冒到顶层 ⇒ 进程退出（表现为后续档位 2.2 s
   秒失败，与"模型算错"难以区分）。现在改为 **fail-closed 但不退出**：把 runner 标记为 degraded、
   后续会话立即 `[reject] runner unavailable` 并关闭连接，**进程保持存活**（心跳/日志继续可见）。

（该批为**纯本机**工作：远端节点 2026-09-24 全部离线，故长时/累积/三段均在同机或 loopback 上完成。）

| 弱网压缩收益 | ⛔ 口径作废，待重测 | 旧表是按目标精度计算的模拟值；当前驱动明确记录 wire 仍为 `float32_le`，不能据此宣称带宽收益 |
| 误差测量（不改链路） | ✅ | 9 档全 32/32；`rel_mean`：f16 8.8e-5 / bf16 1.4e-3 / int8 2.2e-2，且不随 prefill(128→1024) 与步数变化 |
| 多跳（四段）拓扑 | ✅ | torch → Surface → y700 → 本机 32/32（batch 1/2）；`--mid-endpoint` 可重复 + `--mid-stop` + `_MiddleChain`（主循环零改动） |

### 5.3 由 P3 得出的三条可复用结论
1. **数值量化与 wire 压缩必须分开记账**：当前 `--hidden-quant` 是量化后回转 FP32 的数值实验，
   Relay 帧仍发送 FP32；任何模拟字节都不能写成真实带宽收益。后续必须先扩展协议并由实际
   payload 长度出报告，再重跑弱网矩阵。
2. **验证不得依赖 shell 变量残留**：曾因此让 9 档里 8 档"看起来成功"实际根本没跑。改为
   "每档先删旧记录 → 跑完只看记录文件存在 + `verdict.passed`"（跨机实验尤其要守）。
3. **跨机代价与批处理强相关**：batch 2 时 Android 段耗时几乎不涨（吞吐型），单序列 decode 才对
   RTT 敏感 ⇒ 引擎层选档应按画像与批大小决定，而不是一律"本机优先"。

### 5.4 异构 kernel 逐比特一致性（2026-09-21 实测）

探针 `scripts/relay_bitwise_probe.py`：三平台共用**同一份输入字节**（`bitwise/input.npy`，sha256
`088d83e3…`；不是各自按 seed 重算）、同一份工件 `qwen25-05b-f16-mid8-16.gguf`、同一份 C 源编出的
shim、`threads=4`、8 tokens × 896 维：

| 平台 | 输出 sha256 | mean_abs |
| --- | --- | --- |
| 本机 x86_64 | `2eb55979…` | 0.72972679 |
| Surface x86_64 | `2eb55979…`（与本机**逐比特相同**） | 0.72972679 |
| y700 ARM64 | `a4bf986c…` | 0.72984803 |

逐元素比较（记录 `bitwise/compare.json`）：

| 对比 | 逐比特一致 | 差异元素 | `max_abs` | `rel` |
| --- | --- | --- | --- | --- |
| 本机 ↔ Surface（同架构） | ✅ 是 | 0 / 7168 | 0.0 | 0.0 |
| 本机 ↔ y700（跨架构） | ❌ 否 | 7168 / 7168 | 0.0086 | **1.0e-3** |

三点结论：

1. **跨机本身不引入数值差异**：同架构 + 同二进制 + `GGML_NATIVE=OFF` ⇒ 输出逐比特相同。
   因此"跨机"与"跨架构"必须分开表述——前者可以要求逐比特，后者不能。
2. **跨架构漂移是 ulp 级归约顺序差异**：`rel ≈ 1.0e-3`，比 P3 测得的 int8 量化误差（2.2e-2）
   **小 20×**；不是逻辑错误，与本仓既有的上游记录一致（ARM KleidiAI numerical drift）。
3. **验收方式因此分层**：引擎层内部（同架构多节点）可继续要求逐比特；异构混部时按
   "容差 + per-token argmax"验收（P3 的四段实测 32/32 已是该形式的佐证）；记录必须写清参与
   节点的**架构与 kernel 版本**，否则这类差异无法归因。

**数值量级的读法（`1e-3` 到底意味着什么）**：

- **它是"同一层段、不同指令集"的天然下限，不是可忽略的噪声**。跨架构不可能逐比特：浮点
  乘加的**结合顺序**在 SIMD 宽度/Lane 数/是否 FMA 不同时必然不同，误差沿层累积——本段
  **仅 8 层**就累计到 1e-3 相对量级。所以"跨架构逐比特"不是"暂时没做到"，而是**目标本身不成立**。
- **它给"跨层接力的误差预算"定了参照系**。链路里真正可控、可选的误差来源是
  **hidden 压缩**（int8 2.2e-2）与权重/激活量化；跨架构漂移（1e-3）比它们**小约 20×**。推论：
  ① 压缩档应按**最坏节点**（异构）的容差来选，而不是按本机；
  ② 只要能容忍 int8 压缩，就一定能容忍异构节点间接力——四段实测 32/32 正是这个推论的验证。
- **但不能拿单段数字外推全链**：1e-3 是"8 层、一次跳"的量级，层数与跳数都会放大它
  （上游对 ARM KleidiAI drift 的记录同向）。P4 的精度预算必须**按段数 × 层数**外推。
- **最直接的工程价值**：它把"验收判据可以从逐比特退到『容差 + per-token argmax』"从一个工程
  直觉变成**有数值、有归因、有边界**的决定——即"退到哪、为什么可以退、什么时候不能退"。

### 6.3 由 P4 得出的四条可复用结论

1. **单 prompt 的"全绿"不是安全证据**：同一条链路单 prompt 下 12 档全绿、连 35% 的元素级误差都不翻；
   换成 12 条 prompt，`fp16 × int4_block128` 立刻翻 **8** 条。⇒ 量化边界**必须用 prompt 集测**，
   单点结论只能当"没有反例"，不能当"安全"。
2. **相对衰减不能预测翻转，绝对 margin 可以**：基线低的 prompt 衰减 13.9% 就翻（`code`，基线 3.7555），
   基线高的衰减 30.1% 仍不翻（`mixed-zh`，基线 6.8580）。⇒ 判据要用**绝对 margin**，
   而不是"掉了百分之几"。
3. **判据必须分层**：基线 margin 本身就低于闸门的输入（本例 3/12，`code`/`numbers`/`rare`）
   **没有任何量化预算** —— 不是"少省一点"而是"必然出错"；把它们算进档位判定会让对照档也被判 unsafe。
   因此工具把含这类翻转、但有余量子集通过闸门的档位标为 **`safe-headroom-only`**，不得当作全局 safe。
4. **口径先定死**：`int8`/`int4` 上游档曾因把 `quant_type` 交给 HF 而**静默回退 fp16**
   （症状：三档 margin 连小数位都相同）。⇒ 量化对照实验的**第一步**应是验证档位真的生效
   （记录里现在带 `quant_probe` 与替换计数）。

## 8. 部署选型：何时用 D→L，何时纯 L→L

本节把 P2/P3/P4/P4.5 的实测结论收敛成**部署决策**。三条链路都已真机验证过（判据一律
**per-token argmax 与同精度整模一致**，不得用 cosine 代替）；选型只决定"用哪条"，不改变判据。

### 8.1 一句话规则

| 集群情况 | 选型 | 理由 |
| --- | --- | --- |
| **有 CUDA 节点，且该节点能装下整模** | **不要接力**：单机全 llama + CUDA | 实测 **26.6 ms/token vs 接力 129.1 ms/token（4.85×）**；接力的价值是**容量**，不是速度 |
| **有 CUDA 节点，但整模装不下** | **D→L**（PyTorch 上游 + llama.cpp 下游） | CUDA 上游划算，下游吃 llama 的容量与量化；**上游拆层自由**（见 §8.2） |
| **没有任何 CUDA / 没有任何能跑 torch 的节点**（纯边缘：Linux 板 + Android） | **纯 L→L**（全 llama.cpp） | torch 上游在纯 CPU 边缘上不划算；L→L 已真机验证（含"完全无本机"形态） |

**D 档（PyTorch 上游）是给"集群里有 CUDA"准备的**：它的价值是吃 GPU 算力、并承担"整模装不下"
时的上游容量。若集群里没有 CUDA，D 档不该被启用 —— 这就是退化路径的分界线。

### 8.2 上游拆层的自由度差异（选型里最容易被忽略的一条）

| | D 档上游（PyTorch） | L 档段（llama.cpp） |
| --- | --- | --- |
| 切点怎么定 | **任意层**：`model_module.load_layer_range(0, K)` 直接按 `K` 切 | 需要**裁层 GGUF 工件**（`qwen25-05b-f16-cut-kN.gguf`） |
| 代价 | 无需预制工件；改切点＝改一个参数 | **工件要预先离线生成并传输**（数百 MB/份）；改切点＝生成并搬一份新工件 |
| 额外约束 | 无（dense / hybrid 均可任意切） | hybrid 的切点还必须是 `full_attention_interval` 的整数倍（qwen3.5 为 4），否则裁层工件层类型错位、**无法加载** |
| 精度 | 上游 dtype / 量化可自由组合（fp16 / int8 / nf4） | 受工件量化档与 `--hidden-quant` 限制 |

⇒ **计划内的多切点搜索、动态改切点应优先在 D 档做**；L 档切点适合**固定几个候选**（把实测切点
当离散候选，见 §7）。P2 的实测也支持这一点：L 档切点扫描的噪声（最大相对离散 **36%**）大于
切点之间的真实差异，**精调切点没有可测收益**（§7.2）。

⚠️ **首次尝试失败过，根因不在代码，值得记下来**：那次失败正好赶上**局域网崩盘**；而该次用
`ssh ... python3 relay_mid_service.py`（服务**跑在 ssh 会话里**）⇒ 网络中断把 ssh 会话带走、
**远端服务随之退出**。此后隧道端口**仍在本机监听**，于是新连接被"接受"后立即被 reset
（`ConnectionResetError` 10054）—— 现象看起来像模型层错误，实际是**远端根本没有服务**。
**重起四个服务后一次通过。**

⇒ **部署结论（已并入 §8.6）**：服务必须能**脱离 ssh 会话存活**。"前台跑在 ssh 里"只适合实验；
生产形态需要常驻 + 健康检查（否则一次网络抖动就会让远端段静默消失，而客户端只会看到一个与
"模型出错"难以区分的连接错误）。**已具备（R-R9，2026-09-24）**：
`relay_mid_service.py --detach --log-file <p> [--pid-file <p>]`（零依赖脱离会话）
+ `relay_health.py --probe`（**协议级**探活；`--check` 只测端口会漏报"端口在监听但对端已死"）
+ `--heartbeat-interval` 心跳。详见 §8.6。

（诊断过程中另修掉一个**探针真 bug**：`finally` 里的 `client.close()` 抛异常会**掩盖原始错误**，
表现为只看到"关闭失败"—— 现在关闭失败被吞掉，不再掩盖循环里的真实异常。）

远端角色由**帧类型**区分（三者齐备才谈得上"全设备"）：

| 帧 | 角色 | 语义 | 服务端 |
| --- | --- | --- | --- |
| `TOKENS` | 上游段（head） | 吃 **token** 吐 hidden | `--role head`（keep-head shim） |
| `HIDDEN` / `HIDDEN_SEQ` | 中间段（middle） | 吃 hidden 吐 hidden | `--role middle`（keep-head shim） |
| （送 `HIDDEN`）→ 回 `TOKEN` | 末段（tail） | 吃 hidden 吐 token | `--role tail`（shim 或 pip 绑定） |

### 8.5 时序与吞吐（2026-09-22 实测）+ 健康检查

**① 分段计时**（探针 `--json-out` 现带 `timing.segments_ms` / `end_to_end_ms` / `per_step_e2e_ms`）：

四条链路（prefill 32 / gen 32，**全部 PASS 32/32**，判据 per-token argmax）：

| 链路 | 整模 | 接力 | e2e 均值 | e2e **中位** | e2e 最大 | 分段均值（head / mid / tail） |
| --- | --- | --- | --- | --- | --- | --- |
| **A** 全 y700（head8 / mid8-16 / tail16） | 1.12 s | 5.86 s | 176 ms | 148 ms | 970 ms | 60 / 58 / 58 ms |
| **B** 本机 head8 + y700 mid8-16 + y700 tail16 | 1.38 s | 4.87 s | 146 ms | 129 ms | 535 ms | **30** / 75 / 41 ms |
| **C** y700 head8 + **Surface** mid8-16 + y700 tail16 | 1.43 s | 59.1 s | 1831 ms | 799 ms | **27608 ms** | 48 / **1711** / 72 ms |
| **D** 本机 head8 + **Surface** mid8-16 + y700 tail16 | 1.44 s | 40.3 s | 1237 ms | 880 ms | 12419 ms | **32** / **1084** / 121 ms |

对照整模：32 步约 **1.1~1.4 s**（≈35~45 ms/步）⇒ 接力 A/B 组慢 **约 4~5×**，与既有裁决一致
（**接力是容量手段，不是提速手段**）。

**从数字里读出的四条结论**：

1. ⚠️ **真正的瓶颈是"跨网络/经中继"，不是算力**（这条结论经**首轮误判后更正**，见下）：
   C/D 组慢的根因是 **Surface 不在局域网** ⇒ 其流量走 **Tailscale DERP 中继（东京）**。
   证据：`tailscale ping` 显示 Surface `via DERP(tok)`、而 y700 是 `via 192.168.0.100`（局域网直连）；
   本机→Surface 的 RTT 实测 **777 ms**，与 C 组 e2e **中位 799 ms 几乎完全吻合** ⇒ **每步一次往返**，
   时间全花在网络上。**更正说明**：首轮我据"Surface 是低功耗 Windows 笔记本"下了"中段别放这类机器"
   的结论 —— 那是错的。查证后排除两件事：① 我们编的 Windows DLL 并非"通用无 SIMD"
   （`GGML_AVX2/F16C/FMA=ON`、`Release -O3`）；② 同段（8 层）在 y700（ARM）上 58 ms，
   在 i5-1035G4 上也不该差 30×。
   ⇒ **部署结论（正确版）**：中段必须与调用方**在同一局域网**（y700 直连时整段链路 ~150 ms 中位）；
   跨网络尤其经中继的路径，每步一次往返 ⇒ **不可用**。
2. **x86 主机跑 head 段比 ARM 设备快 2×**（28~32 ms vs 48~60 ms）⇒ 有 PC 时让 PC 承担上游段是划算的。
3. ⚠️ **冷启动尖峰必须单独看**：C 组首步 **27.6 s**、D 组首步 12.4 s，之后落到 0.7~2.2 s
   ⇒ 只看**均值会被首步严重污染**（C 组均值 1831 ms 而中位仅 799 ms）。
   这与"std 几乎等于均值"是**同一条教训的第二面**：**边缘/异构环境里的时序结论必须先量化离散度、
   并区分冷热**（P2 的"单轮扫描噪声 36%"也是同一根源）。
4. **首轮误判本身也是一条教训**：我据"设备类型"（Windows 笔记本 vs Android 平板）解释了 30× 的差异，
   而真正的原因是**网络路径**。⇒ 性能归因必须**先量出瓶颈在哪一环**（RTT / 分段耗时），
   不要在没测网络时用"设备档次"讲故事 —— 这与"接力不是提速手段"那类结论同源：
   **先测，再解释**。

**② 一个真 bug（已定位并修复）**：服务端把 `CLOSE` 帧处理成 `runner.close()` ——
而**探针每次实验结束都会发 `CLOSE`** ⇒ 引擎被销毁 ⇒ **该服务此后每个连接都失败**
（实测：帧完全正确——32 tokens / 114688 字节——却报 `rc=-5 参数非法`，现象与"模型算错"**难以区分**，
只能靠重启服务恢复；这正是"B 组时通时不通"的真因）。
`CLOSE` 的语义应是"结束**该会话**"而不是"销毁服务端引擎"：现在只 `reset()`，**不 `close()`**
（引擎属于服务进程、要跨连接复用；真正释放发生在进程退出）。
⚠️ 更值得记的是：**旧行为被一条测试固化了**（`..._closes_runner` 断言 `runner.closed is True`）
⇒ 测试全绿而服务只能服务一次。现在改为断言"只 reset 不 close"，并**新增双会话回归测试**。

**③ 健康检查（已实现并验证）**：

- **服务端心跳**：`--heartbeat-interval`（默认 5 s）定期刷新 ready 文件的 `alive_at` / `pid`
  ⇒ **外部据此判断服务是否还活着**（实测 `alive_at` 从 15:15:14 → 15:15:20 ✓）；
- **客户端探活**：探针在收发**之前**先探远端段，远端段已退出时给出明确诊断
  （"远端服务已退出 / 隧道已断" + "检查该端 ready 的 `alive_at`"），**而不是让它表现成"模型算错"**
  —— 这正是 §8.6 那条教训的落地（实测对 `127.0.0.1:50999` 无人监听给出该诊断 ✓）。
  ⚠️ **已升级为协议级（R-R9，2026-09-24）**：原先只做 **TCP connect**，而 §8.6 那种故障
  **恰恰是"端口仍在监听、connect 会成功"** ⇒ TCP 探活会**漏报**。现在改走
  `scripts/relay_health.py` 的 `probe_relay`（真发 `CLOSE` 帧并等 `TOKEN(-1)` 应答），
  并在 `_RemoteMiddleSegment` 建连**之前** fail-loud
  （实测：假段「accept 后立刻 close」被拒，`handshake_failed` / `ConnectionAbortedError`）。
- **独立健康检查命令** `scripts/relay_health.py`：把两者合起来并给出**可进 CI 的退出码**
  （0 = 全健康 / 1 = 有异常），支持 `--check name=tcp:host:port`、`--ssh-ready name=alias:path`
  （经 ssh 读远端 ready 并检查**心跳新鲜度**，默认 30 s 过期）、`--json`（供驱动解析）。
  实测：四段 TCP 全 OK、y700 两段心跳 `age=4.8 s / 2.2 s`、故障项给出 hint 且 `exit=1` ✓。
  ⚠️ 顺带修掉它自己的一个真 bug：输出用了 `⇒`(U+21D2)，在 **GBK 控制台**下抛 `UnicodeEncodeError`
  把健康检查打成 traceback（**检查工具自伤，比不检查更吵**）⇒ 现在强制 UTF-8+replace、
  输出只用 ASCII 箭头，并有回归测试钉住；
- **脱离 ssh 会话**：初始做法是 `nohup ... &`（当时记录「Termux 无 `setsid`」—— 那指的是
  **`setsid` 命令**缺失，与 `setsid(2)` **系统调用**是否可用无关）。**现已内置（R-R9）**：

### 8.6 设备侧依赖（决定"能不能上"）

- **head / middle 段必须走我们编译的 shim**：它们要取**中间层**输出，而 pip 绑定的
  `llama_cpp.llama_cpp` **不认识**我们补丁新增的符号（实测 `llama_get_embeddings_nextn_ith` /
  `llama_get_embeddings_layer_inp` / `llama_set_embeddings_layer_inp` / `llama_set_embeddings_nextn`
  四个**全部 MISSING**）⇒ 走 pip 路线就得连绑定层一起打补丁并长期跟进上游；
- **tail 段**：`--role tail` 既支持 shim（`ShimTailRunner`，推荐 —— 与 head/middle 同一份 C 源）
  也支持 pip `llama_cpp`（`TailRunner`）；**只做 tail 且装包便宜**的设备可用后者作过渡，
  但记录必须写明该段用的是外部 pip 版本；
- **编译发生在开发机**（NDK 交叉编译，已在真机验证），**设备只收产物** —— 边缘设备不该承担编译；
- 数值一致性：同链路尽量共用**同一份构建配置**的 llama.cpp；跨架构漂移已知约 `1e-3`（§5.4），
  而"两套构建配置混用"会引入不可控差异。
- **服务必须能脱离 ssh 会话存活**（2026-09-22 实测教训）：该次用 `ssh ... python3
  relay_mid_service.py` 起远端段（实验方便），但**网络抖动会把 ssh 会话带走、服务随之退出**；
  此后隧道端口**仍在本机监听**，新连接被"接受"后立即 reset（`ConnectionResetError` 10054）——
  现象与"模型层错误"**难以区分**。
  ⇒ **已具备（R-R9，2026-09-24）**：
  - **常驻**：`relay_mid_service.py --detach --log-file <path> [--pid-file <path>]` —— 用
    `subprocess.Popen` **重起自己**（Windows `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP`；
    POSIX `start_new_session=True`，即 `setsid` 等效）后**父进程退出** ⇒ **服务不依赖发起会话**。
    零依赖：**不**引入 `systemd` / `pywin32`。
  - **心跳**：`--heartbeat-interval`（默认 5 s）刷新 `--ready-file` 的 `alive_at`（发现
    "进程还在但引擎已废"）。
  - **探活**：`scripts/relay_health.py --probe NAME=tcp:HOST:PORT` —— 做一次**协议级**握手
    （`CLOSE` → 服务端回 `TOKEN(-1)`，**不经 runner、不加载模型**）。这一条**专治**上面那个坑：
    `--check`（只 `connect`、不发帧）对"端口在监听但对端已死"**会判健康**（**已知漏报**，
    `--self-check` 里**如实复现**），而 `--probe` **判死**。
    停服务：先 `--probe` 确认活性，再按 `--pid-file`（Windows `taskkill /PID <pid> /T /F` / POSIX `kill`）。
  - **CI 兜底**：`relay_health.py --self-check` 用本机 loopback 做**四条方向断言**

### 10.5 M-RoPE 模型上 embd 注入通道的位置布局（已修，2026-09-23）

llama.cpp 只在 **token 通道**把同一位置广播到全部 RoPE 分量；**embd 注入通道**按 planar 读
`batch.pos[j*n_tokens + i]`（`llama-batch.cpp::llama_batch_allocr::ubatch_add`，
`src_off = batch.token ? 0 : j*batch.n_tokens`），要求调用方给出 `n_tokens * n_pos_per_embd`
个位置，而 `llama_batch_init()` 只分配 `n_tokens` 个 ⇒ M-RoPE 模型（`n_pos_per_embd = 4`）会读到
缓冲区之外（0.5B 的 `NORM` 只跑一次循环，所以历史记录从未暴露它）。

- 修法（三处同一判定，均由 `llama_model_rope_type()` 决定 1 还是 4）：`qlh_keep_head.c` 的
  `qlh_fill_pos_planar()`；`src/llama_engine.py:forward_layers_from_hidden()`；Android
  `qlh_llama_jni.cpp` 的 `qlh_rebuild_pos_planar()`（顺带修掉旧实现**丢弃显式 `positions`**
  的实错 —— 多序列路径原先用 `pos_base + i` 覆盖）。
- 证据：同一 head 段下 tail 段由 FAIL 变 PASS（§10.4 两段行）。

### 10.6 Qwen3.5 的层输出通道（已修：`layer_inp` 的 `lid == n_layer` 槽位）

`src/models/qwen35.cpp`（主 graph）把 `t_h_nextn` 设在 `build_norm(..., model.output_norm, ...)`
**之后**（`h_nextn` 的消费方是 MTP head，期望 norm 后），而层段接力的下游期望**未经
`output_norm`** 的层输出 ⇒ `mode="nextn"` 取到的值多了一次 RMSNorm；qwen2 与 qwen35 的
`t_h_nextn` 因此**不是同一个东西**（这与 P1 否证 pip `embeddings` 通道的老问题同源）。

- 修法（2026-09-23 采用「扩补丁」方案）：`layer_inp` 的槽位**多分配一个**
  （`cparams.embeddings_layer_inp` / `embd_layer_inp` 大小 = `n_layer + 1`），索引 `lid == n_layer`
  即「第 n_layer 层的输入」= **末层输出（`output_norm` 之前）**；各架构 graph 在 `output_norm`
  **之前**登记该槽位。shim 与 Android JNI 的 `nextn` 模式随之统一改用该通道 ⇒ **与架构无关**；
  `t_h_nextn` 的既有语义（MTP）不动。
- 已登记槽位的架构（9 个）：`qwen2`、`qwen35`、`gemma4`、`llama`、`openai-moe`、`qwen3`、
  `qwen3moe`、`qwen35moe`、`qwen3next`；未登记的架构会在 decode 时 GGML_ASSERT（fail-closed）。
- 证据：§10.4 的三行（含架构扩展后的三段复测）；0.5B（qwen2）回归仍 PASS。
- **已接线（2026-09-23）**：协议层新增**可选**字段 `middle_channel`
  （`extract_hidden` | `keep_head_layer_out`；两侧同集合，**缺省 = 旧行为**），并沿
  `AndroidFullWorkerStageExecutor` → `TaskWorkerService` → `LayerForwardRequest` →
  `LocalInferenceEngine.layerForward(keepHead=…)` **全程透传**；worker capabilities 另外上报
  `middle_channel` / `n_pos_per_embd`，调度侧据此可知该节点中间段实际可走哪条通道。
  ⚠️ 落坑记录：两侧的层段字段集合是**精确**校验（`_require_exact_fields` / `requireExact`）⇒
  把可选字段直接并进「必填集合」会让缺该字段的旧对端被判 `field_mismatch`（实测踩到）；
  实现改为按「payload 里是否真的出现」动态放宽。
- **当前状态（2026-09-24 按代码核实）**：① `seq_ids` / `positions`（多序列显式位置）**已上协议**
  —— `src/task_worker_protocol.py:79` 的 `_LAYER_FORWARD_OPTIONAL_FIELDS` 含这两个字段，Android 侧为
  **同集合**且 parse 后透传到 `layerForward(seqIds=, positions=)`，形状非法即 `invalid_<field>` fail-closed；
  但**主仓下发侧仍无生产者**（真实多序列下发属 A1 Relay 生产执行路径，见
  `docs/未完成工作备忘-2026-09-23.md` §1 A12）；② 真机（APK/JNI）上的 `layer_forward` 数值**尚未实测**，
  现有 D/E 证据来自 Termux 里的原生可执行文件（绕过 JNI 封装）；③ Android 侧 `hidden_spec.dtype`
  **已同时接受 `float32` / `float16`**（`AndroidFullWorkerStageExecutor.kt:201` 校验、`:354` 取字节宽度；
  f16 在本段转 f32）—— 事先存在的对称性缺口**已补齐**。

### 10.7 pip `llama_engine.forward_layers_from_hidden()` 的分叉（已定位并修，2026-09-23）

**根因是 flash attention 开关，不是语义 bug**：pip 绑定的 `Llama.__init__` 会**无条件**把
`flash_attn_type` 写成 `DISABLED`、把 `n_threads_batch` 写成 `multiprocessing.cpu_count()`，而自建
shim 那份 llama.cpp 是 `flash_attn = auto → enabled`、`n_threads_batch = n_threads`
（取证：pip 日志 `flash_attn = disabled` / `n_threads_batch = 20`；shim 日志
`Flash Attention was auto, set to enabled`）。两者在 32-token prefill（`ubatch.n_tokens > 1`）上
都会改变浮点结果。pip 自带的是 llama.cpp `4df29be`（比子模块的 `47e1de77` 更新），planar 位置
语义与 IMROPE 支持均具备 ⇒ 版本差异**不是**原因。

**单变量对照**（同一 head 段 = 整模 + `layer_inp`(16)；tail = pip `llama_engine`）：

| tail 参数 | 判据 | 记录 |
| --- | --- | --- |
| pip 默认（FA disabled + `n_threads_batch=20`） | ❌ 1/32 | `l2l-net-local-9b-2seg-layerinphead-piptail-fixed.json` |
| 只对齐 `n_threads_batch=8`（FA 仍 disabled） | ❌ 1/32 | `l2l-net-local-9b-2seg-piptail-tbonly.json` |
| **只打开 FA**（线程仍 `cpu_count`） | ✅ **32/32** | `l2l-net-local-9b-2seg-piptail-faonly.json` |
| 两者都对齐（= 新默认） | ✅ **32/32** | `l2l-net-local-9b-2seg-piptail-default.json` |

⇒ **判据关键是 FA**；线程数不是判据关键，但一并取齐。

- 修法：`scripts/relay_mid_service.py` 的 `TailRunner` 默认 `flash_attn=True`、
  `n_threads_batch=n_threads`（与 shim 取齐），并新增 `--tail-no-flash-attn` /
  `--tail-threads-batch` 以便复现差异；服务启动时上报 `flash_attn` / `n_threads_batch` /
  `llama_cpp_version`（§10.2 记录字段的起步实现）。
- 结论（并入 §8.6 口径）：**两套构建混用时，FA 与 batch 线程必须显式取齐**，否则近并列的 top-1
  会被翻转；「tail 段只走 shim」不再是必需，但共用同一份构建仍是首选。

### 10.4 复验暴露的三个可复用约束（下次别再踩）

1. **keephead shim 需要整套 MinGW 运行时**：只传 `qlh_keep_head.dll` 会报
   `Could not find module ... or one of its dependencies`。必须把 `build/keephead/build-cpu/bin/`
   下的 `libgcc_s_seh-1.dll` / `libstdc++-6.dll` / `libwinpthread-1.dll` / `libgomp-1.dll` /
   `libllama.dll` / `ggml.dll` / `ggml-base.dll` / `ggml-cpu.dll` **连主文件一起传**（共 9 个）。
2. **`relay_mid_service.py --detach` 活不过 ssh 会话**：进程起过（日志有 `[ready]`）但随即消失，
   而隧道端口**仍在本机监听** ⇒ 新连接被"接受"后立即 reset，探活报
   `RelayProtocolError: connection_closed_mid_frame`（**与 §8.6 记录的"接受后立即 reset"同一现象**）。
   ⇒ 远端段改用 **`schtasks`** 起（与 `api_server` 同法），实测可长期存活（新 ssh 会话里仍 `listening`）。
3. **`QLH_RELAY_ENABLED` 是"每节点各自"的开关**：只在主节点设不够 —— 从节点不设会拒收层配置，
   报 `relay_middle requires an enabled valid relay_segment`。

### 10.5 `api_server` 侧 relay 接线修复（2026-09-26）

`QLH_RELAY_ENABLED=1` + `QLH_RELAY_SEGMENTS="<node>=middle@127.0.0.1:<port>#<n_embd>"`
的 worker 合同已改为 **endpoint-backed**：

1. `scheduler_pipeline` 收到 `engine=relay_middle` 时只校验并登记
   `relay_segment`、模型逻辑身份和层范围；**不会调用 `load_model` / `load_layer_range`，
   也不会把 scheduler 的 `ModelHost` 标记为已加载**。
2. 实际层段工件由独立监督的 `relay_mid_service` / keep-head 服务持有；
   `LAYER_FORWARD` 以活动配置的 `engine=relay_middle` 为准，直接把 hidden 转发到 endpoint，
   不再先经过本地 `host.is_loaded` 检查。
3. Task Worker hello 对这类节点公布 `layer_worker=true`、不公布完整模型身份，
   因而不会被 `_task_worker_full_model_ids()` 误判为 Full Worker 后 `opt_out`。
4. `QLH_RELAY_ENABLED` 仍需在每个实际 relay worker 节点开启；endpoint 存活、段工件和
   supervisor 启动属于运行前置，失败时保持 fail-closed。

这解决了“载完整模型才有 scheduler host、但完整模型又触发 Full Worker”的结构性死结，
并恢复了层接力**规避整模加载**的原始目的。§10.1 的三条跨机 PASS 仍然是探针路径
（`relay_l2l_net_probe.py` / `relay_experiment.py`）；产品侧的双机 API/TUI workflow
仍需在真实两节点、真实模型和 `distributed_used=true` 条件下单独验收，不能用探针结果替代。
