## 0. 结论速览

| 命题 | 结论 | 证据强度 |
|---|---|---|
| **每段必需容量随 K 减小，最优切点在 K=N/2** | ✅ 成立，U 形曲线**完美对称** | 5 个 K × 3 次重复，`std = 0` |
| **容量收益 = M_total / max(上游, 下游)** | ✅ **1.55–1.57×**（两段，实测） | 两个模型独立复现 |
| **同一预算下「整模装不下、拆分装得下」** | ✅ **实测 OOM vs 实测 fits** | 受控预算 3.0 GB，2/2 重复 |
| **数值正确性**（接力 token == 整模贪心） | ✅ qwen2.5-0.5b **32/32**；qwen3.5-2b **K=8/12/16/20 全部 32/32**（修复 hybrid cache 契约后重跑） | 见 §5、§9 |

**一句话**：接力把**单设备必需容量**从「全部层」降到「约一半 + 不可分层」，因此**让原本装不下的模型变得可运行**；但收益**有上限**（< 2×），受**不可分层张量**约束。

## 1. 实验设计（单变量）

**唯一变量**：上游保留的层数 `K`（下游 = `N − K`）。

**对照的容量量**：「**单设备必需驻留权重字节**」
* **整模** = 单设备必须同时驻留**全部层** ⇒ `M_total`
* **拆分** = 上游只驻留 K 层、下游装在**另一台设备** ⇒ 单设备最大需求 = `max(上游, 下游)`

**判据**：`容量收益 = M_total / max(上游, 下游)`。

**方法约束（依项目规则）**：
* 上游**必须走主仓引擎** —— `ModelManager.load_layer_range(...)` + `forward_layers(...)`，**不手写前向**；
* 下游用**离线裁层 GGUF**（`scripts/cut_layers.py`，真·层裁切）；
* **单变量分离 + 重复测量 + 给 std**；
* 含一次性成本的过程**分段测量**（加载 / 预热 / 生成分开）。

**资产**：`qwen2.5-0.5b-instruct`（24 层）+ `qwen3-5-2b`（24 层 hybrid）；GPU RTX 4060 Laptop 8 GB；主运行时 `torch 2.13.0+cu126`。

## 3. 为什么收益不是 2×？—— 不可分层张量是硬下限

裁层只切分 **`blk.*`（层）**，而以下张量**必须完整保留**在某一侧：

* `token_embd`（词嵌入）—— **只在上游**（`has_embedding=True`）；
* `output_norm` / `output`（lm_head）—— **只在下游**。

⇒ 设可分层参数 `L`、不可分层 `C`，则 `M_total = L + C`，最优时：

```
上游 = L/2 + C_emb     下游 = L/2 + C_out
收益 = (L + C_emb + C_out) / (L/2 + max(C_emb, C_out))
```

* qwen2.5-0.5b：`C` 占比 **27.56%**（★ 2026-09-24 逐张量实算修正；原文记"约 18%"与实算不符）
  ⇒ 收益 **1.568×**（`(715.8 + 272.3) / (715.8/2 + 272.3)` ⇒ **公式与结论均复现** ✓）
* qwen3-5-2b：**24.01% / 1.613×**（原文"24% / 1.547×"）—— 该口径**把
  `model.visual.blocks.<i>.*` 视觉塔也当可分层**；若按严格口径（**只有 `*.layers.<i>.*` 才可分层**），
  该模型另有 **约 300 个层外张量（视觉塔 + `mtp.*`，~680 MB）** ⇒ `C = 37.31%`、收益 **1.457×**。
  两种口径都写清，避免按错的那个估容量。

⇒ **口径说明（★ R-R5，2026-09-24）**：`C` 应定义为「**不属于任何 `*.layers.<i>.*` 的张量**」——
这样 `model.visual.*` / `mtp.*` 才不会被漏计。实算工具：
`src/relay_capacity_budget.py`（`python src/relay_capacity_budget.py <模型目录> [--visual-splittable]`，
**零依赖**、只读 safetensors 头部、不加载权重）。

⇒ **这就是收益有上限的原因**：词表越大、层外结构越多，收益越低。并且**上限依模型而异**：
**非 tie 模型**（如 `qwen3-0.6b`）现状已把 lm_head 放下游 ⇒ `C` 的**单侧最大值**只有一份
⇒ 实测已达 **2.000×**；而 **tie 模型**（如 `qwen2.5-0.5b`，无独立 lm_head）的 `C` 整份压在
上游 ⇒ 只能拿到 **1.568×**，**唯一**的改善手段是词表维分片。

**推广到 n 段**：`收益 ≈ (L + C) / (L/n + C_split)` ⇒ **n 越大收益越大，但渐近于 `(L+C)/C_split`**。所以「加设备」的边际收益**递减**，且**不可分层张量给出硬下限**。

## 4. 关键实证：「装不下」→「可运行」

K 扫描给出的是**必需容量**。为证明它真的决定**能不能跑**，在同一**受控 CUDA 预算**下对照：

| 配置 | 预算 **3.0 GB** | 预算 3.9 GB |
|---|---|---|
| **整模**（24 层 + embed + lm_head） | ❌ **`controller_rejected_oom`（0/2 fits）** | ✅ fits，peak **3.8018 GB** |
| **上游 12 层** | ✅ **fits（2/2），peak 2.4186 GB** | — |

OOM 报文（权威）：

```
CUDA out of memory. Tried to allocate 24.00 MiB. GPU 0 has a total capacity of 8.00 GiB
of which 4.16 GiB is free. 2.79 GiB allowed; Of the allocated memory 2.78 GiB is
allocated by PyTorch, and 0 bytes is reserved ...
```

⇒ **同一台设备、同一预算 3.0 GB：整模装不下，切出 12 层的上游段装得下且能前向。**

**边界定位**：整模需 3.8018 GB ⇒ 3.0 GB 拒 / 3.9 GB 通过 ⇒ 边界的 3.80–3.90 GB 之间。

> ⚠️ **口径声明（必读）**：这是**受控预算**（`torch.cuda.set_per_process_memory_fraction`，由 CUDA caching allocator 强制），**不是物理显存耗尽**。选它是因为它**可复现、可定量、可比较**。**不得当作物理 OOM 引用。**
> 之所以不能做物理对照：本机 llama.cpp Python 绑定是 **CPU-only**（`graph splits = 1`），整模走 CPU 且 **mmap**，无法用 GPU 预算约束整模。

## 5. qwen3.5 的 **D→L** 数值：已定位根因并修复（涉一次错误归因的纠正）

### 5.1 修复前现象（历史）

| 路径 | 上游 | qwen2.5（1D RoPE） | qwen3.5-2b（M-RoPE + hybrid） |
|---|---|---|---|
| **L→L** | llama.cpp | ✅ | ✅ **`accepted:true` / `all_tokens_match` / 16 步全对** |
| **D→L** | PyTorch（主仓引擎） | ✅ **32/32** | ❌ **2/32**（`idx 2` 起分歧，并出现复读；**修复前**） |

⇒ **同一个 qwen3.5-2b、同一份裁层工件**：上游换回 llama.cpp 就全对。**下游、cut 工件、协议都没有问题。**

### 5.2 排查过程（含一次错误的归因，记录在案）

1. **初判（错误）**：看到 relay 序列复读，判定为「**M-RoPE 未解决边界**」。
   ⚠️ **这个归因是错的** —— M-RoPE 的调用方修法**早已存在且已验证**：
   * `build/cross-framework-layer-poc/llama.cpp/tools/hs-extract-batch/relay-gen-dl.cpp:143-159`
     实现了「`pos` 按 `n_pos_per_embd*n_tokens` 提供」（上游 #28963 / #28902 的调用方修法）；
   * `docs/archive/relay/上游llama-embd注入非确定性-复现与issue材料-2026-09-16.md` 记录该修法"问题消失"，
     并注明「本项目接力实验**恰好选用 Qwen3.5-2B（M-RoPE，最坏情况）**」。

2. **真实缺口**：本次使用的 **`relay_mainrepo_upstream.py` 自己没有实现**这个修法
   （原写法是 `b.pos[i] = pos + i`）。**已补齐**（见 §5.3）。

3. **补齐后仍 FAIL** ⇒ 说明还有**第二个、独立的**原因，且**不在** M-RoPE 的 `pos` 契约上。

### 5.3 已做的修正（`relay_mainrepo_upstream.py`）

* 新增 `_n_pos_per_embd()`：用 `gguf` 读 `<arch>.rope.dimension_sections` 的长度
  （`llama_model_meta_val_str` 读不了**数组**键，实测返回 -1）。
* `llama_batch_init(n_tokens * n_pe, ...)` —— 让 **llama.cpp 自己**分配足以容纳
  `n_pe*n_tokens` 个 `pos` 的缓冲，再按 `pos4[j*n_tokens + i] = pos + i` 填值。
  ⚠️ 这一步的写法**有讲究**：换成 Python 缓冲会与 GC 冲突，换成自己
  `libc.malloc` 的块会**跨 CRT**（`msvcrt` vs llama.cpp 的 `ucrtbase`）⇒ 两者实测
  都报 `0xc0000374 STATUS_HEAP_CORRUPTION`（Windows 堆损坏）。**必须走 llama.cpp 的分配器。**
* 效果：探测到 `n_pos_per_embd=4`，输出改变（不再堆损坏），但**修复前分歧依旧**（仍 `2/32`）。后续 cache 对象修复见 §5.4。

### 5.4 根因定位与修复（2026-09-21）

qwen3.5 是 **hybrid** 架构，其缓存由两部分组成 —— llama.cpp 日志可见：

```
llama_kv_cache:          size = 40.00 MiB (4096 cells,  5 layers)   ← attention KV
llama_memory_recurrent:  size = 16.05 MiB (    1 cells, 20 layers)   ← SSM/recurrent state
```

**界定实验**（`upstream_only_probe.py`：只跑上游 PyTorch 全 24 层 + lm_head，与 llama.cpp 整模对拍）：

| cache 传递方式 | 与 llama.cpp 整模的一致度 |
|---|---|
| `past_key_values`（`tuple of (k,v)`，原契约） | ❌ **1/16**（`Paris of of of of …`，退化） |
| **`cache` 对象**（本次新增） | ✅ **16/16** |

**根因（`src/model_module.py` 的 `forward_layers`）**：

缓存契约被实现为 **`tuple of (k, v)`**，收集侧只取 `layer_cache.keys` / `layer_cache.values`：

```python
keys = getattr(layer_cache, "keys", None)
values = getattr(layer_cache, "values", None)
cache_items.append((keys, values) if keys is not None and values is not None else None)
```

而 **hybrid 的 `linear_attention` 层用的是 `recurrent state`**（`layer_cache` 没有 `.keys`/`.values`）
⇒ 在 tuple 通道里**只能落到 `None`**。原注释假设「它们由模型内部的递归状态自行维护」——
**该假设是错的**：状态**只存在于 cache 对象里**，不传递就等于没有。

⇒ 后果：**prefill（第 1 步）正确**（状态在同一次 forward 内累积），**decode 第 2 步起状态归零**
⇒ 输出退化为复读。这解释了三个现象：① 仅第 2 步起出错；② **qwen2.5（纯 attention）不受影响**；
③ **L→L 正常**（llama.cpp 自己维护 recurrent cache）。

**修复**：
* 收集侧**同时**返回 `result["cache"]`（cache 对象本身，承载 recurrent state）；
  原 `past_key_values`（tuple）保留为**向后兼容通道**，并标注对 hybrid **有损**。
* 接收侧：`past_key_values` 若是 **cache 对象**（非 tuple/list）⇒ **直接复用**，不按 tuple 重建；
  并对层槽做 fail-loud 检查。

**验证**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 上游 PyTorch 整模 vs llama.cpp | 1/16 | ✅ **16/16 完全一致** |
| **D→L 端到端**（qwen35-2b, K=12, gen=32） | 2/32 | ✅ **`token 与纯 llama.cpp 整模一致: True`** |
| qwen2.5-0.5b D→L 回归（1D RoPE） | PASS | ✅ **仍 PASS**（`n_pos_per_embd=1` 自动识别） |
| 测试 | — | ✅ `test_model_module.py` 新增 4 个 cache 契约用例 + 全量回归 |

> **容量结论不受影响**（容量量是权重字节）；**且 qwen3.5 的数值结论现在可以引用了**。

## 6. 过程诚实性：实测中修正的 4 个陷阱

| # | 陷阱 | 症状 | 修正 |
|---|---|---|---|
| 1 | **容量池两边不一致** | 整模走 CPU（mmap）、上游走 GPU ⇒ 首轮读出 **0.4986×**（「拆分更差」） | 两边统一到同一池 |
| 2 | **llama.cpp Python 绑定是 CPU-only** | `--whole-gpu-layers -1` 后 CUDA alloc 仍为 **0.000** | 放弃用 CUDA 量整模，改用权重字节 |
| 3 | **进程 RSS 因 mmap 严重低估整模** | 整模文件 948 MB，RSS 只增 **0.107 GB** | 改用 `llama_model_size()` + PyTorch 参数字节作权威量 |
| 4 | **跨 CRT 的 malloc/free 不匹配** | 为 M-RoPE 自己 `libc.malloc` 的 `pos` 块被 llama.cpp（UCRT）`free` ⇒ **`0xc0000374` 堆损坏**；换成 Python 缓冲则与 GC 冲突，同样崩 | 改走 `llama_batch_init` 的分配器（放大容量），全程不跨 CRT |

⇒ **权威容量量 = 必需驻留权重字节**（llama.cpp `llama_model_size` + PyTorch `numel × element_size`），与 mmap 缺页、缓存分配器行为**无关**。

## 8. 对 `CORE-RELAY-XFRAME-01` 的结论

**「容量收益实测」项可结清**：容量收益**存在、可量化、有上限**。

* 速度：约 **20× 慢**（既有结论）⇒ Relay 定位是**能力组合**，非提速；
* 容量：**1.55–1.57×（两段）**，且**让装不下的模型可运行**（§4 实证）。

⇒ 二者同属「性能」。**仅凭速度不占优而拒绝准入，是把「性能」窄化** —— 准入判据为「**正确性已验证即准入**」，并保留「能单机整模跑时优先单机」的**路由倾向**。

**本实验留下的后续项**：
1. **n 段外推验证**（3 段及以上，检验渐近上限）；
2. **不可分层张量的缩减**（如 shared embedding 强制 shared ⇒ 提高收益上限）；
   ★ **2026-09-24 已测（R-R5）**：见 §3 的口径说明与 `src/relay_capacity_budget.py`。
   实测**推翻了这条建议的方向**：**非 tie 模型现状已达上限 2.000×**，把 lm_head 挪到上游
   （即"强制 shared"式做法）反而降到 **1.414×**；**tie 模型**才需要改善，且唯一手段是**词表维分片**。
   另发现 `qwen3.5` 的**视觉塔（~680 MB）**是层外最大可缩减项（切它 ⇒ 1.457× → 1.613×）。
3. **长时运行**与**远端资产分发自动化**（原票剩余项，见 §9.4）；跨机 SSH 隧道与长序列正确性已由后续证据覆盖（逐步生成 141/141），索引见[跨框架接力-当前有效基线与后续优化计划](跨框架接力-当前有效基线与后续优化计划-2026-09-21.md)。

### 9.3 新增的口径与坑（2026-09-21，引用数据前必读）

1. **主仓下游接口在 M-RoPE 上同样一致**：qwen3.5（`n_pos_per_embd=4`）走 `forward_layers_from_hidden()` 逐 token 一致；裸 `llama_cpp` 路径当年必须把 `pos` 放大到 `4×n_tokens` 才不报堆损坏（它 4 段填的是同一个值，故两条路径数值等价）。**该契约目前只有端到端证据，尚无单测固定**。
2. **`--upstream-quant int4` 是静默回退**：`load_layer_range()` 按 key 手工物化权重、**不走** `BitsAndBytesConfig` ⇒ dtype 实测仍是 fp16。真 NF4 必须显式把 `nn.Linear` 换成 `Linear4bit`（实现：qwen2.5 84 层 / qwen3.5 93 层）。**「档位名 ≠ 实际生效」**应作为引用规则。
3. **上游 compile 被规模门禁用**（0.5B / 2B 均 < `COMPILE_MIN_PARAMS` 1.5B）⇒ §9.2 的速度口径是 **eager 上游**，不含 compile 收益。
4. **混合精度下容量收益 < 1**（实测 0.2722–1.2359×）：上游 f16/f32 的 12 层比整个 Q4_K_M 整模还大 ⇒「D→L 省容量」只在**同精度**口径下成立。
5. **下游 prefill 是主要开销**：主仓 `llama-cpp-python` 是 CPU-only 构建；K=12 下游 prefill 32 token ≈ 1.5 s、512 token ≈ 5.7 s（qwen3.5），且该计时含首次 ubatch 图开销。
6. **L→L 上游不能用 pip 绑定的 embeddings 通道**（2026-09-21 由 P1 统一驱动暴露）：`llama_get_embeddings_ith`（即 `llama_engine.forward_layers_to_hidden()` 的底层）返回的是 `output_norm(H)` —— 实测 vs `RMSNorm(H)*model.norm.weight` 为 `rel_err=0.0018` / `cos=0.999998`，比层接力上游所需的 hidden **多一次归一化** ⇒ L→L 端到端 `first_mismatch=2`。统一驱动对 `l2l_llama` 默认 fail-loud，证据与复现见 `scripts/relay_diag_head_norm.py`。
