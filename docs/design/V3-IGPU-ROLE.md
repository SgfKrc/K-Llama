# 核显的阶段化定位
> 面向 Qwen3.5 系列 · 基于算术强度归因 · 产出 v3 的 prefill/decode 分离输入

> 状态：**设计输入（2026-11-14）**，不是实现方案
> 依据：`docs/measure/IGPU-SLOWDOWN.md` §7、`docs/measure/L3-GEMV-NEGATIVE.md`、`.qlh_tmp/igpu-moe/`（D-OP-PROFILE / FIX-REPORT）
> 平台：Intel Iris Xe（Gen12 / XE1）+ i9-13900H + DDR5-4800 双通道（实测 76.8 GB/s 理论、连续读 55.7 GB/s）

标注约定：**[实测]** 本机带 bracket 对照测出；**[代码]** 由源码读出；**[推算]** 公式算出，假设写在旁边。

## 1 结论

1. **核显不是「小号独显」，是「共享内存总线的第二个计算单元」。** 独显的显存带宽是额外的（4060 @272 GB/s），核显的 40.2 GB/s 与 CPU 的 37.0 GB/s 是同一根 LPDDR5 的两个出口，**只差 8.6%**。
2. **唯一数量级优势是 prefill：2.51×**（93.78 vs 37.38 t/s）。因为 prefill 算术强度高（1820 FLOP/byte），96 EU 喂得饱。
3. **decode 只能 +8.6%**（7.89 vs 7.26 t/s）。这是共享总线的物理上限，不是 kernel 可优化的空间。
4. **MoE 要拿容量换**：35B-A3B 在核显上 16.64 t/s（`d43316a0d` 修 MMVQ 后）接近 CPU 冷态 17.33、超过热态 14.09，但**只能用 Q2/Q3**——15.82 GiB 装不下 Q4 的 22.66 GB。
5. **「核显 offload」是伪概念**：放哪都是同一根总线，`-ngl` 按层切分只付切分开销（`-ngl 16` 实测 tg −19%）换不到带宽收益。
6. **一条待验证通道**：host buffer 的读带宽。若核显读 host buffer 不掉速，则模型可突破 15.82 GiB 堆限制，v3 的容量模型完全改变。

---

## 2 判据：算术强度，而不是「设备快慢」

判断「某设备适不适合某阶段」不要凭直觉，算算术强度再比机器平衡点。

一层 `y = W·x`，W 为 (m×k)：

| 阶段 | 读权重 | 计算量 | 算术强度 |
|---|---|---|---|
| **decode（n=1）** | m×k，**读一遍** | 2·m·k FLOP | **2 / 每参数字节** |
| **prefill（n=N）** | m×k，**还是读一遍** | 2·m·k·**N** FLOP | **2N / 每参数字节** |

Q4_K 每参数 0.5625 B：decode **3.56 FLOP/byte**，prefill N=512 时 **1820**，**差 512 倍正好等于 batch size**。

核显平衡点 = 4.45 TFLOPS / 40.2 GB/s = **111 FLOP/byte**：

- decode 的 3.56 远低于 111 → **带宽受限**，96 EU 只发挥 3%（0.14 TFLOPS）
- prefill 的 1820 远高于 111 → **计算受限**，跑到 1.68 TFLOPS（38%）

**[实测]** 这条判据同时解释了两个看似矛盾的现象：

- L3 独立 kernel 失败（tg −28%）：它在优化一个带宽受限的任务，而带宽不是瓶颈。
- MMVQ 修复只对 Q2/Q3 有效（q4_K 37.4 / q6_K 35.2 GB/s 已贴出口，q2_K 只有 7.5）：那是 **dequant 计算受限**，同一框架的另一种瓶颈。

**推论**：一切 decode 提速手段（投机 / MoE / batch / 更激进量化）本质都是**提高算术强度**，而不是「让设备跑得更快」。

## 3 实测定位

**[实测]** 全部带 bracket 对照（同窗口 9B `-p 0 -n 128` 的 normal 值 7.85–8.01，低于 7.5 判为有负载）。

| 场景 | 核显 | CPU | 谁赢 |
|---|---|---|---|
| prefill pp512（9B Q4_K） | **93.78** | 37.38 | **核显 2.51×** |
| decode tg128（9B Q4_K） | **7.89** | 7.26 | 核显 +8.6% |
| decode tg128（35B-A3B Q2_K） | **16.64** | 17.33 冷 / 14.09 热 | 冷态输 4%、热态赢 18% |
| prefill pp512（35B-A3B Q2_K） | 69.09 | 57.53 | 核显 1.20× |

**整体快慢由 prefill/decode 配比决定**（`T = N/pp + M/tg`）：

| 场景 | prompt | 生成 | 核显/CPU |
|---|---|---:|---:|
| 短问长答 | 100 | 1000 | **0.91×** |
| 均衡 | 1000 | 1000 | 0.84× |
| 长文总结 | 10000 | 100 | **0.42×** |

**所以「核显整体慢于 CPU」只在旧数据（decode 7.00 < 7.35）下成立**——那个数出自四个 agent 并发窗口，同一条命令 pp 被压到 44.51 vs 空闲 93.78（2.1 倍）。干净窗口下所有场景都不慢，只是长生成场景被稀释到 9%。

## 4 三条硬约束

### 4.1 独显不是标配

目标设备必须按「核显 + CPU」设计。独显只能作为可选加速，不能进主路径的假设。

### 4.2 核显堆是系统内存的一部分，不是额外容量

本机：总内存 31.6 GB，核显堆 **15.82 GiB**——这 15.82 GiB 是**从系统内存划走的**，剩下约 16 GB 才是 CPU 可用的。

| | 快层 | 慢层 | 总容量 | 两层代价 |
|---|---|---|---|---|
| 独显 | 8 GB @272 GB/s | 32 GB @37 GB/s | **40 GB** | PCIe 16 GB/s |
| 核显 | 15.82 GiB @40.2 GB/s | 剩余 16 GB @37 GB/s | **31.6 GB** | **零**（同一根总线） |

**独显的 offload 是拿容量换带宽；核显的 offload 是拿容量换一个不存在的带宽差。** 而且核显总容量反而比独显方案小。

### 4.3 「offload」在核显上没有物理意义

`-ngl` 按层切分在核显上只付代价：实测 `-ngl 16` tg **5.92（−19%）**、`-ngl 0` 6.19（−16%）。**分层越细越慢**，因为每层要 fence + 搬 hidden state，而 decode 的 hidden 只有 2048×4 = 8 KB，摊不薄同步开销。

**所以 v3 不需要「卸载」概念**，需要的是**容量规划**（模型怎么放进 31.6 GB）和**算力分配**（哪个阶段用哪个单元）。

## 5 为什么不做「独显 + 核显 + CPU」混合卸载

技术上可行（`--override-tensor` 可按 tensor 指定设备），但三个坑一个比一个根本：

1. **sched 不并行**：`ggml_backend_sched_compute_splits` 按拓扑顺序逐个执行 split（层间有依赖），所以「三设备」实际是串行 + 每次切换的同步开销。
2. **核显参与混合不增加带宽**：核显和 CPU 共享同一根 LPDDR5，40.2 + 37.0 不会变成 77，而是分摊 76.8 GB/s 的理论上限。**多设备只增加算力，不增加内存带宽。**
3. **容量管理变成三方博弈**：独显 8 GB + 核显 15.82 GiB（从 CPU 池抢）+ CPU 剩余，没有全局最优解。

**例外**：prefill 阶段可能划算——batch 大（N=512 时每层传 4 MB，40 层 160 MB），切换开销被摊薄，且 prefill 是计算受限、算力可叠加。**这仍然落在算术强度这条分界线上**：算力能叠加，带宽不能。

## 6 待验证：host buffer 通道

容量是硬约束：35B MoE Q4 是 22.66 GB，装不进 15.82 GiB 的 Vulkan 堆，但**总内存 31.6 GB 装得下**。

**[代码]** `a2ef2d731`（host buffer 出 device heap）让 host buffer 用 `portable_aligned_malloc` 拿系统内存、不占 device heap。当时修它是为了解 #31538 的 OOM，但它**同时打开了一条容量通道**：模型可以超过 15.82 GiB，用系统内存兜住。

**未知数**：核显读 host buffer 里的权重，带宽是多少？

- 若仍接近 40.2 GB/s → 22.66 GB 的 MoE Q4 能装下且不掉速，**v3 的容量问题直接消失**
- 若掉到 PCIe 量级 → 这条路走不通，只能用 Q2/Q3

**这是 v3 可行性最关键的一个数**，比再优化 kernel 有价值。验证方法很便宜：拿 9B dense 的权重强制走 host buffer，测 decode 带宽，与正常 device buffer 对比。

## 7 v2.2 已经给出的底子

| 能力 | 状态 | 对 v3 的意义 |
|---|---|---|
| **混合批**（同一 batch 内一个序列 prefill、另一个 decode） | **组 15 实测 18/0/0**（判据 2–6，`verify_multiseq.py`） | v3 的并发形态已经验证过，不需要新批处理层 |
| 分段链（layer-range 推理） | 已落地，组 1–14 覆盖 | v3 可按段分配设备 |
| per-seq 投机四通道 | 组 14 实测通过 | decode 提高算术强度的现成手段 |
| 零拷贝前提（UMA 上权重 CPU/GPU 都能读） | 已验证（`a2ef2d731`） | v3 可以「数据不动、切换算力」 |

**v2.2 做不到的那一步**：`prefill/decode 分离` 在本版指**同一 batch 内多序列混合**（`V22-MULTISEQ.md` §1.3），**不是按阶段分配设备**。后者需要 llama_context 层在两个 backend 之间切 graph，是 v3 的事。

## 8 未做

- **host buffer 读带宽未测**（§6）。这是 v3 容量模型的前提。
- **Gen11（Surface）上 MMVQ 对 Q2/Q3 是否同样受益未验证**。`d43316a0d` 对所有 Intel 放行 Q2/Q3，若 Gen11 上更慢即为回归。
- **prefill 阶段的多设备混合未实测**（§5 的例外）。
- **核显堆 15.82 GiB 是否可调**（BIOS UMA frame buffer）未查——若可调大，容量约束会松，但那是系统配置不是软件。
- **Q2_0 未实测**（`d43316a0d` 与 Q2_K 同族放行，两个模型都不含它）。
