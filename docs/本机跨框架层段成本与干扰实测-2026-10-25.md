# 本机跨框架层段：每层成本与干扰实测

> 状态：**实验验证完成（仅测量，未落地）**。本机（master）**尚未**接入 llama.cpp 层段，
> 三机拓扑与部署权威没有改变；本文只提供"如果接入，成本与干扰各是多少"的实测数字，
> 供 `LOCAL-EXECUTORS-01` 与 NInfer 上游替换的容量/切点规划直接引用。
> 日期：2026-10-25 ｜ 主机：i9-13900H（6P+8E / 14C20T）、31.6 GB RAM、RTX 4060 Laptop 8 GB

## 0. 为什么要测

三机流水线里 master 跑 PyTorch CUDA，两个远端跑 llama.cpp CPU。`safetensors_layer_offload`
（权重驻留主机内存、每步搬过 PCIe 在 GPU 上算）实测每层成本远高于 llama.cpp 的
"权重常驻 RAM、CPU 就地算"。端到端步时由**最长段**决定，所以"本机也挂一个 llama.cpp 段"
是否值得，取决于两个量：

1. **本机 CPU 每层多少钱**（决定它能不能替远端分担）
2. **它会干扰现有服务多少**（决定代价）

本文把这两个量都测了。

## 1. 每层成本（决定性数据）

工件：`models/q35-9b-local-artifacts/q35-9b-local-mid4-24.gguf`（3.70 GB，`[4,24)` **20 层**）
shim：`build/keephead/build-cpu/bin/qlh_keep_head.dll`（avx2 档）
驱动：`llama_keep_head.KeepHeadUpstream.forward_hidden_to_hidden`（`mode="nextn"`，`n_batch=4096`）
方法：预热 4 步后取 9 步中位数（decode，单 token）

| `n_threads` | ms/步 | ms/层 |
|---|---|---|
| 6 | 142.0 | 7.10 |
| **8** | **136.8** | **6.84** ← 最优 |
| 12 | 156.8 | 7.84 |

**结论**：**本机 9B 中间段 = 6.84 ms/层**，`n_threads=8` 最优。12 线程反而变慢，
与本机 6P+8E 混合核一致（线程跨 P/E 核调度不均匀）。

### 与其它执行方式对比

| 执行方式 | ms/层 | 20 层耗时 | 数据来源 |
|---|---|---|---|
| **本机 llama.cpp（就地算）** | **6.84** | **136.8 ms** | 本文 §1 |
| rog-5060 llama.cpp（Ryzen 5 9600X） | 8.7 | 174 ms | 三机实测 |
| android-542cd254 llama.cpp（骁龙 8 Gen 3） | 20.1 | 402 ms | 三机实测 |
| **`safetensors_layer_offload`（PCIe 搬运）** | **76.8** | **1535 ms** | 三机实测 |

⇒ **就地算比搬运快 11.2 倍，比 rog 快 27%，比 android 快近 3 倍。**

### 参考：本机 7B Q4_K_M 的 `n_ubatch` 扫描

`models/DeepSeek-R1-Distill-Qwen-7B-Q4_K_M.gguf`，`n_threads=8`，每配置取两轮最优：

| `n_ubatch`（`n_batch=4096`） | ms/token | ms/层 @28L |
|---|---|---|
| **512** | **116.7** | **4.17** |
| 1024 | 119.0 | 4.25 |
| 2048 | 124.4 | 4.44 |
| 4096 | 124.1 | 4.43 |

`n_ubatch=512` 略优（约 6%）。**测试方法注意**：同一进程顺序测多配置时，**第一个配置会
承担冷页缓存代价**——本项首次测量把 512 放在最前，得出"512 慢 51%"的相反结论；
统一预热后方向反转。多配置扫描必须预热或打乱顺序。

## 2. 干扰实测（关键负面结论）

背景负载：独立进程加载 §1 的中间段并**持续** `forward_hidden_to_hidden`（8 线程）。
服务侧：同一时刻用 `local_docs/perf-control-read-20261025/collect.py` 采三机
`balanced` 档的端到端请求（各 3 次）。

| 分组 | HTTP | decode | between（master 本地） |
|---|---|---|---|
| 基线（无背景负载） | 10.86 s | **284.5 ms** | 94.3 ms |
| **A：8 线程，无亲和** | 11.15 s | **306.8 ms** | 116.8 ms |
| **B：8 线程，亲和 `0xFF000`（核 12–19）** | 11.48 s | **315.8 ms** | 120.6 ms |

- 干扰量：decode **+7.8%**、`between_steps` **+24%**、HTTP **+2.7%**
- **CPU 亲和性隔离无效**（B 比 A 还差 3%），日志已确认亲和生效
  （`affinity -> [12, …, 19]`）

### 为什么亲和性无效

**瓶颈是内存带宽，不是核数。** 本机段读 3.7 GB 权重 ÷ 136.8 ms ≈ **27 GB/s**，
而 DDR5-5600 双通道实际约 55–65 GB/s ⇒ 单是这一段就占用 30–50% 带宽。
亲和性只约束"哪个核算"，约束不了"内存控制器给谁多少带宽"，服务与段仍共享同一个
内存控制器 ⇒ 干扰原样保留。

这与 `22e`（`LLAMA-COMM-BORROW-01`）把通信成本列为"**CPU、GIL 和内存带宽**"三项一致。

> ⚠️ **给 `LOCAL-EXECUTORS-01` 的结论**：**"CPU 亲和性隔离"不应被当作本机多执行器的
> 隔离方案**，它不解决实际瓶颈。真要做隔离只能走内存带宽配额（Windows 上不易实现），
> 或者接受干扰、用负载均衡的收益覆盖它。

## 3. 收益与代价的相对关系

```
干扰代价：decode  +7.8%（284.5 → 306.8 ms）
潜在收益：切点重排后理论 ~104 ms（-63%）
```

收益来源是**负载重排**而非单点替换：端到端 = 最长段，而现在
`rog` 扛 24 层（约 209 ms）是瓶颈，**最慢的 android（20.1 ms/层）却还在扛 8 层**。
本机以 6.84 ms/层加入后，切点有额外自由度重新均衡，例如：

```
master pytorch [0,4)    4 层 + embedding  ≈  50 ms
本机   llama   [4,16)  12 层 × 6.84      ≈  82 ms
rog    llama   [16,28) 12 层 × 8.7       ≈ 104 ms   ← 瓶颈
android llama  [28,32)  4 层 × 20.1      ≈  80 ms
                                    合计 ≈ 104 ms
```

> 上表是按实测 ms/层做的**推演**，未经端到端验证；接入后必须以真机实测替换。

## 4. 尚未验证 / 已知反证

- **上表的端到端 ~104 ms 是推演**，未实测。收益前提是"大模型 + 显存装不下"。
- `docs/主线开发计划…-2026-09-14.md`：**"分布式请求 657 ms、同机 CPU 回退 313 ms，
  当前 CPU worker 对小模型没有吞吐收益"** ⇒ 小模型上同机 CPU 段可能不划算。
- `src/inference_switches.py`：**"CPU dense 2B 0.927×（亏，pp 也降）"** ⇒ CPU 路径
  非无条件更快。
- 本机 6P+8E 的线程调度跨混合核不均衡，长时间稳定值可能劣于 136.8 ms（本文为短测中位数）。
- **同机容量重复计数未修**：`src/qlh_core/planning/capacity.py` 按节点记账、无物理机去重
  ⇒ 同机两段会各自按整机 RAM 记账。这正是 `LOCAL-EXECUTORS-01` 的交付条件
  （"同物理节点两段可规划，容量无重复计数"）。

## 5. 与既定路线的关系

- **产品方向**：`docs/NInfer与llama混合层段及异步页流水补充调研-2026-10-25.md` 已确定
  「同一物理节点归属 + node/executor 分离」，并**点名反对"重复注册虚拟物理节点"**
  （会掩盖 RAM 共享、断线和设备竞争）。票 `LOCAL-EXECUTORS-01` 是其正式载体。
- **上游替换**：计划将上游从 PyTorch 换为同为 C++ 的 NInfer 并定制化改造。届时
  「本机 GPU 段（NInfer）+ 本机 CPU 段（llama.cpp）」是自然形态；本文的
  **6.84 ms/层**与**+7.8% 干扰**正是那时做容量与切点规划所需的两个输入。
- **已存在的形状**（未启用）：`model_supply.py` 对 master 之外节点按各自申报独立选引擎；
  worker 注册无 loopback 禁止；`peer.py` 的 client 默认连 `127.0.0.1`；
  `pipeline_node_contract.py` 文档化的 `master[0,8) + middle[8,24)` 拓扑。
  现成工具 `scripts/relay_mid_service.py`（本机 loopback 中间段服务）与
  `tests/test_tui_e2e_flow_da.py`（"D-a 档"）可作原型起点，但 D-a 档硬约束
  `real_model_loaded=false`，**不得据此宣称真模型已加载**。
- **路径 C（PyTorch CPU resident）不可行**：`transformers/integrations/hub_kernels.py`
  在模块导入时即绑定 fla 的 Triton CUDA kernel，wrapped 无 device 分派
  ⇒ CPU 张量直接抛 `ValueError: Pointer argument cannot be accessed from Triton`。
  `tests/test_layer_offload_runtime.py` 里"CPU 能跑"是**显式 monkeypatch 掉 fla 绑定**
  的结果，不是生产行为。
