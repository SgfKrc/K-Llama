## 1. 模型管理

文件：`src/model_module.py`、`src/llama_engine.py`、`src/model_config.py`

`ModelManager` 统一管理 PyTorch 与 llama.cpp 引擎：

- `select_engine(profile)`：结合显式配置、CUDA 和设备画像选择引擎。
- `load_model(...)` / `unload_model()` / `switch_model(...)`：加载、卸载和切换注册模型。
- `load_layer_range(...)` / `ensure_layer_range(...)`：加载或确认 PyTorch 连续层段及 Embedding/LM Head 权重。
- `ensure_full_model(...)`：检查显式本地路径的完整模型；分布式专用runtime及裁层GGUF具名拒绝整模补载。
- `forward_layers(...)`：执行 PyTorch 层段前向。
- `chat(...)` / `chat_stream(...)`：完整模型对话入口。

模型注册的唯一可写入口为`CatalogService`，`model_config.py`提供兼容投影。分布式准入由`ExecutionApplication.freeze`核对已发布deployment、assignment及实际runtime回执。

## 2. TCP 通信

文件：`src/tcp_comm.py`

- `TCPServer.start(...)`：主节点监听并处理注册、认证、心跳和业务消息。
- `TCPServer.send_to_client(...)` / `broadcast(...)`：向已注册节点发送消息。
- `TCPClient.connect(...)` / `disconnect()`：从节点建立或关闭连接，并负责重连状态。
- `TCPClient.send_data(...)` / `recv_data(...)`：发送和接收协议消息。
- `serialize_tensor_fast(...)` / `deserialize_tensor_fast(...)`：层流水线张量序列化。
- `MessageType`：注册、配置、推理转发、层前向、结果、取消和心跳等消息类型。

TCP 连接成功、节点注册成功、模型同步成功和流水线 ready 是四个不同状态，UI 和调度器不能互相替代。

排查"节点假在线"时的现行行为：

- 客户端 `_recv_loop` 的清理在 `finally` 中并带兜底 `except`：帧解析异常不会让接收线程静默退出（否则心跳仍在发、主节点仍视其在线、且永不重连，形成"僵尸连接"）。
- `recv_exact()` 区分**空闲超时**与**帧中途超时**：帧读到一半超时抛 `ConnectionError` 走重连，不丢弃已读字节（丢弃会造成字节流失步）。
- 连接代数在**注册成功后**才推进：注册失败不会把心跳与重连线程按旧代数淘汰成孤儿。
- 服务端 per-socket 收包超时在注册后放宽到 `HEARTBEAT_INTERVAL*(MAX_HEARTBEAT_MISSED+1)+2`，与 12 秒心跳容忍一致（固定 5 秒会让从节点卡顿 6 秒即被误踢并触发重新分层）。

## 3. 调度与层编排

文件：`src/scheduler.py`、`src/qlh_core/execution/requests.py`、`src/qlh_core/bootstrap/execution.py`

`Scheduler`保留节点生命周期、主从连接、模型同步、部署与执行适配及指标。请求队列和终局由`RequestService`持有。主要入口包括：

- `start(...)` / `stop()`：启动或停止调度器。
- `init_nodes()`：初始化节点状态。
- `compute_layer_assignment(...)`：生成满足能力和层覆盖约束的分配结果。
- `run_pipeline_safe(...)`：冻结线性部署与具名准入拒绝入口。
- `start_infer_task(...)` / `complete_infer_task(...)` / `fail_infer_task(...)`：转发请求登记与指标；分布式取消由请求owner执行。

`RequestService`拥有有界FIFO、准入暂停、等待取消、deadline及物理排空状态。`run_pipeline_safe`委托`ExecutionApplication`冻结已发布部署，`LinearExecutor`按唯一计划执行。图放置器与三级抢占队列已裁撤。

补充：`compute_layer_assignment()` 按 `device_info.island.enabled` 排除 TP 孤岛网关节点（孤岛承担整请求推理，不参与层拆分）；节点排序打分对孤岛节点按声明的聚合显存与 GPU 数上浮权重。三处 ACK 经 `_send_lock` 保护的 `send_data` 通道发送（直接 `sock.sendall` 会与心跳并发写、导致帧交叉损坏）。`Scheduler.__init__` 显式初始化 `_tcp_client`；健康监控首轮不把启动态判为“恢复”。

## 4. KV Cache

文件：`src/paged_kv_cache.py`、`src/model_module.py`、`src/scheduler.py`

`PagedKVCache` 提供固定页、追加、读取和清理能力。显式传入 `cold_cache_dir` 与 `cold_max_pages` 时，超出热页上限的封存页写入实例隔离的磁盘冷层；冷层读写带 manifest/SHA-256 校验，且当前不跨进程恢复旧实例目录。`cache_unit_size` 用于冻结可复用前缀的固定 token 间隔，必须整除 `page_size`；`KVHost.init()` / `from_profile()` 与 `/v1/kv/init` 支持透传这些可选字段，`/v1/status` 的 `kv_cache.tasks` 返回冷层和缓存单元摘要状态。分布式 PyTorch 前向实际使用的模型 `past_key_values` 按任务和层段由调度器持有，任务完成或中止时清理。两者不能在文档中混写成同一个实现状态。

llama.cpp 侧的推理开关（KV 量化 `type_k`/`type_v`、`flash_attn`、线程数）由 `src/inference_switches.py` 显式映射，不再由各默认值各自为政。它把事实源分成两层：`engine_isa` 是 llama.cpp **构建实际启用**的指令集（`llama_print_system_info()`），`host_isa` 是 CPU **硬件支持**的指令集，二者不等价，不得互相代替。默认档位等于接线前行为（KV 不量化、flash-attn 关、线程数交给调用点、`cpu_moe=auto`），非默认值只能来自 `QLH_INFER_KV_CACHE` / `QLH_INFER_FLASH_ATTN` / `QLH_INFER_THREADS`；调用方显式传入的加载参数始终优先。每条映射都带实测依据（`EVIDENCE`），设备画像 `to_dict()` 的 `inference_switches` 段与引擎加载日志记录实际生效档位，使关闭态同样可观测。

绑定路径（`llama_engine`）与 `llama-server` 子进程（`llama_server_process`）共用同一张映射，入口都是 `resolve_from_device_profile()`：子进程侧经 `server_argv_args()` 翻成 `--threads` / `--cache-type-k` / `--cache-type-v` / `--flash-attn [on|off|auto]`（参数名以本机 `llama-server --help` 实测为准），默认档位不产出任何参数，`ServerSpec.inference_args` 为空即与接线前命令行逐字一致。PyTorch 分层路径同理：`model_module._resolve_pytorch_flash_attn()` 决定 `config.use_flash_attn`，默认仍是关闭（等于接线前的硬编码值）。

`n_ctx` 也不再是全局常量：`llama_engine._default_n_ctx()` 先按**每段 KV 预算**（层数 × KV 头数 × head_dim × 每元素字节，K/V 各按自己的量化档）反推槽位，并注意 llama.cpp 会把 `n_ctx` 按 `n_seq_max` 均分（`llama_keep_head.ctx_per_seq_for`）。推导结果只用于**收窄**上限、不会放大；画像或 GGUF 头不可用时回退既有 `MAX_SEQ_LEN`。

## 5. API 与客户端

文件：`src/api_server.py`、`src/tui_textual.py`、`src/tui_commands.py`、`schemas/`；Web/Android 位于各自子模块

- FastAPI 暴露聊天、流式聊天、模型、节点、队列、集群状态和 bootstrap 等接口。
- `POST /api/chat`、`POST /api/chat/stream` 新增 `allow_external` / `prefer_external` 两个可选布尔字段，缺省均为 `false`，旧客户端行为不变。
- `/api/workflows`、`/api/experimental/speculative`及旧task-graph／队列策略端点由`routes_tasks.retired_workflow`返回HTTP 410与`CLIENT_FEATURE_REMOVED`。
- `/api/status`保留`island`／`external`观测，端点与凭据脱敏；`/api/client/state`及其SSE events使用`ClientSnapshots.current`的schema v2投影。
- `/api/cluster/connect` 等 9 个集群管理端点跑在 `run_in_threadpool` 中：同步阻塞调用不会冻结事件循环（否则连接不可达主节点时会卡住整个事件循环最长约 50 秒）。
- 主线 TUI 展示聊天、模型、节点、层分配和执行指标；`python qlh.py` 是当前稳定入口（只读查询可用 `python src/tui_commands.py <command>`）。
- 外部 Web/Android 产品壳可展示同一组合同，但不改变主仓的引擎与控制面边界。
- Android Full 支持本地 GGUF 与远程 PC 模式；Lite 保持轻量远程入口，当前不注册为 PyTorch `pipeline_worker`。

## 7. TUI 管理入口

文件：`src/tui_textual.py`、`src/tui_commands.py`、`start_tui.sh`、`start_tui.bat`

## 8. 推理宿主与节点运行时（阶段 0 边界治理）

文件：`src/model_host.py`、`src/node_runtime.py`（2026-08-02 新增）

**推理宿主 `model_host`（`src/model_host.py`）**：api_server 与 scheduler 共享的模型管理入口，消除 scheduler 对 api_server 的运行时反向 `import`（原 scheduler.py 中 12 处函数内 `import api_server` 已全部改为 `self._host` 注入）：

- `InferenceHost`：协议类型（`select_engine` / `load_model` / `unload_model` / `load_layer_range` / `forward_layers` / `chat` / `chat_stream` / `ensure_full_model`），行为由 `model_module.ModelManager` 提供。
- `ModelHost`：统一持有内部 manager（惰性加载，原 `api_server._LazyModelManager` 迁入）与模型运行时状态（`model_loaded` / `generation_config` / `current_quant` / `_db_available` / `full_chat_execution_lock`）；显式原生端口读取manager，运行态由`RuntimeController`发布。
- `SchedulerCallbackSet`：组合入口显式注入选定的模型身份、stage执行、提示构建、响应格式与日志回调。

- `node_runtime.get_node_id()` / `set_node_id()` / `get_node_role()` / `set_node_role()` / `update(...)`（线程安全）。
- 写回来源改造：`scheduler._sync_runtime_node_config` 与 `node_config.apply_runtime_config` 不再写 `cfg.NODE_ID` / `cfg.NODE_ROLE`，改经 node_runtime；scheduler 模块级 `NODE_ID` / `NODE_ROLE` 仍同步更新以保持模块内既有读取行为不变。

**接线关系**：API组合入口配置`SchedulerCallbackSet`；scheduler 经 `self._host` 访问模型与回调；阶段 1 起 host 可替换为远程 inference-svc 适配器而不改 scheduler 调用方。

## 9. Relay 层接力合同与探针（CORE-RELAY-01）

文件：`src/relay_contract.py`、`src/relay_planner.py`（2026-09-16 新增）、`scripts/llama_relay_probe.py`

**合同 `relay_contract`（`src/relay_contract.py`）**：把层接力实验（[跨框架层接力重启评估](archive/relay/跨框架层接力重启评估-2026-09-15.md) §7.8–§7.11）的结论冻结为可校验规则：

- `RelayModelIdentity`：区分逻辑模型摘要 `model_sha256` 与具体工件摘要 `artifact_sha256`，并区分 GGUF `block_count`（含 MTP 层）与参与前向的 `n_layer = block_count - nextn_predict_layers`。
- `RelayTrimPlan`：裁层计划（保留 `blk.K..`；`kept_block_count`）与**层号映射** —— 裁层实例 `layer i` ≡ 源模型 `layer i + K`。
- `RelayHiddenSpec`：handoff 线上格式（`n_embd` + dtype，`bytes_per_token`）。
- `build_relay_handoff(...)`：准入校验 —— 同引擎、同逻辑 `model_sha256`、同架构/embedding 宽度、下游 `block_count = 上游 block_count - cut`、MTP 布局一致、`cut_layer ∈ [1, n_layer-1]`（保证被交接层 ≤ `n_layer-2`，**末层永不跨界**）；上下游允许拥有不同 `artifact_sha256`。每条拒绝返回具名 `reason`；**跨引擎（PyTorch → llama.cpp）在 `CORE-RELAY-XFRAME-01` 之前一律 `cross_engine_not_admitted`**。
- `judge_relay_generation(...)`：**唯一判据是逐 token argmax**；`cosine` / `bitwise_equal` 仅作证据记录，**永不作为门限**（§7.11.2：`llama_batch.embd` 路径在单进程内即非确定，低 cosine + argmax 一致才是健康形态）。
- `relay_fallback(reason)`：任何拒绝/失败都回落到 `single_process_llama_cpp`。

**规划器 `relay_planner`（`src/relay_planner.py`）**：`plan_relay_cut(total_layers, n_embd=..., requested_cut=..., downstream_profile=...)` —— 显式 cut 或按下游画像保守自动切分；**缺画像即拒绝**（`downstream_profile_missing`）；`cut` 上限 `total-1` 保证末层不被跨。

**验收探针 `scripts/llama_relay_probe.py`**（票 8 的"可复现命令"）：驱动 `llama-relay-gen` 跑 baseline/relay 对拍，**判定直接调用 `judge_relay_generation`**，输出 JSON 报告与退出码。

- 缺资产 → `missing_assets`，且**不执行任何命令**（不声称跑过未跑的接力）；输出声明步数与实际 token 数不符或未达到请求步数时拒绝。
- `--verify-fallback`：拒绝后**真跑**单机（整模型 token 路径）并报 `single_process_ok`，把"回退可用"从断言变成实测。
- 具名诊断：`runner_dll_missing`（Windows 加载失败 `0xC0000135` / `0xC0000139` —— MSYS2 工具链 bin 不在 PATH 时进程零输出）、`runner_timeout`、`runner_unavailable`、`unparsable_output`、`runner_failed_after_match`。

**接线关系**：本票已完成主仓**合同 + 规划器 + 验收探针 + 回退验证门**，但**尚未接入生产推理路径**；`llama_engine` 侧显式开关、跨进程/网络 handoff 仍由 `CORE-RELAY-XFRAME-01` 受控验证。Relay 默认关闭，不替代 RPC，也不改变现有 `LAYER_FORWARD` 协议。

## 10. Relay XFRAME 实验准入门（CORE-RELAY-XFRAME-01）

> **现行状态**：上游 #28963 的调用方 `pos` 越界读已按 M-RoPE 契约修复；D→L 141-token prefill、逐步生成与 loopback TCP 双进程均严格 `141/141`。生产门保持 fail-closed。

文件：`src/relay_contract.py`、`scripts/llama_relay_xframe_probe.py`（2026-09-16 新增）

- `RelayXFrameRequest`：描述跨边界实验的上/下游引擎、网络范围、请求长度和采样参数。
- `admit_relay_xframe(...)`：实验准入门默认**拒绝**，只允许 PC 显式的 `loopback` 或 `ssh_tunnel` 范围；公网/Tailnet 直连、跨引擎 D→L、非确定性采样和非法/异常序列长度均返回具名 reason，并要求回退到单进程 llama.cpp。
- `xframe_evidence_required` 不是成功结论：它表示请求形状合规但还缺少独立 D→L/跨进程/长序列实测证据。当前没有把该门接到 `llama_engine`、API 或 TUI，也没有把 XFRAME 接入默认生产路由。
- `llama_relay_xframe_probe.py`：读取完整路径与接力路径产生的 raw little-endian float32 logits，逐行计算 argmax 并复用 `judge_relay_generation(...)`；SHA256、bitwise、cosine、top-k 只作为结构化诊断。矩阵为空、形状不整除、位置数不同、非有限值均 fail-closed；`argmax_match_count` 表示全部位置的匹配总数，`verdict.matched_steps` 表示首个分歧前缀长度。
- 验收基线：D→L 同机文件交接 prefill、逐步生成、跨机（SSH 隧道）逐步生成与 f32 权重对照均为 `141/141` 逐 token 一致；采样矩阵只认 `T=0` 确定性档（两侧各自采样必然在第 2 步分叉）。

**接线关系**：XFRAME 冻结生产接入前的边界与失败语义，尚未接入 `llama_engine`、API 或 TUI。行为等价、bitwise 差异、f32/采样矩阵与实时跨进程/网络传输证据分别登记。
