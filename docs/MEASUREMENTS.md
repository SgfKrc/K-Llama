# 层段拆分实测定稿

> 状态：**现行**
> 更新日期：2026-10-28
>
> 适用范围：Qwen3.6-35B-A3B（MoE，40 层，256 专家，激活 8，hidden 2048，Q4_K_XL，
> 20.81 GiB）在本机（i9-13900H 14C/20T + RTX 4060 Laptop 8188 MiB + 31.6 GiB RAM）
> 的单进程与两进程层段拆分实测。原始输出 `H:\slimarc-proto\exp\`。

---

## 1. 结论摘要

| 方案 | tg128 | 相对单进程 |
| --- | ---: | --- |
| 纯 CPU（`-ngl 0`） | 8.23 | 29% |
| **单进程 `-ngl 99 -ncmoe 32`（t=8）** | **28.02 ± 0.15** | 基线 |
| **两进程拆分（t=3，绑核）** | **15.4–18.4（多次测量中位约 17）** | **≈61%** |

两进程拆分**未达到** 28.02 的目标，达到约 **61%**。原因见 §5。
数值正确性**逐位通过**。

### 1.1 测量条件（复现时必须匹配）

本机同时运行 DeepSeek Harness 与浏览器，二者合计占用约 2.8 核。测试负载本身只有
3 线程，与背景同量级，因此：

- **必须绑核**：GPU worker 固定 `0,1`，CPU worker 固定 `2-7`
- 单进程 `llama-bench` 不绑核时可复现 ±0.15 方差（t=8），但与其他负载交错时波动可达 ±4
- `chain_client.py --repeat` 的**第 1 轮永远是冷启动**（模型页未进 page cache），
  18.3 → 38.5 pp 的跳变即为此。稳态取第 2 轮起

未绑核时曾测得 19.55 的瞬时值，绑核后的 4 轮中位 17.1 更可信。

## 2. 裁层工件

`scripts/cut_layers.py` 对 `qwen35moe` 有硬约束：切分点必须是
`full_attention_interval`（=4）的整数倍，否则层类型错位、无法加载。

| 工件 | 命令 | 大小 | 张量数 |
| --- | --- | ---: | ---: |
| `gpu-0-8.gguf` | `--keep-head 8` | 5.03 GB | 149 |
| `cpu-8-40.gguf` | `--k 8` | 16.81 GB | 587 |

合计 21.84 GB（整模 20.81 GB），多出部分是两段各自携带的全局张量。

## 3. 单进程基线扫描

工具 `llama-bench`（d854d98ba / b11889），`-p 64 -n 64 -t 8 -r 5`。

| 专家上卡层数 | `-ncmoe` | tg64 |
| ---: | ---: | ---: |
| 0 | 40 | 25.94 ± 1.67 |
| 4 | 36 | 28.62 ± 0.10 |
| **8** | **32** | **28.99 ± 2.45** |
| 10 | 30 | 32.01 ± 0.33 |
| 12 | 28 | 17.31（`-r 5`）/ 33.29（`-r 2`） |
| 14 | 26 | 11.23 ± 0.09 |
| 16 | 24 | 9.75 ± 0.04 |

### 3.1 只把专家放 GPU 比整层放 GPU 快 3 倍

| 方案 | `-ngl` | `-ncmoe` | tg64 |
| --- | ---: | ---: | ---: |
| 专家上卡（11 层） | 99 | 29 | 30.45 |
| 整层上卡（11 层） | 11 | 29 | 10.11 |

原因：专家占权重 88%（19.67 GB）但每 token 只用 8/256。把"体积最大、访问最稀疏"
的部分放进最快的设备收益最大；attention/norm 每层必读但只占 6.2%。

### 3.2 显存硬边界

12 层专家 ≈ 5.3 GiB 可装，14 层 ≈ 6.2 GiB 溢出。**溢出后不报错**：Windows WDDM
把系统内存当显存用，只表现为掉速（12 层 33 → 17，14 层 → 11）。
`-n` 越大 KV 越大，边界前移（`-n 256` 时 12 层即溢出）。

### 3.3 `-ncmoe` 语义

`N` = 前 N 层专家留 CPU。实现走 `tensor_buft_overrides`
（`tools/llama-bench/llama-bench.cpp:1219-1223`），把匹配层的专家张量钉到
`ggml_backend_cpu_buffer_type`，pattern 为
`blk\.<i>\.ffn_(up|down|gate|gate_up)_(ch|)exps`。

## 4. 两进程拆分

### 4.1 数值正确性

GPU 段（`nextn` 模式）hidden 输出 vs 整模（`layer_inp cut_layer=8`），16 token：

```
max abs diff : 0.000000e+00
cosine       : 1.000000119
result: PASS
```

**逐位相同**，裁层无损。

### 4.2 线程数扫描

两进程模式下，CPU worker 线程数是关键参数：

| 线程数 | tg64 |
| ---: | ---: |
| 2 | 9.29 |
| **3** | **18.60** |
| 4 | 17.93 |
| 6 | 17.33 |
| 14 | 11.35 |
| 20 | 5.34 |

**t=3 最优**。这与单进程的 8 线程结论相反：两进程时两个 Python 主循环都要占核，
CPU 段本身又受内存带宽约束，线程过多只会争用。

### 4.3 最终验收

`chain_client.py --gen 128 --repeat 4 --threads 3 --gpu-cpus 0,1 --cpu-cpus 2,3,4,5,6,7`：

```
run 1: pp32=18.3 t/s  tg128=16.10 t/s  (median 62.1 ms, p90 84.6 ms)  <- 冷启动
run 2: pp32=38.5 t/s  tg128=18.09 t/s  (median 55.3 ms, p90 61.1 ms)
run 3: pp32=41.9 t/s  tg128=18.41 t/s  (median 54.3 ms, p90 64.9 ms)
run 4: pp32=43.6 t/s  tg128=15.34 t/s  (median 65.2 ms, p90 82.2 ms)
```

稳态 **15.4–18.4 t/s**，中位约 17。run 1 的回落是冷启动，run 间波动来自背景负载。

多次独立测量的稳态区间：15.44 / 15.85 / 16.10 / 18.09 / 18.41 / 15.34。
取中位约 **17 t/s** 作为代表值；任何单个瞬时值（含曾出现的 19.55）不作为结论。

### 4.4 分段延迟

| 跳 | 两进程 | 同进程 | 差值 |
| --- | ---: | ---: | ---: |
| GPU 段 | 7.52 ms | 5.8 ms | +1.7 ms |
| CPU 段 | 87.75 ms | 42.3 ms | +45.5 ms |

**GPU 跳的 socket 开销仅 1.7 ms**（8 KiB hidden 走 loopback），说明协议本身不慢。
CPU 跳的 45 ms 差额来自两进程争用，不是传输。

## 5. 为什么拆分慢于单进程

三条原因，按影响排序：

**① 显存必须分摊。** 单进程时 8 GB 显存全部服务于"非专家 + 后 8 层专家"；
拆分后 GPU 段独占 4630 MiB，CPU 段的非专家只能分到 1734 MiB，剩余专家
（14.4 GB）全部留在主机内存。实测 CPU 段一旦让专家上卡就崩溃（0.45 t/s）。

**② 两进程争用 CPU 与内存带宽。** 两进程时最优线程数是 3（单进程是 8），
且 CPU 段单进程 forward 70.8 ms、串联时 87.75 ms，17 ms 花在争用上。

**③ 多一次 hidden 交接。** 1.7 ms，占比小但不是零。

**结论：单机拆分必然慢于单进程。** 拆分的价值在能把 CPU 段挪到另一台设备，
那时两段的内存和显存是**相加**而非**共享**。

## 6. 复现

```powershell
# 单进程基线
llama-bench -m <full.gguf> -p 64 -n 64 -ngl 99 -ncmoe 32 -t 8 -r 5

# 裁层
python scripts/cut_layers.py --src <full.gguf> --dst gpu-0-8.gguf --keep-head 8
python scripts/cut_layers.py --src <full.gguf> --dst cpu-8-40.gguf --k 8

# 数值正确性
python check_correct.py --prompt-tokens 16

# 两进程吞吐
python chain_client.py --gen 128 --repeat 3 --threads 3
```

## 7. 与原定验收的差距

目标为「跨进程拆分后保住 29.74 t/s」，实测稳态 17.1，差距 42%。

差距的根因是**显存总量**：单进程方案靠"8 GB 显存放全部非专家 + 后 8 层专家"取得
28.02，拆成两个 context 后同一块显存要容纳两份模型的非专家部分，无法复现该分配。

实测证据：CPU 段一旦让专家上卡（`n_cpu_moe` 从 32 降到 30），吞吐从 18.48 崩到 0.45
——显存不足时 WDDM 静默溢出，不是计算变慢。

若要把拆分做到同速，需要以下之一：
- 第二台设备承担 CPU 段（内存与显存都独立）——这是本原型的真实目标场景
- 单机增加显存
- 减少总模型体积（更低比特量化）

## 8. 结论：单机拆分不划算，跨机才是目的

| 场景 | 显存 | 内存 | 预期 |
| --- | --- | --- | --- |
| 单机单进程 | 8 GB 全部可用 | 31.6 GB 全部可用 | 28.02 t/s ← 当前最优 |
| 单机两进程 | 8 GB 被两段分摊 | 同上 | 17.1 t/s ← 慢 |
| **跨机两段** | 各段独占本机 8 GB | 各段独占本机内存 | **待测** |

跨机时两段的资源是相加而非共享，理论上 CPU 段能拿到完整的 14.4 GB 专家 + 2.4 GB
非专家，比单机拆分宽松。这是下一阶段要验证的核心假设。

## 9. 段间 hidden 的传输 dtype（2026-10-30，2B）

背景：跨机每步约 157 ms，其中约 24 ms 是 Tailscale 传 8 KB hidden（MTU 1280，
约 6 个包，每包 ~5 ms）。换成 4 KB 就能少一半包。代价是精度——这一节回答
"值不值得"。

测量条件：`topology-2b.toml`（2B 两段，20+4 层，纯 CPU），`checks/verify_wire.py`，
贪心采样，5 个 prompt × 48 token；重复运行用于确认链本身是确定性的。

### 9.1 float16 让输出变了，int16 定点也一样

| 传输 dtype | 单跳量化 max\|diff\| | 相对 max\|a\| | 贪心 token 一致 |
| --- | ---: | ---: | ---: |
| float32 | 0 | 0 | 5/5（基线） |
| float16 | 3.9e-3 | 3.0e-4 | **4/5**，p2 在第 22 步分叉 |
| int16 定点 | 2.2e-4 | 1.5e-5 | **4/5**，p0 在第 16 步分叉 |

hidden 的真实范数 34–100（与 35B 的 9–89 同量级）；int16 是 per-tensor 对称定点，
scale 随 payload 前 4 字节传，量化步长比 float16 的 ULP 细约 20 倍。

float32 与 int16 各重跑一次，两次逐位一致——分叉是量化引起的确定性变化，不是随机
抖动。两个 4 KB 方案各在一个 prompt 上翻转 token，且都发生在输出接近平局的位置。
所以不能用"大多数 prompt 一致"代替"一致"。

**结论：不用 float16，也不用 int16。** 默认 float32；`SA_WIRE_DTYPE` 只是实验开关
（默认 float32），worker 按请求 meta 里的 dtype 解码并用同一 dtype 回复。

### 9.2 拷贝从 5 份降到 1 份，耗时没变

每步 hidden 单向的 8 KB payload 拷贝：

| 位置 | 改前 | 改后 |
| --- | ---: | ---: |
| client `tobytes` | 1 | 0（memoryview 直接进帧） |
| `protocol.encode` 拼接 | 2（+blob、+header） | 1（一次 join） |
| worker `read` | 2（chunks join、payload 切片） | 0（recv_into + memoryview） |
| **合计（单向）** | **5** | **1** |

微基准（`checks/bench_wire.py protocol`）：整帧构造 2.195 → 2.257 µs（噪声内）。
8 KB memcpy 0.15 µs，省 4 次拷贝约 0.6 µs。**这一项不改变延迟。**

loopback worker 往返（2B tail 段，300 次中位）：`StageEngine` 直调 17.45 ms，
worker 往返 17.76 ms，差 0.31 ms。2B 上整个 worker 协议成本不到 1 ms，不是标题里的
11 ms。那 11 ms 出在 ROG 的 35B 段（计算 32 ms），本轮按约束不碰 ROG，本机无法复现；
但它与 8 KB 拷贝的量级不符（5 份 ≈ 0.75 µs），所以拷贝优化注定救不了它。

### 9.3 跨网模拟：4 KB 确实少 3 个包

`checks/bench_wire.py proxy` 在本机 worker 前插一个中继：每方向最多转发 1240 B
（1280 MTU − 40）后 sleep 5 ms，与实测的"每包一个 RTT"同构。这是链路模型，不是
Tailscale 本身；中继会打印转发块数，假设可见。

| dtype | 上行字节/步 | 块数/步 | 中继后每步 | 相对 loopback |
| --- | ---: | ---: | ---: | ---: |
| float32 | 8246 | 7.0 | 51.85 ms | +35.15 |
| float16 | 4150 | 4.0 | 33.83 ms | +17.13 |
| int16 | 4152 | 4.0 | 33.79 ms | +17.09 |

4 KB 比 8 KB 每步少 3 个包 ≈ 15 ms（模拟里 18 ms，含中继固定开销）。按用户实测
口径（8 KB = 6 包、4 KB = 3 包、5 ms/包），157 ms 的每步可到约 142 ms。

**但这 15 ms 买不到**：两个 4 KB 方案都会改 token。实际每步仍是 157 ms。

### 9.4 试过但不做

- **无损压缩**：真实 hidden 的 zlib 压缩率只有 0.93（8 KB → 7.3 KB），包数不变，
  单次压缩还要约 0.3 ms（8 KB）。没有收益。
- **35B / ROG 上的 dtype 验证**：2B 已是 1/5 分叉，结论方向明确，没有必要为此去碰
  ROG；若将来要试别的 dtype，`checks/verify_wire.py --record/--compare` 是现成的判据。
