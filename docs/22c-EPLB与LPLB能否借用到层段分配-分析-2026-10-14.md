## 0. 结论

1. **不引入"迭代式再平衡"** —— 本仓切点求解对 2–3 段**已是精确最优**（全枚举），引入近似贪心只会降级。

## 1. EPLB / LPLB 到底各是什么（外部核实）

| 项 | **EPLB** | **LPLB** |
|---|---|---|
| 仓库 | `deepseek-ai/EPLB`（MIT，2025-02-26 initial commit；开源周 Day 4「Optimized Parallelism Strategies」） | `deepseek-ai/LPLB`（MIT，**created 2025-11-19**，仅 1 commit） |
| 全称 | Expert Parallelism Load Balancer | 同上 + "based on linear programming" |
| 解决 | MoE 专家的跨 GPU **静态**放置/复制 | 同上，但针对 **per-batch 抖动** |
| 算法 | **纯启发式贪心**：`balanced_packing`（等量贪心装箱，`assert num_groups % num_packs == 0`、每包恰好 `n/m` 个）+ `replicate_experts`（反复复制"平均负载最大"者） | **真 LP**：把冗余专家建模为 GPU 之间的**边**（容量 = 该批 token 数），用自研 single-SM IPM 求解 |
| 输入 | `weight: [layers, num_logical_experts]`（**估计负载**，README 说用"历史统计滑动平均"，预测方法**不在本仓范围**）+ `num_replicas/groups/nodes/gpus` | `Planner(r2o, n_routed_experts, …, ep_size, group)`；每批 `run(indices, avail_counter, N_SMS)` |
| 输出 | `physical_to_logical_map` / `logical_to_physical_map` / `expert_count` | 重定向后的 physical expert indices |
| 静态/动态 | **一次求解的无状态函数**；"周期性重平衡"是**调用方的事** | **每批在线求解** + token 级重定向（维护 `avail_counter`，走 `torch.distributed`/NVSHMEM） |
| 官方定位 | "our **deployed** EP load balancing algorithm"、"battle-tested in production" | **"early research stage, performance improvements still under evaluation"** |
| **能否 import** | ✅ **能**：顶层只有 `from typing import Tuple` + `import torch`；**无** C++/扩展、**无** `torch.distributed`、**无** `.cuda()`；入口第一件事 `weight.float().cpu()` ⇒ **装 CPU 版 torch 即可** | ❌ **不能**：顶层 `from lplb._cpp import CompiledSolver`；构造时 `redundant_to_original.int().cuda()`；`pyproject.toml` 打包 `libcusolverdx.fatbin`，README 要求 **CUDA Toolkit ≥12.6.3（带 cuSolverDx）** + `./download-mathdx.sh` + `pip install --no-build-isolation .` |

**两者的关系**（LPLB README 原话）："**LPLB extends EPLB** … While EPLB handles **static** imbalances …, LPLB targets **per-batch fluctuations**." ⇒ **互补，不是升级版**；且 LPLB 自承"Under extreme global load imbalance, LPLB may perform **worse** than EPLB"。

## 2. 为什么"算法不可搬"（三条差异，第 2 条最致命）

### 2.1 "每层一组专家" vs "连续区间"

EPLB 的 `weight: [layers, num_experts]` 里，**layers 维只是一个 for 循环**（每层独立求解同一装箱问题，**层间不耦合**），自由度是**排列**；层流水线的自由度是"1..L 上的**切割位置**"，且**层不可重排**（有严格拓扑序）。

⇒ 硬套会直接撞两处：
1. **等量约束**（`num_groups % num_packs == 0`、每包恰好 `n/m` 个）与**异构设备**（4060 8GB + CPU-only 边缘 + 平板，最优解**必然不等量**）**直接冲突**；
2. **可重排假设**把"层"当成可互换对象 ⇒ 在层流水线里是**错模型**。

⚠️ 但要注意：**"顺序依赖"并不是让算法失效的原因** —— 它把问题从"装箱"变成"**切割**"，搜索空间**更小**、约束**更紧**。所以这里不是"算法不够强"，而是"**过强的机制配在了不匹配的模型上**"。

### 2.2 代价模型差异（**不可复用，不是调参能解决的**）

| | EPLB / LPLB | 本仓（`src/relay_cut_objective.py`） |
|---|---|---|
| 代价量 | token 数 / 专家负载（**纯可加**） | 段内计算（可加）+ **每段固定往返税**（**不可加**） |
| 目标 | `min max_i load_i` | `score = w_capacity·capacity_gain_x + w_latency·speedup_vs_single − w_risk·risk_penalty.total`（`:470-472`） |
| 通信项 | 结构化通信量（把同 group 专家放同节点以减少跨节点流量） | 每跳序列化 + RTT；decode 时**每 token 每跳**都付（`:167-173`） |
| **常数项** | **目标函数里没有常数项** | `STAGE_ROUND_TRIPS·rtt_ms`，`STAGE_ROUND_TRIPS = 2`（`:197-198`） |

⇒ **EPLB 天然偏好"负载摊得越平越好"（段越多越均衡）**；而本仓实测恰恰相反：每多一段固定多付 `2×RTT`，且当 `c_device ≥ c_master` 时**任何层数都不值得**（`:210-211` 原话"若该设备单层耗时不低于 master，则任何层数都不值得"）。
⇒ **把它的目标函数搬过来会得到与实测定量相反的答案。**

另外 LPLB 的"边容量"（= 该批 token 数）在层流水线里**没有对应物**：层段之间没有"可流动的 token"，只有"必须整体顺序执行的层块"。

### 2.3 静态 vs 动态

- **EPLB 一次求解** ⇒ 方向对（切点也应只在**冷事件**上重算），但**没有可搬的实现收益**。
- **LPLB 每批在线求解** ⇒ 层流水线里**完全不可用**：段的物理位置一变就要**重裁权重、重建连接、重传 GB 级 GGUF**。
- ⇒ 对 QLH 真正对口的是**已经有的**做法：用实测点**回归**出"每段固定开销 + 每层耗时"再求最优切点（`fit_segment_profile` `:513-561`，输出 `r2`）。

## 4. ✅ 顺带挖出的两个真缺口（都可安全修）

子 agent 只读调研本仓切点求解时发现（**与 EPLB 无关，是本仓自身的问题**）：

### 4.1 RTT **没有接进**切点求解器

- 切点求解器用的 RTT 只有两种：`SegmentProfile.rtt_ms`（调用方传入）与人工常量
  `MEASURED_TABLET_RTT_MS = 3.0` / `MEASURED_ANDROID_RTT_MS = 19.0`（`src/relay_cut_objective.py:187-198`）。
- 而集群**实际在线 RTT** 是**另一条独立链路**：客户端心跳 EWMA `src/tcp_comm.py:2726-2738`（`avg_rtt_ms`，
  `:2800-2801` 随心跳上报）、`src/network_path.py:211-248`（`HeartbeatQualityWindow` 的
  `rtt_ms_p50/p95/jitter`）、调度侧落库 `src/scheduler.py:1687-1690`。
- ⚠️ **负向声明**：全仓 `grep -rn "avg_rtt_ms"` 在 `relay_cut_objective.py` / `relay_cut_plan.py` /
  `torch_hetero_plan.py` **零命中**。
- ⇒ **即：在线 RTT 测得到、落得了库，但切点求解器读不到。**

### 4.2 `cut_multiple` 靠人工传参，两处默认都是 1（对 hybrid 就是错的）

- `cut_multiple` 是切点合法性的硬约束（`legal_cuts` `:298-309`），因 hybrid 的裁层 GGUF 层类型按
  "本地层号 mod interval" 推导 ⇒ 切错整体错位、llama.cpp 报 `missing tensor`（`:302-304`、`docs/已知问题记录.md:1327-1332` #67）。
- 但 **`relay_cut_plan.py` 与 `torch_hetero_plan.py` 的默认值都是 1**；本仓已有
  `cut_multiple_from_gguf`（`tests/test_cut_multiple_from_gguf.py`）却未被这两个入口默认使用。
- ⇒ **对 `qwen3-5-9b`（`full_attention_interval=4`）默认 1 就是错的**，必须人工记得传。

### 4.3 附带：改动风险清单（决定"能改哪个"）

| 模块 | 引用面 | 风险 |
|---|---|---|
| `src/relay_cut_objective.py` | `src/torch_hetero_plan.py:19`、`scripts/relay_cut_plan.py:34-39`、`tests/test_relay_cut_objective.py`(20 用例)、`tests/test_cut_multiple_from_gguf.py` | **低** —— ⚠️ **不在产品执行路径上**（无 scheduler/api/pipeline_capacity/task_worker 引用） |
| `src/pipeline_capacity.py` | `src/scheduler.py`、`src/model_supply.py`、`src/pipeline_reshard.py`、`src/api/routes_cluster.py` + **十余个测试文件** | **高** —— 生产求解器，改 `reason_code`/字段会波及大量测试 |
| `src/relay_capacity_budget.py` | 仅 `tests/test_relay_capacity_budget.py` | 低（src 内**零调用方**） |

⇒ 这与本票"**只借思想、不引依赖**"的定位一致：若要修 §4 的两个缺口，**只应动 `relay_cut_objective.py` 侧**，
**不要碰 `pipeline_capacity.py`**。

## 5. 可借 / 不能搬（最终清单）

### ✅ 可借（3 条，都是"思想"不是"代码"）

1. **"最重者优先、投给当前最轻者"的贪心**（EPLB `balanced_packing` 核心循环）。
   ⚠️ 但适用条件是**段数/层数大到穷举不现实时**：本仓 2–3 段（如 28 个合法切点 ⇒ 2 段 28 组、3 段 `C(28,2)=378` 组）
   **穷举就是精确最优**（`candidate_limit=512`），此时引入近似贪心**只会降级**。
2. **"两级/分层结构化"编码拓扑**（EPLB `rebalance_experts_hierarchical`：先 group→node、再 expert→GPU）。
   ⇒ 类比物是"若若干设备同处一个 LAN/同一 host，则优先把相邻段放进同一网络域"。
   ⚠️ **当前没有收益**：现状是 4060 主机 + CPU-only 边缘 + 平板，EPLB 那种**整除性/同构性前提不成立**。
3. **从 LPLB 借"把再平衡写成显式带容量约束的优化问题"的形式化习惯** + "重平衡要有明确触发条件、要计入求解开销"。
   ⇒ 落到本仓就是**保持现有"实测回归 → 切点重搜 → 与实测最优对比"的闭环**，
   并把"重算切点"限定为**冷事件**（换设备 / 换网络 / 换量化档），**不做在线循环**。

### ❌ 不能搬（5 条，各带理由）

| # | 不能搬 | 理由 |
|---|---|---|
| 1 | **等量装箱 / 整除性断言** | `num_groups % num_packs == 0`、每包恰好 `n/m` —— 与"异构设备按算力**不等量**分派"直接冲突 |
| 2 | **EPLB 的目标函数 `min max load`** | **没有常数项**，无法表达"每加一段固定付 `STAGE_ROUND_TRIPS·rtt`"；照搬会把最优解推向"段数越多越好"，与实测（去掉一段 **+49%**）方向**相反** |
| 3 | **冗余副本策略** | EPLB 复制重载专家是用**容量换均衡**；而本仓"切段"的**前提就是单机容量不够** ⇒ 复制层段副本会**增加**总容量需求，方向相反（本仓已定量否决"用互连换容量"） |
| 4 | **LPLB 的每批 LP + token 重定向** | 层的物理位置不能每批变（重切要重裁权重、重建连接、重传 GB 级 GGUF）；且本仓候选空间小到可精确枚举，没理由引入需 GPU + cuSolverDx 的求解器 |
| 5 | **上游代码本体** | LPLB 连 import 都过不了；EPLB 能 import 但签名/语义（`weight/layers/experts/ranks`）与"切割"**不同构**，强行包装只会得到"层可随意重排 + 每设备等量层数"的**错模型** |

## 6. 对子票 22c 完成定义的直接回答

> 22c 原文：「评估把 EPLB/LPLB 的放置/再平衡思想用于"层段分配"的可行性 … 本子票要回答的是「是否引入迭代式再平衡」。」

**回答：不引入迭代式再平衡。** 理由：
1. 本仓切点求解对 2–3 段**已精确最优**（全枚举 + 512 上限 fail-closed）⇒ 近似贪心只会降级；
2. EPLB 的代价模型**无法表达固定往返税**，照搬会给出与实测相反的答案；
3. LPLB 是**实验性 + CUDA 依赖**，且其"每批重定向"在层流水线里**结构上不可用**。

**但**把 §4 的两个真缺口列为**可独立开工的小项**（都在 `relay_cut_objective.py` 侧、风险低）：
- **4.1** 把在线 RTT（`avg_rtt_ms` / `HeartbeatQualityWindow`）**接进**切点求解的 `SegmentProfile.rtt_ms`；
- **4.2** 让 `cut_multiple` **默认从 `cut_multiple_from_gguf` 取**，而不是默认 1（对 hybrid 默认 1 是错的）。

⚠️ 并修正 §3 的错误断言（"EPLB/LPLB 纯 Python CPU 可跑" ⇒ 仅 EPLB 成立）。
