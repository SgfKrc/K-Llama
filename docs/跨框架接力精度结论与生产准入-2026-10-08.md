## 一句话结论

跨实现（PyTorch ↔ llama.cpp）之间的数值差异**不是工程 bug，而是 `float32` 加法非结合**的必然结果；
单层 GEMM 的下界为 `O(K·ε)`（`n_embd`=2048 时 `rel ≈ 3.5e-04`），**递推不会额外放大**（XFRAME-6）。
⇒ **"逐 token 与整模一致"不能作为跨框架接力的硬验收判据**；要严格一致必须让两侧**共享量化网格并整型累加**。

## 生产结论

### 1. 可证的精度边界

- **单层**：跨实现差异 `rel ≈ 3.5e-04`（f32、`n_embd`=2048）—— 这是**可证下界**，不是调参能消除的。
- **递推（多步 decode / 层段接力）**：差异**不放大**（XFRAME-6）⇒ 总差异 ≈ 每步 `O(K·ε)`，与步数无关。
- **是否分叉**：取决于 **`累计差异` 与 `argmax margin` 的比较**（XFRAME-3 已实测 margin 量级 0.32–9.6）。
  ⇒ 短序列（margin 充足）**全同**；长上下文逐步逼近 margin ⇒ 存在**必然分叉点**。

### 2. 推荐载体（按可用性排序）

1. **整型累加 + 两侧共享量化网格**（**推荐**，也是唯一"结构性消除"的路径）：
   整数加法满足结合律 ⇒ 归约顺序**不影响结果**；且 int8 相对 f32 把权重/激活压到 **约 1/4**
   ⇒ **容量反而下降**，与既有的"量化是容量旋钮"结论同向。已有端到端证据（XFRAME-3：8/8）。
   ⚠️ **跨框架实测补充（2026-10-08）**：权重同源只解决**权重差异**（≤ f16 舍入）。4-bit 通路另有
   **激活量化**（`llama.cpp` 的 matmul 会把 f32 激活量化成 `q8_0`/`q8_K` 再整数点积）—— 单层 `rel`
   达 `1.5e-3…6.3e-3`，跨实现时**逐层独立发生、不抵消** ⇒ 端到端仍有 `3e-3` 级。⇒ 生产落地需
   **两侧共用同一量化点积 kernel**，或改用**两侧同精度权重**（如都 f16 ⇒ `1.6e-4`）。见「未闭合项」三档对照。
2. **共享分块/线程策略**（两侧归约树完全一致）：理论差为 0，但需锁定两侧 SIMD 宽度与线程划分，
   对 llama.cpp/ggml 而言是**侵入式**改动 ⇒ 仅适合"成本可承担且要严格一致"的场景。
3. **float64 累加**：**仅作机理证明**。它不改变权重/激活/KV 的存储（累加器在寄存器/栈）⇒ 容量不变，
   代价是**吞吐**（SIMD 宽度减半、寄存器压力）且**必须两侧同改**（单侧改反而引入新的不一致）。

### 3. 必须退让的场景（不可消除）

- 两侧都用 f32 SIMD 且**不共享量化网格** ⇒ 差异 ≥ `O(K·ε)`，**无法保证逐 token 一致**；
- **长上下文 / 长生成**：累计差异逼近 margin ⇒ 存在必然分叉点（与"实现好坏"无关）；
- **低 margin 决策点**（近并列的 argmax）⇒ 一旦 `累计差异 > margin` 必分叉。

### 4. 优化叠加性矩阵（2026-10-08 实测）

各维度**能不能同时启用**、合起来能压到多少 —— 同一条真链路并列五组实测
（`scripts/xframe_grid_stack.py`；Qwen2.5-0.5B、K=12、3 prompt × 8 步，判据 = 与整模 argmax 一致数）：

| 组 | 上游（前 K 层） | 交界处 hidden | int8（`levels=127`） | int4（`levels=7`，敏感档） |
|---|---|---|---|---|
| `A` | llama.cpp 整模（基线） | — | — | — |
| `B` | llama.cpp keep-head（同引擎） | 原样 | **24/24** | **24/24** |
| `C` | PyTorch f32 GEMM | int8/int4 共享网格 | **24/24** | 9/24 |
| `E` | PyTorch **int8 网格 + int32 累加** | 同左 | **24/24** | **0/24** |
| `F` | PyTorch **int8 网格 + int32 累加** | 原样（不量化） | **24/24** | **0/24** |

⇒ 三条结论：

1. **有效档位（int8）下四条维度可同时启用**（`B == C == E == F == A`，24/24）；
2. ⚠️ **档位不足（int4）时，「上游也量化」反而比「只在交界处量化」更差**（`0/24` vs `9/24`）——
   上游 GEMM 的量化误差（rms ~1.2–1.8%）**超过 int4 半格** ⇒ 交界处的网格对齐**压不回同格**；
   而 `F`（交界处不量化）同样 `0/24` ⇒ 偏差**来自上游 GEMM 本身**，与交界处是否量化无关。
3. ⇒ **规则**：**不能为了消除"归约顺序"（`1e-7` 级）而把上游 GEMM 降到粗网格**（引入 `1e-2` 级误差）。
   "整型累加"只有在**两侧同网格且档位足够**时才是净收益。

**各维度的代价与叠加性**（合起来看）：

| 维度 | 机制 | 量级 | 代价 | 可叠加 |
|---|---|---|---|---|
| 层段切分 | `ModelManager` 按层加载 | **0**（逐比特） | 无 | 基线 |
| 算子实现 | 共享 C kernel | `1e-7`（本已一致） | 低 | 无需 |
| 归约顺序 | 锁定分块/线程 | ≥`O(K·ε)` | 侵入式 | 与"整型累加"互斥（后者是其解） |
| **权重同源** | GGUF 反量化喂 torch | 降 **40–80×** | 放弃原始 fp32 | ✅ |
| **通路同精度（f16）** | 避免激活量化 | 再降 **14×** | 放弃 4-bit 容量 | ✅ |
| **交界处 int8 网格** | 逐通道共享 scale | 压回同格 | hidden 传 1/3 体积 | ✅ |
| **两侧整型累加** | int32 累加 | 顺序敏感度 → **0** | 见上表（档位不足时反噬） | ⚠️ 有条件 |
| 累加数域 f64 | 累加器 f64 | 顺序差 → `0` | 吞吐↓、须两侧同改 | ✅（与网格正交） |

### 5. 能压到什么程度（端到端，Qwen2.5-0.5B、K=16、3 prompt × 160 步）

| 组合 | 端到端 `rel`（分段均值） | argmax 一致 |
|---|---|---|
| 现状：PyTorch fp32 上游 + 4-bit 下游 | `1.1e-2 … 3.3e-2` | 165/174、163/174、166/172 |
| ＋ 权重同源（Q4_K 反量化） | `3.2e-3 … 8.7e-3` | 173/174、168/174、171/172 |
| **＋ 两侧同精度（f16 通路）** | **`1.6e-4 … 4.4e-4`** | **173/174、174/174、172/172** ← **实测最优** |
| ＋ 交界处 int8 网格（顺带省 3–4× 传输） | 同量级 | 24/24（口径：3 prompt × 8 步） |
| 理论下界（f32 的 `O(K·ε)`，XFRAME-4） | **`3.5e-4`** | — |
| 要 **0** | 须两侧**共用一个实现**（同 kernel） | — |

⇒ **一句话**：跨框架 D→L 的**最优可叠加组合**是「**权重同源 ＋ 两侧同精度（f16）＋ 交界处共享网格**」
⇒ 端到端 `rel` **`1e-4` 级**、argmax 基本全同；**再往下跨框架做不到**（`rel → 0` 需要两侧同构）。

## 对产品路径的约束（验收判据）

1. **不得**把"与整模逐 token 完全一致"作为跨框架接力（D→L / L→L）的**硬验收判据**；
2. 应改为**行为等价 + 可证边界**：① 逐 token 一致**在其中 margin 充足的范围内**成立（实测 8/8、218/218）；
   ② 一旦分叉，必须能**归因到 margin**（而不是"实现不确定"）；
3. 若产品需要**严格一致**（例如可复现性要求）：必须走**载体 1**（量化网格 + 整型累加），
   并在**切点**处统一约定累加域与网格（层段传递的是 f32 hidden ⇒ 需在切点两侧显式量化/对齐）；
4. **层段接力的 hidden 传递**属于"每步一次"，其误差属 XFRAME-4 的 `O(K·ε)`，**不额外累积**（XFRAME-6）
   ⇒ 现有 D→L 接力设计**不需要**为"误差随层数/步数爆炸"担忧；需要关注的是**单步 margin**。
   该判据已在**真链路**上双重复验（均为 3 prompt、160 步生成、位置 170+）：
   ① **跨框架 D→L**（主仓 `ModelManager` PyTorch 上游 ↔ 主仓 `LlamaCppEngine` llama.cpp 下游、
   下游取真裁层件 `q35-2b-cut-k12.gguf`）：`tail/head` = **1.434 / 1.162 / 0.631**；
   ② **同框架 L→L**（上游也走 `KeepHeadUpstream` 的 `q35-2b-head12.gguf`，两侧同量化同引擎）：
   `tail/head` = **1.112 / 0.776 / 0.761** ⇒ **6 条全部 < 2.0**、分段均值均无单调趋势。
   ⇒ 递推不放大**与上游是谁无关**。且两种差异的**位置特征不同**：跨框架的 `rel` **从位置 0 就非零**
   （1.9e-3…4.4e-2，量化差一进入前 K 层输出即注入），同框架的 `rel` **位置 0 恰为 0**、靠累积到 5e-3 级
   ⇒ 首个 argmax 分歧也很靠前（19/5/27）vs 靠后（None/67/81）。
   工具：`scripts/xframe_dl_relay_positions.py`（`--upstream pytorch|llama`）。

## 未闭合项

- f64 档未在 `qwen3-5-2b` 上实操（本机内存不足：f64 需 ~16 GB，可用 ~6 GB）⇒ 用"同实例替换归约语义"
  等价构造对照；若将来有更大内存机器，可补一次 f64 整模对照；
- **层段接力的量化影响：首次给出真链路定量证据（2026-10-08）** —— 用 QLH 正式工具
  `scripts/xframe_divergence_report.py --layer-profile`，以**真裁层工件**（`q35-2b-head12/16.gguf`，`tensor_type` 含 **Q4_K**、`general.file_type=15`）对照 HF 上游
  `hidden_states[K]`：

  | 切点 | `rel_err` | `cos` | `max_abs` |
  |---|---|---|---|
  | K=12 | **0.1955** | 0.980865 | 0.2607 |
  | K=16 | **0.1963** | 0.980629 | 0.2895 |

  ⇒ **与切点几乎无关**（0.1955 vs 0.1963，不随层数放大）⇒ 是**每层都存在的稳定偏差**，符合量化误差特征。
  与其余层级对比（现已把"切分"这一环补进链中）：
  **量化 ≈ 2e-01  ≫  归约顺序 3.5e-04  ≫  算子 1e-07  ≫  层段切分 = 0（逐比特）**（相差 3–6 个数量级）
  ⇒ **量化是跨框架接力的第一差异源**，这从真链路侧支撑了本文件「推荐载体 = 整型累加 + **共享量化网格**」的结论。
  （`cos≈0.981` 也解释了为何量化下仍可能逐 token 一致：方向仍高度一致，argmax 由方向主导。）

  **同批对照（决定性）**：`--same-engine`（**整模** `models/qwen3-5-2b-gguf/qwen35-2b-Q4_K_M.gguf` vs **分层链** `q35-2b-head12.gguf + q35-2b-cut-k12.gguf`，两侧**同量化**）
  ⇒ **4/4 逐 token 完全一致**（`token 级分歧 0`、`首分歧步 = []`）
  ⇒ **分层接力机制本身不引入差异**；`--layer-profile` 里那 `0.196` 的差**全部归因于量化**。
  两条合起来即「**共享量化网格 ⇒ 一致**」的直接证据 —— 但注意本链路的"共享"是 **llama.cpp 两侧同量化**；
  生产形态是 **PyTorch 上游 ↔ llama.cpp 下游**，故此处属**机制验证**，不等于生产链路验证。

  **主仓引擎复验（2026-10-08，新增工具 `scripts/xframe_layer_range_equivalence.py`，配 3 例单测）**：
  上面 `--layer-profile` 对照的是「HF 整模 vs **keep-head 上游**（llama.cpp）」，覆盖的是**跨框架**接口；
  而生产 D 档上游走的是**主仓自己的层段路径** ——
  `ModelManager.load_layer_range(0, K, has_embedding=True, has_lm_head=False)` + `forward_layers(...)`。
  两者跑同一 prompt 的对照：

  | 切点 | `rel_err` | `cos` | `max_abs` | `identical` |
  |---|---|---|---|---|
  | K=12 | **0.000e+00** | 1.000000000 | 0.000e+00 | **True** |
  | K=16 | **0.000e+00** | 1.000000000 | 0.000e+00 | **True** |
  | K=20 / K=22 / K=23 | **0.000e+00** | 1.000000000 | 0.000e+00 | **True** |

  ⇒ **层段切分本身逐比特中性**（同一份权重、同一套算子语义 ⇒ 完全一致）⇒
  D→L 的差异**不可能**来自"把层拆开"这一步，只能来自**下游内核/量化**。
  这也把上面的证据链补完整：**切分 0 → 算子 1e-07 → 归约顺序 3.5e-04 → 量化 ≈ 2e-01**。

  **边界澄清（否定性发现，2026-10-08）**：K=24（= `num_hidden_layers`）在首轮扫描里给出
  `rel_err=0.7594 / rms 3.3695 vs 0.8843` 的"偏离"，逐项排除后**不是缺陷**，而是**对照口径无效**：
  `hidden_states[k]` 记的是**第 k 层的输入**，`hidden_states[-1]` 由 transformers v5 的通用记录器
  （`_can_record_outputs`）取到 `Qwen3_5TextModel.forward` **层循环之后的 final norm** 结果
  ⇒ 它**不是最后一层的输出**。判定证据（用 forward hook 抓 HF 内部真值）：

  | 比较 | 结果 |
  |---|---|
  | `hidden_states[23]` vs HF `layer23` 的**输入** | `rel=0.000e+00` |
  | 层段 `forward_layers(0,24)` vs HF `layer23` 的**输出** | **`rel=0.000e+00`（`identical=True`）** |
  | 层段 `forward_layers(0,24)` vs `hidden_states[24]` | `rel=7.594e-01` |

  ⇒ **层段路径与 HF 的逐层执行逐比特一致**；故本工具把 K 的有效上界固化为 `len(hidden_states)-2`，
  并对越界的 K 打印原因后跳过，避免这一口径再次被误读为精度缺陷。

  **量化分量与实现分量的分离（2026-10-08）**：Qwen3.5-2B 本机无法造 f16 整模
  （仓内 `convert_hf_to_gguf.py` 不支持 `qwen3_5`，且无 f16 整模工件 ⇒ 需联网下载 4.5 GB），
  故改用**同一模型、同一工具、只改上游工件量化类型**的对照 —— Qwen2.5-0.5B（HF 目录、
  f16 裁层件、Q4_K 整模均在手；Q4_K 裁层件由 `scripts/cut_layers.py` 现造）：

  | 模型 / 切点 | 上游工件（`file_type` 已核验） | `rel_err` | `cos` | `max_abs` |
  |---|---|---|---|---|
  | Qwen2.5-0.5B / K=8 | **f16**（`file_type=1`） | **3.315e-04** | 1.000000 | 0.5204 |
  | Qwen2.5-0.5B / K=8 | Q4_K_M（`file_type=15`） | 7.563e-03 | 0.999987 | 8.662 |
  | Qwen2.5-0.5B / K=16 | **f16**（`file_type=1`） | **3.327e-04** | 1.000000 | 0.5215 |
  | Qwen2.5-0.5B / K=16 | Q4_K_M（`file_type=15`） | 9.263e-03 | 0.999974 | 9.104 |

  ⇒ 分离结果：**跨框架实现差异 ≈ 3.3e-04**（与切点无关，与 XFRAME-4 的归约顺序下界 3.5e-04 同量级），
  **量化差异 ≈ 7.6e-03…9.3e-03**，即 **量化约为实现差异的 23–28×** ⇒ 把"量化是第一差异源"从推断变为**分离测量**。

  **权重同源 × 通路：2×2 隔离（2026-10-08，Qwen2.5-0.5B、K=16、同一批工件）**

  把"PyTorch 侧权重是否与下游同源"与"通路是否为 4-bit"两个因素正交开：

  | 通路 | 权重**不同源** | 权重**同源** | 趋同收益 |
  |---|---|---|---|
  | **4-bit**（llama.cpp 会量化激活） | `9.263e-3` | **`4.713e-3`** | **1.97×** |
  | **f16**（不量化激活） | `3.327e-4` | **`3.325e-4`** | **1.00×（≈零）** |

  另有 hybrid（Qwen3.5-2B、K=12/16、同一 head 工件）：PyTorch 用原始 fp32 `0.1955 / 0.1963`
  → 用 Q4_K 反量化 **`0.05059 / 0.05132`**（**3.8×**）。

  ⇒ 三条结论：

  1. **权重这一层能做到的不是"趋同"，而是"相同"** —— `scripts/gguf_dequant_to_hf.py` 让两侧持同一份
     GGUF 的反量化值（权重级已验证：F32 张量 `0.000e+00`，其余差异 = f16 舍入 `1.6e-4…2.2e-4`）
     ⇒ "权重误差分布趋同"这个目标**已超额达成**。
  2. **但「权重相同」≠「误差相同」**：4-bit 通路里 llama.cpp 的 `mul_mat` 会先把 **f32 激活**
     量化成 `q8_0`/`q8_K` 再整数点积（`vec_dot_type`/`from_float`）。这一层误差
     **与权重用什么量化算法无关、却与输入相关** ⇒ 权重同源后仍剩 `4.7e-3`（0.5B）/ `5.1e-2`（2B），
     换任何"模仿 Q4_K_M 的算法"都动不了它。
  3. **故若目标是"两侧接近"，模仿 Q4_K_M 是错误方向**：f16 通路的 `3.3e-4` 比 4-bit 通路
     **同源后**的 `4.7e-3` 还好 **14×**；而 f16 通路上"权重同源"收益恰为 **1.00×** ——
     那里的误差**完全由计算路径（GEMM 实现 + 归约顺序）决定**，与权重精度/同源性无关。
     ⇒ 该做的是让两侧都**不走量化通路**，或两侧**量化到同一网格 + 整型累加**（XFRAME-3/5），
     而不是让 PyTorch 也去做 Q4_K_M。

  ⚠️ **量级与架构相关**：Qwen3.5-2B 在 Q4_K 下的 `rel_err`（`0.1955`/`0.1963`）比 Qwen2.5-0.5B 的
  `9.3e-03` 大 **21×**；权重同源后降到 `0.0506`/`0.0513`（见上节 2×2）。⇒ **hybrid 模型在 4-bit 下的
  层输出偏差显著更大**：跨框架接力对它**必须**共享量化网格，否则下游拿到的是被 `2e-01` 级偏差污染的 hidden。

  **跨框架共享量化网格：层段级端到端验证（2026-10-08）**：
  生产形态是 **PyTorch 上游 ↔ llama.cpp 下游**。首次让**切点两侧持同一份权重**来验证"共享网格 ⇒ 差异降回实现层"。
  构造：新增 `scripts/gguf_dequant_to_hf.py`（+8 例单测）把 GGUF **逐张量按各自 `tensor_type` 反量化**成
  HF safetensors 目录（`tie_word_embeddings` 的 `output.weight` 记录后跳过；每张量的 qtype 与形状均入清单），
  再以该目录作 `xframe_dl_relay_positions.py` 的 PyTorch 上游；下游与参照都是同一族 GGUF。
  三档对照（Qwen2.5-0.5B、K=16、3 prompt、160 步、位置 170+；判据同 `summarise`）：

  | 配置 | PyTorch 上游的权重 | 与下游权重的关系 | 分段均值 `rel` | argmax 一致 |
  |---|---|---|---|---|
  | **A 现状** | 原始 fp32（HF 目录） | **网格不同**（fp32 vs 4-bit） | 1.1e-2 … 3.3e-2 | 165/174、163/174、166/172 |
  | **B** | Q4_K GGUF 经 python 反量化 | **权重同源**（≤ f16 舍入），但**仍走 4-bit 通路** | 3.2e-3 … 8.7e-3 | 173/174、168/174、171/172 |
  | **D** | f16 GGUF 反量化（**无损**） | **逐位同源**、**无激活量化** | **1.6e-4 … 4.4e-4** | **173/174、174/174、172/172** |

  ⇒ 三条结论：

  1. **权重同源有效**：A→D 降 **约 40–80×**，把跨框架差异压到 `1.6e-4…4.4e-4` ——
     与 XFRAME-4 的可证下界（`3.5e-04`）**同量级**；argmax 一致率从 165/163/166 提到 **173/174/172**。
  2. **4-bit 通路另有主导差异源：激活量化**。四条证据：
     - **权重级**：`llama-quantize --allow-requantize … F16`（走 C 的 `dequantize_row_q4_K/q5_0/q6_K`）
       与 python `gguf.quants.dequantize` 逐张量比较 ⇒ `rel = 1.6e-4…2.2e-4`（**正是 f16 舍入量级**），
       且 **F32 张量 `0.000e+00`** ⇒ 两套反量化**语义等价**；
     - **源码级**：`ggml-cpu.c:1266-1344`（`ggml_compute_forward_mul_mat`）—— 量化权重的
       `vec_dot_type` 是 `Q8_0`/`Q8_K`，于是 `from_float = quantize_row_q8_0/q8_K` 会把 **F32 激活**
       写进 `wdata` 再做整数点积；F16 权重的 `vec_dot_type` 是 `F16`（只做 f32→f16 转换，**不量化**）；
     - **单层级（定量）**：在同一份真实激活上，`q8_0(x) @ Wᵀ` vs `x @ Wᵀ` 的 `rel` 为
       **1.55e-3 / 5.27e-3 / 6.32e-3 / 3.66e-3**（`q_proj` / `o_proj` / `down_proj` / `gate_proj`），
       是归约下界（`3.5e-04`）的 **4–18×**；同权重精确计算的对照恒为 `0.000e+00`；
       **hybrid（Qwen3.5-2B）同法测得 `2.79e-3…9.02e-3`**（含 `linear_attn.in_proj_qkv`、
       全注意力的 `q_proj`、以及 MLP 三矩阵）⇒ 同量级；
     - **行为级（负面结果，排除"上游补上量化即可修复"）**：给 PyTorch 上游也加同样的 q8_0 激活量化，
       残差**未减小**（`3.465e-3 → 3.939e-3`）—— 两侧的量化输入本就略有不同，
       独立量化产生的误差**不相关、不抵消**。
  3. **故 4-bit 与 f16 的 10–20× 差距不能靠"共享网格"消除**：共享网格解决的是**权重差异**
     （≤ f16 舍入，权重级已证）；而 4-bit 通路里**每层 matmul 都会量化激活**，其单层误差
     `1.5e-3…6.3e-3` 在跨实现时逐层独立发生 ⇒ 端到端 `3e-3` 级。

  ⇒ **生产含义**：跨框架接力若要压到实现层下界，必须让两侧**共用同一套量化点积 kernel**，
  而不只是"权重同源" —— 因为激活量化是 **matmul 内部行为**，PyTorch 侧无法靠"喂同源权重"复现。
  可行形态：① 两侧同精度权重（如都 f16，即配置 D，代价是放弃 4-bit 容量收益）；
  ② 两侧共用自研量化 kernel。⇒ 这也解释了 XFRAME-3 的 `int8` 8/8 为何成立：那是**同一引擎内**，
  两侧的激活量化是同一份实现、同一份输入。

  **产物**：`build/keephead/qwen25-05b-{q4km,f16}-dequant/`、`build/keephead/qwen25-05b-q4km-cut-16.gguf`、
  `build/keephead/qwen25-05b-from-q4km-f16.gguf`、`build/keephead/xframe-sharedgrid-{orig,dequant,f16}.json`。

  **hybrid（Qwen3.5）复验（2026-10-08）**：`gguf_dequant_to_hf.py` 已支持 `qwen35`
  （架构感知映射表 + `conv1d` 补维 + 两处 HF 逆变换）。Qwen3.5-2B 的 Q4_K_M **335 个张量全部映射**；
  与 HF 原始目录比对：键集合只差 **297 个 `model.visual.*`**（GGUF 是 text-only）、**shape 不一致 0**。

  ⇒ **过程中发现并修复了两个 Qwen3.5 特有的表示差**（不修会得到 `2e-1…5e-1` 的错误残差，
  实测 argmax 仅 26/142）：
  1. **RMSNorm 的 `1.0 + weight`**：`Qwen3_5RMSNorm` 的 `weight` 是零初始化的**偏移量**（前向 `1 + weight`，
     见 PR #29402），而 GGUF 存的是**合并后的值** ⇒ 转 HF 须**减 1**。实测 68 个 norm 的
     `delta = dequant - orig` **恰为 `1.00000`、标准差 0**。
     ⚠️ 例外：`linear_attn.norm.weight`（`Qwen3_5RMSNormGated`）是标准 `weight`（delta = 0）⇒ **不减**。
  2. **SSM 的 `A_log`**：GGUF `ssm_a` 存的是 **`-exp(A_log)`**（逐元素吻合）⇒ 须 **`log(-x)`**。
  修复后同名张量比对：norm 类 median **`0.000e+00`**（F32 无损）、全体 `max 8.95e-2`（纯 Q4_K 量化误差）。

  两项测量（修复后）：

  | 项 | Qwen2.5-0.5B（标准 attention） | Qwen3.5-2B（hybrid） |
  |---|---|---|
  | 激活量化**单层** `rel` | 1.55e-3 … 6.32e-3 | **2.79e-3 … 9.02e-3** |
  | **端到端**（权重同源 + 4-bit 通路） | 3.2e-3 … 8.7e-3；argmax 173/168/171（K=16） | **3.3e-3 … 1.1e-2；argmax 142/142、139/142、139/140**（K=12） |

  ⇒ **hybrid 与标准 attention 同量级**（`1e-2` 级），且与"激活量化单层量级"自洽 ⇒
  4-bit 通路的跨框架残差**不因架构而变**，仍由激活量化主导 ⇒ 上一轮"待验证"的疑虑消除。

  **仍缺**：跨框架 4-bit 共享网格的**自研共用 kernel** 形态尚未实现 —— 已定出"为何需要它"与所需量级。
- 长上下文分叉点：**已扫到 ~1050 位置**（2026-10-08，`--min-new-tokens 1024` 强制长度，三个 prompt）。
  结果：`argmax` **全同**（1050/1050、1050/1050、1048/1048），`rel_first ≈ 9.8e-08` 且
  `rel_last ≤ 2.4e-07`，回归斜率 ≈ ±3e-11 ⇒ **无额外累积、无分叉**。
