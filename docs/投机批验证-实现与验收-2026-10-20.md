> 状态：**部分实施**（full-attention显式路径实现与本机开发门通过；设备与收益门开放）

> 适用范围：票21b `COMM-BATCH-01` 的greedy单请求draft、批量验证、接受／纠错、跨段状态恢复及计量。多位置wire合同由[21b-0](末段多位置argmax-实现与验收-2026-10-20.md)维护；hybrid recurrent回滚、随机采样和多请求并发另立能力门。

## 1. 启用与准入

`src/qlh_core/contracts/speculation.py:resolve_speculative_gamma`解析显式请求参数`speculative_gamma`和应用冻结环境`QLH_SPECULATIVE_GAMMA`，请求优先，缺省为1。请求值为严格整数，环境为整数字符串，范围1至8；1沿用`LinearExecutor`，2至8选择`SpeculativeExecutor`。gamma表示一次验证的最大输入行数，其中一行是上一枚已提交token，最多另带gamma−1枚draft；剩余输出预算会缩短批次。

`src/api_server.py:ChatRequest.pipeline_speculation`提供HTTP入口，普通请求、interactive／fast／full SSE及`INFER_FORWARD`双边透传显式值。省略／null留给执行owner解析环境；显式投机遇本地、外部整模或缺可用线性路径以`speculative_route_unsupported`拒绝。请求例：

```json
{
  "message": "请继续这段文本……",
  "routing_preference": "distributed_required",
  "temperature": 0,
  "speculative_gamma": 4
}
```

`NativePorts.prepare_speculation`在请求执行锁内检查当前owner和已发布计划，首个能力面限定Qwen2 GGUF、CPU、每段单序列、同上下文及可用KV。准入优先检查实际`loaded_artifact`裁层工件，源描述器的`model_path`可继续指向整模。模型header中的架构、层数、hidden维度及SSM／recurrent／sliding-window／MTP字段逐项核验；末段须声明`multi_position_argmax`，各远段沿用`stage_kv_cleanup`准入。恢复的完整前缀须容纳在每段冻结`batch_size`内，预算不足以`speculative_replay_batch_limit`拒绝。该能力范围与框架支持的完整模型列表分别维护。

## 2. draft与目标验证

`src/qlh_core/execution/speculative.py:draft_ngram`只读取prompt和已提交输出，在长度上限四的后缀中选择最长匹配，再取最新历史匹配的已知后继。未命中即缩短或结束draft；生成候选不会新增模型owner或物化整模。

prefill取末位目标argmax并按`StopPolicy`提交首token。随后验证输入为`[上一已提交token] + draft`，位置从`prompt长度 + 已提交token数 − 1`连续递增。`NativePorts.forward_tokens`执行首段并依次转发全部远段；末段请求21b-0的全部行结果，再绑定本次行数与绝对positions。标量回退无法满足本路径的多行合同，结果缺组以具名错误结束请求。

`greedy_accept`比较draft与目标每行argmax的最长相同前缀。全部接受时提交draft和末位bonus；出现首个不同位置时采用目标对应行作为纠错token。EOS、文本停止和max-new-tokens仍由同一`StopPolicy`逐token处理，只发送通过验证的流式增量。

## 3. 拒绝恢复与请求归属

拒绝恢复采用严格清空及已提交前缀重放。`NativePorts.restore_prefix`先等待已有attempt物理排空，向每个已使用远段发送`cleanup_only`并核对`kv_cleared=true`，再调用首段实际owner的`clear_pipeline_kv`。reset offer也追踪原请求的`execution_attempts`，取消后的最终清理先等待reset物理排空。全过程持有原执行锁并消费原deadline。随后仅重放`prompt + 之前已提交输出 + 本批已接受draft`，末位greedy须等于待提交纠错token；不一致以`speculation_replay_mismatch`结束。

验证、恢复重放使用单调递增operation step，独立于已提交token索引及绝对位置。每次forward的`StageIdentity`仍绑定冻结deployment、assignment、incarnation、connection、request与attempt；恢复stage采用独立请求／stage后缀。中间段逐次校验receipt与输出摘要，部署变更或取消后丢弃结果。

`RequestService`继续拥有FIFO、唯一终态和排空／隔离。请求最终由`NativePorts.cleanup`确认各段KV释放并解锁；单个远段失败时仍按原deadline尝试其余远段和本地清理，再汇总失败；物理清理未确认的部署沿用cleanup-pending隔离。重放是一项可测的恢复成本，完整生成收益按实际提交token及整个请求时间判断。
