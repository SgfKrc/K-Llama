## 0. 为什么现在做这份审计

《本机跨框架层段落地与验收状态》的 §3 记录了 21 处同型修复，且已写出规律：

> `_worker_runtime_active` / `worker_prepare_identity` / `node_incarnation` / 帧预算 /
> prepare-ack 这一族都是**"远端 worker 才有的属性"**；凡按 `node_id` 单独应用的地方，
> 本机执行器必炸。

但那份记录是**按症状追出来的**（炸了才查），不是**按模式扫出来的**。本文件补的是后者：
把 `node_id` 当唯一身份、以及把"当前已就绪"当"唯一允许"这两类模式系统地扫一遍。

## 1. 方法论

- 只读源码，不写文件、不跑落盘测试（源码当时正被另一个 agent 修改）。
- 先按"变量/键的语义"筛候选，再逐个读上下文确认；对可疑但不确定的，
  用纯计算脚本复现判定逻辑（见 §5 的 A1 实证）。
- **明确区分**三类：
  - **缺陷**：同机两执行器会得到错误结果；
  - **有意保留**：注释已说明设计意图，放宽反而错（§4）；
  - **已正确**：确认过不用改（§3）。

## 2. (a) 类：仍以 `node_id` 作唯一身份 —— 12 处

### 阻断（3 处）

#### A1. `scheduler.py:2952-2961` — 布局引擎映射按 node_id 覆盖

```python
engines = {item["node_id"]: item["engine"] for item in capacity_nodes if item.get("engine")}
result["assignments"] = [
    {**item, "engine": engines[item["node_id"]]}
    if item.get("node_id") in engines and not item.get("engine") else dict(item)
    for item in (result.get("assignments") or [])
]
```

`_local_cpu_executor_record` **追加**在主记录之后 ⇒ `engines["master"]` 最终是
`"llama_cpp"`。求解器的 assignment 不带 `engine`（`capacity.py:1680-1735` 无此键）
⇒ 两个 assignment 都满足回填条件 ⇒ **主段被盖上 CPU 段的引擎**。

**实证**（§5）：主段 `[0,8)` 得到 `engine='llama_cpp'`，应为 `'pytorch'`；改二元组后全对。

**实际影响范围**（已用日志排除最坏情况）：执行路径的 freeze 用的是**求解结果的原始
assignments**（无 `engine` 键 ⇒ 回退 `transaction.manager`，实测 13:44:31
`frozen=['cpu']` 成功），所以 A1 没有毒死执行。它污染的是 `_attach_pipeline_node_contract`
的**返回值**：

- `pipeline_node_contract.py:498-509` 用 `assignment.get("engine")` 决定
  `artifact_kind` / `cross_engine` ⇒ **主段被标成 gguf 段，同机两段不再被识别为
  跨引擎接力**（layout 语义错误）；
- `model_supply.py:1941-1942` 用 `plan["assignments"][0]["engine"]` 推 `quant_type`
  ⇒ 主段是 `llama_cpp` 时推出 `quant_type="gguf"`（供给决策被误导）。

**这是 `model_host.py:812-816` 那个已修 bug 的镜像**：那边注释写"此前用
`transaction.manager` 判 `native` ⇒ CPU 段被当成 safetensors 段"；A1 让同一个键
**反向**犯病。**建议**：键改 `(node_id, executor_id)`。

#### A2. `model_supply.py:1389-1393` — offload 物化按 node_id 施加

```python
offload_records = [
    {**record, "materialization": "safetensors_layer_offload"}
    if record["node_id"] == "master" else record
    for record in records
]
```

同机 CPU 段也被标成 `safetensors_layer_offload` ⇒ 进
`model_supply_runtime_capacity.py:511-516` 的 `if engine != "pytorch": fail(...)`
⇒ `SUPPLY_RUNTIME_LOAD_SPEC_INVALID`，从 1394 行无 try 直接冒泡 ⇒ **整次供给失败**。

`CAPACITY_PLANNING_MODE` 缺省是 `balanced`（`config.py:431-435`），此时 offload 开启
⇒ **默认配置就会踩**。当前 `.env` 显式设了 `fastest`，所以暂时看不到 —— 这是一颗
定时炸弹：任何人调回 `balanced` 立即炸。**建议**：条件改
`record["node_id"] == "master" and not record.get("executor_id")`。

#### A7. `scheduler.py:3454-3473` — 手动分层计划按 node_id 取容量记录

`records = {item["node_id"]: item for item in capacity_records}` ⇒ 后者覆盖前者 ⇒
手写"master 拿 `[0,8)`"会拿 CPU 段的额度/引擎/`layer_budget=[8,24)` 去校验 ⇒
大概率被拒；且 `assignments` 不读 `executor_id` ⇒ 无法把某段指定给 CPU 执行器。
仅 manual override 且非分布式请求时使用，故优先级略低于 A1/A2。

## 3. (b) 类：把"当前已就绪"当"唯一允许" —— 2 处（均降级）

### B1. `scheduler.py:3325-3347` + `model_supply_plan_reuse.py:228-240`

上一轮切点只在**解不出来**时才释放：

```python
if (not result.get("admitted")
        and any("candidate_layer_ranges" in node for node in capacity_nodes or [])):
    result = solve_pipeline_capacity(descriptor, released_nodes, ...)
```

只要"不含本机 CPU 段的方案仍然可行"，就不触发释放 ⇒ 陈旧切点作为硬约束永久保留，
附加执行器在后续轮次被**结构性挤出**拓扑。这正是
`model_supply.py:1236-1245` 记的 "android[[8,20]]+TABLET[[20,32]] 占满 [8,32)，
CPU 段从未被选"在另一层的表现。**"可行但已不该沿用"的布局永远不会重切。**

**建议**：除"无解"外再加触发条件 —— 本次解里缺少期望的附加执行器
（`local_executors` 为空）时也跑一次 released 求解，按目标函数取优。

### B2. `pipeline_reshard.py:363-380`

恢复计划只拿**当前 layout 的 nodes**（已发布/已装载）去证明候选布局的 requirements。
能自裁的 worker（`layer_budget.local_cut`）本可接受新切段，但当前工件区间不覆盖 ⇒
一律 `pipeline_reshard_assets_required` ⇒ "已就绪"实际限制了可规划的切点范围。
与 A3 叠加时还会出现**反向伪就绪**。

**建议**：把"可由 prepare 满足（自裁能力）"表达为 `assets_pending` 而非 `missing`。

## 9. 修复结果（2026-10-27）

### 9.1 逐项落地

**A1（阻断）** `scheduler.py:_attach_pipeline_node_contract` —— `engines` 键改
`(node_id, executor_id)`。实证：修复前主段 `[0,8)` 得到 `engine='llama_cpp'`（应为
`pytorch`），修复后四段全对。这是 `model_host.py` 那句注释（"此前用
`transaction.manager` 判 `native` ⇒ CPU 段被当成 safetensors 段"）的**镜像** —— 同一个键，
反方向的错法。

**A2（阻断）** `model_supply.py` 的 `offload_records` 条件补 `and not executor_id`。
触发条件是 `host_ram_offload_enabled()`，即 `QLH_CAPACITY_PLANNING_MODE=balanced`
（**缺省值**）—— 本机一直没事只因 `.env` 钉了 `fastest`，是一颗定时炸弹。
`local_cut`/GGUF 段的语义也印证：CPU 段权重本来就在主机内存、就地计算，没有"offload"。

**A3/A4 + 已确认的 `:446`（阻断/降级）** `pipeline_reshard.py`：
- `:446` 改 `len(survivors) < 2`（数**记录数**），与 `reason` 文案（"capacity
  **records**"）和求解器 `len(usable) < 2` 同口径。实证：只剩 master 两执行器时
  旧版误判 `survivors_unavailable`，新版 `accepted=True` 并给出
  `[('master','',(0,18)), ('master','cpu',(18,32))]` —— 正是"只剩本机两执行器"的目标形态。
- `:426`/`:468` 新增 `_failure_targets()` / `_failed_identity_keys()`：**节点级**（裸
  `node_id` = 整机失联）与**执行器级**（`(node_id, executor_id)`）分开表达，
  `(node_id, "")` 与裸 `node_id` **刻意不等价**。`PipelineReshardPlan` 末尾加
  `failed_executor_ids` 并参与 `plan_id`。
- `covers()` 比 `(node_id, executor_id)`：实证 availability `master#"" / (0,32)` 去覆盖
  requirement `master#cpu / (8,24)`，旧判据 `True`（伪就绪），新 `False`。
- **必要联动**（不补会挂）：`_commit_ready_pipeline_reshard` 的 `record_artifact` 必须抄
  `executor_id`；`_stage_pipeline_reshard_after_disconnect` 跨轮累积失败要补读
  `failed_executor_ids`。

**A5/A6** `capacity.py`：
- `exclude()` 键改 `(node_id, executor_id, start, end, reason_code)`，`executor_id` 放在
  `**(budget or {})` **之后**（身份不被预算字段覆盖）。实证：同区间同 reason 时旧版只剩
  4 条、新版 8 条且主段/CPU 段各一条。
- `used_ids` 改二元组；新增 `_node_executor_label()`：**主执行器裸 `node_id`、附加执行器
  `node#executor`**（兼容规则，既有拓扑输出逐字节不变）。`control_only_nodes` /
  `single_node_full_model_candidates` / `bottleneck_node_id` / `uncalibrated_segments`
  四处统一用它。
- **逐字节回归证据**：用 `git show HEAD:` 加载改前模块，对 9 组无 `executor_id` 的既有拓扑
  整份 plan dict 比对 ⇒ 除 `candidate_exclusions` 新增的空 `executor_id` 外**完全相同（含
  `plan_id`）**，且入参未被修改。纯函数门 63 passed。

**A7（阻断，手动分层路径）** `scheduler.py:_build_manual_pipeline_capacity_plan` ——
`records` 键改二元组、循环读 `executor_id`、`record = records.get((node_id, executor_id))`，
附加执行器**不**回退到主段记录（那正是要消灭的串味）；未写 `executor_id` 的旧方案仍指主段。
另把 `executor_id` 加进 `plan_identity`（**只在非空时**，保既有 `plan_id` 逐字节不变）——
否则"master 主段 + master#cpu"与"换成别的执行器"会得到同一个 `plan_id`。

**A8/A9 + B1** 复用偏好与切点释放：
- A8：`_candidates` 只跳过**主执行器**（不是整个 `master`）；`active` / `_preserves` 的唯一性
  与 `engine_by_node` 全部改二元组；`capabilities_by_node` 仍按裸 `node_id`，但附加执行器
  **不再回退**到主段快照（避免用主段的 engines/artifacts 给 CPU 段作证）。
- **前置补齐**（否则键修了在真机上等于没修）：`_local_cpu_layer_artifacts` 补
  `source_model_id` / `tokenizer_sha256` / `hidden_size`（三项齐全才声明），CPU 容量记录补
  `models`。`_candidates` 的准入门是"物理身份可证"，缺一项候选就恒空。
- A9：新增 `_preferred_ranges_for()`（身份键优先，裸 `node_id` 只兼容主执行器）；校验里
  只有**主执行器**不能有偏好；`project` 尾部按身份写回 `layer_ranges`。
- **B1**：新增 `src/executor_coexistence.py`（scheduler 与供给侧**共用**，避免两处口径
  漂移）。触发条件从"解不出来"扩展为"**可行但缺少期望的附加执行器**且有候选锁"。
  取优优先级链（`plan_rank`，越小越好）：`admitted` → **期望附加执行器实际参与数** →
  参与执行器总数 → 求解器目标函数 → 打平**保留 baseline**。
  第 2 项排在第 4 项之前是这张票的直接目标："配置了 CPU 段却被挤出，方案再可行也不该
  沿用"；若把目标函数提前，"更快的两段方案"就会永久挤掉 CPU 段 —— 正是 B1 要解决的形态。
  打平保留 baseline 保证机制稳定性：换布局后下一轮候选锁来自新布局，release 求解得到
  同一个解 ⇒ 自然收敛、不来回震荡。
  链上**没有可调数值**（布尔/整数/确定性目标值，逐位相同无需容差），故未新增 `QLH_*`。
- 另修了 offload 路径的两个真实断点：lambda 此前不接收 `release_candidates` ⇒ `TypeError`
  被吞 ⇒ **offload 物化的释放机制从未生效**；其 `engine_by_node` 也仍是裸 `node_id`。

**A10** `model_intent.py` —— 视图键可能是 `master#cpu`，而 `acks`/`expected` 都是裸
`node_id`。改为先 `partition("#")` 取 base 再查 ack；带执行器后缀的键**不**套远端那套
`prepared` 判据（本机执行器没有 prepare/commit 回执链），按 `result["status"]` 推导。

**A11** `model_supply.py` —— 隐式按 `node_id` 去重改**显式断言**
`SUPPLY_MULTIPLE_LOCAL_EXECUTORS`（带节点名与两个 executor 名）。产品口径已确认"每机一个
附加执行器"是当前设计；隐式丢弃在诊断上很坏（将来加 cpu2/npu 会静默不参与规划）。

**A12** `model_supply_diagnostics.py` —— `originals`/`by_id` 键改二元组，行上带
`executor_id`，避免同机两段的 `required_bytes`/`layer_range` 互相串位。

### 9.3 B2 为什么决定不改

报告原本建议把"能由 prepare 满足（自裁能力）"表达为 `assets_pending` 而非 `missing`。
**验证后否定**，理由按强度排序：

1. **`assets_ready` 没有决策消费者**。全仓只有 `to_dict()` 投影和 `commit()` 的重算，而
   commit 发生在**加载完成之后**（worker ACK `commit/loaded` 之后才调
   `_commit_ready_pipeline_reshard`）⇒ `assets_required` 是**预期暂态**，不阻塞任何加载/
   发布路径，只影响状态可读性。
2. **"自裁就能接受新切段"这条前提本身是错的**。`capacity.py:1293-1298` 已论证并真机踩过：
   `local_cut` **只解锁切分粒度、不解锁工件边界**（实测把 `[0,8)` 派给了只有 `mid8-24`
   工件的执行器）。照 B2 字面实现 `assets_pending` 等于把这个已修 bug 引回来，并让
   `assets_ready=True` 覆盖"工件根本不覆盖该段"的情形 —— 正是 A3 要消灭的那种伪就绪。
3. **边界内现有判据已够用**：`from_node()` 用 `source_layer_range` 表达"手上有哪个区间"，
   求解器又用 `min_layer`/`max_layer` 把切点钉在边界内 ⇒ 新切段必被旧区间包含。
   B2 现象只出现在边界外，而**边界外真就是缺工件**。
4. **成本与收益不匹配**：需把执行器自裁边界从 capacity record 一路透传到
   `PipelineArtifactRequirement`（这些字段目前都不进 `PipelineNode`），再加 `pending` 三态
   投影，约 50–70 行 + 3–4 测试，需单独评审与真机验证，收益仅为状态文案。
