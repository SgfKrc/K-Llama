## 1. 裁定

**任务图（`task_graph` / `workflow`）从产品路径降级为实验路径。**

* **产品路径**默认**不开放**任务图：对话请求走**层段（Route-A `stage_offer_v3`）**路径；
* 任务图**保留**为实现与实验能力（`/mode task_graph`、`/workflows` 观察口、相关单测与探针不删），
  但不再是产品路径的**主判据**，也不作为默认路由；
* **参考实现者：Ollama** —— 产品定位对齐 Ollama 那种"单机/边缘、单一进程、简单直接"的形态：
  用户可见概念里**没有**"任务图/工作流编排"这一层。QLH 的产品路径同样不把编排暴露给用户；
* **优先级：低于 TORCH 系列票**（PyTorch/引擎方向的后续工作线）。
  ⚠️ 截至本决策，本仓台账中**尚未**以 `TORCH-` 前缀登记任何票（全仓检索 `TORCH` 仅命中
  llama.cpp 子模块文档里的 `pytorch`）⇒ 此处按用户裁定记为"**优先级高于本项的后续工作线**"，
  其票面待建；本决策不臆造该系列的内容。

## 2. 依据（均为实测，非推理）

1. **任务图需要整模加载**，因此它的前置条件与"分布式省钱"的目标方向相反：
   `/cluster/pipeline-capacity` 在层段模式下给的是 `admitted=True` / `reason_code=distributed_forced`
   / `master 0-20` + `android-21af7c52 20-24`（两节点真机），而 master 此时
   `current.loaded=False` + `pipeline_prepared=True` —— **master 按层段参与、不持有整模**
   （`/status.model_loaded` 与 `/models/current.loaded` 同源，都读 `model_host.model_loaded`）。
2. **产品实际请求不会落到任务图**（实测日志）：TUI 内 `/mode task_graph` 确实生效
   （`app.execution_mode == "task_graph"` 断言通过），但**同一请求**的后端日志走的是 Route-A：
   `Route-A 分配原始: raw=[('master',0,20,20,None),('android-21af7c52',20,24,4,'stage_offer_v3')]`
   + 逐 step `stage handoff`，**不产生 workflow**。
   ⇒ 结论：不是缺陷，而是**优先级使然**（层段路径优先）。
3. **层段路径能独立承担产品验收**：`test_dual_host_tui_routed_pipeline_streams_text` 经 TUI 输入框
   发送请求，断言状态行 `分布式 ✓（N 段·层 x-y）` 且该承层区间与 `/cluster/pipeline-capacity` 的
   **远端段有交叠**（防"本地假装分布式"），真两节点下通过。
4. **既有裁定一致**：`docs/已知问题记录.md:242` 早已注明 `execution_mode=route_a_stage_offer_v3`
   **不是请求字段**（`ChatRequest.execution_mode` 只有 `auto` / `task_graph`）—— 产品面上"执行模式"
   的真实语义一直由路由决定，而非由任务图决定。

## 4. 验收判据（产品路径）

1. **默认路径**：`/route required` + 默认执行模式 ⇒ 走层段（Route-A），**不要求** workflow；
2. **分布式证据**：单条请求的用户可见状态行必须给出 `分布式 ✓` + 承层区间，且与 capacity 规划
   **交叉一致**（客户端：TUI 状态行 / 安卓聊天指标；后端：`claimed_layers` / `layer_segments`）；
3. **不得静默**：请求了分布式而未生效时，客户端必须显示具名原因（含请求侧意图
   `routing_preference`，不能只看全局开关）；
4. **不引入 fail-closed**：保持"能答就答"；任务图不可用**不**改变产品可用性。
