# KV 缓存优化与注意力结构调研：GQA / MLA 能否用于本项目（2026-10-14）

> 状态：**调研结论，未落地**
> 触发问题：边缘设备（如 Surface）算力不足；本仓 KV 优化「好像就一个分页」；想知道 GQA / MLA 能否吃进本项目（推理引擎允许定制化）。
> 方法：两名只读子 agent 分头做「本仓存量消化」与「外部前沿 + 本机 llama.cpp 源码核查」，下列结论凡带行号者均为实读源码/文件所得，凡属推测或记忆一律显式标注。

---

## 0. 结论速览（先看这五条）

1. **GQA 不是「能不能用」的问题 —— 你已经在用。** `qwen3-0.6b` 是 GQA 2x（16 Q heads / 8 KV heads），`qwen3-5-9b` 是 GQA 4x（16/4）。GQA 的 KV 头数**在权重里定死**，不是推理开关。
2. **MLA 也不是开关，而且本仓的靶子很窄。** MLA 由 GGUF 元数据 `attention.key_length_mla` / `value_length_mla` 决定（`src/llama-hparams.cpp:244-248`），**不存在 `--mla` 选项**；且 llama.cpp **当前只支持「全层 MLA 或全层非 MLA」**（`src/llama-hparams.h:356` 原文：`currently only support if either all or none of the layers are MLA`）。⇒ 对 `qwen3-5-9b`（3 层线性 + 1 层全注意力循环）**不可行**；对 `qwen3-0.6b`（纯全注意力）**才可行**。
3. **但 llama.cpp 里 MLA 已经有真优化实现**（不只是「能加载」）：K-only KV cache（V 是 K 的 view）、absorption 退化成 MQA、CUDA 侧有 `(576,512)` 专用模板。见 §3。
4. **最便宜的一档还没接**：`--cache-type-k/-v`（KV 量化）在本仓**从未被传过**（全仓 grep `type_k|type_v` 只命中一行 docstring）。这是 KV 内存 **≈ −50%**、1–2 小时可验证的动作。见 §5 Tier 0。
5. **一个必须澄清的架构事实**：层流水线拓扑下，**段间只传 hidden states，KV 从不跨设备传输**。所以「KV 压缩」**不会**降低跨设备网络流量，它换来的**是本段能开更长 ctx / 承载更多层**。两笔账要分开算。见 §6.2。

## 1. 先算账：现役模型的 KV 到底多大

每 token·每层 KV 字节（`B` = 每元素字节）：

| 结构 | 每 token·每层 | 说明 |
|---|---|---|
| MHA | `2 · n_h · d_h · B` | 原始 Transformer |
| GQA | `2 · n_kv · d_h · B` | `n_h / n_kv` 必须整除 |
| MQA | `2 · 1 · d_h · B` | 单 KV 头 |
| MLA | `(d_c + d_r) · 1 · B`，**V 不单独存**（是 latent 的 view） | `d_c`=latent、`d_r`=decoupled RoPE |

llama.cpp 的口径（`src/llama-kv-cache.cpp:244-248`，`const bool has_v = !is_mla;`）：

```
bytes ≈ n_ctx × Σ_il [ n_embd_k_gqa(il) + (is_mla ? 0 : n_embd_v_gqa(il)) ] × ggml_type_size(type)
n_embd_k_gqa(il) = n_embd_head_k(il) × n_head_kv(il)      // src/llama-hparams.cpp:131-141
```

代入现役模型（f16，单序列）：

| 模型 | 每 token·每层 | 持 KV 的层 | 每 token | 40K ctx 单序列 |
|---|---|---|---|---|
| `qwen3-0.6b` | `2×8×128×2 = 4096 B` | 28 / 28 | **112 KB** | **≈ 4.4 GB** |
| `qwen3-0.6b`（KV 用 q8_0） | 2048 B | 28 / 28 | 56 KB | ≈ 2.2 GB |
| `qwen3-5-9b` | `2×4×256×2 = 4096 B` | **8 / 32**（其余是线性注意力，状态不随 ctx 增长） | 32 KB | ≈ 1.3 GB |

⚠️ **第一个数字就是本项目最该被「打到」的目标**：一个 **0.6B** 模型在 40K 上下文下的 KV（≈4.4 GB）**比它的权重本身大一个数量级**。边缘设备跑不动长上下文，主因在这里，不在「模型太大」。

## 2. 为什么 MLA 比 GQA 更省

DeepSeek-V2/V3 的 MLA（arXiv 2405.04434，摘要原文：*"significantly compressing the Key-Value (KV) cache into a latent vector… reduces the KV cache by 93.3%"*）压了三件事，别混为一谈：

1. **低秩 latent KV**：`c_KV = W_DKV · h`（V2/V3 `kv_lora_rank = 512`），只缓存 latent，而非逐头 K/V。
2. **Decoupled RoPE**：另加一路共享的 rope 分量（`qk_rope_head_dim = 64`），把位置信息从 latent 里拆出。llama.cpp 落地：`wkv_a_mqa → kv_cmpr(512) + k_pe(64)`（`src/models/deepseek2.cpp:280-300`）。
3. **Absorption**：把 `W_UK` 吸进 Q 侧，attention 退化成 **MQA（1 个 KV head）**。llama.cpp 源码注释（`src/models/deepseek2.cpp:325`、`:362`）：
   ```
   // note: MLA with the absorption optimization converts into MQA (ie: GQA with 1 group)
   // note: MLA without the absorption optimization converts into MHA (ie: GQA with full n_head groups)
   ```

**两条压缩轴是独立的、可叠乘**：GQA 省「头数」，MLA 省「每 token 的 KV 维度」。

### 3.2 三条硬约束（写死在代码里，踩了会直接失败或静默变慢）

1. **V 侧量化必须开 Flash Attention**：`src/llama-context.cpp:3556-3559` 与 `:407-411` —— 否则直接报 `"V cache quantization requires flash_attn"`。
2. **量化类型的 block size 必须整除 head_dim**（`:3534-3554`）。现役模型：`128 % 32 = 0` ✓、`256 % 32 = 0` ✓、MLA 的 `576 % 32 = 0` ✓。
3. **`n_ctx` 会被 `n_seq_max` 均分**（每序列槽 = `n_ctx // n_seq_max`）—— 本仓已踩过，代码在 `src/llama_keep_head.py:75-84`、`:168-203`。

### 3.3 MLA 在 llama.cpp 的现状（**这里纠正一个常见误解**）

「能跑 DeepSeek-V2/V3」**过去**只意味着能加载权重，但**现在不止**：

- **K-only KV cache**：MLA 模型不分配 V cache（`src/llama-kv-cache.cpp:244-248`），PR #18986。
- **Absorption 在 graph 里**：PR #12801（DeepSeek V2/V3 MLA 实现）、PR #12953（FA 兼容 MLA + Metal kernel）。
- **CUDA 专用 kernel**：`V_is_K_view = DKQ == 576`（`ggml/src/ggml-cuda/fattn-mma-f16.cuh:1915`），`(576,512)` 模板专为 MLA 生成（`template-instances/generate_cu_files.py:97`），PR #19057。
- **其它 MLA 模型**：PR #18755（Kimi-Linear + MLA KV cache）。

**但「有实现」≠「你的模型能吃到」**，三个前提缺一不可：

1. **GGUF 必须是新版转换产物**（`is_mla()` 只读 `attention.key_length_mla` + `attention.value_length_mla`，由 `conversion/deepseek.py:334-335` 写入；张量须已拆成 `ATTN_K_B` / `ATTN_V_B`）。旧 GGUF 不会自动升级。
2. **全层 MLA 或全层非 MLA**（`src/llama-hparams.h:356`）。
3. FA 路径的 head dim 由模板实例决定（MLA 走 `(576,512)`）；非 FA 路径要在 graph 里做 MQA→MHA 解压（`src/llama-graph.cpp:2488-2492`），会损失部分收益。

### 3.4 GQA 在 ggml 侧的实现（不显式复制 K/V）

1. **非 FA**：K/V 形状 `[head_dim, n_head_kv, n_kv_tokens]`，靠 dim2 整除广播（`ggml.c:3241-3247`）。
2. **FA**：后端 kernel 内做整除索引 —— CPU 侧 `const int ik2 = iq2 / rk2; const int iv2 = iq2 / rv2;`（`ggml/src/ggml-cpu/ops.cpp:8468-8481`）；CUDA 侧 MMA kernel 对 GQA 特化。

⇒ MLA 的 MQA 情形（`n_head_kv = 1`）走的正是同一条整除映射，所以 **MLA 的 K-only cache 在 CPU/CUDA 上都成立，不是 CUDA 专属**。

## 6. 层流水线跨设备拓扑下的特殊机会（QLH 独有）

### 6.1 每段只持有自己那几层的 KV —— 已在代码里成立

- `src/scheduler_pipeline.py:6281`：`"kv_cache": False,  # KV 在远端段，本节点没有本地 KV`
- `src/scheduler.py:1046`：`self._kv_cache: dict = {}  # 本节点层范围的 KV cache`
- 每段是独立 context，KV 预算按「段内层数 × 每层每 token 字节 × 每序列 ctx」独立算（`QLH_LAYER_N_CTX`，默认 4096）。

⇒ **推论**：切段不改变 KV 总量，但改变 **KV 的分布**。于是「KV 压缩」与「切点选择」可以**联合优化**：把吃 KV 的层尽量放在内存大的节点；边缘段要么层数少，要么段内根本不吃 KV。

**对 `qwen3-5-9b` 的特别推论**：3/4 是线性注意力层，其状态**每序列定长、不随 ctx 增长**（`src/llama-memory-recurrent.cpp:99-101`），且与 KV 是**两套内存**（`llama-memory-hybrid.cpp:30-64` = `llama_kv_cache(filter_attn)` + `llama_memory_recurrent(filter_recr)`）。⇒ **理论上可以让边缘段只放线性/递归层，得到「常数内存」的边缘段**（前提是切点落在 `layer_types` 边界，README 已记录该约束）。

### 6.2 两笔独立的账（⚠️ 最容易被混为一谈的点）

- 跨段传的是 **float32 hidden**：`src/scheduler_pipeline.py:300`（`cpu.numpy().tobytes()`）、`:353-354`（`frombuffer(dtype=float32)`）。
- **KV 只在本地，不参与网络传输。**

⇒ 所以：**KV 压缩不降低跨设备流量**；**hidden 压缩（f16/bf16 传输）也不降低 KV 内存**。想同时省必须两条分别动手。这是「层流水线把 KV 留在各段本地（不像 tensor parallel 那样分片同步）」带来的架构事实。

### 6.3 MLA latent 对「冷页」有价值

| 场景 | 结论 |
|---|---|
| 正常 decode 接力 | **无关** —— 段间只传 hidden，latent 从不跨设备移动。MLA 的价值是**降低每段本地 KV 内存** |
| 要把 KV 搬走（session 迁移、prefix 复用、本仓 `paged_kv_cache.py` 的冷页 spill/hydrate） | **显著更适合**：latent 是「最小充分状态」，1 个头、无逐头重复，同容量可存约 1–2 个数量级更多 token（**具体倍数取决于被替代的基线头数，不要对外用固定倍数**）。且 `ColdPageRecord` 已是「整页 sha256 + 形状」的通用载体，接 latent 不需改抽象 |
| 跨设备「分片 KV」 | 不适合：MLA 的 K 必须与 Q 侧的吸收投影同段（`wk_b` 是 per-layer 权重） |

### 6.4 边缘段的第一约束是内存（不是带宽）

- 边缘/移动档直接把 `n_ctx` 砍到 1024/512（`src/model_host.py:977`：`{"edge": 1024, "mobile": 512, "ultrabook": 2048}.get(tier, 4096)`），`src/qlh_edge.py:83` 用 `QLH_EDGE_N_CTX=2048`。
- 本仓自己的 relay 文档已下结论：「容量扩展最便宜的一档」未暴露（`docs/archive/relay/跨框架接力与异构内存分层-辨析-2026-09-16.md:42,135`）。

⇒ **「KV 压缩换更长上下文 / 更大层段」在边缘段是直接可兑现的**。例外：`-ctv` 强制 `-fa`，而 CPU 上 FA 常比非 FA 慢 ⇒ 边缘段更现实的是**只压 K（`-ctk q8_0`）不动 V**，把精度开销留在 CUDA 段。

### 6.5 按段分配不同 KV 精度 —— 现成能力

`type_k/type_v` 是 **context 级**参数（`src/llama-context.cpp:333` 塞进 `cparams`）⇒ **段间可不同，段内必须统一**（不能逐层设）。两条通道：

## 7.6 ⚠️ 优先级必须被这条实测判据改写：瓶颈是「往返税」，不是 FLOPs

（2026-10-14 第三个子 agent 挖出，引用本仓既有实测；**这一节取代 §7 的排序口径**）

**净亏判据**（`docs/已知问题记录.md` #71）：

```
把 n 层分给设备 D 当独立段，值得 ⟺ n·c_master > 2·RTT_D + n·c_D
                            ⟺ n > 2·RTT_D / (c_master − c_D)   （仅当 c_master > c_D 时有解）
实测：c_master = 3.06 ms/层（master GPU，batch=1）
      Surface 段 c_D = 11.75 ms/层；Y700 c_D = 11.5 ms/层
      RTT：PC↔PC 3 ms；PC↔Y700 19~43 ms
```

⇒ **Surface 段要让「分段」从净亏变净赚，每层耗时必须从 11.75 ms 压到 < 3.06 ms（约 4×）**。

**往返税占比**（#70）：单段 `a+r = 68 ms`，其中一次跨机往返中位 **19 ms**；**每段 2 次往返 ≈ 38 ms，2 段 ≈ 76 ms/步，占 195 ms/步的 39%**，而对端计算只有约 60 ms/步。

⇒ ⇒ **本拓扑中「减少每步往返次数或步数」比「减少计算量」更值钱。**

另一个必须记住的对照事实（#65）：**去掉 Surface 段 = +49%（4.3→6.4 tok/s，零代码）** ⇒ 弱设备的真正价值是**容量**（跑得下更大的模型 / 更长的上下文），不是速度。

### 由此改写后的优先级

| 排序 | 手段 | 为什么 | 成本 |
|---|---|---|---|
| **1** | **Surface 线程数 + 二进制标定**：worker 默认 `n_threads=8`，而 Surface 是 4C8T（超订逻辑核）；同时 A/B AVX2 vs `-DGGML_NATIVE=ON` | 先把 `c_D` 的真实构成量出来，否则后续收益无法归因 | ≈0 代码，1 天 |
| **2** | **投机解码（MTP / ngram）** | 唯一能**同时**砍计算与**摊薄 38 ms 往返税**的手段（每 token 摊到的往返税从 `2·RTT/段` 降到 `2·RTT/(k+1)/段`） | 低（现成开关；Qwen3.5 自带 MTP head） |
| **3** | **边缘段工件降档**（Q3_K_M/IQ3_* 或 `--tensor-type` 只压 `ffn_*`）+ 重解切点 | 减字节 ⇒ 直击带宽/固定开销；乐观 15~30% | 中（须重跑 P2 闭环 + per-token argmax 对拍） |
| 4 | 删层（`llama-quantize --prune-layers` / `scripts/cut_layers.py`） | 线性减少边缘段层数与传输，但**不改净亏判据的斜率** | 中（hybrid 必须按 `full_attention_interval` 对齐） |
| 5+ | §7 Tier 0 的 KV 专项 | KV 压缩换的是**容量**（边缘段能开更长 ctx / 承载更多层），不是速度 | 低 |

### 明确不建议（第三个子 agent 的负面结论，均带理由）

| 手段 | 不做的理由 |
|---|---|
| 非结构化 / 2:4 稀疏 | llama.cpp **CPU 后端没有任何稀疏 GEMM**（`ggml/src` 里 `sparse` 只命中 `ggml-cann`（华为 NPU）与 `ggml-virtgpu`）；2:4 是 NVIDIA Ampere tensor core 特性，x86 无对应指令 |
| 通道/头结构化剪枝 | 需自训练 + 自造 GGUF 形状，**本仓工具链无路径** |
| early-exit / CALM / LayerSkip / 跳层 | ① **hybrid 的 linear 层是 recurrent state，不可事后重建**（不像 KV 能补写）⇒ 对 `qwen3-5-9b` 不可行；② 合法切点间隔 = 4 ⇒ 决策粒度粗到「每段一次」，可省比例被压缩；③ 本仓**零实现**（grep `early_exit\|exit_layer\|adaptive_depth` 于 `src/` → 0 命中） |
| Mixture-of-Depths | 按 **token** 稀疏，而本仓 decode 是 **batch=1（每层只有 1 个 token）** ⇒ 无 token 可省，**收益为零** |
| NSA / MoBA / MInference / SSM 替换 | 收益来自**序列维稀疏**（长 prompt / 长 ctx），本项目 decode 是短上下文 batch=1 ⇒ 近乎无收益；且需重训 + 自写 CPU kernel |
| GPTQ / AWQ / SmoothQuant / PyTorch dynamic quant | 工程实现面向 GPU kernel；且**边缘档已被刻意去 torch 化**（`llama_cpp_only`，7 项依赖）⇒ 与项目方向相反 |
| 跨机专家并行 / 专家 offload | 专家在**层内**，与「段=连续层区间」正交，且每层每 token 都要往返 ⇒ 用 RTT 税换稀疏性**必然亏**（对比：每段才 2 次往返都已占 39%） |
| `-ot / --override-tensor`（按张量放置） | llama.cpp CLI 有，但**绑定路径未暴露**（`src/llama_engine.py:860-861` 已记录）⇒ 边缘（走绑定）用不了 |

### Surface 实测补充（2026-10-14，SSH 直连实跑）

工件：Surface 上真实被当 worker 用的 4 层段 `models/q35-2b-cut-16-20.gguf`（537 MB），llama_cpp 0.3.35，逐项 A/B（每次 warmup 后计时一次）：

| n_threads（n_ctx=512） | decode tok/s | 整段 4 层 ms/token | 每层 ms |
|---|---|---|---|
| 3 | 46.88 | 21.33 | 5.33 |
| 4 | 53.98 | 18.53 | 4.63 |
| 5 | 58.90 | 16.98 | 4.25 |
| **8** | **66.58** | **15.02** | **3.76** |

| n_ctx（n_threads=8） | prompt tok | prefill tok/s | decode tok/s | 每层 ms |
|---|---|---|---|---|
| 512 | 121 | 202.56 | 53.57 | 4.67 |
| 2048 | 511 | 449.29 | 28.14 | 8.89 |
| **4096** | 1021 | 542.34 | **17.00** | **14.71** |

**三条结论（两条与预期相反）**：

1. ❌ **「默认 8 线程超订逻辑核会变慢」被实测否定**：`n_threads=8` 最快（8 vs 4 = 1.23×，8 vs 3 = 1.42×）。默认值是对的，**不要改**。
2. ✅ **decode 随 ctx 急剧恶化**：`n_ctx` 512→4096 时 decode 从 53.57 掉到 17.00 tok/s（**慢 3.15×**），每层 ms 从 4.67 涨到 **14.71**。
3. ⚠️ **这解释了 `c_D = 11.75 ms/层` 的来源**：它对应**真实 ctx=4096 下的 decode**（本次实测 14.71，同量级）；而**小 ctx 下 Surface 只要 3.76~4.67 ms/层，已接近 master 的 3.06 ms/层**。⇒ `c_D` 里的大头**不是「非计算固定开销」，而是「KV / attention 随 ctx 的线性增长」**。

⇒ **因此优先级要再次修正**：**KV 压缩/量化（§7 Tier 0）不是「容量手段」，而是直击 Surface 段最大开销的手段** —— 把 KV 压小等于把这条随 ctx 增长的曲线压平，比「先标定、后投机」更靠前。
（#70 的「往返税占 39%」依然成立 —— 两者是**两笔不同的账**，都要打。）

#### AVX512 的补充判断（承接 §7.5）

- `GGML_AVX512` / `GGML_AVX512_VNNI` **默认 OFF**（`ggml/CMakeLists.txt:123,140-171`）；只有 `GGML_NATIVE=ON` 才走 `-march=native`。

- ⚠️ **但 AVX512-VNNI 对本仓主力档（Q4_K_M）大概率无用**：VNNI 内核走 `GGML_CPU_REPACK` 的 **Q4_0 运行时转换**路径（`ggml/CMakeLists.txt:152`），而 K-quant 不走 repack。
- 降频风险：现有权威表述是「降频主要影响 **Ice Lake 之前**的实现」（256-bit 的 AVX512VL 不触发）⇒ **Ice Lake 15W 是否净亏「不确定」，必须自测**。

### KV 量化实测：⚠️ 在 CPU 边缘段反而更慢（2026-10-14，Surface）

工件同上，`n_ctx=4096`，`n_threads=8`，prompt ≈2295 tok：

| case | decode tok/s | ms/token | 每层 ms | 输出 sha8 |
|---|---|---|---|---|
| baseline f16 KV, fa=off | 9.00 | 111.05 | 27.76 | 85e7eac2 |
| f16 KV, fa=on | 9.55 | 104.70 | 26.18 | 85e7eac2 (1.06×) |
| K=q8_0 only, fa=off | 9.23 | 108.36 | 27.09 | 85e7eac2 (1.02×) |
| K=q8_0 V=q8_0, fa=on | 8.03 | 124.55 | 31.14 | 85e7eac2 (**0.89×**) |
| K=q4_0 V=q4_0, fa=on | 7.57 | 132.11 | 33.03 | 85e7eac2 (**0.84×**) |

**所有 case 输出 sha8 完全相同** ⇒ 正确性无差异，差异纯在速度。

**解读**：
- CPU 上**去量化的额外算力 > 省下的带宽** ⇒ KV 量化净亏；且 `-ctv` 强制 `-fa`，而 **CPU 上的 FA 本身也不快**（f16 KV + fa=on 只有 1.06×）。
- 本表 prompt 是 2295 tok（比 ctx A/B 的 4096 档 1021 tok 更长）⇒ decode 只有 9 tok/s、27.76 ms/层。这**再次印证**：真正的变量是**「上下文里已有多少 token」**，而不是 `n_ctx` 配置本身。

**⇒ 结论：要缓解这条曲线，必须减少「被 attention 扫的 KV 数量」，而不是「每个 KV 的字节数」（本小节取代上面把 KV 量化排最前的口径）**

- ❌ **KV 量化（`-ctk/-ctv`）在 CPU 边缘段不是答案**（实测更慢）。
- ✅ 真正对症的是：**滑窗注意力（SWA）/ KV 驱逐（StreamingLLM、H2O、SnapKV 类）/ 用 hybrid 模型的线性注意力层（状态不随 ctx 增长）**。
- ⇒ 而 **`qwen3-5-9b` 的 3/4 层本来就是线性注意力** ⇒ **边缘段应优先承载线性注意力层**（§6.1 的推论，现已有实测支撑）。
- 现成可试的 llama.cpp 旋钮：`--keep N`（≈ attention sink 保留）、`--context-shift`、`--cache-reuse`；若模型自带 SWA，**不要**开 `--swa-full`（那是把它关掉的反面）。

## 7.7 收口：四轮实测的总账与两条否证（2026-10-14）

在 Surface（i5-1035G4，SSH 直连）上共跑四轮实测，**三轮推翻了初始假设**，另一轮证明实验设计需要重做。汇总：

| 轮次 | 假设 | 实测结论 | 状态 |
|---|---|---|---|
| 1 | 边缘默认 8 线程超订逻辑核会变慢 | ❌ **8 最优**（3/4/5/8 → 46.9/54.0/58.9/66.6 tok/s，n_ctx=512）⇒ 默认值不改 | 已否证 |
| 2 | `c_D` 的大头是非计算固定开销 | ❌ 实为 **KV/attention 随 ctx 的线性开销**（512→4096 慢 3.15×） | 已否证 |
| 3 | 接 `-ctk/-ctv` 就能提速 | ❌ **CPU 上反而更慢**（q8_0 0.89×、q4_0 0.84×，输出 sha8 全同） | 已否证 |
| 4 | 用「hybrid 段 vs 纯 full 段」验证线性层的 ctx 无关性 | ⚠️ **该架构上不可行**（见下） | 设计作废 |

**第 4 轮为何不可行（这是本轮最有价值的否定结论）**：
- 同一模型切不出「纯 linear 段」——`qwen35.full_attention_interval = 4`（GGUF metadata 实测）意味着**每 4 层必有 1 层 full**，任何段的 full 占比**恒为 1/4** ⇒ 按层归一化的斜率必然相同，**无法分离线性层的贡献**。
- 且不同模型的段**参数不同**（2B hybrid vs 0.5B full 差 4×），斜率本就不可比。
- ⇒ 结论：**「线性层不随 ctx 增长」只能靠上游源码事实（`llama_memory_recurrent.cpp:99-101` 分配定长张量）间接支持，不能靠段对照实验证明**。

**附带发现（工程风险）**：Surface 上的 cut 工件**命名与实际内容不符**（`qwen25-05b-f16-cut-16.gguf` 的 `block_count` 实为 **8**，而非 16）。⇒ **任何基于这批工件的测量都必须先读 GGUF metadata 校验**，否则会得到不成比例的数据（本轮就出现过 3815 ms/token 的假异常）。

**GGUF metadata 核实（本轮新增的一手数据）**：

```
q35-2b-cut-16-20.gguf:   arch=qwen35  block_count=4  head_count=8  head_count_kv=2
                         key_length=256  value_length=256  full_attention_interval=4
                         ssm.state_size=128 / conv_kernel=4 / inner_size=2048   ← 线性层用 SSM(GatedDeltaNet)
qwen25-05b-f16-cut-16-20.gguf:  head_count=14  head_count_kv=2  block_count=4   ← 纯 full，GQA 7x
qwen25-05b-f16-cut-16.gguf:     block_count=8                                     ← ⚠️ 名不符实
```

Surface 系统内存：**总 15.60 GB / 可用 9.62 GB** —— 而上述三段在 ctx=4096 下的 KV 分别只有 **8.4 MB / 8.4 MB / 16.8 MB** ⇒ 第 4 轮的假异常**与内存无关**。

**本轮的实际产出价值**：三轮否证把「边缘段提速」的搜索空间砍掉了一大半 —— 线程数不用动、固定开销不是大头、KV 量化不是答案、段对照验证不了。剩下的方向收敛为：**减少被 attention 扫的 KV 数量**（滑窗/驱逐）与**让不吃 KV 的层落在边缘**。

## 8. 一句话回答最初的问题

- **GQA**：已经在用（0.6B 是 2x、9B 是 4x）。要更省得改权重，不是开关。
- **MLA**：llama.cpp **已实现**（K-only cache + absorption + CUDA kernel），但**它是模型属性**，且**只支持全层 MLA、不支持混合模型**。⇒ 本仓可落地的靶子是 **`qwen3-0.6b`**（纯全注意力），**不是** `qwen3-5-9b`。
- **真正常识性的收益不在「引入 MLA」，而在**：① 把已经存在的 `-ctk/-ctv` 接出来（KV 减半，1–2 小时）；② 用 `qwen3-5-9b` 的 hybrid 结构把边缘段做成「常数内存段」；③ 按段差异化 KV 精度/ctx；④ 若要长期收益，再考虑驱逐/合并类 kernel 或 MLA 化 0.6B。
- **但最重要的结论在 §7.6**：按本仓实测的分段净亏判据（#71）与往返税占比（#70），**边缘段的瓶颈不是 FLOPs，而是「每段 2 次跨机往返 + 固定开销」**（2 段占 195 ms/步的 39%，而对端计算仅约 60 ms）。⇒ 优先级应该是 **①标定（线程数/构建）→ ②投机解码（同时摊薄往返税）→ ③工件降档**，而**不是**先去啃剪枝/降维/MLA 化。KV 压缩与 MLA 在这里的价值是**换容量**（边缘段能开更长 ctx / 承载更多层），不是换速度。
- **关于「知识储备不足」这件事**：本轮三个调研给出的负面结论（2:4 稀疏/通道剪枝/early-exit/MoD/NSA/跨机专家并行都不可行，且每条都有理由）比正面清单更有用 —— 它把搜索空间砍掉了大半。需要补的底子集中在三处：**注意力结构与 KV 体积的换算**（§1）、**「架构决定 vs 运行时开关」的分界**（§2/§3.3）、**「按层流水线的观测口径算账」的习惯**（§7.6，本仓已有现成判据与打点工具可直接复用）。
