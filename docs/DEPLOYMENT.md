# 部署与分段

> 状态：**整模 + 层范围**（裁段方案已退场，见 §7）
> 更新日期：2026-11-01

本文件定下三件事：每台机器上放什么、换分段时怎么做、以及**控制面不做什么**。
最后一条比前两条重要——前身仓库的控制面涨到无法维护，起点都是"帮人算一下"。

## 1. 每台机器放什么

```
shim/                       CPU 版约 8.1 MB，CUDA 版约 553 MB
<整模>.gguf                 约 21.87 GiB（35B-A3B，Q4_K_M 系）
topology-<站点>.toml        本机拓扑，不入库
```

**没有"自己那段"这种东西。** 每台机器持有同一份完整 checkpoint，加载时由
`LLAMA_LAYER_RANGE=lo:hi` 决定只创建、只读取哪几层（见 `PATCHES.md` 第二代）。

### 为什么存整模

三个原因，第一个是硬的：

1. **MTP 头**。裁切件没有 `blk.40`，而投机解码要它。
2. **空间上反而更省**。四段合计比整模还大——每段都要重复带 `token_embd` /
   `output.weight`，各约 515 MB，四份就是 2 GB 级别的浪费。
3. **换分段零传输**。段是派生物，改拓扑里的数字就是换分段；裁段方案要重切、重 scp。

### 传输

```
scp <整模>.gguf 到每台设备       一次性
```

ROG 实测 22 MB/s（跨 Tailscale），21.87 GiB 约 17 分钟。一次性成本。（原写 11 分钟是按 14.8 GB 算的，那个数字本身是错的。）

## 2. 换分段怎么做

```
1. 改 topology 的 layers / layer_range
2. 重启 worker
```

不动磁盘、不联网、不重传、不碰别的机器。

`layer_range` **不能省**：没有它每段都会跑完整 40 层，而且不报错——只是结果错。
`topology-local-32-8.toml` 的注释记着这条。

切分点必须落在 `full_attention_interval`（本模型是 4）的整数倍上，
`topology.py` 按这条 fail-closed。

## 3. 溯源与校验

现行形态下，**`layer_range` 本身就是溯源**——拓扑说这一段覆盖源模型的哪几层，
不用去工件里找元数据。

两层校验：

| 校验 | 位置 | 抓什么 |
| --- | --- | --- |
| worker 侧 HELLO + driver 校验 | `stage_worker._session` / `StageClient._read_identity` | 实际加载的 `n_layer` / `n_embd` / `layer_range` / dtype 与拓扑不符 → 立即失败 |
| 段覆盖拼合 | `topology.verify_ranges` | 各段拼起来不覆盖源模型（比如声明 20 层但源模型 24 层），会跑出"看着通顺的垃圾" |

第一条是 2026-11-01 加的：在那之前就绪判据只有"TCP 连上了"，这对一个装错切分的
worker 同样成立。

**没声明 `layer_range` 的段**（裁段时代的工件）没有可读的溯源，覆盖校验回退到 sidecar
`.qlh.json`，`verify_ranges` 会读它。本机已无这样的拓扑——`topology-2b.toml` 也改成了
整模 + `layer_range`，但回退分支仍是活代码。格式与读写契约见 [`CUT-TOOL.md`](CUT-TOOL.md)。

## 4. 跨机启动

拓扑里的 `ssh_user` / `start_cmd` 描述怎么把远端那段拉起来，由
`chain_client.start_remote` 执行。

两个实现约束都是实测的：

- **用 schtasks，不用 `start`**。`ssh target "cmd /c start ..."` 返回 0 但什么都不发生：
  ssh 会话没有交互式窗口站，`start` 的新控制台永远不出现（用副作用验证过）。
- **先探端口**。worker 的 serve 循环跨 chain 常驻、模型一直加载着，重复拉起只会抢端口。

`ssh_user` 留空表示"这段由人手工起，harness 只连不管起"。

## 5. 控制面不做什么

### 不做自动切分求解

`topology.toml` 是人写的。prima.cpp 用 806 行整数规划求解切点，前提是"设备未知、
数量不定"；我们的设备是已知的三台、层区间是配置项。评估与开工条件见
[`AUTO-ASSIGN-PLAN.md`](AUTO-ASSIGN-PLAN.md)。

### 不做工件传输

没有工件。整模一次性 scp，之后不再传模型文件。

### 不做动态重平衡

推理中不重新分配层。prima 的调度也是纯静态（`-lw "16,16,16"` 或启动时求解一次），
这是同一思路。

### 控制面只做四件事

读拓扑、起 worker、连 worker、跑链。**加起来一千行以内**，不是四千行。

## 6. 交叉模型投机解码**没有**做

`draft` 与 `target` 必须是同一个模型文件，两边的 `layer_range` 之外张量
（tokenizer / output / nextn）才对得上。用别的模型当草稿会错得很隐蔽。

这条限制的实测背景在 [`SPECULATION.md`](SPECULATION.md)。

## 6.5 `gpu_layers` 怎么定：扫一遍，别猜

`[[stage]]` 的 `gpu_layers` 决定这段有多少层上显卡，其余在 CPU。**它有一个明确的拐点**，
而且拐点之后性能会回落——回落时单段耗时反而更快，因为溢出的部分走了系统内存。

本机两段（`topology-local-32-8`，head 32 层、tail 在 CPU）的实测（2026-11-01，DFlash k=5，
`--gen 128`，代码 prompt）：

| `gpu_layers` | tg | stage 0 中位 | 判 |
| ---: | ---: | ---: | --- |
| 4 | 7.2 tok/s | 394.6 ms | — |
| 5 | 7.9 tok/s | 363.1 ms | +10% |
| **6** | **8.7 tok/s** | 354.0 ms | **+21%，拐点** |
| 7 | 8.1 tok/s | **346.1 ms** | 回落 |

7 层那行的特征值得记住：**stage 0 更快（346.1）但 tg 变慢（8.1）**。GPU 侧的层变多所以单段
计算变快，但溢出的权重走系统内存，每个 token 多付一次搬运。**只看单段耗时会把拐点判错。**

而 6 层**本身也在溢出**：2026-11-02 的 DFlash 实测报 `2.74 GiB resident for 3.28 GiB of GPU
weights`——84% 驻留，低于 `VRAM_LANDED_SLACK=0.85`，所以告警会打出来。它仍然是这四档里最快
的一档。**溢出和更慢不是一回事**：溢出的那部分每次要过一次系统内存，但如果换来少跑两层
CPU，净收益仍为正。所以判据只能看 tg，`!! VRAM spill detected` 这行出现也不等于该退回去。

顶到显存上限的层数：12 层要 9.45 GiB，本机 8 GiB 卡只有 7.91 GiB 可用。

**所以定这个值的方法是扫 4/5/6/7 看 tg，不是看 stage 耗时，也不是按显存除一下。**

## 6.6 `gpu_layers` 与 `cpu_moe` 的组合：专家留 CPU，注意力上卡

`gpu_layers` 决定多少**层**上卡，`cpu_moe` 决定多少层的**专家**留在 CPU。两者不是一回事，
而且对 35B-A3B 这种 MoE 来说，分开调比整层 offload 好得多。

本机（RTX 4060 Laptop 8 GiB）+ Surface 两段，k=2、直连、2026-11-02：

| `gpu_layers` / `cpu_moe` | tg | stage 0 | 预期驻留 |
| --- | ---: | ---: | ---: |
| 6 / 0（整层 offload） | 3.8 tok/s | 179.5 ms | 7.55 GiB |
| 14 / 32 | 4.2 | 168.3 ms | 10.61 |
| 22 / 32 | 4.8 | 166.2 ms | 13.67 |
| **26 / 32** | **5.1** | **147.4 ms** | 15.20 |
| 32 / 32 | 5.0 | **135.4 ms** | 17.50 |

**为什么把专家留在 CPU 反而快**：专家占权重的 91%（19.86 / 21.87 GiB），但每个 token 只
命中 8 个；注意力只占 9%，却每个 token 全部要算。只把注意力搬上卡，显存只要 1.3 GiB，
就够让 26 层的注意力命中显卡。

**32 / 32 是那个陷阱**：它的 `stage 0` 最快（135.4），整链却更慢。原因不是显存（才 1.6 GiB），
是**预期驻留 17.50 GiB 逼近了内存预算**，开始换页。判据只能看 tg——这和 §6.5 里 7 层那个
"stage 更快、tg 更慢"是同一个形状，只是原因从显存溢出换成了内存压力。

**内存预检会随机器空闲程度变化**：同一条 `-ngl 32` 配置，机器忙时预算 15.90 GiB（拒绝），
空闲时 22.72 GiB（放行）。所以"这个配置跑不了"要先看预检报的预算，不是看配置本身。

## 6.7 Surface 段的 `threads`：6 比物理核数 4 快，8 会崩

Surface 是 i5-1035G4，4 物理核 8 逻辑核，tail 段跑 8 层。2026-11-02 扫（k=2、直连、head 固定 26/32）：

| `threads` | tg | tail 段耗时 |
| ---: | ---: | ---: |
| 3 | 4.0 tok/s | 151.4 ms |
| 4（物理核数） | 3.6 | 138.5 ms |
| **6** | **4.3 → 5.2**（两次测量，见下） | **130.4 → 113.2 ms** |
| 8（全部逻辑核） | **0.2** | **6994 ms** |

`threads=6` 后来复测到 5.2 tok/s / 113.2 ms（同一配置、直连、k=2）。两次差 21%——宿主机负载
会影响这个数字，所以**跨时间比较前先确认机器空闲**。

两点值得记：

**6 比 4 快。** 超线程那一半不是废的——tail 段的 8 层里有大量等内存的停顿，第二个线程能填进去。
所以"取物理核数"这条经验在内存受限的模型上不成立。

**8 会崩，而且是灾难性的**（6994 ms，慢 50 倍）。4 个物理核塞 8 个线程，每次调度都要等满一轮。

顺带一条：**tail 段耗时随 `threads` 单调下降（151 → 130），而 tg 不是**（4.0 → 3.6 → 4.3 → 0.2）。
这和 §6.5/§6.6 是同一个教训——**单段耗时不能当判据**，第三次了。

**另一个前提**：`threads` 必须写进远端启动脚本，不是拓扑。拓扑的 `threads` 只对本地段生效，
远端段由 `start_cmd` 指向的 `.cmd` 里的参数决定（`schtasks /tr` 不能带参数，所以只能写死）。

## 6.8 量化类型按段分布：IQ4_XS 全在 head，tail 一个都没有

这是 2026-11-02 直读 GGUF 头（753 个张量）得到的事实，解释力比它看起来大：

| 段 | 大小 | 构成 |
| --- | ---: | --- |
| head（blk.0–31） | 15.86 GiB | **IQ4_XS 8.37** + Q6_K 3.86 + Q5_K 3.09 |
| tail（blk.32–39） | 4.88 GiB | Q6_K 2.66 + Q5_K 2.06 + Q8_0 0.03，**零 IQ4_XS** |
| `output.weight` | 0.39 GiB | Q6_K（248320 × 2048） |

**这解释了两件事。**

**① 为什么 `CPU_REPACK` 全部回退**：IQ4_XS 占了权重的大头，而它在**所有后端都只有
MMV（向量乘），没有 MMQ（矩阵乘）**——Vulkan 和 SYCL 一样，OpenCL 与 OpenVINO 干脆不支持。
所以"换量化就能吃到 repack"这个直觉在这里不成立：占面积最大的那种类型恰恰是最没优化的。

**② 为什么核显只可能救 tail**：head 的 15.86 GiB 里 8.37 是 IQ4_XS，塞进核显那 15.82 GiB
共享堆会连系统一起挤死；而 tail 全是 Q5_K/Q6_K/Q8_0，四种后端全覆盖，4.88 GiB 能整段常驻。

**关于核显的一个实测**（本机 Iris Xe，ctypes 直调 OpenCL）：

```
流式读 780 MiB     13.1 ms = 58.2 GB/s   （本机 CPU 6 线程 23.7 GB/s）
lm_head 形状 GEMV  20.5 ms = 23.6 GB/s   （朴素/协作/向量化三版都在 22.6-24.2）
```

两者差 2.5 倍，说明**低算术强度的 GEMV 只能吃到约四成 DRAM 带宽**，别指望这条路上有数量级。

对照：Surface 的 tail 现在是 130.4 ms 对应每轮必读 814 MiB = **6.5 GB/s**，而 LPDDR4x 峰值
约 59.7 GB/s。所以空间确实存在，但能不能兑现要实测——**判据是 tail 段单机的 tg，不是带宽**。

## 7. 历史：裁段方案为什么退场

2026-10-29 之前的形态是每段一个 `.gguf`，由 `cut.py` 切出。退场原因、sidecar 格式
契约、以及历史验证结论都在 [`CUT-TOOL.md`](CUT-TOOL.md)。工具实现留在
`_archive/tools/cut.py`（本机，不入库）。

一句话：**裁段是"每台机器必须只持有一段"时的方案**，而
`ARCHITECTURE.md` 已经把"同一台机器拆两段"定性为设计错误——所以这个前提在现在的
部署形态里不成立。
