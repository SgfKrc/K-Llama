# 部署与裁段

> 状态：裁段方案已定，代码已实现
> 更新日期：2026-10-30

本文件定下三件事：每台机器上放什么、换分段时怎么做、以及**控制面不做什么**。
最后一条比前两条重要——前身仓库的控制面涨到无法维护，起点都是"帮人算一下"。

## 1. 每台机器放什么

```
shim/                       CPU 版约 8.1 MB，CUDA 版约 553 MB
<整模>.gguf                 约 20.8 GB（35B-A3B Q4_K_XL）
<自己那段>.gguf             4-9 GB，由整模切出
<自己那段>.gguf.qlh.json    溯源，随工件一起复制
```

**设备不需要段的总和，也不需要别的设备的段。** 只需要整模 + 自己那段。

### 为什么每台存整模

直觉上"只发自己那段"更省，实测不是：

| | 大小 |
|---|---|
| 整模 | 20.82 GB |
| 四段合计 | 22.37 GB |

段加起来比整模还大 1.55 GB，因为每段都要重复带 `token_embd` / `output.weight`
（各约 515 MB）。四段就是四份。

所以存整模在空间上就是赚的，换来的是换分段时零传输。

### 传输

```
master（唯一有整模的机器）
  cut.py 切出各段            11 秒/段（实测 412 MB/s）
  scp 整模到各设备           一次性
  scp 各段到对应设备         只发自己那段

其他设备
  scp 收整模 + 自己那段
```

ROG 实测 22 MB/s（跨 Tailscale），20.82 GB 约 16 分钟。一次性成本。

## 2. 换分段怎么做

```
1. 本地 cut.py 切自己那段         11 秒
2. 改 topology 的 layers / host / port
3. 起 worker
```

不联网、不重传、不动别的机器。段是派生物，删了随时能重建。

```powershell
python cut.py --src <整模> --dst <段> --keep-head 8          # 首段
python cut.py --src <整模> --dst <段> --k 8 --end 24          # 中段
python cut.py --src <整模> --dst <段> --k 24                  # 尾段
```

每次都写 `<段>.gguf.qlh.json`。它记录源模型、覆盖区间、层数、文件大小。

## 3. 溯源与校验

`cut.py` 把同样的信息写两处：

- **工件内的 `qlh.*` KV** —— 自描述，工件复制到别的机器也带着
- **旁边的 `.qlh.json`** —— 校验时读这个

两份的理由：读工件内的 KV 要 7 秒/个（GGUF 把 248k 个 tokenizer 字符串放在头部，
任何读取器都得走过它），sidecar 是毫秒级。

`topology.load()` 每次都会校验，失败分两种：

| 情况 | 行为 |
|---|---|
| 区间重叠、有空洞、层数与声明不符 | `TopologyError`，拒绝启动 |
| 没有 sidecar（老工件） | `ProvenanceWarning`，照常启动 |

第二种是刻意留的：老工件没有溯源，拒绝启动就是回归。但要意识到**它没被校验**。

### 这条校验为什么必须有

分段缺层不会报错。24 层的模型只跑前 20 层，`source_layers` 又写错成 20，
则"各段之和 == 声明值"通过、每段的层数也各自对上，链路一路跑通，
输出是通顺但错误的中文：

```
缺 4 层    "中国的首都是" → "______。<think>…asking what capitalsitalize…"
完整 24 层 "中国的首都是" → "北京，但北京并非中国唯一的…"
```

所以 `source_layers` 这种手填的总量必须能被独立核对一次。

## 4. 控制面不做什么

三条硬约束。

### 不做自动切分求解

"帮我算最优切分"是无底洞：切分点取决于设备内存、网络、想跑多少层、
要不要留显存给别的程序。这是人的决策，不是求解器的输出。

`cut.py` 只接受人给的 `--k` / `--keep-head` / `--end`，不猜。

### 不做工件传输

scp / rsync 够用。自己实现传输就要自己实现断点续传、校验、重试，
那是另一个项目。

### 不做动态重平衡

运行中把层段搬到别的机器 = KV cache 迁移 = 另一个项目。

### 控制面只做四件事

读 topology、校验工件、起 worker、连链路。就这些。

## 5. 交叉模型投机解码**没有**做

计划文档里要记录这条，因为它是"看起来该做但实测不划算"的典型。

词表已验证一致（35B / 2B / 9B 都是 248320 tokens，指纹相同），技术上可行。
但词表一致的最小模型就是 2B，33 ms/token；而目标模型在本机三段上只需 98.7 ms/token。
草稿只快 3 倍，加上验证成本后是亏的。只有四段含远程机器（297 ms/token）时才回本，
而那时的瓶颈恰恰是远程那台机器本身——把它修好，这条路的收益就消失了。

## 6. 另一条路：改 llama.cpp 不裁段（评估过，暂不做）

`llama-model-loader.cpp` 的 `get_weight()` 是唯一的张量查找入口：

```cpp
const llama_model_loader::llama_tensor_weight * llama_model_loader::get_weight(const char * name) const {
    auto pos = weights_map.find(name);   // ← 在这里把 blk.0 映射成 blk.20
    ...
}
```

配合覆盖 GGUF 的 `block_count`，可以让架构代码只用段内编号访问整模，
从而**完全不需要裁段工件**：每台只存整模，换分段只改 topology 里的数字。

不做的理由：

- 要改上游源码 + 重新编译整份 llama.cpp（CUDA 部分 20-30 分钟）
- 覆盖 `block_count` 比改 `get_weight` 难——它要在 hparams 解析前生效
- 要验证输出与裁段逐位一致
- 而裁切只要 11 秒，收益不足

什么时候值得回头：分段需要频繁变动（例如做自动实验），或者磁盘比时间贵。
