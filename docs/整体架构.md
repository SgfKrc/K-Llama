## 1. 产品目标与当前基线

QLH使多台异构PC和Android设备通过层段接力运行单机容量受限的模型。用户在一台设备选模，master统一规划、供给和准备；各计算节点只加载自己的连续层段，通过master完成逻辑多段接力。

当前发行合同为[release-contract.json](../release-contract.json)`route-a-production-v1`，开启A3 `stage_offer_v3`。2026-10-18已在Windows免安装程序及Android参与的Qwen3.5-9B三机LL／DL实测中完成自动供给、正常判停和无fallback；准确层段、来源与独立装载观测见[票13实测](ci-release-followup-2026-10-16.md#13-rog-免安装续验与-frozen-来源合同2026-10-18)。票13产品验收已收口，完整严格重采与可信签名发行实际执行独立后置。

## 2. 当前执行路径

| 路径 | 引擎与实际职责 | 边界 |
| --- | --- | --- |
| LL层段接力 | master llama.cpp首段→各worker llama.cpp后续段；master转发所有hidden | 正式分布式路径，proper GGUF、keep-head／native前向；所有节点仅加载本段 |
| DL跨框架接力 | master PyTorch选择性物化首段→llama.cpp worker后续段 | 正式分布式路径；校验源模型／tokenizer等价证明及hidden合同 |
| 显式本地推理 | 节点退出计算参与、退休层段后，选择本地完整模型引擎 | 允许整模基线；重新参与前卸载整模；`_set_node_inference_mode`控制转换 |
| 本地llama.cpp runtime分流 | binding／keep-head提供层段能力；llama-server用于其已验证的本地完整模型路径 | `inference_path_selector.select_inference_path`裁决，不能把server当层段执行器 |
| external／island | 外部整请求服务或单个逻辑网关引擎 | 可选扩展、独立数据作用域与fallback观测；不计作本仓LL／DL多段成功 |
| task graph／PoC／专用sidecar | 通用workflow、独立投机实验及模型专用runtime | 当前为实验／专用路径；新分支规划裁撤通用任务图与PoC，专用扩展单独评估 |

本地n-gram自投机与层段执行能力分别建账。二进制hidden和分片已接入task-worker传输；分布式投机批验证仍缺draft和hybrid回滚等前置。实现状态及符号以[审计矩阵](当前功能与事实归属审计-2026-10-18.md#2-功能清单与取舍)为准。

## 3. 星状物理拓扑与逻辑接力

```mermaid
flowchart LR
    UI[任一设备客户端] --> M[master：编排、首段与转发]
    M -->|stage offer / hidden| W1[worker A：本段]
    W1 -->|hidden / result| M
    M -->|stage offer / hidden| W2[worker B：本段]
    W2 -->|hidden / result| M
```

逻辑顺序为首段→中间段→末段，物理连接始终通过master。层段数量根据实际能力和容量求解；节点ID只表示身份，worker不接收peer地址以建立层数据直连。master至少执行首段一层并承担embedding；LM head在计划中明确归属。

master统一验证task、attempt、model、config、assignment、连接代际、step和相邻段关系。实际入口为[scheduler_pipeline.py](../src/scheduler_pipeline.py)`_run_route_a_stage_pipeline`，远端准备为[worker_prepare_coordinator.py](../src/worker_prepare_coordinator.py)。库存、HELLO及文件available只证明对应阶段；ready需要当前assignment实际装载回执。

## 4. 当前实现分层

| 层 | 主要实现 | 实际职责与结构边界 |
| --- | --- | --- |
| PC客户端／管理 | `qlh.py`、`tui_textual.py`、`tui_commands.py`、`tui_api.py` | 选模、聊天、进度与状态；不应自行决定集群ready |
| Android／Web | Android Full／Lite、`frontend_cybergothic`子模块 | Full本机计算与UI、Lite客户端；Room／DataStore仍有各自用户数据和本地设置 |
| API与应用门面 | `api_server.py`、`api/routes_*.py` | 鉴权、用例和服务组合；router已拆分，共享门面状态仍待重构 |
| 意图／供给 | `model_intent.py`、`model_supply.py`、`model_supply_worker.py`、`model_supply_assets.py` | 目标模型、inventory、裁切／分发、校验、进度与供给回执 |
| 放置／调度 | `scheduler.py`及mixin、`pipeline_capacity.py` | 容量求解、部署状态、请求队列和节点事件；存在多事实组合，见专项审计 |
| 准备与执行 | `worker_prepare.py`、`worker_prepare_coordinator.py`、`model_host.py`、`inference_service/engine_host.py` | 候选装载、commit、实际runtime、KV及物理退休；master和worker各有本地owner |
| 引擎 | `llama_engine.py`、`llama_keep_head.py`／shim、`model_module.py`、`llama_server_engine.py` | proper层段或显式本地完整模型；按runtime能力选择 |
| 通信与控制权 | `tcp_comm.py`、`task_worker_protocol.py`、`cluster_auto_role*.py`、quorum／fence | 星状传输、注册、连接恢复及授权；自动接管和恢复仍有接线／证据缺口 |
| 存储／证据 | `local_store.py`、`task_journal.py`、供给manifest／JSON、runtime source／product observer | 各自持久事实及独立观测；目标设计将控制记录归入明确领域事务 |
| 启动／打包 | `packaging/packaging/launcher.py`、`qlh_launcher.py`、正式spec及平台包装 | 主程序与独立维护壳职责不同；新分支先接住首启／helper／维护职责，再裁撤独立Launcher |

源码功能清单也包括独立工作台的工具、摘要、RAG、记忆和生图扩展；这些有自己的用户数据及入口，不等于已接入主聊天或分布式核心。

## 5. 自动选主、模式与恢复

当前auto-role已有quorum取证、启动选举、续租和失去quorum禁写。`QuorumPolicy.election_allowed`要求至少3个配置voter；发行默认角色、发现候选与自动quorum是不同配置语义。TCP失联／重连到auto-role及运行时角色转换的事件闭环仍需补齐，不能只凭选举协议单测宣称掉主自动接管完成。

计算资格、控制可达、用户模式和模型驻留分别描述。节点显式本地模式可以保留管理HTTP或绑定信息；分布式执行期间任何节点的加载、prepare、失败补救均须遵守整模禁载。既有本地重启会恢复lifecycle与清理债务后重取ready，图journal的复制水位尚不足以证明跨主模型部署已恢复。

现有assignment registry、请求deadline／终局latch、会话revision/CAS、安全凭据epoch与路径防护是保留合同。真实源字节／进程观测与可信签名发行分别验收，`/api/health`与`/api/ready`分别表示可响应和运行时就绪。
