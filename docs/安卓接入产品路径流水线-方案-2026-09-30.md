### 1.3 真实 gap（三点，按阻塞度）

1. **★ `capabilities` 与 `pipeline_worker`/`backend_id` 自相矛盾**（**根因已坐实**）。
   实测 `GET /api/cluster/nodes` 的 android 节点：
   `"pipeline_worker": true, "backend_id": "llama_cpp", "capabilities": []`。
   根因在 **App 侧**（不是 master 映射 bug）：
   `android/.../MainViewModel.kt:1187-1192` 发 **task worker** 的 device_info 时
   ```kotlin
   val deviceInfo = buildAndroidPresenceDeviceInfo().toMutableMap().apply {
       put("connection_type", "tcp_task_worker")
       put("pipeline_worker", true)     // 无条件硬写
       put("task_worker", true)
       put("backend_id", "llama_cpp")   // 无条件硬写
   }
   ```
   而 `capabilities` 仍来自 `buildAndroidPresenceDeviceInfo()`（`MainViewModelLogic.kt:209`），
   其条件是 `runtime?.nativeRuntimeAvailable == true && !isLite` ⇒ 该 native runtime 未就绪时
   落成 `[]`，与刚硬写的 `pipeline_worker=true` / `backend_id=llama_cpp` **互相打脸**。
   影响：`_client_supports_forward_layers`（`api_server.py:4832`）与 `_node_supports_forward_layers`
   （`scheduler.py:252-282`）都优先读 `capabilities`；本机实测这两处**靠 `backend_id` 兜底**才
   判成 True（故 skip 理由落在下游的 `not_eligible`，而不是 `no_forward_layers`）——
   即：**能力门现在被"硬写的 backend_id"蒙过去了，一旦设备 native runtime 真没就绪，
   这两个字段会一起说谎**。
   修法（阶段 0）：App 侧三处字段必须**同源** —— `pipeline_worker`/`backend_id`/`capabilities`
   统一由同一个 `nativeRuntimeAvailable` 派生，不得硬写。
   **✅ 已实施（2026-09-30，`e3b1554`）**：抽出纯函数 `buildTaskWorkerDeviceInfo(presence)`
   只补 worker 专属字段；真机复验 master 侧变为
   `pipeline_worker=False backend_id=[] caps=[] task_worker=True`（**三字段自洽**）。
   测试 150 passed，含「该红必须红」守卫（改回硬写版即失败）。

1b. **★ 实测暴露的既有问题：该设备 `nativeRuntimeAvailable` 恒为 false**（阶段 1 的**真正前置**）。
   ~~真机 logcat：`native 运行时未就绪（上报值=false）` 在 0.793s，而 `nativeloader`
   Load `libqlh_llama_jni.so` 在 0.817s；30s 后复查仍 false。~~
   **✅ 已修复（2026-09-30，android `bd52055`）**：启动路径在异步 runtime 状态刷新完成前就起
   task worker，此时 `_uiState.value.runtimeStatus` 为 `null`，而 payload 按
   `runtime?.nativeRuntimeAvailable == true` 求值 ⇒ 把它当成"不可用"**永久**写进首个 lease。
   修法：`null` 时用 `createPassiveRuntimeStatus(...)` **同步**探活一次。
   **真机复验（master `/api/cluster/nodes`）**：
   ```
   android-c3f9d855  pipeline_worker=True  backend_id=[llama_cpp]
                     capabilities=[forward_layers]  task_worker=True  app=0.1.8.3-debug
   ```
   ⇒ 与「三字段同源」（`e3b1554`）联合后，android **已能正确声明 `forward_layers`**，
   阶段 1 的能力门前置**已解除**。
   （对照修复前：`pipeline_worker=true` + `backend_id="llama_cpp"` + `capabilities=[]` 自相矛盾。）
2. **product 路径未发起 `stage_offer`**。全仓搜 `send_stage_offer` 无 master 侧调用点；
   现有入口是 `task_graph`（`execution_mode="task_graph"`）+
   `TASK_WORKER_EXPERIMENTAL_ENABLED`（默认 false，`config.py:361`）。
3. **开关与准入门**：v3 还需 `manual_stage_dispatch_enabled`
   （`task_worker_adapter.py:346` 由 `connected` 决定；`scheduler_task_worker.py:484` 用它拒收）。

## 2. 方案

### 阶段 0：先修 `capabilities` 映射（前置，独立可验证）

- 定位 `buildAndroidPresenceDeviceInfo` 的 `capabilities` 字段在 master 侧被落成 `[]` 的环节
  （重点查 `inference_service/peer.py` 的 presence/device_info 组装、`cluster_join` 的归一化路径）。
- 判据：`GET /api/cluster/nodes` 的 android 节点 `capabilities` 从 `[]` 变为 `["forward_layers"]`
  （与 `pipeline_worker: true` 自洽）。**该红必须红**：先写一个断言"同条件字段必须同取值的用例"。

### 阶段 1：让 product 路径把层段派给 android（核心）

两条备选实现路线，**建议 A**：

**路线 A（推荐）—— 在 `scheduler_pipeline` 内新增 stage 委派分支**
- 在 `_push_layer_config_to_clients_locked`（`:152`）的 `node_type == "pc"` 过滤旁，
  **新增**一条：`node_type == "android"` 且该 worker 的 v3 `stage_offer` 可用时，
  把它按 **relay/exempt 语义**纳入 `eligible_node_ids`，其层段由 stage 链路承载
  （而不是发 `LAYER_CONFIG`）。
- 理由：与既有 `relay_middle` 的做法同构 —— relay worker 也是"零层 + 由远端代跑"，
  已在 `_append_relay_assignments`（`scheduler.py:408`）落地并有三机验收证据。
  照此模式，android 只需在 `layer_assignments` 里声明它认领的层区间，
  实际执行走 stage offer。
- 改动面（预估）：`scheduler_pipeline.py`（过滤 + 委派）、`scheduler.py`
  （`_split_relay_nodes` 同位置加 android 分流）、`api_server.py`（开关贯通）、
  `task_worker_adapter`/`scheduler_task_worker`（把 stage 结果接回 pipeline 的 token 流）。
- 风险：**执行回路拼接**是主要风险 —— stage 返回的是 hidden/token 帧，
  要接回 `_run_pipeline` 的逐 step 循环；这是本路线大部分工作量所在。

**路线 B（更保守）—— 让 product 路径在 `execution_mode` 层转发到 task_graph**
- 当 `routing_preference=distributed_required` 且集群里只有 android 参与时，
  `_execute_chat_full` 内部改调 `_execute_task_graph_chat_with_slot`（已验证的 v3 链路）。
- 优点：不新写执行回路，直接复用 v3 全链（协议/适配上文 §1.2 已具备）。
- 缺点：需要在 `api_server` 加一处显式分流，且要处理"PC + android 混合"时的拓扑选择。

### 阶段 2：真机证据

沿用已固化的真机链路（`scripts/android_validation.py` 已支持 `am start` + logcat 证据）：
- 模型分片请求（层段确实下发到 android）
- 连续生成（≥32 decode，判据 per-token argmax）
- 取消（ABORT）
- 断线/重连
- 热/电量采样（`thermal_status` 已在 `buildAndroidPresenceDeviceInfo` 里上报）

## 3. Phase 1 Route A implementation status (2026-10-01)

Route A is now wired as a fail-closed control/data contract, with a stage-only
execution path for the master-prefix plus Android chain:

- Android `layer_forward` results include `hidden_out_f32` (little-endian raw f32, base64) together with `hidden_out_sha256`; the Android unit test covers the intermediate handoff payload.
- The task-worker control plane exposes `layer_stage_dispatch_enabled` separately from full-model dispatch. A healthy Android worker with `layer_forward` and an admitted `layer_ranges` capability is eligible without receiving legacy `LAYER_CONFIG`.
- `scheduler_pipeline` admits those Android nodes into the capacity candidate set and records `execution=stage_offer_v3`; it never publishes a legacy layer configuration to them. Readiness probes use the v3 provider and advertised range.
- `_execute_layer_stage_offer` and `_layer_stage_result_to_pipeline_value` define the stage-to-pipeline-step bridge. The bridge validates hidden dimensions and SHA-256 before returning a Torch tensor or tail `token_argmax`.
- A stage-only chain now runs both prefill and decode through v3 offers, with explicit `seq_ids/positions` and master KV state. Mixed legacy/v3 chains remain fail-closed under `route_a_mixed_legacy_execution_bridge_not_ready`.
- Android intermediate results now preserve the full `[n_tokens, n_embd]` hidden batch. Returning only the last prefill row would build an incomplete downstream KV cache and is explicitly covered by Kotlin parity tests.

Phase 1 acceptance still requires a real two-node prefill plus at least two decode steps through this bridge, with matching `model_identity`, hidden digest, layer handoff, and KV position semantics. The code path is now executable, but the current environment has not produced that real-device acceptance evidence yet.

## 3.1 2026-10-01 真机复核与 fail-closed 修复

- Y700 已通过 v3 `hello` 上报 `stage_types=[layer_forward]`、`layer_ranges=[[4,16)]`、`resource_gate.admitted=true`。master 的 `worker_protocol` 与 `pipeline-capacity` 均可观察到这份能力合同。
- Android 的可用内存从 `device_info.memory.available_bytes` 投影到容量规划器；此前只读取 PC 的 `ram.available_gb`，会把已准入的 Android 节点错误排除。
- 容量规划器现在把 `layer_ranges` 作为执行合同：assignment 必须完全落在节点广告区间内；若区间无法连续覆盖请求，会返回 `pipeline_layer_range_coverage_insufficient`，不会再生成错误的 `[1,24)` 计划。
- 当前实测 qwen3_5 descriptor 为 24 层，而 Y700 只广告 `[4,16)`。master 加该 Android 节点没有覆盖 `[0,24)` 的 Route A 拓扑，因此当前真实请求仍应拒绝，不宣称 prefill 或 decode 验收通过。
- 拓扑与身份对齐已定：采用 Android 尾段 artifact（master `[0,4)` → Android `[4,16)` → Android `[16,24)`），`model_identity` 采用源指纹加转换可复现规则。见 [安卓层段拓扑与跨格式身份对齐决策](安卓层段拓扑与跨格式身份对齐决策-2026-10-03.md)。
