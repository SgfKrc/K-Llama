# 重构模型目录、工件与能力 R2

> 状态：**现行**（R2软件门完成）
> 更新日期：2026-10-18
> 适用范围：`REFACTOR-CATALOG-01` 的模型身份、目录写入、工件库存、引擎能力与纯容量规划软件门。完整部署事务、实际 runtime 回执和新发行物设备门分别由 R3、R4、R6 接续。

## 1. 事实归属与兼容入口

模型别名的唯一发布 owner 为 [catalog.py](../src/qlh_core/control/catalog.py)`CatalogService`，版本推进与 payload 身份校验均由该服务决定。[catalog_repository.py](../src/qlh_core/adapters/catalog_repository.py)`SqliteCatalogRepository`在同一 SQLite 写事务内核对版本并提交。[local_store.py](../src/local_store.py)`publish_local_model_registry`及旧兼容入口代理至该 owner，`RuntimeServices.catalog`通过所属`RuntimeLocalStore`的连接端口隔离实例。

`model_registry_versions`独立保存每个别名的单调版本；删除保留版本，重建继续推进，旧版本无法通过删除／重建形成 ABA。`RegistrySnapshot`为递归不可变快照；公开列表继续返回兼容字典，字典投影携带不序列化的 CAS token。无版本的`save_local_experimental_model`仅接受首次插入；生产更新均使用开始工作时冻结的版本。plain dict 的旧 payload CAS 兼容口只保证 payload 比较，新调用方使用显式版本。

[model_download_jobs.py](../src/model_download_jobs.py)`create_job/_register`、[routes_models.py](../src/api/routes_models.py)`register_model`、[model_supply_sources.py](../src/model_supply_sources.py)`_registered/_save`和[import_model.py](../scripts/model_tools/import_model.py)`register_model`共用该发布规则。手工注册遇到并发修改返回`MODEL_REGISTRY_CHANGED`。下载发布后登记失败保留目录，在持久任务的`target/error`中记录`cleanup_pending`；CLI输出相同的恢复回执。回收由R3供给owner统一处理，避免catalog引用检查与删除之间的并发窗口。`publish_registration_manifest`采用原子创建，相同证据幂等，目录已绑定其他修订时返回`MODEL_MANIFEST_CONFLICT`并保留原件。

## 2. 模型修订与本地库存

[catalog.py合同](../src/qlh_core/contracts/catalog.py)`ModelRevision`冻结谱系、架构维度、源权重、manifest、tokenizer与模板摘要；`ArtifactRef`独立绑定格式、字节摘要、量化、层段、组件和源修订。跨格式通过`EquivalenceProof`连接各自摘要，等价证明纳入修订身份。

[artifacts.py](../src/qlh_core/adapters/artifacts.py)`ArtifactStore`管理注册与验证分离的库存回执。`DiskInventory`验证磁盘字节，`SafInventory`通过注入的`DocumentPort`分别核对 grant、locator 和实际内容；授权成功仅证明可访问。`ResolvedArtifact`将模型修订、精确工件、本地位置与验证回执冻结在一起。

[services.py](../src/qlh_core/bootstrap/services.py)`RuntimeServices`持有同实例的`ArtifactStore`与`CatalogLoadGuard`，通过[model_host.py](../src/model_host.py)`configure_catalog`接入主host、延迟创建的manager、GGUF候选及stage host。[api_server.py](../src/api_server.py)`_get_layer_stage_host`代理所属runtime的同一stage host。配置目录校验端口保持延迟构造语义，首次配置和能力读取均无需物化torch manager。

[model_module.py](../src/model_module.py)`ModelManager._registry_load_identity`包含builtin覆盖记录；`_artifact_load_identity`绑定本地元数据变化。[llama_engine.py](../src/llama_engine.py)`get_pipeline_descriptor`按当前工件修订解析tokenizer。身份快照读取只检查元数据，字节验证放在工件准入边界。两种引擎的`load_layer_range`在元数据／权重加载前复核准备时冻结的`ResolvedArtifact`；别名替换或删除返回`artifact_revision_mismatch`，拒绝后保留原绑定，后续重试继续拒绝。

GGUF源文件通过目录校验后，`_find_layer_artifact`独立核对裁层manifest的源摘要、范围和实际工件摘要，内部物化入口仅接收通过校验的裁层路径。该路径在测试中只物化指定segment；源文件保持身份与描述器用途。对应生产组合、双runtime隔离、篡改及重试反例见[test_refactor_catalog_loading.py](../tests/test_refactor_catalog_loading.py)。

## 3. 旧注册表迁移

[LegacyRegistryImporter](../src/qlh_core/adapters/artifacts.py)`dry_run/import_registry`逐行检测 schema、损坏元数据、目标冲突和工件身份，输出来源与计划摘要、影响清单、工件引用字节及元数据空间估算；`verify_import_report`可重新核验报告完整性。工件保持原位置，runtime／selected／ready字段在导入前剔除。坏条目保留原件并具名拒绝，其余条目独立规划。

入口为[migrate_model_catalog.py](../scripts/migrate_model_catalog.py)`main`。默认 dry-run 只读源和目标，目标目录尚不存在时保持不存在。SQLite源使用无待处理 WAL 的离线快照；在线库先导出 JSON 或 SQLite 快照。导入要求既有 dry-run 报告，并重查源内容、目标版本和库存；目标已存在同名别名时保留目标记录。

```powershell
python -B scripts/migrate_model_catalog.py legacy-models.json --sqlite-path state/catalog.sqlite3 > catalog-review.json
python -B scripts/migrate_model_catalog.py legacy-models.json --sqlite-path state/catalog.sqlite3 --apply --review-report catalog-review.json
```

## 4. 引擎能力合同

[engines.py](../src/qlh_core/contracts/engines.py)`ENGINE_REGISTRY`按 family × runtime kind × operation定义格式、架构、精度、I/O、native ABI与优化约束。动态 probe通过`narrow`仅收窄可用操作。旧`_BACKEND_CAPABILITIES`和`ENGINE_CAPABILITIES`为共同定义的派生投影。

llama.cpp binding、keep-head、Android native和llama-server为不同runtime；server仅提供整请求。`model_load_resolver.resolve_model_load`、[task_worker_capabilities.py](../src/task_worker_capabilities.py)`build_engine_capabilities/node_supports_forward_layers`共用该schema。未知ABI、路径不一致及缺少具体执行证据的节点保留解码兼容性，层段准入具名收紧。

PC与Android使用相同的[engine-capabilities-v1.json](../fixtures/engine-capabilities-v1.json)；Android的[EngineRegistry.kt](../android/app/src/main/java/com/qlh/inference/worker/EngineRegistry.kt)、`AndroidWorkerCapabilities`和`TaskWorkerProtocol`同步编解码与白名单。能力 fixture 通过真实builder与validator检查，包含server过度声明和未知ABI的反例。

[scheduler_task_worker.py](../src/scheduler_task_worker.py)`_task_worker_capabilities`区分已登记层段和可执行操作。缺少该架构的层段runtime时保留工件诊断，并收窄整请求声明；`_task_worker_full_model_identities`要求`full_inference`能力，`aggregate`诊断入口和局部工件均不授予整模执行身份。

## 5. 纯容量与加载规格

[capacity.py](../src/qlh_core/planning/capacity.py)`solve_pipeline_capacity`仅消费显式输入，保留旧[pipeline_capacity.py](../src/pipeline_capacity.py)为代理。`capacity_budget`统一产生 required／available／reserved／shortfall；required包含预留，available为预留前的空闲采样，KV预算属于预留的一部分。准入和排除原因使用相同计算。

[load.py](../src/qlh_core/contracts/load.py)`RuntimeLoadSpec`冻结device、dtype、quant、context、KV、组件及物化策略，提供规范序列化和摘要。[worker_prepare_contract.py](../src/worker_prepare_contract.py)`validate_load_spec`校验完整文档与identity摘要、context一致；[EngineHost](../src/inference_service/engine_host.py)`_build_worker_runtime/_build_supplied_layer_manager`对携带spec的PC命令按冻结策略物化并核对device／dtype。

R3负责协商后逐assignment强制spec、传播stage identity和核对实际回执。缺spec的旧命令保持原兼容路径，F06 strict xfail继续跟踪该迁移。完整部署／供给事务及已发布工件的自动回收与清理债务归R3；真实Android SAF平台适配及新版本三机LL／DL验收由后续客户端与设备门执行。

控制权回归另将[cluster_auto_role_runtime.py](../src/cluster_auto_role_runtime.py)`HTTPRemoteVoter`改为直接连接配置的peer，避免下载代理或进程级urllib opener影响集群RPC。独立worker测试入口显式打开`AppRuntime`身份后构造Scheduler，不再依赖导入配置时读取凭据。
