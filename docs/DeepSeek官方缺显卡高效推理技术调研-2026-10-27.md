# DeepSeek 官方「缺显卡条件下高效训练/推理」技术调研

> 状态：调研报告（外部技术，非 QLH 实测）
> 日期：2026-10-27
> 对象：QLH 三机异构串行推理（Qwen3.5-9B，32 层，[0,8) CUDA / [8,24) 本机 CPU / [24,28) y700 / [28,32) Surface）
> 证据等级：`[官方文档]` 官方仓库 README／官方技术文档；`[论文]` arXiv 报告；`[实测数据]` QLH 或官方公开运行数据；`[推测]` 本文推算或工程判断

## 0. 一页结论

1. DeepSeek 官方在「算力受限」上的核心资产是**系统层**而非模型层：FP8 混合精度训练、DualPipe、DeepEP、DeepGEMM、FlashMLA、3FS 这一套，目标是把 H800（NVLink 带宽约为 H100 一半）这类"被削减的卡"用满。这与我们的处境同构，但**规模差 3 个数量级**（2048 卡 vs 4 台设备），直接搬运的只有方法论。
2. 对我们**最直接可用**的是官方《V3/R1 推理系统概览》里的三条工程决策：prefill/decode 分离、EP 承载大 batch、通信完全藏进计算。前两条我们做不到（模型不是 MoE、batch=1），第三条恰好指向我们真正的问题：**串行链路上没有任何可重叠的独立工作**。
3. **DualPipe 不能降低单请求首 token 延迟**，数学上必然如此（关键路径 = Σ各段耗时，与调度无关）。它只在"同时有 ≥ R 个独立工作单元"时有效，我们推到判据 `R > (k-1)/(u-1)`（§2）。
4. **MLA 的 93.3% KV 压缩对我们的 CPU 段内存带宽几乎零收益**：CPU 段的瓶颈是每 token 读一遍 8 层权重（batch=1 复用率为 1，约 1.3 GB/token），短上下文下 KV 读量只有它的 1/20–1/5（§3）。可借鉴的是它的"低秩 latent + 只缓存压缩态"思想，用于跨段传输和 KV 量化，不是照搬 MLA。
5. 我们的供给链路实测（local_cut 58.7 s vs distribute 628 s，10.7×）说明**内网有效带宽是数量级瓶颈**，3FS 那套 RDMA+SSD 聚合的前提在家庭/办公网络里不存在；值得学的是"共享存储 + 版本化缓存 + 就近读"，不是它的架构（§1.6）。

## 1. 逐项核实

### 1.1 DeepSeek-V3 / R1 技术报告

**MoE 稀疏度**：V3 总参数 671B，每 token 激活 37B，稀疏比 **18.1×**（671/37）；256 路由专家 + 1 共享专家，top-8 路由，61 层；14.8T token 预训练；全流程 **2.788M H800 GPU-hours**（预训练 2664K + 长上下文 119K + 后训练 5K），按 $2/GPU-hour 计约 $5.576M；2048 张 H800 上每万亿 token 约 180K GPU-hours（3.7 天）。`[论文]` <https://arxiv.org/abs/2412.19437>

**MLA 的 KV 压缩**：官方给出的量化说法在 V2 报告：相对 DeepSeek 67B（MHA）**KV cache 减少 93.3%，最大生成吞吐提升 5.76×**，训练成本降 42.5%。`[论文]` <https://arxiv.org/abs/2405.04434>。V3 沿用 MLA，机制上只缓存压缩 latent `c_t^KV` 和带 RoPE 的解耦 key `k_t^R`，不缓存完整 K/V（V3 §2.1.1 原文）。`[论文]`

> **注意基线**：93.3% 是对 **MHA** 的压缩率。按 V3 配置（d_c=512、RoPE 维 64、61 层、bf16）推算，每 token KV 约 576×2×61 ≈ **70 KB**；若换成 Qwen 系常见的 GQA（8 KV heads × 128 × 32 层），每 token 已只有 ~128 KB。也就是说 **MLA 相对 GQA 只能再省 ~3.5×，不是 15×**。`[推测，按公开维度推算]`

**无辅助损失负载均衡**：给每个专家一个可在线更新的 bias 加在路由 logits 上，按观测负载调整，避免传统 aux-loss 对语言建模目标的干扰；V3 还加了 sequence-wise 辅助损失和 node-limited routing（每 token 最多分发到 4 个节点）以限制通信量。`[论文]` 对我们的意义：**我们没有 MoE，此项不可迁移**，但"用推理期可调偏置代替训练期硬约束"的思想，可用于我们的层段切分热调整（见 §5 P2）。

**FP8 训练**：大部分 GEMM 用 **E4M3**；激活按 **1×128 tile**、权重按 **128×128 block** 做细粒度 scaling 抑制离群值；主权重与优化器状态保持 BF16/FP32；每 128 个元素的部分和提升到 CUDA core 做高精度累加；**不需要 loss scaling**（E4M3 指数范围足够）；embedding、输出头、MoE gating、归一化、attention 等敏感算子保持 BF16。`[论文]`（V3 §3.3）

> V3 报告没有给出"FP8 vs BF16 精度损失百分比"的单一数字（附录 B 只做 loss 曲线对比），**未找到公开的量化误差数值**，不要引用"误差 <0.25%"这类流传说法。

**DualPipe**：双向流水，把 micro-batch 从两端同时灌入，使前向与反向的通信/计算完全重叠。官方仓库给出的气泡公式（k 段、偶数）：

| 方法 | 气泡 | 每设备参数 | 每设备激活 |
|---|---|---|---|
| 1F1B | (k−1)(F+B) | 1× | k |
| DualPipe | (k/2−1)(F&B+B−3W) | 2× | k+1 |

`[官方文档]` <https://github.com/deepseek-ai/DualPipe>。代价是**每设备参数与激活翻倍**——这在 8GB 显存的 4060 上直接不可行，何况我们做的是推理而不是训练（§2）。

**R1**：纯 RL 激励推理能力，架构与 V3 同源（671B/37B），本身没有新的推理系统贡献。`[论文]` <https://arxiv.org/abs/2501.12948>。它对我们的真正影响是**输出 token 数大幅增加**（长 CoT），即 decode 阶段占比更高——这恰好是我们最弱的环节。

### 1.2 官方《V3/R1 推理系统概览》——最相关的一手材料

这是 DeepSeek 唯一系统性地讲"如何用有限 H800 做高效在线推理"的官方文档。`[官方文档]` <https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md>

关键数字与机制（均为官方原文）：

- **Prefill**：routed expert EP32 + MLA/共享专家 DP32，部署单元跨 4 节点，32 个冗余专家，每 GPU 9 个路由专家 + 1 共享专家。
- **Decode**：routed expert **EP144** + MLA/共享专家 DP144，跨 **18 节点**，每 GPU 仅 2 个路由专家 + 1 共享专家。
- 由于 256 专家只激活 8 个，**必须把全局 batch 做得极大**才能让每个专家有足够 token——这是"稀疏模型反而需要更大 batch"的反直觉结论，也解释了为什么 batch=1 场景下 MoE 的稀疏优势在延迟上不成立。
- **通信重叠**：prefill 用双 micro-batch 交替；decode 把 attention 拆成两步、用 **5 级流水**实现无缝重叠。
- **精度分工**：矩阵乘与 dispatch 传输用 FP8（与训练一致），**core MLA 计算与 combine 传输用 BF16**。
- **实测服务数据**（2025-02-27～28，24h）：峰值 278 节点、均值 226.75 节点（每节点 8×H800）；输入 608B token（其中 342B，即 56.3% 命中磁盘 KV cache）；输出 168B token；**单用户平均 20–22 tok/s**；平均 KV 长度 4,989 token；**每节点** prefill 吞吐约 73.7k tok/s、decode 约 14.8k tok/s；按 $2/GPU-hour 计日成本 $87,072。`[实测数据]`
- 成本结构上还有一个我们永远学不来的点：**白天全量推理、夜间把节点还给训练**，用削峰填谷把闲置算力变现。

对我们的启示（按重要性）：① 他们把"KV cache 落盘 + 56.3% 命中"当成一等公民，我们连跨请求的 prefix 复用都还在做；② decode 的 5 级流水本质是"把一个 token 的计算切成更细的段"，段数越多越能藏通信——但前提是**批里有很多 token 可填**；③ 每节点 14.8k tok/s 的输出意味着单请求 20 tok/s 是"用吞吐换延迟"的产物，与我们的单请求串行目标不同。

### 1.3 DeepEP（专家并行通信库）

定位：MoE dispatch/combine 的 **all-to-all** 专用 kernel 库，高吞吐与低延迟两类 API 已统一到 `EPBuffer` 接口，支持 FP8 dispatch（x 传 `[data, scale_factors]`），节点内 **NVLink**、节点间 **RDMA**，混合/直连两种模式，SM 与 QP 数量按拓扑解析式估算（不再自动调参），当前版本要求 Hopper 及以上 GPU、NCCL ≥ 2.32.3、CUDA ≥ 13.1，kernel 由 DeepJIT 在运行时编译。README 明确：**EP dispatch/combine 需要占用 GPU SM，不支持 zero-SM RDMA EP**。`[官方文档]` <https://github.com/deepseek-ai/DeepEP>

**可迁移性：低。** 我们没有专家、没有 RDMA、没有 NVLink；且 DeepEP 要的是"同一批 token 打散到多卡上的专家"，我们是"同一批 token 顺序穿过 4 台设备"，通信模式完全不同（all-to-all vs 单链 handoff）。

**唯一可借**：它的低延迟模式设计目标——"小消息、低 SM 占用、与计算异步重叠，用 `EventOverlap.wait()` 把等待点推迟到真正需要结果的地方"。这与我们"层段 handoff 的 RTT 无法隐藏"形成对照：我们的每次 handoff 都是**同步等待**，没有可插入的独立计算（源码侧见 [异构推理吞吐瓶颈与外部技术调研](异构推理吞吐瓶颈与外部技术调研-2026-10-24.md) §2.3 的 host 执行锁）。

### 1.4 DeepGEMM

- FP8（及后续 FP4/BF16）GEMM 库，**DeepJIT 运行时编译**，安装时不需要 CUDA 编译；NT/TN/NN/TT 多种布局（SM90 仅 NT）；grouped GEMM 只沿 M 轴分组（N、K 固定），另有 masked grouped GEMM 服务 decode（CUDA Graph 下 CPU 不知道每专家收到多少 token）。
- **细粒度 scaling**：SM90 要求 FP32 scaling 因子并按 TMA 对齐转置布局，SM100 要求打包成 **UE8M0**（4 个塞进一个 int32）；转置与 FP8 cast 由调用方另行处理（说明"量化本身不是免费的"，要融进前一个 kernel）。
- 性能：2025-04-18 起在 H800 上最高 **1550 TFLOPS**；2026 版把 EP dispatch、两个线性层、SwiGLU、combine 融进一个 **Mega MoE** kernel，重叠 NVLink 通信与张量核心计算。`[官方文档]` <https://github.com/deepseek-ai/DeepGEMM>

**可迁移性：低（硬件）/ 中（思路）。** 我们没有任何 Hopper/Blackwell 卡，4060 是 Ada（SM89），拿不到 FP8 tensor core 的完整收益，且跨框架（pytorch + llama.cpp）无法共享 kernel。**可借的是"算子融合 + 量化融进上游 kernel"**：我们每段入口都有 f32→量化→f16 的转换（`_hidden_to_raw_f32`、binary hidden codec），按 DeepGEMM 的做法应把这些转换融进上一段的输出 kernel，而不是单独一趟内存读写。

### 1.5 FlashMLA

- 最初（2025-02）是解码阶段 MLA 的专用 kernel，**分页 KV cache（block size 64）**，靠"按页调度 + 变长序列切分"把 attention 做成访存受限下的高带宽 kernel；后续加入 FP8/FP4 KV cache、token 级稀疏（DSA，DeepSeek Sparse Attention）、融合 norm-RoPE-attn-RoPE-cast 的单 kernel。
- 公开口径：2025-04-22 版本在 H800 SXM5 上计算受限场景最高 **660 TFLOPS**；V3.2 稀疏版 prefill 640 TFLOPS、decode 410 TFLOPS；B200 上融合 kernel prefill 1460 / decode 950 TFLOPS。`[官方文档]` <https://github.com/deepseek-ai/FlashMLA>
- 首版发布时的"3000 GB/s、580 TFLOPS"是 H800 上的**访存受限/计算受限**两组上界，已被后续版本数字取代；本文以当前 README 为准，**不复述旧数字**。

**可迁移性：低。** 我们没有 Hopper，也没有 MLA 模型；llama.cpp 的 attention 已自带 paged KV 与量化。**可借**：block=64 的分页粒度对"CPU 段按页换入 KV"是可用的经验值；以及"把 Q-norm/RoPE/cast 融进 attention kernel"的融合边界划定方法。

### 1.6 3FS / Fire-Flyer 文件系统

架构：分离式（无状态元数据 + FoundationDB 事务 KV）、CRAQ 强一致、FUSE 文件接口、面向 dataloader/checkpoint/KV cache 四类负载。性能：180 存储节点（每节点 2×200 Gbps IB + 16×14 TiB NVMe）、500+ 客户端（各 1×200 Gbps）下**聚合读 6.6 TiB/s**（含训练后台流量）；GraySort 110.5 TiB / 30 分 14 秒 = 3.66 TiB/min；**KV cache 读峰值 40 GiB/s**。`[官方文档]` <https://github.com/deepseek-ai/3FS>

换算一下：6.6 TiB/s ≈ 7.26 TB/s ÷ 180 节点 ≈ **40 GB/s/节点 ≈ 323 Gbps**，约为单节点 400 Gbps 网卡的 **81%**——这是"用 RDMA 把几千块 NVMe 拼成一层"的极限工程。

**对我们的供给链路：借鉴价值在"缓存层"而非"文件系统"。** 我们的实测是 local_cut 58.7 s、distribute 628 s（10.7×）。若段权重量级在数 GB，628 s 对应有效带宽只有**个位数 MB/s**（`[推测]`，需用实际字节数校正），这与 3FS 的单客户端 200 Gbps 差 **3–4 个数量级**。结论：**在现有内网下不要指望"从内网收段"作为稳态供给**，应把它降级为冷启动兜底；主线是本地一次裁层 + 版本化缓存 + 增量 diff。3FS 真正可搬的是两条：① KV cache 可以当"共享存储层"用（我们对应的是 prefix 缓存落盘）；② 元数据与数据分离、客户端就近读——我们对应的是"每台设备保留自己那段权重的本地副本 + 内容哈希校验"，而不是每次全量拉取。

### 1.7 官方对硬件的诉求（V3 §3.5）

V3 报告专门写了一节 "Suggestions on Hardware Design"，包括通信硬件（更低延迟、更高带宽的互连）与计算硬件（**更高的 FP8 GEMM 累加精度**、**tile-wise/block-wise 量化支持**、**online quantization 支持**、**转置 GEMM 支持**）。`[论文]` 这条对我们有现实意义：官方是在说"通用 GPU 缺这些特性，所以我们才要手写 kernel 绕过"。我们的 4060/Iris Plus/手机 SoC 缺得更多——**不要指望在这些设备上复现 DeepSeek 的 kernel 级效率，只能在算法层（量化、稀疏、缓存、调度）取收益**。

## 2. 专项：DualPipe / 流水线并行对「当前串行执行」的可用性

### 2.1 先厘清对象

我们现在的执行是 **layer-partitioned serial**：token 依次穿过 4 段，每段算完把 hidden states 交给下一段，**没有任何两个段同时在算不同的工作**。这与 DualPipe 解决的"训练时前向/反向 micro-batch 交错"不是同一个问题，但共享同一个数学骨架：**把一个任务切成 k 段，段间有依赖**。

### 2.2 单请求 TTFT 不可能被流水化降低

设第 i 段单 token 计算时间 t_i，段间传输/协议开销 τ_i，k=4。串行单 token 延迟：

```
T_serial = Σ(t_i + τ_i)
```

任何流水调度都无法让一个 token 跳过任何一段，所以 **首 token 延迟 = Σt_i + Στ_i + 排队**，下限就是这个和。把 pipeline 引进来，只会增加 handoff 次数（k−1 次同步点），对 batch=1 **净变慢**。这不是实现问题，是依赖图的拓扑性质。

**因此：DualPipe 对我们的 decode 阶段（batch=1、每步 1 token）价值为零，甚至为负。**

### 2.3 有效条件：并发工作单元数 R

流水只有在"同时有 R 个互不依赖的工作单元"时才有意义。设 k 段、各段总时间 Σt，最慢段 T_max = max(t_i)，定义**不均度 u = Σt / T_max**（各段等长时 u=k，越不均 u 越接近 1）。

R 个请求流水执行的总时间 ≈ (k + R − 1)·T_max；串行执行 ≈ R·Σt。加速比：

```
S(R) = R·Σt / ((k+R-1)·T_max) = R·u / (k+R-1) > 1
  ⟺  R > (k-1) / (u-1)
```

代入我们的形态：k=4；若 CPU 段（y700 + Surface 共 8 层）确实占大头，取 u≈2.5（最慢段约占 40% 总时延），则 **R > 2**，即 3 个并发请求才开始赚钱，R=4 时 S≈**1.43**；若 u 只有 1.5（四段比较均衡），要 **R > 6** 才为正收益。`[推测，公式推导]`

而且 S(R) 是**吞吐**加速比，**不是延迟加速比**：每个请求的 TTFT 仍是 Σt，还会因为排队更差。这正是官方推理系统"单用户 20–22 tok/s、靠 EP 大 batch 换总吞吐"的取舍。

### 2.4 传输/计算判据：τ 会不会把收益吃光

流水化会把 handoff 次数从每请求 1 次变成每 chunk 1 次。以 prefill 分块（m 个 chunk）为例：

```
串行:  T = m·Σt
流水:  T = (m + k - 1)·(T_max + τ)   （τ 为最慢链路的单次传输+协议开销）
加速>1 ⟺ m·Σt > (m+k-1)(T_max + τ)
m→∞ 时 ⟺ Σt - T_max > τ
```

即：**只有当"除最慢段之外的所有段的时间之和"大于一次跨段传输开销时，流水才可能正收益**。这条判据非常苛刻，因为我们最慢的段恰恰在弱机链路上（y700 / Surface 一侧）。

用我们的两个实测反推量级：distribute 628 s vs local_cut 58.7 s，若段权重为数 GB，则内网有效带宽约 **8 MB/s 量级**（`[推测]`，需校正）。在这个带宽下，1000 token 的 f32 hidden（h=4096 时约 16 MB）单次传输就要 **约 2 s**，而 CPU 段算 1000 token 的 prefill 大概率在百毫秒量级——**τ >> t，流水加速被传输完全吃掉**。反过来，若把 hidden 改成 f16/bf16 并启用 binary 帧（内部已有实现，见 [二进制hidden帧](二进制hidden帧-实现与验收-2026-10-20.md)），传输量减半，判据才可能翻盘。

### 2.5 结论与可做的实验

| 问题 | 结论 |
|---|---|
| DualPipe 能降低首 token 延迟吗 | **不能**，batch=1 单请求下数学上不可能；k=4 时（k−1）次同步点全是净开销 |
| 能提高总吞吐吗 | 能，条件是**并发请求 R > (k−1)/(u−1)**；按 u≈2.5 估算需 R≥3 |
| 值不值得做 | 先做**测量**：解掉 `NativePorts.prepare` 的 host 执行锁、让 R=4 个请求真并发，测 u 与 τ；若 u<1.6（此时需 R≥6 才为正）或 τ>Σt−T_max，直接放弃流水化 |
| 更划算的替代 | ① 减少段数/把弱机段合并到强机；② 降低 τ（binary 帧 + f16 + 合并 RTT）；③ 提高单段效率（量化、内核）；④ prefill 分块流水（只对长 prompt 有意义） |

**建议的最小实验**（成本低、可证伪）：固定模型与切点，构造 R=1/2/4/8 个相同长度的并发请求，记录总吞吐与每请求 TTFT；同时用 1 MB/8 MB/16 MB 的 dummy hidden 测一次真实 handoff 的 τ。把 u、τ 代入上面两式，**用数据决定是否立项**，而不是先写调度器。

## 3. 专项：MLA 的 KV 压缩比对「CPU 段内存带宽受限」有没有用

### 3.1 先算清楚量级

batch=1 decode 时，每段耗时近似由**权重读取**决定：

```
每层耗时 ≈ 该层权重字节数 / 该设备有效内存带宽
```

以 9B/32 层、Q4（约 4.5 bit/权重）估算：每层约 281M × 4.5/8 ≈ **158 MB**，8 层约 **1.27 GB**；若 CPU 段有效带宽 10 GB/s，仅这一段每 token 就要 **~127 ms**（≈7.9 tok/s），与 KV 无关。`[推测，按典型值估算，需用实际量化位宽校正]`

同期 KV cache：Qwen 系 GQA（8 KV heads × 128、bf16）每 token 每层 4 KB，32 层合计 **128 KB/token**。关键在 decode 时 attention 要读**全部历史 KV**，所以每步 KV 读量 ≈ 上下文长度 × 每层 4 KB，且只在拥有该层的段上发生（CPU 段 8 层）：

| 上下文 | CPU 段每步 KV 读量 | 对比该段权重 1.27 GB |
|---|---|---|
| 2k | 8 层 × 2k × 4 KB ≈ 64 MB | ~5% |
| 8k | ≈ 256 MB | ~20% |
| 32k | ≈ 1 GB | ~80% |

（按 bf16 KV 估算，`[推测]`）

也就是说：**短上下文下 KV 确实不是瓶颈；只有到 8k 以上、或 KV 用更高精度时，KV 压缩才开始与权重带宽同量级。**

而 MLA 压缩的是"K/V 的存储与读取"，**完全不减少权重读取**——所以它对我们"CPU 段内存带宽受限"的主因（权重 × batch=1 复用率 1）**零帮助**。

### 3.2 93.3% 不能直接套

- 那个数字的基线是 DeepSeek 67B 的 **MHA**。
- 我们的基线是 **GQA**：KV 已是 MHA 的 1/4（32 heads → 8 KV heads）。MLA 式低秩（d_c=512+64）相对 GQA 只能再省 ~3.5×（128 KB → ~36 KB/token，`[推测]` 按维度推算）。
- 换算成"每 token 省多少字节"：短上下文下 92 KB，相对 1.3 GB 权重是 **0.007%**。可以忽略。

### 3.3 真正可借鉴的三件事

1. **"只缓存压缩态"的分层缓存观**：MLA 不缓存 K/V，只缓存 latent，用时再上投影。对应我们：跨段只传 latent/降维后的 hidden（低秩投影后再过网），而不是原始 hidden；以及 KV 只保留量化后的页，用到再反量化。
2. **KV 量化**（FP8/INT8/INT4 KV cache）：这是 Qwen 系可直接用的。内部已有 `inference_switches.py` 的 KV 量化开关，但没有产品级收益证据（见 [异构推理吞吐瓶颈](异构推理吞吐瓶颈与外部技术调研-2026-10-24.md) §3）。**这才是"CPU 段省带宽"的正解**：省的是长上下文时的 KV 读流量。
3. **注意力与前后处理的融合边界**：FlashMLA 把 norm/RoPE/cast 融进 attention kernel；我们对应的是把 KV 量化的 dequant 融进 attention，而不是单独一趟。

### 3.4 一句话

**MLA 的压缩比对我们是"错位的解"**：它省 KV，我们缺的是权重带宽；它假设长上下文高并发，我们是短上下文 batch=1。真正该做的是权重低比特化 + 长上下文时的 KV 量化，而不是在 Qwen 上模拟 MLA。

## 4. 迁移性总表

| 技术点 | 解决什么问题 | 可迁移性 | 理由 | 落地代价 |
|---|---|---|---|---|
| V3/R1 MoE 稀疏（671B/37B） | 用稀疏激活换参数容量 | **低** | 模型非 MoE，无法改架构；且稀疏在 batch=1 时不利于延迟 | 不可行（换模型才谈得上） |
| 无辅助损失负载均衡 | 免 aux-loss 的专家均衡 | **低** | 无专家；仅"在线偏置调参"思想可用于切点热调整 | 低（若只借思想） |
| FP8 训练（E4M3 + 1×128/128×128 scaling） | 训练吞吐 ×2、显存减半 | **低** | 无 Hopper、无训练任务；4060 的 FP8 收益有限 | 高（需重训/校准） |
| FP8/INT8 推理量化（含 KV） | 降权重与 KV 带宽 | **高** | 与硬件无关，直接降 CPU 段每 token 字节数；已有开关与工具 | 中（校准 + 精度门 + 内核） |
| DualPipe 双向流水 | 藏通信、减气泡 | **低（decode）/ 中（prefill 分块）** | batch=1 无并发单元；仅在 R≥3 或长 prompt 分块时有意义 | 高（调度器 + 状态所有权） |
| 官方推理系统：prefill/decode 分离 | 两种负载用不同并行度 | **中** | 我们天然已是"层段串行"，但可把 prefill 与 decode 的切点/并行策略分开 | 中（两套部署配置） |
| 官方推理系统：5 级 decode 流水 | 把单 token 计算切细以藏通信 | **低** | 需要大量 token/批填满；我们是单 token | 高 |
| DeepEP all-to-all | MoE 专家通信 | **低** | 无专家、无 RDMA/NVLink | 不可行 |
| DeepEP 低延迟事件重叠 API | 把等待推迟到需要时 | **中** | 可借鉴其"异步提交 + 迟到等待"接口设计到 handoff | 中（改协议与状态机） |

| DeepGEMM 算子融合（Mega MoE） | 减 kernel 启动与内存往返 | **中** | 我们入口的 f32→量化→f16 转换应融进上游 kernel | 中（改 C++/llama.cpp 侧） |
| FlashMLA 分页 KV（block=64） | 解码期高效 attention | **低** | 无 Hopper、无 MLA；llama.cpp 已有 paged KV | 低（仅参考块大小） |
| FlashMLA 融合 norm/RoPE/cast | 省小 kernel | **中** | 同"算子融合"思路 | 中 |
| 3FS 聚合存储 | 训练数据/KV 的共享存储层 | **低（架构）/ 中（缓存策略）** | 需 RDMA + 数千 SSD；家庭网络差 4 个数量级 | 高 |
| 3FS KV cache 落盘 | 跨请求复用前缀 | **高** | 直接对应我们的 prefix 缓存与磁盘 KV | 中（已有基础） |
| 官方硬件诉求（FP8 累加/tile 量化/online quant） | 解释为何要手写 kernel | **中（认知）** | 提醒我们别在弱设备上追求 kernel 极限 | 无（仅指导） |
| MTP / 投机解码 | 提高单请求有效输出率 | **中** | 与 n-gram 投机同源，内部已有实现但当前负收益 | 中（状态合同） |

## 5. 落地建议（按性价比排序）

**P0（本周可做，纯测量）**
1. 测 u 与 τ：R=1/2/4/8 并发 + 1/8/16 MB dummy handoff，代入 §2.3/§2.4 两式。**先有数，再决定是否做流水**。
2. 把 hidden 传输从 f32 降到 f16/bf16 并开 binary 帧（内部已有），量化它对 TTFT 的贡献。这是"减少 τ"里最便宜的一刀。

**P1（2–4 周）**
3. 权重低比特化 + KV 量化（长上下文才开），用质量门验收；这是唯一能同时降 CPU 段与 GPU 段每 token 字节数的通用手段。
4. 供给链路改成本地裁层 + 版本化缓存 + 增量 diff，把 distribute 降到冷启动兜底；参照 3FS 的"元数据/数据分离"拆出清单校验与数据面。
5. 消除 `NativePorts.prepare` 的 host 全局锁，否则 R>1 的并发根本不存在，§2.3 的前提不成立。

**P2（观察项）**
6. prefill 分块流水：仅对长 prompt 有意义，需先满足 `m > (k−1)(T_max+τ)/(Σt−T_max−τ)`。
7. 切点热调整：借"在线偏置"思想，按实测段成本动态挪 1–2 层（如 Surface 与 y700 之间），但必须有精度门。
8. 常态化的 prefix/KV 落盘复用：对标官方 56.3% 的磁盘 KV 命中率。
