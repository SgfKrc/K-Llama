# CPU 上的大模型推理优化：技术调研与 QLH 落地判断（2026-10-27）

> 状态：**调研结论**，未改任何生产路径
> 对象：QLH 三机层段切分中的 CPU 段（master#cpu `[8,24)`、y700 `[24,28)`、Surface `[28,32)`）
> 方法：一手代码/文档（llama.cpp、ik_llama.cpp、OpenVINO backend、PowerInfer 论文）+ 本仓既有实测（22b、Surface 线程/KV 扫描、6.84 ms/层）
> 标注：`[官方文档]` `[实测数据]` `[社区报告]` `[计算]` `[推测]` `[未核实]`。**无公开数值处一律写明"未找到公开数值"，不做外推。**

## 0. 结论摘要

1. **CPU 段的 decode 是内存带宽问题，不是 FMA 算力问题。** 最硬的证据是一组 VNNI 内核实测：把 Q4_0/Q8_0 的矩阵乘换成 VNNI 指令后，prompt 处理（pp）涨 1.5–3.2×，而 token 生成（tg）几乎不变（1.00×）[社区报告，[PR #30036](https://github.com/ggml-org/llama.cpp/pull/30036)]。这直接决定了"该投哪"：**能提速 decode 的只有减少每 token 的字节数（降位宽、减层）或减少每 token 的访存次数，而不是换更宽的 SIMD。**
2. **我们现在的 CPU 二进制没有用到 Surface CPU 的 AVX-512/VNNI**（构建是 `GGML_NATIVE=OFF` → AVX2 基线）。补上这一档的收益主要落在 **prefill**；对每步只喂 1 个 token 的 layer-forward 路径预期接近 0 [推测，基于上一条]。
3. **上游 repack（交织布局）已经生效，且本仓已实测到 1.05–1.36×**（22b：0.5B pp 105.5→143.3、tg 22.9→27.6；2B pp 46.7→52.9、tg 13.6→14.3）[实测数据，[22b](archive/misc/22b-CPU内核候选-评估与验收-2026-10-20.md)]。这是当前唯一已兑现的 CPU 侧收益，不要再重复投入。
4. **`ik_llama.cpp` 的收益几乎全在 prefill**（Zen4 pp 平均 2.88×，TG 只有 1.0–1.4×）[社区报告，[ik wiki](https://github.com/ikawrakow/ik_llama.cpp/wiki/Jan-2025:-prompt-processing-performance-comparison)]。对"每 token 只算 1 行 hidden"的层段，换引擎的收益上限约等于那 1.0–1.4×，而移植 `layer_inp` 补丁的成本与数值门代价极高 → **不建议换**。
5. **低比特在 CPU 上"速度真实、质量有坑"**：TG 速度大致随 bpw 线性改善（Q2_K_S 18.70 vs Q4_K_S 13.24 t/s），但 IQ 系列因解包查表在 CPU 上 pp 慢 3–5×（IQ2_XXS pp 43.5 vs Q4_0 146.2）[社区报告，同上 wiki]。要降位宽就选 **Q3_K/Q2_K**，不要选 IQ2/IQ3。
6. **Surface 段存在硬地板**：该段工件 1.98 GB，decode 每 token 必须完整读一遍；按该类平台 30–40 GB/s 有效带宽，理论下界 **50–66 ms/token** [计算]。调参能拿到的上限约 1.3–1.5×，再往下必须改切分（减层/把 head 移走）或降位宽。
7. **Windows 集合（Surface）吃不到 NUMA/大页/绑核那一套**：`--cpu-affinity`、THP、`-dexp`/`-prexp` 都是 Linux-only [官方文档，[ik parameters.md](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/parameters.md)]。对这些不要排期。

## 1. llama.cpp 的 CPU 优化现状

### 1.1 支持的 SIMD 指令集与"真实"加速比

编译面（`ggml-cpu` 一次性支持全部档位，靠 CMake 开关 + 运行时分发）[官方文档，[ggml-cpu/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/CMakeLists.txt)]：

- x86：SSE4.2 / AVX / AVX2 / **AVX-VNNI**（Alder Lake 起的客户端，无 AVX-512 也有）/ **AVX-512**（F/CD/VL/DQ/BW）/ **AVX-512-VNNI** / **AVX-512-VBMI** / **AVX-512-BF16** / **AMX-TILE/INT8/BF16**；
- ARM：NEON 基线 + **dotprod** + **i8mm** + **SVE/SVE2** + **SME**，以及 **KleidiAI v1.32.0** 微内核（`GGML_CPU_KLEIDIAI=ON`，仅 aarch64）[官方文档，[docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)]；
- 另有 `GGML_CPU_ALL_VARIANTS`（一次打包多个 ISA 变体、运行时择优）与 `GGML_BACKEND_DL`。

代际加速比（有实测的部分）：

| ISA 档位 | 场景 | 实测加速比 | 来源 |
|---|---|---|---|
| AVX-VNNI（Core Ultra 7 155H，4 线程） | Q4_0 pp2048 / tg128 | **1.84× / 1.21×** | [PR #30036](https://github.com/ggml-org/llama.cpp/pull/30036) [社区报告] |
| AVX-VNNI | Q8_0 pp2048 / tg128 | **2.79× / 1.15×** | 同上 |
| AVX-512-VNNI（Ryzen 9 9950X） | Q4_0 pp2048 / tg128 | **1.68× / 1.00×** | 同上 |
| AVX-512-VNNI | Q8_0 pp2048 / tg128 | **3.24× / 1.00×** | 同上 |
| AVX-512（无 VNNI 的通用路径） | 相对 AVX2 | 上游"大部分仍未利用 AVX-512"（作者原话），未找到统一倍数 | [ik wiki](https://github.com/ikawrakow/ik_llama.cpp/wiki/Jan-2025:-prompt-processing-performance-comparison) [社区报告] |
| AMX（Sapphire Rapids+） | 仅 AMX CPU 编译启用，无消费级可用 | 未找到可迁移数值 | [官方文档 CMakeLists] |

要点：
- **上述 1.5–3× 全部是 prefill**；tg 一列是 0.99–1.21×。这就是"decode 内存受限"最干净的一组证据。
- **Ice Lake 客户端（Surface 的 i5-1035G4）属于 AVX-512 + VNNI 一代**（Ice Lake 是客户端首批带 AVX512-VNNI 的核心，服务器侧 Cascade Lake 更早）[推测/通用架构事实，**未找到 Intel ARK 页面的直接引用**]；本仓二进制是 AVX2 基线 → 这一档完全没吃到。
- 但按上表，**吃到也只对 prefill 有意义**（本仓 CPU 段只有 32–数百 token 的 prefill，且关键路径是逐 token decode）。
- 换 ISA 一定改归约 lane 顺序 → 按本仓既有结论必须重跑逐 token argmax 门 [实测数据，[跨框架接力数值差异机理](跨框架接力数值差异机理-2026-10-05.md)]。

### 1.2 GGUF 量化格式在 CPU 上的速度—质量权衡

8B 级模型、llama.cpp 本体、纯 CPU 的横向数据。**两列来自不同时间/不同机器**：pp 列是 LLaMA-3.1-8B @Zen4（2025-01），tg 列是 LLaMA-3-8B @AVX2（2024-07）——只看列内趋势，不要跨列做比值：

| 类型 | bpw | pp512（Zen4，t/s） | tg（AVX2，4 线程，t/s） |
|---|---|---:|---:|
| Q4_0 | 4.5 | **146.20** | 10.97 |
| Q4_K_S | 4.5 | 102.85 | **13.24** |
| Q5_K_S | 5.5 | 71.82 | 11.05 |
| Q6_K | 6.6 | 78.24 | 9.74 |
| Q2_K_S | ~2.98 | 115.23 | **18.70** |
| IQ2_XXS | 2.06 | **43.54** | 10.06 |
| IQ3_S | 3.44 | 28.96 | 6.80 |
| IQ4_XS | 4.25 | 70.67 | 13.36 |

来源：[ik wiki pp 表](https://github.com/ikawrakow/ik_llama.cpp/wiki/Jan-2025:-prompt-processing-performance-comparison) + [ik wiki tg 表](https://github.com/ikawrakow/ik_llama.cpp/wiki/July-2024:-Token-generation-performance-comparison) [社区报告]。

**为什么 K-quant 在 CPU 上不一定比 Q4_0 快（甚至更慢）？**
- **pp（compute-bound）**：Q4_0 的 block 是 32 权重 + 1 个 f16 scale，解包就是 `maddubs + madd` 两条 SIMD 指令；K-quant 每 256 权重一个 super-block、内含 6-bit 量化尺度与 4-bit 子尺度，解包要做多级移位/掩码/跨 lane 洗牌 → **同 bpw 下 Q4_0 的 pp 快 1.4×**（146.2 vs 102.9）。上游在 ARM 上甚至给 Q4_0 写了专门实现，使 ik 相对它只快 1.085× [同上]。
- **tg（memory-bound）**：两者字节数相同，K-quant 的 super-block 让尺度读取与行内局部性更好，反而更快（Q4_K_S 13.24 vs Q4_0 10.97）。**所以"tg 用 K-quant、pp 用 Q4_0"的取舍在 CPU 上确实存在**；QLH 只跑 decode，结论偏向 K-quant 或更低 bpw。
- **i-quant（IQ2/IQ3/IQ4_XS）**：用码本查表（LUT）+ 复杂解包，**pp 掉 3–5×**；tg 因为 bpw 低能追平 Q4_0，但并不比同字节的 Q2_K 快（IQ2_XXS 10.06 vs Q2_K_S 18.70 —— 后者 bpw 更高却快 1.86×，说明 IQ 在 CPU decode 上同样吃亏）。

质量侧：IQ2/IQ3 依靠 imatrix 才能把损失压住，K-quant 的 Q3_K/Q2_K 在不带 imatrix 时退化更明显 [官方文档，[ik parameters.md 的量化章节](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/parameters.md)]。**Qwen3.5-9B 在 Q2_K/IQ2 下的具体 PPL 增益/损失：未找到公开数值**，必须自己用本仓 `llama-perplexity` 在裁层工件上测，不能引用别的模型数字。

### 1.3 线程数：物理核、超线程与 `-t`

- ik 的官方建议：`-t` 默认 4，"尽量等于物理核数，避免奇数"；GPU 全卸载时 `-tb` 反而要降到 2 [官方文档，[parameters.md](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/parameters.md)]。
- 反例（为什么不能照抄）：**本仓 Surface 实测 8 线程最优**（4C8T）：8 vs 4 = 1.20×（ctx512）、1.28×（ctx2048）[实测数据，[KV/注意力调研 §7.9.1](archive/relay/KV缓存优化与注意力结构调研-GQA与MLA-2026-10-14.md)]。说明在**单请求、纯矩阵乘、无其他负载**时，SMT 的额外吞吐能覆盖争用成本。
- 反方向的坑：llama.cpp/ik 明确警告**线程过度订阅会显著变慢**（示例里 `-t 7` 在 7 物理核 + GPU 卸载下只有 1.7 t/s，`-t 4` 是 9.1 t/s）[社区报告，[token_generation_performance_tips.md](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/development/token_generation_performance_tips.md)]。QLH 的 master#cpu 与网络 I/O、Python 侧同机竞争，**每段都要单独标定，不能用一个全局值**。
- 同一文档还给了笔记本热降频实测：**CPU 推理 1–2 分钟后从 25–30 t/s 掉到 15–18 t/s**（95–100 °C）[社区报告，同上]。Surface 是 15W 平板，这个风险比台式机高得多。

### 1.4 memory-bound 还是 compute-bound：给一个可算的判据

单 token decode 的算术强度：`AI = 2·N / (N·b/8) = 16/b`（ops/byte，b 为 bpw）[计算]。
- Q4_K_M（b≈4.85）→ **AI ≈ 3.3 ops/byte**；
- 平台算力/带宽比：4 核 AVX2 @3.7 GHz ≈ 4×16 FLOP/cycle×3.7e9 ≈ 237 GFLOP/s，LPDDR4x-3733 双通道 ≈ 59.7 GB/s → **约 4.0 FLOP/byte**。
- ⇒ AI(3.3) < 平台比(4.0)：**decode 落在内存受限侧**；把 SIMD 宽度翻倍（AVX-512）只会把平台比抬到 8 FLOP/byte，内存受限更深，实测 tg 1.00× 正是这个结果 [计算 + 社区报告]。

prefill 完全不同：batch B 下 AI ≈ 16B/b，B=512 时 ≈ 1700 ops/byte → **compute-bound**，于是 VNNI 能拿到 1.5–3× [计算 + 同上 PR]。

本仓数据交叉验证：9B / 32 层 / Q4_K_M，每层权重约 `9.0e9/32 × 4.85/8 ≈ 170 MB`；实测 **6.84 ms/层**（i9-13900H，n_threads=8）[实测数据，[本机跨框架层段成本](本机跨框架层段成本与干扰实测-2026-10-25.md)] → 反推有效带宽 ≈ **24.9 GB/s** [计算]。这个数字远低于台式 DDR5 峰值，既说明"按字节计费"的模型成立，也说明**还有一部分时间不在纯带宽上**（图调度、KV 读写、线程同步），单看调参最多再挤出 10–20%。

### 2.1 PowerInfer 的思路对我们是否适用：**否**

- 机理：热/冷神经元分离，热神经元常驻 GPU、冷神经元在 CPU 算，靠**激活稀疏**跳过不活跃神经元。官方数据：RTX 4090 上量化模型平均 13.20 tok/s，相对 llama.cpp 最高 **8.00×（量化）/11.69×（非量化）**；前提是 OPT 类 ReLU 模型（稀疏 **97%**）[论文 §1、表 1]。
- 换到 Qwen 系：SwiGLU 的可动态剪枝稀疏只有 **LLaMA2-13B 43%、Yi-34B 53%** [论文表 1]，而"26%（OPT）/ 69%（LLaMA2-SwiGLU）的神经元承担 80% 激活"——**热集太大，拆分的收益基础就没了**。
- 结构上更致命：PowerInfer 是"整模前向 + 神经元级调度"，不提供"只加载 4 层并导出段末 hidden"的接口；而且它把 **CPU 当协处理器**，我们恰恰是要把 CPU 段本身做快。
- 结论：可借的只有"**batch < 32 时 CPU 直接算比搬去 GPU 快**"这条判据（论文图 6 实测）——它支持我们"把段留在 CPU"的既有选择，但不能带来新优化。

## 3. CPU 上的具体加速手段

### 3.1 KV cache 量化 / 分页：本仓已否证，不要再做

Surface 实测（qwen2.5-0.5B Q4_K_M，8 线程）：KV 量化在 CPU 上**更慢**；`kv_cache_seq_rm` 手动滑窗在 ctx=4096/prompt≈3000 时慢 **1.16–1.83×**，K 小时输出还会变 [实测数据，[KV 调研 §7.9](archive/relay/KV缓存优化与注意力结构调研-GQA与MLA-2026-10-14.md)]。原因：CPU 的 KV 反量化/重排开销 > 省下的 attention 时间。
配套结论：`n_ctx=8192` 比 2048 慢 **1.31×**（prompt 相同）→ **边缘段不宜配大 ctx**，4096 不亏 [实测数据，同上]。ik 侧同样只把 KV 量化当"省内存/长上下文"手段，Q8_0/KV 低比特需要 CPU FA 配套 [官方文档，[parameters.md](https://github.com/ikawrakow/ik_llama.cpp/blob/main/docs/parameters.md)]。

"分页"在 CPU 侧也要区分：llama.cpp 的 KV 是**统一 cell 池 + `seq_rm` 重排**，没有 vLLM 式块表/逻辑-物理映射；因此 vLLM 那套 PagedAttention 分页收益在 CPU 上无从谈起，而唯一的"分页"替代品（把 KV 放磁盘 mmap）会把每步 attention 变成随机 I/O。**CPU 侧分页实现：未找到公开的可用先例。**

### 3.2 算子融合与 CPU 版 flash attention

- 上游 CPU FA 在 2026 年仍活跃：例如"一个 chunk 的内核把 V 累加改成 F32"（[PR #29810](https://github.com/ggml-org/llama.cpp/pull/29810)）、"非向量整数倍 head dim 的 tiled FA（x86）"（[PR #29423](https://github.com/ggml-org/llama.cpp/pull/29423)）[社区报告]。它们改善的是**长上下文 prefill/大 batch**，对 4 层段、batch=1 的 decode 影响有限。
- ik 有独立的 CPU FA 内核与开关（PR #429 "Option to enable or disable the CPU FA kernels"、PR #332 "Better CPU FA token generation performance"）[社区报告，[README](https://github.com/ikawrakow/ik_llama.cpp)]——**这是 ik 唯一可能改善 decode 的部分，量级未公开，必须自测**。
- Qwen3.5 是 hybrid（`full_attention_interval=4`，每 4 层 1 层 full），本仓已量出"段内 full 层占比恒为 1/4"，无法用段对照分离 attention 成本 [实测数据，[KV 调研 §7.10](archive/relay/KV缓存优化与注意力结构调研-GQA与MLA-2026-10-14.md)]。

### 3.3 大页、NUMA、CPU 亲和性：**Surface 全部吃不到**

- llama.cpp 有 mmap 的 **MADV_HUGEPAGE**（THP）提示（[PR #22022](https://github.com/ggml-org/llama.cpp/pull/22022)）与 NUMA 策略（`ggml_backend_numa_strategy`，[绑定声明](https://docs.rs/llama-cpp-bindings/0.4.1/src/llama_cpp_bindings/llama_backend_numa_strategy.rs.html)），ik 侧有 `--cpu-affinity`（只 Linux）、`GGML_CUDA_HOST_MALLOC_THP`（只 CUDA host 分配）[官方文档，parameters.md]。
- Surface 是 **Windows 单 NUMA 节点 4C8T**：NUMA 无意义；大页需要 `SeLockMemoryPrivilege`，llama.cpp 不主动申请；绑核只能靠 `start /affinity` 或 PowerShell 处理器关联，**收益未验证** [推测]。
- 结论：这一整块对本项目 CPU 段（Surface/y700）**收益≈0**；master#cpu 同机 Windows，同样不成立。**不排期**。

### 3.4 权重内存布局（interleaved / blocked）：已在用，且是本仓唯一实证收益

- 上游 `ggml-cpu/repack.cpp` 把支持的量化类型在加载时重排成 8×8/4×4 交织块，走 `extra_buffer` 快路径（`GGML_CPU_REPACK`）[官方文档，CMakeLists]。机理：decode 的 GEMV 每读一个 cache line 只会用到其中少量 lane，交织让"8 行 × 同列区间"打包进连续块，使一次 line 填充服务 8 行点积、减少 line 数与 TLB 压力；本仓 22b 记录的 `block_q4_Kx8` 即 8-byte 交织、1152 B/块，普通代码不能直接消费。
- 本仓 22b 实测（i9-13900H，ctx256/batch16/ubatch16/4 线程）：repack ON/OFF 的 **pp 1.358×（0.5B）/1.132×（2B）、tg 1.208×/1.054×** [实测数据，[22b](archive/misc/22b-CPU内核候选-评估与验收-2026-10-20.md)]。代价是两条 K-quant 实现的数值差异：hidden 相对 L2 达 2.46% / 4.04%（已定性为设计内差异 #104）→ **每次动 repack/ISA 都要重过数值门**。
- ik 的 `-rtr` 是同类但更激进的运行时重排（且与 CUDA 组合有坑：k-quants 的重排布局无 CUDA 实现，会把计算留在 CPU）[官方文档，README 警告]。

## 4. 量化到更低比特（Q2/IQ2/1.58-bit）在 CPU 上可行吗

| 方案 | 速度（CPU） | 质量 | 结论 |
|---|---|---|---|
| **Q3_K_M / Q3_K_S** | TG 约 1.2–1.35×（相对 Q4_K_S），pp 略降 | 9B 级通常可接受，但需自测 PPL | **首选降位宽档** |
| **Q2_K / Q2_K_S** | TG **1.41×**（18.70 vs 13.24 t/s）[社区报告] | 明显退化，长上下文/代码任务更明显；需 imatrix | 可作容量兜底，不作默认 |
| **IQ2_XXS/IQ2_XS/IQ3_S** | **pp 慢 3–5×**，tg 不快于同字节 Q2_K（IQ2_XXS 10.06 vs Q2_K_S 18.70） | 需要 imatrix，CPU 上"省字节但费指令" | **不选** |
| **1.58-bit（BitNet b1.58）** | 只有三值专用模型 + bitnet.cpp/BitNet 专用内核才有意义 | 需要**重新训练**的模型，与 Qwen3.5-9B 不兼容 | 不适用（本仓 2026-10-14 已裁决）[实测/内部结论，[DeepSeek 与社区 CPU 成果调研](archive/relay/DeepSeek与社区CPU推理成果调研-能否当引擎后端-2026-10-14.md)] |

量化速度与位宽的关系在 TG 上基本服从"字节比"（Q2_K_S 2.78 GiB vs Q4_K_S 4.36 GiB = 0.638 → 1/0.638 = 1.57× 理论，实测 1.41×）→ 再次印证 **decode 按字节计费** [计算+社区报告]。**Qwen3.5-9B 的具体 PPL 变化未找到公开数值**；建议在本仓裁层工件上用 `llama-perplexity` 加同一批 wiki 文本对比 Q4_K_M / Q3_K_M / Q2_K，并把"逐 token argmax 一致率"一起记（降位宽必然改变数值，不能套用当前数值门）。

## 5. 给 Surface 7 Pro（4C8T + Iris Plus + 15.6 GB）的具体调参建议

现状（本仓事实）：段 `[28,32)`，工件 **1.98 GB**，llama.cpp CPU 后端，GGUF Q4_K_M，二进制为 **AVX2 基线**（`GGML_NATIVE=OFF`）；实测 `n_threads=8` 最优（1.20–1.28× vs 4 线程），`n_ctx` 4096 与 2048 几乎无差，KV 量化无效 [实测数据，[已知问题记录](已知问题记录.md#L60)、[KV 调研](archive/relay/KV缓存优化与注意力结构调研-GQA与MLA-2026-10-14.md)]。

建议组合（按优先级）：

1. **线程**：`-t 8 -tb 8`（= 逻辑核数），**不要**按"物理核 4"设。若与网络 I/O 同机竞争，改 `-t 6` 并复测；避免奇数（ik 建议）[官方文档 + 实测]。
2. **ubatch**：decode 阶段 batch=1，`-ub` 对 decode 无影响；但 **prefill 时 32–512 token 会走 `ubatch`**，用 `-ub 512`（本仓 7B 扫描：512 比更大 ubatch 快约 6%）[实测数据，[本机跨框架层段成本](本机跨框架层段成本与干扰实测-2026-10-25.md)]。**不要**把 `n_ubatch` 设成 ctx（会按 worst-case 预留图，Android 上曾因此 43 s）[实测数据，[DIST 缺陷审计](archive/misc/DIST后续核心链路缺陷审计-2026-10-07.md)]。
3. **mmap**：**保持开启**（默认）。段工件 1.98 GB < 可用内存，mmap 让页缓存复用、避免加载期拷贝；`--no-mmap` 只在该文件被反复 truncate/替换时才有意义。若观察到换页抖动，再试 `--mlock` 锁定工作集 [官方文档，parameters.md]。
4. **量化格式**：优先 **Q4_K_M 保持**（当前）；若要提速，走 **Q3_K_M**（TG 预期 1.2–1.3×，工件 1.98→约 1.25 GB，理论下界同步降到 ~32–42 ms）[计算]。**不要**换 Q4_0（pp 快、tg 不占优，且要重裁层）；**不要** IQ2/IQ3。
5. **构建档位**：单独给 Surface 出 **AVX-512 + VNNI** 变体（`-DGGML_AVX512=ON -DGGML_AVX512_VNNI=ON`，或用 `GGML_NATIVE=ON` 本机编译）。**预期只改善 prefill 与首次段加载后的首 token**；对逐 token decode 预期 ≈1.0× [推测，基于 PR #30036]。必须重跑数值门（ISA 改归约顺序）。
6. **上下文**：`-c 4096` 上限，**不要**给到 8192（实测慢 1.31×）。
7. **避免热降频**：15 W 平板持续跑 CPU 推理会在 1–2 分钟内降频（社区实测 25–30 → 15–18 t/s）[社区报告，ik 文档]；把 Surface 放在通风处/提高功耗墙（Windows 电源计划"处理器最大状态 99%"可抑制激进 turbo），并把**长 prompt 的 prefill 与 decode 分开计时**，否则会把降频误判成算法退化。
8. **不要做的事**：KV 量化、手动滑窗、`--numa`/THP、`-t 4`。

> 一句话：Surface 段剩下的旋钮只有 **线程 8 / ctx 4K / mmap 开 / 位宽降到 Q3_K / 单独 AVX512 构建**，全部叠加预期 1.3–1.5×；再想快只能**减层**。

## 6. llama.cpp CPU 段的已知天花板（诚实版）

1. **几何下界**：Surface 段 1.98 GB 工件、decode batch=1 ⇒ 每 token 至少读 1.98 GB。按 LPDDR4x-3733 双通道理论 59.7 GB/s、实际有效 30–40 GB/s 计，**理论下界 50–66 ms/token** [计算]。本机 4 层（6.84 ms/层）是 27.4 ms，Surface 在同一算法下**至少慢 2–2.5×**——调参不可能把它压到 20 ms。
2. **调参可兑现的总额**：线程标定（已兑现 1.2–1.28×）+ repack（已在用）+ AVX512 构建（prefill 为主）+ 位宽降一档（1.2–1.4×）。**在 decode 路径上，调参的乐观上限约 1.3–1.5×，且互有重叠**。
3. **换引擎的天花板**：ik 的 TG 只有 1.0–1.4×，且要移植补丁 + 重过全部数值门；OpenVINO 后端**没有公开性能数字**，且它在 ggml 图层融合，能否保留本仓 `layer_inp` 钩子**未验证**——这是硬阻塞项，不是"调一下就有" [未核实]。
4. **必须改切分/位宽的两件事**：
   - **减少落在最弱机上的字节数**：把末段 `lm_head`（若含）或其他非 decoder 张量移出 Surface、把 `[28,32)` 缩到 3 层、或把该段挪回 master#cpu（网络已证同 AP 内 PC↔PC 仅 3 ms）[实测数据，[已知问题 #69](已知问题记录.md#L2159)]；
   - **降位宽**：Q3_K_M 直接把下界乘 0.65。
5. **不该再投入**：AVX-512 换来的 decode 提速、KV 量化、滑窗、NUMA/大页、i-quant、换 MNN/ncnn/llamafile（都不满足层段硬指标）。

## 7. 优化手段总表

| 优化手段 | 预期收益 | 适用机器 | 落地代价 | 风险 |
|---|---|---|---|---|
| **减少 Surface 段层数 / 移走 head** | **线性减 25–50%** 关键路径 | Surface | 改切分与规划（改代码） | 重过数值门；容量核算变化 |
| **位宽 Q4_K_M → Q3_K_M** | decode ≈1.2–1.4× | Surface、y700 | 重新量化+裁层+质量评估 | 质量下降；需自测 PPL |
| 线程数标定（8 线程） | 1.20–1.28×（已兑现） | Surface、y700 | 调参 | 与 I/O 争核；热降频 |
| repack（已在用） | pp 1.13–1.36×、tg 1.05–1.21×（已兑现） | 全部 CPU 段 | 零（默认开） | 数值与 no-repack 差 2.5–4% L2 |
| AVX-512/VNNI 专用构建 | pp 1.5–3×，decode ≈1.0× | Surface（Ice Lake） | 改构建 + 重过数值门 | 15W 下降频；收益不进关键路径 |
| ubatch 512→256（prefill） | prefill 约 3–6% | 全部 CPU 段 | 调参 | 无明显风险 |
| CPU FA / ik 的 CPU FA 内核 | 未公开数值，需自测 | 全部 CPU 段 | 换构建/换 fork | 数值门；fork 维护 |
| ik_llama.cpp 整体替换 | pp 1.5–2.9×，tg 1.0–1.4× | master#cpu 的 prefill 场景 | 移植补丁 + 高 | 大，收益主要在非关键路径 |
| OpenVINO 后端 | 无公开数值；图融合潜力在 prefill | Surface（Windows 有官方支持） | 加后端依赖 + 构建 | **可能破坏 layer hook**；数值未知 |
| KV 量化 | **负收益（已证）** | — | — | 不要做 |
| 手动滑窗 / seq_rm | 负收益（已证） | — | — | 不要做 |
| 大页 / NUMA / 绑核 | ≈0（Linux-only） | — | — | Windows 不可用 |
| Q2_K / IQ2 / 1.58-bit | Q2_K 1.4×；IQ2 更慢 | 容量兜底场景 | 重新量化 | 质量损失显著；IQ 在 CPU 不划算 |
| PowerInfer | 不适用（需 ReLU 模型） | — | — | 结构不兼容 |
