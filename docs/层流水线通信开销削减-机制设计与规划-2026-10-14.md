## 0. 结论速览

1. **最优路径不是“更快地传”，而是“让 RTT 被摊薄”**：用投机解码的 γ 个 draft token 充当 micro-batch，把实测完整stage成本摊到最终提交的token。已有多个专门系统（SpecPipe / FlowSpec / SPD / Intel AI PC 分层），**这是低并发场景的正解**。
2. **物理前提支持这条**：γ=4 的 f32 hidden ≈64KB（base64 后 88KB），在 Y700 实测链路上约 **4.6ms**，**远小于 19ms RTT**⇒ **传输字节便宜、RTT 昂贵**。⇒ 优化目标函数是「**往返次数 × RTT**」，不是带宽。
3. **19ms 的本底是设备侧，不是软件栈**：空闲 ping 73ms vs 连续 TCP connect 16.2ms（Android PSM/U-APSD 唤醒）+ 2.4GHz 争用，**且路由器只有 2.4GHz**（`#69`、`#71`）。⇒ **Nagle / epoll / io_uring / “避免 per-step accept” 收益≈0，别投入**。
4. **本仓已有“安全演进”的三件套**（这条决定了后续风险可控），见 §2.3：控制面/传输实现分离（`transport_port.py`）、**影子+双栈+断路器**（`transport_runtime.py`）、能力协商 + fail-closed（协议 `version=3`，relay flags 低 3 位）。
5. **micro-batch 类编排（1F1B / GPipe / PipeDream / Zero Bubble / Chimera）在 batch=1 decode 下全部无效**（无 micro-batch；Zero Bubble 还需要 backward）⇒ 明确列为**不要做**。
6. **推荐顺序**：②二进制帧（小时级、零语义风险）→ ①投机当 micro-batch（收益最大）→ ③[投递时序采证](offer投递时序-实现与验收-2026-10-20.md)→ 其余在 ① 之后才有边际价值。

## 2. 机制设计

### 2.1 目标函数（先把口径定死）

```
每 token 有效延迟 = 计算时间 + (往返次数 × RTT) / 每步产出 token 数
                  = C            + R / γ
```

⇒ 两条正交的减压轴：**降 R**（少往返）与**升 γ**（每步多产出 token）。**降 bandwidth 项在本场景是次要项**（19ms RTT ≫ 4.6ms 传输时间）。

### 2.2 六个候选手段（按「收益 × 本项目落地风险」排序）

| # | 手段 | 期望收益（基线：195ms/步、网络税 76ms） | batch=1 有效？ | 风险 | 依据 |
|---|---|---|---|---|---|
| **①** | **投机 token 当 micro-batch**（spec decoding × pipeline） | **最大**：γ=3 全接受时网络税摊到 25ms/token（理论接近 3×） | ✅ **专为此场景设计** | 中：KV/段状态与 draft 源需对齐；**输出等价性必须逐 token 验收**（已有 `src/speculative.py` + argmax 判据） | arXiv 2504.04104（SpecPipe，4.19–5.53×）、2507.02620（FlowSpec，代码公开）、2605.30852（SPD，代码公开）、2504.08242（Jupiter）、2509.19368（PPSD）、**2608.19147（Intel AI PC 分层，声称 token-for-token identical）** |
| **②** | **hidden 换二进制帧**（去 base64/JSON） | 体积 **−25%** + 省 base64/JSON 的 CPU；γ>1 后约省 1–2ms/步 | ✅ 与 batch 无关 | **低**：不改语义，走能力位/版本协商（relay flags 是现成范式） | `task_worker_protocol.py:35,1440-1472`；二进制先例 `relay_transport.py:37-58` |
| **③** | **投递关键路径采证** | 以同条件A/B完整stage时间读取 | ✅ 与 batch 无关 | 保留准入、租约、取消与身份围栏 | [21c当前实现](offer投递时序-实现与验收-2026-10-20.md) |
| **④** | 计算-通信重叠（异步 send、提前 offer/租约续期） | 上限 `min(19, 30) = 19ms/段`，但**弱设备上发送线程可能抢 CPU/内存带宽而抵消**（未实测） | ⚠️ **纯 batch=1 下无分割维度**（单 token 的 hidden 是 `1×n_embd` 不可分块）；**仅在 γ>1 后成立** | 中 | 分析；arXiv 2311.18677（Splitwise 依赖高速背板）、2504.02263（MegaScale-Infer：需专用 M2N 库消除拷贝与同步）、2403.02310（Sarathi-Serve 是**批次内**切块） |
| **⑤** | 心跳/超时参数与传输实现**解耦** | 不直接省时间，**防止换层时误判断线**（可用性回退） | ✅ | 低-中：可在 `TransportRuntimeBridge` 上以具名错误码做双栈对照 | gRPC keepalive 官方指南（`too_many_pings` 的 GOAWAY 教训；`TCP_USER_TIMEOUT` 只监测到 LB 那一跳）；`network_path.py:222`；`cluster_partition.py:375-404` |
| **⑥** | hidden 量化作为**近似 draft**，由精确 verify 兜底 | γ=1 时几乎无感（0.5–4ms/段）；γ>1 后有边际价值 | ✅（需配 spec） | 中：**不可能保住逐 token 一致**，只能放进“draft + 验收”框架 | `relay_hidden_quant.py`；arXiv 2605.01255（无偏压缩对线性算子安全、对非线性有问题）、2211.17192（spec decoding 的分布等价保证） |

### 2.3 我们已经有的“安全演进”三件套（**新机制应建立在其上，而不是另起**）

1. **控制面与传输实现分离**：`src/transport_port.py` —— Scheduler **不直接** `import tcp_comm`，其注释写明 “a future transport can be selected without changing control-plane code”。
2. **影子 + 双栈 + 断路器**：`src/transport_runtime.py`
   - `mode=legacy_tcp`：**只观察、不改 wire 字节**的纯影子；
   - `mode="v2"`：显式端点选择；
   - `TransportCircuitBreaker(failure_threshold=3, cooldown_seconds=30)`；
   - `TransportWindow(1MiB)` 流控；
   - `generation` + `attempt_id` 栅栏 ⇒ 具名错误码 `generation_stale` / `attempt_fenced` / `circuit_open`。
   - `src/wss_loopback.py` 是现成的**第二个端点实现**（可作双栈演练对象）。
3. **版本/能力协商 + fail-closed**：`min(remote_max, local_max)` 否则 `unsupported_protocol_version`（`task_worker_protocol.py:386-412`）；能力声明式兼容（`stage_chunked_output`、relay flags 低 3 位）⇒ **不升 version 也能演进，旧对端直接拒**。

**工程范式**：Martin Fowler 的 **Parallel Change（expand–migrate–contract）** —— 它明确把 canary / blue-green 列为部署应用、建议用 FeatureFlag 控制迁移期走向、并警告 **“若不执行 contract 阶段，会比原来更糟”**。

## 3. 分阶段实施规划（每阶段：改动面 / 不变式 / 验证 / 回滚）

> 总原则：**一次只动一层**；每阶段都必须能**独立回滚**；**Phase C 之前不许碰 A1–A10 任何一条语义**。

### Phase A — 零语义风险的传输优化（②）

- **改动面**：hidden 帧的编码（JSON+base64 → 二进制），走**能力位协商**；旧对端保持 base64 路径。
- **不变式**：A1–A10 全部不变；wire 上**新增能力位而不改既有字段**（对齐 relay flags 的范式）。
- **验证**：per-token argmax 对拍（32/32）+ 字节数与耗时对比；旧/新对端混跑。
- **回滚**：关能力位即回旧路径（无需回滚代码）。
- **预期**：−25% 传输体积；γ=1 下节省有限（小报文），**主要是为 ① 铺路**。

### Phase B — 摊薄 RTT 的核心手段（①）

- **改动面**：让流水线按 γ 个 draft token 连续推进；draft 源可复用现有 `src/speculative*.py`（n-gram / MTP 已在生产路径）。
- **不变式**：**输出必须逐 token 一致**（`speculative` 的分布等价语义）；A5/A6/A7 的 fencing 与幂等不得放宽；**段 KV/state 的推进必须与 verify 结果一致**（hybrid 的 linear 层是 recurrent state，**不可事后重建** —— 这是最大风险点，见 §4）。
- **验证**：先本机两段回环（`qwen3_pipeline_loopback.py`）验等价性，再上真机；用 `#70` 的 `perf2 a=.. r=..` 打点验证摊薄效果。
- **回滚**：γ=1 即退化为现状（**这是天然的回滚开关**）。
- **预期**：γ=3 全接受时每 token 有效延迟 ≈65ms vs 195ms。

### Phase B 前置核查结论（2026-10-14，第三个子 agent 只读核查）

⚠️ **Phase B 不能按初稿直接开工** —— 核查发现三处必须先解决的前置，且初稿有一处能力误判。

**① 承担层段接力的引擎在当前形态下没有投机能力（最重要，改写成本估计）**

- `llama-cpp-python` 的 `draft_model` 投机循环**只在 `Llama.generate()` / `create_completion()` 内部**
  （`.venv-test/Lib/site-packages/llama_cpp/llama.py:111,470,1016-1025`；`LlamaPromptLookupDecoding` 在 `llama_speculative.py:17-64`）。
- 而**层段前向走原生 `llama_decode`**：`src/llama_keep_head.py:445 forward_tokens_to_hidden`、
  `:546 forward_hidden_to_hidden`、`:476 forward_hidden_to_token`；shim 只导出 `SHIM_SYMBOLS`（`:59-61`）。
- 且 server 路径 `serves_layer_segments=False`（`src/llama_server_engine.py:233`、`src/inference_path_selector.py:64`，
  注释 `:58` 写明「server 路径绝不得宣称」）。
- ⇒ **票 15c 的 1.30× / 5.5× 都是「整模推理」的收益，层流水线上尚未获得任何投机收益。**

**② 「被拒 token 的状态必须能撤销」在 hybrid 上没有落地（Phase B 的真正阻断项）**

- 上游 llama.cpp **有** recurrent 回滚机制（`llama_memory_recurrent` / `n_rs_seq`；EXPERIMENTAL、有界、带 TODO）
  ⇒ **不是架构不可能，是接线/工程风险**。
- 但本仓**未暴露/未使用**：本仓自有 JNI/shim 对 `seq_rm` **零命中**，只有 `llama_memory_clear`（整清）。
- transformers 侧对 recurrent **明确不支持 crop**（`cache_utils.py:965-1010`）。
- 协议**回程只给单个 `token_argmax`**（`src/task_worker_protocol.py:158-161`；`llama_keep_head.py:476-544`
  末段入口返回单个 int）⇒ **不返回多位置结果**。
- ⇒ 三者中**任何一条**都足以让 `qwen3-5-9b` 上的 γ>1 在**不改 A5/A7 与协议字段语义**的前提下不可行。
- ⇒ **先验顺序修正：先在纯 full-attention 模型（`qwen3-0.6b`）上验机制，hybrid 另行评估**（否则无法归因）。

**③ 末段只输出单个 argmax（★ 2026-10-18 精确化；原表述「多个 token 同时在飞」混入了并发限制）**

- **不需要新建**：一次推多 token 与多序列绑定都已就位 ——
  `forward_tokens_to_hidden(tokens)` → `[n_tokens, n_embd]`（`src/llama_keep_head.py:447`）、
  `forward_hidden_to_hidden` 按 `shape[0]` 取 n_tokens（`:548`）、`seq_ids` / `positions` / `n_seq_max`
  （`:173`、`:193`）。与本节 ⑤ 的既有结论一致。

**⑥ 2026-10-14 实测确认：现成装置无法直接验 γ>1（本轮已跑满 10 组）**

在打通链路后（布局：上游 0-8 → 中段 8-16 → 末段 16-24，**10 组全部 `tokens_match=True`**，
逐 token 与整模一致），尝试用 `--prefill {8,16,32,64,128}` × `--mid-extra-latency-ms {0,19}` 直接验证
「RTT 被摊薄」，**结果该设计不成立**：

| 注入 | prefill 8 → 128 | 每 token 有效延迟变化 |
|---|---|---|
| 0ms | 24.834 → 23.125 ms | 1.07×（几乎无变化） |
| 19ms | 30.535 → 35.039 ms | 0.87×（**反而变慢**） |

**根因**：`--prefill N` 改的是**上下文长度**，不是**每步产出多少 token**；而 relay 的 decode 是
**逐 token** 的（`scripts/relay_experiment.py:1416-1418` 记录 `activation_policy="prefill:full_sequence+decode:last_position"`，
回程只给单个 token）⇒ **用 prefill 模拟 γ 是错的**。
另外 `upstream/middle/downstream_decode_ms` 三段**不可相加**（三者之和已大于 `baseline_ms_per_step`），
且 `--gen 16` 样本下 `std` 有 1–3ms 量级噪声。

⇒ **结论：要验证目标函数，必须先给 relay 增加"一次解多个位置 + 多位置回程"的最小能力**
—— 而这**正是票 21b 第一步的工作内容**。因此 21b 的第一步不是"跑个实验"，而是"**先造这个能力**"。

**本轮实测的副产品（有独立价值）**：
- 打通了三段网络接力的完整链路与判据（含 `--mid-extra-latency-ms` 延迟注入）。
- 发现并修正了一处真实陷阱：`qwen25-05b-f16-mid8-24.gguf` 的 manifest 是
  `source_layer_range: [8, 24]`、`first_local_layer_maps_to: 8`、**16 层会全部跑完** ⇒
  若同时再挂一个 16-24 的末段，会**重叠 8 层**，表现为 `first_mismatch_index: 0`
  （从第 0 个 token 就错，**极易被误读成精度问题**）。正确做法是用 `scripts/cut_layers.py`
  造 **`--k 8 --end 16`** 的中段件（8 层），实测即 `first_mismatch=None`。

## 4. 风险矩阵（与可用性机制的交互，**这是本设计的主要目的**）

| 风险 | 触发场景 | 影响 | 缓解 |
|---|---|---|---|
| **旧包在重连后到达** | 双栈/相位切换期间新旧路径并存 | 违反 A5（`cluster_partition.py:375-404` 明确视为违规） | 双栈期**必须继续 fencing 旧路径**，并把它做成显式测试用例 |

| **hybrid recurrent state 不一致** | γ>1 时某 token 提前退出/跳段 | 下游无法补算（**linear 层 state 不可事后重建**） | Phase B 前置条件：**只有落在 `layer_types` 边界且段内含 full-attn 时才允许跨段 draft**；否则退化为 γ=1；用逐 token argmax 全量验收 |
| **租约/幂等顺序被合并打乱** | Phase C 乐观执行 | 重复执行或越权接受 | 走协议评审；`lease_epoch` 单调性断言；对抗用例 |

| **“若不执行 contract 阶段会比原来更糟”** | 双栈期无限延长 | 长期双路径 ⇒ 缺陷面翻倍 | 每个 Phase 都定义 **contract 完成条件**（旧路径删除判据） |

## 5. 明确的负面清单（**不要做**，避免团队再投入）

- ❌ **micro-batch 类编排**：1F1B / GPipe / PipeDream（需多 micro-batch）、**Zero Bubble**（需 backward）、**Chimera**（需双向灌批）—— 在 batch=1 decode 下全部无效。
- ❌ **Nagle / TCP_NODELAY / epoll / io_uring / “避免 per-step accept”**：19ms 本底来自设备唤醒与 2.4GHz 争用；且本仓已是持久 TCP + 长活 runner 子进程；io_uring 在 Windows 不存在。
- ❌ **`--override-tensor` 当提速手段**：它是容量旋钮。
- ❌ **`int4_block128` 量化档**：23/32 FAIL，且误差反馈救不回。
- ❌ **把“数值一致”当 hidden 压缩的验收标准**：结构上不可保证；应改为“**输出分布等价 + 逐 token argmax 重算验收**”（这正是 spec decoding 的原文保证，arXiv 2211.17192）。
- ⚠️ **外部方案的硬件前提不满足时要放弃**：Splitwise 依赖高速背板、MegaScale-Infer 依赖专用 M2N 库消除拷贝与同步 ⇒ 在 2.4GHz WiFi + CPU-only 对端上，**“重叠”缺少硬件前提**。

## 8. 外部同类系统对照（2026-10-19）

本节把「流水线并行」的两条**独立技术线**分开记录。它们常被混在一处引用，但前提与优化目标完全不同，
混读会把训练侧结论误当推理依据。

### 8.1 两组技术的分野

| 组 | 场景 | 前提 | 优化目标 | 对本项目 |
|---|---|---|---|---|
| GPipe / PipeDream / 1F1B / Zero Bubble / Chimera | **训练** | 有 micro-batch 可切、有 backward | 训练吞吐（time-to-accuracy） | **不适用**（§8.2） |
| SpecPipe / FlowSpec / Jupiter / Intel AI-PC / SPD / PPSD | **推理** | batch=1 亦可用 | 单请求延迟（TBT / TPOT） | **正是 ① 的理论依据**（§8.3） |

本项目的场景是**推理 + batch=1 自回归 decode + 跨机层流水线** ⇒ 前者结构不适用，后者对口。

### 8.2 训练侧流水线并行（**不读、不用、不改造**）

| 工作 | 核心机制 | 为什么对本项目无效 |
|---|---|---|
| **GPipe**（arXiv 1811.06965） | 把 mini-batch 切成多个 micro-batch 依次灌入各级，最后统一梯度累积 | 前提是 **batch 可切**；batch=1 decode 每步只产 1 token，切完每片剩 1/γ |
| **PipeDream / 1F1B**（arXiv 1806.03377） | 1 次 forward + 1 次 backward 交替，降低在飞 micro-batch 数与显存峰；weight stashing 处理异步梯度陈旧 | 前提是**有 backward 可交错**；推理无 backward，1F1B 退化为顺序执行 |
| **Zero Bubble**（arXiv 2401.10241） | 把 backward 拆成 B（输入梯度，须按序）与 W（权重梯度，可延后），用 W 填气泡 | 推理**无 backward** ⇒ 机制不可移植 |
| **Chimera**（arXiv 2107.06925） | 双向流水线，两个方向同时灌批 | 推理无此自由度 |

与 §1.5「已证伪的优化」同源；此处补记**机制层面**的理由，避免后续再评估一次。

### 8.3 推理侧：投机填流水线（**① 的直接依据**）

共同洞察：batch=1 下气泡无法用 batch 填，但可以用**投机解码的 γ 个 draft token** 填 —— 一次前向推
γ 个位置、一次回程收 γ 个 token，把每步 2 次跨机往返摊到 γ 个 token（即 §2.1 的 `C + R/γ`）。

| 工作 | 解决的问题 | 关键机制 | 可借用点 |
|---|---|---|---|
| **SpecPipe**（arXiv 2504.04104） | 流水线并行推理延迟高 | 用投机 token 逐步填满流水线；8-stage 单请求 **TBT 4.19–5.53×** | 证明气泡可被投机转成有效算力；其 γ-填充调度是 ① 的参照 |
| **FlowSpec**（arXiv 2507.02620，**代码公开**） | 边缘请求稀疏时流水线利用率低 | pipeline-parallel **tree** speculative decoding，**1.37–1.73×** | 树形 draft 接受率高于线性 draft；边缘低并发与本仓 Y700/Surface 场景同构 |
| **Jupiter**（arXiv 2504.08242，INFOCOM'25） | 边缘协作推理的端到端延迟 | pipeline + outline-based pipeline decoding + 投机，**↓26.1×** | 三段式边缘协作拓扑与本仓 master→中间段→末段同构 |
| **Intel AI-PC 分层**（arXiv 2608.19147，**代码公开**） | 层切分推理在**广域网**下的吞吐 | 均分层切分 + 独立小模型 draft + 多用户 stream 交织；状态回收用 **mask rewind** 而非物理 trim（§8.4） | **场景最贴近本仓**（层切分、跨机、普通 TCP、token 一致）；其 mask rewind 正对本仓「被拒 draft 状态回收」卡点 |
| **SPD**（arXiv 2605.30852，代码公开） | 同类 | — | 有实现可对照 draft 接受逻辑 |
| **PPSD**（arXiv 2509.19368） | 同类 | — | 备查 |

⚠️ 上表中 **Intel AI-PC 的 micro-batching 不是「用 γ 填气泡」**，而是多用户请求交织（§8.4）；它对 ① 的
价值在状态回收与回程压缩，不在填充调度。其余五者的共同点才是「用投机 token 填流水线气泡」。

### 8.4 Intel AI-PC 分层（2608.19147）的具体机制

**出处**：Tate Berenbaum、Muthaiah Venkatachalam（Intel），2026-08-19，cs.DC，标题
*Pre-Compiled Pipeline Shards for Distributed LLM Inference on Intel AI PC Fleets*；复现包
`github.com/labscommunity/pipeline-sharded-inference-paper`（`main.tex` + `reproduction/`）。
以下机制主要自复现包代码（`cascadia/pipeline/{spec_decode,stage_worker,coordinator}.py`、
`coord/mini_coord_spec_mbatch.py`、`bench/bench_spec_wan_K.py`、`proxy/wan_sweep_v2.py`）与官方
`reproduction/{CLAIMS,RESULTS,MODELS}.md` 读出。论文 §3–§8 正文未取得完整原文，正文未覆盖处以
「未声明」标注，不代其表述。

#### 8.4.1 架构与切分

- **按层号连续均分，无算力加权**：8B 两段为 16+16 层、三段为 11+11+10 层；70B 四段每 shard 9 GB。
  异构件（Lunar Lake ×2 + Panther Lake ×1）之间没有做算力配比，相关实验也未覆盖不均衡拓扑。
- **prefill 与 decode 不分离**：`MaskedReq.feed(prompt_ids)` 一次性把整段 prompt 穿过全部 stage，
  随后进入自回归循环；论文把 TD-Pipe / Splitwise 的 PD 分离列为对照工作。
- **coordinator 兼任首段**：stage 0 所在机同时持有 draft 模型，并负责构造 `attention_mask` 与
  `position_ids`，二者**随激活一起下发给下游**（`forward_stage1(stream_id, hidden, attn_mask, position_ids)`）。
  整个状态回收方案建立在这个接口上。

#### 8.4.2 micro-batching 的真实含义（**与 ① 不同**）

`NUM_STREAMS` 个线程各跑一条完整的投机解码循环，用 `threading.Barrier` 对齐起点；**每条 stream 有
独立 KV 状态**，且因 OpenVINO 2026.1 多 InferRequest 的 reset-state 缺陷，**每条 stream 各自
`compile_model()`** 一份 stage 0 与 draft（内存 × stream 数）。传输共用一个 socket 并以锁串行化
（故 2-stream 是并行计算、交错等待，而非并行传输）。

⇒ 这是**多用户请求交织**填气泡，不是「用 γ 个 draft token 填气泡」。它绕开了 batch=1 无 micro-batch
可切的问题（总有第二个用户），因此**不能为 ① 提供 batch=1 下的填充经验**；对本仓的价值在两处：
状态回收（§8.4.3）与回程压缩（§8.4.5）。

#### 8.4.3 ★ 被拒 draft 的状态回收：mask rewind 替代物理 trim

**动机**：`query_state()`/`set_state()` 的物理截断在 72-token cache 上需 **46.6–49.9 ms/次**
（Arc B390 iGPU），「足以让投机在盈亏平衡点变成净损失」。

**机制**（`spec_decode.py::MaskedReq`）：维护三条不变量，**物理 KV 只增不减**。

| 变量 | 语义 |
|---|---|
| `cache_len` | 物理 KV 长度，**单调递增、append-only** |
| `logical_pos` | 逻辑序列位置，下一次 feed 的 `position_ids` 从它起算 |
| `valid_mask[i]` | 该物理位置是否 live |

`rewind(k)` 只做两件事：`valid_mask[cache_len-k : cache_len] = 0`、`logical_pos -= k`。
每次 feed 重建 `attention_mask`（`valid_mask` 打底、新位置填 1）与
`position_ids = arange(logical_pos, logical_pos + n)`。⇒ 被拒位置的数据仍在物理 KV 中，但后续 token
全部 `mask=0` 看不见它，RoPE 位置也从回退后的 `logical_pos` 重算，**逻辑上等价于删除**。

**等价性**：论文摘要称 masking 与物理 trim **bit-identical**；代码 docstring 记
「max logit diff 0.0000 at each accept decision point」。

**跨机形态（对本案最关键）**：`DistributedTargetMaskedReq` 把 `attn_mask` + `position_ids` 透传给
下游段，下游 stateful IR 用同一份 mask 做同样回退 ⇒ **不需要任何跨机回滚 RPC**，回滚只是「下一次
请求里多带一份 mask 与 position」。据此，本仓「被拒 draft 的状态回收」卡点可以换个问法：关键不在
「能否 `seq_rm`」，而在「**能否把 per-position mask 与 position_ids 注入每段**」。

**代价（作者自陈）**：回退位置永久占用物理内存，>2k token 需周期性 compaction，**未实现**；实测膨胀
系数在 128 tok 为 1.26×、1024 tok 1.04×、2048 tok 1.02×（接受率高时几乎不膨胀）。

#### 8.4.4 token-for-token identical 的确切范围

| 层级 | 保证内容 | 证据强度 |
|---|---|---|
| 同拓扑、spec vs target-only | 70B 四段「output token-for-token identical to the same four-node pipeline decoding without speculation」；K=3/5/10/15 首 10 token 全同 | 官方 RESULTS 逐位记录 |
| 跨拓扑（distributed vs mono） | 「bit-correct / first 10 tokens identical to mono target-only」，8 组 prompt 全一致 | **首 10 token 抽样**，非全序列证明 |
| 机制来源 | greedy + 最长前缀接受 + `valid_mask`/`logical_pos` 回退 ⇒ 输出恒等于 target 自身的 greedy 解码 | 代码 docstring |

**未保证的部分**：仅 greedy（无温度/采样下的分布等价性）；不保证 logits 逐位等于 mono（不同分段的
数值路径不同，只有「mask vs 物理 trim」这一对达到 logit 级 0 差异）；**未见对 hybrid / 线性注意力 /
MoE 的适用性声明** —— 实验只有 dense Llama 3.1 8B/70B 与 Gemma 4 E2B，且 Gemma 表中只有
target-only 与 mbatch 行、**没有 spec 行**，说明 mask rewind 未在该模型上验证。

#### 8.4.5 广域网适应

| 手段 | 做法与效果 |
|---|---|
| **Top-1 logits 压缩** | 末段先 argmax，回程只发 `int64` token id（协议以 `vocab_size==0` 标记该模式）；8B 下 K+1=4 时回程从约 512 KB 降到 8 字节。Tailscale DERP（≈16 ms RTT）上 **3.97 → 22.12 tok/s** |
| 激活压缩 | FP32 13.57 / FP16 12.71 / INT8 15.10 tok/s（INT8 反而更快）；对应脚本不在仓库文件清单内，仅存于官方 CLAIMS 记录 |
| 延迟模拟 | ① 段间 `time.sleep(L)`；② 本地 TCP 代理 + release-time delay queue（匹配 tc-netem 的多段在飞行为） |
| 传输 | 裸 TCP + 小端二进制帧（`<IIII` 头 + attn_mask int64 + hidden f32）、`TCP_NODELAY`、`SO_KEEPALIVE`；**无重传、无应用层超时重试、无断线重连** |

#### 8.4.6 实验与主结果

硬件 3 台消费级 AI PC（Zenbook S 14 ×2 Lunar Lake + OmniBook X 16 Panther Lake，Arc B390 iGPU），
**Wi-Fi**，1 hop TCP RTT 实测 **6 ms**；扩展实验为 Tiber Cloud 4×Lunar Lake。模型 Llama 3.1 8B INT4
（1.5 GB/stage）、Llama 3.2 1B INT4 draft、Gemma 4 E2B FP32、Llama 3.1 70B INT4（9 GB/shard ×4）。

| 配置 | tok/s | 相对 |
|---|---|---|
| mono 单用户 | 22.96 | — |
| 2-stage 单流 | 14.51 | **0.67× mono**（层切分自身 +23 ms/token） |
| + 2-stream micro-batch | 29.46 | 2.03× 单流 |
| + mask spec K=3 | 41.25（实测 43.97） | 1.79–1.89× mono |
| 3-stage 3-stream K=5 | 54.92（实测 64.67） | 2.64× mono |
| 70B 4-stage：target-only / K=10 | 1.74 / **5.42** | 3.11× @K=10 |

接受率：8B+1B K=3 → **70.7%**、K=5 → 67.1%、K=10 → 52.5%；70B K=3 → 76.7% 递减至 K=15 的 51.4%。
**全部指标为吞吐（tok/s），未报告 TTFT / TBT / TPOT。**

**负面结果（可直接借用其结论）**：计算-通信异步重叠 **11.08 vs 11.05**（无收益，与 §8.5 对 ④ 的保留一致）；
INT8 KV cache 反而慢 4%；用户态 Python 仅占 0.6% wall time；per-token 分解显示 **Python + OV dispatch
15 ms** 与 1 hop RTT 6 ms 同量级 —— 在「计算只有几十 ms」的异构 CPU 场景，调度与框架开销会与网络税同量级。

#### 8.4.7 对本仓的可迁移判定

**可搬**：

1. **mask rewind 替代物理 trim** —— 正对「被拒 draft 状态回收」卡点。full-attention 段可直接照抄；
   hybrid 需另判（见下）。
2. **回程只传 argmax** —— 与票 21a 的二进制帧正交，且 γ>1 时省得更多。
3. **γ 用「接受率 × γ × RTT」离线扫描而非自适应** —— 本仓 19 ms RTT 落在该文 LAN（6 ms）与
   50 ms/hop 之间 ⇒ **γ≈3–5 是合理起点**（与 §6 的开放问题一致，仍需实测接受率）。
4. **per-token 开销分解表**（compute / TCP / dispatch）作为记账方法。
5. **per-stream 独立 state 隔离**：同一 compiled model 的多个 InferRequest 会串 state ⇒ 本仓
   「多位置在飞」的等价风险是同一段复用同一 KV 会话。

**搬不动**：

1. **多用户 micro-batching（2.03×）整条不可用** —— 本仓是 batch=1 单请求。这是该文最强的收益，
   也最不可迁移。
2. **对 hybrid / recurrent state 无答案** —— mask rewind 的正确性依赖「状态 = 可被 attention_mask
   屏蔽的 KV」，对 recurrent state 不成立；该文未在 hybrid 上验证，适用性边界亦未声明。本仓卡点仍需
   自解（沙盒槽 `seq_cp` 方案与这是两条独立路径，见
   [沙盒槽设计](层流水线通信开销削减-PhaseB第二步-沙盒槽设计-2026-10-14.md)）。
3. **OpenVINO stateful IR 的状态契约**、`beam_idx` Gather 注入为 Intel GPU plugin 专属，与 llama.cpp 无关。
4. **同构假设**：均分切分在「骁龙 8 Gen 3 与桌面机差一个数量级」的拓扑上会把流水线卡在最慢段；
   该文无算力加权、无异构不均衡实验。

**一处口径修正**：该文**不依赖 RDMA／高速背板**（普通 TCP + Tailscale DERP），因此「依赖 RDMA 搬不动」
的担心在它身上不成立；真正搬不动的是它的状态契约与「必须有第二个请求填气泡」这一前提。

### 8.5 对本项目的取舍

- **优先读**：Intel AI-PC 分层（§8.4：mask rewind 与回程压缩直接对口）、SpecPipe（γ-填充调度）。
- **看代码**：FlowSpec、SPD（draft 接受与状态处理）。
- **不要照抄绝对倍数**：SpecPipe（8-stage）与 Jupiter（边缘协作）在**数据中心同构 GPU + RDMA／高速
  背板**上验证；Intel AI-PC 虽用普通 TCP + Tailscale DERP（无 RDMA 依赖），但拓扑是近同构
  Lunar/Panther Lake 且靠**第二个用户**填气泡。本仓约束是 **19ms RTT + 异构 CPU + Wi-Fi/Tailscale +
  batch=1 单请求** ⇒ 三者的绝对倍数（4.19–5.53×、↓26.1×、1.79–3.11×）**均不可直接外推**。可迁移的是
  「用投机填气泡」的机制、mask rewind 的状态回收形状，以及对**接受率 × γ × RTT** 的建模方式。
- **口径提醒**：本仓的 5.43× 是**通信探针**（γ=8 vs γ=1；条件含已知 prompt、预计算 head、注入等待），
  该数字按通信探针读取；当前full-attention生成闭环及完整成本验收见[21b实现与验收](投机批验证-实现与验收-2026-10-20.md)。
