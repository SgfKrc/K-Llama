## 0. 结论速览

1. **误差由"两侧权重网格差"主导**，不是归约顺序、也不是算子实现（后两者都是 `1e-7` 级）。
   旧默认组合 `fp32 上游 × Q4_K_M 下游` 在第 16 层差 `1.96e-01`，是同源 `f16 × f16`（`3.33e-04`）的 **590×**。
2. **可以同时启用的是 4 条**：权重同源 ＋ 两侧同精度（f16）＋ 交界处共享网格 ＋ 整型累加（或 f64 累加）。
   在有效档位（int8）下四条并列实测 **24/24**，与整模完全一致。
3. ⚠️ **有一条不能叠加**：为了"消除归约顺序"（省 `1e-7`）而把**上游 GEMM 也降到粗网格**是**反噬** ——
   int4 档下 `0/24`，比"只在交界处量化"的 `9/24` **更差**。规则：**别用 `1e-2` 级的代价换 `1e-7` 级的收益**。
4. **最优可叠加组合能压到**：端到端 `rel` `1.32e-4 … 4.39e-4`（比旧默认降 **40–80×**）、
   argmax `173/174`、**`174/174`**、**`172/172`**（合计 **519/520 = 99.8%**）。
   再往下跨框架做不到 —— `rel → 0` 需要两侧**共用一个实现**，而那种场合本来就不需要接力。
5. **接入生产**（2026-10-08 落地）：`src/relay_precision.py` 把上表固化成**可调用判据**，
   在接力上下游入口**自动登记并检查**，不对齐时打具名 WARN（`QLH_RELAY_PRECISION_STRICT=1` 可 fail-loud）。
   **不改任何路由/准入/默认配置**。

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| 模型 | Qwen2.5-0.5B-Instruct |
| 切点 | `K = 16`（上游跑 `0..15` 层，下游跑 `16..`） |
| 判据 | **逐 token `argmax` 一致数**（⚠️ 纪律：**不得用 cosine 代替**；分叉就如实标 FAIL） |
| 生成 | 贪心，`gen_steps = 160`，每步重跑完整序列（无 KV 复用，排除缓存干扰） |
| 工况 | 3 prompt：浮点加法解释 / 三原色 / 恰好五个词的句子 |
| 叠加性实验 | `K = 12`，`gen_steps = 8`，档位 `int8`（`levels = 127`）与 `int4`（`levels = 7`） |

⚠️ **口径**：叠加性实验的步数（8）与端到端台账（160）**不同**，两者只在**同一张表内**可比。
之所以两个档位都跑：`int8` 档对误差不敏感（各配置都全同，**无区分度**），
必须用 `int4` 这一**敏感档**才能暴露"某维度是否真的改变了结果"。

## 2. 误差有多大（分层，全部实测）

| 层 | 量级 | 证据 |
| --- | --- | --- |
| 层段切分（PyTorch `load_layer_range` vs HF 整模） | **0（逐比特）** | `xframe-layer-range.json` |
| 算子实现（RMSNorm / SiLU / SwiGLU） | `1e-7` | XFRAME-2（RMSNorm 逐 bit `896/896`） |
| 归约顺序（f32，分段 1/2/4/8） | `2.2e-07` | `xframe-int8-grid.json` |
| 累加数域（f32 累加器 vs f64） | `2.2e-07 → 0` | XFRAME-4 / XFRAME-5 |
| 两侧整型累加（int32，同网格） | **`0`（逐位相同）** | `xframe-int8-grid.json`（`torch.int32` 与 `numpy.int32` 亦一致） |
| 交界处 int8 逐通道共享网格 | `~1e-3`（hidden rms 0.1%） | XFRAME-3 |
| 激活量化（llama.cpp `vec_dot` 内） | `1.5e-3 … 6.3e-3` | `xframe-actquant.json` |
| **权重网格不同**（fp32 vs Q4_K_M，第 16 层） | **`1.963e-01`** | `xframe-layerprofile16.json` |
| **端到端（旧默认：fp32 上游 ＋ Q4_K_M 下游）** | **`1.08e-2 … 4.01e-2`** | `xframe-sharedgrid-orig.json` |

⇒ 表格自上而下是**三个数量级**的台阶：`1e-7`（算术）→ `1e-3`（量化传输/激活量化）→ **`2e-1`（权重网格差）**。
**优化只能从最大那一项开始**，这也解释了为什么"锁归约顺序"这类改动在端到端上看不出效果。

## 3. 优化维度 × 叠加性（五组并列实测）

同一条真链路并列五组（`scripts/xframe_grid_stack.py`；`K = 12`、3 prompt × 8 步）：

| 组 | 上游（前 K 层） | 交界处 hidden | int8（`levels=127`） | **int4（`levels=7`，敏感档）** |
| --- | --- | --- | --- | --- |
| `A` | llama.cpp 整模（基线） | — | — | — |
| `B` | llama.cpp keep-head（同引擎） | 原样 | **24/24** | **24/24** |
| `C` | PyTorch f32 GEMM | 共享网格量化 | **24/24** | 9/24 |
| `E` | PyTorch **int8 网格 ＋ int32 累加** | 共享网格量化 | **24/24** | **0/24** |
| `F` | PyTorch **int8 网格 ＋ int32 累加** | 原样（不量化） | **24/24** | **0/24** |

**判读契约**：`C == A` ⇒ 交界处网格对齐有效；`E == C` ⇒ 整型累加可与网格对齐叠加；`F != B` ⇒ 上游整型累加自身引入偏差。

⇒ 三条结论：

1. **有效档位（`int8`）下四条维度可同时启用** —— `B == C == E == F == A`（24/24），
   即"整型累加"**不会**破坏"交界处网格对齐"（两者正交）；
2. ⚠️ **档位不足（`int4`）时「上游也量化」反而更差**（`E = 0/24` vs `C = 9/24`）：
   上游 GEMM 的量化误差（rms `1.2–1.8%`）**超过 int4 半格** ⇒ 交界处的网格对齐**压不回同格**；
   而 `F`（交界处不量化）同样 `0/24` ⇒ 偏差来自**上游 GEMM 本身**，与交界处是否量化无关；
3. ⇒ **规则**：**不能为了消除"归约顺序"（`1e-7` 级）而把上游 GEMM 降到粗网格**（引入 `1e-2` 级误差）；
   "整型累加"只在**两侧同网格且档位足够**时才是净收益。

### 3.1 各维度的代价与叠加性（合并视图）

| 维度 | 机制 | 量级 | 代价 | 可叠加 |
| --- | --- | --- | --- | --- |
| 层段切分 | `ModelManager` 按层加载 | **0**（逐比特） | 无 | 基线 |
| 算子实现 | 共享 C kernel | `1e-7`（本已一致） | 低 | 无需 |
| 归约顺序 | 锁定分块/线程 | ≥`O(K·ε)` | 侵入式 | 与"整型累加"互斥（后者是其解） |
| **权重同源** | GGUF 反量化喂 torch | 降 **40–80×** | 放弃原始 fp32 | ✅ |
| **通路同精度（f16）** | 避免边缘侧激活量化 | 再降 **14×** | 放弃 4-bit 容量 | ✅ |
| **交界处 int8 网格** | 逐通道共享 scale | 压回同格 | hidden 传 1/3 体积 | ✅ |
| **两侧整型累加** | int32 累加 | 顺序敏感度 → **0** | 见 §3 | ⚠️ 有条件 |
| 累加数域 f64 | 累加器 f64 | 顺序差 → `0` | 吞吐↓、须两侧同改 | ✅（与网格正交） |

## 4. 能压到什么程度

端到端台账（Qwen2.5-0.5B、`K = 16`、`gen_steps = 160`、3 prompt）。
`rel` 取 **`segment_mean_rel` 的 4 段均值范围**（各 prompt 并集），比单看 head/tail 更严：

| 组合 | 端到端 `rel`（4 段均值范围） | median `rel` | 逐 token argmax 一致 |
| --- | --- | --- | --- |
| **旧默认**：fp32 上游 ＋ `Q4_K_M` 下游 | `1.08e-2 … 4.01e-2` | `1.13e-2 … 2.49e-2` | 165/174、163/174、166/172（**494/520 = 95.0%**） |
| ＋ 权重同源（`Q4_K_M` 反量化） | `3.16e-3 … 8.70e-3` | `2.77e-3 … 4.20e-3` | 173/174、168/174、171/172（**512/520 = 98.5%**） |
| **＋ 两侧同精度（f16 同源）** | **`1.32e-4 … 4.39e-4`** | `1.39e-4 … 2.31e-4` | 173/174、**174/174**、**172/172**（**519/520 = 99.8%**） |
| ＋ 交界处 int8 共享网格 | 同量级（传输降 3–4×） | — | 24/24（口径：`K=12`、3 prompt × 8 步） |
| 理论下界（f32 的 `O(K·ε)`，XFRAME-4） | `3.5e-4` | — | — |
| 要 **`0`** | 须两侧**共用一个实现**（同 kernel） | — | — |

**危险度不只看一致率，还看首分歧位置**（越早、剩余步数越多，自回归把局部翻转累积成语义漂移的空间越大）：

| 组合 | `first_argmax_divergence`（三个 prompt） |
| --- | --- |
| 旧默认 | `0`、`6`、`6`（**第 0/6 步就分叉**） |
| 权重同源（Q4_K_M） | `37`、`0`、`6` |
| **两侧同精度（f16）** | `34`、**无分叉**、**无分叉** |

⇒ **一句话**：最优可叠加组合 = 「**权重同源 ＋ 两侧同精度（f16）＋ 交界处共享网格**」
⇒ 端到端 `rel` 降到 **`1e-4` 级**、argmax **基本全同**（3 个 prompt 里 2 个完全全同）；
**再往下跨框架做不到**。

## 5. 接入生产（已落地）

### 5.1 为什么是"精度对齐"这一条

四条可叠加维度里，**只有"两侧精度对齐"能在不改协议、不改算法、不碰热路径计算的前提下落地**：

* 「权重同源」＋「两侧同精度」⇒ **部署配置 + 一次检查**；
* 「交界处共享网格」⇒ **生产已具备**（`relay_hidden_quant.py` 的 `int8_block128` 传输档，
  实测 512 步内不改变任何 token）；
* 「两侧整型累加」⇒ **不接入**（上游 GEMM 由 aten 承担；改它按 §3 是反噬）。

⇒ 接入的落点是**把"两侧精度对不对齐"变成产品能自己发现的事实** —— 此前旧默认组合（`fp32 × Q4_K_M`）
是最大误差源，却**没有任何提示**（实测算出第 16 层差 `1.96e-01`，无人知道）。

### 5.2 实现（`src/relay_precision.py`）

| 构件 | 作用 |
| --- | --- |
| `MEASURED_PRECISION_PAIRS` | **实测判据表**（§4 的三个数值，保留 JSON 完整精度） |
| `evaluate_relay_precision(up, down)` | 归一两侧口径 → 给 `rel`、`level`（`ok`/`warn`/`critical`/`unknown`）、`advice` |
| `note_upstream_precision(...)` / `note_downstream_precision(...)` | 两侧各自登记（**不改任何方法签名**） |
| `check_relay_precision(...)` | 两侧齐备后比对；**默认只 WARN 一次**，`strict` 才 fail-loud |
| `relay_precision_report()` | 供健康检查/诊断读取 |

**两条纪律**（都写进了代码与单测）：

* **判据只覆盖实测过的组合**，未测组合回 `unknown` 并把"先跑哪个探针、登记到哪"写进 `advice` —— **不猜**；
* **`int4` / `int8` 是 `config.QUANT_TYPE` 的配置意图，不是具体网格** ⇒ 原样保留，**不**折叠成某个 `q*` 档。

### 5.3 挂点与开关

| 位置 | 动作 |
| --- | --- |
| `llama_engine.forward_layers_from_hidden`（**下游入口**） | 首次进入时登记下游档位（取 GGUF `general.file_type`，**权威**；实测 `'1'`=f16、`'15'`=Q4_K_M），并触发一次对齐检查 |
| `model_module.load_layer_range`（**上游入口**） | 登记上游档位（优先级：路径标记 `*-f16-dequant` > 实际 dtype > `quant_type` 意图） |
| `relay_contract.RelayXFrameEvidence` | 新增**记录字段** `precision_verdict` / `precision_aligned`（默认 `unknown` / `False`） |
| `QLH_RELAY_PRECISION_STRICT=1` | 未对齐时 fail-loud（抛 `RelayPrecisionMismatch`，继承 `RuntimeError`） |

⚠️ **两个实现坑**（已写进代码注释，都踩过）：

1. **必须平铺导入**（`from relay_precision import ...`）：该模块带**进程级状态**；
   若一处写 `from src.relay_precision import ...`、另一处写 `from relay_precision import ...`，
   Python 会当成**两个模块**、状态各存一份 ⇒ 登记互不可见、检查**静默**永不触发。
2. **登记函数不能吞掉严格模式的异常**：`_note_relay_downstream_precision` 对普通异常做兜底
   （诊断绝不能影响推理），但必须把 `RelayPrecisionMismatch` **重新抛出**，否则严格模式失效。

### 5.4 怎么用

```powershell
# 看两侧精度与判据（不启动推理）
python -c "import sys; sys.path.insert(0,'src'); import relay_precision as P; print(P.relay_precision_report())"

# 想让不对齐直接拦住启动（默认只 WARN）
$env:QLH_RELAY_PRECISION_STRICT = "1"
```

要让**旧默认**变成**最优组合**（两个动作，都是部署侧，都不改代码）：

1. 上游加载**与下游同源**的反量化目录（`--dtype float16` ⇒ 与下游 f16 同网格）：

   ```powershell
   python scripts/gguf_dequant_to_hf.py --gguf models/qwen25-05b-f16.gguf `
       --dst build/keephead/qwen25-05b-f16-dequant --dtype float16 `
       --tokenizer-src models/qwen2.5-0.5b-instruct
   ```

2. 下游用**同源**的 `f16` 裁层工件（`models/qwen25-05b-f16.gguf` 系列），
   然后按 §7 的命令复跑对照，确认 argmax 一致数升到 `519/520` 档。

### 5.5 明确**没有**做的

* **未改准入判据**：`RelayXFrameEvidence.admits_production()` 仍只看 `correctness_verified`；
  `precision_verdict` 是**记录字段**（与 `performance_verdict` 同性质）；
* **未改默认部署**：`config.QUANT_TYPE`、默认模型、默认工件组合**都没动** ——
  切默认是**独立决定**（代价是下游放弃 4-bit 容量、体积/显存上升）；
* **未宣称"误差为零"**：`rel → 0` 需要两侧同构，超出跨框架接力的范畴。

## 6. 口径与边界

1. **`rel` 口径**：`segment_mean_rel` = 把位置序列等分 4 段、每段求 mean 再取并集范围；
   它**大于** `median_rel`、**小于** `max_rel`。引用时必须带"哪个统计量 + 哪种组合"。
2. **`argmax` 判据优先**：`rel` 只作辅助；是否可用**以逐 token argmax 一致数为准**，**禁止用 cosine 代替**。
3. **叠加性实验与端到端台账的实验参数不同**（`K=12`/8 步 vs `K=16`/160 步）⇒ 结论可互相印证，**数字不可互相换算**。
4. **单层 vs 端到端**：`xframe-layerprofile*.json` 是"第 16 层单层相对误差"，用于**归因**；
   端到端 `rel` 是整链累计，两者不相等也不该相等。
5. **未实测组合不推断**：`fp32 × f16`、`f16 × Q4_K_M`、`q4_k_s` 等组合**没有实测** ⇒
   `evaluate_relay_precision` 一律回 `unknown`。
6. **`general.file_type` 映射**：`1`（f16）与 `15`（Q4_K_M）为**本仓实测**；其余为 llama.cpp
   `llama_ftype` 枚举直译（未在本仓逐档验证）⇒ 表里已逐项标注。
