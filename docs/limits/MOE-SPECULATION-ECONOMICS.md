# MoE 的投机解码经济学与稠密模型不同

> 状态：**已验证**
> 更新日期：2026-11-03
> 适用范围：35B-A3B（MoE，激活 3B）+ 248,320 词表上的投机解码成本结构，以及为何不能照搬
> 稠密模型的社区参数；读者为调参与后续评估者。
> 相关：`SPECULATION.md`（四方向判定）、`MEASUREMENTS.md`（层段拆分实测）

社区里投机解码的经验（`m=24~64`、加速 1.5–2×）建立在**稠密模型 + 小词表**上。
本项目是 **35B-A3B（MoE，激活 3B）+ 248,320 词表**，成本结构完全不同，所以最优参数也完全不同。
这份文档解释为什么，以及为什么不能照搬社区数字。

---

## 1. 一句话

**MoE 把层计算压到激活的那点参数上，但 `lm_head` 一分不少——于是它的相对成本被放大数倍，
最优 k 反而更小，"大草稿"类方法天然吃亏。**

---

## 2. 成本结构

`lm_head` 的成本是 `n_vocab × n_embd`，与层数无关、与激活参数量无关：

| | 本项目 | 稠密 7B/8B |
| --- | --- | --- |
| 模型 | 35B-**A3B**（激活约 3B） | 7B（全激活） |
| 词表 | **248,320** | 32k–128k |
| `lm_head` 参数 | 248320×2048 = **508M** | 32000×4096 = **131M** |
| 每 token 实际计算 | ~3B | ~7B |
| **`lm_head` / 单 token 计算** | **17%** | **1.9%** |

实测吻合（`topology-local-32-8.toml`，tail 段 8 层，本机 CPU）：

    单行 37.6 ms = 8 层约 25.3 ms + lm_head 12.3 ms  →  lm_head 占 33%
    （lm_head 由 `slimarc/prototype:checks/bench_lm_head.py`（v2，已退场）实测：M=1、q6_K、本机 6 线程、reps=15）

---

## 3. 为什么最优 k 更小

投机解码的验证是"一次提交 k+1 行"，成本随行数增长的部分是 `lm_head`，能被 batch 摊薄的是层计算。

稠密 7B 验证 48 行时 `lm_head` 约占 26%（大 k 几乎免费）；本项目验证 6 行时**占 57%**
（实测：M=6 的 33.0 ms ÷（33.0 + 8 层 25.3 ms）= 57%）。
所以社区能上 `m=48`，我们的拐点是 **k=5**——不是实现差，是结构决定的。

---

## 4. 为什么 n-gram 这类方法天然吃亏

n-gram 的价值在于"一次给很多草稿"（`m=24~64`）。它的成本前提是**大 k 不贵**。

而在本项目：

- 大 k 的代价主要是 `lm_head`，且它按 16 列一档阶梯增长（§5）
- `m_eff`（每轮前进倍数）要过盈亏线 2.5，长历史 + 重述型负载才够
- 两者相乘之后，只剩"长文件重写"这种极端场景可能为正

实测（`slimarc/prototype:checks/probe_ngram_replay.py`（v2，已退场），6 个真实场景）：只有"重述已有代码 128 token"过线
（m_eff 3.05），而它需要 `m=8` → 9 行验证，成本上仍然亏 6%。

---

## 5. `lm_head` 的成本形状：阶梯，不是直线

`output.weight` 是 248320 × 2048 的 q6_K（397.9 MiB）。它的成本**不随行数线性增长**：
`ggml-cpu.c` 把 `mul_mat` 按 16 列一档分块（`chunk_size = 16`，`nchunk1 = ceil(ne1/16)`）。

实测（`slimarc/prototype:checks/bench_lm_head.py`（v2，已退场），直接调 ggml 的 `MUL_MAT`，本机 i9-13900H，`n_threads=6`；
每点报中位与 min，`--reps` 默认 15）：

| M | q6_K |
| ---: | ---: |
| 1 | 12.0 ms |
| 2 | 16.4 |
| 4 | 24.0 |
| 6 | **33.0** |
| 8 | 53.2 |
| **16** | **52.9** |
| 17 | **81.3** |

**6 → 8 行跳 63%（33.0 → 53.2），跳变点是 `TILED_MM_MIN_ROWS = 8`**：8 行起改走 tiled
路径，而这个 shape 上 tiled 并没有更快。所以要避开的不是"多两行"，是"跨过 8 行"。

**M=8 与 M=16 同价，M=17 跳 54%。** 所以"k 少两行省一点"在这条路上一分钱也省不到——那
6 行整个落在第一档内。这也解释了拐点为什么在 k=5：k=5 的验证块是 6 行，还在 8 行门槛之下；
k=7 就是 8 行，直接吃 20 ms 的跳变。

**两条常见假设不成立**：（a）验证成本随 k 线性涨——实测是阶梯（上表），M=8 与 M=16 同价；
（b）补上 x86 的 Q6_K 交错 GEMM 能摊薄——**M=1 时交错是负收益**（`q4_K/repack` 0.3064 对
`plain` 0.2927 ms/op，慢 7%），每专家只有 1 行、没有行可摊薄。上游三个 PR 的 `tg −2.5%~0%`
就是这件事的证据（见 §6.5）。

把 `output.weight` 单独放上 GPU（`SA_OUTPUT_GPU=1`）也只能省 37%（k=16 时 164.8 → 125.3 ms），
k=5 只省约 11 ms/轮——因为 248320 × 2048 是极瘦 GEMM，CPU 和 GPU 都填不满。

## 6. 推论

1. **不能照搬社区参数。** 社区的 `m=24~64` 建立在稠密模型上；本项目 k=5 是结构决定的最优。
2. **大词表是隐性成本。** 248,320 的 vocab 带来多语言能力，但让每个候选 token 的验证固定多
   7 ms。若只看投机效率，词表小一半、k 能翻倍。
3. **改 kernel 的收益上限很低。** 三条复用路线默认全开，剩下的空间是"把 148 提到 232 GFLOP/s"，
   约 10–15%，且要动最热的公共路径——**所以先试换量化类型，不写内核**。
4. **要真正改变这个结构**，得动词表或换投机范式，不是优化矩阵乘。

---

## 6.5 更一般的规律：通用性是要付钱的

上面这些不是 MoE 独有的毛病，而是**引擎为兼容付出的代价**的一个切面：

- `ggml` 的 repack traits 表要为每个 `(量化类型 × 架构)` 组合准备内核。x86 的 Q6_K 那一格
  至今是空的（`repack.cpp:4930`），于是 Q6_K 只能走通用 `vec_dot`。
- 上游试过三次（#15275 closed、#19706 至今 open、#27590 closed），**它们不是同一件事**：
  前两个是 Q6_K 的 8×8 交错（+4264 行，全部依赖交错布局，`tg −2.9%`）；#27590 **不是交错**，
  只改 `arch/x86/quants.c` 的 `vec_dot_q5_K/q6_K`，用 AVX-VNNI 的 `vpdpwssd` 替 madd+add。
- **#27590 的数字反过来证明了本节的观点**：q6_K 的 dot 从 2.84 → 1.97 cyc/32 值（**−31%**），
  端到端 `tg` 却是 3.162 → 3.176 t/s（**0%**）。dot 快三成、整链不动——**内核不是天花板**。
- **x86 上 Q6_K 那一格空着的原因是 M=1 时交错 GEMM 本来就没有收益**：交错的价值来自多行复用
  权重，而 decode 每专家只有 1 行。实测 `q4_K/repack` 0.3064 ms/op 对 `plain` 0.2927——**慢 7%**。

**所以"不同架构的优化方向可能相反"不是修辞**：

三组具体对照：**MoE vs 稠密**（大 k 便宜 vs 贵）、**词表 248k vs 32k**（k 可翻倍 vs 要压到 5）、
**量化类型**（Q4_0 有 VNNI 路径 vs Q6_K/Q5_K/IQ4_XS 在 x86 都没有交错 GEMM）。

### 机制要说准：不是"抽象→慢"，是"抽象冻结了本可常量折叠的自由度"

分派本身几乎不花钱——一个 107 分支的大 switch（`ggml-cpu.c:1754`）每 token 只值几十微秒。
真正的代价是 `ggml_vec_dot_t` 把**类型、布局、输出落点**三样全变成运行时变量，于是通用路径
只能每行一次间接调用、写栈上的 `float tmp[32]`、再 `memcpy` 回写
（`ggml-cpu.c:1212-1213, 1219, 1253, 1257`）。专用 kernel 赢的不是"少跳一次"，而是
**k-loop 整个被编译器看见**。

**损失 = 该自由度在热点里的占比。** 这就是同一个缺口在稠密 7B（占 1.9%）是噪声、在本项目
（占 17%）是主成本项的原因——也是"缩窄范围"全部价值与全部风险的来源。

最强的证据来自同一份代码内部：**llama.cpp 的 CPU 侧通用、GPU 侧全面特化**
（`mmq-config-{ampere,blackwell,cdna,gcn,pascal,rdna2,rdna3,rdna4}.cuh` 十份 per-arch 配置）。
同一个项目对同一件事做了两个相反的选择——所以"通用不可避免"不成立。

上游自己的注释也承认过（`ggml-cpu.c:1469` "can be optimized... keeping it like this for
simplicity"、`:1200` "not sure if it helps"）。

### 推论：缩窄的粒度选 op，不选架构

收益 ≈（该自由度在热点占比）×（缩窄能省的比例）− 维护成本。

- **架构级是坏解**：维护面 O(arch)——`case LLM_ARCH_` 全树 468 处（`llama-model.cpp` 371、
  `llama-arch.cpp` 95）；换代风险全押在架构上（nextn 层号、`blk.40`、MoE 元数据，换代即失效）；
  分叉的那层正是上游每周在改的（`repack.cpp` 5260 行 / `ops.cpp` 12512 行）。
- **op 级是好解**：`lm_head` 是一个 op、与架构无关，维护 O(1)；走 `traits.cpp:12` 的既有钩子
  则受上游 API 契约保护。

**关键一条**：本项目已经跑过"缩窄到极致"的负例——**两进程层段拆分只有单进程的 61%**
（15.4–18.4 对 28.02 tok/s，`MEASUREMENTS.md` §1），权重重复与跨进程同步吃掉全部收益。

> **所以"缩窄 = 更快"是错的。"缩窄 = 把运行时未知变成编译期已知"才对**，只在能让编译器
> 看见常量的地方成立——切进程不是，换 kernel 是。

判断标准不是"通用好不好"，而是：该 op 热点占比是否 >10% 且有实测、模型族是否稳定一个换代
周期、能否挂既有钩子而不新增分叉。对本项目（单模型 35B-A3B、长期跑）答案是"值得"。

## 6.6 本项目最大的类型缺口：专家张量在 x86 上全无优化内核

上面 §6.5 说"通用引擎的性能由它服务过的最差组合决定"。本项目的组合恰好很差：

| 张量 | 数量 | x86 交错 GEMM |
| --- | ---: | --- |
| `ffn_*_exps` | IQ4_XS 63 / Q5_K 30 / Q6_K 27 | **都没有**（IQ4_XS 连 NEON 也没有；Q5_K/Q6_K 只有 NEON） |
| `attn_*` 全部 | Q6_K 90 | **没有** |
| `output.weight` | Q6_K 1 | 没有 |
| `ffn_*_shexp` | Q8_0 41 | 有 |

**但"没有内核"不等于"补上就赚"**：M=1 的交错 GEMM 本身是负收益（−7%），因为每专家只有
1 行、没有行可摊薄。这张表描述的是**一种看起来像缺口、实际不该补的东西**；真正的瓶颈在别处
（见本节末）。

只有 `Q4_K` 在 x86 上有 AVX2 8×8 内核（`repack.cpp:5012`），而**本模型里一个 Q4_K 张量都没有**。

这是 `Q4_K_M` 这个档位的设计：它把注意力、`output.weight`、共享专家提到 Q5_K/Q6_K/Q8_0，
把普通专家留在 IQ4_XS。**对精度是对的，对 x86 的速度是反的**——被提升的类型全在"无内核"
那一侧。

**所以"换量化"不是无脑降精度，而是一次精确的手术**：

- **只换 IQ4_XS → Q4_K**：4.25 → **4.5 bpw（略升）**，零降智风险。
- **不要动注意力和 `output.weight` 的 Q6_K**：那是 `Q4_K_M` 刻意保留的高精度部分。
- **补内核（Q5_K/Q6_K）反而最不该做**：Q6_K 每字节效率已经最高（0.0677 对 q4_K 0.0650），
  交错版只会重演 −7%。

**天花板不在内核**（#27590 的 −31% dot 换来 0% 端到端就是证据），而在**访存与窗口宽度**。

**每个专家的循环只有一次 barrier**：HEAD 上它在循环前（`ggml-cpu.c:1683`），
`ggml-cpu.c:1685-1749` 里专家之间是 `atomic_current_chunk[cur_a]` 的工作窃取，线程各自推进。
而"整张 op 一起并行"这件事，上游已经做了：**tiled matmul**（默认开，`GGML_CPU_TILED_MM`，
入口 `ggml-cpu.c:1693` → `tiled.cpp:838`），把每专家变成 64 行 × 256 列的 GEMM 窗口，
激活一次装载广播到 64 行。

实测（`slimarc/prototype:checks/probe_moe_cache.py --token-graph 6`，iq4_xs，25 reps 取中位、脚本同时记 min/max，
2026-11-02）：

| threads | tiled on | tiled off |
| ---: | ---: | ---: |
| 1 | 0.497 ms/op（8.4 GiB/s） | 0.585（7.1） |
| 4 | **0.234**（**17.7**） | 0.415（10.0） |
| 8 | 0.263（15.8） | 0.332（12.5） |

**tiled 已经兑现 1.42×**。本节末表的 iq4_xs 0.3287 ms/op、40.4 ms/token 是 **tiled OFF**
口径，引用时须注明 `GGML_CPU_TILED_MM` 的状态。

剩下的头寸是真的：4 线程 17.7 GB/s 对纯读上限 37.7–45.6 GB/s（`checks/probe_bw_ceiling.c`
实测 1 线程 15.6、4 线程 37.7–45.6、8 线程 56.6），`[推断]`
2.0–2.4× 仍成立。但**杠杆在 tiled 的窗口宽度与预取**（`tiled.cpp:719` 的 `TILED_MMID_GROUP`
64 → 128/256、解包前软件预取、`nrows==1` 时省掉 `tiled_repack_src1`），**不在
`ggml-cpu.c` 的循环结构**。

**实测（2026-11-02，6 个专家 bank 串进一个 graph，模拟真实 token 的 123 个 op；各点取中位）**：

| 类型 | ms/op | 123 op/token |
| --- | ---: | ---: |
| q4_K/plain | 0.2927 | **36.0 ms** |
| q4_K/repack | 0.3064 | 37.7 |
| iq4_xs/plain | 0.3287 | 40.4 |
| q6_K/plain | 0.4445 | 54.7 |

**重转全 Q4_K 是 +26%，零代码**（要配 `--no-repack`；默认走 8×8 只剩 +21%）。

而单 op 微基准给出的相反结论（IQ4_XS 0.348 < Q4_K 0.436）是**方法学假象**：每 op 付一次线程
唤醒，唤醒成本与字节数无关，于是系统性偏袒字节少的类型。摊到 123 个 op 之后排序反转。**类型
之间的比较必须交错测量**——同一 IQ4_XS 点在顺序测量的两次 run 里给出 28.4 与 42.9 ms/token。
