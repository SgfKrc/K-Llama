## 1. 问题：主节点身份是"部署时钉死"的，而且理由已经消失

**当前实现（源码证据）**：

| 位置 | 事实 |
| --- | --- |
| `src/config.py:450` | `NODE_ROLE` 默认值 = `"master" if getattr(sys, "frozen", False) else "client"` —— 角色来自**环境变量/打包形态** |
| `src/config.py:452` | `_normalize_node_role(_initial_role)` —— 角色是一次性解析的常量 |
| `src/config.py:485` | `CLIENT_MASTER_HOST` / `CLIENT_MASTER_PORT` —— 从节点连谁，是**静态配置** |
| `src/bootstrap.py:76` | `select_advertised_master_host()` —— 只决定"广播哪个 host 当入口"，**不是选举** |
| `src/api_server.py:7470` | 已有 `presence_generation` / `presence_lease_id` —— 存在**租约与代次**的概念，但用于 Android presence，**没有用于主节点身份** |

**为什么这是结构性问题**：

1. **主节点的职责已经与 GPU 算力解绑**。P0–P4 之后，主节点承担的是控制面：设备画像、容量计划、
   层段合同、准入、租约与 epoch fencing、任务图调度。它**不需要 CUDA**，也不是吞吐瓶颈所在。
   ⇒ 但"谁是主节点"仍然由**部署时的一个环境变量**决定 —— 于是整个集群的管理角色被钉在
   一台**与它的实际能力无关**的机器上（可能是最弱的那个）。
2. **边缘集群的算力排序本来就会变**：设备上/下线（y700 会休眠、Surface 会合盖）、负载波动、
   热降频、网络路径变化。静态身份无法跟随，只能靠人工改配置重启。
3. **代价不对称**：主节点选错（选到弱机）会持续拖慢整个集群的调度与准入；而"谁是主节点"
   恰恰是**最容易按能力自动决定**的一件事。

设计口径（2026-09-21 起）：
> 主节点身份不永久固定，按 CPU 算力自选，并配套完整的分布式管理机制。

## 2. 目标

| # | 目标 | 可验证形态 |
| --- | --- | --- |
| G1 | **受约束自选**：只有拿到集群授权的候选才能按管理能力排序成为主节点 | 有效多数派时产生唯一可写主；无多数派时所有候选降为只读/不可提交 |
| G2 | **可迁移**：更强的候选上线、或现任主节点降级/掉线时，主节点身份可以**交接** | 交接完成后旧主不再是主，且新 term/epoch 由授权集签发并严格递增 |
| G3 | **不脑裂**：任何时刻**至多一个**持有有效 quorum certificate 的主节点可以提交状态 | 旧主失去有效证书后写入被拒（fail-closed）；本地看到更大 epoch 不能单独取得写权 |
| G4 | **不改数值面**：主节点迁移**不得**改变任何推理结果的判据 | 迁移前后同一 prompt 的 per-token argmax 一致（沿用现有判据） |

G4 是边界：P4.5 是**控制面**重构，必须证明它对数值面是透明的（这也是"系统软件内核 / 用户软件外壳"
分层里，控制面可以演进的那部分 —— 见 README「这是什么软件」一节）。

## 3. 设计

### 3.1 能力评分（候选排序）

主节点候选按**管理能力**打分，而不是按推理能力。建议维度（都可本地采集，无需特权）：

| 维度 | 采集方式 | 权重意图 |
| --- | --- | --- |
| CPU 逻辑核数 | `os.cpu_count()` | 主要项（按"CPU 算力最强"排序） |
| CPU 基准分 | 启动时跑一次固定微基准（矩阵乘/哈希，~100 ms，结果入缓存） | 区分同核数不同代次 |
| 可用内存 | `psutil.virtual_memory().available` | 控制面内存需求与容忍度 |
| 当前负载 | 采样 1/5/15 分钟负载或进程 CPU | 避免选到已被推理占满的机器 |
| 稳定性 | 在线时长 + 近期心跳丢失次数 | **平台中性**：按可测的在线/抖动表现排序；"平台是 Android 所以降权"**不得**作为内建规则（见 §3.5） |
| 网络位置 | 与多数节点的 RTT 中位数（tailnet 直连/中继） | 减少控制面延迟 |
| 角色约束 | 是否被运维显式钉为 `client`（opt-out） | 尊重人工意愿 |

**输出**：每个节点一个 `master_score`（浮点）+ `master_score_version`（评分算法版本，
避免不同版本节点互相比较）。评分**不参与数值面**，只影响排序。

**关键取舍**：评分是**启发式**，因此选举必须能容忍"选错"。为此 G2（可迁移）比"选得绝对准"更重要 ——
先保证能换，再逐步调准。

### 3.2 选举与续租（谁持有 quorum certificate，谁是主）

原设计的“广播 + 先到先得 + `max(seen_epoch)+1`”不能证明 G3：网络分区时两侧都能看到租约过期、各自生成 epoch 并继续写入。新的安全基线如下：

1. 集群维护带版本的 `voter_set`。每个投票节点使用已有 Ed25519 节点身份签名；节点能力/score 只决定候选顺序，不产生投票权。
2. 选举、续租和 term 分配必须取得上一版 `voter_set` 的严格多数签名，形成 `QuorumCertificate{cluster_id, voter_set_epoch, term, leader_id, lease_id, expires_at, signatures}`。没有多数派时不得产生可写主。
3. 一个 voter 在同一 `voter_set_epoch + term` 最多签一个候选；term 由持久化的投票/任期记录推进，不能由候选单独用 `max(seen_epoch)+1` 生成。
4. 状态提交（容量计划、层段合同、任务图控制状态、模型/分片租约）必须携带证书摘要和 `(term, lease_id)`。接收方只有在证书可验证、租约未过期、term 不低于本地已提交 term 时才接受；只有本身仍能维持多数派的主才允许继续写。
5. `NodePresence` 仅用于发现和候选观测；它不能授予主权。广播/发现也不能替代已认证的 TCP/控制面请求。

这不是引入完整 Raft 数据复制，而是先实现最小的多数派租约/投票合同。单节点或两节点没有外部 witness 时，自动故障接管必须保持关闭；可以继续使用人工 TOTP 转让，但转让结果仍必须落入同一 term/证书校验路径。

### 3.3 交接（handoff）

主节点迁移不是"重新开始"，要交接四类状态：

| 状态 | 交接方式 | 失败时的行为 |
| --- | --- | --- |
| 任务图（`TaskGraphCoordinator` 的在途任务与预约） | 先只转移已落盘、可重放的 journal 状态；当前在途任务不得假定可从 `snapshot()` 恢复 | 旧主失联时任务按 lease 超时/幂等重试处理；在途任务不得声称“已迁移” |
| 容量计划 / 层段分配（`pipeline_capacity` / `pipeline_reshard`） | 传 manifest（已是可序列化契约） | 新主重新求解，不猜测旧主状态 |
| 租约与预约（worker 预约、模型加载预约） | 按 `term/lease_id` 转移；旧 term 的预约在新 term 下**默认失效** | 默认失效而非默认继承（避免幽灵预约占用算力） |
| presence / 心跳表 | 新主从自己的视角重建，旧主数据仅作参考 | 允许短期不一致，以心跳为准 |

**交接的原子性**：term/证书签发、manifest 摘要和新主状态提交必须由同一控制面事件记录；不能把两个节点各自写入本地 SQLite 描述成跨节点原子事务。未完成证书提交时维持只读或回退到人工接管。

### 3.5 集群构成中性：不假设有 PC，也不预设平台排除

**两条约束（2026-09-21 起）**：

1. **不假设集群里有 PC 节点**。边缘集群的实际构成**未知**——无法确认现场是 Linux 开发板更多
   还是 Android 设备更多，也完全可能**一个 PC 都没有**。因此"主节点/上游需要一台 PC"这类
   隐含前提不得出现在设计里。
2. **不预设"Android 不能当主节点"**。此前草案里"Android 默认不自动取得 voter 身份"是一个
   **未经验证的假设**（依据只是"移动端会休眠"），**降级为待定项**，并且必须做成
   **可更换、可裁撤**的策略：

| 项 | 调整后的做法 |
| --- | --- |
| voter 资格 | **只看能力合同 + 显式配置**（证书、term、可用性、score 下限），**不按平台预判**；Android 与 Linux 板走同一条资格路径 |
| "移动端降权" | 从**内建规则**降为**可配置策略**（默认仅按可测的在线/抖动表现排序）；策略本身有版本号，可整包更换或删除 |
| 决策依据 | 新增一张**设备构成调查票**（现场 Linux 板 vs Android 的比例、休眠模式、供电与常驻条件），作为"是否值得引入平台相关策略"的**输入**，而不是先写死结论 |
| 可裁撤性 | 任何平台相关策略都必须能**在不改 schema、不改协议**的前提下关闭；关闭后集群行为退化为"纯能力排序" |
| 休眠抖动 | 用**机制**解决而不是用平台标签解决：任期最短存活时间 + 续租 TTL + 交接确认（§3.2/§3.3），这对任何会休眠的设备都成立 |

**退化路径：没有 PC 时，层接力退化为纯 llama 接力**。D 档（PyTorch 上游）是**可选的加速/对照
手段，不是接力的前提**；当集群里没有任何适合跑 torch 的节点时（纯边缘集群），接力应退化为
**L→L**：所有段都由 llama.cpp 承载（head GGUF + 中间段 keep-head + cut GGUF 下游），并且
**具备 GPU 的 Android 平板也按同一路径参与**（GPU 后端由 llama.cpp 侧提供）。

- 仓内已有这条路径的 2 段形态：`l2l_llama` / `l2l_keep_head`（两侧都是 llama.cpp，中间用
  keep-head 通道吐 hidden）；多段形态见 §P2 续「多段拓扑」；
- **待验证项**：L→L 多段在"纯边缘集群"（无 PC、含 Android GPU 设备）上的数值与性能证据；
  Android 侧 GPU 后端的可用性与开关（属 D/E 层的既有工作，见 android 验证文档）；
- **判据不降级**：退化路径仍要求 per-token argmax 与同精度整模一致（不得因为是"无 PC 场景"
  就放宽判据）。

**关于"不能在设备上装 llama-cpp-python"（上一轮表述已修正）**：

准确说法是**不是不能编，而是成本与风险明显更高**。实测依据（本机 pip 绑定）：

| 补丁符号 | `llama_cpp.llama_cpp` |
| --- | --- |
| `llama_get_embeddings_nextn_ith` | **MISSING** |
| `llama_get_embeddings_layer_inp` | **MISSING** |
| `llama_set_embeddings_layer_inp` | **MISSING** |
| `llama_set_embeddings_nextn` | **MISSING** |
| `llama_get_model` / `llama_vocab_n_tokens` / `llama_get_logits_ith` | 都在 |

⇒ 用 pip 版做 **head/middle** 需要三件事：① 把它 vendor 的 llama.cpp 换成我们的补丁版（**可行**）；
② **给 `llama_cpp/llama_cpp.py` 补符号声明** —— 它是**逐函数 ctypes 声明**，不认识我们新增的符号，
**这才是真正的卡点**；③ 长期跟进上游维护这个 fork。此外 pip 版的构建选项（`GGML_*`、后端、OpenMP）
由它的 CMake 默认值决定、**不受我们控制**（而 shim 用我们自己的构建脚本），且编译要发生在**设备侧**
（Termux 现场装 clang/cmake/ninja，Surface 需 MSVC/MinGW，每个 Python 版本各编一次）。
相反，**tail 段不需要补丁**（只用 embd 注入 + logits 等标准 API）⇒ 若某设备**只做 tail**，
用 pip 包是可接受的**过渡手段**，但记录必须写清该段用的是**外部 pip 版本**。

**当前诚实结论**：退化路径的**数值正确性**已证（纯 llama 两段/三段 32/32，含真机中段；tail 的
shim 实现与 pip 实现等价）；"**位置上也完全不依赖 PC**"尚待第 2 项（设备端 head 角色 + 协议扩展）
落地。在此之前，本机在这条链路里的角色是"跑 head 段的普通 CPU 节点"（llama.cpp、无 torch、
无 GPU），**不等价于"集群必须有 PC"**。

## 4. 分阶段

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| **P4.5.0 安全契约与兼容边界** | 固化 cluster/term/voter/lease/certificate schema、错误码、只读降级和静态模式兼容；**不改变角色行为** | 契约测试先通过；无证书不能提交；旧模式不绕过 fencing |
| **P4.5.1 观测与评分** | 只采集并展示候选 score、版本、稳定性、voter 状态和“可否取得多数派”，**不改变主节点行为** | TUI/API/日志可解释；score 不再冒充选举裁决 |
| **P4.5.2 最小多数派租约** | 实现 voter ledger、term 分配、投票一次性约束、lease renew、certificate 校验；无多数派只读 | 双分区模拟中至多一侧取得证书，另一侧写入 fail-closed |
| **P4.5.3 自动接管** | `NODE_ROLE=auto` 仅在多数派证书路径启用；单/双节点继续人工 TOTP 或只读 | 主节点掉线后新主可写；无 witness 的两节点不自动接管 |
| **P4.5.4 计划内交接** | 复用现有 `ROLE_TRANSFER` 做控制面交接，但先提交新 term/certificate，再切换旧主写权 | 旧主被 fencing；交接事件可审计；不宣称在途任务已迁移 |
| **P4.5.5 恢复与任务语义** | 基于本地 journal 的可重放状态恢复；明确 in-flight 任务继续、取消重试或 `handoff_timeout`，不伪造快照迁移 | 崩溃/断线后任务无静默丢失；恢复状态可追溯 |

**顺序理由**：先修正安全不变量和兼容边界，再做观测/评分；之后才允许多数派租约和自动接管，最后处理计划交接与任务恢复。任何“先自选、后仲裁”的实现顺序都不再接受。

## 5. 验收判据（fail-closed）

1. **唯一性**：任意时刻，只有持有当前 term 有效 quorum certificate 的一侧可以提交状态；无多数派时全部写请求拒绝或进入只读，
   并且**报错要进错误码白名单**（不得泄露内部异常）。
2. **迁移可观测**：每次主节点变化都有 `(old_term, new_term, reason)` 记录；无变化时不得产生噪声。
3. **任务不丢**：交接期间在途任务必须落到"完成 / 显式转移 / `handoff_timeout` 上报"三者之一，
   不得静默消失。
4. **数值透明（G4）**：迁移前后跑同一 prompt，per-token argmax 一致（沿用 P3/P4 的判据与记录 schema）。
5. **候选排序可解释**：在同一 `master_score_version` 和相同资格集合内，主节点应按 score/稳定性/节点 ID 的确定性规则产生；score 低不构成安全失败，失去证书才构成安全失败。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 移动端（Android）休眠被误判为掉线 → 频繁换主 | **不靠平台标签，靠机制**：任期最短存活时间 + 续租 TTL + 交接确认（§3.2/§3.3）—— 对任何会休眠的设备都成立；"Android 降权/排除"是**待定假设**，且必须可整包裁撤（§3.5） |
| 低算力节点因心跳快而抢到主节点 | 主节点资格设**下限**（如 score ≥ 阈值），不足则从下一名顺延 |
| 交接期状态不一致导致幽灵预约占住算力 | **旧 epoch 的预约默认失效**（§3.3），宁可让用户重买一次算力 |
| 跨机推理正在进行时换主 | 只影响控制面：在途的层段接力按已签发的层段合同继续跑完；合同变更走下一轮 |
| 评分算法版本不一致导致排序无意义 | 记录 `master_score_version`；版本不一致时**按 node_id 字典序**保守裁决 |

## 7. 边界（不做的事）

- **不做**推理层的重排或重分片（那是 P2/pipeline_reshard 的职责）——P4.5 只换"谁在管"；
- **不做**完整 Raft/Paxos 数据复制栈；但**必须做最小多数派租约/投票证书**。仅靠租约 + epoch 无法满足“不脑裂”，
  无多数派时宁可只读，不以可用性换写安全；
- **不做**自动跨节点权重分发（与既有裁决一致：不内网传权重）。

## 9. 设计审计（2026-09-22）

### 9.1 结论

原设计**不能直接进入自动选举开发**。能力评分、租约和 epoch fencing 的方向可保留，但“广播 + 先到先得 + 本地 `max(seen_epoch)+1`”无法在网络分区时保证 G3。若按原顺序先做 `P4.5.1 自选`，会得到两个都能写入控制面的候选，而不是一个安全的主节点。

### 9.2 问题清单

| 严重度 | 问题 | 证据/影响 | 修订 |
| --- | --- | --- | --- |
| **P0** | 没有外部裁决者却声称“至多一个可写主” | 两侧都能观察到 lease 过期并自行续租；TCP 广播不是共识，`lease_id` 也不能让另一侧立即知道撤销 | 引入固定 voter set + 严格多数 `QuorumCertificate`；无多数派只读 |
| **P0** | `max(seen_epoch)+1` 不是全局 term 分配 | 并发竞选可生成相同 epoch；分区后新 epoch 可能只在一侧存在，接收方的“已见最大值”不是共享裁决 | term/投票记录持久化；每个 voter 每个 term 只签一个候选 |
| **P0** | “epoch + manifest 原子提交”在两个本地 SQLite 间并不原子 | `TaskJournal` 是本地 SQLite，且有实例锁；`TaskGraphCoordinator.snapshot()` 是观测投影，不是可恢复的运行时迁移协议 | 先做控制面事件/证书提交；任务迁移改为 journal 重放与显式重试，未实现前不宣称 handoff 完成 |
| **P1** | 审计前的决策文档与本立项冲突 | `docs/QLH异构分布式形态决策-2026-09-14.md` 原先写“人工 TOTP 快转让、不做 quorum”；本立项却要求自动接管 | 已同步修订为：单/双节点无 witness 只能人工转让或只读；自动接管必须走多数派票 |
| **P1** | `NODE_ROLE=auto` 尚未存在 | `src/config.py:_normalize_node_role()` 当前只归一为 `master/client`；`scheduler.init_nodes()` 仍按静态角色创建本地主节点或客户端 | 先实现兼容状态机，再启用 auto；显式 master 不能绕过 fencing |
| **P1** | Android presence 租约与控制面主租约边界混淆 | `presence_generation/presence_lease_id` 服务 Android presence 注册/心跳，不包含 voter、term 或控制面写权限 | 新增独立 control-lease schema，只复用 TTL/过期处理经验 |
| **P1** | score 不是选举裁决，且当前画像没有稳定的管理 score 合同 | 现有 `score_total`/scheduler weight 主要服务推理资源分配；CPU 基准、版本、签名、滞后和最低资格尚未固定 | score 只做候选排序；先完成版本化观测和资格快照，再参与选举 |
| **P2** | G4 数值透明判据过宽 | 主节点迁移可能改变 KV、采样状态或模型工件；只比较 prompt 的 argmax 不能覆盖控制面之外的状态变化 | 固定模型摘要、引擎、采样矩阵和输入；控制面先证明不改请求/工件，数值复验归入既有 P3/P4/P5 门 |

### 9.3 不变量修订

1. **安全优先于可用**：没有 quorum certificate 就没有自动可写主；网络分区时允许停写，不允许双写。
2. **score 不授予权力**：score 只能在同一资格集合内排序候选，不能覆盖 voter 身份、term 或证书。
3. **发现不等于裁决**：tailnet/heartbeat 只提供候选观测；所有主权、续租和状态写入必须走认证控制面。
4. **静态模式仍需 fencing**：`master` 只表示引导/单机/人工维护意愿，不得绕过 term、lease 和写入校验。
5. **任务迁移后置**：在途任务没有可恢复协议前，只能继续等待、按租约取消重试，或显式报告 `handoff_timeout`。

## 27. Durable journal replication core (2026-09-24)

Status: **authenticated TCP replication core and cross-process crash/reopen simulation implemented; physical HA acceptance remains open**.

- `src/journal_replication.py` adds a transport-neutral `JournalCheckpoint` and
  `build_checkpoint()`. A checkpoint contains the source node/stream identity,
  the complete workflow event prefix, the projection snapshot, an event hash
  chain from a fixed genesis digest, and a checkpoint digest binding the
  snapshot to that chain. Invalid schema, source identity, workflow identity,
  sequence gaps, forks, and digest mismatches fail closed.
- `DurableJournalReplica` persists the replicated event prefix and projection in
  a separate SQLite WAL database with `synchronous=FULL`. Applying a checkpoint
  is one transaction; replay is idempotent; incremental checkpoints must extend
  the existing chain; a backwards checkpoint, fork, missing sequence, event
  count mismatch, or tampered snapshot is rejected without exposing recovery.
- `src/journal_replication_transport.py` adds bounded length-prefixed TCP frames,
  HMAC-SHA256 authentication over the source identity and checkpoint, and
  authenticated durable acknowledgements. The default bind is loopback. HMAC
  does not encrypt traffic or provide quorum commitment; production deployment
  still needs protected transport and managed key provisioning/rotation.
- `recovery_status()` verifies the durable watermark, event sequence, event hash
  chain, snapshot identity, chain head, and checkpoint digest. Only a verified
  replica can produce `recovery_projection()`; `DurableJournalReplica.decide_recovery()`
  then invokes the unchanged local `cluster_recovery.decide_recovery()` policy.
- `tests/test_journal_replication.py` covers full and incremental replay,
  idempotency, source fork, sequence gap, reopen persistence, snapshot tamper,
  event tamper, wire round-trip, bad-secret rejection, and TCP delivery to a
  separate spawned process followed by receiver termination and durable reopen.
  These remain local cross-process simulations. Replication/journal/HA tests:
  **38 passed**; expanded quorum/fence/handoff/cross-host tests: **67 passed**.

This is deliberately **not** a consensus protocol or production-ready
deployment. Retry/backpressure, quorum commit index, snapshot compaction, key
provisioning/rotation, TLS, and online physical cross-node failure tests remain
open. It must not be described as physical cross-host HA recovery.
`production_availability_claim` remains `false` and `NODE_ROLE=auto` remains
disabled.

## 28. HA-CROSSHOST-01 physical follow-up #6 (2026-09-24): retry/backoff for lossy links (R-R2)

§26 left a hard boundary: at 5 % loss the SSH reverse-TCP smoke fails, and the failure point is a
**single** `listener.accept()` wait (measured SSH connect success ≈ 1/3 through the same proxy).
R-R2 closes the **code side** of that boundary by adding **retry with bounded exponential backoff**:

- `retry_delays()` — pure function (`base = 0.5 s`, doubling, **capped at 4 s**), so the policy is
  unit-testable and cannot make the smoke hang.
- `_ssh_works()` — the reachability probe now retries (`SSH_RETRY_ATTEMPTS = 3`).
- `_connect_with_retry()` — treats **"start the worker + wait for it to dial back" as one retryable
  unit**. A single `accept()` timeout is not enough on a lossy link: the right response is to start a
  **new** connection and wait again. Intermediate failures are reaped; the **last** process is *not*
  reaped, because the caller needs its `stderr` for diagnosis (the raised error carries `.process`).
- Both smoke flows (`_run_surface`, `_run_quorum_exchange`) now go through it, and their `finally`
  blocks reap only when the process actually exists.

**Why retry is the right fix**: an `accept()` timeout is *not* a protocol violation — it only means
that particular SSH connection never established. Retrying costs `0.5 + 1.0 = 1.5 s` of backoff and,
on the measured single-attempt success rate of ~1/3, raises the probability of a successful
establishment to **70.4 %** (2 attempts 55.6 %, 4 attempts 80.2 %).

⚠️ **CORRECTED 2026-09-24 — this projection is WITHDRAWN** (physical re-measurement, see §29 below).
It assumed the ~1/3 rate measured for a **bare SSH connect**, which does **not** transfer to the
end-to-end smoke (that also has to establish the reverse tunnel and exchange control frames). Measured
end-to-end rates are an order of magnitude lower (≈1/6 with retries disabled, ≈0–1/7 with them
enabled) ⇒ retry/backoff turned out **not** to be what this boundary needs. The 70.4 % figure is kept
above only to show what was claimed at the time — **do not cite it**.

**Evidence**: `tests/test_ha_crosshost_physical_smoke.py` — **17 passed**, including two tests that
use a **real socket and real subprocesses** (first two workers never dial back, a later one does), so
the `accept()`-timeout failure point is exercised for real **without depending on a remote host**.
HA / journal / cluster suites: **133 passed**.

**Still open (physical, needs an online peer)**: re-measuring 5 % / 15 % loss over a real link.
Surface was offline during this round (`ssh … Connection timed out`). Local `sshd` *is* running
(OpenSSH 9.5p1, listening on `:22`) but has no `authorized_keys`, so a **loopback** end-to-end run
would first need the user to authorise adding one. `production_availability_claim` remains `false`;
automatic role takeover remains disabled.

## 29. HA-CROSSHOST-01 physical follow-up #7 (2026-09-24): 5 % loss re-measured with Surface online (R-R2 physical side)

§28 implemented retry/backoff but could not measure the physical side (Surface was offline). Surface
(`tablet-2tlucnu8` / `100.100.52.106`) is now online (`tailscale ping` ⇒ 19 ms direct), so this round
re-runs the **same** lossy profile across configurations.

**Setup** — `scripts/ha_crosshost_physical_smoke.py`, `--weaknet-delay-ms 30 --weaknet-loss-pct 5`
(the §26 profile), `--long-steps 1`; the worker is streamed over SSH stdin and never written to the
remote disk. Evidence under `local_docs/evidence/ha-crosshost/`. Three env knobs were added so that
scanning needs no code edits (**all defaults unchanged**): `QLH_SSH_RETRY_ATTEMPTS` (3),
`QLH_SSH_FIRST_FRAME_TIMEOUT_S` (15), `QLH_SSH_CONTROL_TIMEOUT_S` (15).

| configuration | attempts | success |
| --- | --- | --- |
| baseline `c587524` (**retry code absent**) | 1 | **1 / 6** |
| `dev` (retry, default knobs) | 3 | **0 / 6** (plus one separate run that passed ⇒ ≈1/7) |
| `attempts=4` + first-frame/control timeout 45 s | 4 | **0 / 3** |
| `attempts=8` | 8 | **aborted** — stalled (>25 min for one round, no `ssh` child alive) |

**Conclusion — retry/backoff does *not* lift this boundary.**
- Raising attempts 1 → 3 → 4 gives **no measurable improvement** (≈1/6 vs ≈0–1/7 vs 0/3). The samples
  are far too small to distinguish — and that itself is the finding: there is no effect to see.
- Two distinct failure modes appear, the second of which is **new** relative to §26:
  `worker_connect_retry_exhausted:TimeoutError` (never established) and `physical worker disconnected`
  (established, then the tunnel dropped).
- With `attempts=8` the failure point **moved later** ("cannot establish" → "timed out after
  connecting"), which is why the two timeout knobs were exposed — but `attempts=4` + 45 s still fails.
- ⇒ The evidence points at the **injection/transport behaviour**, not at "too few retries":
  `--weaknet-bridge` drops **whole chunks** (`--weaknet-loss-pct`), not individual TCP segments, so one
  drop can cost an entire control-frame round trip — **harsher than a real 5 % loss**.

**Status**: `HA-CROSSHOST-01` **remains open on the physical side**. R-R2's *code* side stands (pure
`retry_delays()` + real-socket/real-subprocess tests; `tests/test_ha_crosshost_physical_smoke.py`
**19 passed**), but its premise — "retry is what this boundary needs" — is **not supported** by the
measurement, and the §28 numeric projection is withdrawn.

**Next options (a decision is needed; none taken here)**: (a) switch to per-*packet* loss injection
instead of whole-chunk drops; (b) treat the lossy profile as **out of scope for the smoke gate** and
validate on a real carrier link instead; (c) keep the knobs configurable and let the acceptance owner
pick the profile. `production_availability_claim` remains `false`; automatic role takeover remains
disabled.
