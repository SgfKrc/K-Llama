# 多设备自动分配：工程量与实施边界评估

> 状态：**方案（搁置）**——2026-11-10 起：§2 列的积木全部随 v2 退场，重启本方案前要先在 v2.1
> 的形态上重建预算模型与拓扑校验
> 更新日期：2026-11-03
> 适用范围：多设备自动分配是否做、做到哪一档、工程量与停手红线；读者为后续实现者。
> 背景：prima.cpp 的 Halda 调度器给了"自动分配"的参考实现，但我们的场景（2-3 台固定设备）
> 用不上它的 LP。相关结论见 `PRIMA-ANALYSIS.md` §3.2。

待定项：P2（自动采集远端档案）的启动时机——需设备数 ≥ 4（§1）；P1 的范围、工程量与
验收判据已定（§3、§7）。

---

## 0. 结论

**值得做，但只做一档；做完就停。**

| 档 | 内容 | 工程量 | 建议 |
| --- | --- | ---: | --- |
| **P1** | **设备档案手填 + 线性分割 DP + 生成候选 TOML** | **~250 行 / 1–1.5 天** | ✅ 做这一档 |
| P2 | 自动采集远端档案（探针 + gather 协议） | +~230 行 / 2–3 天 | ⏸ 等设备数 ≥ 4 再说 |
| P3 | prima 式 LP/Halda（806 行）与全量 profiler（2,745 行） | 不估 | ❌ 不做 |

**关键判断：工程量的大头不在"求解器"，而在三处基础设施**（§4）。求解器本身只有约 120 行，
因为段间成本可加（串行接力）且切点是一维分割，用线性 DP 就能求解，预算模型**已经存在**。

---

## 1. 什么时候才做（触发条件）

三个条件**同时**满足才开工，否则继续手写 TOML：

1. **设备数 ≥ 3**，或切点不再是"本机全部 + 远端剩下的"这种一眼可见的形态。
   现在 32:40 的切点是实测出来的拐点（`topology-cross-mtp.toml` 注释），自动分配赢不过它。
2. **至少两台机器有 GPU**。单 GPU 时切点由显存倒推，手算就够；
   多 GPU 才出现"谁背哪段"的组合问题。
3. **有一台设备装不下**（否则 `README.md` 的「这套东西的价值在哪」那节结论仍然成立：拆分本身是负收益）。

## 3. P1 的分期与工程量

### 3.1 第 1 步：设备档案（~40 行）

**独立文件 `devices.toml`，不进 `topology.toml`。** 理由：`topology.load()` 只返回
`tuple[Stage, ...]`，它读 `stage` 与 `source_layers` 两个键、其余一概不看——
把 `[device]` 塞进同一个文件，结果是**写了但没人读的孤儿字段**，而且为了读到它就得改 `load()` 的
签名（`chain_client` / `koakuma` / 测试全部要跟改）。设备档案的生命周期也不同：机器不常变，拓扑常变。

```toml
# devices.toml —— 每台机器的硬件事实，由人填或由探针刷新
[device."127.0.0.1"]
ram_avail_gib = 20.0
vram_avail_gib = 7.9      # 0 表示纯 CPU
model_bytes = 20820000000 # 该机器上整模的字节数（远端无法 stat）

[device."100.116.17.12"]
ram_avail_gib = 11.4
vram_avail_gib = 0
model_bytes = 20820000000
```

这**完全不触碰现有拓扑**：`topology.py` 一行不改，手写 TOML 仍可用，`--dry-run` 行为不变。

### 3.2 第 2 步：求解器（~130 行）——**用 DP，不用穷举也不用 LP**

穷举在 2–3 台时够用，但**4–5 台就爆**：

| 段数 | 切点组合 | × 每段 offload 配置（5^n） | 合计（推算） |
| ---: | ---: | ---: | ---: |
| 2 | 39 | 25 | 975 |
| 3 | 741 | 125 | 92,625 |
| **4** | 9,139 | 625 | **5,711,875** |
| **5** | 82,251 | 3,125 | **257,034,375** |

正确解法是**线性分割 DP**（不是 prima 的 LP）：

```
f[k][i] = 用前 k 台设备覆盖前 i 层的最小总成本
f[k][i] = min over j < i（i-j 满足 4 对齐）
          { f[k-1][j] + cost(device k-1, layers [j, i)) }
cost(d, lo, hi) = 调 estimate_ram_bytes / estimate_vram_bytes 判可行；
                  可行则给一个耗时估计，超预算则 +inf
复杂度 O(N · L² · C)：L=40, N=5, C=5 → 40,000 次评估（穷举的 1/6400，且与段数线性）
```

**DP 成立的前提**——两个都满足：
1. 成本对段可加：总耗时 = Σ 各段耗时（串行接力，`_walk` 就是这个结构）。
2. 段与段无耦合：只传 hidden，跨机 RTT 是常数，可以提到目标函数外。

`[推断]` 若将来出现"段间带宽不均匀"（比如一段走 Wi-Fi、一段走有线），RTT 不再可提，
DP 的状态要加一维"上一跳链路"——那时成本才真的变成图问题，届时再评估，**不要现在就加**。

**仍然不需要 LP**：prima 用 HiGHS 是因为它同时决定 `k`（圈数）、`w`（窗口）、`n`（上卡层数）
三个维度的整数规划，且设备数未知；我们 `k≡1`、设备是有限的给定集合，
DP 比 LP 更简单、更可解释、结果可复现，且不需要 HiGHS 依赖。

### 3.3 第 3 步：TOML 写出（~60 行）

`tomllib` **只读**（全仓库无写入库，`topology.py` 只 `import tomllib`）。两个选择：

| 做法 | 行数 | 代价 |
| --- | ---: | --- |
| 手写格式化（只支持我们用的子集） | ~60 | 无新依赖；格式必须与 `topology.py` 的解析对齐 |
| 加 `tomli-w` 依赖 | ~10 | 多一个依赖；`README.md` 快速开始那行 `pip install` 要改 |

**优先手写**：我们的 TOML 只有一个顶层标量 + `[[stage]]` 数组 + `[device]` 表，
60 行足够，且能控制注释输出（自动生成的配置必须带"这是候选，需人工复核"的抬头）。

### 3.4 合计

| 项 | 行数 | 说明 |
| --- | ---: | --- |
| 设备档案解析 | 40 | 含缺省回退与校验 |
| 求解器（DP） | 130 | 转移 + 预算门 + 回溯 |
| TOML 写出 | 60 | 手写格式化 |
| 测试 | 60 | 复用 `test_topology.py` 的 26 单测框架 |
| **合计** | **~290** | 扣除可复用部分后约 **250 行净新增** |

工期：**1–1.5 天**（不含"跑一轮实测验证候选是否真的更快"）。

## 4. 三个真实障碍（都不是算法问题）

### 4.1 远端预算无法直接复用

`chain_client.estimate_ram_bytes()` 与 `chain_client.estimate_vram_bytes()` 都**只算 `is_local`
的段**——因为远端在自己的机器上加载。

自动分配器要给远端算预算，必须**按设备分组后分别评估**：把"属于 ROG 的那一段"
当成"本机段"喂给 `estimate_*`，再用 ROG 的档案做上限比较。

**这是最容易写错的一处**：漏了这层转换，远端段的预算会被静默算成 0，求解器会
把所有层都塞给远端，而预检（`--dry-run`）也不会报错——因为真正启动时每台各自检查自己的。

必须显式写一个 `_evaluate_for_device(stages_of_that_device, device)` 包装，并在测试里
覆盖"远端有 GPU / 纯 CPU / RAM 紧张"三种。

### 4.2 远端路径无法 stat

`chain_client.stage_bytes()` 用 `stage.model.stat().st_size`。
远端段的模型路径在本机不存在 → 必须从 `devices.toml` 的 `model_bytes` 或远端 GGUF 头读，
否则 `stage_bytes()` 直接抛 `FileNotFoundError`。

这也解释了为什么设备档案是 P1 的**前置条件**而不是可选项——而且必须独立成文件（§3.1）。

### 4.3 耗时模型没有可靠来源

这是**唯一一个无解的问题**，也是 P1 与 P2 的分界线：

- `MEASUREMENT-PITFALLS.md` 已证明段内计时随 `n_past` 呈 U 型，单一数字会骗人；
- `PRIMA-LESSONS.md` §7 指出 MoE 的层间耗时有方差，而"每层常数耗时"是该假设的反面；
- prima 的 Halda 也栽在这里（`common/common.cpp:906-918` 按 FLOPs 求和，假设每层恒定）。

**结论：P1 的排序只做"预算可行性 + 层数/算力比例"这种粗粒度，绝不声称"预测 t/s"。**
一旦开始调耗时模型，就会滑向 P3。

## 5. 停手红线（出现任一条就停手）

1. **出现第二套预算估算**。自动分配必须 `import estimate_ram_bytes / estimate_vram_bytes`，
   不许复制一份"更精确的"。两套真相是这类工具腐化的起点。
2. **自动结果直接启动**。只允许"生成候选 TOML → 人审 → 正常启动"。一旦加 `--auto-start`
   或让求解器结果覆盖已有 `topology-*.toml`，就会有人拿它跑实验、然后无法复现。
3. **校准常数从 5 个变成 6 个**。现有 5 个都有实测注释。再加一个"修正系数"意味着模型
   已经不可解释了，那时该退回手写 TOML。
4. **探针引入平台 API**。fio / `mincore` / `io_uring` / WMI 任何一样出现，就是 P2 失控的信号
   （我们在 SLIM-ARC win32 移植上已经付过一次代价）。
5. **开始处理"弱设备剔除 / 自动加成"**。那是 prima 的 `common/common.cpp:1595-1657`
   （迭代移除只分到 1 层的设备）。我们 2-3 台设备不需要，加进来就是 P3。

## 6. 设计约束（四条硬规则）

1. **求解器是纯函数**：`(总层数, 设备档案, 模型字节) → 候选列表`，不做 I/O、不读环境、
   不启动进程。这样它能被单测覆盖，也不需要 mock。
2. **输出必须过 `topology.load()`**：候选 TOML 先写盘再用现有校验器读一遍，
   不通过就丢弃。复用 `topology._validate()` 的 10 条不变量，不新增校验。
3. **单机多段不是求解目标，但不是错误**：v2.1 把同机多段（`--split-tail-range`）做成一等形态，
   "同一 host 出现两次"是受支持的形态、收益是省一次跨机往返；求解器**不该**再拒绝它。仍优先
   跨机分摊，同机第二段留给人工决定——那条"每节点一段"的限制只属于 v2 的 Python 驱动链。
4. **设备档案与拓扑分文件**：`devices.toml` 是机器的属性，`topology-*.toml` 是这次实验的布局。
   合并会立刻产生"一个文件两个消费者、而其中一个只读一半"的耦合（§3.1）。

## 7. 验收判据（做完怎么算成功）

| 判据 | 标准 |
| --- | --- |
| 正确性 | 对现有 `topology-cross-mtp.toml`（32:40，`-ngl 32 -ncmoe 24`），求解器应给出**同一档或更差**的候选；若它宣称"更优"，说明排序模型错了 |
| 可复现 | 同一输入两次运行，输出逐字节相同（无随机、无时间戳） |
| 不劣化现状 | 手写 TOML 仍然完全可用，`--dry-run` 行为不变 |
| 可解释 | 每个候选附带"为什么选它"的三行理由（预算利用率、层数比例、被剔除的原因） |
| 无新依赖 | 不加 `tomli-w`，不改 `README.md` 的 `pip install` 行 |

---

## 8. 与 prima 的关系（一句话）

prima 的 Halda 证明了"自动分配"这件事可做，但也证明了它的代价：806 行 LP + 2,745 行 probe，
且**它的耗时模型在 MoE 上是错的**（`PRIMA-ANALYSIS.md` §5）。
我们只借它的**问题定义**（在 RAM/VRAM 约束下最小化总耗时），不借它的求解器与 profiler。
