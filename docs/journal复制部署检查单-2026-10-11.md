# journal 复制部署检查单（#93 收尾，2026-10-11）

> 状态：**历史参考**（quorum journal 复制部署要求已退役）
> 更新日期：2026-10-28（历史检查结果与脚本说明保留）
> 适用范围：保存旧 quorum journal replica 演练与部署检查证据；不再作为当前部署清单。

> **现行产品规则**：自动选主、quorum voter 与多数 journal 复制不属于支持运行时。本文中的 receiver 启动、密钥配置和跨机同步步骤已由[静态主节点部署与认证退役决策](静态主节点部署与认证退役决策-2026-10-27.md)取代。

本文把两件真机踩出来的部署事实固化成**可执行**的东西：

1. replica 接收端必须**持久运行**才算数（临时 ssh 子进程会被回收）；
2. 换版时必须**成套同步**，否则远端会以「quorum 不可用」的形式静静失败。

## 1. 组件

| 文件 | 作用 |
|---|---|
| `scripts/start_journal_replica_receiver.py` | 正式启动器（替代此前一次性的演练脚本）：校验 secret/端口/路径，可选 `--pid-file`，支持 `--print-plan` 干跑 |
| `scripts/start_journal_replica_receiver.ps1` | Windows 包装：找 python、检查 secret 在环境里、后台启动 + 落日志/pid，**不碰计划任务** |
| `scripts/verify_journal_replication_sync.ps1` | 换版同步检查单：打印必需文件的 SHA256，可比对远端（`-Remote` / `-RemoteRoot` / `-RemoteShell`） |
| `tests/test_journal_replica_receiver_script.py` | 启动器的最小测试（干跑、短 secret、缺目录、非法端口、secret 优先级） |

启动（干跑，不占端口）：

```powershell
$env:QLH_JOURNAL_REPLICATION_SECRET = '<40+ 字节 secret>'
powershell -File scripts\start_journal_replica_receiver.ps1 `
    -Replica D:\qlh\jr\node.sqlite3 -Port 9200 -SourceNodeId node-leader -PrintPlan
```

启动（后台，Windows）：

```powershell
powershell -File scripts\start_journal_replica_receiver.ps1 `
    -Replica D:\qlh\jr\node.sqlite3 -Port 9200 -SourceNodeId node-leader `
    -PidFile build\journal-receiver.pid
```

> secret 一律走环境变量 `QLH_JOURNAL_REPLICATION_SECRET`（命令行会出现在进程列表里）；
> 启动器与包装脚本都会拒绝短于 32 字节的 secret。

## 2. 持久化（开机/会话结束后仍在跑）

**Windows（本机 / ROG）**：`Start-Process -WindowStyle Hidden` 只在父会话存活期内可靠。
要跨重启，用**计划任务**（需你确认后自行创建，本仓库不自动安装）：

```powershell
schtasks /Create /TN "QLH-JournalReplicaReceiver" /SC ONSTART /RL HIGHEST /RU SYSTEM `
  /TR "powershell -NoProfile -ExecutionPolicy Bypass -File G:\C\PYT\qlh\scripts\start_journal_replica_receiver.ps1 -Replica D:\qlh\jr\node.sqlite3 -Port 9200 -SourceNodeId node-leader"
```

注意：`/RU SYSTEM` 的计划任务**不继承交互会话的环境变量**，因此 secret 需要写进任务环境或改用
机器级环境变量（`[Environment]::SetEnvironmentVariable(name, value, 'Machine')`）。

**Termux（Y700）**：需要 **Termux:Boot**（装上后 `~/.termux/boot/` 下的脚本会在开机执行）。
示例（放 `~/.termux/boot/start-journal-receiver.sh`，记得 `chmod +x`）：

```sh
#!/data/data/com.termux/files/usr/bin/sh
termux-wake-lock
cd "$HOME/qlh-jr"
QLH_JOURNAL_REPLICATION_SECRET='<40+ 字节 secret>' \
  python3 src/start_journal_replica_receiver.py \
    --replica "$HOME/qlh-jr/node.sqlite3" --port 9200 --host 0.0.0.0 \
    --source-node-id node-leader --pid-file "$HOME/qlh-jr/receiver.pid" \
    >> "$HOME/qlh-jr/receiver.log" 2>&1
```

真机踩到：**不要**依赖 `nohup ... &`（在这些设备上已验证不可靠）；要么用 Boot 脚本，
要么让某个长驻会话持有它。

## 3. 换版同步（真机事故的直接产物）

2026-10-11 三机接管演练里，远端 voter 只更新了 `cluster_auto_role_runtime.py`，没更新
`cluster_control_contract.py` ⇒ 它在 import 阶段就死了：

```
ImportError: cannot import name 'CommitWatermark' from 'cluster_control_contract'
```

表现是「voter 端口不监听 + 主节点只看到 quorum 不可用」，**看起来像网络故障**，极易误判。

**必需文件分两组**（改了 #93 语义就必须整组同步）：

- `control-plane-trio`：`cluster_control_contract.py`、`cluster_quorum.py`、`cluster_auto_role_runtime.py`
- `journal-set`：`journal_replication.py`、`journal_replication_transport.py`、`journal_replication_service.py`、`task_journal.py`

用检查单核对（本地打印 / 跨机比对）：

```powershell
# 本地
powershell -File scripts\verify_journal_replication_sync.ps1

# Windows 远端
powershell -File scripts\verify_journal_replication_sync.ps1 -Remote 'ROG@100.116.17.12' `
    -RemoteRoot 'L:\新建文件夹\LEDS_BJTU\src' -RemotePython python -RemoteShell windows

# Termux 远端（~/ 会展开成 $HOME）
powershell -File scripts\verify_journal_replication_sync.ps1 -Remote y700-ip `
    -RemoteRoot '~/qlh-jr/src' -RemotePython python3
```

输出解读：

- `OK` = 哈希一致；`SKEW` = **必须同步**（有偏差时脚本 `exit 1`）；
- `missing` = 该目录下没有这个文件 —— 对**只作接收端**的目录（例如 Y700 的 `~/qlh-jr/src`）
  这是预期结果：那里只需要 `journal-set`，不需要 `control-plane-trio`；
- `UNKNOWN` = 远端没解析出哈希（检查 `-RemoteShell` / `-RemotePython`）。

## 4. 与 #93 的关系

- 接收端是「多数耐久 ACK」的来源：不跑、或 secret 不对，就等于这一票不存在；
- 换版不同步会让 voter 直接死亡，把**版本问题伪装成网络问题**，与 #93「必须能区分
  多数不可用 / 多数不持有」的目标冲突，因此这里把它固化为检查单。
