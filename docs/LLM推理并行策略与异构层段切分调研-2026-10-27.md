# LLM 推理并行策略与异构设备层段切分：调研与切分建议

> 场景：QLH 三机四段、Qwen3.5-9B 32 层、batch=1、关注 TTFT 与 TPOT。当前 `master GPU [0,8)` → `master#cpu [8,24)` → `y700 [24,28)` → `Surface [28,32)`，全程串行。
> 标注：`[实测数据]` 本仓真机实测；`[论文]`；`[官方文档]`；`[源码]` 本仓代码事实；`[推测]` 无实测、由已知量外推，**必须换成实测才能当结论**。

## 0. 结论先行

1. **层间并行在数学上不存在**。前馈链只有一条路径，token t 的第 k+1 层必须等第 k 层。可并行维度只剩 token 维、batch 维、head/tensor 维、专家维，而这四者的可行性全由**往返次数 × RTT** 决定，与算力无关。
2. **GPipe / 1F1B / Zero Bubble / DualPipe 全部不适用**：它们的收益来源是"用多个 micro-batch 填气泡"，而 batch=1 的 decode 每步只有一个 token，可切维度为零；Zero Bubble 更依赖 backward 才能把 B/W 拆开。
3. **batch=1 下流水的收益恒为 0；能降延迟的只有"合并往返"（投机/合批），不是"拆分往返"（分块/流水）**。合并：固定税按 1/γ 摊销；拆分：固定税被收 γ 次。同一条 40~90 ms 往返的链上，后者必亏。
4. **当前 4 段里至少 2 段是纯税**。层从 6.84 ms/层的本机 CPU 挪到 20.1 的 y700、再到 ~30 的 Surface，每层都在加时间，只换来容量与"多设备协同"的叙事。反证：删掉 Surface 段一项，decode `216.6 → 156.8 ms`、`tok/s 4.3 → 6.4`（+49%），token 逐位一致 `[实测数据]`。
5. **"按各段耗时相等"在 4 段固定下几乎无解**：无约束等耗时解要求 y700 拿 1.4 层、Surface 拿 1.8 层，而切点必须是 `full_attention_interval=4` 的倍数 `[源码]`。强制每段 ≥4 层后，等耗时重分配相对当前只省 **4%**（§6.2）。2× 在"减段"和"投机"上，不在"重切层"上。
6. **最大单项杠杆是投机解码**：decode 单步 169 ms 的 stage 里固定项占 **94%**（hidden 仅 ~10 KB）`[实测数据]`，这笔钱按"次"付，可按 γ 摊；而 master GPU 每步 78% 时间在等对端 `[实测数据]`——正是 draft 模型的免费算力窗口。

## 1. Pipeline Parallelism：谱系与适用边界

| 算法 | 机制 | 前提 | batch=1 推理 |
|---|---|---|---|
| GPipe `[论文]` [1811.06965](https://arxiv.org/abs/1811.06965) | 切 micro-batch 依次灌段，末尾累积梯度 | batch 可切 | 不可用，切完每片只剩 1/γ token |
| PipeDream / 1F1B `[论文]` [1806.03377](https://arxiv.org/abs/1806.03377) | 1F1B 交替，压住在飞 micro-batch 数与显存 | 有 backward 可交错 | 不可用，退化为顺序 |
| Interleaved 1F1B / PTD-P `[论文]` [2104.04473](https://arxiv.org/abs/2104.04473) | 每设备持多个不连续层块，虚拟段减气泡 | ≥2 个在飞 micro-batch | 不可用，C=1 时气泡 100% |
| Zero Bubble `[论文]` [2401.10241](https://arxiv.org/abs/2401.10241) | backward 拆 B/W，用 W 填气泡 | **必须有 backward** | 不可用，载体不存在 |
| Chimera `[论文]` [2107.06925](https://arxiv.org/abs/2107.06925) | 双向灌批 | 双向独立数据流 | 不可用 |
| DualPipe `[官方文档]` [DualPipe](https://github.com/deepseek-ai/DualPipe)、[2412.19437](https://arxiv.org/abs/2412.19437) | 双向 micro-batch 对填 + 计算通信重叠 | 双向 micro-batch + 高带宽互联 | 不可用，两个前提都缺 |

### 1.1 气泡占比与传输/计算比（形式化）

设 S 段、段 k 有 n_k 层、单层耗时 c_k、每段每步固定开销 a_k、段间传输税 d_k、尾段回传 r。

```
串行：  T_ser = Σ_k (a_k + d_k + n_k·c_k) + r                       (1)
流水：  T_pipe(C) = (C + S − 1) · max_k (a_k + d_k + n_k·c_k / C) + r  (2)
```

(2) 是全文最关键的式子：**它把固定税 (a_k+d_k) 从"每链一次"变成"每工作单元一次"**——`max` 里的固定税不随 C 缩小，而 `(C+S−1)` 让它乘 C 倍。

- 气泡 `bubble = (S−1)/(C+S−1)`。C=1（我们的 decode）⇒ 100%，(2) 退化为 (1)，**收益恒为 0**，与怎么切段无关。
- 忽略 a、d 的乐观情形下，成立条件化为负载均衡条件：

```
ρ = max_k t_k / mean_k t_k < C·S / (C + S − 1)                      (3)
```

S=4、C=1 时右端 =1.0，而 ρ≥1 恒成立 ⇒ **无解**。这就是"batch=1 不可能靠流水加速"的形式化表达。
- 把固定税算进来更糟：以 §6.2 输入，y700 段 `d≈48 ms`、`n·c≈80 ms`，C=8 时 (2) 给约 760 ms，**比串行 467 ms 更差**，因为 8 份 chunk 各付一次 48 ms。

### 1.2 什么时候流水更慢

1. **固定税 ≫ 计算**：`d_k > n_k·c_k` 的段一经切细就是灾难。decode 的 hidden 仅 ~10 KB 而往返 40~90 ms，正是这一型。
2. **阶段不平衡**：时间为 `(C+S−1)·max`，最短段不参与，投在它上面的层数白花。
3. **同步成本**：中心辐射拓扑下每步 `2(S−1)` 次单向传输 `[源码]`，S 越多线性上升。
4. **硬件前提缺失**：Splitwise `[论文]` [2311.18677](https://arxiv.org/abs/2311.18677) 依赖高速背板做 PD 分离，MegaScale-Infer `[论文]` [2504.02263](https://arxiv.org/abs/2504.02263) 依赖专用 M2N 库消除拷贝与同步；2.4 GHz WiFi + CPU-only 对端上这些"重叠"没有物理前提。

**⇒ 对 pipeline 这一族，结论不是"选哪个算法"，而是"全都不该做"**。本仓已在 `docs/层流水线通信开销削减-机制设计与规划-2026-10-14.md` §8.2 列入负面清单，本文补形式化依据。

## 2. 异构设备的层分配算法

### 2.1 按什么分配

1. **实测单层耗时 c_k（首选）**。decode 是访存受限，`c_k` 天然吃进量化位宽、线程数、混合核调度。本仓已有 `fit_segment_profile` / `fit_two_segment` 在若干切点上回归"固定开销 + 每层"，再交求解器 `[源码]`。**不要用"整段平均 ms/层"排序**：同一份数据里 24 层摊 1.13、4 层摊 2.57 ms/层，固定开销会把结论带反 `[实测数据]`。
2. **按段取的实测 RTT**。`#71` 要求分段取：PC↔PC 3 ms、PC↔y700 19~43 ms `[实测数据]`，不能用全局中位。
3. **容量**——是硬约束，不是权重。它决定 `n_k` 上界。本仓 `compute_node_weight` 把 VRAM/RAM/CPU/加速器/孤岛加权求和 `[源码]`，那是**放置打分（选谁）**，不能当**层数分配（给几层）**，否则出现"master 恒为 `[0,8)`、主机 32 GB 全程闲置"的既有现象 `[实测数据]`。
4. **算力（FLOPS）**——几乎无解释力，用它排序会把集显排在 CPU 前。

### 2.2 均匀 vs 等耗时 vs 延迟最优

设 L=32、S 段、连续区间、切点对齐 q=4（层类型按本地层号对 interval 取模推导，切错则整体错位 `[源码]`）。

- **均匀**：`n_k = L/S`。只在同构集群上近似合理。
- **等耗时**（min-max，最小化 (2) 的 max 项）：求 K 使

```
n_k = (K − a_k − d_k)/c_k ,  Σ n_k = L ,  n_k ∈ {0} ∪ q·Z+          (4)
```

这是**吞吐目标**下的最优（C≫S 时 `T_pipe ≈ max_k t_k`）。对 batch=1 延迟**不是最优**：延迟看的是 (1) 的和式，均衡化只改 `max`，而延迟根本不看 `max`。

- **延迟最优**：由 (1)，

```
min Σ_k n_k·c_k   s.t. Σ n_k = L,  n_k ≤ cap_k/w_k,  n_k ∈ {0} ∪ q·Z+   (5)
```

这是 ILP，但目标对 `c_k` 单调，最优解有闭式结构：**按 c_k 升序水填充**——先喂满最快段的容量上界，剩余给次快段；**凡 `c_k` 不低于当前边际段耗时的设备，`n_k = 0`**（即"减段"）。这与本仓 `SegmentEconomics` 判据同源：

```
值得把 n 层挪给设备 X ⟺ n·c_cur > 2·RTT_X + n·c_X
                     ⟺ n > 2·RTT_X / (c_cur − c_X)   （仅 c_cur > c_X 时有解）
```

`c_X ≥ c_cur` 时无解 ⇒ **任何层数都不值得**，该段的价值只在容量 `[源码]`。

### 2.3 静态 vs 动态

静态：解一次、裁好工件、重启沿用，可复现且与"工件不可自裁"约束一致 `[源码]`。动态：外部未见"按 RTT 触发在线重搜切点"的先例 `[推测]`。真正的动态动机不是 RTT，而是 **c_k 随上下文漂移**：`n_ctx` 512→4096 时每层 ms 从 4.67 涨到 14.71（3.15×，2B 实测）`[实测数据]`。所以动态的正确粒度是**按上下文长度分档的静态表**（≤512 / ≤2K / >2K），不是逐请求重解——后者会带来切点迁移与缓存失效。

### 2.4 现成算法/工具

- **EdgeShard** `[论文]` [2405.14371](https://arxiv.org/abs/2405.14371)：边缘协作、**按层拆分 + 动态规划选切点**，报告延迟 −50%。与我们问题定义最接近。
- **HexGen-2** `[论文]` [2502.07903](https://arxiv.org/abs/2502.07903)：异构分组、组内 TP 组间 PP，同预算吞吐 1.3–2.0×，可借其"非对称 PP"思路（目标仍是吞吐）。
- **Helix** `[论文]` [2406.01566](https://arxiv.org/abs/2406.01566) / [代码](https://github.com/Thesys-lab/Helix-ASPLOS25)：max-flow/MILP 联合放置与路由，其 MILP 与 (5) 同构，可直接借建模。
- **Alpa** `[官方文档]` [alpa-projects/alpa](https://github.com/alpa-projects/alpa)：层/算子/流水三级自动并行，是"自动切分"最常见的工程实现；但其代价模型面向**同构 GPU + NVLink**，不含跨 WiFi 异构边缘。
- **nnScaler**（OSDI'24，微软）：约束引导 + 放置感知的并行方案生成，把合法方案表达为约束求解，与 (5) 的"连续层 + 对齐 + 容量"同构。**其单篇稳定 URL 本次未能在线核对，故不作 URL 引用。**
- **DeepSpeed Inference** `[官方文档]` [inference-tutorial](https://www.deepspeed.ai/tutorials/inference-tutorial/)：`inference.pipeline` 只支持均分或手写层号，无按实测 c_k 求解的能力，不能直接用。
- **GPipe 的自动切分**：原文按参数量均分 `[论文]` §3，为同构 TPU 设计，无异构权重。

## 3. MoE 与稀疏化的影响

- **层切分对 MoE 完全兼容**：专家权重按层归属，切在第 k 层就把该层全部专家一起切走，hidden 接口不变——**换 MoE 不需要改接力协议**。
- **专家并行（EP）在慢网下不可行**：每层每 token 都要 all-to-all，同步次数与层数同阶，比 TP 的 all-reduce 更重，判据见 (7) 且结论更差。
- **MoE 改变的是容量/速度天平**：激活专家少 ⇒ 单层计算便宜，但全部专家必须驻留 ⇒ 容量需求暴涨。这正是多机在延迟目标下唯一站得住的理由：**不是更快，是装得下**。可概括为"MoE 让层切分从速度手段回归容量手段"。
- **EPLB 类负载均衡**偏好"段多且均衡"，与我们"段少且快"方向相反 `[实测数据]`，不能照搬。

## 4. Tensor Parallelism 能不能用：不能

**判据是 RTT × 同步次数，不是带宽。** 每层至少 2 次 all-reduce（attention 输出、MLP 输出）：

```
T_TP ≈ (Σ_k n_k·c_k)/N + 2·L·t_ar ,  t_ar ≥ α ≈ RTT
可用必要条件：2·L·RTT < Σ_k n_k·c_k                                  (6/7)
```

代入 L=32、RTT=19 ms（y700 `[实测数据]`）：纯同步税 `2×32×19 = 1216 ms`，而当前整步才 ~284 ms（三段 R6 基线 `[实测数据]`），**4.3× 恶化**。反解可用上限 `RTT < 284/64 ≈ 4.4 ms`。

- 同机 loopback（≈0.1 ms）⇒ `2×32×0.1 = 6.4 ms`，尚可；跨机直接出局。
- 异构放大 straggler：TP 每层是同步栅栏，最慢设备决定整层，且**每层付一次**；PP 只在段边界付。
- 边缘 TP 确有正面工作（TPI-LLM `[论文]` [2410.00531](https://arxiv.org/abs/2410.00531) 靠内存滑窗 + 星型 all-reduce；Galaxy `[论文]` [2405.17245](https://arxiv.org/abs/2405.17245) 需 125 Mbps+ 局域网与 tile 重叠），但均自证瓶颈是链路延迟，且前提是**同构、高速、可重叠**，我们三条都不满足。
- **⇒ TP 只在"同机多卡 + NVLink/PCIe 直连"时是选项；跨 WiFi 异构三机，(7) 差 4 倍以上，不做。**

## 5. 降低 batch=1 延迟的其他手段

| 手段 | 机制 | 能否用 | 条件 |
|---|---|---|---|
| **投机解码** `[论文]` [2211.17192](https://arxiv.org/abs/2211.17192) | draft 猜 γ 个 token，目标模型一次验证 | **能，最大杠杆** | §5.1 |
| 合批（多请求拼 hidden） | N 个请求往返合并为 1 次 | 能（协议已支持多序列），需拆锁 | `PipelineQueue`/`_inference_lock`/`max_concurrency=1` 让路 `[源码]` |
| Chunked prefill `[论文]` [2403.02310](https://arxiv.org/abs/2403.02310) | 长 prompt 切块灌入、块间重叠 | **仅同机/高速链**；慢网按 (2) 变慢 | 固定税被收 C 次 |
| 层跳过 / early exit | 提前退出省层 | 现成 9B 无 exit head | 需微调 + 置信度判据；hybrid 的 recurrent state 回滚风险已记录 `[源码]` |
| 星型/并行分支 | 多分支同时算 | **不安全** | 前馈链只有一条路径，无结构可分叉 |

### 5.1 投机的收益条件：草稿放哪、验证怎么摊

decode 单步成本分解（`[实测数据]`）：`f=18 ms`（本地前向）+ `h=31 ms`（等 GPU）+ `s=169 ms`（全部层段 offer）；hidden 仅 ~10 KB ⇒ **固定项占 stage 的 94%**。prefill 侧拟合 `s ≈ 472 + 12.39×chars`（corr=0.9992）`[实测数据]`。

一次验证 γ+1 个位置时，**层段成本几乎不随位置数增长**（decode 访存受限，权重读取量与 token 数弱相关；本仓观察 Android 段"batch 2 几乎不涨，吞吐型" `[实测数据]`）：

```
每 token 有效成本 ≈ ( Σ_k(a_k+d_k) + Σ_k n_k·c_k(γ+1) + draft ) / γ_eff
γ_eff = 1 + (γ−1)·a_rate                                              (8)
收益条件：(8) < T_1  ⟺  γ_eff > 1 + (γ·Δc + draft)/T_1               (9)
```

固定税占 94% ⇒ `Δc` 很小 ⇒ (9) 极易满足，上限接近 `γ_eff`。与既有止损判据"`tokens_per_round ≤ 1.5` 或 `RTT > tokens_per_round/本地 tok/s` 则冻结"同源 `[实测数据]`。

- **草稿放哪台**：放 **master GPU**。理由不是快，而是它在空闲——每步 78% 时间在等对端 `[实测数据]`；draft 只产 token id、不跨段，是唯一能填这个洞且**不引入新往返**的工作项。（这正面回应了 `#63` 的"CUDA 空闲无工作项可填"：现在有了。）
- **验证成本怎么摊**：验证必须走完整条链（要真值 logits），但 **γ+1 个位置一次过链** ⇒ 摊薄的是 `(S−1)` 次往返税，正是最贵的一项。反面做法是把验证拆成 γ 次独立过链——那就是 (2) 的 C=γ 拆分，固定税 ×γ，必亏。
- **硬前置** `[源码]`：层段引擎当前无投机能力；hybrid 的 recurrent/conv state 无法撤销（回滚正确性是主要风险）；末段只回单值 argmax（需 `21b-0`）。验收必须是"逐 token argmax 与逐 token 基线一致"，不是 hidden 数值一致。

## 6. ★ 针对 32 层 / 4 段 / 异构 3 机的切分优化建议

### 6.1 可计算的分配公式

**输入**（每段一组、均可实测）：`c_k` 单层耗时；`d_k` 进入税（= 2×RTT_k + 编解码常数）；`a_k` 每步固定开销；`w_k` 每层权重字节；`cap_k` 可用容量；`r` 回传。**硬约束**：`q=4`、`n_k ∈ {0} ∪ 4·Z+`、区间连续、末段含 lm_head。

**延迟目标**（我们的真实目标）：

```
min_n Σ_k n_k·c_k   s.t. Σ n_k = 32 ; n_k·w_k ≤ cap_k ; n_k = 0 或 n_k ∈ {4,8,…}   (5)
```

**闭式求解**：① 按 `c_k` 升序；② `n_k = min(floor_q((cap_k − headroom_k)/w_k), 剩余层)`；③ 若 `c_k ≥` 边际段成本 ⇒ `n_k = 0`（省掉 `a_k+d_k`）；④ 剩余层由最后参与的段收尾。

**吞吐目标**（多请求填满流水）才用 (4) 的等耗时解。

> ⚠️ `c_1`、`c_4` 是估算，其中 **Surface 的 `c_4` 最不可靠且结论最敏感**。按 §6.4 一次 3 点标定即可替换。

**(a) 当前 `[8,16,4,4]`** 代入 (1)：

```
(5+8×4.5) + (3+8+16×6.84) + (48+10+4×20.1) + (22+10+4×30) + 15
=   41    +    120.4      +     138.4      +      152      + 15  = 466.8 ms  [模型估算]
```

**(b) 等耗时重分配**（4 段全活、每段 ≥4 层）。无约束解由 (4) 得 `K≈85.7`，要求 `n_3=1.38`、`n_4=1.79`——**低于 4，不可行**。故显式加"每段 ≥4"，剩余 24 层在段 1/2 间均衡（`5+4.5n_1 = 11+6.84n_2`、`n_1+n_2=24`）⇒ `n_1≈15`，取 4 的倍数：

```
[16,8,4,4] → (5+72) + (3+8+54.7) + (58+80.4) + (32+120) + 15 = 448.1 ms   相对当前 −4.0%
```

**⇒ "按各段耗时相等会是多少层"：`[16,8,4,4]`，只值 4%。** 因为 y700、Surface 的段预算 `a_k+d_k` 已超过等耗时值 K，怎么分都不划算；被"每段 ≥4"钉死后，可优化空间只剩 GPU/CPU 之间的 24 层。

**(c) 延迟最优（减段）**：

```
[8,24,0,0] → (5+36) + (3+8+164.2) + 15 = 231.2 ms        相对当前 −50.5%（2.02×）
[16,16,0,0] → (5+72) + (3+8+109.4) + 15 = 212.4 ms      −54.5%，但 16 层 fp16=9 GB > 8 GB，不可行
```

`[8,24,0,0]` 的 8 层是 fp16 主段容量上界（4.5 GB 权重 + KV/激活）`[推测]`，即"不换量化、不改引擎"前提下的延迟下界。**方向与实测 `#65` 一致**（删 1 段 tok/s +49%、延迟 −27.6%），这里是更激进的删 2 段外推。

**(d) 主段换 Q4 CUDA（单机全装）**：9B Q4_K_M 每层 ~175 MB，8 GB 可装 32 层，(5) 的容量约束失效，解塌缩为 `S=1`。带宽下界 = 5.6 GB ÷ ~256 GB/s ≈ **22 ms/token** `[推测]`（对照本仓 2.5B/24 层 llama.cpp CUDA 全层 26.6 ms/token `[实测数据]`）。量级比 (c) 还好一个身位，但它把"分布式"整个消掉——**这是产品目标与延迟目标的正面冲突，须产品裁定，不能用技术指标掩盖**。

### 6.3 策略对照表

| 并行/切分策略 | 适用场景 | batch=1 延迟场景是否适用 | 预期收益 | 落地代价 |
|---|---|---|---|---|
| GPipe / 1F1B / Interleaved / Zero Bubble / DualPipe | 训练、大 batch 吞吐 | **否**（C=1，气泡 100%；无 backward） | 0 | 无（不要做） |
| 等耗时重分配层数（4 段固定） | 多请求吞吐 | **部分**：只值 4%（`[16,8,4,4]`） | −4% TPOT | 低：改切点 + 重裁工件（约 1 天） |
| **减段** | 任何 | **是，最直接** | **−50%（2.0×，模型估算）**；同类实测 `#65` 删 1 段 −27.6% | 低：改分配、现成工件可复用；`#65` 已验证 token 逐位一致 |
| 合批（多请求拼批） | 并发 ≥2 | 对吞吐是，对单请求 TTFT 否 | 聚合吞吐 ↑，跨机未实测 | 中：拆四重串行锁 `[源码]` |
| Chunked prefill | 长 prompt + 高速链 | **仅同机/loopback**，跨机为负 | 同机小收益 | 中：多位置回程 + 状态语义 |
| **投机解码 γ** | batch=1 decode | **是，最大单项杠杆** | 上限 ≈`γ_eff`；先按 1.5–2× 预算 | 高：draft 接线、state 回滚、`21b-0` |
| TP | 同机多卡 NVLink | **否**（(7) 差 4.3×） | 负 | 高（且不该做） |
| EP（MoE 专家并行） | 高带宽 | 否（all-to-all 更重） | 负 | 高 |
| MoE 的层切分（非 EP） | 容量不足 | 是（**只买容量**） | 延迟 0、容量↑ | 低（协议不变） |
| 层跳过 / early exit | 有 exit head 的模型 | 现成 9B 不可用 | 未知（质量风险） | 高（需微调） |
| 星型 / 并行分支 | 有并行结构 | **否**（前馈链无分叉） | 0 | — |

### 6.4 落地步骤（把估算换成实测）

1. **3 个切点标定**：如 `[0,8)`/`[0,12)`/`[0,16)`，固定 prompt、固定种子，预热后取 9 步中位，**按段记 RTT**（`rtt_ms_from_heartbeat` 已可直接用在线心跳 p50 `[源码]`）。
2. **用现成拟合**：`fit_segment_profile` 回归 `(a_k, c_k)`，`fit_two_segment` 做两段对照，再交 `solve_relay_cut`（`qlh.relay_cut_plan.v1`）。**不要新写求解器**——(5) 与现有目标只差 `max`→`Σ`。
3. **校准**：拿 (a) 预测值与 R6 基线 `decode_median=284.5 ms`（三段）`[实测数据]` 对拍，相对误差 >20% 先修 `c_k`/`d_k`，再谈切分。
4. **验收**：任何切点变更以"同 prompt 两次运行 token 逐位相同 + 与整模 argmax 对齐"为门（81/81 argmax 门已有先例 `[实测数据]`）。

### 6.5 转折点：CPU 段慢到什么程度该把层挪回 GPU

**(i) 挪回"已在显存里"的 GPU 段**：每层省 `c_CPU − c_GPU = 2.34 ms`，**收益恒正、转折点不存在**；限制只在容量 `n_max = (cap − headroom)/w`，fp16 下 ≈8 层 `[推测]`。

**(ii) 靠 offload 挪回（权重驻留 RAM、每步过 PCIe）**：

```
c_offload ≈ w_layer / BW_pcie_eff ≈ 0.5625 GB / 8 GB/s ≈ 70 ms/层
实测 76.8 ms/层（safetensors_layer_offload）                          [实测数据]
转折点：c_CPU > 76.8 ms/层，而当前 6.84 —— 差 11.2 倍 ⇒ 结构性否决
```

**"哪怕显存放不下也要 offload 挪回 GPU"这条路，在本机被实测否决**：不是"再优化一下"的量级差。

**(iii) 真正的瓶颈段无法靠挪层解决**。`c_CPU` 上涨时把层挪走是直觉做法，但本场景不可执行：① GPU 段已饱和（fp16 下 `n_G ≤ 8`，正是当前值 `[推测]`），**没有空位**；② 其余段更慢，挪过去只会让总和变大（(5) 的死区情形）。所以这个问题指向错了变量，可控的是**每层字节** `w_k`：

| 主段量化 | `w_k` | `n_G` 上限 | (5) 的最优解 | 估算 TPOT |
|---|---|---|---|---|
| fp16 | 562 MB | ~8 | `[8,24,0,0]` | 231 ms `[模型估算]` |
| Q4_K_M | 175 MB | ~30 | 塌缩到 `S=1` | ~70–90 ms `[推测]` |

**⇒ 转折点是"主段能否把 562 MB/层降到 175 MB/层"，不是"CPU 慢到多少"。** 降下来后 `c_CPU > c_G` 恒成立，最优解一路推到全回 GPU。代价在数值与工程：本仓 `int4` 档有 **23/32 FAIL** 的实测反例（不可用），而 Q4_K_M 的 argmax **81/81** 仅在 CPU 段验过，**GPU 侧 Q4 无本仓证据**，必须先过数值门。

另有一类与上下文强相关的加重项：若 9B 与 2B 同比例（`n_ctx` 512→4096 每层 ms 4.67→14.71，**3.15×** `[实测数据]`），CPU 段 24 层会从 164 ms 涨到 ~516 ms。**此时"减段/降 w_k"的收益不是变小而是变大**——结论不变，只是 P0 更急。

## 7. 串行 vs 流水：决断

**问"现在能不能并行"，分三层回答，每层给条件：**

1. **层间并行：不能，且永远不能。** 第 k+1 层依赖第 k 层输出。任何声称做到的，都在偷换"不同 token"或"不同请求"。
2. **同一请求内的 token 并行（流水）：**
   - **decode：不能。** C=1，(2) 退化为 (1)，**收益恒为 0**，与怎么切段、用哪种调度无关。这是数学，不是工程限制。
   - **prefill：有条件可行。** 需 `C ≥ 2` 且 (3) 成立，**但**同时需 `C·Σ(a_k+d_k) < Σ n_k c_k`——本项目 `d_y700≈48 ms`、`Σ n_k c_k≈380 ms` 下 **C 最多 2~3**，超过就亏。即使 TTFT 能并行，收益上限也只有 10~20%，而代价是多位置回程 + 状态语义，不成比例。
3. **多请求并行：能，但需先拆锁。** 实测并发 1/2/4 的聚合吞吐是 **4.1 / 4.1 / 4.2 tok/s——完全不涨** `[实测数据]`，因为 `PipelineQueue` 单工作线程、`_inference_lock`、worker `max_concurrency=1` 把请求串起来了 `[源码]`。拆掉后聚合吞吐理论上限 `1/max_k t_k`；同机双后端的软件流水已实测 **1.291×**（天花板 1.79×，达成 72%）`[实测数据]`。**这是"并行"唯一站得住的形式，但它优化吞吐，不优化首 token 延迟。**

**优先级（对齐"首 token 延迟 + 后续 token 稳定吞吐"）：**

| 优先级 | 动作 | 依据 | 备注 |
|---|---|---|---|
| P0 | **减段到 2 段**（`[8,24,0,0]`） | 模型 −50%；同类实测 `#65` 延迟 −27.6% | 零协议改动、零数值风险；与"多设备协同"目标冲突，需产品裁定 |
| P0' | 4 段必须保留时，按 (5) 重算切点 | −4% | 同一求解器，只换目标函数 |
| P1 | **投机 γ**（GPU 空闲跑 draft） | 摊销 94% 固定税；上限 ≈`γ_eff` | 最大杠杆，前置最重（state 回滚 / 多位置回程 / `21b-0`） |
| P2 | 拆锁做多请求交错 | 聚合吞吐（同机 1.29× 已验证） | 改吞吐不改 TTFT |
| P3 | chunked prefill（仅同机/高速链） | TTFT 10~20%，跨机为负 | 不建议在 WiFi 链上做 |
| ❌ | GPipe / 1F1B / Zero Bubble / DualPipe / TP / EP / 星型并行 | 0 或负 | 列入负面清单，不再评估 |

**一句话**：现在的串行链**不该改成并行**，该改成**更短**（减段）和**更粗**（投机把多次往返合成一次）。"并行"在这个拓扑上没有可乘的维度——能重叠的只有 master 的等待时间，而填它的正确材料是 draft token，不是另一层。
