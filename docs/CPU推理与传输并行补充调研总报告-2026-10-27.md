## 1. 对三个原假设的裁决

提问时的三个判断：「CPU 推理占大头」「PCIe 带宽是关键路径」「CPU 计算速度/计算量是关键」。

| 假设 | 裁决 | 依据 |
| --- | --- | --- |
| CPU 推理占大头 | **成立** | CPU 段合计承担 8/32 层，且落在两台最弱机器上（4 核 Surface + 手机） |
| PCIe 带宽是关键路径 | **不成立**（推理期） | 每 step 跨 GPU↔CPU 边界只搬 hidden，**16 KiB**；在 PCIe 4.0 x8（15.75 GB/s）上传输部分约 **1 µs**。主导项是固定开销与 base64/JSON 编解码，不是带宽 |
| CPU 计算速度/计算量是关键 | **方向对、归因需修正** | 瓶颈是**内存带宽**，不是 SIMD 算力。最硬证据：llama.cpp 把 VNNI 重排内核接入 Q4_0/Q8_0 后，prefill 涨 1.5–3.2×，而 **token 生成稳定 1.00×** |

第三点是本轮最有价值的修正。算术强度算一遍就明白：Q4_K_M 的 decode 约 **3.3 ops/byte**，
而 4 核 AVX2 + LPDDR4x-3733 平台的算力/带宽比约 4.0 FLOP/byte ⇒ 落在**内存受限侧**；
prefill 在 B=512 时算术强度约 1700，才变成算力受限。**所以换更宽的指令集救不了 decode。**

由此推出的 Surface 硬地板：「段工件 1.98 GB，decode 每 token 必须完整读一遍，按 30–40 GB/s
有效带宽 ⇒ **50–66 ms/token 下界**」。这是计算值，不是实测，但和本机同算法 4 层 27.4 ms
的量级一致。

## 2. 「能不能并行」——数学上不能（batch=1）

结论不是"实现难"，是**依赖图性质**：

```
串行   T_ser     = Σ_k (a_k + d_k + n_k·c_k) + r
流水   T_pipe(C) = (C + S − 1) · max_k (a_k + d_k + n_k·c_k/C) + r
```

**C = 1（我们的 decode）时，(2) 式直接退化为 (1) 式**，与怎么切段、用哪种调度算法无关。
忽略固定税时流水有意义需 `ρ = max t_k / mean t_k < C·S/(C+S−1)`；S=4、C=1 时右端恰为
**1.0**，而 ρ ≥ 1 恒成立 ⇒ **无解**。算上固定税更糟：y700 段 d ≈ 48 ms、n·c ≈ 80 ms，
C=8 时流水 760 ms > 串行 467 ms。

GPipe / 1F1B / Interleaved / Zero Bubble / DualPipe **整族不适用**——它们的收益来自
micro-batch 与反向传播填气泡，我们两者都没有。这一点 DeepSeek 子报告从另一个角度得到
同一结论：TTFT 下限 = Σ(t_i + τ_i)，流水只增加 (k−1) 次同步点。

**流水只在吞吐侧有意义**，判据 `R > (k−1)/(u−1)`（R = 并发请求数，u = Σt / T_max）。
k=4、u≈2.5 时需 **R ≥ 3** 个并发请求才转正（吞吐 S≈1.43）。而当前 `NativePorts.prepare`
的 host 全局锁让 R>1 根本不存在——**这是前置条件，不解决就不用谈流水**。

## 3. 「能不能换切分」——能，但收益只有 4%

按「各段耗时相等」重算，答案是 **`[16,8,4,4]`**，模型估算 466.8 → 448.1 ms，
**−4.0%**。约束来自两边：无约束解要求 y700 拿 1.38 层、Surface 拿 1.79 层，低于 4 不可行
（切点必须是 `full_attention_interval=4` 的倍数）；强制每段 ≥4 层后只剩 GPU/CPU 之间
24 层可调。

**真正的 2× 在「减段」，不在「重切层」**：

| 方案 | 估算 decode | 相对当前 |
| --- | --- | --- |
| 当前 `[8,16,4,4]` | 466.8 ms | — |
| 等耗时重切 `[16,8,4,4]` | 448.1 ms | −4.0% |
| **减到 2 段 `[8,24,0,0]`** | **231.2 ms** | **−50.5%（2.02×）** |

`[8,24,0,0]` 与既有实测 `#65`（删掉 Surface 一段：tok/s 4.3→6.4 即 +49%、延迟 −27.6%）
同向。代价是放弃"多设备协同"这个产品叙事——**需要产品裁定**。

一个与直觉相反的结论：**「哪怕显存放不下也 offload 回 GPU」不成立**。转折点是
`c_CPU > 76.8 ms/层`，当前实测 6.84，**差 11.2 倍**。真正的转折点是"主段每层能否从
562 MB(fp16) 降到 175 MB(Q4_K_M)"——降下来后 GPU 能多接约 22 层，最优解塌缩到单段。

## 4. 最大单项杠杆是投机解码，不是并行

decode 单步 217 ms 的实测分解是 `f=18 / h=31 / s=169`（`#62`），**stage 固定项占 94%**，
而 hidden 只有 10 KB。这类"按次付"的税可以按 γ 摊掉，而且 master GPU 每步有约 **78%**
时间在等对端——draft 是唯一既能填这个洞、又不引入新往返的工作项。

收益条件 `γ_eff > 1 + (γ·Δc + draft)/T_1`。硬前置：无投机能力、hybrid recurrent state
不可撤销、末段单值 argmax。这是**能力改造**而非调参，排在减段之后。

## 5. 传输链路：3.15 MB/s 的真相不是带宽

同一轮日志停在 `bytes_received=11534336`，即 **11 MiB 整**，且**小于第一个 16 MiB
checkpoint 门槛**（`src/model_supply_assets.py:40`）——数据流在第一次 journal checkpoint
**之前**就停了。因此磁盘 flush、fsync、落地后二次哈希**都不是**本轮主因，排查范围可以直接
砍掉一半。Android 同轮约 100 MB/s 也说明 master 出口具备千兆线速能力。

最高优先级嫌疑（此前无人提出）：**并发供给的队头阻塞**。发送端是 FastAPI
`StreamingResponse` 的同步生成器，且**每个 1 MiB chunk 都要调一次** `authorize_file()` 和
`touch_capacity_evidence()`，还经 `iterate_in_threadpool` 每 chunk 一次线程池往返。
master 同时向 y700 传 1.1 GB 时，两条流共享同一事件循环与供给协调状态。

**决定性实验（约 10 分钟、零代码改动）**：同一段、同一节点，**独占供给 vs 并发供给**各跑
一次。独占速度翻倍以上 ⇒ 确认队头阻塞；独占仍 ~3 MB/s ⇒ 排除，转查网络层。

这条应在改任何传输代码之前先做。

## 6. 该做与不该做

**P0（按此顺序）**

1. **独占/并发供给对照实验** —— 10 分钟，零改动，决定传输优化方向。
2. **减段到 2 段** —— 最大收益（−50.5%），零协议改动，`#65` 已验证 token 逐位一致；需产品裁定。
3. **解掉 `NativePorts.prepare` 的 host 全局锁** —— 多请求并行的前置条件；不解则 R>1 不存在，
   流水线、投机摊薄都无从谈起。

**P1**

4. **Surface 段调参**：`-t 8 -tb 8`、`-ub 512`、mmap 保持开、ctx 4096 封顶（8192 慢 1.31×）、
   位宽降 Q3_K_M。调参乐观上限 **1.3–1.5×**，拿完就到底。
5. **4 段必须保留时按新目标函数重算切点**（−4%）：复用 `solve_relay_cut`，现有目标只差
   `max`→`Σ`，不新写求解器。
6. **去掉 hidden 的 `f32 → base64 → JSON → sha256` 税**：每 step 每边界一次，4/3 膨胀。

**P2**

7. 投机解码（最大杠杆，前置最重）。
8. Surface 单独 AVX-512 + VNNI 构建 —— 只改善 prefill，decode 预期 ≈1.0×，且须重过数值门。

**明确不做**（避免重复调研）

| 项 | 否决依据 |
| --- | --- |
| 换 `ik_llama.cpp` | 2.88× 是 **prefill** 数字，TG 只有 1.0–1.4×，且无 `layer_inp` 需移植补丁 |
| UVM | CUDA 文档把 Windows/WSL 归入「有限统一内存支持」，不支持并发访问与超配换页 |
| GPUDirect RDMA/Storage | 官方限定 Tesla/Quadro + 同 root complex + Linux 内核模块，本组合全不满足 |
| 张量并行 | 判据 `2·L·RTT < Σ n_k c_k`：1216 ms vs 当前 284 ms，**4.3× 恶化**；可用 RTT 上限 4.4 ms |
| KV 量化 / 滑窗 / 大页 / NUMA | Windows 吃不到；CPU 段 KV 读量仅约 5%（每 token 读权重 1.27 GB vs KV 64 MB） |
| i-quant（IQ2/IQ3） | 同字节下 Q2_K_S tg 18.70 vs IQ2_XXS 10.06，且 pp 慢 3–5× |
| PowerInfer | 需要 ReLU 类 97% 稀疏，SwiGLU 只有 43–53%；且结构上不导出段末 hidden |
| MLA 直接套用 | 我们缺的是权重带宽不是 KV 带宽；且 93.3% 那个数字的基线是 MHA，我们的 GQA 已只剩 1/4 |
| 3FS 类存储架构 | 单节点 ~40 GB/s，比我们的有效带宽高 3–4 个数量级，家庭/办公网不可复现 |

## 8. 未核实项（如实登记）

1. **Qwen3.5-9B 在 Q3_K/Q2_K 下的 PPL** —— 无公开数值，必须自测才能决定是否降位宽。
2. **Surface 段是否含 `lm_head`** —— 若含，把它移出是该段最强的单项优化，优先级会超过调参。
3. **Surface AVX-512/VNNI 的实机收益** —— 推断只改善 prefill，decode ≈1.0×，未实测。
4. **Ice Lake 上 AVX-512 的频率影响** —— 可能抵消部分收益。
5. **OpenVINO backend 能否保留本仓 `layer_inp` 钩子** —— 未验证，是硬阻塞。
6. **并发供给队头阻塞假设** —— 待第 6 节 P0-1 的实验判定。
7. **本轮未采到推理分段耗时**：环境侧 `prepare_artifact_identity_missing`（供给准备状态不一致），
   日志里也没有分段的耗时埋点。第三节的 decode 分解引用的是历史实测 `#62`，
   不是今天重测。**要拿到当前切分的分段耗时，需要在推理路径加埋点**。
