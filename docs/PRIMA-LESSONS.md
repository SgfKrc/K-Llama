> 分析对象：`H:\prima.cpp`（344 源文件 / 175,783 行），只读未改动；详细证据与代码行号见 `PRIMA-ANALYSIS.md`。

## 1. 最重要的一条：分界线不在"切不切文件"

两边做的事是一样的：**每台机器都持有同一份整模，加载时只创建、只读取属于自己的那几层，
其余靠 mmap 惰性从不触碰**。没有"切模型"这个动作。

真正的差别是**过滤层号放在哪一层**：

| | prima | 本项目 |
| --- | --- | --- |
| 过滤位置 | build graph 时跳过（`11043` 判断 + `11066` 映射） | **model-loader 改写 `block_count`**（`LLAMA_LAYER_RANGE`）+ `get_weight` 重映射 |
| 要改架构代码 | 每个 `build_*` 都要复制这套钩子 | **一行不改**，架构以为自己只有 `hi-lo` 层 |
| 支持架构 | **2 个** | 全部架构 |

`src/llama.cpp:17003` 的断言在 `switch` 之前：

```c
GGML_ASSERT((model.arch == LLM_ARCH_LLAMA || model.arch == LLM_ARCH_QWEN2) && ...);
```

**它不是忘了加 MoE，是这条路线注定的**：层过滤一旦写进 build graph，每支持一个架构就要
改它的 build 函数一次，于是永远只能支持改过的那几个。而把过滤放在 model-loader，
`qwen35moe` 只需要 8 文件 +227/−13、两处 tap（见 `PATCHES.md`）。

这是我们最该保护的技术资产——prima 替我们把另一条路走到了尽头。

## 2. 它跑不了 MoE —— 这是我们的空间

`qwen35moe` 的 GGUF 在 prima 上**连加载都失败**：架构枚举里没有 `LLM_ARCH_QWEN3MOE`，
`17003` 的断言先拦死。

即便加上架构也还不够。它的预取按"名字含 `weight` 且 buffer 非 cuda"过滤
（`18164`、`18173`），不认识"这个专家本 token 没激活"：

| 模型类型 | 预取利用率（推算） | 结论 |
| --- | --- | --- |
| dense | 读 100% 用 100% | 等价变换，无浪费 |
| **MoE（8/256 激活）** | 读 100% 用 **3%** | **32 倍 I/O 放大** |

而 `18173` 那个 `buffer 非 cuda` 的判断**正是我们缺的一半**：我们的注册在
`llama-model-loader.cpp:1566-1587` 一次性遍历 `weights_map`，不区分上卡与否，
对 `-ngl` 已经驻留的层也发 `PrefetchVirtualMemory`。页缓存命中时它不花钱（`issued` 恒 0），
所以优先级低，但它是纯噪声。

## 3. 它的预取机制：简单，但对我们场景是坏交换

- `init_mappings(false)`，不做 `MAP_POPULATE`
- 对下一 subgraph 的**全部** weight 整段 `MADV_WILLNEED`（`18571`）
- 全仓没有一行 `DONTNEED`，回收完全交给 OS
- `is_graph_loaded()`（`mincore` 算驻留比）是**死函数**，从未被调用

所以"内存压力 <10%"是论文的实验测量值，**不是机制保证**。

与 SLIM-ARC 对比：

| 维度 | prima | SLIM-ARC |
| --- | --- | --- |
| 预取策略 | 无脑下一段全量 | 6 GiB 门槛 + 专家级选择性 |
| 预算控制 | 无 | `memory_budget` |
| 压力反馈 | 无（死函数） | pressure 状态机 |
| 显式回收 | **无** | 有 |

两者都不理解 MoE 的激活稀疏性；区别是 SLIM-ARC 把它当成可调预算，prima 当成固定开销。

## 4. 控制面：约 4,000 行，其中 3,551 行我们不需要

| 模块 | 行数 | 我们要不要 |
| --- | ---: | --- |
| profiler（设备探测） | 2,745 | **不要** |
| HiGHS 整数规划 | 806 | **不要** |
| 编排 / 参数 / 工具 | 260 | 参考 |
| 分布式运行时（`src/llama.cpp` 内） | ~2,000 | 部分参考 |

这 3,551 行是为**"未知异构 + 无配置"**付的税。我们的设备是已知的三台、层区间是配置项，
这笔税不必交——1000 行控制面因此是宽裕的。

它的调度也是纯静态：`-lw "16,16,16,16"`（`arg.cpp:707-740`）或启动时 profile → 一次
整数规划 → bcast，**推理中不重分配**。这与我们的 `topology.toml` 是同一思路。

## 5. "15x faster" 的口径

有正式论文（ICLR 2026，OpenReview `h0LjpOG1jq`），核心是 PRP（把磁盘 I/O 藏到计算后）
与 Halda 调度器。

基线是"同一批设备里的**一台**、而且**装不下**"：

```
Llama3-70B：prima 674 ms vs llama.cpp 10120 ms
```

README 自认小模型会退化成 `32:0:0:0`（全放一台），**此时两者 15 ms 打平**。

**这一点同样适用于我们自己**：本机单卡整模只上 6 层是 10.5 tok/s，跨机两段 12.2，
加 DFlash 20.9。拆分本身不提速，价值只在**装不下**时；差别不在机制，在基线有多惨——
它拿 swap 到磁盘的 70B 当基线。

所以写文档时不要引用 prima 的倍数来暗示拆分效率。

## 6. 可抄 / 不抄

### 值得抄

| 项 | 说明 |
| --- | --- |
| **集群 ACK barrier**（`20590-20682`） | **我们完全没有**。现在是"拓扑里 `start_cmd` 拉起 + 连上即就绪"，段多了以后"某台已起但未 ready"会被误判为可用 |
| 预取排除已驻留张量 | 见 §2 末：按 buffer 类型过滤，我们的注册不区分 |
| `NODE_TYPE` 三态（`WORKER`/`FORWARDER`/`EXIT`，`20684-20829`） | 节点被剔除后环跨过它重接。做容错时的现成模型 |
| `base_port + rank` | 比逐个写端口简洁 |
| device_info 字段表 | 直接用作 TUI 列 |
| hidden 帧 `[key][dims][f32]` | 我们的协议已同构 |

### 明确不要抄

| 项 | 原因 |
| --- | --- |
| **Windows 驻留检测用 `VirtualQuery` + `MEM_COMMIT`**（`18083-18096`） | 对 file-backed mmap **恒为真**（section 已提交），比我们"未知即跳过"更糟。正解是 `QueryWorkingSetEx`（PSAPI） |
| PRP 多圈 k（`cycle_offset` / `cycle_size`，`3863-3882`） | `L = k·W` 只是把窗口切碎，**不减少**总持有量。我们"段数 = 节点数"下 k≡1 |
| 通信 / 预取重叠 | 我们确实是空白（预取只与计算重叠，不与"等下游回包"重叠），但整模在页缓存里时无页可补，等弱设备接入再说。**记录不实现** |
| 无脑全量预取 | MoE 下 32 倍放大，见 §2 |

## 7. 一个我们要补的测量：每段耗时的尾延迟

prima 的 Halda 假设**每层耗时是常数**（`common/common.cpp:906-918`）。MoE 不同 token
路由到不同专家，同一层耗时抖动；串行接力里总耗时 = Σ各段耗时，抖动会被直接放大成 TPOT 方差。

**`MEASUREMENTS.md` 应按段记 decode 耗时的 p50 / p99**，比值大的段是瓶颈候选，切分点应避开。

现有数据（两进程、未按段拆分）：

```
run 1: median 62.1 ms, p90 84.6 ms   → p90/p50 = 1.36
run 2: median 55.3 ms, p90 61.1 ms   → p90/p50 = 1.10
run 3: median 54.3 ms, p90 64.9 ms   → p90/p50 = 1.20
run 4: median 65.2 ms, p90 82.2 ms   → p90/p50 = 1.26
```

已显示 10–36% 的尾延迟，需要按段拆开看是哪一段贡献的。
