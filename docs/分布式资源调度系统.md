# 分布式资源调度：FIFO、容量规划与部署发布

> 状态：**现行**
> 更新日期：2026-10-19
> 适用范围：主仓请求排序、纯容量规划、部署发布与冻结执行的职责。客户端及裁撤证据见[R5客户端切换](重构客户端切换-R5-2026-10-19.md)。

## 1. 调度职责

| 职责 | 事实owner／主要入口 | 输出 |
| --- | --- | --- |
| 请求排序与终局 | [RequestService](../src/qlh_core/execution/requests.py)的`run/pause/resume/cancel` | 有界FIFO、唯一terminal及物理execution_state |
| 容量规划 | [solve_pipeline_capacity](../src/qlh_core/planning/capacity.py) | 基于冻结模型、节点能力、工件及预算的方案与具名排除原因 |
| 部署发布 | [DeploymentService](../src/qlh_core/control/deployment.py)的`save_execution/runnable` | 已验证assignment、实际回执、active deployment及清理义务 |
| 计划冻结与执行 | [ExecutionApplication](../src/qlh_core/bootstrap/execution.py)的`freeze/run`与[LinearExecutor](../src/qlh_core/execution/linear.py) | 不可变连续段顺序、请求内身份校验及结果 |

`Scheduler`保留节点连接、部署及执行适配。规划、部署就绪和请求终局分别由上述owner持有，客户端消费版本化投影。MLFQ、SJF、老化、协作抢占和图放置器已裁撤，现行职责及软件证据统一见R5报告。

## 2. 有界FIFO

`RequestService.run`按到达顺序入队，每次保留一个执行序列；`capacity`限制等待队列。准入检查取消、deadline、关闭、持久化失败、暂停和deployment清理隔离，队满返回`request_queue_full`。

- `pause`停止接收新请求，已接收请求继续；`resume`恢复准入。
- 等待中取消立即释放队列容量；运行中取消先决定逻辑终局，物理执行槽继续由当前请求占用。
- `execution_state`区分`waiting/running/draining/stopped`；只有真实停止与KV清理证据齐备后才复用native资源。
- 排队、前向、等待远端及清理共用[RequestDeadline](../src/qlh_core/contracts/deadline.py)的原绝对截止时间。

请求快照由`queue_snapshot/recent`输出schema v2的revision、identity、observed_at、validity及结构化reason；耐久历史查询保持只读。`SqliteRequestRepository.transact`原子保存请求记录和hash chain，重启以`request_process_restarted`结束未完成生成并保留`recovery_required`。

## 3. 容量规划与部署

`solve_pipeline_capacity`只消费输入并产出方案；[assignment_load_spec](../src/qlh_core/planning/load_spec.py)将设备、dtype、量化、组件、KV和物化策略冻结到`RuntimeLoadSpec`。工件可读、库存available与连接在线各证明对应阶段，执行准入还需当前部署的实际装载回执。

`DeploymentService.save_execution`保存候选事务、命令、发布点和cleanup ledger；`runnable`核对当前boot、authority、连接代际和输入revision。失败或节点换代时撤销准入，后续加载与重规划由部署用例推进。完整发布与恢复合同见[R3供给与部署](重构供给与部署-R3-2026-10-18.md)。

## 4. 冻结执行与星状传输

```mermaid
flowchart LR
    P[纯容量规划] --> D[准备、提交与部署发布]
    D --> F[冻结ExecutionPlan]
    F --> Q[有界FIFO]
    Q --> E[LinearExecutor]
    E --> M[master首段与转发]
    M --> W[worker连续段]
    W --> M
```

[ExecutionPlan](../src/qlh_core/contracts/execution.py)固定deployment、authority、assignment、node incarnation、connection、段顺序、embedding和唯一LM head。master至少承担首段，所有worker数据经master转发。执行器每段前后重验身份，失效返回具名原因。

默认分布式采样采用`SamplingPolicy`的greedy合同；EOS、文本stop和token上限由共用`StopPolicy`处理。成功turn按会话revision CAS提交，取消与部分输出保留独立记录。执行、取消和KV排空的完整合同见[R4接力执行](重构接力执行-R4-2026-10-18.md)。
