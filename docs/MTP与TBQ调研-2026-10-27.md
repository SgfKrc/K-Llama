# llama.cpp 的 MTP 与 TBQ：能给 QLH 带来什么（2026-10-27）

> 调研对象：llama.cpp 当前的 **MTP（Multi-Token Prediction）** 与 **TBQ（TurboQuant）**。
> 结论先行：**MTP 在主线已落地且是投机解码的一种实现，但我们的 9B 工件没有 MTP 头；TBQ 在 llama.cpp 里指的是 KV cache 的 TurboQuant 类型，且从未合并进主线，对"权重带宽受限"的 decode 基本无收益。**
> 标注：`[官方文档]` `[PR]` `[实测数据]` `[社区报告]` `[推测]`。查不到的一律写"未找到"。

---

## 0. 结论摘要

| 优化项 | 解决什么 | 我们的可迁移性 | 前置条件 | 预期收益量级 |
|---|---|---|---|---|
| **MTP（draft-mtp）** | 用模型自带的 nextn 头一次猜多 token，摊薄"每 token 读一遍权重" | **低**（当前工件无头）→ 换带 MTP 的 9B 工件后为**中** | 模型原生带 `nextn_predict_layers`；draft 所在设备要能读 `lm_head`；每段支持 batch>1 前向 | 理论上限 `γ_eff`（约 1.5–3×），实测他机 1.5–2.4× `[社区报告]` |
| **独立草稿模型（draft-simple）** | 同上，但草稿是另加载的小模型 | **中** | 同词表小模型（我们有 2B，词表同为 248320 `[实测数据]`）+ batch 验证 + 末段多位置 argmax | 同上，但 draft 成本高于 MTP |
| **TBQ3_0/TBQ4_0** | 压 **KV cache**（3.06/4.06 bit/elem），不压权重 | **极低（≈0 或负）** | 未合并，需自己打补丁 | 我们的 KV 每 token 只占 1–3% 读取量 → <1% 收益，CPU 上实测反而慢 47% |
| **普通低位宽（Q3_K_M / Q2_K）** | 真·压权重比特，直接减每 token 读取量 | **高（工程上已验证的同类）** | 重新量化 + 裁层 + 重过数值门 | master#cpu −10~13%，Surface −5~24%（含 lm_head 降档）`[计算]` |

一句话取舍：**能真正动我们痛点的只有"减字节"和"一次前向算多个位置"这两件事；MTP 属于后者（前置是模型要带头），TBQ 两件都不是。**

## 1. MTP（Multi-Token Prediction）

### 1.1 llama.cpp 现在支持到什么程度

**已落地，且是一类一等公民的投机解码实现**，不是实验开关：

- 官方文档的原话是 `draft-mtp | Use Multi Token Prediction (MTP) heads from the main model` `[官方文档]`，<https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md>。同一张表里并列 `draft-simple / draft-eagle3 / draft-dflash / draft-mtp / ngram-*`。
- 我们的树（`android/app/src/main/cpp/llama.cpp`，2026-09-23 上游基点 + QLH 补丁）里 `common_speculative_type` 已有 `COMMON_SPECULATIVE_TYPE_DRAFT_MTP`，`common/speculative.cpp:1201` 起是完整实现 `common_speculative_impl_draft_mtp` `[实测数据]（读源码）`。
- 引入链：`llama + spec: MTP Support (#22673)` → `llama : MTP clean-up (#23269)`，之后按架构逐个补齐：`llama : add Gemma4 MTP (#23398)`、`qwen35: use post-norm hidden state for MTP (#24025)`、`StepFun 3.5 MTP (#23274)`、`spec : Support Step3.5/3.7 flash mtp3 (#24340)`、`llama: add llm_graph_input_mtp (#23643)` `[PR]`。
- 实现细节对我们很关键：`draft-mtp` 的三种模式写在构造函数注释里——`gemma4` 共享目标 KV、`step35` 逐层链式头、**`qwen35/qwen35moe` 是单个训练好的 MTP 头**；`qwen35.cpp:497` 断言 `n_layer_nextn == 1`，即 **Qwen 系只支持 1 个 MTP 块** `[实测数据]（源码）`。

结论：**不是"只支持 DeepSeek V3/R1 的 MTP 层"**，而是按架构实现了通用 nextn/MTP 头（gemma4、qwen35、qwen35moe、glm4/glm-dsa、exaone、step35、cohere2moe 等），用法上又是标准投机解码的一种。

### 1.2 它和"投机解码"是什么关系

MTP 是 **投机解码的一种 draft 来源**，不是替代品。区别只在草稿从哪来：

| | 草稿来源 | 需要另训/另下模型 | 每次 draft 成本 |
|---|---|---|---|
| `draft-simple` | 独立小模型 | 是（可用现成小模型） | 小模型一次前向 |
| `draft-eagle3` | 1 层 transformer，读目标 hidden | 是（EAGLE-3 checkpoint） | 很便宜 |
| `draft-mtp` | 主模型自带的 nextn 头 | **否**（头随主模型发布） | 1 层 + 一次 `lm_head` |
| `ngram-*` | 无模型，查历史 n-gram | 否 | 几乎为零 |

所以"**MTP 是内置草稿头，不需要独立草稿模型**"这个说法是对的 `[官方文档]`。注意它仍然需要一个独立的 `llama_context`（`ctx_dft`），可以是主 GGUF 里的 nextn 层，也可以是单独导出的 mtp-only GGUF（社区常见做法，例如 `-md mtp-*-31B-it.gguf`）`[社区报告]`（issue #31077、#30860 的命令行即如此）。

### 1.3 关键问题：对 batch=1 的 decode，它真的把"每 token 读一遍权重"摊薄了吗

**是，但摊薄的是"一次前向"而不是"一次读取"，而且只按接受到的 token 计费。**

机制：验证时把 `γ+1` 个位置拼成一个 batch 灌进整条链。每段仍然**读一遍自己的整段权重**，但这一次读取服务了 `γ+1` 个候选位置；其中只有被接受的 `γ_eff` 个算产出。所以

```
T(k) ≈ T_bytes + k·T_compute        (k = γ+1)          ← 每段
每 token 有效成本 = Σ_k T_k(k) / γ_eff
γ_eff = 1 + (γ−1)·a                                     a = 接受率
收益条件：a > (Δ/T1)·γ/(γ−1)                            Δ = 每多一个位置的边际成本
```

这个判据的含义：**只要"每多一个位置的成本增量占比"低于接受率，投机就赚**。`Δ/T1` 是我们唯一必须实测的量（见 §5）。

- 若 `Δ/T1 = 0.05`（本仓 Android 段的观察：batch 2 几乎不涨 `[实测数据]`，见 [LLM推理并行策略调研 §5.1](LLM推理并行策略与异构层段切分调研-2026-10-27.md)）：γ=4 时只需 `a > 6.7%`，几乎白送。
- 若 `Δ/T1 = 0.4`（每位置都真按算力线性涨）：γ=4 时需 `a > 53%`，就要看模型和采样温度了。
- ⚠️ 重要区分：它**不是**把 2 GB 权重读一次摊到 γ 个"已确认"token 上（那是理想化的 3–4×），而是摊到 `γ_eff` 个；且 batch 验证会让每段的算术强度从 3.3 ops/byte 涨到 `3.3(γ+1)`，一旦越过平台算力/带宽比（我们估 3.6–4.0），时间就开始随 γ 涨。这正是 §5 要标定的 `Δ`。

另有旁证说明"batch=1 的 draft 前向"确实被上游当成热点在做：`ggml-webgpu: improve MTP inference by using mat-vec path for small batches (#24811)`、`Remove padding and multiple D2D copies for MTP (#24086)` `[PR]`。

外部实测佐证（GPU 单卡）：Qwen3.8-27B Q8 单卡，`N=3` 时 43→97.9 tok/s、`N=5` 时 104.5 tok/s（2.4×），其 32K 裁剪草稿词表版本实测接受率 82.89% `[PR #29143]`；另一台 4090 Laptop `tg 17 → 26~28 t/s`（约 1.6×）`[社区报告 #27428]`。注意 #27428 同时报告：**多卡 layer split 下 MTP 让 prefill 掉 80–100%**，单卡只掉 3%——因为 MTP 的每条 ubatch 追赶解码打断了流水。**我们是 4 段串行，这个副作用必须当成已知风险。**

### 1.4 我们的模型没有 MTP 头——这是实测，不是猜测

直接解析 GGUF 头的 KV 与 tensor 目录（只读头部，不加载权重）得到 `[实测数据]`：

| 工件 | arch | blocks | `nextn_predict_layers` | nextn 张量 |
|---|---|---|---|---|
| `models/qwen3-5-9b-gguf/Qwen3.5-9B-Q4_K_M.gguf` | qwen35 | **32** | **无** | **0** |
| `models/qwen35-9b-dsv4flash-q4_k_m.gguf` | qwen35 | **32** | **无** | **0** |
| `models/qwen3-5-2b-gguf/qwen35-2b-Q4_K_M.gguf` | qwen35 | **25** | **1** | **4**（eh_proj/enorm/hnorm/shared_head_norm） |
| `…Qwen3.6-35B-A3B-DSV4Pro-Distill-MTP…gguf` | qwen35moe | 41 | 1 | 4 |

两点必须写进结论：

1. **9B 确实没有 MTP 头**（两个独立 9B 工件都没有）。当前开 `--spec-type draft-mtp` 没有可用的 `ctx_dft`；即便拿同一份无 nextn 的 GGUF 冒充 draft，`graph_mtp` 的前置断言语义也不成立（`qwen35.cpp:496` 要求 `n_layer_nextn > 0`，`common_speculative_impl_draft_mtp` 构造时只是 `max(1, n_layer_nextn)` 兜底），结果是运行时崩溃而不是"自动退回逐 token" `[实测数据，源码]`。
2. **Qwen3.5 家族不是全都没有**——2B 就带 1 个 nextn 层。所以"Qwen3.5 自带 MTP head"这句既有判断**对我们这个 9B 工件不成立**（[KV缓存优化调研 §附录](archive/relay/KV缓存优化与注意力结构调研-GQA与MLA-2026-10-14.md) 第 298 行的"Qwen3.5 自带 MTP head"需按尺寸限定）。这也意味着：**只要出现带 MTP 头的 Qwen3.5-9B 发布件，换文件即可启用**，不需要改我们代码。是否有该发布件：**未找到**（无外网 HF 访问，仅确认本机两个 9B 工件均无）。

要用上 MTP，必须满足以下之一 `[推测，基于源码]`：

- (a) 换/等官方带 nextn 的 9B checkpoint（最省事，成本≈0）；
- (b) 自己训一个 MTP 头（1 个 `eh_proj` + 3 个 norm，参数量约 1700 万，但要目标模型 hidden + logits 对齐的数据和训练工序；参考 DeepSeek-V3 的 MTP 训练目标 `[论文 arXiv:2412.19437]`）；
- (c) 放弃 MTP，走 `draft-simple`/`draft-eagle3`。

还有一个架构层面的坑：MTP draft 每步都要 **一次 `lm_head`（我们 834 MB Q6_K）** 才能采样出候选 token。放在 Surface（最弱、且读 834 MB 要 ~60 ms）就是灾难；放在 master GPU（读一次 ~5.6 ms）却拿不到末层 hidden。**因此 MTP 与"把 lm_head 移回 GPU"是同一张票**，不是两个独立优化。

## 2. TBQ

### 2.1 先澄清多义

"TBQ" 在 llama.cpp 语境里**有确定的所指，但也有两个容易混淆的近邻**：

| 候选 | 在 llama.cpp 里的实际形态 | 状态 |
|---|---|---|
| **TurboQuant（tbq3_0 / tbq4_0）** | 新增的 **KV cache** ggml 类型，`98 B/256 elem`（3.0625 bpw）、`130 B/256 elem`（4.0625 bpw），基于随机正交旋转 + Lloyd-Max 码本 | **未合并**。PR #21089 关闭（`merged_at: null`）、issue #20977 以 `not_planned` 关闭；我们的树 `ggml/src/` 里 grep 不到任何 `tbq/turbo` `[实测数据]` |
| Ternary Quantization（TQ1_0 / TQ2_0） | 三值**权重**格式（BitNet b1.58 风格），`ggml-cpu` 有 `vec_dot`，`llama-quantize` 可产出 | 早已在主线（本地树可见 `tq1_0/tq2_0`），原始引入 PR 编号**未找到** |
| "Ternary-Bit/Block Quantization" 之类的自造说法 | 无对应实现 | 不存在 |

所以**当前 llama.cpp 实际在做的 TBQ = TurboQuant 的 KV cache 类型**，且停在 PR 阶段、没有进主线。三个 PR（#21089 CPU、#21062 CUDA、#21817/#21818 后续）全部关闭，#21062 与 #21818 的标题还挂着 `(AI policy violation)` `[PR]`。

### 2.2 它压缩的是什么

**压的是 KV cache 里每个元素的比特数**，既不是权重比特，也不是 block 内 scaling 开销：

- 做法：对每个 KV 向量乘随机正交阵（QR 分解高斯矩阵）→ 每坐标落成集中分布 → 查 Lloyd-Max 码本 → 索引按 2/3/4 bit 打包 + 存一个 **fp16 范数** `[PR #21089 / #21062]`。
- 所以 block 内的"scaling 开销"只有一个 fp16 norm（256 元素 / 2 字节），本来就不大；它省的是主体数据位宽。
- 官方给出的压缩比（相对 f16）：`tbq3_0` 5.22×、`tbq4_0` 3.94× `[PR #21089]`。

**这直接决定了它对我们的适用性：它一个字节的权重都不省。**

### 2.3 官方实测（pp 与 tg 分开）

PR #21089 的 CPU 数据（Qwen3.5-4B-Q4_K_M，4 线程，flash_attn on，`llama-bench pp32/tg8`）`[PR]`：

| KV 类型 | pp t/s | **tg t/s** | KV MiB | 压缩 | PPL |
|---|---|---|---|---|---|
| f16 | 50.67 | **15.72** | 64.00 | 1.00× | 13.8387 |
| q8_0 | 50.63 | 15.67 | 34.00 | 1.88× | 13.8348 |
| q4_0 | 50.46 | 15.64 | 18.00 | 3.56× | 13.8400 |
| **tbq4_0** | 45.84 | **8.31** | 16.25 | 3.94× | 13.8323 |
| **tbq3_0** | 46.19 | **8.29** | 12.25 | 5.22× | 14.3198 |

要点：**pp 掉 8–10%，tg 直接腰斩（−47%）**，即使 KV 小了 3.9–5.2 倍。原因是每步都要把 KV 解量化（反旋转 + 码本查表），而 decode 的 KV 访问本来就是"小批量、随机、延迟敏感"。CUDA/Metal 版本同样掉速：Llama 3.2 3B FP16 → TBQ3 从 604/82 掉到 308/28 t/s `[PR #21062]`；Gemma 3 4B 从 2210/126.7 掉到 869/38.6 `[PR #21818]`。**三个平台一致：省内存不省时间。**

### 2.4 对我们：KV 每 token 只占 1–3% 的读取量

用我们自己的几何与字节算（`qwen35.attention.head_count_kv=4`、`key/value_length=256`、`full_attention_interval=4`、32 层 ⇒ 8 个 full attention 层）`[实测数据 + 计算]`：

- 每 token 每 full 层 KV = `4 heads × 256 × 2(K,V) × 2 B = 4 KiB`；全模 8 层 ⇒ **32 KiB/token**。
- `ctx=4096` ⇒ 全模 KV ≈ **131 MB**；`ctx=512` ⇒ 16 MB。
- 分段后每段每 token 相对该段权重读取量：

| 段 | 该段 full 层数 | KV@4K | 该段权重读取 | KV 占比 |
|---|---|---|---|---|
| master#cpu `[8,24)` | 4 | 67 MB | 2046.9 MB | **3.3%** |
| Surface `[28,32)` | 1 | 16.8 MB | 1399.9 MB（output+4 层） | **1.2%** |

TBQ 把 KV 压到 1/3.9–1/5.2，于是：master#cpu 最多省 **2.4%** 的读取量，Surface 最多省 **0.9%**。而 PR 实测 CPU 上解量化让 tg 慢 47%。**净结论：负收益，不用做。** 这与既有结论"KV 量化在 CPU 上更慢、已否证"完全同向（[CPU推理优化调研 §3.1](CPU推理优化调研-2026-10-27.md)）。

TBQ 唯一可能成立的场景是长上下文（ctx ≥ 32K，KV 涨到 1 GB 以上）且显存/内存不够装——那是"能不能跑"的问题，不是我们的延迟问题。

## 3. MTP 与投机解码的区别与选择（单列）

**关系**：MTP 是投机解码的 draft 侧实现之一；验证侧完全一样（一次 batch 前向 + 逐位置 argmax + KV 回滚）。所以"MTP vs 投机解码"是伪对立，真问题是 **draft 由谁产、在哪产、值不值**。

**选择矩阵（我们的四段串行链路）**：

| draft 方案 | 我们能否立刻做 | draft 成本 | 关键风险 |
|---|---|---|---|
| `draft-mtp` | **否**（9B 无 nextn 头） | 1 层 + 一次 `lm_head`（放在 Surface 每步 +60 ms，不可接受） | 头要能拿到末层 hidden 且读得起 `lm_head` |
| `draft-simple`（Qwen3.5-2B） | **可以**：本机已有 2B，词表同为 248320 `[实测数据]` | 2B Q4 在 4060 上每 token 约 5–8 ms `[推测]`，且可与"等对端"的 78% 空闲重叠 | 显存（1.2 GB）+ 需要 batch 验证 |
| `draft-eagle3` | 无现成 Qwen3.5-9B 的 EAGLE-3 头（**未找到**） | 最低 | 需另训/另找 |
| `ngram-*` | 已试过：**净负收益** | ~0 | 命中率与重放开销 |

**为什么我们已有的投机实测是负的**：`投机批验证` 在 Qwen2.5-0.5B 双段上，gamma=1/2/4/8 分别是 19.4/8.7/8.7/8.6 t/s，结论是"普通 n-gram 投机为净负收益，**完整前缀重放**增加计算与通信" `[实测数据，[投机批验证](投机批验证-实现与验收-2026-10-20.md)]`。注意：那次是**重放 γ 个位置**，不是"一次 batch 前向算 γ+1 个位置"。前者把每段成本乘 γ，后者几乎不涨——这是同一个词（投机）下两种完全不同的成本结构。**要判它值不值，必须先让每段具备 batch 内多位置前向，否则不必再测。**

**在"串行 4 段 + 固定税 94% + 传输慢"的场景里值不值得做**：

- "固定税 94%"这个口径来自 decode 单步 `f=18 + h=31 + s=169 ms` 的分解（其中固定项占 stage 的 94%）`[实测数据，[LLM推理并行策略 §5.1](LLM推理并行策略与异构层段切分调研-2026-10-27.md)]`。但**按本轮新实测**（master#cpu 104.08 ms 读 2046.9 MB = 19.7 GB/s，Surface 112.86 ms 读约 1400 MB = 12.4 GB/s），这两段的主体现在是**权重读取**，不再是纯网络固定税。所以投机摊薄的对象应从"往返税"改写为"每段的一次权重读取 + 往返税"，**这反而让投机的账面更好看**（权重读取也是每 token 付一次的大头）。
- 但前提是每段一次前向。若做不到，传输慢会让重放成本进一步放大（多传 `γ×16 KiB` 的 hidden 和回程 logits，虽小但每步都付）。
- 因此我的判断是：**值得做，但排序在"每段 batch 前向 + 末段多位置 argmax + KV/状态回滚"三件基础设施之后**，且先做 draft-simple（2B），MTP 等有带头的 9B 工件再说。

## 4. TBQ / 低位宽对我们每段的预期收益（用实测字节与带宽算）

先给三段的实测口径（本轮 GGUF 头解析 + 你给的计时）`[实测数据]`：

| 段 | 层 | 层字节 | 头尾 | 实测 | 有效读取带宽 | 相对 copy 上限 |
|---|---|---|---|---|---|---|
| master#cpu `[8,24)` | 16 | **2046.9 MB**（127.93/层） | — | 104.08 ms | **19.7 GB/s** | 30.6 → **64%** |
| Surface `[28,32)` | 4 | **565.5 MB**（141.38/层） | output 834.36 + token_embd 572.13 | 112.86 ms | **12.4 GB/s**（只算 output+层）/ 17.5（全算） | 22.2 → **56%** / 79% |

有两个必须纠正的直觉：

1. **`token_embd` 572 MB 不进入每 token 读取。** decode 时它只被 `get_rows` 取一行；它进段文件是加载/容量问题，不是带宽问题。所以 Surface 的 1983 MB 里真正的每 token 读取约 **1400 MB**，有效带宽只有 12.4 GB/s（上限 22.2 的 56%）——**Surface 段其实没到带宽墙，是 4 核算力/解量化在限速**。这解释了为什么 threads 2/4/8 只有 139.85/113.43/112.86（4 核以上不再涨），也意味着**单纯降比特在 Surface 上收不全**。
2. master#cpu 的 19.7 GB/s / 30.6 GB/s = 64%，同样还有 36% 花在解量化与 MAC 上。

**这两条都可当场证伪**：把 tail 工件里的 `token_embd` 张量抽掉（或换成分段只读不加载），重测 Surface 的 ms/token。若读数不变，则 572 MB 确实是"内存占用而非带宽"；若明显变快，说明我们的注入路径把整表读进来了，那是一项比 TBQ 大得多的 bug 级收益。

据此算收益（**假设时间按字节线性、乐观上界**；`[计算]`）：

| 改动 | master#cpu 字节/时间 | Surface 字节/时间 |
|---|---|---|
| 现状 Q4_K_M | 2046.9 MB → 104.08 ms | 1399.9 MB → 112.86 ms |
| 层权重 → Q3_K_M（×0.87） | 1780.8 MB → **−13%**（理论 90.5 ms） | 1326.4 MB → **−5.3%**（理论 106.9 ms） |
| 上面 + `output` Q6_K→Q4_K（834→572 MB） | —（该段无 head） | 1064.1 MB → **−24.0%**（理论 85.8 ms） |
| 层权重 → Q2_K（×0.578，需 imatrix） | 1183.1 MB → **−42%**（理论 60.1 ms） | 1161.3 MB → **−17.0%** |
| **TBQ（只压 KV）** | −2.4%（且 CPU 解量化更贵）→ **净负** | −0.9% → **净负** |

诚实打折：master#cpu 的 64% 效率意味着降比特的收益会被"解量化指令数"吃掉一部分；社区数据 Q4_K_S→Q3_K_S 实测 tg 1.2–1.35×、Q2_K_S 1.41× `[社区报告，[CPU推理优化调研 §4](CPU推理优化调研-2026-10-27.md)]`。我建议把 **master#cpu −10%、Surface −15~18%（含 head 降档）** 作为立项预算，而不是按字节比算出的 −13%/−24%。

## 5. 可行性排序与建议动作

1. **把 `lm_head` 移出 Surface（或整体上提到 master GPU）+ 把末段层数再压 1 层**——这是唯一"同时降字节数和降最弱段"的动作，收益线性且不需要新模型。与 MTP 是同一张票（§1.4）。
2. **低位宽：master#cpu 走 Q3_K_M，Surface 走 Q3_K_M + head Q4_K**——工程路径已经跑通过裁层/量化流水；前置是重跑数值门与 PPL。预期 master#cpu −10%、Surface −15~18% `[计算]`。
3. **投机基础设施（batch 验证 + 多位置 argmax + 状态回滚）→ 再上 draft-simple（2B，同词表）**。这是唯一能突破"每 token 必须读一遍权重"的手段，上限 `γ_eff`。**先实测每段的 `Δ/T1`（k=1,2,4,8 各 100 步的 ms/step），再决定 γ**。
4. **MTP**：等带 nextn 的 9B 工件；不要为它改框架（`draft-mtp` 与 `draft-simple` 走同一套验证代码）。
5. **TBQ：不做。** 除非将来出现 ctx≥32K 的容量需求（那是省内存，不是提延迟）。

**待实测/未找到**：

- 每段 `Δ/T1`（batch 2/4/8 的相对增量）——无实测，判据上空着。
- Qwen3.5-9B 在 Q3_K_M/Q2_K 下的 PPL 与 argmax 一致率——**未找到**公开数值（既有文档同样标记未核实）。
- 是否存在带 MTP 头的 Qwen3.5-9B 官方/社区发布件——**未找到**（本机两个 9B 工件均无 nextn）。
- TQ1_0/TQ2_0 的原始引入 PR 编号——**未找到**（可确认格式在主线存在）。
