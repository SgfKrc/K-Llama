## 0. 结论先行

本项目当前的三条关键路径上，**只有一条真的被传输卡住**：

| 边界 | 实际走什么 | 是否是瓶颈 | 依据 |
| --- | --- | --- | --- |
| 推理期：`master` GPU 段 → `master#cpu` CPU 段 | **进程内直调，不发帧**（`LocalFullModelProvider`），但 hidden 仍过 `f32 → base64 → JSON → sha256` | 非网络问题；是**编解码拷贝税** | `scheduler_task_worker.py:_ensure_local_task_worker_provider`（注释："没有 TCP 连接"）；`engine_host.py:3449-3452` |
| 供给期：`distribute` 把段推到节点 | HTTP Range 逐文件 + 1 MiB chunk + 每 16 MiB checkpoint | **是瓶颈，且是伪瓶颈**（§3.2） | `model_supply_assets.py:40-41`、`api/routes_model_supply.py:supply_file` |
| 供给期：`local_cut` | 本地读源 → 裁切 → 写产物，零网络 | 否（58.7 s 已贴磁盘限） | `docs/已知问题记录.md:59-68` |

**一句话诊断**：`628 s / 1.98 GB = 3.15 MB/s` 这个平均值有误导性。日志里同一轮卡在 `bytes_received=11534336/1983372689`（**恰好 11 MiB 整**，`docs/已知问题记录.md:98`），且**小于第一个 16 MiB checkpoint 门槛** —— 在第一次 journal checkpoint 之前数据流就已停止流动。这不是"带宽低"，是**传输停摆**。同一轮 Android 走 ≈100 MB/s，证明 master 侧出口有千兆线速能力。

**PCIe 在本项目不是主瓶颈**：推理期每 step 跨 GPU↔CPU 边界只有 `4096 × 4 B = 16 KiB` 激活（§1.3），在 15.75 GB/s 链路上传输部分约 1 µs，真正花掉的是固定开销与 base64/JSON 编解码。吃 PCIe 的是**权重上/下卡**，而那是供给期一次性动作。

## 1. PCIe 的物理现实

### 1.1 各代有效带宽

下表是"单向、已扣除物理层编码开销"的有效数据率，不是营销口径的 GT/s：

| 代 | x1 | x4 | x8 | x16 |
| --- | --- | --- | --- | --- |
| PCIe 3.0 | 985 MB/s | 3,938 MB/s | **7,877 MB/s** | **15,754 MB/s** |
| PCIe 4.0 | 1,969 MB/s | 7,877 MB/s | **15,754 MB/s** | **31,508 MB/s** |
| PCIe 5.0 | 3,938 MB/s | 15,754 MB/s | **31,508 MB/s** | **63,015 MB/s** |

来源：TrueNAS 文档《Interconnect Maximum Effective Data Rates》，注明单流向、尽量剔除物理编码开销 [官方文档] <https://cdn.truenas.com/docs/references/performance/interconnectdatarates/>。
交叉验证（同一量级、按 GT/s 与 128b/130b 编码推导：3.0 = 8 GT/s、4.0 = 16 GT/s、5.0 = 32 GT/s）[官方文档/社区报告] <https://www.thomas-krenn.com/en/wiki/PCI_Express>。

**实际可达率低于上表**：上表是有效数据率，但 `cudaMemcpy` 端到端还要付 TLP、DMA 引擎启动、同步等开销，常见落在有效值的 **75%–90%**（4.0 x8 上约 11–14 GB/s）[推测]。别用这个区间做验收，用 `cuda-samples` 实测：

```
bandwidthTest.exe --device=0 --mode=shmoo     # 本机 pinned / pageable 两条曲线
```

### 1.2 笔记本 vs 台式机：`RTX 4060 Laptop` 是 x8

实机报告显示 `RTX 4060 Laptop GPU` 的链路为 **PCIe 4.0 x8**：SiSoftware 基准结果页明确标注 `PCIe 4.0 x8` [社区报告] <https://ranker.sisoftware.co.uk/show_run.php?q=c2ffcdfadcbddce1d0e5d4e1d7e2c4b68bbb9df89da090b6c5f8cb&l=en>。

含义不是"笔记本才缩水"，而是**这一档 GPU 芯片本身就只引出 8 条 lane** ⇒ 15,754 MB/s 是这台机器的天花板，而非 x16 的 31,508 MB/s。笔记本平台 CPU 侧 lane 更紧（独显 x8 + NVMe x4 + 雷电），叠加后更不可能给到 x16 [推测]。

**必须实测，不要相信型号名**：

```
# Windows
Get-PnpDevice -Class Display | Select-Object FriendlyName, InstanceId
# 更直接：装 GPU-Z 看 "Bus Interface"，或在 WSL/Linux 下
lspci -vv | Select-String -Pattern "LnkCap:|LnkSta:"
```

`LnkSta` 显示实际协商宽度与速率（例如 `Width x8, Speed 16GT/s`），`LnkCap` 是上限。降速/降宽（`x8 → x4`、`16GT/s → 8GT/s`）在笔记本上并不罕见（M.2 复用、BIOS 节能），这是必须先排除的一条。

### 1.3 单次传输的延迟开销：为什么"搬激活"和"搬权重"是两个模型

设：
- `B` = 有效单向带宽（B/s）；
- `n` = 本次传输字节数；
- `L` = 一次传输的固定开销（API 调用 + 提交 + 完成/同步 + 驱动路径），**与 n 无关**。

单次耗时 `T ≈ L + n/B`。`L` 的量级在消费级 Windows 驱动栈上是 **数微秒到数十微秒** [推测，须实测]。

两个极端：

| 场景 | n | n/B（4.0 x8, 15.75 GB/s） | L（假设 10 µs） | 有效带宽利用率 |
| --- | --- | --- | --- | --- |
| 搬 1 token 激活（d=4096, f32） | 16 KiB | 1.0 µs | 10 µs | **≈ 9%** |
| 搬 1 层 Q4 权重（≈495 MB） | 495 MB | 31 ms | 10 µs | ≈ 100% |
| 搬整段 `[28,32)`（实测 1.98 GB） | 1.98 GB | 126 ms | 10 µs | ≈ 100% |

结论（这是本项目最该记住的一条）：

- **激活传输是延迟受限的（latency-bound）**。把 hidden 从 f32 换成 f16 只能把 1 µs 的传输段减半，对 10 µs 的固定开销毫无影响；要提速只能**减少搬运次数**（合并 step、整段 prefill 一次搬）或**减少固定开销**（复用 pinned buffer、避免 per-call 分配）。
- **权重传输是带宽受限的（bandwidth-bound）**。它天然摊薄固定开销，所以"权重走 PCIe"在物理上完全不亏 —— 前提是**不要每一步都搬**。

`L` 必须实测，不能引用别人的数字：

```python
# 最小验证：固定 16 KiB，循环 1000 次 cudaMemcpyAsync + sync，取中位数
# 对照 1 MiB / 16 MiB 三档，斜率 = 1/B，截距 = L
```

本项目的 `L` 还要叠加 Python 侧税：`np.ascontiguousarray(...).tobytes()` → `base64.b64encode` → JSON 序列化 → 对端 `base64.b64decode(validate=True)` → `np.frombuffer` → `hashlib.sha256`（`src/inference_service/engine_host.py:3449-3452`、`:3478-3482`；`src/inference_service/protocol.py:206`）。base64 本身有 **4/3 膨胀**，且这几步在 batch=1 的 decode 路径上是**每 step 每边界**都发生一次 —— 这部分是纯 CPU 时间，与 PCIe 无关，但同样是"搬激活"成本模型里被忽略的大头 [实测数据/代码事实]。

## 2. 减少 PCIe 搬运算量的工程手段

### 2.1 Pinned (page-locked) memory

pageable 主机内存不能被 DMA 直接访问，驱动必须先把它拷进一块临时的 pinned 暂存区，于是 **H2D 变成两跳**（pageable → staging → device），D2H 同理。`cudaHostAlloc` / `cudaHostRegister` 得到的内存由 GPU 与 CPU 共享、无迁移、GPU 侧按 2 MB 页映射 [官方文档] <https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html>（allocator 对比表）。

- 收益：更大带宽、可异步、可被零拷贝映射。
- 代价：pinned 内存不可换页，**过量分配会拖垮整机**（尤其这台 31.6 GB 内存的笔记本同时要装 `[8,24)` 的常驻权重）。
- 本项目落点：给 hidden 收发各准备**一块按最大 `n_tokens` 预分配的 pinned ring buffer**，禁止 per-step `np.ascontiguousarray().tobytes()` 新建。收益在**去掉页锁定/释放开销**，不在提升峰值 [推测]。

### 2.2 `cudaMemcpyAsync` + CUDA stream

要点：异步拷贝必须配 **pinned 源/目的**，否则运行时自动退化（内部插入同步）。默认流与计算流交错会序列化，必须显式建流 + event 依赖。

### 2.3 零拷贝（zero-copy / mapped memory）

`cudaHostAlloc(cudaHostAllocMapped)` 得到的 pinned 内存可被 GPU 经 PCIe BAR 直接读写，无需显式 `cudaMemcpy`。适用：**一次性、小数据、只读写一次**；不适用：反复访问（每次都付一次 PCIe 事务）。对本项目 16 KiB 激活，这是"把 memcpy 换成 kernel 直接读 host 内存"，省一次拷贝但把延迟摊进 kernel，**净值须实测** [推测]。

### 2.4 GPUDirect RDMA / GPUDirect Storage：本项目**不适用**

官方手册的关键限制 [官方文档] <https://docs.nvidia.com/cuda/gpudirect-rdma/index.html>：

1. "GPUDirect RDMA is available on both **Tesla and Quadro** GPUs" —— RTX 4060 Laptop 是 GeForce，不在支持之列；
2. "the two devices must **share the same upstream PCI Express root complex**"；
3. 需要改**内核驱动**（`nvidia_p2p_get_pages`）+ `nvidia-peermem` + ConnectX-3 VPI 或更新网卡，全部是 **Linux** 路径；
4. 每次 pin 的开销"up to **milliseconds**"，必须做 lazy unpinning + registration cache 才可用。

⇒ 结论：三机异构、Windows/Android、GeForce 的组合下，GPUDirect 系列**直接排除**，不要在这上面花工。GPUDirect Storage 同理（同样依赖 Tesla 级 + 特定文件系统/内核支持）。

### 2.5 统一内存（UVM）在 Windows 上：不要用

CUDA 编程指南把 Windows/WSL 归入"**有限统一内存支持**"的独立范式，单列一节（`Unified Memory on Windows, WSL, and Tegra`），与 Linux HMM / Grace Hopper 的完整支持区分开 [官方文档] <https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html>。

该范式的实际含义：managed 内存从 CPU 内存起、按**粗粒度**迁移到 GPU，CPU 与 GPU **不能并发访问**同一区域，必须显式同步；**不支持超配换页**（显存放不下时不会自动迁回主机）—— 对 8 GB 显存跑 9B 模型是致命的；迁移由缺页驱动，随机访问小块会触发 TLB 风暴。

⇒ 本项目应**显式分段 + 显式 pinned 拷贝**。UVM 在这里没有收益，只有不可控的延迟尖峰。

### 2.6 计算与传输重叠

实现要点：双缓冲（A 在算、B 在传）、`cudaMemcpyAsync` + 独立 stream、按 chunk 提交。收益边界：重叠上限是 `min(T_compute, T_transfer)`；当固定开销 `L` 占比高、单次 `n` 小时，**流水化增加提交次数 = 增加总开销**。本项目 decode 阶段 16 KiB/step 延迟受限，**双缓冲几乎无效**；prefill 一次 4096 token（64 MiB f32）带宽受限，**chunked + 双缓冲有效** [推测]。落地判据：先量 `T_transfer/(T_transfer+T_compute)`，< 10% 就别做重叠，去做"减少边界数"。

## 3. 跨机器传输优化

### 3.1 局域网 TCP 的真实吞吐

| 链路 | 有效数据率（单向，L2 口径） | TCP 实测上限（典型） |
| --- | --- | --- |
| 1 GbE | 125 MB/s | **≈ 118 MB/s**（940–948 Mbps） |
| 2.5 GbE | ≈ 312 MB/s [推测，按 1GbE 线性放大] | ≈ 280–295 MB/s [社区报告，实测被限在 ~1.9 Gbps 的例子见 Dell 社区帖] |
| 10 GbE | 1,250 MB/s | ≈ 1,100–1,180 MB/s [推测，取决于 CPU 与 NIC offload] |

L2 有效数据率来源：TrueNAS 文档（1 GbE = 125 MB/s，10 GbE = 1,250 MB/s）[官方文档] <https://cdn.truenas.com/docs/references/performance/interconnectdatarates/>。
千兆 TCP 上限的 **940–948 Mbps** 有多条独立实测互相印证 [社区报告]：<https://github.com/mendel5/iperf3-results>、<https://superuser.com/questions/1417479/iperf-indicating-940-mbits-sec-using-cat-5-cable>、<https://packetlife.net/blog/2011/feb/28/proving-network-not-problem-iperf/>。

**这条数字是本项目最重要的锚**：Android 实测 1.1 GB / 11 s ≈ **100 MB/s**，已经落在千兆线速的 85% 上。所以 `3.15 MB/s` 不可能是"网络带宽不够"，只能是**这条流自己的问题**。

调优点（按性价比）：

1. **MTU**：全路径支持时用 9000。1 GbE 上线速已近饱和、收益有限，Wi-Fi 与虚拟网卡路径上明显 [推测]。
2. **窗口与拥塞控制**：Windows 从 `autotuninglevel=normal` 起步；高 RTT 链路必须保证窗口 ≥ `BDP`（1 GbE × 30 ms ≈ 3.75 MB，窗口小于它就跑不满）。
3. 关键命令：
```
netsh int tcp show global
netsh interface tcp show heuristics        # 确认没有第三方 profile 干扰
Get-NetTCPSetting | Select-Object SettingName, AutoTuningLevelLocal, CongestionProvider
iperf3.exe -c <peer> -t 30 -P 1            # 单流
iperf3.exe -c <peer> -t 30 -P 8            # 多流，区分"单流受限"与"链路受限"
```
**判据**：单流慢、多流快 ⇒ 窗口/单连接问题；单流多流都慢 ⇒ 链路问题；`iperf3` 快但应用慢 ⇒ 应用层问题（本项目正好落在这一档）。

### 3.2 `3.15 MB/s vs 100 MB/s` 的根因排查手册

按可能性排序。每条给"怎么验证"与"怎么排除"。

**#1（最高）传输停摆，不是平均慢。**
证据：卡在 `bytes_received=11534336`（11 MiB 整）超过 7 分钟（`docs/已知问题记录.md:98`）。11 MiB 是 1 MiB chunk 的整数倍，说明进度按 chunk 上报；`11534336 < 16 MiB`，说明**第一个 journal checkpoint 还没到**，与磁盘 checkpoint 无关。
验证：把供给日志按秒打点，算瞬时速率而非平均速率。
```powershell
# 抓这一条流的瞬时率
Get-Counter '\Network Interface(*)\Bytes Received/sec' -SampleInterval 1 -MaxSamples 60
# 单流 TCP 重传/丢包
netstat -s -p tcp | Select-String -Pattern 'retrans|Resets'
```
若瞬时率在某点后长期为 0 ⇒ 是"挂住"，直接跳到 #2/#5；若长期稳定在 3 MB/s ⇒ 才是速率问题。

**#2（很高）并发供给的队头阻塞。**
master 同时向 Y700 传 1.1 GB、向 Surface 传 1.98 GB。发送端是 FastAPI `StreamingResponse` 的**同步生成器**，且**每个 1 MiB chunk 都要调一次** `authorize_file()` 与 `touch_capacity_evidence()`（`src/api/routes_model_supply.py:supply_file`）。这两者都触碰供给协调状态；同步生成器还经 `iterate_in_threadpool` 每 chunk 一次线程池往返。
验证（决定性实验）：**同一段、同一节点，独占供给 vs 并发供给各一次**，比单流吞吐。
- 独占翻倍以上 ⇒ 确认队头阻塞；
- 独占仍 ~3 MB/s ⇒ 排除本条。
加固命令/改法：把 `authorize_file` 移出循环（进入生成器前校验一次，循环内只在有取消信号时校验），chunk 从 1 MiB 提到 4–8 MiB。

**#3 Surface 走的是 Wi-Fi，不是以太网。**
Surface 7 Pro 无 RJ45，2.5 GbE/有线假设直接不成立。
验证：
```powershell
netsh wlan show interfaces
# 看: 接收/传输速率(Mbps)、信号、信道、Radio type(802.11ac/ax)
Get-NetAdapter | Select-Object Name, InterfaceDescription, LinkSpeed, Status
```
若 `Receive rate` 只有 100–200 Mbps ⇒ 有效 ≈ 12–25 MB/s 上限，且实际常再打三折。若信号 < 60% 或与 master 不在同一 5 GHz 信道，**足以解释 3 MB/s**。
排除法：临时用 USB-C 千兆网卡接同一交换机，重测同一段。

**#4（高）tailscale 走了 DERP 中继而非直连。**
项目自己的 `src/network_path.py` 已实现 `tailscale_direct` / `gateway_relay` 判据，说明这类路径真实存在过。
验证：
```powershell
tailscale status                 # 对端显示 direct: 还是 relay "xxx":
tailscale ping <peer>            # 出现 "via DERP" 即中继
tailscale netcheck               # 看 UDP 是否可达、NAT 类型
```
DERP 是应用层中继，吞吐常被限在个位数 MB/s 量级 [社区报告/推测]。若命中，改走同一局域网直连地址（项目 `detect_lan_ip()` 已主动排除 tailscale/zerotier 接口，`src/tcp_comm.py:549-630`，但供给 URL 用的是哪个 host 必须单独确认）。

**#5 接收端每 16 MiB 的 flush + journal checkpoint，以及结尾整文件 `fsync`。**
`_RESUME_INTERVAL = 16 MiB`，每次触发 `handle.flush()` + `journal.checkpoint()`；结束再 `os.fsync`（`src/model_supply_assets.py:40, 2377-2386`）。1.98 GB ≈ 124 次 checkpoint + 一次 2 GB 脏页回写。
验证：在这两处打时间戳，量单次耗时；把 `_RESUME_INTERVAL` 临时改成 64 MiB 重测。
```powershell
# 看是不是磁盘饱和
Get-Counter '\PhysicalDisk(*)\% Disk Time','\PhysicalDisk(*)\Avg. Disk Queue Length'
```
判据：`% Disk Time` 长期 >90% 且队列 >2 ⇒ 磁盘是瓶颈；否则排除。

**#6 Windows Defender 实时扫描。**
下载目录若被实时扫描，写入变慢且 CPU 被吃。
验证：
```powershell
Get-MpPreference | Select-Object -ExpandProperty ExclusionPath
# 临时把接收目录加入排除后重测同一段
```

**#7 逐文件 + 每文件结尾全校验，小文件占比高。**
每文件一次 HTTP 请求 + 一次最终 sha256；文件多而小时，连接建立与慢启动占比高。
验证：统计段内 `files` 数量与平均大小；`Get-NetTCPConnection -State Established` 看并发连接数。判据：平均 < 10 MB ⇒ 连接开销不可忽略。

**#8 `timeout=30` 触发的重连，导致反复从同一 offset 重发。**
验证：日志里同一文件的 `Range: bytes=<offset>-` 起点序列；起点反复回到旧值 ⇒ 断点续传未生效。

**#9 源端被同机其他供给/加载挤占。**
master 同时向显存加载 PyTorch 段、向 Android 供段，磁盘与 CPU 都忙。
验证：`Get-Counter '\Process(python*)\% Processor Time'`，并确认显存加载与供段是否时间重叠。

**排序后的操作顺序**：#1（10 分钟，免费）→ #2（一次对照实验，最有信息量）→ #5（改一个常量）→ #3 → #4 → #6/#7/#9。

### 3.3 传输与校验能否重叠：能，而且当前**已经不是瓶颈**

现有实现是**边收边算**：`running_digest.update(chunk)` 在接收循环内（`src/model_supply_assets.py:2375-2376`）。这是正确做法 —— 校验与网络接收天然并行，只要哈希吞吐 > 链路吞吐就不会成为瓶颈。

数量级判断：单核 SHA-256 通常 **300 MB/s 以上**，带 SHA-NI 的现代 x86 可到 1 GB/s 量级 [推测，须实测]；而这条流只有 3.15 MB/s，相差两个数量级。**校验不是本轮的瓶颈，也不会成为伪瓶颈。**

但有两处**真实的冗余**值得砍：

1. 落地后 `_verify_files` 全量重算摘要 ⇒ 把 1.98 GB **再读一遍**（盘 300 MB/s 约 6.6 s，50 MB/s 约 40 s）。
2. 每次 checkpoint 写一次 journal（约 124 次）。`_RESUME_INTERVAL` 16→64 MiB 可减 4× 状态写入，代价是断点粒度变粗。

建议：保留"边收边算"，把二次校验改成"仅当 checkpoint 不完整/续传中断时才全量重算"。实测哈希吞吐：

```powershell
Measure-Command { Get-FileHash 'X:\path\segment.gguf' -Algorithm SHA256 }   # 大小 ÷ 耗时
```

## 4. 架构层面的关键问题：同机跨引擎数据交换

### 4.1 正确的零拷贝路径（按优先级）

同机两段的"零拷贝"分级，不要一上来谈 GPU 零拷贝：

1. **进程内直调（最优，本项目已实现）**。同 host 两执行器共进程时，hidden 就是一个 `np.ndarray`，连 IPC 都不该有。`master#cpu` 走的正是这条路：复用与远端 worker **完全相同**的 `StageRequest`/`ProviderExecutor` 契约，但**不发帧**（`scheduler_task_worker.py:_ensure_local_task_worker_provider`："与远端 worker 共用同一套契约，却没有 TCP 连接"）。
2. **共享内存 + pinned buffer**。必须跨进程时：GPU 段 `cudaMemcpyAsync` 到 pinned host buffer，对端 `mmap`/`CreateFileMapping` 同一物理页，零二次拷贝。
3. **mapped pinned memory**。`cudaHostAlloc(cudaHostAllocMapped)` + UVA，GPU 直写主机 pinned 内存，同机对端即同一物理内存，省掉显式 D2H。
4. **回环 TCP（最差）**。仍要过 socket、协议栈、base64、JSON，延迟与 CPU 税远超前三种。

### 4.2 判据：什么样的实现会不小心把内存拷贝变成网络往返

这是本次调研最该固化成 checklist 的部分。出现以下任一现象，就是绕路（或至少是多一层税）：

| # | 现象/判据 | 检查方法 | 本项目现状 |
| --- | --- | --- | --- |
| A | 同机边界的调用栈里出现 `socket` / `send` / `recv` / `http` / `urllib` | 在边界前后打 callstack；或抓 loopback 流量（`pktmon` / Wireshark `\Device\NPF_Loopback`） | ✅ 已修（进程内直调） |
| B | 对同机对端使用**非回环地址**（LAN IP `192.168.*`、tailnet `100.64/10`、`*.ts.net`） | 打印实际连接的 `peer`，与 `127.0.0.1` 比对 | ⚠️ 需逐条确认：`detect_lan_ip()` 优先返回真实 LAN IP，会**排除** tailscale 接口（`src/tcp_comm.py:549-630`）—— 逻辑正确，但若注册端点落到 LAN IP 而供给 URL 又用它，就是"用网卡地址访问自己" |
| C | 每 step 出现 `base64` / `json` / `pickle` 编解码 | grep 线上的字段名（本项目是 `hidden_f32` / `hidden_out_f32` / `tensor_ref`） | ⚠️ **仍在用**：`f32 + base64 + JSON + sha256`，每 step 每边界一次 |
| D | 每 step 重新分配/释放 pinned buffer | 看是否 per-call `np.ascontiguousarray().tobytes()` | ⚠️ 是，per-call 新建 |
| E | 同机两个执行器各自建了一套 TCP 连接与回执通道 | 数 `_connections` 里 `node_id` 的条目数 | ✅ 已按物理机去重、按执行器分视图（`src/model_supply.py:1857-1872`） |
| F | 权重"就地常驻"的段却仍走传输通道 | 看该段 `actual_downloaded_bytes` 是否为 0 | ✅ `master#cpu` 走 `_local_resident_view`，不发网络（`src/model_supply.py:1028, 1886-1894`） |

**把 C 和 D 修掉的具体收益估算**：hidden `4096 × 4 B = 16 KiB`，base64 后 21.3 KiB；JSON 再包一层，字符串处理 + 两次内存拷贝 + 一次 sha256。batch=1 decode 时每 step 每边界 1 次，4 段链 ⇒ 约 4 次/step。以 1 tok/s 的现状看，这部分单次成本在几十微秒到几百微秒量级 [推测]，**不是当前主瓶颈**；但一旦 decode 提速到 10 tok/s 以上，它会立刻变成可测量的固定税。修法：控制面仍走 JSON，**数据面改二进制帧**（f16 + 裸字节 + 长度头，去掉 base64 与 JSON）。

## 5. 成本判据：什么时候搬激活、什么时候搬权重、什么时候本地裁层

### 5.1 基本不等式

符号：
- `W` = 该段权重字节（本项目实测 `[28,32)` 4 层 = 1.98 GB，`docs/已知问题记录.md:60`）
- `B` = 有效单向带宽（PCIe 4.0 x8 = 15.75 GB/s；1 GbE TCP = 0.118 GB/s）
- `a` = 每 token 激活原始字节 = `n_embd × 4`（f32）；线上膨胀系数 `κ`（base64 ⇒ 4/3）
- `N` = 该段要处理的累计 token 数（prefill + decode × 请求数）
- `L` = 单次传输固定开销（PCIe ≈ 10 µs；跨机 ≈ RTT + 序列化 ≈ 0.1–5 ms，视路径而定）[推测]
- `t_c` = 本机算该段每 token 时间

**搬权重更优 ⇔**

```
N · (a·κ/B + L)  >  W/B + L
⇒  N  >  (W/B) / (a·κ/B + L)
```

代入 PCIe 4.0 x8、`W = 1.98 GB`、`a·κ = 4096×4×4/3 ≈ 21.3 KiB`、`L = 10 µs`：

```
W/B  = 0.126 s
分母 = 21.3 KiB / 15.75 GB/s + 10 µs ≈ 1.35 µs + 10 µs = 11.4 µs
N > 0.126 / 11.4e-6 ≈ 11,000 token
```

**判读**：同机 PCIe 上，这段要连续吃满 **约 1.1 万 token** 才值得把权重搬过去（且此后不换段）。单请求 32–4096 token 远低于门槛 ⇒ **权重就地常驻、激活才搬**。这就是 `local_cut` / `master#cpu` 常驻的正确性依据，也是 `distribute` 在单次请求语境下不划算的量化原因。

代入 1 GbE 跨机、`W = 1.98 GB`、`B = 0.118 GB/s`、`L ≈ 1 ms`：

```
W/B  = 16.8 s
分母 = 21.3 KiB / 0.118 GB/s + 1 ms ≈ 0.18 ms + 1 ms = 1.18 ms
N > 16.8 / 0.00118 ≈ 14,000 token
```

**判读**：跨机同理 —— 一段要处理上万 token 才值得从网络拉权重。注意口径：`distribute` 的收益是**跨请求累积**（拉一次、之后复用），所以"拉一次当常驻"合理，错的是"**每轮重拉**"。本项目已有跨 operation 内容复用（`receive_segment` 先走 `_reuse`，内容键排除 `operation_id`），必须保证真命中 —— 一旦退化成重拉，就是 628 s 这种代价。

### 5.2 本地裁层 vs 内网传段

**选 `local_cut` ⇔**

```
T_cut  <  W / B_net + W / B_disk_write + T_verify
```

本项目实测直接给出结论：

| 路径 | 实测 | 推算有效吞吐 |
| --- | --- | --- |
| `local_cut` | 58.7 s | 读源 + 写产物（约 2×1.98 GB）⇒ **≈67 MB/s** 磁盘有效吞吐 |
| `distribute` | 628 s | 1.98 GB ⇒ **3.15 MB/s** |

**只要节点持有与本次供给 `source_model_sha256` 一致的整模源，`local_cut` 在数学上就必胜**（58.7 s < 628 s，差 10.7×）。这不是调参问题，是路径选择问题。所以：

- 判据一：**网络有效带宽 < 本地磁盘有效吞吐 ⇒ 一律本地裁层**。1 GbE 的 118 MB/s 理论值虽高于 67 MB/s，但叠加校验、checkpoint、并发争用后实测只剩 3.15 MB/s，胜出方永远是本地。
- 判据二：`local_cut` 的**前置条件**是源可得且身份可核（`find_spec("gguf")` + `cut_layers.py`）。`docs/已知问题记录.md:70-84` 已记录缺 `gguf` 导致能力声明为假、静默退化到 `distribute` 的故障 —— **能力声明为真 ≠ 真能裁**，必须由 `inventory()` 的真实磁盘清点背书（同一文档 `:101-120`）。
- 判据三：网络路径修好后不等式可能翻转。修复后必须重跑同一段对照，用新的 `628 s → ?` 重新判定，**不要沿用旧的 3.15 MB/s 做长期架构决策**。

### 5.3 什么时候该搬激活

- 段权重大（> 数百 MB）且单次请求 token 数少（< 门槛 N）⇒ 搬激活；
- 边界多（4 段链）⇒ 每条边界一次小传输，此时**减少边界数**（合并段/减机器）的收益远大于"优化单次传输"；
- 激活是延迟受限的 ⇒ 优化方向是**减少次数**和**去掉 base64/JSON**，不是提高带宽。

## 6. 优化手段总表

| 优化手段 | 预期收益 | 实施代价 | 前置条件 | 风险 |
| --- | --- | --- | --- | --- |
| **供给加并发/去队头阻塞**（`authorize_file` 移出 chunk 循环、chunk 1 MiB→8 MiB） | 若命中 #2，单流吞吐可数倍提升 [推测] | 低（1 个函数改动 + 回归） | 需先用独占/并发对照实验确认根因 | 取消/撤权的响应粒度变粗（每 8 MiB 才检查一次） |
| **修 `distribute` 停摆（先查 #1/#3/#4/#5）** | 从 3.15 MB/s 拉回 10–100 MB/s 量级 | 中（需真机分项定位） | 真机 + 抓包/计数器权限 | 归因错误会把时间花在无关环节 |
| **`local_cut` 能力真实化**（`gguf` 依赖 + 磁盘清点判据） | 已实测 **628 s → 58.7 s（10.7×）**；冷启 670.83 s → 112.98 s | 低（已修，待真机验收） | 节点持有同 sha 整模源 | 清点与磁盘脱节会退化成真下载 |
| **hidden 数据面去 base64/JSON**（改二进制帧，f16 + 长度头） | 去掉每 step 每边界的编解码与 sha256；decode 提速后才显著 | 中（协议双侧 + 回归） | 两端可同时升级（版本协商） | 协议不兼容；f16 会引入数值差（需逐 token 对拍） |
| **hidden 复用 pinned ring buffer** | 去掉 per-step 分配/页锁定开销 [推测] | 低 | 最大 `n_tokens` 可预估 | pinned 过量会饿死本机 CPU 段 |
| **prefill 分块 + 双缓冲** | prefill 阶段带宽利用率提升；对 decode 无收益 | 中 | 需先量 `T_transfer/(T_transfer+T_compute) > 10%` | 小 chunk 增加固定开销，可能变慢 |
| **chunked transfer（供给端）** | 已存在（1 MiB）；提到 4–8 MiB 减少 syscall/线程池往返 | 极低 | 无 | 内存峰值 +几 MiB |
| **校验重叠**（保留边收边算，砍掉落地后二次全量重算） | 省一次 1.98 GB 读盘（慢盘约 40 s） | 低 | checkpoint 需完整记录摘要 | 续传中断时需回退到全量重算 |
| **`_RESUME_INTERVAL` 16→64 MiB** | 状态写入次数降 4× | 极低 | 无 | 断点粒度变粗，崩溃后重传更多 |
| **jumbo MTU / TCP 窗口调优** | 1 GbE 上收益有限（已近线速）；Wi-Fi/跨网段明显 | 低 | 全路径支持 9000 MTU | 任一跳不支持会静默降级/黑洞 |
| **Pinned memory + `cudaMemcpyAsync`** | 提高 H2D/D2H 有效带宽、允许重叠 | 中 | 需固定缓冲管理 | 见上 |
| **Zero-copy mapped memory** | 省一次显式 D2H（小数据） | 中 | UVA + `cudaHostAllocMapped` | 反复访问时远慢于显存；净值须实测 |
| **UVM（`cudaMallocManaged`）** | **无正向收益** | — | — | Windows 属有限支持范式：不支持并发访问与超配换页 ⇒ **不采用** |
| **GPUDirect RDMA / Storage** | **不可用** | — | 需 Tesla/Quadro + 同 root complex + Linux 内核模块 + ConnectX | GeForce/Windows/Android 全不满足 ⇒ **不投入** |
| **减少段边界数（合并机器/段）** | 每条边界省一次小传输 + 一次同步 | 高（架构级） | 容量允许 | 与"异构拼接"的产品定位冲突 |

## 7. 对本项目的落地建议（按优先级）

1. **先做 10 分钟的免费判定**：跑 §3.2 的 #1（瞬时速率）与 #2（独占/并发对照）。拿到这两个数之前不要改任何传输代码。
2. **确认 PCIe 实际宽度**：`LnkSta` 是否真为 x8 / 16GT/s。若降到 x4，权重上卡时间翻倍，§5.1 的 `N` 门槛随之改变。
3. **把 `local_cut` 钉死为默认路径**，`distribute` 仅兜底且必须命中跨 operation 复用。10.7× 的实测差距，没有理由让网络传输成为常态。
4. **推理期同机边界维持进程内直调**，不要为"统一"改回 TCP —— 那是把一个 `np.ndarray` 换成 socket + base64 往返。
5. **hidden 数据面迁到二进制帧**，排在传输停摆之后、decode 提速之前。
6. **明确写下不做的事**：UVM（Windows 有限支持）、GPUDirect（GeForce/Windows 不支持）。写进 ADR 免得重复调研。
