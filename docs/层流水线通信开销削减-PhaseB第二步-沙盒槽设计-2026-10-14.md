## 0. 问题：为什么"回滚"是 Phase B 的死结

Phase B 的想法是「一次推 γ 个位置、一次回 γ 个 token」以摊薄 RTT。但投机解码要求：**被拒绝的 draft 必须把状态退回**，否则下一步的 KV / recurrent state 就脏了。

**现状（已核实）**：
- 本仓**没有任何 KV / recurrent 回滚实现**：`grep -E 'def verify|rollback|回滚|revoke|crop|truncat'` 于 `src/` 的命中**全是 auth / cluster 的会话吊销**，与推理状态无关。
- 上游 llama.cpp **有** `seq_rm`（`android/app/src/main/cpp/llama.cpp/src/llama-kv-cache.cpp:395`），也有 `seq_cp`（`:463`）与 `seq_add`（`:582`）。
- **hybrid（`qwen3-5-9b`）的 linear 层是 recurrent state，不可事后重建** ⇒ 即使有 `seq_rm`，这条路在 hybrid 上依然危险（Phase B 前置核查 ②）。
- 生产 worker 的 `forward_hidden_to_token` 每次只回一个位置（`src/llama_keep_head.py:476-544`）。

⇒ 如果坚持"先写主序列、再撤销"，就要同时解决**KV 裁剪**与**recurrent 重建**两个问题，后者在 hybrid 上近乎不可行。

---

## 1. 方案：把"先写再撤"换成"在沙盒里算，接受才写"

核心改动是**状态归属**，不是算法：

```
主序列 seq 0  ── 持有 prefix 的 KV（唯一权威状态）
                  │
                  ├─ seq_cp(0 → 沙盒 S, 0..prefix_len)   # 把 prefix 的 KV 单元格"挂"给沙盒
                  │    （seq_cp 是给已有 cell 加 seq 标记，不复制数据 ⇒ 不重算 prefix）
                  │
沙盒序列 S    ── 一次 forward γ 个位置（token = [draft_1..draft_γ]）
                  │    每个位置各自的 logits ⇒ 与下一个 draft 比对
                  │
接受 k 个      ── seq_cp(S → 0, 0..prefix_len+k)         # 只把"已接受"的部分并回主序列
                  └─ 丢���沙盒 S（seq_rm(S, -1, -1) 或整体作废）
```

**为什么这绕开了死结**：
1. **主序列的 KV 从不被 draft 污染** ⇒ 不需要"撤销"，只不需要"合并"。
2. ⇒ **不需要逐位置 `seq_rm`**（沙盒整体丢弃即可）。
3. ⇒ **recurrent state 同理**：沙盒那一次 forward 只动沙盒的状态；主序列的状态**从没被推进过** ⇒ 不存在"重建"问题（**前提见 §4 待核实 4**）。

**为什么 draft 必须是"可独立产生"的**：这条链成立的关键是 γ 个位置能被**一次** forward（它们的输入 token 必须在这一步之前就已知）。n-gram / prompt-lookup draft 正是如此（从 prompt 里查重复片段），所以：

- **可行**：n-gram / prompt-lookup draft（本仓 `src/llama_engine.py:119 _apply_ngram_draft_model` 已在整模路径用过）+ 沙盒验证。
- **也可行但更贵**：用一个 draft 模型自回归产生 γ 个 token（本仓 `src/speculative*.py` 的路线），仍需一次 forward 验证。
- ⇒ 两者都与"一次推 γ 个位置"的物理形状吻合。

## 2. 已核实的约束（决定成本，必须写进设计）

| 事实 | 出处 | 设计含义 |
|---|---|---|
| **`n_ctx` 按 `n_seq_max` 均分**：`ctx_per_seq = n_ctx // n_seq_max` | `src/llama_keep_head.py:75-84`（注释记录了实测：`n_ctx=2048 / n_seq_max=8` ⇒ 单序列仅 **256** 槽位，且失败表现是 `runner_failed`，**与"模型算错"难以区分**） | **沙盒不是免费的**：多一个序列槽就少一份 ctx 预算。⇒ **只开 1 个沙盒**（串行复用），成本 = **`n_ctx × 2`** |
| `seq_cp` 只在 **full（非分页）** KV 上支持 | `llama-kv-cache.cpp:518` `GGML_ASSERT(is_full && "seq_cp() is only supported for full KV buffers")` | 需要确认本仓实际跑的是 full KV（本仓 `src/paged_kv_cache.py` 是**自有**分页层，llama.cpp 侧应仍为 full —— **待核实 1**） |
| `seq_cp` 语义 = 给已有 cell 加 seq 标记 | `llama-kv-cache.cpp:463-538`（`cells.seq_add(i, seq_id_dst)`） | **prefix 不重算** ⇒ 沙盒相对"独立跑一遍 prefix"是净省 |

## 3. 与可用性语义（A1–A10）的关系：**天然隔离**

这条是本方案最大的优点，也是选它而不是"改协议"的理由：

| 层面 | 是否触及 |
|---|---|
| 协议字段 / 帧类型 | **不触及** —— 沙盒与 `seq_cp` **全在 worker 本地**；跨机仍是既有的 `TOKEN_SEQ` 多位置回程（已落地，提交 `6da8e286`） |
| 租约 / `attempt_id` / `lease_epoch` 栅栏（A7） | **不触及** —— 一次 stage 仍是一次 offer/accept；沙盒只是这一次 stage **内部**的实现细节 |
| 心跳 / 断线检测 / 重连（A2/A4/A6） | **不触及** |
| 旧的包在重连后到达必须 fencing（A5） | **不触及** |
| 供给事务性（A9） | **不触及** |
| deadline 收敛（A8） | **部分相关** —— γ 个位置的一次 forward 比单 token 长，需要确认仍在 stage deadline 内（**待核实 3**） |

⇒ 结论：**本方案改动面在 worker 的推理实现内，不需要动 A1–A10 任何一条**。这与 Phase C（offer+hidden 合并，动准入时序）形成鲜明对比。

- 本装置用的是 **prompt 的 γ 个位置**（每个位置喂的是真实 token）—— 这与"prefill 语义"等价，

- 上游注释里那句"`ubatch.n_tokens > 1` 会改变浮点结果"在本装置上**没有造成 argmax 分歧**，
  但这不等于"逐位 float 相同"——本次判据是**逐 token argmax**（本仓纪律），不是逐位相等。

## 6. 一页纸结论

- **难点不是"多位置传输"**（已落地：`TOKEN_SEQ`，实测摊薄 5.43×），**而是"被拒 draft 的状态回收"**。
- **方案**：`seq_cp` 沙盒 —— 主序列持 prefix，沙盒做 γ 个位置的一次 forward，接受 k 个才把 `0..prefix+k` 并回主序列，沙盒整体丢弃。**不需要逐位置 `seq_rm`，也不碰 recurrent 重建**。
- **代价**：`ctx_per_seq = n_ctx // n_seq_max` ⇒ 只开 1 个沙盒 ⇒ **`n_ctx × 2`**。
- **优点**：**完全不触及 A1–A10**（沙盒是 worker 本地实现细节），因此**不需要改协议**，风险远低于 Phase C。
- **最大工程量**：**shim 需要扩展导出 `seq_cp` / `seq_rm`**（本仓 shim 现只导出 `forward_*`）。
- **第一步应该是**：在现有 relay 装置里测「一次 forward γ 个位置」与「逐 token 顺序推进」的**等价性** —— 这一步可能直接否掉语义前提，且零生产风险。
- **hybrid 仍另行评估**（recurrent state 大概率不随 `seq_cp` 复制）。
