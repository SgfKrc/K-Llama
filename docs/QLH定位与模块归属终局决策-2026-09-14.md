## 1. 主项目定位（最终裁定）

**主项目 QLH = 轻量分布式推理系统：引擎（数据面）+ 管理器（控制面）+ TUI/合同/验收基建，同仓同项目。**

- **一句话**：在边缘设备（无/弱 GPU）上默认用 <=1B GGUF/llama.cpp 模型本地完成推理，同时把 Edge/PC/工作站/Android 节点组织成可验证的 llama.cpp 模型分片系统，让更大模型由多个节点共同承载——**引擎层统一名为 Koakuma（混合推理引擎）**，内部承载 llama.cpp/GGUF 与 PyTorch/Safetensors 两套 backend；**有 CUDA 的节点保留 torch 能力并默认开启（显式开关，可关闭并退化为 llama.cpp）**，**无 CUDA 节点（含边缘默认安装）必须去 torch 化**；**Relay R 是 PC-only 的架构兼容轨道**，用于验证连续层段的 hidden handoff，当前不进入默认生产；**控制面**负责调度、分片合同、节点、租约和故障绕行。
- **主交付（重心）**：**TUI 对话与集群控制**——当前稳定入口是标准库 `tui_admin`，`CORE-TUI-01` 收口统一的 `qlh chat` 入口；两者都使用稳定协议调用本地或集群引擎。`qlh_edge` 只提供最小 HTTP/节点接入面；Edge 必须保留本地 <=1B 推理和 RPC worker 能力，不能退化为 HTTP 远程壳。Web/Android 是外部产品壳，不再定义主项目交付。
- **拆分原则**：控制面与数据面仍同仓分层；产品壳、知识库、图像生成、发布和运营工具独立为支线/子模块，Koakumix 接收小模型增强和生图侧车。
- **纪律**：控制面与数据面在**代码组织上分层**（目录/包可辨识、依赖单向：控制面可调用数据面，反之禁止），**不拆仓、不拆 CI**；产品壳与知识库不再占主仓。新增功能准入问句："它服务这套推理系统（引擎或管理器）吗？"

## 4. 分层与接口（同仓两层怎么协作）

```
[主仓·控制面 QLH Control]                [主仓·数据面 Koakuma]
  调度/集群/节点/控制入口  ──分片/模型/回退合同──▶  llama.cpp backend（无 CUDA / Edge）
  设备画像/合同/降级                                    torch backend（有 CUDA，默认开启）
        │                                                  TUI 对话（qlh chat）
        └────── 契约：schemas/（推理请求/结果/任务协议）──────┘
  Relay R（PC only） ───── hidden handoff 兼容验证，不替代 RPC
[产品壳支线] Web/Android/Koakumix ──▶ 可选用户体验（经版本化合同）
```

- **依赖方向（强纪律）**：控制面 → 数据面**单向**（管理器调用引擎执行任务；**引擎不得 import 控制面**）；同仓不同目录，可用一次性测试断言守住（import 检查）。
- **数据面对外**：`qlh chat`（TUI 对话，主交付）、`qlh_edge`（最小 HTTP）、models 资产面；
- **控制面对外**：cluster/scheduler/节点/审批面（`api_server` 控制侧端点）。

## 5. 实施路径（先固化断点，再并行攻克分片与 Relay 兼容）

| 阶段 | 动作 | 验收 |
| --- | --- | --- |
| **P1 TUI 对话**（主做，立即） | 收口 `qlh chat`：接入引擎和模型舰队；现行 TUI 形态是 Textual 外壳 `src/tui_textual.py`（旧自研实现已归档，见 [docs/TUI使用指南.md](TUI使用指南.md)） | 一条命令本地多轮/流式对话；Edge 无 torch |
| **P1.5 断点与低耦合门**（v5） | 对功能裁切/引擎重写做入口、import、合同、测试、资源和外置子模块映射；确保 TUI/API/模型下载/模型选择不断线 | 旧前端、邮件、生图、微服务不再被主线引用；外置仓只经稳定协议接入 |
| **P2 llama.cpp 单机基线**（v5） | Edge/PC 先跑通单进程 GGUF，默认 <=1B：模板/thinking、流式、多模态按模型舰队选配、TUI/API、CPU/可选 GPU；记录质量/内存/吞吐 | 默认 Edge/PC 无 torch；与既有行为有可复现对照 |
| **P2-R Relay 兼容**（v8） | L→L/D→L 严格行为对拍已完成（主仓矩阵 27/27 逐 token 一致）；位置契约、loopback 与跨机 SSH 隧道逐步生成均已落地（跨机 SSH 隧道 141/141）；下一步验证 f32 与采样矩阵 | loopback 证据与跨机/生产证据分开记录；默认关闭，不进入 Edge 路径；任一步未过生产门保持 fail-closed |
| **P3 llama.cpp 双进程与真机分片**（v5/v6） | 同机 host + RPC worker 双进程模拟，再做 PC 跨机，最后接 Android `librpc.so`；验证单机装不下、每节点部分驻留、租约/故障/安全 | 通过模型分片证据后才进入默认生产路由；Relay 不替代此门 |
| **P4 引擎分档与收敛**（v7 修订） | **有 CUDA 节点：Koakuma torch backend 默认开启（显式开关、可关闭并退化）**；无 CUDA 节点：llama.cpp/GGUF 且去 torch 化；任务图保持临时整模回退 | 主仓生产发行 = llama.cpp + Koakuma（按节点选 backend）+ control + TUI + contracts + evidence；**无 CUDA/Edge 安装包不得含 torch 依赖**；Relay 仅 PC 显式能力 |

> 注：首版的"管理包化/独立仓"路径（P2/P3）**撤销**——控制面留主仓；未来若出现触发条件（独立交付/宿主外使用/CI 冲突），再按候选计划四条件评估。

## 6. 不变式（本次决策不改变的事）

1. Koakumix/docagent/bridge/spawnledger 的既有独立状态与纪律不变；
2. 实验体系（fixtures/experiments/MANIFEST/EX-N3 门）留主仓（引擎质量基建）；
3. 边缘基线（≤300MB venv / ≤15s 冷启动 / 无 torch / TUI 可用）为**无 CUDA 数据面**的交付标准；**有 CUDA 节点**走 Koakuma torch backend（默认开启、可关闭并退化），不适用该基线；
4. 文档双轨归档（docs/archive、_archive）与"先归档后删"纪律不变；
 5. 控制面内部（scheduler 等）不因本决策提前改动行为；先通过断点门，再逐步替换执行适配器。
6. 分布式真机前必须完成 Edge/PC 单机与同机双进程模拟；失败时保留 Edge <=1B 本地 llama.cpp、其他节点分片或任务图回退，不得伪造分片成功。
7. Relay 的 loopback 与跨机 SSH 隧道逐步生成证据（主仓矩阵 27/27、跨机 141/141）不代表 f32 或采样矩阵已通过；旧 `LAYER_FORWARD` 协议不因 Relay 扩展为通用张量协议。
8. **默认值必须显式且入档**：Relay 默认关闭；有 CUDA 节点的 torch backend 默认开启但必须可显式关闭并退化。任何"隐式默认"都不作为验收依据。
