## 1. 已实现（有代码 + 有证据）

### 1.1 三个身份分离

| 身份 | 语义 | 缺省值 = 今天的行为 |
| --- | --- | --- |
| `node_id` | 物理节点 + 传输身份（TCP 键、incarnation 归属、故障归属） | 不变 |
| `executor_id` | 节点内执行器（`""` = 主执行器） | `""` |
| `capacity_domain_id` | 共享同一份内存总账的域 | `= node_id`（每节点独立） |

**缺省值让既有三机拓扑逐字节不变** —— 这是所有改动的回归门。

### 1.2 各层落点

- **契约层**：`Segment.executor_id` / `PipelineNode.executor_id`，唯一性判据放宽到
  `(node_id, executor_id)`。新字段一律**加末尾带默认值**（`Segment` 已有 9 个位置参数，
  插中间会静默错位）。
- **容量层**：`capacity_domains()` + `validate_capacity_domains()`，超额 `fail closed`。
- **执行层**：本机执行器复用 `LocalFullModelProvider` 容器，执行体是
  `EngineHost.execute_task_worker_stage`（签名与 `ProviderExecutor` 协议逐字匹配，
  自带 `_worker_layer_lock()`）。**懒建**：构造 provider 不构造 `EngineHost`。
- **producer 链**：`QLH_LOCAL_CPU_EXECUTOR=1` 开启后，`_get_pipeline_capacity_nodes`
  产出一条同 `node_id`、不同 `executor_id` 的记录；`assignment` 透传身份；
  部署与两个控制面白名单登记 `local_executors`。

### 1.3 离线可证的形态

`scripts/probe_local_executor_placement.py`（**不需要集群**）复刻四执行器与真实约束后：

```
usable（head → middle → tail）:
  master       mode=head
  master/cpu   mode=middle
  android      mode=tail
  rog          mode=tail

admitted=True
  master       [0,8)      ← GPU 段（PyTorch）
  master/cpu   [8,24)     ← 同机 CPU 段（llama.cpp keep-head），16 层
  android      [24,25)
  rog          [25,32)
```

**这就是目标形态**：CPU 段权重常驻主机内存、CPU 就地计算、零 PCIe 搬运。

## 2. 真机验收（2026-10-26 达成）

### 2.1 四段并存的实测形态

三机（master / TABLET-2TLUCNU8 / android-542cd254）在线后供给，`POST /api/models/intent`
→ `intent=ready`（221 s）：

```
master          ''      [0,8)     pytorch     cuda
master          'cpu'   [8,24)    llama_cpp   cpu     ← 同机第二段（本票目标）
android-542cd254 ''     [24,28)   llama_cpp   cpu
TABLET-2TLUCNNU8 ''     [28,32)   llama_cpp   cpu
```

端到端一次请求 **21.28 s**，`layer_segments = [0,8) [8,24) [24,28) [28,32)`
（连续覆盖 32 层），`distributed_used=true fallback=false`。
同一请求两次运行的 token 序列**逐位相同**。

### 2.2 六条判据

| 判据 | 内容 | 结果 |
| --- | --- | --- |
| 1 并存 | plan 里**同时**出现 `('master','',0,8)` 与 `('master','cpu',8,24)` | ✅ 上表 |
| 2 不越界 | CPU 段区间落在工件实际覆盖范围内（`QLH_LOCAL_CPU_EXECUTOR_LAYER_RANGE=8,24`） | ✅ `[8,24)` 恰为 `mid8-24.gguf` 覆盖范围 |
| 3 容量无重复计数 | 同机两段申报之和 ≤ 共享域总账，超额 fail closed | ✅ `capacity_domain_id` 按 `node_id` 记账，`domains` 超额 0 |
| 4 数值门 | CPU 段（Q4_K_M）与同层段（PyTorch fp16）逐元素比对 | ✅ **argmax 81/81 一致**（短 prompt 12/12、长 prompt 69/69），cosine 0.994、相对 L2 11.0% |
| 5 计时门 | 本机 CPU 段 ms/层 | ✅ **6.84 ms/层**（i9-13900H，`n_threads=8`）；对照 rog 8.7 / android 20.1 |
| 6 不回归 | `QLH_LOCAL_CPU_EXECUTOR` 缺省关闭时行为逐字节一致 | ✅ 关闭时无任何 CPU 段事件，供给输入恰好两个执行器 |

**判据 4 为什么不用端到端 token 对比**：关掉 CPU 段会连带改变层段划分与供给拓扑，
那样量到的差异无法归因到"执行器"这一个变量。改用
[`scripts/probe_local_cpu_segment_numerics.py`](../scripts/probe_local_cpu_segment_numerics.py)：
固定同一份真实 hidden，只换执行器（PyTorch `[8,24)` vs llama.cpp `mid8-24.gguf`），
逐元素报 max_abs / cosine / rel_l2 / argmax。

**为什么"逐位一致"在这里不适用**：CPU 段工件是 Q4_K_M 量化的 GGUF，基线是 fp16
safetensors，两者不可能逐位相同。决定生成 token 的量是 argmax，那一项 100% 命中。

### 2.3 原判据 5（"与关掉 CPU 段的三机基线 token 逐位一致"）的处置

原判据要求 `balanced` 模式下让 master 独自承担那 16 层（`[0,24)`，约 13.8 GB 主机内存），
与四段方案对比 token。**该路径实测 221 s 到 `ready`**，且与 legacy 分层的交互需复核；
更重要的是它混淆了"执行器差异"与"拓扑差异"两个变量。故判据 4 改由离线数值门承担，
端到端 token 对比保留为**后续可选项**而非准入条件。

## 3. 根因链（这一票真正花了时间的地方）

**所有故障几乎都是同一个模式**：某个位置把 `node_id` 当作唯一身份，或把"一次性副作用"
当作"稳定的声明值"，或把"远端 worker 才有的事实"套到本机执行器身上。累计清掉 **21 处**。

### 3.1 第一批：`node_id` 被当作唯一身份（6 处，2026-10-25）

| # | 位置 | 症状 |
| --- | --- | --- |
| 1 | `capacity._normalize_nodes` 唯一性判据 | `node_id must be non-empty and unique` |
| 2 | `ExecutionPlan` / `validate_pipeline_nodes` | 同机两段撞 `execution_requires_two_nodes` |
| 3 | `SupplyCapacityEvidence.project()` 的 `by_id` | 主段被 CPU 段覆盖 ⇒ 主记录消失、CPU 段拿到主段切点 |
| 4 | `model_supply` 的 `capacity_by_id` | 供给 plan 里 master 被标成 `executor_id='cpu'` |
| 5 | `capacity_domains()` 用 `capacity_bytes` | **VRAM 与 RAM 被合并记账** ⇒ 假超额 |
| 6 | `_normalize_nodes` 的排序 | CPU 段（middle）排在 head 前 ⇒ DFS 单向不回头 ⇒ **结构性跳过** |

### 3.2 第二批：`node_id` 串味的其余 15 处（2026-10-26）

按"哪里把 `node_id` 当身份"归类：

| 类别 | 位置 | 症状 |
| --- | --- | --- |
| 供给唯一性 | `_get_pipeline_capacity_nodes` 的键 | `Supply nodes must have unique nonempty identities` |
| 候选区间规则 | "master 必须从 0 开始" | 约束到了 CPU 段 ⇒ 与 `[8,24)` 冲突 |
| 容量输入继承 | `runtime_host_ranges` | CPU 段继承了主段的 host 预算 |
| 区间边界丢失 | `layer_budget` 被 pop | 丢掉 `min_layer`/`max_layer` ⇒ 复现越界 |
| 整模视图缺层 | descriptor 24 层零字节 | `pipeline_capacity_descriptor_invalid`（见 3.3） |
| 布局契约 | `PipelineNode(...)` 未传 `executor_id` | `pipeline node_id values must be unique` |
| 身份块硬取 | `worker_prepare_identity` | 本机执行器只有 `identity` ⇒ `KeyError` |
| prepare/commit 回执 | 本机执行器被要求 ACK | `worker_native_prepare_required` |
| stage 帧大小 | TCP 帧约束套到本机 | `route_a_stage_frame_too_large`（本机无网络帧） |
| cleanup | 硬要求 `_worker_runtime_active` | `execution_kv_cleanup_runtime_missing` ⇒ 整个部署被隔离 |
| 模型选择 | 落回 `get_selected_model()` | `supplied_layer_range_mismatch`（拿到全局主模型） |
| incarnation 栅栏 | `current(plan)` 比对本地段 | `execution_deployment_fenced`（本地段无 TCP worker） |
| 生命周期快照 | 未输出 `local_executors` | `execution_segment_coverage_invalid` |
| 预算口径（两份实现） | `worker_prepare_coordinator` + `require_runtime_receipt` | `materialization_budget_exceeded`（GGUF 段带全词表） |
| 就绪视图索引 | `scheduler_pipeline` 按 `node_id` 取 ack | 同机 CPU 段状态显示不出（仅视图，未修） |

**规律**：`_worker_runtime_active` / `worker_prepare_identity` / `node_incarnation` /
帧预算 / prepare-ack 这一族都是**"远端 worker 才有的属性"**；凡按 `node_id` 单独应用的地方，
本机执行器必炸。找到的每一处都已分支到 `executor_id` 或跳过 `local_node_id`。

**仍未修的两处**（本票范围外，登记在案）：
- `pipeline_reshard.py:446` —— `len({node_id}) < 2` 但意图是数 records；
  同机两段在只剩本机时会算成 1 个 ⇒ 误判"幸存者不足"。
- `pipeline_reshard.py:444` —— 按 `node_id` 剔除 `failed`；主执行器故障会连带剔除同机 CPU 段。
- `scheduler_pipeline.py:7321-7322` —— 就绪视图按 `node_id` 取 `expected_configs`/`ack`；
  本机执行器不走 prepare/commit 状态机 ⇒ 状态显示不出（仅视图，不影响执行）。

### 3.3 其中两处最不直观

- **VRAM 与 RAM 不能相加**：`capacity_bytes` 对 CUDA 节点是 **VRAM**
  （`capacity_source="gpu.vram_free_gb"`），对 CPU 执行器是 **RAM**。直接相加会把两种
  独立资源混成一份总账。共享**内存**域必须按 `host_capacity_bytes` /
  `domain_allocatable_bytes` 记账。
- **排序决定 DFS 遍历次序**：DFS 是**单向**的（`cursor` 只前进、不回头）⇒ 段类型必须与
  层顺序一致。次序为 `head(0) → 未声明(0.5) → middle(1) → tail(2)`。
  **"未声明"要早排而不是晚排** —— 它最灵活，早安排不会被挤掉；晚排会被有约束的
  `tail` 占满位置 ⇒ 无解（这是第一版假设的错误，被
  `test_per_artifact_modes_select_the_matching_range_and_identity` 直接打掉）。

**分摊必须幂等**：不能在 `host_capacity_bytes` 上原地做减法（
`_get_pipeline_capacity_nodes` 会被多次调用、每次重建 records，扣除只对那一次生效），
也不能扣那个字段（它承载 `safetensors_layer_offload` 的 host 预算）。正确做法是
**从声明值重新推导**（`domain_allocatable_bytes`）。

### 3.4 CPU 段的工件边界与切分粒度（2026-10-26 的两个关键修正）

- **`local_cut` 只解锁切分粒度，不解锁工件边界**。本机 CPU 段手上只有**裁好的部分
  工件**，不能自裁到任意区间 ⇒ 用 `layer_budget.min_layer/max_layer` 钉住可切范围。
  缺了这两项，求解器会把工件覆盖不到的层派给它，而失败发生在**执行期**
  （层号越界/权重缺失）—— 真机实测踩到过：capacity plan 给 `('master','cpu',0,8)`，
  工件却是 `mid8-24`。
- **切点必须换算到组空间**。`assignment.start_layer/end_layer` 是**层索引**
  （master 段 `[0,8)`、CPU 段 `[8,24)`），而 `candidate_layer_ranges` 的契约是
  **对齐组**索引（`start // alignment`，求解器工作空间是 `32 ÷ 4 = 8` 组）。
  此前把层索引直接抄进候选 ⇒ `[[0,8]]` 被理解成"组 0..8" = "层 0..32" ⇒ prepare
  按错误的候选重新切段 ⇒ 与已裁好的段对不上。

## 5. 相关配置（本机侧，已就绪）

```
QLH_CAPACITY_PLANNING_MODE=fastest
QLH_LOCAL_CPU_EXECUTOR=1
QLH_LOCAL_CPU_EXECUTOR_LAYER_RANGE=8,24
QLH_LOCAL_CPU_EXECUTOR_HOST_FRACTION=0.7
QLH_LAYER_GGUF=models/q35-9b-local-artifacts/q35-9b-local-mid8-24.gguf
QLH_KEEP_HEAD_SHIM=build/keephead/build-cpu/bin/qlh_keep_head.dll
QLH_LAYER_THREADS=8
QLH_LAYER_N_BATCH=4096
QLH_LAYER_N_CTX=8192
QLH_PIPELINE_MODEL_SYNC_TIMEOUT=600
QLH_LAYER_COST_MS=master=12.6,rog-5060=8.7,android-542cd254=20.1
```

**`QLH_LAYER_N_BATCH` 必须 ≥ prefill token 数**：默认 2048 小于本模型一次 prefill 的
2644 个 token ⇒ `GGML_ASSERT(n_tokens_all <= n_batch)` ⇒ worker init 后立刻退出，
master 侧只看到 `keep-head worker exited before response`。同一条坑在
`llama_engine.py` 的注释里已记录过。

**默认关闭**：`QLH_LOCAL_CPU_EXECUTOR` 缺省为 0 ⇒ 既有三机拓扑逐位不变。
这一档改变的是"哪些层由哪台机器算"，属于部署决策，不该因一次升级就悄悄生效。

**工件**：`q35-9b-local-mid8-24.gguf`（`[8,24)`，3.23 GB，`blk.8..blk.23`，215 张量），
由 `scripts/cut_layers.py --k 8 --end 24` 从整模裁出；`head4` / `mid4-24` / `tail24-32`
为既有工件。**注意每个 GGUF 段都自带全词表**（`token_embd` 4096×248320 Q4_K ≈555 MB +
`output` Q6_K ≈820 MB ≈ 1.35 GB），与段覆盖多少层无关 —— 这是预算口径必须按
"物理实际大小"而非"层宽估算"计的原因。
