# v2.2 补丁独立性与每周上游同步

> 面向长期维护 · 基于 4 个提交的文件重叠矩阵与上游冲突面统计 · 产出每周 rebase 的可执行方案

---

## 0. 一句话

**4 个提交彼此独立，可以单独 apply / revert**：`wbuf`（1 文件）与 `vulkan`（4 文件）与其它提交零重叠，`split`（50 文件）与 `pin`（4 文件）只共享 `src/llama-context.cpp` 一个文件（4 行调用点）。**每周同步上游的主要成本在 `split` 提交**——我们改的 58 个文件里 21 个上游也在改，其中 50 文件里有相当部分落在这 21 个里；另外 37 个是我们独有的，rebase 不会碰。

## 1. 四个提交的独立性

| 提交 | 文件数 | 与其它提交的重叠 |
|---|---:|---|
| `73edc41e6` llama : weight buffer placement policy | **1**（`src/qlh-weight-buft.h`，纯新增） | **0** |
| `0f14ec06c` server : split a model by layer range | **50**（+19611 −248） | 与 `pin` 共享 `src/llama-context.cpp` |
| `675b0e30f` vulkan : Intel iGPU fixes | **4**（+210 −88） | **0** |
| `1c7f7967c` llama : pin host expert pages | **4**（+195 −1） | 与 `split` 共享 `src/llama-context.cpp` |

**逐条判定**：

- **`wbuf` 完全独立**：只新增一个头文件，没有任何 include 之外的影响面。可以单独 `git revert`，也可以单独 cherry-pick 到任何分支。
- **`vulkan` 完全独立**：4 个文件全在 `ggml/src/ggml-vulkan/` 下，与我们的 split 代码零交集。可以单独 revert，且**可以单独提交给上游**（它修的是上游的 Intel 问题，不是 fork 特有的）。
- **`split` 是主体**：50 文件 +19611，包含 `tools/split-stage/main.cpp`（+2890 纯新增）、`src/llama-split-remote.cpp`（+1125 纯新增）、协议头、server 接线、qwen35 模型改动。它**不依赖**另外三个提交。
- **`pin` 逻辑独立但共享一个文件**：`llama-moe-cache.cpp` 是上游 `951d465f5` 建的（split 提交没碰它），所以 pin 不依赖 split 的 moe-cache 改动；它与 split 的唯一交集是 `src/llama-context.cpp` 里的 4 行（`sched_reserve()` 之后调 `moe_cache->pin()`）。单独 revert pin 只会在这 4 行附近产生冲突，不会波及 split。

**「干净」的判定**：4 个提交都是单一逻辑单元——没有「顺手改的无关文件」，没有「为了能编译而夹带的临时改动」。`split` 里包含 `src/models/qwen35.cpp`/`qwen35moe.cpp` 的 `t_layer_inp` 槽位，这是 split 的必需依赖（不是夹带），在提交信息里写明了。

## 2. 每周同步上游的成本在哪

**上游 2 天（`09338b85e` → `a956a852c`）改了 245 个文件、66 个提交**——按这个速率，每周约 **230 个提交**。

**我们改的 58 个文件里**：

| 类别 | 文件数 | rebase 影响 |
|---|---:|---|
| **冲突面**（上游也改） | **21** | 每次 rebase 都可能要手工合并 |
| **独有**（上游没碰） | **37** | 直接应用，零冲突 |

**21 个冲突面文件**：

```
common/arg.cpp              common/common.h
common/speculative.cpp      common/speculative.h
ggml/src/ggml-cuda/ggml-cuda.cu
ggml/src/ggml-vulkan/ggml-vulkan-types.h
ggml/src/ggml-vulkan/ggml-vulkan.cpp
include/llama.h             src/llama-context.cpp
src/llama-context.h         src/llama-cparams.h
src/llama-ext.h             src/llama-graph.cpp
src/llama-model.cpp         src/llama-moe-cache.cpp
src/llama-moe-cache.h       src/llama.cpp
src/models/dflash.cpp       src/models/qwen35.cpp
tools/server/server-context.cpp   tools/server/server.cpp
```

**其中最难的三处**（按历史冲突经验）：

1. **`src/llama-context.cpp`**（我们 +2099）——上游每周都在改这个文件（图构建、调度、内存），且我们的 split 逻辑深度嵌入。这是 rebase 的主要工作量。
2. **`common/speculative.cpp`**（我们 +1240）——上游 `32bdc3a89` 刚做过 DFlash 重构，后续还会动；我们的 chain 逻辑挂在它的基类上。
3. **`tools/server/server-context.cpp`**（我们 +1553）——上游 server 迭代频繁。

**相对安全的**：`tools/split-stage/main.cpp`（+3202 纯新增，上游没有这个目录）、`src/llama-split-remote.cpp`（+1356 纯新增）、`src/llama-split-proto.h`（+912 纯新增）、`src/slim-arc-*.cpp`（4 文件，上游没有）。

## 3. 每周同步的可执行方案

### 3.1 推荐流程（保持 4 提交）

```bash
# 1. 拉上游
git fetch upstream
OLD=$(git merge-base HEAD upstream/master)

# 2. rebase 到新上游（4 个提交依次重放）
git rebase --onto upstream/master $OLD rebase/onto-<date>

# 3. 冲突集中在 split（21 文件里的多数）
#    wbuf / vulkan / pin 三个小提交通常零冲突
```

**为什么保持 4 个提交而不是 squash**：
- `wbuf`/`vulkan`/`pin` 各自独立，冲突时只需处理它们自己的文件，不会和 split 混在一起；
- 单独 revert 任一个都不影响另外三个（`pin` 的冲突面只有 `llama-context.cpp` 4 行）；
- `vulkan` 甚至可以直接抽出来提上游。

**代价**：`split` 那 50 文件的提交在每次 rebase 时都要重放一次，冲突集中在那里。如果哪天 `split` 的冲突量变得不可控，可以考虑把它拆成「协议层 / 传输层 / 模型接线」三个提交——但**现在不建议**，因为它是一个连贯的功能单元，拆开会失去「一次 rebase 解决一个整体」的便利。

### 3.2 kvmem 的位置

`kvmem/integration` = `3f930466d`（**WIP，提交信息自述「本地双段链构造成功但语义不达标」**），基于 v2.1 的 base（`09338b85e`）+ 6 个提交（v2.1 的 5 个 + kvmem 1 个），91 文件 +21611 −376。

**它不在 v2.2 里**——v2.2 的 diff 没有任何 kvmem 文件。所以 kvmem 目前是「v2.1 之上的一条 WIP 支线」。

**要把它纳入每周同步，需要两步**：

1. **先完成语义**（WIP 状态不达标，不能作为可选补丁发布）；
2. **再 rebase 到 v2.2 之上**——它和 split 共享大量文件（`llama-context.cpp`、`speculative.cpp`、`server-context.cpp`、`llama.h`），冲突面比 v2.2 对上游的 21 文件更大。

**建议**：kvmem 完成前不要并行同步——否则每周要 rebase 两条线，且两条线在 `llama-context.cpp` 上互相冲突。

### 3.3 slim-arc 的可选性

v2.2 里 slim-arc 还在（4 文件：`slim-arc-page-range.cpp/.h`、`slim-arc-prefetch.cpp/.h`），通过**运行时 env** 开关：

```
SLIM_ARC_PREFETCH=1      # 总开关（默认关）
SLIM_ARC_BUDGET_MB=N     # 预算
SLIM_ARC_MAX_CALLS=N     # 调用上限
SLIM_ARC_NOOP=1          # 只记录不动作
```

**它不占 rebase 冲突面**——4 个文件都是我们独有的（上游没有 `slim-arc-*`），且没有 CMake 条件编译（始终编译进 `llama`，但默认不运行）。

**所以 slim-arc 已经是「可选补丁」**：不需要单独分支，靠 env 开关即可。v2.2 删掉的那 3 个 orphan 单元（`slim-arc-expert-{reclaim,residency,transition}`）本来就是不可达代码，删了不影响开关语义。

## 4. 结论

| 问题 | 答案 |
|---|---|
| 4 个提交各自独立吗 | **是**。`wbuf`/`vulkan` 零重叠，`split`/`pin` 只共享 `llama-context.cpp` 4 行 |
| 干净吗 | **是**。四个都是单一逻辑单元，无夹带；`split` 里的模型改动是必需依赖 |
| 能单独 revert 吗 | `wbuf`/`vulkan` 可以直接 revert；`pin` 会碰 `llama-context.cpp` 4 行；`split` 是主体，revert 等于回退功能 |
| 每周同步可行吗 | **可行**，成本在 `split`（21 个冲突面文件里的多数）。`wbuf`/`vulkan`/`pin` 通常零冲突 |
| kvmem 怎么办 | 先完成语义，再 rebase 到 v2.2；完成前不要并行同步两条线 |
| slim-arc 怎么办 | 已经是 env 开关（默认关），4 个文件全独有，不占冲突面 |

**一个可选的改进**（不影响当前结构）：把 `vulkan` 提交单独提给上游——它修的是上游的 Intel iGPU 问题（`ggml_vk_should_use_mmvq` 的 Q2/Q3 例外、单堆 UMA 判定），与 fork 无关。提上去之后，每周 rebase 就少一个提交。
