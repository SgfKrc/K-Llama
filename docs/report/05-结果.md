## 0. 读法：先看口径，再看数字

同一段代码在不同测法下能差一个数量级：stage0 同进程直连 3.6 ms、两段链路每步只量整链 105.9 ms，
代码路径完全一样（`MEASUREMENT-PITFALLS.md` §1）。所以本章每条都写全七件事——**模型、量化、设备、
切点、采样、样本数、日期**——缺一项的数只当参考，不当结论。跨表比较一律禁止；同一表内也只比同口径的行。

## 1. 分段 vs 整模的吞吐

### 1.1 唯一一处同口径 A/B（2B，本机，纯 CPU）

| 配置 | 整模 | 双段链 | 链 / 整模 |
| --- | ---: | ---: | ---: |
| MTP k=2，`-np 1`，ms/token | **22.56** | **28.33** | **1.26×（链慢 26%）** |

口径：`qwen35-2b-Q4_K_M`（24 层），head `0:20` + tail `20:24`，本机双进程，纯 CPU `build-split`，贪心，
`n_predict 192`，三次取中位；出处 `SPECULATION-DATA.md` §1.3。

**本机双进程测不出投机收益**：没有 25–30 ms 跨机往返可省，两个进程还抢同一套 CPU 与内存带宽——这一行
只说明「同机拆开更慢」，不能外推（`SPLIT-MEASUREMENTS.md` §0）。

### 1.2 整模与边缘设备的绝对吞吐（跨行不可比）

| 形态 | 吞吐 | 口径 |
| --- | ---: | --- |
| 35B 整模，纯 CPU，MTP k=2 | **10.54** gen tok/s | 官方 `UD-Q4_K_M`，`-c 4096 -b 512 -t 8 -ngl 0`，3 prompt 均值，**有背景负载**；`MODEL-SWAP.md` §11.2 |
| 35B 链，head 本机 + tail Y700（安卓 Termux） | 6.34 / 6.79 / 8.50 tok/s | 官方整模，`32:40` 8 层驻留约 4.90 GiB，`-t 8`、`ngl 0`；`CROSS-MACHINE.md` §6.2 |
| 2B 链，head 本机 + tail Y700 | **15.76** tok/s | `qwen35-2b-Q4_K_M`，`0:12` / `12:24`，64-token 生成；`CROSS-MACHINE.md` §6.1 |
| 35B **三段**链，head 本机 `0:20` + Surface relay `20:28` + Y700 tail `28:40` | **6.53 / 6.94** tok/s（两次） | 1522 token prompt、64 token 生成；同 prompt 两段是 7.42 / 8.71，**三段慢 12–25%**（hidden 过网 4 次 vs 2 次）；`CROSS-MACHINE.md` §7 |

远程链（ROG，LAN）与弱机（Surface）的绝对吞吐在 §3 的表里，那里同时给了投机对照。35B 的 10.54 与 §3 的
8.18–9.73 **不能相减**：一个是官方权重、一个是旧蒸馏版，一个整模、一个两段链，采样 prompt 也不同
（`MODEL-SWAP.md` §11.7）。

## 2. 投机接受率

### 2.1 同一套 prompt 上的链上折扣（35B 官方，`n_predict 64`，3 prompt，本地双段）

| 配置 | accept（a/g） | mean len | 相对整模 |
| --- | ---: | ---: | --- |
| 整模 MTP k=2 | **0.9098**（121/133） | 2.81 | — |
| 链上 MTP，旧路径（每轮清草稿 KV） | 0.68790（108/157） | 2.37 | −24% |
| 链上 MTP，keep-KV（2026-11-10 起默认） | **0.78767**（115/146） | — | −13% |
| 链上 MTP，keep-KV + catch-up mode 1（仅 prefill） | 0.8551（118/138） | — | −6% |
| 链上 MTP，keep-KV + catch-up mode 2（每批） | **0.9098**（121/133） | — | **= 整模，逐位相同** |

出处：`MODEL-SWAP.md` §11.4；三次独立重跑逐位相同，mode 2 与整模连每条 prompt 的 accepted/generated
都一样。512 档的整模上限是 0.7557，mode 2 也是 0.7557——**512 档的 0.7557 是模型的真实上限，不是链的**
（`MODEL-SWAP.md` §11.4）。

### 2.2 跨机：接受率零损失，但吞吐要看 prompt 长度

接受率（prompt 1102 token，k=2，Tailscale → Surface）：

| 草稿源 | 链上 accept（a/g） | 与整模逐 prompt |
| --- | ---: | --- |
| DFlash k=2 | **117/141 = 0.82979** | **相同** |
| DSpark k=2 | **117/140 = 0.83571** | **相同** |
| MTP k=2（对照） | 108/157 = 0.68790 | 对照（与 §2.1 旧路径同一批数据） |

口径：官方 `UD-Q4_K_M`（`22,663,387,424 B`），head 本机 `0:32`、tail Surface `32:40`，贪心，三个 prompt
各跑一遍，输出 **3/3 逐字节相同**（250 / 244 / 249 字符）；`CROSS-MACHINE.md` §3.1。这是本项目第一次在
**真跨机**链上拿到「与整模逐 prompt 相同」的接受率。

**接受率零损失，带宽代价要另算。** 远程链上开了投机就走 whole-logits（248320 × 4 B ≈ **993 KB/轮**），
不投机是 top-20 候选（**48 B/轮**）——因为投机每步要采样多行，候选通道只描述单行
（`plan_remote_candidates()` 把 `spec != nullptr` 判成不能用 top-k）。

所以净收益取决于接受率能不能赚回这份带宽。实测（本机 head `0:32` + Y700 tail `32:40`，**1522 token**
prompt，64 token，T=0，两轮）：

| 配置 | 第 1 轮 tok/s | 第 2 轮 tok/s | accept（两轮逐位相同） | mean len |
| --- | ---: | ---: | ---: | ---: |
| 不投机 | 7.42 | 8.71 | — | — |
| DFlash k=2 | 7.41 | 8.29 | 0.69231（36/52） | 2.38 |
| **DSpark k=2** | **8.70** | **9.79** | 0.74000（37/50） | 2.48 |

DSpark **+12.4% ~ +17.2%**、DFlash 持平到 −4.8%。差别有机制解释：DFlash 的 8 个 extract layer 里 **2 个
在 head**、DSpark 的 5 个里只有 **1 个**，tap 过网更少。**短 prompt 上不划算**：draft ctx 的固定建仓约
2.1 s，摊在 64 token 上就是 −25%。机制与完整数据见 `SPECULATION-DATA.md` §4。

### 2.3 整模上的选型基线（`n_predict 64`，k=2，3 prompt）

| 草稿源 | accept | mean len |
| --- | ---: | ---: |
| MTP | **0.9098** | 2.820 |
| DSpark-6L | 0.8357 | 2.671 |
| DFlash（6 层） | 0.8298 | 2.660 |
| DSpark-5L | 0.7986 | 2.597 |

出处：`SPECULATION-DATA.md` §3.1。**DSpark-6L 的 base 是 NVFP4 而非官方 BF16**，所以「6L 比 DFlash 高」
这一格不能排除混杂；比较只在「这份文件 vs 那份文件」这一层成立。

同一个 `--spec-type draft-mtp` 在整模与链上是**两套路径**。整模上 draft context 建在同一模型上、走上游
非 chain 分支、catch-up decode 正常；链上 `is_chain` / `is_remote` 把 catch-up 关掉、`draft()` 每轮清
草稿 KV，两处都是本仓加的（`MODEL-SWAP.md` §11.4）。所以「整模上 MTP 好用」推不出「链上 MTP 一样
好用」；DFlash / DSpark 走 `layer_inp` tap 通道，才有跨机零损失。

## 3. 跨机三形态

| 形态 | 不投机 | 投机 k=2 | 相对 | 口径 |
| --- | ---: | ---: | ---: | --- |
| ROG（LAN，强 head） | 8.18 / 8.74 / 9.47 / 7.51 / 9.73 | 8.47 / 9.47 / 9.36 / 7.62 / 10.75 | **中位 +6%**（+8.4% ~ −1.2%） | 旧蒸馏版，五类 prompt（散文 / 代码 / JSON / agent / 人为重复），32-token 生成；`CROSS-MACHINE.md` §1 |
| Surface（4C8T，弱机） | 8.65 | 5.21 | **−40%** | 旧蒸馏版，散文；`CROSS-MACHINE.md` §2 |
| 本机回环，带 grammar | 20.82 | 13.95 | **0.67×** | `toolcall.gbnf`，每帧两次 hop；`CROSS-MACHINE.md` §2 |

**收益排序是条件句**：LAN + 强 head + 接受率高的负载才为正；弱机器、回环、严格 grammar 都翻号。四个
原因：

1. 每帧两次 hop；
2. MTP draft 不看 grammar / rbudget（接受率 2.76 → 1.46–1.73 token/帧）；
3. 回退率 9–19%（`toolcall.gbnf` 实测 11/16 帧被拒，每次回退 ≈ 一整个普通 round）；
4. 回环上 993 KB 只要约 1 ms，省带宽这个唯一好处不存在（`CROSS-MACHINE.md` §2）。

安卓（Y700 / Termux / arm64）是第三种形态：**§1.2 那三次吞吐不是单调关系**。拆解：26 token 那一发是同一
进程的第二个请求（`graphs reused = 118`，图已建），prompt eval 1905.98 ms / 24 token，而第一个请求是
3605.68 ms / 27 token——**冷启动的图构建摊在第一个请求里**，拿它当基线会低估。

所以这三次不能当「生成越短越快」的曲线读；要曲线得同时段交替跑、丢掉每个进程的第一个请求
（`CROSS-MACHINE.md` §6.2）。安卓尾段驻留约 **4.90 GiB**（= 4.022 + 0.493 + 0.389），是把 21.11 GiB
整模拆到平板上的直接证据（同节）。

## 4. 内存：按实际输出行数分配

| 项 | 修前 | 修后 | 口径 |
| --- | ---: | ---: | --- |
| tail 的 logits 缓冲 | **1710.76 MiB** | **3.79 MiB** | 同一个 1806-token ubatch，2B 链，`-c 8192 -np 4 -b 2048` |
| 同一 ubatch 的 prefill | 172.61 t/s（10485.85 ms） | **219.39 t/s**（8250.22 ms） | 同上，1810 含采样行 |
| 远程 `20:24` 段的 pp 图缓冲 | **2052.10 MiB** | **240.09 MiB** | 2B，`-c 4096 -b 2048`，`n_seq_max=1`，词表 248320 |
| head 的 hidden 缓冲 | 14.11 MiB | 14.11 MiB（不变） | `logits=no, embd=yes` |
| 本地链上下文 checkpoint | — | 19.266 MiB | @1806 token（`checkpoint 1 of 32`） |
| 远程段 state blob | — | 2B 的 8 层段 **6.42 MiB**；35B 的 8 层段 **12.56 MiB** | 2B 是 6,733,996 B、与历史长度无关；35B 是 13,172,908 B。**blob 留在 stage 内，v6 起过网 8 字节 handle**（`06-局限与结论.md` §1.9） |

出处：`SPLIT-MEASUREMENTS.md` §1、§5，`SEGMENTED-LIMITS.md` §2.5。机理：修前 tail 按 `n_batch` 行分配
logits，修后只为「实际要被读的行」分配（`n_seq_max × (1+n_max)`）——省的不只是内存，同一 ubatch 的 prefill
顺带快 27%，因为不再申请 / 清零那 1.7 GiB。

## 5. 段级 offload 与 MoE 缓存

| 配置 | 指标 | 结果 | 口径 |
| --- | --- | ---: | --- |
| tail `32:40` 纯 CPU → `-ngl all` | 段内 pp / tg | 64.4 → **1018.5** t/s；35.7 → **1754.2** t/s | 4.2 GiB 权重全进显存，段级 probe，`-c 512`；`SEGMENT-OFFLOAD.md` §3 |
| head `0:32`，`-ngl 8`，`op_offload` 开 → `--no-op-offload` | tg | 12.47（相对纯 CPU 16.37 是 −24%）→ **21.00（+28%）** | 官方 35B，CUDA 构建，`-c 1024`；`SEGMENT-OFFLOAD.md` §4 |
| MoE：`-ncmoe` + `--moe-cache-mib` 0 → 1024 | tg | 18.05 → **31.99**（相对 cache 0 是 +77%；相对纯 CPU 16.37 是 **+95%**） | head `-ngl 32 --n-cpu-moe 32 --no-op-offload`，`-c 1024 -b 256 --pp 128 -n 24`；`SEGMENT-OFFLOAD.md` §5.1 |
| 同上，命中率 | 专家缓存命中 | **82.2%**（1024 MiB；2048 MiB 是 84.6%、tg 32.57） | 同上；纯 CPU 对照 16.37 |
| 部署形态（head 独占本机、tail 在另一台） | tg | `-ngl 8` **+19.6%**（另一轮 +34%）；`-ncmoe` + cache 1024 **+40.9%** | probe，pp 55 / n 64；`SEGMENT-OFFLOAD.md` §7.2 |

两条读法：**`-ngl N` 数的是「本段最后 N 块」**，不是整模层号（tail `32:40` 含 NextN 是 9 块，整段上卡要
`-ngl 9` 或 `all`）；**同机构造测不出 head offload 的收益，方向甚至会反**（`-ngl 8` 的 plain 图帧 80.30 vs
76.01 ms，慢 5.6%）——head offload 的判据只能用部署形态（`SEGMENTED-LIMITS.md` §2.10）。

## 6. prefill 的 tap 代价

| 配置 | prefill（1102 token） | 相对 MTP |
| --- | ---: | ---: |
| A DFlash k=2 | 32784 / 31506 ms → **~32.1 s** | +2.4 s |
| B DSpark k=2 | 32840 ms → **~32.8 s** | +3.1 s |
| C MTP k=2（对照） | 27499 / 28212 / 29698 / 30783 ms → **~29.7 s** | — |

**A − C ≈ +2.4 s，与「25 MB ÷ 9.5 MB/s ≈ 2.6 s」吻合**（prefill 每个 512 行 ubatch 是 8 MB，1102 token
约 3 个 ubatch 即 24 MB）。这证明 tap 是**成批**走的：若逐 token 往返，1102 个 token 会报出数量级更大的差
（`CROSS-MACHINE.md` §3.2、`PROTOCOL-V9.md` §3.3）。

回环对照：1192 token 差 **0.2%**；跨机 1102 token 差 **~2.4 s（7–8%）**。数千 token 的 prompt 会到
10 s 级（`CROSS-MACHINE.md` §3.3）。

## 7. 测量纪律：三种比法是错的

1. **accept 率跨 `n_predict` 比较会翻号。** 同一对草稿源（DSpark-6L vs DFlash）在 `n=64` 时差 **+0.59 点**、
   在 `n=256` 时差 **−0.94 点**。报 accept 必须带 `n_predict` 与 k，否则同一个结论可以有两个符号
   （`SPECULATION-DATA.md` §3.3）。
2. **`mean_len` 跨 k 比较没有意义。** `mean_len = 1 + accept × k`，k 不同就不是同一个量；`mean_len` 只能
   在同一 k 下比接受率（`README.md` 口径坑）。
3. **估算不能当结论。** 两个历史案例：
   - 核显 prefill 曾记 **3.1×**，同构建 CPU 基线复测是 **1.90×**——缩水的主因是 v2 的 CPU 基线用错了
     构建，不是核显变差（`IGPU-SLOWDOWN.md` §①、`BUILD.md`）；
   - catch-up 成本曾按 248k output head 估成 **30–60 s / 2000 行**（那一版估算见提交 `4092bce4` 的提交
     信息），实测每行 **1.19 ms**、2000 行 ≈ **2.4 s**，高估 10–40 倍（`MODEL-SWAP.md` §11.4）。

另有两条同源的口径坑：基座不是同一个 BF16 时只能说「这份文件比那份文件高」；`-np > 1` 下 MTP 变慢
（整模 22.56 → 28.37 ms/token）的机理仍未定论，别当成排队（`SPECULATION-DATA.md` §1.3、§3.3）。

## 8. 本章的边界

- **没有跨模型的吞吐对照**：v2 的吞吐数据（`MEASUREMENTS.md`）属于 Python 驱动链，已退场；与 v2.1 的数字
  不可混用（`README.md` 分工段）。
- **没有 35B 本地双段链的 gen tok/s 同口径对照**：§2.1 只有接受率；§3 表里的 8.18–9.73 是旧蒸馏版远程链。
- **安卓的 6.34 / 6.79 / 8.50 不是曲线**：三次的进程状态不同（§3），要曲线得重测。
