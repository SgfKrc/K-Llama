## 0. 形状：一条链是什么

```
llama-server  ← 链首，加载源模型 [0, N)，持有 token、采样、slot、HTTP 面
   │  hidden（n_embd × f32）
   ├─ split-stage --role relay  [N, M)       ← 可以有多段
   │  hidden
   └─ split-stage --role tail   [M, 40]      ← 出 logits
```

四句话说完：

1. **每个节点持有同一份整模**，加载时只创建、只读取属于自己那几层的张量，没有「切模型」这个动作，
   也没有「层段工件」这类中间产物（`ARCHITECTURE.md` §0）。
2. **段间只传一个 `n_embd` 宽的 float32 向量**：2048 × 4 B = **8 KB**（`ARCHITECTURE.md` §4）。
3. **链的驱动者是 `llama_context`**，`llama-server` 自己走链；客户端不需要知道段在哪台机器上
   （`README.md` 开头）。
4. **控制面只做三件事**：读拓扑、起停进程、探活（`DEPLOYMENT.md` §7）。

下面七个决策是这套形状的全部承重墙，每个都写了代价——代价是选它的理由的另一面。

## 1. 决策一：链下沉进 `llama_context`，而不是继续用 Python 驱动链

**选了什么**：v2 的 Python 驱动链（`chain_client.py` / `stage_worker.py` / `shim/`）整体退场，
把接力下沉到 `llama_context` 里（`decode_split`、`ctx_tail`），`llama-server` 成为链的驱动者。

**为什么**：能力对齐。v2 里 `llama-server` 的服务面（`/completion`、`/chat/completions`）由驱动层
重新实现，slot、prompt cache、grammar、投机、多序列都要在 Python 侧再写一遍；下沉之后这些全部走
原生路径，客户端无感。三条可直接对照的：

| 能力 | 下沉后的形态 | 判据 |
| --- | --- | --- |
| prompt cache | checkpoint 覆盖全链（`state_seq_*` 走聚合视图 `get_memory()`） | 3103 token 历史第二轮只算 38 个新 token：**714 ms** vs 整段重算 **19847 ms**（`SPLIT-MEASUREMENTS.md` §1） |
| grammar / rbudget | 候选逐 token 自检、被拒整帧回退；预算耗尽只收紧不放宽 | `common_sampler_grammar_rejects()`；`PATCHES.md` 第四代 |
| 本地并发 | `-np 4` 四并发输出与串行逐字节相同 | `verify/verify.sh` 组 5；`README.md` 能力表 |

**代价**：要改上游代码，并且要维护 rebase。rebase 到 `09338b85e`（上游 193 个提交之后）时，
改动 `git apply --3way` 打在 12 个文件 / 29 个块上冲突，全部落在上游重构过的 `llama-context.cpp`、
`llama-graph.cpp`、`server-context.cpp`（`PATCHES.md`「与上游 193 个提交的重合」）。这条代价是
持续性的：上游每动一次这三个文件，本仓就要跟一次。

**一条边界**：下沉**没有**让远程链支持多序列。`llama_split_attach_remote()` 仍拒绝
`n_seq_max > 1`（`SEGMENTED-LIMITS.md` §2.4）。多序列只在单机内成立；远程链要多租户就在链首起多个
server、各走自己的链。

## 2. 决策二：不复用上游 RPC 的传输层，只复用它的服务面

**选了什么**：上游已有的服务面能复用就复用，链路本身走下沉路线。可核的是它落地后的形状（下两段与
下表）：上游的 RPC（`-DGGML_RPC=ON`）能跨机，但只被当作能力边界的参照，没有被复用为传输层。

**为什么**：两者语义不同。上游 RPC 的协议命令是 `SET_TENSOR` / `SET_TENSOR_2D` 上传张量、
`GRAPH_COMPUTE` 让远端执行子图、`GET_TENSOR` 取回结果——**它把设备虚拟化，模型仍然一份**：主机必须
装下整模，权重从主机通过网络发到远端，主机维护全局计算图，远端只执行派过去的那部分 op
（`PATCHES.md`「与原生 RPC 的分界」）。本项目要的是另一种东西：**每段自己算完一层，把隐藏态交给
下一段**，没有全局图，没有中心。两者在协议层就无法对齐：

| 维度 | 上游 RPC | 本项目 |
| --- | --- | --- |
| 权重从哪来 | 主机通过 `SET_TENSOR` 发给远端 | 各节点本地读整模的对应层 |
| 首次跨机流量 | 权重总量（GB 级） | 0 |
| 主机必须装下整模 | 是 | 否（只装自己那几层） |
| 每步流量 | 激活 + 图指令 | 8 KB hidden |
| 计算图 | 主机维护全局图 | 每段独立进程，无全局图 |
| 异构 | 需要相同 ggml backend | 自定义 TCP，可跨不同 CPU / GPU |

（表出自 `ARCHITECTURE.md` §8，与 `PATCHES.md` 同名的表一致。）

**代价**：段是黑盒，段内不能跨机器拆算子，**每一段必须能单独装下**；RPC 可以把任意 op 派到远端，
粒度更细。这条代价在部署上是硬的：35B 分两段已经贴边，切点不能随便往细里切
（`ANDROID-SURFACE-段接入评估.md` §0）。

## 3. 决策三：段间只传 `n_embd` 个 float 的 pre-norm 隐藏态

**选了什么**：载荷是链首导出的、`output_norm` **之前**的隐藏态，float32，宽度 `n_embd`（35B 上是
2048），即每 token 8 KB。

**为什么是 pre-norm**：上游的 `t_embd` 是 `build_norm` **之后**的值（pooling 要归一化后的结果）。
接力要的是原始输出——多过一次 RMSNorm，第一个 token 就分叉。

开关是 `llama_context_params::embeddings_pre_norm`，它把 tap 点前移，顺带不建 lm_head，中段因此再省
398 MiB（`ARCHITECTURE.md` §3）。

**为什么不是 logits**：logits 是词表维度，**248,320** 宽（`MOE-SPECULATION-ECONOMICS.md` §2），
比 `n_embd` 宽约 121 倍——两个数量级。一行 logits 是 993,312 B，一行 hidden 是 8 KB
（`PROTOCOL-V9.md` §2 与 §3.3 的帧大小口径）。链上每一段之间传 logits 等于把每步的流量放大两个
数量级，而 logits 只在最后一段才有意义。

**为什么选 fp32（fp16 / int16 的实测分叉）**：判据是逐位一致。2B 两段实测（5 个贪心 prompt ×
48 token）：fp16 有 1 个在第 22 步换了 token，int16 定点同样 1/5（第 16 步）——量化步长细 20 倍也
照样翻转，因为分叉点都落在输出接近平局的位置（`ARCHITECTURE.md` §4）。

**代价**：`embeddings_pre_norm` 只覆盖 `qwen35` / `qwen35moe` 两个架构（`src/models/*.cpp` 计数 **176**
个实现里的 2 个；`enum llm_arch` 条目是 173）；其他架构在建上下文前被 `split_arch_exports_pre_norm()`
拒掉，失败方式从「静默数值偏移」变成「启动即拒」。换模型要按模型补 tap 点，是机械工作但要逐个验证
`output_norm` 位置与 norm 类型。这条边界与逐架构出口的取舍详版见 [06-局限与结论](06-局限与结论.md) §1.1、§1.7。

## 4. 决策四：链首不能是 `split-stage`

**选了什么**：两段链的形态固定为 `llama-server` 加载 `0:N` + `split-stage` 加载 `N:M`。链首永远是
`llama-server`。

**为什么**：`split-stage` 自己拒绝。`--role` 只有 `relay|tail` 两个值（`tools/split-stage/main.cpp`
的 `validate_options()`：「`--role must be 'relay' or 'tail'`」），并且同一个函数要求 `layer_lo > 0`：

```
layer-lo must be > 0 (got %d): the head owns the front of the model and
runs in the driving process, a split-stage only consumes hidden rows
```

（`tools/split-stage/main.cpp`，`validate_options()`；`H:\llamacpp-c` 的 `4acf03c8b` 上逐字核对。）
理由是结构性的：**层 0 之前的东西是 token**，而 token 只在驱动进程里——`split-stage` 只消费 hidden
行，它拿不到 token id，也就无从算 embedding。

**代价**：链首必须能装下前 N 层，且它同时是 HTTP 面所在的那台机器。想「让最弱的那台当链首」不行；
弱设备只能当 relay / tail（`ANDROID-SURFACE-段接入评估.md` §0 的纯弱设备链就是把 Y700 放在 tail）。

另一条代价：链首的 `-t` 不过网（`PATCHES-DETAIL.md` §1 的 split-stage 线程一行），所以链首和段的
线程数要分开给。

## 5. 决策五：协议按通道选——同一个 `--spec-type`，整模与链上是两套路径

**选了什么**：三种草稿源按**通道**分流，而不是按名字分流：

| 草稿源 | 通道 | 链上表现 |
| --- | --- | --- |
| DFlash / DSpark | `layer_inp` tap（协议 v9） | **跨机零损失**：逐 prompt 与整模相同 |
| MTP | nextn 通道（协议 v8 起可下沉到 tail） | 链上接受率低于整模（现行默认 −13%，旧路径 −24%） |

**为什么**：两种源的取数位置不同。DFlash / DSpark 要的是**中间层**的 hidden
（`dflash.target_layers = [2,7,12,17,23,28,33,38]`，每层一份），这些层横跨 head 与 tail，所以 v9 把
tap 挂在 decode 回复的附带段上过网（请求带**源模型层号**，回复追加 `n_rows × n_taps × n_embd` 的
f32 段，`MAX_LAYER_INP_TAPS = 16`）。

MTP 要的是**末段**的 NextN 头，走 nextn 通道；v8 把它下沉到 tail（`OP_MTP_DRAFT`，k 步递归在 stage
内跑，一帧只回 k 个 id）。

同一个 `--spec-type` 在整模与链上是两套路径——整模上 MTP 好用，推不出链上一样好用；两套路径的机制与
实测在 [05-结果](05-结果.md) §2.3，本章只写「通道怎么选、代价在哪」。

**代价**：MTP 在链上有折扣。实测（官方 35B、k=2、`n_predict 64`）：整模 0.9098、链上旧路径 0.6879、
现行默认 0.7877；三档对照与 mean len 见 [05-结果](05-结果.md) §2.1，修法与「默认关」的取舍见
[06-局限与结论](06-局限与结论.md) §1.3。

v9 的代价是 prefill 传输量：512 行 ubatch = 8 MB / 4 MB，真跨机 prefill 多 3.05 s（9–10%，
`PROTOCOL-V9.md` §3.3）。

## 6. 决策六：控制面只做三件事

**选了什么**：`control/qlhctl.py`（944 行）+ `control/topology.example.toml`（56 行），合计 1000
行——「控制面一千行以内的承诺」（`DEPLOYMENT.md` §7）。三个子命令：`up` / `status` / `down`。

**为什么**：控制面不实现协议、不碰 token、不理解层、不采样、不校验层范围与切点——那些在
`split-stage` 与 `llama_context` 里（`control/qlhctl.py` 模块 docstring 逐条列出）。这样切有两个
直接后果：

1. 删掉控制面，链照样能手工起，它省掉的只是「记住五条命令、盯五个日志、猜哪一段死了」；
2. 判据不会漂——协议只有一处实现，不会出现「Python 侧和 C 侧对帧的理解不一致」这类失败。

反面参照是 prima.cpp：约 4,000 行控制面里 3,551 行（profiler 2,745 + HiGHS 806）是给「未知异构
设备 + 无配置」付的税；我们设备固定、层区间是配置项，那笔税不必付（`PRIMA-ANALYSIS.md` §7）。

**代价**：没有自动切分求解、没有工件传输、没有动态重平衡（`DEPLOYMENT.md` §7）。拓扑是人写的，
切点算错不会有人替你纠正——只在 C 侧被拒（`SEGMENTED-LIMITS.md` §2.6 的两道检查）。

## 7. 决策七：每台机器持同一份整模，不存裁切件

**选了什么**：每台机器放同一份完整 GGUF，加载时用 `--split-layer-range` / `--layer-range` 决定只
创建、只读取哪几层；段是加载时的视图，磁盘上只有整模（`DEPLOYMENT.md` §1）。

**为什么**，三条，按分量排：

1. **MTP 头**。裁切件没有 `blk.40`（NextN 层），而投机解码要它。
2. **空间上反而更省**。每段都要重复带 `token_embd`（**515 MiB，Q8_0**）/ `output.weight`（**398 MiB，Q6_K**），
   四段合计比
   整模还大。
3. **换分段零传输**。段是派生物，改拓扑里的数字就是换分段；裁段方案要重切、重 scp。

（`DEPLOYMENT.md` §1；`ARCHITECTURE.md` §2.3 记中段因此省 **~913 MiB**——`token_embd` 515 MiB
与 `output` 398 MiB 两个都不建。）

**代价**：首次部署要传一次整模，21.87 GiB 按 ROG 实测 22 MB/s 约 17 分钟（`DEPLOYMENT.md` §1 的口径，
那是蒸馏版体积；官方 `UD-Q4_K_M` 是 21.11 GiB，`MODEL-SWAP.md` §11.1）；每台机器的磁盘要放得下整模。

另一条代价是**权重一致性靠人**：`OP_HELLO` 只报 range / 宽度 / 深度，区分不了同形状不同权重的 GGUF
（`SEGMENTED-LIMITS.md` §2.7 末段），控制面只能补一道 size / mtime 的启发式自检
（`control/qlhctl.py` 的 `check_weights()`）。

## 8. 这套形状主动放弃了什么

| 放弃的 | 为什么 | 出处 |
| --- | --- | --- |
| token 间流水 | 单序列上不可行：`t_{p+1}` 只可能由 `tail(p)` 产出，依赖图是单链 | `ARCHITECTURE.md` §11 |
| 远程链多序列 | `n_seq_max > 1` 被拒；多租户改部署形态（链首起多个 server） | `SEGMENTED-LIMITS.md` §2.4 |
| 跨 ubatch 的回退 | 上游 `ab3768cdc` 拒绝超出本 ubatch 快照的回退，本仓删掉了 shift 机制 | `SEGMENTED-LIMITS.md` §0.2 |
| 级联投机（DFlash 块 + MTP 尾巴） | 触发条件「整块全接受」随跨 ubatch 与深草稿迅速变稀（k=15 只剩 2.8%） | `SEGMENTED-LIMITS.md` §2.3 |
| 采样投机 | 链这条路只支持贪心；原生验证器支持 rejection sampling，链上缺一次判据实验 | `ARCHITECTURE.md` §7 末段 |
| 把 `-ngl` 做成全局最优 | 显存与预算按段独立核算；head 与 tail 不在同一台机器时没有全局解 | `SEGMENTED-LIMITS.md` §1.2 |
