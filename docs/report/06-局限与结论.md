# 06 局限与结论

> 状态：**现行**
> 更新日期：2026-11-11
> 适用范围：这套改造主动接受或暂时接受的全部边界（每条写现象、根因、影响范围、修复代价）、主动不做

> 验证判据见 [04-验证](04-验证.md)，数字口径见 [05-结果](05-结果.md)，设计取舍见

## 0. 一句话

这套改造**没有**让分段链在所有维度上等于整模：它让「数值」等于整模（逐位 / 逐字节），让「容量」从装
不下变成装得下，代价写在下面十条里。每条边界都是选它的理由的另一面，并标了修复要付什么。

## 1. 十条边界

### 1.1 架构白名单：只认 `qwen35` / `qwen35moe`

**现象**：链首必须导出 `output_norm` 之前的隐藏态；其他架构在建上下文前报错退出——
`split_arch_exports_pre_norm()` 只认 `LLM_ARCH_QWEN35` / `LLM_ARCH_QWEN35MOE`，三处建链检查都
`return -1`（`SEGMENTED-LIMITS.md` §2.1）。

**根因**：出口逐架构手写，没有公共挂点。

**影响**：tail 段只出 logits、不受此限；远程段的架构在链首看不见，`OP_HELLO` 只报 range / 宽度 / 层深。

**代价**：按模型补是机械工作，但要逐个验证 `output_norm` 位置与 norm 类型；真正解法是抽到
`llm_graph_result` 层的公共出口，要改上游公共代码——产品阶段的事。

### 1.2 远程链单序列：`n_seq_max > 1` 被拒

**现象**：`llama_split_attach_remote()` 拒绝 `n_seq_max > 1`，`-np > 1` 在 `tools/server/server.cpp` 的
启动检查里先被拒。

**根因**：设计决定——远程链解决「一台装不下」或「借用算力」，不是多租户。

**影响**：远程链上 slot 复用退化；并发只能链首起多个 server、各走自己的链（`SEGMENTED-LIMITS.md` §2.4）。

**代价**：技术上约 105 行可做（协议加每行 `seq_id`），决策是「不修这条，改部署形态」。

### 1.3 链上 MTP 的通道差异：结构性低 13%（旧路径 24%）

**现象**：官方 35B、k=2、`n_predict 64`：整模 0.9098，链上默认 0.7877，旧路径 0.6879。

**根因**：`speculative::process()` 的 catch-up 条件是 `!is_mem_shared && !is_chain && !is_remote`（上游
只有 `!is_mem_shared`），`speculative::draft()` 在 chain 下每轮清草稿 KV；两处自洽成循环
（`MODEL-SWAP.md` §11.4）。

**影响**：远程链没有 `ctx_dft`，keep-KV 的收益不适用，所以远程链的 MTP 上限就是 0.788 那一档。

**代价**：keep-KV 已默认开（零额外前向、零传输）；catch-up 能追平 0.9098，成本 `N_prompt × 1.19 ms`。
自 2026-11-11 起**未设置 = 逐请求自适应**：`n_predict ≤ 128` → mode 2，`N_prompt > 3 × n_predict` → 不做，
其余 → mode 1；显式 `QLH_CHAIN_DRAFT_CATCHUP=0/1/2` 完全接管（`=0` 与未设置靠 `catchup_mode_env()` 的
`-1` 区分）。四场景实测见 `MODEL-SWAP.md` §11.4。

### 1.4 层范围合法性：两道检查，边界在「标记由谁置真」

**现象**：一个层范围单独起 server，两种误配都在加载后、建上下文前报错：范围在模型中间结束又没给
`--split-tail-range` / `--split-remote`；或范围不从 0 开始（`20:24` 这种「就是尾巴」）而
`common_params::split_range_is_stage` 为假。

**根因**：区分「合法一环」与「误配」只能靠内部标记（默认 false，只有 `llama-server` 加载 tail 时置真），
判据在 `common_init_from_params()`，读 `llama_model_layer_range()` / `llama_model_n_layer_src()`。

**影响**：判据是「本进程是不是在拼链」，不是「范围是否合法」；任何在进程内构造 `common_params` 又把标记
置真的调用方都跳过第二道检查。

**代价**：把标记换成「范围 + 链身份」的显式描述，是参数 / 协议层重构，现在不值得
（`SEGMENTED-LIMITS.md` §2.6）。

### 1.5 核显按整段 offload：中间档一律更差

**现象**：`-ngl 99` 各段全上；中间档一律更差，交叉点随 prompt 长度移动（pp32 0.69× → pp256 1.90×），
35B 装不进共享堆。

**根因**：iGPU 共享系统内存，段内部分 offload 没有收益区间；全量 offload 的 prefill 仍大赢、decode
基本持平（同构建基线 −4.8% / 1.90×）。

**影响**：主线走纯 CPU；iGPU 只在 2B / 9B 小模型 + 全量 offload + 长 prefill 上有正收益
（`IGPU-SLOWDOWN.md` §①、§⑥）。

**代价**：不修；要的是「按段 × 按 prompt 长度」选档，属于部署策略不是内核改动。

### 1.6 hybrid 的 partial `seq_rm`：上游缺陷，本仓只做「失败可见 + 降级」

**现象**：上游 `llama_memory_hybrid::seq_rm` 先删 recurrent，失败就 `return false`，**attention KV 的
删除被整体跳过**；hybrid 在 server 默认 `n_rs_seq = 0` 下 partial 分支要求 `rollback <= n_rs_seq` 不成立，
于是永远失败。

**根因**：上游设计（open PR #28007 / issue #31656），本仓不提新 issue、不改上游语义。

**影响**：本仓把 `common_memory::seq_rm` / `common_context_seq_rm` 从 `void` 改成 `bool`，五个调用点按
场景降级，链路停摆不杀进程（`SEGMENTED-LIMITS.md` §2.9）。

**代价**：上游修之前只能「失败可见 + 降级」；产品形状的回退由 grammar / rbudget 两组逐位覆盖，那两组全绿。

### 1.7 `embeddings_pre_norm` 的出口逐架构手写：176 个实现里只有 2 个

**现象**：`src/models/` **176 个 `.cpp`**（按 `src/models/*.cpp` 计数；`enum llm_arch` 条目是 173）里，
只有 `qwen35.cpp` 与 `qwen35moe.cpp` 有 `embeddings_pre_norm` 分支。

**根因**：出口逐架构手写，没有公共挂点；换到上游通用的 `t_layer_inp` 会丢掉「relay 段顺带不裁 LM head」
这个好处（省一次近 515 MiB 的 `output` 张量），且第一代就走那个槽位、因要给 9 个架构各登记一次而放弃。

**影响**：新增架构要按模型补 tap 点；失败方式从「静默数值偏移」变成「启动即拒」。

**代价**：机械工作 + 逐个验证 `output_norm` 位置与 norm 类型（同 §1.1）；改走 `t_layer_inp[n_layer]` 要
每架构补一行登记并放弃裁 LM head。

### 1.8 远程链 append-only：slot 复用退化为从头重算

**现象**：远程链只导出 checkpoint 那一档序列状态（`LLAMA_STATE_SEQ_FLAGS_PARTIAL_ONLY`），全量 state
（含 KV）由 `split_state_unavailable()` 判掉、`state_get_size()` 返回 0。

**根因**：与单序列同一个设计决定。

**影响**：slot 复用在远程链上退化为从头重算；追加式复用全命中，但聊天历史被模板重渲染时一个 token 都
复用不上（`SEGMENTED-LIMITS.md` §2.4）。

**代价**：同 §1.2，约 105 行；不做。

### 1.9 远程链的 checkpoint：blob 12.56 MiB 留在 stage 内，v6 起过网 8 字节

**现象**：35B 的 8 层 qwen35moe 段，每段 blob 实测 **13,172,908 B = 12.56 MiB（恒定）**；整份
checkpoint 62.813 MiB = head 本地 50.2 + 远程 12.56。**这个 blob 留在 stage 进程内，不过网。**

**根因**：正确性成本——只存链首会让尾段停在旧位置。

**v5 及更早**：链首把 blob 存下来再原样递回，跨机实测两次 remote blob 26.3 MiB、1.91 s。
**v6 起**（`STATE_FLAG_HANDLE`，`src/llama-split-proto.h:224-235`）：stage 自己保存快照，链首每段
只传 **8 字节 handle**（下行 8 + 上行 8），`proto.h` 的注释记了被消除的实测 0.8–1.2 s/次（16 MB/s）。
handle 过期是**可恢复**答案（`ST_STALE`，stage 在应用前就拒绝），不是断链。

**剩余代价**：同 slot 连发两个请求，第二个命中 136 token（2830.7 ms），不命中按 122 ms/token 重算
约 17.8 s → 净赚约 14.7 s，平衡点约 15–20 token 复用前缀。这一条是前缀复用本身的账，与 handle 无关。

### 1.10 `can_shift = false`：对 qwen35 忠实，对本地纯 KV 链过度保守

**现象**：聚合 memory 的 `get_can_shift()` 恒返回 false。

**根因**：`qwen35` / `qwen35moe` 是 IMROPE，`n_pos_per_embd() = 4`，而
`llama_kv_cache::get_can_shift()` 对 `n_pos_per_embd() > 1` 返回 false——整模同样不支持 ctx_shift，
差距为 0。

**影响**：本地纯 KV 链（`n_pos_per_embd() == 1`）本来可以 shift，聚合视图一律报 false，server 退化到
重算前缀。

**代价**：`can_shift` 要变成「所有段的与」，且 shift 要真广播到每一段；后者是 `seq_add` 的跨段语义
（现在 `reject_remote("seq_add")` 直接拒绝），所以只对本地链有意义（`SEGMENTED-LIMITS.md` §2.8）。

## 2. 主动不做：分页 KV 为什么是「换机制」

立项时的 KV 优化方案是 Python 侧自研 PagedAttention（`main` 分支 `src/paged_kv_cache.py`，574 行）。
v2.1 用数据关掉了这个方向，换的是机制。先看 KV 在整模里占多大：

| 项 | 大小 | 占整模 |
| --- | ---: | ---: |
| 权重（UD-Q4_K_M 整模） | 21.10 GiB | 100% |
| 其中专家（`*_exps` 张量） | 18.68 GiB | **88.5%** |
| KV（`-c 4096`，单序列） | **88 MiB** | **0.41%** |

口径：权重按 GGUF 头逐张量累加（753 个张量，`gguf` python 包），与 `print_info: file size` 的 21.10 一致；
文档别处的 21.11 是 `accept_baseline.md` 上表口径，差 0.01 GiB（`MODEL-SWAP.md` §11.1）。KV 的账来自 Y700 尾段日志
`llama_kv_cache: size = 16.00 MiB (4096 cells, 2 layers, 1/1 seqs), K (f16): 8.00 MiB, V (f16): 8.00 MiB`
与 `size = 8.00 MiB (4096 cells, 1 layers, 1/1 seqs)`，即**每 cell 每层 2 KiB**（GQA：4 个 KV head ×
head_dim 128 × K+V × f16）。

整模 11 个 full attention 层（head 8 + tail 3）× 4096 cells × 2 KiB = **88 MiB**。（旧蒸馏版 Q6_K 是
19.86 GiB 专家 / 21.86 GiB 整模 = 90.8%，见 `MODEL-SWAP.md` §11.1；两版不能混着算。）

三条论据：

1. **量级不对**：分页 KV 能省的是 88 MiB 里的碎片，最极端 40% 碎片率也只省 35 MiB；专家那边是 18.68 GiB
   的池子。**差约 217 倍**（18.68 GiB ÷ 88 MiB ≈ 217）。
2. **收益场景不存在**：分页 KV 的钱来自「多序列变长碎片 / 前缀共享 copy-on-write / 高并发吞吐」三处。

   远程链是单序列（§1.2）；前缀复用 `llama.cpp` 已有 prompt cache（3103 token 历史整段重算 19847 ms →
   第二轮只解 38 个新 token 用 714 ms），分页省的是复用背后的内存、不是时间；`-np 4` 是能力不是主战场。
3. **代价方向错了**：`llama.cpp` 的 KV 是启动时按 `n_ctx` 预分配的定长 slot，做分页等于重写上游 KV 管理
   核心，而这棵树的立身之本是「16 个文件与 `09338b85e` 逐字节相同」「rebase 后自己的代码少了 17 个文件」
   （`SEGMENTED-LIMITS.md` §0.1、`PATCHES.md`）。为 0.41% 去动上游核心，方向错了。

**替代方案（都有实测，是换机制不是没做）**：prompt cache 前缀复用（19847 ms → 714 ms）；checkpoint 序列
状态导出 / 导入（远程链每段 blob 12.56 MiB 留在 stage 内，v6 起过网 8 字节，§1.9）；`--moe-cache-mib 1024`（命中率 82.2%，tg 18.05 →
31.99，`SEGMENT-OFFLOAD.md` §5.1）。

**一条限制**：专家缓存只在「该层全部专家在 host **且**该层被分配到 GPU」时启用
（`llama_moe_cache_is_host_weight()` + `dev_layer()`），所以纯 CPU 的链（安卓 Y700、Surface、本机
`-ngl 0`）用不上——它救的是「有卡但显存装不下 35B」那种形态。

**定性**：这是工程判断，与仓库里两个已有先例同类——`INVENTORY.md` 用逐功能域盘点关掉了老仓库 129,337
行里的绝大部分；`SLIM-ARC-接入计划.md` 用「两项都量完、收益低于 10% 就不接」的门槛把第二级
（on-demand 加载器）留在未接。

## 3. 已知未做（照实写）

1. **catch-up 的自适应阈值**——已补（2026-11-11）。原来只写在 `MODEL-SWAP.md` §11.4 的建议里：默认
   mode 1；`n_predict ≤ 128` 升 mode 2；`N_prompt > 3 × n_predict` 不做。现在实现为逐请求自适应，显式
   `QLH_CHAIN_DRAFT_CATCHUP=0/1/2` 完全接管（`=0` 与未设置靠 `catchup_mode_env()` 的 -1 区分）。四场景
   实测（本机 `0:32+32:40`、T=0、k=2、3 prompt）：mode 2 得 **0.9098 = 整模逐位相同**，mode 1 得
   0.7355，长 prompt 落到 mode 0、显式 `=0` 回到 0.7877（覆盖优先）。判定在 server 的 `batch_building`，
   结果经 `QLH_CHAIN_DRAFT_CATCHUP_AUTO` 交给 spec 层，**接口零改动**（`MODEL-SWAP.md` §11.4）。
2. **远程链的 catch-up。** 需要一条 prompt token-id 通道（N × 4 B），**明确在范围外**；远程 head 没有
   `ctx_dft`，本地链那套 keep-KV 的收益不适用（`MODEL-SWAP.md` §11.4、`SEGMENTED-LIMITS.md` §2.2）。所以
   远程链的 MTP 停在 0.788 那一档是结构性的。
3. **SLIM-ARC 只接了 prefetch 一块。** 驻留**决策器**已接（`select_resident_experts()` 被
   `issue_expert_willneed()` 调用），但喂它的**压力源**零调用点（`set_expert_residency_pressure` /
   `expert_pressure_controller::update` / `set_expert_budget`），所以开 `SLIM_ARC_EXPERT_RESIDENCY=1` 时
   恒走 `missing` 分支，等于放行全部。I/O 调度器确实未移植（`unified_io_scheduler` 只在注释里出现，
   预算由 `default_prefetch_budget_bytes()` 兜底），KV 驱逐确实未做。默认关闭，
   `SLIM_ARC_PREFETCH=1` 才装，且只在「段装不下、真的在读盘」的降级形态里有事可做（`README.md` 代码与
   验收、`SLIM-ARC-接入计划.md`）。

## 4. 结论：能力对齐走到哪一步

**做到了逐位 / 逐字节相同的路径**：

- DFlash / DSpark 跨机零损失（[05-结果](05-结果.md) §2.2）；
- MTP catch-up mode 2 与整模逐位相同（[05-结果](05-结果.md) §2.1）；
- `-np 4` 四并发输出与串行逐字节相同（`verify/verify.sh` 组 5、`README.md` 能力表）；
- 三段链全 vocab 逐位、checkpoint 往返逐位、安卓尾段入链（[04-验证](04-验证.md) §2、§6）。

**还差的**：远程链的 MTP 接受率停在 §1.3 的 0.788 那一档，**且是结构性的**——远程 head 没有 `ctx_dft`，
本地链的 keep-KV 收益不适用；catch-up 要 prompt token-id 通道（§3 第 2 条）。要追平整模得改协议，不是
调参数。

所以「能力与整模对齐」这条主线的准确表述是：**本地链已经走到「逐位相同」，远程链走到「除 MTP 接受率外
逐位相同」**；而分段买到的容量是真的（[05-结果](05-结果.md) §1.2、§3）。

## 5. 可以怎么往下做

1. **远程链 catch-up**：协议加 prompt token-id 通道（N × 4 B），把 0.788 推到 0.91；这是把「远程链除 MTP
   外逐位」补成「全维逐位」的唯一一条路。
2. **架构出口抽到公共挂点**（`llm_graph_result` 层），解掉「176 个实现里 2 个」的白名单；同时保留「relay
   段不裁 LM head」。
3. **远程链多序列**：协议加每行 `seq_id`（约 105 行），换多租户；不做也能靠「链首起多个 server」绕过。
4. **SLIM-ARC 第二级**（on-demand 加载器）：只在「段装不下、真在读盘」的降级形态里有事可做。

## 6. 本章哪些是定性 / 未实测

- §1.1 与 §1.7 的「抽到公共出口」是代码级推断，**未实施**；修复代价是按改动面估的。
- §1.2 / §1.8 的「约 105 行」是估算，不是实测工作量。
- §1.10 的「本地纯 KV 链可以 shift」是代码级结论，**打开是否安全从未验证**（`SPECULATION-DATA.md` §5）。
- §2 的「重写上游 KV 管理核心」是代价判断；分页 KV 本身**未实现、未实测**，88 MiB / 0.41% / 217 倍是
  算出来的，不是量出来的。
- §2 的专家缓存限制是从 `llama_moe_cache_is_host_weight()` 与 `dev_layer()` 两个条件推出的；纯 CPU 链上
  它本来就不启用，所以没有「关掉前后」的对照实测。
- §3 第 1 条的阈值已实现并实测（2026-11-11，四场景见 `MODEL-SWAP.md` §11.4）；8.8% 与「3 × n_predict」平衡点
  仍是同一节的公式推导。
