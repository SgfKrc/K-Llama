# 01 背景与目标

> 状态：**现行**
> 更新日期：2026-11-11
> 适用范围：项目要解决的问题、既有做法的代价、目标与验收判据的立场，以及 v2 → v2.1 的沿革。
> 读者是第一次接触本项目的评审与后续维护者。总体设计见 [02-总体设计](02-总体设计.md)，实现见
> [03-实现](03-实现.md)，总纲见 [`../REPORT.md`](../REPORT.md)。

## 0. 一句话

大模型在边缘设备上跑不动有两个互相独立的维度——**装不下**和**算得慢**。本项目把一台机器装不下的
模型按层拆到多台机器上，并且要求拆完之后**能力与整模对齐**：判据是逐位 / 逐字节的 logits 与 token，
不是「生成的文字看着对」。

## 1. 问题一：单机内存装不下

以本项目的目标模型 `Qwen3.6-35B-A3B-UD-Q4_K_M` 为例，整模 **21.11 GiB**（`README.md`「实测」
一节的口径行；`MODEL-SWAP.md` §11.1 另记 5.10 BPW）。而一台 16 GiB 的边缘设备（Surface Pro 7，
i5-1035G4，4C/8T）连装都装不下：

| 形态 | 每轮 | 吞吐 | 说明 |
| --- | ---: | ---: | --- |
| 单台 Surface 跑整模 | 363 ms | **2.75 t/s** | 抖动区（22 GiB > 16 GiB） |
| Surface `0:24` + Y700 `24:40`（纯弱设备链） | 153 ms | **6.50 t/s** | 不占本机 |

（`ANDROID-SURFACE-段接入评估.md` §0；Q6_K、21.87 GiB / 35.51 B 口径，与 §1 的 21.11 GiB 不是同一份
权重，两份不能混用——`MODEL-SWAP.md` §11.1。）

这张表是本项目立项理由最直接的一条：**装不下意味着这条路本来跑不起来**，比「慢」更硬。同一份材料
里，两段纯弱设备链比单台弱设备快 2.4 倍，且两端都持整模、没有裁层工件。

内存维度还有两条更省事的解法——换更小的模型或压得更狠，各有自己的天花板，见 §3。

## 2. 问题二：单机算力不够

算力维度不能靠「把层搬走」直接解决，因为单序列 decode 的依赖图是一条链：`tail(p)` 产出 `t_{p+1}`，
`head(p+1)` 才可能开始，**一次 decode 的墙钟 ≈ 各段耗时之和**（`ARCHITECTURE.md` §11）。多一段就多
一次跨机往返，外加每段 33–35 ms 的固定开销（`ARCHITECTURE.md` §11 的表）。

可对照的算力量级（都是生成阶段口径）：

| 形态 | 吞吐 | 出处与口径 |
| --- | ---: | --- |
| 35B 整模、纯 CPU、MTP k=2 | 10.54 gen tok/s | `MODEL-SWAP.md` §11.2；`-c 4096 -b 512 -t 8 -ngl 0`，三个 prompt 均值，**有背景负载** |
| 35B 整模、纯 CPU（旧蒸馏版） | 7.1 tok/s | `PROGRESS.md` §1；v2 口径、文档已退场，**不作 v2.1 判据** |
| 35B 链、head `0:32` 本机 + tail ROG 纯 CPU | 7.51–9.73 tok/s（五类 prompt） | `CROSS-MACHINE.md` §1；旧蒸馏版，32-token 生成 |

拆开买到的是**容量**，代价是往返与段数。本项目的目标因此是「装不下的能装下，且算出来的东西和整模
一样」（§4）。这条立场也是 04 / 05 两章所有数字的读法。

## 3. 既有做法与它们的代价

| 做法 | 买到什么 | 代价 | 依据等级 |
| --- | --- | --- | --- |
| 蒸馏 / 换小模型 | 体积与算力同时下降 | 能力上限由教师与学生共同决定，换不回来 | **定性**（本仓无通用能力评测） |
| 量化 | 体积随位宽线性下降 | 有下限；本项目已落在 5.10 BPW（`MODEL-SWAP.md` §11.1），再往下压本仓未实测 | 部分实测 |
| 上游 RPC（`-DGGML_RPC=ON`） | 远端当「远程 GPU」，主机维护全局图 | 主机必须装下整模；首次跨机流量 = 权重总量（GB 级）；每次图计算一次 `GRAPH_COMPUTE` 往返 | 代码走查（`ARCHITECTURE.md` §8、`PATCHES.md`「与原生 RPC 的分界」） |
| 另一条 fork 路线（prima.cpp：build graph 时跳层） | 每节点持同一份整模、只读自己几层 | 必须改每个架构的 build 函数，于是只能支持 LLaMA / Qwen2；控制面约 4,000 行里 3,551 行是给「未知异构设备 + 无配置」付的税 | **只读代码走查、未编译运行**（`PRIMA-ANALYSIS.md` §0、§7、§8） |
| 投机解码（本项目自己也用） | 一轮多前进几个 token | 收益随负载翻号：跨机中位 +6%（+8.4% ~ −1.2%）、弱机 −40%、回环 0.67× | 实测（`CROSS-MACHINE.md` §1、§2） |

两条口径说明：

1. **第一行是定性判断。** 本仓有蒸馏版与官方版的对照，但那是「草稿源的 hidden 分布一致性」
   （k=2 接受率 0.699 vs 0.910，`MODEL-SWAP.md` §11.3），不是通用能力评测。用这条对照去论证
   「蒸馏掉能力」是偷换口径，所以这里只写定性。
2. **RPC 那一行的「代价」是结构性的，不是实测的。** 本仓没有跑过 RPC 与分段链的 A/B；表中的
   三条来自协议命令与「主机必须装下整模」这一事实（`ARCHITECTURE.md` §8 的表：首次跨机流量、
   主机是否装下整模、每步流量、计算图归属、异构要求）。

## 4. 本项目的目标

立项时的技术路线是 **Python + PyTorch + Qwen-1.8B + 三台校园笔记本**、主从式 TCP 架构：在
llama.cpp 外面套一层 Python 调度，做 4/8 bit 量化、算子融合、KV 缓存优化，再把 Transformer 层按层
拆到多台终端（`local_docs/plans/立项.md`「主要研究内容」与「研究方案」两节）。

这套原方案有据可查地留在 `main` 分支上：**41 个文件**，`src/` 9 个 `.py` 加一个 React 前端
（`git ls-tree -r main`）。

**立项承诺的六项（4/8 bit 量化、算子融合、K 缓存优化、多终端协同、模型分层拆分、可演示可部署）与
现行形态的逐项对照留给总纲**（[`../REPORT.md`](../REPORT.md)），本章不重复。本章只交代结论：现行的
两条硬要求是

1. **能力与整模对齐**——判据见 §5；
2. **边缘弱设备（安卓平板、老笔记本）能成为链上的一段**——实测形态见
   `ANDROID-SURFACE-段接入评估.md` §0 与 `CROSS-MACHINE.md` 的安卓尾段一节。

这两条是从「装不下」（§1）直接推出来的：如果拆完能力掉了，拆开就没有意义；如果弱设备接不进来，
「边缘」这个词就只剩「两台工作站」。至于从 1.8B 换到 35B-A3B、从主从式换到「每段各持整模 + 只传
`n_embd` 宽的隐藏态」、把可视化平台降级为约 1000 行的控制面——这些是 §6 讲的三次收敛的产物。

## 5. 判据先说清：逐位 / 逐字节，不是「看着对」

本章立起判据。`ARCHITECTURE.md` §9 把证据分三级：

| 级别 | 例子 |
| --- | --- |
| **硬判据** | 贪心 token 与整模逐位一致；段间 hidden `max\|diff\| = 0` |
| 参考 | 吞吐、接受率（必须带口径：模型、量化、生成长度、设备） |
| 不算 | 「输出看起来通顺」、单次运行、跨配置比较 |

为什么必须这么严：这类改造的失败形状**多数不报错，只算错或悄悄退化**（`SEGMENTED-LIMITS.md` §4）——
层号重映射漏一处会读到源文件的 `blk.0`，输出仍然通顺、只是错的；`seq_rm` 失败被吞掉之后，调用方在
「prompt 已回退、KV 没回退」的状态上继续算，不报错、只算错。这两类实例的详版见
[04-验证](04-验证.md) §1。

判据还带来一条自我约束：投机解码的硬判据是「链上投机 == **整模投机**逐字节相同」；「投机 == 不投机」
测的是 batch invariance——llama.cpp 只对 RMSNorm（全 backend）与 CUDA 的 MatMul / Attention 承诺它，
CPU + 量化正落在这片空白里（`PROTOCOL-V9.md` §4、`ARCHITECTURE.md` §9）。**判据要先问「这份代码
承诺过什么」。**

## 6. 三次收敛：v1 → v2 → v2.1

仓库的演变是**同一个项目的三次收敛**，每一步都在缩小代码面、同时提高能力。

| 阶段 | 形态 | 代码面 | 仓库落点 |
| --- | --- | --- | --- |
| **v1** | Python + PyTorch + Qwen-1.8B + 三台校园笔记本，主从式 TCP；带着历史包袱与初期的 slot 式对话调度设计 | `dev` 分支 **1099 文件**（src 201 / tests 445 / scripts 158 / docs 167） | `dev` 分支；立项原方案另在 `main` 分支（41 文件） |
| **v2** | 精简 + 验证：Python 驱动链（`chain_client.py` / `stage_worker.py` / `shim/`），第一次把「层段接力」跑通并逐位验证 | 已归档，不在现行树里 | `slimarc/prototype` |
| **v2.1** | 下沉改造：链进 `llama_context`，`llama-server` 自己就是驱动者，能力与整模对齐 | **157 文件**（docs 55 / checks 42 / verify 28 / longctx 16 / scripts 10 / control 2） | `slimarc/segmented`（现行） |

**收敛的依据**：v1 是「1.8B + PyTorch，在 llama.cpp 外面套一层」，v2.1 是「35B-A3B（总参数 35B /
激活 3B）+ 把链下沉进 llama.cpp 内部并做到逐位对齐」。模型大了、判据从「能跑」变成「逐位」，代码面
反而小了 7 倍（1099 → 157）——因为**v1 的大部分代码在解决「怎么把一个 Python 调度器写完整」，不是在
解决「怎么把层段接起来」**。

取舍有据可查。`docs/legacy/INVENTORY.md` 是 v1 → v2 盘点的逐功能域判定表，对象是旧 `qlh/src` 的
**232 个 `.py` / 129,337 行非空行**，逐域给出「保留 / 部分保留 / 抛弃」与理由：

- F04 引擎适配层 7,066 行抛弃、F05 模型供给 14,157 行抛弃、F06 调度控制面 29,752 行抛弃；
- F07 `qlh_core` 8,108 行抛弃、F10 API server 16,018 行抛弃；
- 只保留层段接力、keep-head 通道、工件裁切的一部分、帧编解码约 280 行。

`docs/legacy/BASELINE.md` 是同一件事的另一面：为「控制面 + llama.cpp worker」框定必须移植的最小面。两份文档
的头部都写明**盘点的是前身仓库**，因此只作取舍依据。

v2 → v2.1 那一跳的取舍在 [02-总体设计](02-总体设计.md) §1（为什么下沉）。一条纪律贯穿全文：两代的
数字**不可混用**——v2 的吞吐数据归 `MEASUREMENTS.md`，v2.1 的判据归 `SPLIT-MEASUREMENTS.md`
（`README.md` 的分工段）。本报告只讲 v2.1。
