## 0. 一句话

判据是**逐位 / 逐字节的 logits 与 token**，不是生成的文字。套件分两层：`verify/verify.sh` 的 95 项
覆盖「链没坏」，七个专项脚本覆盖「套件碰不到的失败路径」（链死、协议边界、投机回退、上游已知缺陷）。
两层的共同前提是：**被测对象是上游 llama.cpp 的构建产物**，不是本仓库的 Python 驱动链（`verify/README.md` 开头）。

## 1. 为什么比 logits，不比文字

| 判据 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 生成的文字相同 | 这一次的 argmax 轨迹相同 | 数值相同。argmax 一致经常是巧合（`SEGMENTED-LIMITS.md` §4） |
| logits 逐位相同 | 这条路径的数值与整模一致 | 跨 ubatch 的一致性（见下） |
| 链上投机 == 整模投机（逐字节） | 分段没改变投机结果 | 「投机 == 不投机」——那测的是 batch invariance |

三条理由，按分量排：

1. **文字相同不能证明数值相同。** 层号重映射漏一处会读到源文件的 `blk.0`，输出仍然通顺、只是错的
   （`ARCHITECTURE.md` §2.2）；`seq_rm` 失败被吞掉之后，调用方在「prompt 已回退、KV 没回退」的状态上
   继续算，不报错、只算错（`SEGMENTED-LIMITS.md` §2.9）。

   这类失败形状多数不报错，判据必须落在数值上（`SEGMENTED-LIMITS.md` §4）。

2. **batch invariance 有边界。** llama.cpp 只对 RMSNorm（全 backend）与 CUDA 的 MatMul / Attention
   承诺它，CPU + 量化正落在这片空白里（`PROTOCOL-V9.md` §4）。

   实测：整模、`n_ubatch=512`、2 行 vs 1 行前向，`h` 的 2048 个元素全部不同，`max|Δ| = 0.27`；同一
   情形跑两遍 `max|Δ| = 0`——是确定性的 kernel 形状差异，不是抖动（`verify/verify_mtp_e2e.sh` 文件头）。
   所以「投机 == 不投机」只能当 INFO。

3. **跨 ubatch 的「逐位相同」不成立。** 同一 prompt 装不进 `n_ubatch` 时 GEMM 累加顺序改变，head
   自己的 tap 与整模的差可以有 **4e-4**（29 token / `n_ubatch=12`），同一轮测量里最大到 1e-1 量级
   （`SEGMENTED-LIMITS.md` §3.1，后者未落盘）。

   所以所有逐位验收都必须在单 ubatch 内做，长 prompt 的逐位对比要把 ubatch 边界写进结论。

### 2.1 组 11 补的是哪个洞

组 9 / 10 跑的是 `tests/dflash-taps.cpp`：它只 link `llama`，**从不调** `llama_set_embeddings_layer_inp_dev`
（`ctx_tgt` 没有 device buffer），batch 用 `llama_batch_init` 而不是 `llama_batch_ext_add_embd_row`
（`ubatch.embd_row` 恒空，graph 走 host embd 分支）。所以 `common/speculative.cpp` 那条 **device-buffer
注入路径在验收里零覆盖**。

v9 的默认路径在远程链上第一次请求就断言，产品崩而组 9/10 全绿，就是这么漏掉的（`verify/verify.sh`
文件头）。组 11 直接跑产品路径：整模必须仍走 device buffer（宽度谓词不能误杀整模），链必须按预期回退
到 host copies、无 `GGML_ASSERT`，且输出与整模逐字节相同——特征错了采样分布就变，输出不可能仍逐字节
相同（`verify/verify_dflash_dev_path.sh` 文件头）。

## 3. 七个专项脚本

这些不进 `verify.sh`，因为它们要么要等 120 s 读超时、要么要挂起进程、要么要跑整模对照，跑一趟几分钟到
十几分钟。每一项都能独立跑（`verify/README.md` §4）。

| 脚本 | 项 | 判据 | 为什么单列 |
| --- | ---: | --- | --- |
| `verify_chain_death.py` | 36 | 挂起 stage 后 `/completion` 约 120 s 失败、head 活着、`/health` 仍 200；链死后后续请求立即 500、`?deep=1` 立即 503；错误信息点名段 / endpoint / seq / 范围；只重启 stage 能自愈且输出与从未断过逐字节相同；5 个连续请求只触发 1 次重连（5 s 节流）；`-np 2 + --split-remote` 启动即被拒 | 它要真的 `NtSuspendProcess` 挂起一个 stage 再等它自己的 120 s 读超时，跑一趟约 4–5 分钟；混进套件会让人不敢跑（`verify/verify_chain_death.py` 文件头） |
| `verify_seq_id.py` | 9 | 越界 `seq_id` 回 `ST_BAD_REQ` 且连接可继续用；合法 `seq_id=0` 回 `ST_OK` 两次 | stage 曾把线上的 `seq_id` 直接传进 memory 层；协议边界只能对着线缆测 |
| `verify_mtp.sh` | 6 | wire 上回传的 `h_nextn` 与整模逐位；远程 tail 3 步递归的 3 个 token 与「整模 + MTP」逐个相同 | 它要一个与 `split-rows` 的 head 分界一致的 tail（`20:24`），与套件里 `8:16` / `16:24` 的形状对不上 |
| `verify_mtp_e2e.sh` | 6 | 远程链 MTP（temp=0）与整模 MTP 逐字节相同；附三组速度对照 | 端到端：投机只改变「谁来猜」，不改变「采出什么 token」；位置 / h 链 / 接受逻辑错了会从某个 token 起分叉，而 tok/s 看起来正常 |
| `verify_grammar_spec.sh` | 23 | 带 grammar 的请求真在投机、分段不改变结果、被拒行能回退、走逐行通道、无 abort | grammar 曾经整请求禁用投机；回退路径要 8 次服务启动才覆盖全 |
| `verify_rbudget_spec.sh` | 36 | 真实 tools 请求不被 rbudget 闸门挡掉、走逐行通道、不投机 / 投机两种形态链 == 整模逐字节、预算耗尽后强制段正确且回退不多扣 | v8 放开 grammar 后 rbudget 这条闸门还在；要 12 次服务启动 |
| `verify_seq_rm_exact.py` | 6 用例 | `seq_rm(p,-1)` 后重算第 p 行逐位相同；越界回退必须明确拒绝 | 不 split、不起服务；A1/A2/B1/B2/B3 是**上游 hybrid 的已知基线**（`n_rs_seq=0` 下永远失败、rebase 后 `rs_max=0` 使部分回退必被拒），用 `--expect-known-fail` 跑 = **1 pass / 5 known-fail / 0 unexpected**，退出 0 |

`verify_seq_rm_exact.py` 那 5 条 known-fail 不是本仓的欠账：产品形状下的回退由 grammar / rbudget 两组
逐位覆盖，那两组全绿（`verify/README.md` §5）。

## 6. 跨机与安卓：五步破坏性验收

跨机**不是**跑 `verify.sh`——套件里所有脚本都是 `127.0.0.1`，没有一条真的跑两台机器
（`verify/README.md` §9）。跨机的验收是手工的**五步破坏性**流程，打在同一条链上：

| 步骤 | 判据 | 安卓实测（Y700 尾段） |
| --- | --- | --- |
| `status`（基线） | 全部段 ok | `2/2 段 ok` |
| 杀掉远端尾段 | —— | 尾段被外部结束，日志停在 `OP_STATE_SAVE`、没有退出原因 |
| 再 `status` | 报 `DEAD`、退出码 1 | `DEAD`，退出码 1 |
| 浅 `/health` | 仍 200（存活语义） | `200 {"status":"ok"}`，13.7 ms |
| `/health?deep=1` | 503、点名远端段 | `503`，1.52 s，点名 `remote stage 1 (<tailscale-ip-y700>:9482)` |
| 生成请求 | 立即 500、不挂住 | `500`，**2.6 ms** 返回 |
| `down` | 两端干净 | 干净，9481 端口 connection refused |

**为什么单列**：这一流程要真的挂起一个 stage、再等它自己的 120 s 读超时，跑一趟约 6 分钟
（`verify/verify.sh` 文件头、`verify/verify_chain_death.py` 文件头）。同一批实测里还有一条判据：
**杀段后链的死活只有 `status` 与 `?deep=1` 能判**，浅探针照样 200（`CROSS-MACHINE.md` §6.1、§6.3）。

安卓那一侧的吞吐与三次非单调的拆解见 [05-结果](05-结果.md) §1.2、§3 与 `CROSS-MACHINE.md` §6.2。
**安卓 / ARM 的结论没有任何脚本支撑，全靠人工**（`verify/README.md` §9）。

## 7. 一条纪律：SKIP 不算通过

`QLH_VERIFY_FAST=1` 只跑 2B 的组（1–8 与 12），组 9/10/11 **明确 SKIP**，并把「这一轮没有测到 35B 的 DFlash / DSpark」
显著打印出来；`SKIP` 既不算通过也不算失败，`FAIL=0` 只说明被测过的那些组没有退化，**一次运行不能当成
完整验收**（`verify/verify.sh` 的 `skip()` 与结果段、`verify/README.md` §4）。组 13 不受这个开关影响：它换的是
`build-kvmem2` 构建，不进 35B 显存闸门（构建或 KVMem 源码根不存在时仍记 SKIP）。两条相关口径：

- 内存低于闸门（`QLH_VERIFY_MIN_FREE_GB`，默认 20 GB）时组 9/10 记 **SKIP**；**缺 35B 模型时记 FAIL，不是
  SKIP**（`verify/README.md` §5）。
- 闸门读的是「可用」= 空闲 + 可回收 standby，且要等它稳定：刚杀完进程立刻读会读到 19 GB（误 SKIP），
  稳定后 22 GB（`verify/verify.sh` 的 `available_gb_settled()`）。

## 8. 本章的边界

- **跨机与安卓不可重跑**：结论来自手工实测，套件全是回环（`verify/README.md` §9）。
- **没有性能回归闸门**：tok/s、接受率漂移只记录不比，判据只有「逐位相同」这类硬判据
  （`verify/README.md` §9）。
- **GPU 侧只覆盖了段级 offload 与 KVMem 两项**：组 1–11 全部跑在 `GGML_CUDA=OFF` 的 `build-split` 上、所有
  server 都是 `-ngl 0`；组 12 用 CUDA 构建验「整模 vs `--split-layer-range 0:24`，都 `-ngl 4`」逐字节
  相同，这是段级 offload 的唯一自动项；组 13 用 `build-kvmem2`（`LLAMA_KVMEM=ON`）验 KV 虚拟化的四项
  （能跑 / 驱逐 / 保留的 KV 是对的 / 确定性）。MoE 缓存（`--moe-cache-mib`）、`op_offload` 段默认、显存预算、
  SLIM-ARC 这四项**仍没有自动验收**——`verify/` 里搜不到 `op-offload` / `moe-cache` / `SLIM_ARC`，
  它们的数字只来自手工实测（`SEGMENT-OFFLOAD.md`、`IGPU-SLOWDOWN.md`、`SLIM-ARC-接入计划.md`）。
  catch-up 的逐请求自适应同理（组 8 只跑 keep-KV 默认路径），实测见 `MODEL-SWAP.md` §11.4。
- **控制面与架构白名单也没有自动项**：`control/qlhctl.py` 的 `up/status/down` 靠人工五步验收；
  「非 `qwen35` 架构启动即拒」是代码级结论，组 1 的「不衔接的链被拒」测的是层范围校验，不是架构白名单。
- **两条已做但本批验收未覆盖**：`seq_rm` 的 `p0` 退化分支是 code-review-verified, not run；
  shared-prefix 路径的 `[INFO] injection never fired` 表示该路径未产生有效注入（`SEGMENTED-LIMITS.md` §2.9）。
- **多模态端到端没跑过**：4 个 M-RoPE section 能跨段传是代码级结论，分段链 + mtmd 的组合从未跑过
  （`SPLIT-MEASUREMENTS.md` §7）。
