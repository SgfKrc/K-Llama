## P0 阻断项

- **运行时去 torch 化** —— ✅ **已关闭（2026-10-03）**：构建期由 `QLH_BUILD_PROFILE` 显式选 profile（`packaging/packaging/qlh-slim.spec`，包内只带选定 profile 的那一份运行时清单），manifest 字段由 `packaging/packaging/install_manifest.py` 按 `runtime_guard.RUNTIME_PROFILES` 校验；包体自描述由 `qlh_launcher.bundled_runtime_profile()` 从"包内是哪份清单"反查出 profile 并写入 `QLH_RUNTIME_PROFILE` 交给子进程；子进程用 `device_profiler.detect_runtime_profile()` 随 device_info 上报，主节点 `/api/cluster/nodes`（`NodeInfo.to_dict`）可见 ⇒ 调度能区分无 torch 的边缘节点与带 torch 的 PC 节点。契约测试：`tests/test_runtime_profile_advertise.py`（含 src 与打包侧 profile 集合一致性）、`packaging/tests/test_bundled_runtime_profile.py`。注意：未显式指定时默认 CPU SLIM 仍保持 `torch_cpu` 兼容行为，`llama_cpp_only` 必须由发行构建显式选择。
- **Linux 最小变体**：`packaging/packaging/linux/build-deb.sh:206-215` 当前无条件装 torch，且 `control-cpu` 宣传 PyTorch 备选引擎（`packaging/packaging/linux/control-cpu:14-16`）。应补 `llama-cpp-only`/edge 变体：只带受管 `llama-quantize`、`llama-cpp-python`（或纯 native RPC worker）、FastAPI/TUI 所需轻依赖；安装后执行 `python -c 'import importlib.util; assert ... torch is None'` 作为硬门。**发行口径已排除 Linux 原生产物**（只发行 **Android + Windows**；Linux 必要时用 WSL 代替并标注「WSL 证据 ≠ 原生机证据」）⇒ 本项**不在发行门内**，保留为后续变体工作。
- **动态导入审计** —— ✅ **已关闭（2026-09-28）：静态闭包与干净 venv 运行扫描两侧都落地**。
  两侧意义不同、缺一不可：
  - **静态**（`scripts/edge_import_audit.py`，纯标准库 + AST）：从入口做 **import 闭包 BFS**，
    用**两遍传播**把「导入即崩」（`must_load`：只沿**无条件顶层** import 扩散）与「走到才崩」
    （函数内 / `try/except ImportError` 兜住）分开；接在 `startup_matrix.py` 的 `edge` profile。
  - **运行时**（`scripts/edge_preflight.py` 的探针）：在**目标 venv** 里真 `import` 各入口，
    查 `sys.modules` 看 forbidden 有没有被拽进来 —— **Edge 档真正装载的是它**。

  实测（`edge` profile，`.venv-edge` = **106.11 MB**，无 torch 系）：

  | 入口 | 静态 `must_load` / `blocking` | 运行时 |
  |---|---|---|
  | `qlh_edge`（Edge 最小入口；契约 = 裸 `/health` 等）| 2 / **0** | import OK（329 模块）|
  | **`src.api_server`**（**SLIM 真实载荷**：`uvicorn src.api_server:app`，路径带 `/api/` 前缀）| **66** / **0** | **import OK（144 条路由全注册，0.48 s）** |

  两入口的 `forbidden_loaded` 与 `forbidden_installed` **均为空**。

  **顺带查实三件事**（都已写进代码注释，防止回归）：
  1. **预检对象 ≠ 发行物载荷**：`edge_preflight.py` 过去只探 `qlh_edge`，而 SLIM 跑的是
     `src.api_server`（`packaging/packaging/qlh_launcher.py`）⇒ 现在**两个入口都探**，
     且各跑**独立子进程**（同进程会互相污染 `sys.modules`，第二个入口的判据就不可信），
     对 `src.api_server` **不查路由**（`REQUIRED_ROUTES` 是 `qlh_edge` 的契约，混用会误判）。
  2. **PyInstaller `excludes` 依然不能替代这一步**：SLIM 运行的是**源码**，
     顶层命中即**导入即 ImportError**，`excludes` 只在打**冻结包**时起作用。
  3. **`startup_matrix._run_subprocess` 只保留 stdout 尾部 `OUTPUT_TAIL` 字符** ⇒
     全量 JSON（含 86 个模块名）会被**截断**并伪装成"JSON 非法"（实测踩过）⇒
     两个脚本都改用紧凑/摘要输出，并各自显式区分「被截断」与「JSON 非法」。

  **余量（不影响本项关闭）**：`src.api_server` 闭包里仍有 **27 处函数内**命中。运行时扫描已证明
  无 torch 的 venv 里 `import` 成功且 `sys.modules` 里没有 torch ⇒ 它们当下**不是**可触发的崩溃点；
  但"分别是哪 27 处、SLIM 常规路径会不会走到"尚未逐条核对。
- **包体边界复验** —— ✅ **已落地（2026-10-03）**：`packaging/packaging/bundle_boundary_scan.py`。
  拿实际磁盘内容比对 profile 的禁品集合，并解析二进制导入表（PE 用 `pefile` 读导入目录、
  ELF 用标准库直接解 `DT_NEEDED`）⇒ 既抓"文件本身不该在"，也抓"文件在但链到了禁品"——
  后者只扫文件名会漏。判据分档与 `runtime_guard.RUNTIME_PROFILES` 同源：
  `llama_cpp_only` 不得含 torch / transformers / accelerate / safetensors；
  `llama_cpp_only`与`torch_cpu`拒绝CUDA运行库及其导入；显式`torch_cuda`允许CUDA spec冻结的native依赖闭包。开发残留（构建脚本 / 测试 / agent 配置 / `__pycache__`）对所有
  profile 一视同仁。报告写 JSON（`--report`），纳入发布附件。`pefile` 缺失时**报违规**
  而非静默跳过（否则"没装 pefile"会伪装成"没有违规"）。
  与 `install_manifest.py` 的分工：后者证明**文件完整性**（磁盘与清单一致），本脚本证明
  **依赖闭包**（清单里不该有的东西真的不在）。两者缺一不可。
  实测 `dist/QLH-Edge-Inference`（2026-08-11 旧产物，早于 profile 化）：按 `torch_cpu` 扫
  495 个二进制 / 2002 个导入**无违规**；按 `llama_cpp_only` 扫抓出 3797 项（该产物确实含
  torch 系）⇒ 两个方向都验证了判据有效。回归测试见
  `packaging/tests/test_bundle_boundary_scan.py`（17 passed）。
  **余下**：用**新契约构建的**发行物跑一遍（现有 `dist/` 产物早于 profile 化，不能作为
  发布证据）；以及把报告接进发布附件流程。

## P1 平台审计与修复

### Windows

- 为 SLIM 增加 CPU-GGUF 首启路径：无网络或无 Python 时应能给出可操作失败，不得偷偷创建 torch runtime；外部 runtime 目录需记录 engine/profile 与版本锁。
- `qlh-slim.spec:59-64` 的排除列表应配套静态 import 检查；对 `_internal/src` 做 `compileall`、只读 CLI、API health 和 GGUF 单轮生成 smoke。
- 真实干净 Windows 机仍需完成安装、升级、断网、权限受限、repair/回滚和卸载后用户数据保留；当前文档仅记录 Launcher 基础验收，不能替代主应用验收。

### Linux

- `build-deb.sh:25` 版本号与 `packaging/packaging/version.txt`、Launcher 版本存在漂移风险；构建前应由单一版本源生成 `.deb`/manifest/服务文件。
- `build-deb.sh:190-202` 在 ensurepip 不可用时在线下载 `get-pip.py`；最小离线发行必须提供受管 bootstrap 方案或明确把联网安装列为安装前置，并将 SHA-256/代理/证书失败写入验收门。
- `.deb` 需在 Ubuntu 22.04、Debian 12 原生主机分别做 `dpkg-deb --contents`、`ldd`、安装/升级/卸载、systemd 无头启动、桌面/TUI/API health 和 GGUF 生成；WSL 只能作为构建辅助，不能替代运行时证据。

### Android

- `android/app/build.gradle.kts:43-108` 当前只有 arm64 ABI；需明确设备矩阵（16 KB page、Android API、arm64 真机/模拟器）和 Full/Lite 包的模型/worker 能力差异。
- `scripts/android_validation.py` 的 `arm64_native_worker` —— ✅ **判据已改（2026-09-30，`70431d36`）**：
  不再只由「安装+启动+ABI」推导，改为要求**真机可观测**证据：进程存活 **且**
  `nativeloader` 实际装载包内 `libqlh_llama_jni.so`（另单列弱证据
  `device_foreground_service_started` / `device_worker_service_referenced`）。
  真机实测（Y700/TB321FU/Android 15/SDK 35）：`status=native-worker-candidate`、
  `jni_library_loaded=true`、`foreground_service_started=true`。
  **剩余**：模型分片请求、连续生成、取消、重连、热/电量采样 —— 需 App 进 distributed 模式后采。
  ⚠️ 两个已固化的真机坑：① `--launch` **不能**用 `monkey`（联想 ZUI `AutoRunService` 会把它
  当「system relative auto run」**主动 kill**，看起来像闪退）；② `adb logcat` 含非 GBK 字节时
  旧 `_run` 会 `UnicodeDecodeError` 打断校验。
- `android/app/src/main/AndroidManifest.xml` 开启 `usesCleartextTraffic` 和多个前台服务；发布前必须做 TLS/网络安全配置、最小权限审计、签名/anti-debug/备份策略审计，并验证 release APK 的 native 库和 proguard 规则。
- ★ **APK 应内置 llama 运行时（否则 Android 节点缺 `tail` 角色）** —— 2026-09-28 三机验收的**实测依据**：
  Y700 上**没有 pip `llama_cpp`**，而 `relay_mid_service.py` 的 `tail` 角色默认走 `TailRunner`
  （**依赖 pip 绑定**）⇒ **Y700 跑不了 tail**，只能做 `middle` / `head`
  （那两条走 `ShimTailRunner` / `HeadRunner`，即自带 shim）。
  ⇒ 若要让 Android 节点承担 **tail（吃 hidden 吐 token）**，发行包里就**必须带 `libllama.so`
  等原生运行时**（并把 `qlh_keep_head` 一起打进 `jniLibs`）；或者显式接受
  「Android 只做 middle/head」这一限制，并写进能力广告与调度判据。
  ⇒ 相关脚本：`scripts/relay_y700_build.sh`（在设备上编译 llama.cpp + shim，
  含 **SONAME 符号链接**与 **`cp -L`** 两个坑的固化）。
  ★ **2026-09-30 实测更正**：APK **已经内置** `lib/arm64-v8a/libqlh_llama_jni.so`
  （**11.84 MB**，含 llama.cpp + 我们的 JNI 层段入口）⇒ 上面"必须带原生运行时"这条
  **已满足**（App 侧）。（此前 Lite 变体的同名 .so 是 0.00 MB 空壳；full/lite 区分已于
  `e0fc54f` 放弃 ⇒ 单一变体就是带运行时的那份。）
  **仍需澄清**：App 的 JNI 层段入口 **≠** Termux 侧 `relay_mid_service.py` 的
  `tail`/`middle` 角色，两者不是同一条链 ⇒ 「Android 能否承担 relay tail」要按 JNI 路径
  单独裁定，不能由"包里有 .so"直接推出。

## 统一验收门

1. **依赖门**：Edge 三平台干净环境中 `torch`、`transformers`、`accelerate`、`bitsandbytes` 不存在；启动、健康检查、GGUF 单轮生成通过。

5. **发布证据门**：每个产物附构建环境锁定、依赖清单、SBOM/许可证、SHA-256、签名 manifest、测试命令和原始 JSON/日志；三平台均有可复现命令。

### 已排除的 5 个真实障碍（**都会被重踩**，务必留档）

### 三机验收怎么复现（用法）

**前置**：三机在线（`tailscale status`）、工件 sha 一致（T1）。跨机段服务**只允许 loopback**
（`relay_transport.is_loopback_host` 的硬约束）⇒ 远端服务必须先经 **SSH 隧道**铺到本机 loopback。

**1) 起远端段服务**

```bash
# Y700（Android/Termux；先用 scripts/relay_y700_build.sh 装好 shim 与 llama.cpp）
cd ~/qlh-keephead
export LD_LIBRARY_PATH="$PWD/bin:${LD_LIBRARY_PATH:-}"
export PYTHONPATH="$PWD:$PWD/src"
termux-wake-lock                                   # ★ 防 Android 杀后台
setsid python3 relay_mid_service.py --role middle --listen 127.0.0.1:50180 \
    --keep-head-shim "$PWD/bin/libqlh_keep_head.so" \
    --model /sdcard/Download/QLH/models/<中段工件>.gguf \
    --mode nextn --threads 4 --n-seq-max 1 --n-batch 2048 \
    --ready-file "$PWD/mid.ready" --max-connections 8 \
    < /dev/null > "$PWD/mid-nohup.log" 2>&1 &
```

Surface（Windows）用 **`schtasks`** 起（`Start-Process` 起的会随 ssh 会话被回收）：
先写 `.bat`（内容 = `cd /d <repo> && .venv-test\Scripts\python.exe scripts\relay_mid_service.py …`），
再 `schtasks /create /tn qlh-tail-surface /tr <bat> /sc once /st 23:59 /f` + `/run`。
⚠️ `/tr` 有 **261 字符上限** ⇒ 长命令必须走 `.bat`。
⚠️ 若该环境**没有** pip `llama_cpp`（或它的绑定不支持该架构），tail 段需加
`--keep-head-shim`（+ `--dll-dir`）走 `ShimTailRunner`，否则落到 `TailRunner`（依赖 pip 绑定）。

**2) 建隧道（`scripts/relay_ssh_tunnel.py`）**

```bash
python scripts/relay_ssh_tunnel.py open  --target y700 --remote-port 50180 --local-port 50180 --wait 25
python scripts/relay_ssh_tunnel.py open  --target surface@100.100.52.106 --remote-port 50188 --local-port 50310 --wait 25
python scripts/relay_ssh_tunnel.py check --local-port 50180      # 协议级探活（relay_health --probe）
python scripts/relay_ssh_tunnel.py close --local-port 50180
```

★ Windows 上它**走 `schtasks`**（`.bat` → `/create` → `/run`），隧道由任务计划程序托管
⇒ **跨命令 / 跨会话都活着**（原先的 `DETACHED_PROCESS` 留不住，实测踩到）；
pid 文件里存 **pid（POSIX）或任务名（Windows）**，`close` 两种都能停。

**3) 跑探针（判据一律 per-token argmax）**

```bash
# 三段 L→L（本机 head → Y700 middle → Surface tail）；层范围从 manifest 自动读
python scripts/relay_l2l_net_probe.py \
    --head-model <本机 head 工件>.gguf \
    --middle-endpoint 127.0.0.1:50180 --tail-endpoint 127.0.0.1:50310 \
    --whole-model <同精度整模>.gguf --model-dir <HF 目录> \
    --prompt <prompt 文件> --prefill 32 --gen 32 --threads 8 \
    --mid-manifest <中段 manifest>.json --tail-manifest <末段 manifest>.json \
    --total-layers 24 --strict-coverage --json-out <证据>.json

# DL 三段落（D 档上游，需 CUDA ⇒ 用系统 Python）
python scripts/relay_experiment.py --path d2l2l_keep_head_net --model-dir <HF 目录> \
    --layers 8 --mid-layers 16 --mid-endpoint 127.0.0.1:50180 --mid-stop 16 \
    --cut-model <末段>.gguf --whole-model <整模>.gguf \
    --prompt <prompt 文件> --prefill 32 --gen 32 [--mid-extra-latency-ms 50]
```

**4) 收工**：`relay_ssh_tunnel.py close` 逐条清隧道 + 停远端服务
（Y700：`pkill -f relay_mid_service` + `termux-wake-unlock`；Surface：`schtasks /end /tn qlh-tail-surface`）。

⚠️ **两个最易踩的坑**（实测踩到）
- **工件/模型必须与上游匹配**：`n_embd` 由**上游**决定；若远端段载的是**别的模型**
  （hybrid 2048 vs qwen2 896），会在**远端**报 `hidden_payload_size_mismatch`
  （不是崩溃 —— 这个报错很好排查，但要先想到去看远端日志）。
- **`--n-seq-max` 别用默认 8**：单序列长 decode 会因「ctx 被均分」在 ~512 步
  `llama_decode rc=1` ⇒ 现象是 `runner_failed`，**与"模型算错"难区分**。单序列用 `--n-seq-max 1`。

## 遗留：单机装不下整模的分布式实验（待做）

**为什么要它**：去 torch 化的连通性验收全程用 `qwen2.5-0.5b` / `qwen25-05b-f16`（不到 1GB）打通链路。这类小模型**单机就装得下**，于是任何「层区间分配被忽略」「退回整模」的退化都不会暴露 —— 容量求解、`layer_ranges` 约束、relay 段认领这些机制在小模型上"碰巧都对"，验不出通用性。

**要验的四件事**：

1. **分配必须是分布式**：模型权重总量超过单机可用内存 ⇒ 容量求解**不可能**退回单机分层。当前所有 `distributed_required` 断言靠的是"两端都在线"，而不是"单机真装不下"。
2. **容量账与实测量级一致**：每节点 `required_bytes` 由 `layer_weight_bytes` 推出，要与实际加载后的内存占用对得上（小模型上这个误差看不出来）。
3. **不依赖 qwen2 的隐含假设**：换 `architecture`（含 hybrid / Gated Delta Net 那类不能朴素截断的）、换 tied vs untied `lm_head`，确认没有"只对 qwen2 成立"的 assume。
4. **工件命名不耦合**：`_find_layer_artifact` 靠 manifest 的 `source_layer_range` 匹配而非文件名（已实测 `cut-16` 的名字对应 `[16,24)`），需要在异构命名下复核这条不变量。

**顺带暴露一个新缺口（待登记）**：`_find_layer_artifact` **只按 `source_layer_range` 匹配、
不校验模型身份** ⇒ 混放不同模型的裁层工件会**互相冒充**：

```

qwen25-05b-f16-cut-16.manifest.json  range=[16,24] mode=tail   ← 与 q35-9b-b 的 [16,24] 相同
```

而 manifest **本身已记录** `source_model_sha256`（q35 段为 `9be22744…`）—— 只是匹配时没用。
⇒ 修法很小：比对 manifest 的 `source_model_sha256` 与当前加载模型的身份。

**判据 ②（容量账与实测量级一致）—— 已取数，结论：账偏保守 1.43×。**

用主仓引擎的算法（`llama_engine.py:378` 经 `read_gguf_tensor_bytes`，注释明确「不用 offset 差值，
因为差值含 32 字节对齐填充」）算三段容量账：

| 段 | raw_MB | required(×1.2) | 附分量 |
|---|---|---|---|
| head `[0,16)` | 2677.9 | 3213.5 | embedding 572.1 |
| mid `[16,24)` | 1017.2 | 1220.7 | — |
| tail `[24,32)` | 1923.0 | 2307.6 | lm_head 834.4 |

组件字节：`embedding = 572.1 MB`、`lm_head = 834.4 MB`、`final_norm = 0.0`。

**实测**（`LlamaCppEngine.load_layer_range(24, 32, has_embedding=False, has_lm_head=True)`）：

```
loaded. delta_MB = 1615.7        ← 进程 RSS 增量
```

⇒ `required_bytes=2307.6` vs 实测 `1615.7` ⇒ **账偏大 1.43 倍**。

- **方向安全**：账 > 实测 ⇒ 不会误判「装得下」（不会把装不下的层派给节点）；
- **精度粗**：差距来自 **mmap 惰性分页**（只加载不 touch，RSS 增量小于权重字节）。若推理时
  真正 touch 全部页，RSS 会接近 raw 值。
- 这正是判据②所说「小模型上这个误差看不出来」——在 0.5B 上 raw 只有几十 MB，1.4× 的差距
  淹没在噪声里；到 9B 才显形。

### 三、`sys.executable` 在 PyInstaller 产物里**不是 Python 解释器**

`llama_keep_head.py` 的隔离 worker 用 `[sys.executable, worker.py, "--shim", ...]` 启动自己：

- **源码态**：`sys.executable` = `python.exe` ⇒ 正确；
- **冻结态**：`sys.executable` = `QLH-Edge-Inference.exe` ⇒ 它**不会**去执行那个 `.py`，
  而是重跑自己的入口 `launcher.py`（一看 8000 已有实例就停住）⇒ **worker 的 stdin/stdout
  协议永不建立**。

**实测证据**（进程命令行 + 日志 + 超时三者互相印证）：

```
ProcessId=7576   CommandLine=QLH-Edge-Inference.exe app-ui
ProcessId=13660  CommandLine=QLH-Edge-Inference.exe ...\_internal\llama_keep_head_worker.py --shim ...
                 ↑ .py 被当参数传给了 exe 自己
keephead-worker.log   0 字节          ← 脚本从未执行
master                60s 超时         ← 协议未建立
```

**修法**：给 launcher 加 `--keephead-worker` 早期分派（packaging `165339a`），冻结态改走
`[sys.executable, "--keephead-worker", ...]`，由**同一个 exe** 用 `runpy.run_path` 把包内 worker
脚本当 `__main__` 跑（主仓 `a0f22342`）；源码态保持原样。回归：`31 passed, 7 skipped`。

### 四、打包环境被污染 —— 已重建

`packaging/.venv-packaging` 是指向**主仓根** `.venv-packaging` 的 junction，而那个 venv 里累积了
**1,131 MB / 86 个包**（含 `accelerate` / `bitsandbytes` / `huggingface_hub` / `hf_xet` / `pandas`
/ `sympy` / `networkx` / `diskcache` —— 全是 torch 生态遗留）。PyInstaller 正是从它收依赖，
这正是包体膨胀到 255 MB 的来源。

**重建**（2026-10-06）：删 junction → 删旧 venv → `python -m venv` → 重连 junction。现状：

```
packaging\.venv-packaging  →  G:\C\PYT\qlh\.venv-packaging
内容：仅 pip 25.0.1      大小：11 MB      （重建前 1,131 MB / 86 包）
```

**踩到的坑**：`Remove-Item 'packaging\.venv-packaging'` 在非交互 PowerShell 下报「处于非交互
模式」而**不删**，随后 `New-Item -ItemType Junction` 因「目录不为空」失败 ⇒ **junction 静默
保留旧目标**。清 junction 必须用 `cmd /c rmdir`（只摘链接、不动目标）。

### 五、**真正的根因**：`build-cpu.bat` 的依赖清单没跟随 profile

重建干净 venv 后重打包，**体积与包列表一模一样又变回 86 个包 / 1148 MB** —— 证明污染不是 venv
的历史遗留，而是**每次 build 都重新装进去的**。追到 `build-cpu.bat`：

```bat
if /i "!QLH_BUILD_PROFILE!"=="llama_cpp_only" (
    echo   跳过 PyTorch（llama_cpp_only 档不装 torch）
) else (
    "%PYTHON%" -m pip install torch --index-url https://download.pytorch.org/whl/cpu --quiet
)
"%PYTHON%" -m pip install -r packaging\requirements-cpu.txt --quiet     ← 无条件！
```

**torch 确实被 profile 分支跳过了**，但**下一行无条件装 `requirements-cpu.txt`**，而它含：

```
transformers>=5.17.0     accelerate>=1.0.0     huggingface_hub>=1.5.0
transformers-stream-generator>=0.0.4     einops>=0.6.0
bitsandbytes>=0.45.0     pandas>=2.0.0
```

这些的**传递依赖会把 torch 拽回来**（所以 venv 里赫然出现 `torch 2.14.1`），而 **torch 本体被
spec 的 `excludes` 剔掉了、它们的依赖 `huggingface_hub` / `hf_xet` 却不在 excludes 里** ⇒ 被收进
包 ⇒ **~50MB → 255MB**。

⇒ **不是「去 torch 化搞砸」，是「依赖清单没跟着 profile 走」**。修法：slim 档改用
`requirements-runtime-llama_cpp_only.txt`（**只有 7 项**：fastapi / uvicorn / httpx / psutil /
python-dotenv / llama-cpp-python / textual），torch 与非 slim 依赖都留给 `else` 分支
（packaging `592960c`）。

### 六、**最后一处**：`launcher.py` 把 stdout 重定向到了日志文件

上面那处修好后，keep-head worker 确实起来了（`keephead-worker.log` 出现完整 GGUF 加载日志、
`[qlh_keep_head] ctx ready`），但三段请求**仍等满 60s**。根因在 `launcher.py` **模块级**：

```python
# packaging/packaging/launcher.py:36-41（import 时即执行）
_redirect_dir = os.path.join(os.path.dirname(os.path.abspath(sys.executable)), "logs")
os.makedirs(_redirect_dir, exist_ok=True)
sys.stdout = open(os.path.join(_redirect_dir, f"stdout_{_ts}.log"), "w", encoding="utf-8")
sys.stderr = open(os.path.join(_redirect_dir, f"stderr_{_ts}.log"), "w", encoding="utf-8")
```

那是给 GUI/TUI 模式用的。但 **keep-head worker 的协议通道正是 `stdout`**：

- worker 端：`print(json.dumps(payload), flush=True)`
- 父进程端：`line = process.stdout.readline()`（`src/llama_keep_head.py:363`）

⇒ 重定向后 worker 的响应被写进 `stdout_*.log`，**父进程永远读不到** ⇒ 等满 60s 超时。
`--keephead-worker` 分派（同一个 `main()` 里）**发生在重定向之后**，所以必须显式还原：

```python
if "--keephead-worker" in sys.argv:
    sys.stdout = sys.__stdout__      # ← 还原协议通道
    sys.stderr = sys.__stderr__
    ...
```

（packaging `5265678`）

**这六处构成一条完整的因果链**，任一处不修，Edge 包都无法作为 layer worker 工作：

| ③ | 冻结包 `sys.executable` 不是解释器 | worker 进程在但协议不建立 |

| ⑤ | 精简清单漏 `python-multipart` 等 | 服务启动即失败 |
