## 1. 调研结论（2026-09-15；本地代码核实 + 官方来源）

1. **llama.cpp RPC 存在跨机权重/KV 分布能力，但尚未达到生产支持**：主 host 可通过 `--rpc host:port,...` 使用多个 `ggml-rpc-server` worker，权重和 KV 可按设备内存比例分布；官方仍将 RPC 定性为 proof-of-concept、fragile、insecure，并明确不应暴露到开放网络。QLH 将它列为主线攻关对象，但在分片驻留、身份、传输保护、租约、回滚和 soak 门通过前，不宣称已接入生产。
2. **llama.cpp 的本地多设备 split 与 RPC 必须分开**：server 当前有 `--split-mode layer/row/tensor`；layer 是默认的 pipeline 形态，tensor 仍是实验性路径。它们证明的是同一运行时内的模型分割能力，不等于 QLH 已获得跨生态、异构网络的稳定分布式协议。
3. **Android 的 PyTorch 生态路径是 ExecuTorch AOT，而不是完整 PyTorch 运行时**：官方 ExecuTorch Qwen3 示例覆盖 Qwen3 0.6B/1.7B/4B，Android 通过 AAR 和 XNNPACK/Vulkan 等后端运行；代价是导出链和模型集合受限。它是远期可选引擎，不改当前 L=GGUF、D=PyTorch 的双档边界。
4. **跨框架层接力没有可直接复用的通用中间张量标准**，但本地实验已经证明 L→L（llama.cpp→llama.cpp）裁层 GGUF + `embd` 注入可以逐 token 16/16 行为等价。D→L 主仓双引擎矩阵 27/27 逐 token 一致，跨机 SSH 隧道逐步生成 141/141，L→L 与 D→L 均按 per-token argmax 对拍；Relay 保持独立合同与 fail-closed 门。旧 PyTorch `LAYER_FORWARD` 协议不改。
   - **XFRAME 首轮诊断（2026-09-16，已解决）**：141-token 长批曾出现 f16 `132/141`、全 f32 `128/141` 的分歧（首分歧位置 18 / 14）；控制组把根因收敛到 **llama.cpp 长批 `embd` 输入图/续算路径**（`build_inp_embd()` 在 embedding 模式下仍构造并调度未被写入的 token 分支）。上游调用方按 `n_pos_per_embd*n_tokens` 修正 `pos` 后，D→L 长序列已恢复逐 token 一致（主仓矩阵 27/27、跨机 SSH 隧道 141/141）。
5. **任务图/整请求级分发只能作为迁就型回退**：OpenAI 兼容 HTTP 是最低公共层，任务池可以承载 Android/GGUF 轻节点，但它要求完整模型可在某个执行节点装下，不能实现“单机装不下、各节点只装一部分”的核心价值；主线不再把它当作模型分布式形态。
6. 本地核对：项目已有三种代码形态（PyTorch 层拆分、TP 孤岛、任务池）；Android Full 当前使用本地 llama.cpp/HTTP 任务路径，构建未启用 `GGML_RPC=ON`，因此不能把 RPC 或 Android Layer Worker 写成已交付能力。

### 1.1 Silica Cluster 外部复核

- [Silica Cluster](https://github.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI) 确实把 Android 设备包装成 `libllama.so` 主节点或 `librpc.so` worker，并通过标准 llama.cpp `--rpc` 连接远端节点。
- [BinaryRunner.kt](https://raw.githubusercontent.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI/main/app/src/main/java/io/github/shintochakkiath/silicacluster/BinaryRunner.kt) 的“精确层拆分”实际是 `-ngl N`；没有完整层数时则使用 `--tensor-split` 比例。按 llama.cpp 官方语义，`-ngl` 是设备上限层数，`--tensor-split` 是各设备比例，不是 QLH 的跨节点连续 `layer_range` 合同。
- [SilicaService.kt](https://raw.githubusercontent.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI/main/app/src/main/java/io/github/shintochakkiath/silicacluster/SilicaService.kt) 还包含完整模型上传到 worker 后再启动引擎的路径，因此它验证的是 Android 承载 GGUF/RPC 的可行性，不是模型层段只持有、带身份校验和可恢复租约的分布式层流水线。
- **结论（2026-09-15 改写）**：Silica 的价值不只在 Android，而在于它给出了“llama.cpp host + RPC backend + Android worker”的攻关入口。QLH 主线将 llama.cpp 模型分片/RPC 作为生产主攻，先完成 PC 单机、同机双进程模拟，再做 PC/Android 真机；PyTorch 降为 PC 对照，任务图降为完整模型回退。QLH 要补的是把“比例/上限分配”升级为**可校验的部分驻留合同**，并补上身份校验、传输保护与租约。Silica 为 AGPLv3，**不复制其代码**，只借鉴协议边界与验证方法。
  - **（2026-09-16 v7 修订）** 上文“PyTorch 降为 PC 对照”为 2026-09-15 时点结论，已由 §6 不变式 1 的 v7 裁决取代：**有 CUDA 的节点保留 torch 能力并默认开启（显式开关、可关闭并退化）**。Silica 相关的“不复制代码/只借鉴”结论不变。

## 2. 四形态定案（主线排序）

> 2026-09-16 v7 更新（2026-10-02 修订）：新增 Relay 架构兼容形态（L→L 同机单进程行为证据已通过；D→L 主仓双引擎矩阵 27/27 逐 token 一致，跨机 SSH 隧道 141/141）；Android RPC 仍属 llama.cpp 模型分片主形态；**PyTorch 在 CUDA 节点为默认加速引擎（Koakuma torch backend，默认开启 + 显式开关 + 可退化）**，在无 CUDA 节点由 llama.cpp 承载；任务图仍是临时回退。

| # | 形态 | 适用节点 | 实现载体 | 语义 |
| --- | --- | --- | --- | --- |
| 1 | **llama.cpp 模型分片/RPC（主线）** | PC、Android、CPU/弱 GPU 节点 | 本地 `llama-cpp-python`；分布式 `llama-server`/`ggml-rpc-server`；QLH 分片合同 | **同一 GGUF 的模型级分片**：目标是单节点装不下、各节点只承载部分数据；Silica 提供 Android worker 参考 |
| 2 | **层接力兼容（Relay R）** | 当前仅 PC；L→L 已验证；D→L 主仓矩阵 27/27、跨机 SSH 隧道 141/141 | 裁层 GGUF + hidden handoff + `llama_batch.embd`；独立于旧 `LAYER_FORWARD` | **架构兼容轨道**：验证连续层段可交换 hidden；默认关闭，不进入 Edge 默认路由，不替代 RPC |
| 3 | **PyTorch 层流水线（Koakuma torch backend）** | **有 CUDA 的节点（生产加速）+ PC 对照** | `model_module.py` + `tcp_comm.py` + `qwen3_pipeline_*`/`inference_service` | **CUDA 节点默认开启的加速 backend**（显式开关可关闭并退化为 llama.cpp），同时继续担任正确性/性能/容量对照与 D→L Relay 来源侧；**不进入无 CUDA 节点与边缘默认安装** |
| 4 | **任务图/整请求（临时回退）** | 无法参加模型分片的异构节点 | `task_worker_protocol.py`/`task_provider.py`/`task_chain` | 要求某个节点装下完整模型；只做兼容回退与对照，不代表模型已被分布式拆开 |

### 2.1 身份与可用性的历史方案（人类认证/HA 部分已被取代）

> **2026-10-27 退役裁定**：本节的 TOTP 人类授权、quorum 自动选主、备用主节点、转让/审查要求已由[静态主节点部署与认证退役决策](静态主节点部署与认证退役决策-2026-10-27.md)取代。下表和原方案依据仅保留为历史记录；机器身份的 `cluster_secret`、bootstrap、HMAC 与可信来源检查继续保留，不因退役而取消。

llama.cpp 分片主路径是“跨设备参与同一模型计算”，因此它必须自带**参与资格**与**故障语义**。这两件事**不是可选项**，也不能等到接入生产才补——它们是这层的地基。QLH 侧**已有可用件**，不需要从零造：

| 维度 | 要求 | QLH 已有 / 复用 | 对应票 |
| --- | --- | --- | --- |
| **节点身份（auth）** | 每个 RPC worker 持有可验证身份；入群授权一次性、不可重放 | `src/cluster_join.py`：Ed25519 节点密钥 + 一次性 nonce 消费 + 300s 短 TTL grant + 请求摘要防篡改 | `AUTH-TOTP-01/02` |
| **人类授权（auth）** | 签发 / 转让 / 移除等高危动作必须由人确认一次 | **TOTP 一步确认**：authapp 输入一次 6 位码即视为审核通过，替代原邮件审核与"布尔审批接缝" | `AUTH-TOTP-01/02` |
| **分片租约** | worker 的“我持有哪些模型数据/计算分片”必须是**有时限、可回收**的租约，而非一次性分配 | `src/llama_rpc_contract.py`：lease TTL/renew、单调 epoch、旧提交 fencing；后续接入统一认证摘要 | `CORE-LLAMA-PC-RPC-01` |
| **故障恢复** | worker 掉线 → 重新分配分片；恢复后**不双写** | 心跳 + 重分配（PC/Android 阶段验证） | `CORE-LLAMA-PC-RPC-01` |
| **防脑裂（fencing）** | 备用主节点接管后，旧主**必须立即失效** | **term/epoch + quorum certificate + fencing**（旧主凭据作废） | `HA-CONTRACT-01` → `HA-QUORUM-01` → `HA-FENCE-01` |
| **备用主节点 / 快转让** | 主节点不可用时可接管；安全优先于秒级可用 | **多数派证书自动接管**；单/双节点无 witness 保留 TOTP 快转让或只读；不把 presence lease 当主租约 | `HA-ROLE-AUTO-01` / `HA-HANDOFF-01` |
| **参与资格** | 按**能力标签**判定，不按硬件型号硬编码 | 能力标签 + `votes`/`weight` 分离（MongoDB 副本集模式） | `REVIEW-ROLE-01` |
| **传输保护** | RPC 通道不得裸奔（上游 llama.cpp RPC **未加密**） | 限定内网 / 隧道（Tailscale 等），不新增公网暴露面 | `CORE-LLAMA-PC-RPC-01` |

**与既有文档的关系**：这一节补的是此前缺失的一环 —— 过去只讨论"**能不能拆**"，没写"**拆完谁有资格参与、节点掉了怎么办、主节点挂了谁接管**"。方案与业内对照见[分布式组网审核与可用性重构调研](archive/distributed/分布式组网审核与可用性重构调研-2026-09-15.md)，落地顺序以其中 §4 行动表为准。

## 3. 选型规则（形态怎么挑）

- **输入**：`device_profiler` 画像（显存/内存/算力/平台）+ 节点能力表（能否装 torch、互联带宽）；
- **规则**：
  - 能运行 GGML/RPC 且可证明部分驻留的 PC/Android 节点 → ① llama.cpp 模型分片；
  - **有 CUDA 且画像允许的节点 → ③ Koakuma torch backend（默认开启，可显式关闭并退化为 llama.cpp）**；
  - 无 CUDA 节点（含 Edge）→ ① llama.cpp/GGUF，**去 torch 化**；
  - 能运行 PyTorch 且明确加入 Relay 实验的 PC 节点 → ② Relay 来源侧，必须显式启用并单独记录；
  - 无法参与模型分片但能运行完整模型的节点 → ④ 临时任务图回退；
- **分层决策**：不再由票据固定 `gpu_layers`。RPC planner 消费 `DeviceProfiler.to_dict()` 的 CPU/RAM/GPU/`score_total` 结构，并叠加 CPU 利用率、RTT/带宽、worker budget 和保留内存；画像缺失或 CPU 过载时 fail-closed，CPU worker 默认采用保守上限；显式手工层数只保留作对照实验覆盖。
- **协议纪律**：模型粒度优先使用 llama.cpp 分片合同；Relay 使用独立 hidden handoff 合同；整请求 HTTP/任务协议只作回退；禁止把 Relay 伪装成旧 `LAYER_FORWARD` 或默认生产协议。

## 4. llama.cpp 模型分片攻关与验收顺序

- **G0 断点门**：先做功能裁切/重写后的入口、import、schema、测试、资源和外置子模块合同检查；TUI、模型下载/选择、API、llama 单机入口不能断。
- **G1 单机门**：PC 单进程 llama.cpp 跑通模型舰队代表工件，记录模板/thinking、流式、质量、RSS/PSS、冷启动和吞吐；默认路径不导入 torch。
- **G2 双进程门**：同一台机器启动 **1 个 llama host + 1 个 `ggml-rpc-server` worker**，先用 loopback 验证 RPC。必须证明各进程/后端只持有分配部分，合计可承载单进程装不下的模型；禁止以“两个进程各自加载完整 GGUF”通过。
- **G2-R Relay 门**：在单进程内复跑 L→L 裁层接力；D→L 同机变体按逐 token argmax 对拍（主仓矩阵 27/27 逐 token 一致）。判据使用逐 token argmax/top-k 行为，不把 `embd` bitwise 非确定性误写为错误或一致。跨机 SSH 隧道逐步生成（141/141）、逐 token 生成和采样另列后续门。
  - **D→L 修复顺序（XFRAME 首轮结论，2026-09-16；2026-10-02 更新）**：上游调用方按 `n_pos_per_embd*n_tokens` 修正 `pos` 后，完整模型 token/embedding 控制组与裁层模型 D→L 均已逐 token 一致（主仓矩阵 27/27）；跨机 SSH 隧道逐步生成已通过（141/141）；f32 与采样矩阵留待后续门。
- **G3 PC 真机门**：跨 PC 验证模型身份/摘要、画像驱动分片分配、带 TTL 的租约、epoch fencing、断线重分配、内存收益、正确性和吞吐；RPC 上游未加密，必须限制在内网/隧道。CPU worker 对小模型若慢于本地回退，只记录为容量/故障证据，不得宣称优化收益。
- **G4 Android 门**：借鉴 Silica 的 `librpc.so`/`ggml-rpc-server`，完成 Android worker 交叉编译、真机接入、热/能耗、断线和安全验证；Android UI 不回流主仓。
- **生产准入**：G0→G2 未通过不得做真机网络实测；G3 未通过不得默认开启 RPC；G4 是 Android 生产路径的必要门。Relay 只在 `CORE-RELAY-01`/`CORE-RELAY-XFRAME-01` 的 PC 明确开关下运行，不阻塞最小发行。所有阶段保留 llama 单机回退和 **CUDA 节点的 torch 加速路径**（默认开启、可关闭并退化）。

## 5. ExecuTorch（主线外研究，记录）

- **触发条件**：安卓侧需要 PyTorch 生态模型，或 GGUF 覆盖不足时评估；
- **已知**：Qwen3 0.6B/1.7B/4B 官方支持、Android AAR、AOT 导出链、性能同量级；代价 = 模型集受限与导出工程量；
- **当前动作**：不进入主线发行或默认运行时；只作为端侧 AOT 研究对照。Android 主线优先走 llama.cpp/GGUF RPC。

## 6. 不变式

1. **引擎层统一命名为 Koakuma（混合推理引擎），内部承载两套 backend**：llama.cpp/GGUF 与 PyTorch/Safetensors。**有 CUDA 的节点保留 torch 能力并默认开启（显式开关，可关闭并退化到 llama.cpp）**；**无 CUDA 节点（含边缘安装）必须去 torch 化**：不得 import torch、不得要求 torch 安装、不得进入边缘默认安装或默认路由。
2. 已有代码、模拟和受控验证不能替代 Android 真机、真实模型、长时和生产网络验收；
3. 任务图是完整模型回退，不等价于模型分片；Relay 是独立的 PC-only 架构兼容攻关，不等价于 RPC，也不进入 Edge 默认路径；llama.cpp 分片适配仍是本项目核心技术攻关。
4. 分布式真机实测前必须完成单机与同机双进程模拟，且功能裁切/重写断点和子模块低耦合门必须先通过。
5. **默认值必须显式且入档**：Relay 默认关闭；CUDA 节点 torch 加速默认开启但可关闭。任何"隐式默认"都不作为验收依据。

- [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)：确认 `--split-mode layer/row/tensor` 的本地 split 语义，以及 tensor 路径的实验性边界。
