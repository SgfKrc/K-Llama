## 1. 主线裁决

QLH 主仓只解决一个问题：**在异构设备上把推理任务可靠地跑起来，并用可复现证据证明内存、时延、吞吐和故障边界**。

### 1.1 复核收口票（2026-09-20）

最近一轮大提交复核发现，主线功能基线已通过全量回归，但认证/来源边界、TOTP 审批、TUI 流式认证、RAG 外置残留和依赖锁仍需收口。修复票统一登记在[已知问题记录](已知问题记录.md)的“2026-09-20 安全与迁移复核修复票”中，当前优先顺序为：

1. `SEC-AUTH-BOUNDARY-01`：统一 `/api` 来源边界，并在强制认证模式保护推理/控制面；保留健康、登录、bootstrap 和节点内部协议例外。**已完成（2026-09-20）**。
2. `SEC-AUTH-SESSION-01`：密码/禁用/角色变更吊销旧会话。**已完成（2026-09-20）**。
3. `SEC-AUTH-JOIN-01`：真实 Auth App/TOTP 接线，移除布尔审批接缝。**已完成（2026-09-20）**。
4. `SEC-TOTP-RATE-01`：按账户与来源隔离 TOTP 失败、锁定与 replay 状态；当前为进程内存边界。**已完成（2026-09-20）**。
5. `SEC-TUI-SSE-AUTH-01`：补齐 TUI SSE Bearer/source 透传。**已完成（2026-09-20）**：SSE 头部构造与 REST 共享 Bearer/log token，真实流式登录回归通过；来源按 TCP peer 判定，不增加可伪造 source 头。
6. `MIG-RAG-HARNESS-01`：完成 RAG 外置后的 harness/docagent 迁移收口。**已完成（2026-09-20）**：harness 基准与 docagent Patchouli 均不再导入主仓 `src.rag_*`；harness 测试条件改为仅检查自身资源，harness 定向 `27 passed`、全量 `476 passed / 3 skipped`，Patchouli `87 passed`。
7. `DEP-LLAMA-LOCK-01`：统一 llama-cpp-python 主环境、Edge、测试和 packaging 锁定。**已完成（2026-09-20）**。
8. `SEC-RELAY-ERROR-01`：Relay 错误对端脱敏，详细异常仅写本地日志。**已完成（2026-09-20）**。

这些票是安全与工程收口，不改变 llama.cpp 分片/RPC 主线、Edge <=1B 本地推理和 TUI 主入口基线；第 1 票已完成，后续票继续按上述顺序推进。

主仓由五个相互约束的部分组成。**引擎层统一命名为 Koakuma（混合推理引擎），内部承载两套 backend**：llama.cpp/GGUF 与 PyTorch/Safetensors；**有 CUDA 的节点保留 torch 能力并默认开启（显式开关，可关闭并退化为 llama.cpp）**，**无 CUDA 节点（含边缘）去 torch 化为硬约束**（2026-09-16 v7 决策）：

| 部分 | 责任 | 是否交付能力 |
| --- | --- | --- |
| **Koakuma · llama.cpp backend（Engine L）** | GGUF/llama.cpp 单机推理、模型分片/RPC、CPU/弱 GPU 路径、KV/缓存和边缘入口 | 是；PC 与边缘版均为生产目标；**无 CUDA 节点的唯一路径** |
| Relay R | hidden-state 层接力兼容合同与验证：先覆盖 llama.cpp→llama.cpp，再验证 PyTorch→llama.cpp | 是架构攻关能力；当前 PC-only、默认关闭，不替代 L/RPC |
| **Koakuma · torch backend（Reference P → D 档）** | PyTorch/Safetensors 层流水线与张量传输 | **有 CUDA 节点：默认开启的加速 backend（可关闭并退化）**；同时继续作正确性/性能/容量对照与 D→L Relay 来源侧；**不进入无 CUDA 节点与边缘安装** |
| Control | 节点、能力画像、调度、租约、任务路由、集群状态和降级 | 是；控制面与数据面同仓但分层 |
| Contracts & evidence | 模型画像、manifest、协议、质量门、性能实验和回归测试 | 是；没有证据的能力不能进入“支持” |

本次基线重排只改变实验轨道和下一票顺序，不撤销 `CORE-LLAMA-PC-RPC-01` 已完成的自动分层、租约和故障治理工作；其性能准入仍按原票继续。Relay 先行是为了把已取得的 L→L 架构证据固化为主仓合同，不能替代 RPC 的部分驻留目标。

**主项目交互入口是 TUI。** 当前统一入口是 `qlh`（无参）/ `qlh chat`（Textual 外壳，9 个功能屏 + 1 个调试兜底屏）；Edge/排障基线与 CI 用**只读薄层** `python src/tui_commands.py <command>`（纯标准库、无 UI 依赖、不启动后端）。`qlh_edge` 提供极简 HTTP 供远程任务和外部壳调用；Web、Android 和图形启动器不是主仓的交付入口。

主仓不再新增下列能力：图像生成/编辑、通用知识库和长期记忆、Web 产品界面、Android 产品界面、安装器/更新器、答辩演示、联网 Fetch、邮件通知和面向用户的运营工作台。这些能力的归属与迁移顺序见支线计划。

## 2. Koakuma 引擎、模型舰队与参考引擎

### 2.1 运行基线

| 角色 | 引擎 | 模型格式 | 目标设备 | 依赖边界 |
| --- | --- | --- | --- | --- |
| **主线 L（llama.cpp backend）** | llama.cpp：本地使用 `llama-cpp-python`，分布式使用 `llama-server`/原生 `ggml-rpc-server` | GGUF | Edge、CPU、集显、普通 PC、Android、**任意无 CUDA 节点** | Edge 默认 <=1B 本地推理；Edge 同时可作 RPC worker 参与更大模型；**默认不装 torch（硬约束）** |
| **D 档（torch backend）** | PyTorch/Transformers | Safetensors 等原生权重 | **有 CUDA 的节点（PC/工作站/CUDA 服务器）** | **默认开启的加速 backend，可显式关闭并退化为 L 档**；同时用于正确性、性能和算法对照；**不进入无 CUDA 节点与边缘安装** |

主线的技术目标是让一个 GGUF 模型在单节点装不下时由 llama.cpp host 与 RPC backend 共同承载，每个节点只保有实际分配的模型数据/计算资源。Edge 节点不是 HTTP-only 客户端：它应在本地用 <=1B 模型独立完成推理，并在资源允许时承担更大模型的分片计算。Silica Cluster 提供 Android 侧实现参考；QLH 必须用实测证明“部分驻留、容量合并、输出正确、可恢复”，不能用整模型复制或任务图 Stage 并行替代。

模型舰队只登记**模型身份、格式、引擎、能力、资源预算、模板和工件摘要**。权重仍由用户选择、下载和持有。用户通过 TUI 的模型列表/画像/选择操作决定使用文本模型或可选多模态模型；QLH 不把某一个视觉模型写成所有设备的必选依赖。

没有本地模型不等于主程序不能启动：正常启动仍进入控制面、TUI 和模型下载工作区，用户可以先从模型舰队选择或下载模型；只有 `--check-only` 这类严格诊断模式才要求本地模型资产存在。无模型时推理请求应明确报告缺失并保持可下载/可选择状态，而不是阻塞进入主程序。

多模态是**可选模型能力**而不是主线产品形态：模型画像必须声明 `vision`、输入格式、上下文预算、内存预算和平台支持；设备没有对应资源时要明确降级到文本模型。主仓保留能证明分布式推理边界所需的多模态协议/运行时，但边缘最小安装不预装多模态大件。

### 2.2 分布式形态排序

| 形态 | 主线归属 | 适用范围 | 当前结论 |
| --- | --- | --- | --- |
| **① llama.cpp 模型分片/RPC** | L 档主线 | PC、Android、CPU/弱 GPU 节点 | **主攻形态**；目标是单机装不下时每节点只承载部分模型，Silica 式 Android worker 纳入攻关 |
| **② 层接力兼容（Relay R）** | L/R 的架构兼容轨道 | 当前仅 PC；Android 不作为 D→L 上游 | 裁层 GGUF + hidden/`embd` 接力已完成同引擎与 D→L 正确性验证；主仓双引擎 qwen2.5 样本 47.501 ms/步、32 步一致；不进入 Edge 默认路由，不替代 RPC |
| **③ Koakuma torch backend（原 Reference P）** | **有 CUDA 节点的默认加速 backend**，兼容对照与 Relay D→L 来源 | **有 CUDA 的节点**（PC/工作站/CUDA 服务器）；**不适用无 CUDA 节点与 Edge** | **默认开启，可显式关闭并退化为 L 档**；对照用途保留 |
| **④ 任务图/整请求分发** | 兼容回退 | 任务级异构协作、临时无法分片的节点 | **迁就型临时方案**；可用于回退和对照，不再作为模型分布式主路线 |

llama.cpp 当前还提供两类与 GGUF 相关的能力，但要分开表述：

- 同一主机的 `--split-mode layer/row/tensor` 和 `--tensor-split` 是本地多设备拆分能力；`tensor` 仍按上游标注保守处理。
- `ggml-rpc-server` + `--rpc` 可以把 GGUF 权重/KV 按设备内存比例放到远端设备，**但上游仍标为 proof-of-concept、fragile、insecure**。QLH 将其作为主线攻关对象，但在准入前必须保持显式开关、隔离网络、模型校验和可回退。
- 外部 [Silica Cluster](https://github.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI) 证明 Android 可以承载 `libllama.so`/`librpc.so` 并接入 `--rpc`；其源码中的 `-ngl`/`--tensor-split` 是 offload/比例 split，不是 QLH 的连续 `layer_range` 协议。QLH 的创新任务是把它升级为可校验的模型分片合同，并先在 PC 单机双进程完成证据闭环。

旧的 PyTorch `LAYER_FORWARD` 协议不直接接收 GGUF，也不因 Relay 试验而扩大为通用张量协议。Relay 使用独立的 hidden handoff 合同：L→L 与 D→L 正确性均已验证，且 `src/llama_engine.py` 已提供 `forward_layers_from_hidden()`，允许上下游都走主仓引擎。qwen2.5-0.5B 的当前主仓双引擎样本为 12+12 层、gen=32、47.501 ms/步且 token 一致；qwen3.5 hybrid 的 **K=8/12/16/20** 在 cache 修复后全部 32/32，且同接口的双主仓端到端矩阵 **27/27 逐 token 一致**。该轨道 PC-only、显式开启，不进入 Edge 默认路径或替代 llama.cpp RPC。**无 CUDA 节点不得依赖 torch**。

Qwen 在 Android 的主路线是 llama.cpp/GGUF；ExecuTorch 保留为独立研究对照，不进入主线发行或默认运行时。多模态仍由模型舰队按设备能力按需选择，不把视觉模型做成边缘必选依赖。

## 3. 边缘版硬基线

边缘版是主线的硬交付约束，不是删减后的宣传名：

| 项目 | 基线 |
| --- | --- |
| 运行档位 | llama.cpp/GGUF；Edge 默认 <=1B 本地推理，CPU 路径永远可用；RPC 分片是 Edge/PC 的正式协作能力 |
| 交互 | Textual 外壳 `qlh`（统一入口，9 个功能屏 + 1 个调试兜底屏）；Edge/CI 用只读薄层 `python src/tui_commands.py <command>`（纯标准库）；最小 HTTP 仅用于状态、健康、推理和任务协议 |
| 依赖 | `llama-cpp-python`/llama.cpp、FastAPI、Uvicorn、psutil、httpx 等最小集合；**边缘/无 CUDA 发行禁止 torch**（有 CUDA 节点由 Koakuma torch backend 提供加速，不适用本条） |
| 环境体积 | venv 目标不超过 300 MB；当前开发测量约 120 MB |
| 冷启动 | 健康检查目标不超过 15 秒；当前开发测量约 0.57 秒 |
| 资源 | 默认选择 <=1B 和 Q4；更大模型通过集群分片按节点能力装载；能力画像必须在加载前检查 RAM、上下文和工件摘要 |
| 可选能力 | 多模态随模型舰队按需选择；没有对应模型或预算时保持 <=1B 文本本地路径可用；节点故障时允许调度绕行到其他分片、完整模型节点或本地小模型；任务图仅作临时回退 |
| 明确排除 | Web/Android UI、图像生成、RAG、邮件/审批、安装器、演示、联网工具和重型实验依赖 |

边缘版可以作为单机产品运行，也可以作为任务池节点加入集群；“边缘”不等于只能被远程调用。主仓必须持续保留一条不依赖 CUDA、torch 或产品壳的可运行路径。

## 4. 角色与依赖纪律

```text
TUI / qlh_edge
        |
        v
Control  ------ task / model / capability contracts ------>  Koakuma · llama.cpp backend
        |                                                    (无 CUDA 节点与 Edge)
        |                                                    Koakuma · torch backend
        |                                                    (有 CUDA 节点，默认开启)
        +------------- shard / lease / fallback -------------+

Reference/对照用途(有 CUDA 节点内) <------ comparison/evidence ------ Control

External shell / Koakumix / Patchouli
        \\------------ HTTP + schemas only ------------> QLH
```

- Control 可以调用 Koakuma；**引擎层不得 import Control**；**调度层不关心节点用哪个 backend**（只依据能力表与合同）。
- TUI 只依赖稳定的 HTTP/协议和模型能力摘要，不读取内部路径、凭据或实验临时文件。
- 产品壳、Koakumix 和 Patchouli 只能通过协议、manifest 或模型工件边界接入，不复制主仓推理实现。
- 实验和质量门中与推理优化直接相关的代码留主仓；演示、报告排版、网络探针和环境编排外置。
