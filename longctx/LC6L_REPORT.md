## 6) 核心判据

**表面现象**：k=8 下 6L−DFlash 从短档 +2.9 点 → 中/长档 +15.3/+14.5 点，像是「优势随上下文放大」。

**但对同长度的 hard 对照只有 +4.1 点**（与短档同量级）。上下文长度几乎相同（1146 vs 1157），差值相差 11 点 → 放大的驱动因素不是「长度」，而是「输出是否能从上下文逐 token 复制」。

**结论**：6L 的 markov head 收益主要来自「预测会重复/结构化的内容」，而不是「长距离语义依赖」。它确实让 6L 在 k=8、mid/long 这类任务上拿到 +15 点，但这是抄写红利，且对 DFlash 同样存在（+28 点），只是 6L 吃得更狠。

**k=2 下没有任何优势**（−0.5 ~ −0.9 点），与 pos0/pos1 接近打平的 per-position 数据一致：markov/confidence head 的价值从 pos2 才开始显现。

## 7) 注意事项

1. **n_predict 必须标注**：同一短档，n=64 时 6L 领先 +0.59，n=256 时落后 −0.94。接受率不可跨 n_predict 比较。
2. **6L 的 base 是 `unsloth/Qwen3.6-35B-A3B-NVFP4`，不是官方 BF16**（target 是官方 BF16 的 Q4_K_M）。本测无法排除「NVFP4 数据分布恰好利于长上下文」这一混杂变量；要干净归因，需 BF16 base 的 6L。
3. **hard 档同时改变了输出语言**（英文→中文），中文 token 的绝对接受率本身偏低（短档 zh 0.63 vs prose 0.69/code 0.84）。因此 hard 的 0.376 不能全部归因于「难抄」；但 6L−DFlash 的相对差从 +15 收缩到 +4，这个收缩方向与语言无关（短档 zh 上 6L 并不落后）。
4. T=0 下重复请求**逐位一致**（hard/mid 重复两次，gen_draft、acc、steps 完全相同），因此单 prompt 间的差异是内容差异、不是采样噪声；但每档只有 1 个 prompt（短档 3 个），不能代表任务分布。
5. 6L 的 GGUF 缺 `sample_from_anchor` / `has_confidence_head` 字段，但日志确认 `sample_from_anchor=true`、布局正常，未影响本次测量。

## 8) 对选型的含义

- **k=8 + 结构化/可复制输出**（JSON 键名、函数签名、表格、文档引用、代码补全）：6L 有实质优势（+15 点 accept，tok/s 也高 10–18%）。
- **k=8 + 自由生成/翻译/解释**：优势回落到 +4 点，接近短上下文水平。
- **k=2**：两者等价（6L 略负），不必为 markov head 付代价。
- 「长上下文让 DSpark 更强的说法」不成立；正确说法是「可抄写内容让 DSpark 更强」。
