A replicated key-value store must keep its data consistent while serving requests from many clients at once. The usual approach is to elect a single leader for each shard, have the leader append every mutation to a durable write-ahead log, and replicate that log to followers before acknowledging the write. This gives linearizable reads and writes as long as the leader is stable. When the leader fails, a follower with the longest log is promoted, and any entries that were never committed are discarded. The hard part is not the election itself but the recovery protocol: every replica must agree on which entries are committed before it accepts new writes, or the system can silently diverge and serve stale or conflicting values to different clients.

To make the decision about commitment explicit, the leader tracks the highest log index that a quorum has acknowledged, and advancement of that index is itself replicated so that followers learn the commit point through the same log. A follower that becomes leader first appends a no-op entry and waits for it to commit; that single round trip tells the new leader everything it needs to know about the old term. This is the trick that makes Raft understandable, and it is also why a read can be served locally only after the leader has confirmed with a quorum that it still holds leadership. Without that confirmation, a deposed leader could answer a read from stale state and violate the consistency guarantee that clients were promised.

Storage engines underneath that log face a related problem: they must keep recent mutations in memory, flush them to disk in a way that is crash-safe, and recover quickly after a power loss. A log-structured merge tree solves this by buffering writes in a sorted in-memory table, flushing full tables to immutable files, and merging those files in the background. Each flush produces a manifest entry that records the file ranges and their sequence numbers. Recovery replays the manifest and the write-ahead log, skipping incomplete flushes. The cost is write amplification: one logical byte can be rewritten several times as it moves from memory to level zero and then down through the levels. Choosing the merge policy is really a choice about which read and write patterns matter most, and a workload of many small updates to a small hot key range behaves very differently from a bulk import that once writes every key.

Point lookups in such a store are accelerated with a compact in-memory index that maps each key to the position of its block in the newest file that might contain it. Bloom filters further reduce the number of files that must be read when a key is absent, which matters for workloads that spend most of their lookups on keys that do not exist. Range scans, by contrast, must merge the key ranges of several files at once, so the read path needs a merge iterator whose cost grows with the number of overlapping tables. This tradeoff explains why compaction strategies often target one workload and degrade gracefully on others rather than trying to be optimal everywhere.

A modern serving system built on top of that storage has a second set of problems that have nothing to do with durability. Requests arrive with wildly different prompt lengths, some tiny and some many thousands of tokens. The model processes prefill in a single forward pass over the prompt, then generates one token at a time, and the two phases stress the hardware differently. Prefill is compute bound and benefits from large batch sizes that keep every core busy. Decoding is memory bound because each generated token requires reading the weight matrices again while the batch stays small. Systems therefore schedule them separately, batching prefill requests together to fill the compute units and interleaving decode steps so that the model weights are read once for several sequences. The scheduler must balance latency for interactive users against throughput for bulk jobs, and that balance changes the moment the prompt exceeds the context window that the cache can hold.

When the context is long, the attention mechanism itself becomes the dominant cost, because every new token attends to every token before it. Caching the key and value tensors of previous tokens avoids recomputation, but the cache must be managed carefully: each sequence owns a contiguous range of slots, evictions must not corrupt another sequence, and a sequence that is restored from a prompt cache must be told exactly which tokens are already present. Getting this bookkeeping wrong produces the most confusing failures in the system, where the model answers as if it had read a different prompt, and the bug appears only when two requests overlap in the cache.

Speculative decoding attacks a different bottleneck: a small draft model proposes several tokens, and the large target model verifies all of them in one pass, accepting the longest prefix that matches its own greedy choices. When the draft is accurate the target model produces several tokens per forward pass, which is a large win; when it is inaccurate the system pays for the rejected proposals. The acceptance rate depends on the draft and the target sharing a distribution, and it falls quickly with the number of tokens drafted, so the number must be tuned per model pair. A draft that is merely a layer slice of the target shares its vocabulary and embeddings exactly, which keeps the acceptance rate high even for a single draft position, but it cannot anticipate the target's future choices as well as a separately trained model does.

Expert mixtures complicate all of this. Each token is routed to a small number of experts out of many, so the compute per token is low but the memory traffic is high, and the router must balance load across experts or a few of them become hot and slow the whole batch down. Expert parallelism adds one more dimension to the scheduling problem, since a token's hidden state may have to cross the network before its expert can process it. Quantization reduces the memory footprint of the weights, which is essential when a model is larger than the available accelerator memory, but it also changes the hidden state distribution slightly, and any draft model attached to a quantized target inherits that shift. The acceptance rate is therefore not an intrinsic property of the draft alone; it always refers to a specific target, quantization, and set of prompts, and comparing numbers across those boundaries produces misleading conclusions.

Caching and consistency interact in the serving layer as well. When several workers share a cache, a request routed to a different worker must either find the cached prompt state on that worker or recompute it, and the routing decision must account for how expensive recomputation would be. Sticky routing by prompt prefix helps, but it creates hotspots and makes failover worse. The usual compromise is to replicate the hottest prefixes to a few workers and let the rest recompute, accepting a small delay for the cold fraction of traffic. All of these choices are visible in the tail latency numbers, which is why a system that looks simple in a diagram becomes a collection of approximate policies in production.

Operators watching such a system care about a few dozen signals. Queue depth shows whether the scheduler is saturated. Time to first token shows the speed of prefill. Inter-token latency shows the speed of decode. Cache hit rate shows how much work is being repeated. Rejection rate shows whether speculative decoding is helping. No single number proves that the system is healthy, because a fast decode with a long prefill can be worse for users than a slow decode with a short prefill. The right way to evaluate a change is to measure the workload that actually runs, on the hardware that actually serves it, and to keep the old numbers so that a regression can be attributed to the code and not to the environment.
